### deploy/scripts/install.sh

#### [SWALLOWED_ERROR] jq's own failure text is discarded in `read_descriptor_field`
- Location: line 356
- Issue: `value="$(jq -r "$jq_path // empty" "$descriptor" </dev/null 2>/dev/null)"` throws jq's stderr away, and the error that replaces it always claims the file "could not be parsed as JSON" regardless of the real cause (invalid filter, jq I/O failure, truncated write while Exasol Personal is still starting). Every other external-command failure in this script does the opposite — `push_slc_to_vm` reports "scp said: $out", `ssh_vm_reachable` reports "ssh said: $out", `saas_upload_file` reports "curl said: ...". The operator debugging a half-written `deployment.json` gets no diagnostic.
- Fix: In `deploy/scripts/install.sh` `read_descriptor_field` (line 356), capture jq's stderr instead of discarding it — change the redirect to `2>&1` into a local variable (e.g. `jq_err`) using the same capture shape as `push_slc_to_vm`, and append `jq said: $jq_err` to the existing error message.

#### [INFORMATION_LEAKAGE] `download_engine` re-declares the engine asset base name that `ENGINE_ASSET` already owns
- Location: line 1347
- Issue: `asset="lakehouse-engine$suffix.tar.gz"` hardcodes the literal `lakehouse-engine`, but `ENGINE_ASSET="lakehouse-engine.tar.gz"` (line 25) already owns that naming decision — and the very next line compares `"$asset" != "$ENGINE_ASSET"`. The release-asset base name now has two homes in one file; renaming the release asset requires editing both, and a mismatch would silently break the `mv` guard rather than fail loudly.
- Fix: In `deploy/scripts/install.sh` `download_engine` (line 1347), replace `asset="lakehouse-engine$suffix.tar.gz"` with `asset="${ENGINE_ASSET%.tar.gz}$suffix.tar.gz"` so `ENGINE_ASSET` remains the single owner of the base name.

#### [SENTINEL_ERROR_VALUE] `detect_host_arch` returns `x86_64` as a stand-in for "could not detect"
- Location: lines 866-873
- Issue: `machine="$(uname -m 2>/dev/null)"` followed by `*) printf '%s\n' "x86_64"` makes `x86_64` the answer for every input that is not `arm64`/`aarch64` — including an empty string when `uname` is missing or fails, and any unrecognized machine type. `--arch` in `parse_args` (lines 586-593) is strict and rejects anything outside `x86_64|aarch64` with a message naming the valid values; the auto-detect path that replaces it silently guesses instead. The failure is deferred and opaque: a wrong-architecture `.so` installs cleanly and only surfaces later as a UDF load failure inside Exasol, with nothing pointing back at the detection step.
- Fix: In `deploy/scripts/install.sh` `detect_host_arch` (lines 866-873), make the fallback an error rather than a value: keep `arm64|aarch64` → `aarch64`, add an explicit `x86_64|amd64` → `x86_64` case, and in the `*)` case call `err` naming the raw `uname -m` output and instructing the operator to pass `--arch x86_64|aarch64` explicitly, then `return 1`. Propagate that failure in `resolve_deployment_transport` (line 738) with `ARG_ARCH="$(detect_host_arch)" || return 1`. Add a test in `deploy/scripts/tests/install.test.sh` next to `deployment_local_autodetects_arch` that stubs `uname -m` to an unsupported value (e.g. `ppc64le`) and asserts a nonzero exit whose message names both the detected value and the `--arch` flag.

#### [TACTICAL_SHORTCUT] Unvalidated `ARG_BFS_BUCKET` is interpolated into a remote `rm -rf`
- Location: line 1161 (guard at line 725)
- Issue: `push_slc_to_vm` builds a remote shell command by string interpolation — `ssh_vm "set -e; rm -rf '$dest'; mkdir -p '$dest'; ..."` — where `$dest` comes from `vm_bucket_dir()` and therefore from the operator-supplied `--bfs-bucket`. The only guard on that value (line 725) checks it is non-empty. A bucket value containing a single quote closes the quoting and the remainder is executed as shell on the VM, in front of an `rm -rf`. This is the one operator-controlled component of a destructive remote command and it is passed through raw.
- Fix: In `deploy/scripts/install.sh` `resolve_deployment_transport`, replace the empty-string check at line 725 with a character-class validation — `if [[ ! "$ARG_BFS_BUCKET" =~ ^[A-Za-z0-9._-]+$ ]]` — and make the error message name the rejected value and the allowed character set alongside the existing explanation of what the bucket names. Add a test in `deploy/scripts/tests/install.test.sh` in the `--deployment transport selection` group asserting that a `--bfs-bucket` value containing a single quote is rejected with a nonzero exit before any transport is selected.

#### [TACTICAL_SHORTCUT] A fixed 3-second sleep is the only synchronization before the DDL runs
- Location: line 54 (`VM_RECONCILE_SECONDS=3`), lines 1440-1441
- Issue: `deploy_personal_local` writes files into the VM's BucketFS directory over SSH and then waits a fixed 3 seconds for the database to reconcile them before `register_script_languages` and `create_engine_scripts` run. Nothing verifies the reconciliation happened. This script already owns the correct shape for exactly this problem in the HTTP path — `bucketfs_wait_for_path` is a bounded poll with an explicit timeout and an actionable failure message, and `register_slc` calls it for precisely this reason (line 1373: "SaaS verifies synchronously inside saas_upload_file; BucketFS needs the bounded wait"). The SSH path silently drops that discipline. On a cold or loaded Personal VM 3 seconds is a guess: when it is short the failure surfaces later as an opaque DDL or smoke-test error with no pointer back to reconciliation, and when it is long every install pays 3 seconds it did not need. The constant is named, so this is not a magic number — it is a verification step replaced by a hope.
- Fix: In `deploy/scripts/install.sh`, replace the unconditional `sleep` at lines 1440-1441 with a bounded, verified wait modelled on `bucketfs_wait_for_path`: add a `vm_wait_for_reconciled_path` function that polls over `ssh_vm` for the presence of the engine `.so` and the extracted SLC tree at their `vm_bucket_dir` destinations, with a deadline expressed as a named constant replacing `VM_RECONCILE_SECONDS`, and fails with an error naming both the polled paths and the elapsed timeout when the deadline passes. Add a test in `deploy/scripts/tests/install.test.sh` (on the `ssh` stub introduced by the coverage finding above) covering both the eventually-appears case and the never-appears timeout case, mirroring `test_bucketfs_verify_listed_and_wait` (line 1440).

### Makefile

#### [INFORMATION_LEAKAGE] The arch-suffix naming rule now has two homes that disagree on `arm64`
- Location: `Makefile` lines 128-134; `deploy/scripts/install.sh` lines 858-873
- Issue: the "unsuffixed x86_64, `-aarch64` suffixed aarch64" convention is decided independently in two places. `install.sh` decides it in `resolve_arch_suffix` behind a validated `--arch` (only `x86_64|aarch64` reach it) and normalizes the Apple Silicon spelling in `detect_host_arch` (`arm64` → `aarch64`). The Makefile decides it with `ifeq ($(ARCH),x86_64) ... else SLC_ARCH_SUFFIX := -$(ARCH)`, which validates nothing and normalizes nothing. Measured: `make -n install-slc ARCH=arm64` → `lc-rust-0.22.1-arm64.tar.gz`, and `make -n install-slc ARCH=totally-bogus` → `lc-rust-0.22.1-totally-bogus.tar.gz`. `arm64` is not a hypothetical typo — it is exactly what `uname -m` prints on the Apple Silicon machines this plan targets, and the value `install.sh` goes out of its way to normalize away. A developer who types it gets a silent 404 from a URL that looks plausible, with nothing naming `ARCH` as the cause. Separately, the plan's Verification table specifies a `makefile_slc_url_arch_aware` test in `deploy/scripts/tests/install.test.sh`; `grep -n 'makefile' deploy/scripts/tests/install.test.sh` returns nothing, so the Makefile's URL composition ships untested and this divergence had nothing to catch it.
- Fix: In `Makefile` around lines 128-134, make `ARCH` validated and normalized to match `install.sh`: map `arm64` to `aarch64` before computing the suffix, and for any value other than `x86_64`/`aarch64` (post-normalization) raise `$(error ...)` naming the rejected `ARCH` value and the two accepted values, using the same wording as `install.sh`'s `--arch` rejection at line 590. Then add the plan-mandated `makefile_slc_url_arch_aware` test to `deploy/scripts/tests/install.test.sh`, registered in `main()`, asserting via `make -n install-slc` (or `make -pn`) that `ARCH` unset and `ARCH=x86_64` both yield the unsuffixed `lc-rust-<v>.tar.gz` URL, that `ARCH=aarch64` and `ARCH=arm64` both yield `lc-rust-<v>-aarch64.tar.gz`, and that an invalid `ARCH` exits nonzero with a message naming the value.

### .github/workflows/ci.yml

#### [TACTICAL_SHORTCUT] The aarch64 tarball is released without the arm64 test job gating it
- Location: line 347 (`arm64` job), line 921 (`release` `needs:`)
- Issue: `release`'s `needs:` list is `[e2e, e2e-lakekeeper, e2e-unity, lint, unit-tests, licenses, install-script, install-script-e2e]`. The new `arm64` job is absent, so a red `cargo test --workspace` on aarch64 does not stop the release job from attaching `lakehouse-engine-aarch64.tar.gz` to the GitHub Release. The x86_64 counterpart, `unit-tests`, is in the list — so this PR ships a second architecture with strictly weaker gating than the first, and `arm64` is the only architecture-specific test signal that exists at all (aarch64 E2E is a deliberate plan Non-Goal, which makes the unit-test job the whole safety net rather than a supplement). The `.so` build itself is gated transitively — `e2e` needs `build-so`, and a matrix `needs` waits on both legs with `fail-fast: false` — so the artifact will always exist; only its test signal is ungated. This needs judgment rather than a reflex edit: the comment immediately above line 921 documents that `e2e-azure` is *deliberately* excluded so a third-party outage cannot block every release. `arm64` is not in that class — it is a GitHub-hosted runner running the same `cargo test` as `unit-tests`, with the same reliability profile — but the decision and its reasoning should be made explicitly and recorded where the existing exclusion rationale lives.
- Fix: In `.github/workflows/ci.yml`, add `arm64` to the `release` job's `needs:` list at line 921 so a failing aarch64 unit-test run blocks the release, and extend the existing rationale comment block above that line to state that `arm64` gates the release (unlike `e2e-azure`) because it is a GitHub-hosted runner with no third-party dependency and is the only architecture-specific signal covering the `lakehouse-engine-aarch64.tar.gz` asset. Record the decision in `specs/_plans/add-aarch64-build-and-personal-install/decision-log.md`. This comment is a deliberate exception to this PR's no-new-comments rule — it extends the pre-existing `needs:` rationale block that already explains the `e2e-azure` exclusion, and leaving the new gate unexplained beside a documented non-gate would invite a future reader to "fix" it by removal.
