## Summary
- Axes checked: 6/6

## Premortem

Three ways this plan fails after approval:

1. **The build breaks on task 1.1 and the spec forbids the fix.** Adding the second variant turns five irrefutable `let StorageBackend::S3(..)` bindings and one single-arm `match` into compile errors. The plan lists none of them, and its own characterization clause permits exactly one class of test edit. The implementer either stalls or edits the gate that is supposed to prove S3 is unchanged, unreviewed.
2. **An Azure account key reaches an Exasol user.** A manifest-read failure on the ADLS `FileIO` path is redacted by `redact_credentials` alone — a label list with no Azure label in it. Three spec clauses forbid this outcome; no task makes any of them true.
3. **A sovereign-cloud or private-endpoint Azure deployment fails at `build()` and the spec says it should not.** `MicrosoftAzureBuilder::parse_url` accepts only four host suffixes; the spec asserts the verbatim pass-through leaves other endpoints unbroken.

#### [UNSTATED_ASSUMPTION] BLOCKER

- Location: `vs-adapter/storage-backend-enum/spec.md:52`
- Issue: The clause reads "SHALL pass the account host through VERBATIM rather than reconstructing `<account>.dfs.core.windows.net`, **so a non-`core.windows.net` Azure endpoint is neither special-cased nor broken**". The trailing claim is false against the resolved dependency. `object_store-0.13.2/src/azure/builder.rs:668-680` matches the host against exactly four suffixes — `dfs.core.windows.net`, `blob.core.windows.net`, `dfs.fabric.microsoft.com`, `blob.fabric.microsoft.com` — and returns `Error::UrlNotRecognised` for anything else. A sovereign-cloud host (`*.dfs.core.chinacloudapi.cn`), a private endpoint, or any other Azure-compatible host therefore fails at `build()`, not silently but definitely broken. A test written from this clause fails.
- Fix: In `vs-adapter/storage-backend-enum/spec.md:52`, delete the "neither special-cased nor broken" claim and replace it with the verified behaviour: the arm passes the host verbatim because reconstruction would be wrong, AND `MicrosoftAzureBuilder` accepts only the four host suffixes listed at `object_store-0.13.2/src/azure/builder.rs:668-680`, so any other host surfaces a redacted `UrlNotRecognised` build error. Add a matching Background bullet naming the four suffixes, and either add a scenario clause pinning that error path (redacted, naming no value) or record the restriction as a scoped limitation with a tracking issue per CLAUDE.md's tracked-exception rule.

## Requirement Quality

#### [COMPLETENESS_GAP] BLOCKER

- Location: `vs-adapter/storage-backend-enum/spec.md:51`; `plan.md` § Implementation Tasks 3.1
- Issue: The clause scopes the equivalence guarantee to `s3://` only — "the `Url` that derivation returns **for an `s3://` file list** MUST equal the value the deleted function's caller produced". `s3a://` is a documented, reachable production input on this exact path: `crates/lakehouse-engine/src/scan/spec.rs:445` and `:730` both say a `FileEntry.path` is "an absolute URI (S3 **or s3a**)", and `crates/lakehouse-engine/tests/e2e_int96_timestamp_test.rs:128-130` handles both. For an `s3a://` file list the deleted function produced `Url::parse("s3://bucket")` (scheme rewritten to `s3` by `format!`), while `side_store_url` returns `s3a://bucket`. That is a silent registered-key change on the very path the plan promises is unchanged, and it is neither specified nor tested. The plan's central risk control — "Adding the Azure backend leaves the S3 path unchanged" — has a documented input it does not cover.
- Fix: In `vs-adapter/storage-backend-enum/spec.md:51`, restate the clause over every scheme `crates/lakehouse-engine/src/scan/spec.rs:445` documents (`s3://` and `s3a://`), and state explicitly which key each yields after the change and whether the `s3a://` change is intended. Add a scenario clause pinning the `s3a://` outcome, a task-mapped test name to § Verification § Scenario Coverage, and — if the `s3a://` key genuinely changes — a line in `plan.md` § Impact declaring it.

#### [UNSTATED_ASSUMPTION] ADVISORY

- Location: `vs-adapter/storage-backend-enum/spec.md:14` and `:36`
- Issue: The two clauses contradict each other. `:36` requires `catalog_storage_props` to emit `ADLS_ACCOUNT_NAME` "**when `account_name` is non-empty**", while `:14` claims "Because `validate_creds` requires `account_name` for every Azure CONNECTION, the key is always present and **the guard is always armed**". `Adls { account_name: String }` is a bare `String` on a deserialized wire type; a scan spec reaching the UDF with an empty `account_name` (a hand-built spec, or a future slice-D merge) emits no key and disarms `iceberg-storage-opendal`'s wrong-account check at `azdls.rs:163-170` — silently, which is the failure mode the bullet exists to prevent.
- Fix: In `vs-adapter/storage-backend-enum/spec.md:36`, make `ADLS_ACCOUNT_NAME` emission unconditional so the guard cannot be disarmed by an empty payload, and delete the "when `account_name` is non-empty" condition; or, if conditional emission is intended, strike "the guard is always armed" from `:14` and state the empty-account-name behaviour explicitly.

#### [COMPLETENESS_GAP] ADVISORY

- Location: `decision-log.md` § Design Decisions `[9]`; `vs-adapter/connection-credentials/spec.md:47`
- Issue: Decision `[9]` makes `storage_block` total by falling through to S3 when an Azure account name or credential is missing. That behaviour appears nowhere in a spec delta, and the closest spec clause reads the other way: `connection-credentials/spec.md:47` says "the adapter MUST NOT fall back to the S3 backend for any of the three shapes". `storage_block` is `pub` (`crates/lakehouse-engine/src/adapter/connection.rs:180`), so its contract is observable independently of `read_connection`. An implementer reading only the spec would write a `Result` or a panic.
- Fix: Add one clause to the `vs-adapter/connection-credentials` delta's "Azure account-key credentials select the ADLS storage backend" scenario stating that `storage_block` is total — it returns the S3 variant for a `ConnectionCreds` that names no complete Azure credential set, never panicking, because a panic inside a UDF triggers the engine's SIGKILL fan-out — and cross-reference the `MUST NOT fall back` clause at `:47` as applying to `read_connection`'s result, not to `storage_block` in isolation.

#### [NFR_IGNORED] ADVISORY

#### [COMPLETENESS_GAP] ADVISORY

- Location: `plan.md` § Implementation Tasks 4.3; `vs-adapter/storage-backend-enum/spec.md:56`
- Issue: The plan adds a test "two sides in different accounts both register" without pinning what those two stores share. `build_session_context` hands **one whole-spec size index** to every registered store (`crates/lakehouse-engine/src/scan/object_store.rs:60-65`), keyed by `ListingTableUrl::prefix()` — which for `abfss://` excludes the container and for `s3://` excludes the bucket. Two sides in different accounts whose relative paths collide resolve one entry for both, returning a wrong `ObjectMeta.size` and a truncated or over-long Parquet read. Pre-existing for two S3 buckets, but this plan is what first asserts the two-account case is supported and tested.
- Fix: Add one clause to the "The scan registers its object store without naming the backend" scenario stating whether colliding container-relative paths across two registered stores are in or out of contract, and extend the task 4.3 test `register_side_store_registers_both_sides_in_different_accounts` to assert the size-index outcome for a colliding relative path — or record the collision as a tracked exception with an issue number.
