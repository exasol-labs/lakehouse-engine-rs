## Premortem

Three failure stories, each routed into the taxonomy below.

1. **The feature ships and a customer's first table comes back as text.** A Spark-written directory
   carries `INT64 TIMESTAMP(MILLIS)` and `INT(8, true)` columns. `arrow_type_to_tag` has no entry for
   `Timestamp(Millisecond, _)` or `Int8`, so it returns `"utf8"` for both. The declaration says
   `VARCHAR(2000000)` and the scan registers `Utf8`. No error fires anywhere. Routed to
   `[UNSTATED_ASSUMPTION]` below.
2. **A 400k-file directory hangs a `CREATE VIRTUAL SCHEMA`, and the recorded exception points at the
   wrong issue.** The plan records the missing file-count limit against issue #409, which tracks
   Unity Catalog PARQUET-table routing. Nobody finds the gap in the tracker. Routed to
   `[COMPLETENESS_GAP]` below.
3. **A two-table join over direct-storage tables fails in production and no test caught it.** The
   issue asked for a join and a GROUP BY in the parity smoke test. The plan ships projection, filter,
   LIMIT, and a single-group aggregate. The join path is the one the plan changed most, through
   concurrent leg resolution and seam-based broadcast sizing. Routed to `[SCOPE_REDUCTION]` below.

## Intent Fidelity

#### [SCOPE_REDUCTION] BLOCKER
- Location: `specs/_plans/add-direct-storage-catalog-kind/e2e-harness/direct-storage-e2e-properties/spec.md` § Scenario: Projection, filter, and LIMIT reach the direct-storage scan
- Issue: issue #407 specifies the parity smoke test as "projection + filter + LIMIT + GROUP BY + a two-table join over direct-storage tables, confirming the format-neutral paths do not care which reader produced the spec". The scenario covers projection, filter, LIMIT, and "a single-group aggregate over the same table". GROUP BY and the two-table join are absent from this spec, from every other delta, and from tasks 6.3 and 6.4. The join case is the one this plan reshapes hardest: decision-log entry [14] makes join-leg resolution concurrent because a direct-storage leg reads footers at plan time, and `vs-adapter/direct-storage-table-planning` adds a clause requiring each broadcast side to size itself from the seam's listing. Both land with no live proof over this kind.
- Fix: Add two clauses to the `Projection, filter, and LIMIT reach the direct-storage scan` scenario in `e2e-harness/direct-storage-e2e-properties/spec.md`: one requiring a `GROUP BY` aggregate over a direct-storage table to return the same answer the equivalent unpushed query returns, and one requiring a two-table inner equi-join over two direct-storage tables to return the correct rows with both legs resolved through the one shared admission-limited store. Add the matching rows to `plan.md` § Scenario Coverage with test names in `crates/lakehouse-engine/tests/e2e_direct_storage_test.rs`, and name both tests in task 6.4.
- Escalation: HUMAN. The dropped coverage is part of the scope contract the requester supplied, and reinstating it widens an E2E binary the requester sized. Only the requester settles whether the join and GROUP BY cases ship here or move to a follow-up.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `specs/_plans/add-direct-storage-catalog-kind/vs-adapter/direct-storage-table-discovery/spec.md` § Scenario: A table's columns and data files come from the one shared directory seam, and `datafusion-scan/type-mapping/spec.md` § Scenario: A Parquet-sourced column maps through the Arrow-input direction
- Issue: the plan rests on a lossless round trip that the codebase refutes. The discovery delta states "the client SHALL apply the string substitution for a nested or unrepresentable column BEFORE it renders that tag, so every tag it emits names a type the vocabulary can express and the round trip back to an Arrow type is lossless". The vocabulary is `arrow_type_to_tag` / `arrow_type_from_tag` in `crates/lakehouse-engine/src/types/mapping.rs` lines 425 to 486. It covers exactly `bool`, `int32`, `int64`, `float32`, `float64`, `utf8`, `date32`, `timestamp_us`, `timestamp_ns`, `timestamptz_us`, `timestamptz_ns`, and `decimal128(p,s)`. Its own doc comment scopes it: "The tag vocabulary covers every type reachable from `iceberg_type_to_arrow`". The Arrow-input classifier `compatible_exasol_type` (same file, lines 47 to 80) admits a strictly larger set and returns a non-VARCHAR Exasol type for `Int8`, `Int16`, `UInt8`, `UInt16`, `UInt32`, `UInt64`, `LargeUtf8`, and `Timestamp(TimeUnit::Millisecond, _)`. None of those is "nested or unrepresentable", so the string substitution never fires for them. `arrow_type_to_tag` falls through to `"utf8"` for every one. A Parquet `INT64 TIMESTAMP(MILLIS)` column, which is a common Spark output, is therefore declared `VARCHAR(2000000)`, and `build_logical_arrow_schema` (`crates/lakehouse-engine/src/scan/field_id_projection.rs` line 1017) registers it as `Utf8`. The `datafusion-scan/type-mapping` delta's "an unparseable tag SHALL resolve to `VARCHAR(2000000)`" clause never fires either, because no unparseable tag is produced. The failure is silent. No delta in this plan widens the tag vocabulary, and the recorded `datafusion-scan/scan-execution-field-id-projection` spec pins the vocabulary as primitive-only at line 42 and enumerates it in a scenario GIVEN at line 224, so widening it needs a delta this plan does not carry.
- Fix: Add a DELTA:CHANGED block to `specs/_plans/add-direct-storage-catalog-kind/datafusion-scan/type-mapping/spec.md` requiring the scan-spec tag vocabulary to carry one entry for every Arrow type `compatible_exasol_type` admits, naming `Int8`, `Int16`, `UInt8`, `UInt16`, `UInt32`, `UInt64`, `LargeUtf8`, and `Timestamp` at every `TimeUnit`, and requiring `arrow_type_to_tag` and `arrow_type_from_tag` to round-trip each one. Add a matching DELTA:CHANGED block to `specs/_plans/add-direct-storage-catalog-kind/datafusion-scan/scan-execution-field-id-projection/spec.md` superseding the recorded primitive-only enumeration at its line 42 and the tag list in its round-trip scenario GIVEN. Add a clause to `vs-adapter/direct-storage-table-discovery/spec.md` § A table's columns and data files come from the one shared directory seam requiring that a folded Arrow type the vocabulary cannot express fail the enumeration with an error naming the column and the type, rather than silently tagging `utf8`. Add task 3.5 to `plan.md` § Implementation Tasks covering the vocabulary extension and its round-trip test, and add the scenario rows to § Scenario Coverage.
- Escalation: MECHANICAL. The codebase settles the fact, and the fix is a spec edit plus one task.

## Requirement Quality

#### [COMPLETENESS_GAP] BLOCKER
- Location: `specs/_plans/add-direct-storage-catalog-kind/plan.md` § Design Non-Goals (lines 30 to 32), and `decision-log.md` § [16]
- Issue: three of the four tracked-exception citations are wrong, and one gap has no tracking issue at all. `plan.md` reads "a file-count or file-size safety limit (#409) ... non-Parquet file formats (#410)", and decision [16] repeats both. The real issues are #409 "feat(vs-adapter): route Unity Catalog PARQUET tables to the Parquet reader" and #410 "feat(vs-adapter): read non-Iceberg Glue tables", verified through `gh api repos/:owner/:repo/issues/409` and `/410`. A search of every open issue in the repository finds no issue tracking a file-count or file-size safety limit. CLAUDE.md requires a known gap to be "an explicit, accurately-scoped tracked exception". The unbounded plan-time footer read is the plan's largest operational risk, it is recorded against an issue that tracks something else, and issue #407's two real out-of-scope items, Unity PARQUET tables and Glue Hive tables, are absent from the plan under their true meaning.
- Fix: In `plan.md` § Design Non-Goals and in `decision-log.md` § [16], correct the citations to read "Unity Catalog PARQUET-table routing (#409)" and "non-Iceberg Glue tables (#410)". Remove the file-count and file-size safety limit from the tracked-exception list, and instead state it as an untracked gap whose tracking issue must be opened before merge, naming it in `plan.md` § Impact beside the existing plan-time footer cost caution. Add a clause to `vs-adapter/direct-storage-table-planning/spec.md` § Every plan-time footer is read and the resulting cost is stated recording the absence of any file-count or file-size bound as an explicit exception, with the new issue number cited inline once it exists.
- Escalation: MECHANICAL. The issue tracker settles the citations, and the fix is a text correction plus one recorded exception.

#### [COMPLETENESS_GAP] BLOCKER
- Location: `specs/_plans/add-direct-storage-catalog-kind/vs-adapter/direct-storage-table-discovery/spec.md` § Scenario: The direct-storage client is a boxed catalog client declared in the engine crate
- Issue: `CatalogClient` (`crates/lakehouse-catalog/src/client.rs` lines 134 to 147) declares two required methods, `list_tables` and `load_table`. The scenario states "the adapter reaches both trait operations through the trait exactly as it does for the other two kinds". That is false twice over. `load_table` has exactly one caller in the engine, `crates/lakehouse-engine/src/adapter/pushdown/scan_resolution.rs` line 131, on the Unity Catalog path alone, so the Iceberg kind does not reach it either. For direct storage `vs-adapter/direct-storage-table-planning` states the opposite in its own scenario, "the direct-storage variant SHALL carry NO catalog table metadata, because this kind loads no table". No scenario and no task in § Implementation Tasks says what `DirectStorageCatalogClient::load_table` returns, yet the trait forces an implementation. The two deltas contradict each other and neither answers the question an implementer must answer.
- Fix: Replace the "reaches both trait operations" clause in `vs-adapter/direct-storage-table-discovery/spec.md` with a clause stating that the adapter reaches this client's enumeration through `list_tables` exactly as it does for the other two kinds, and that `load_table` is unreachable for this kind because the pushdown path resolves a direct-storage table from its composed root rather than from a catalog load. Add a further clause requiring `load_table` to return a clear `UdfError` naming the kind and stating that a direct-storage table is not loaded through the catalog trait, so a future caller meets an error rather than a panic or an empty table. Name that behaviour in task 4.2 and add a unit-test row to `plan.md` § Scenario Coverage in `adapter/direct_storage_tests.rs`.
- Escalation: MECHANICAL. The trait declaration and the single call site settle it.

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: `specs/_plans/add-direct-storage-catalog-kind/vs-adapter/parquet-directory-seam/spec.md` § Scenario: One seam answers the file list and the schema for both callers, and § Scenario: The merge mode selects every footer or exactly one
- Issue: the seam's return contract is unspecified in one of its two modes, so no pass or fail test can be written for it. Scenario one states unconditionally that the seam returns "each file's parsed Parquet metadata" and that "the returned per-file metadata SHALL be the PARSED footer rather than the schema alone, so a later consumer that prunes files from footer statistics re-reads no footer". Scenario four states that the sample-one-file mode "SHALL read EXACTLY ONE footer" while returning the same file list. Under that mode the seam holds metadata for one file and a list of N files. The spec never says what the metadata side of the return looks like then, whether it is a shorter sequence, a per-file option, or a keyed map, and the forward-compatibility promise issue #407 makes load-bearing ("must not re-read a single footer") cannot hold in that mode at all. Task 2.5 restates the promise without resolving the shape.
- Fix: Add a clause to `vs-adapter/parquet-directory-seam/spec.md` § The merge mode selects every footer or exactly one stating that the returned per-file metadata is paired with the files whose footers the mode read, and is ABSENT for every other listed file, so a consumer reads presence rather than assuming one entry per file. Amend the forward-compatibility clause in § One seam answers the file list and the schema for both callers to scope its promise to the fold-every-file mode, and to state that a consumer needing statistics under the sample-one-file mode asks the seam for them rather than re-reading footers behind its back. Restate task 2.5 to name the paired-and-absent shape.
- Escalation: MECHANICAL. The plan's own two scenarios settle the conflict once the shape is stated.

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `specs/_plans/add-direct-storage-catalog-kind/datafusion-scan/type-relaxation/spec.md` § Background
- Issue: the delta claims "The read behaviour, the cast mechanism, the supported-set table, and both format conformance arguments are unchanged". The read behaviour does change. The recorded `specs/datafusion-scan/type-relaxation/spec.md` lines 66 to 72 state "The two cast sites carry OPPOSITE overflow policies, and only the widening direction makes that safe ... Every pair in the supported set is a WIDENING, so no value can overflow either site, and the asymmetry is unreachable from this feature." `MERGE_SCHEMA = 'FALSE'` makes the narrowing direction reachable for the first time: the declaration carries the sampled footer's narrow type while a later file's physical column is wider, so the delegated `DefaultPhysicalExprAdapter` inserts a NARROWING cast. The plan states the consequence twice, in decision-log entry [8] and in `e2e-harness/direct-storage-e2e/spec.md` § Background, but no delta supersedes the recorded clause that says the overflow asymmetry is unreachable. A reader of the merged library meets two contradictory statements.
- Fix: Add a Background bullet to `specs/_plans/add-direct-storage-catalog-kind/datafusion-scan/type-relaxation/spec.md` superseding the recorded "the asymmetry is unreachable from this feature" sentence, and stating that the direct-storage `MERGE_SCHEMA = 'FALSE'` mode makes the read-side `safe: false` cast reachable in the narrowing direction, where it returns a clean error rather than a wrong value. Correct the opening bullet's claim that the read behaviour is unchanged to name that one addition. State that the emit boundary's `safe: true` policy stays unreachable, because the read-side cast fails before any overflowing value reaches it.
- Escalation: MECHANICAL. The recorded spec and the plan's own artifacts settle it.

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: `specs/_plans/add-direct-storage-catalog-kind/datafusion-scan/type-relaxation/spec.md` § Scenario: The supported pair set answers a plan-time widening question from one production owner
- Issue: the scenario requires two things that cannot both hold. It requires "exactly ONE production item SHALL answer, taking the two Arrow types and returning the WIDER one", and it requires "the existing test list `supported_relaxation_pairs` SHALL be derived from it rather than restating it". A function of shape `fn(&DataType, &DataType) -> Option<DataType>` cannot be enumerated, so no list derives from it. The set is also rule-based rather than finite: rows 9 to 12 of the recorded table are parameterized, and the scenario itself requires evaluation "over the CONCRETE types rather than over row names". A parameterized rule yields no representative pair to derive. Worse, if the list were derived from the oracle, the recorded suite's own guarantee collapses: `arrow_castability_pins_every_supported_relaxation_pair` (`crates/lakehouse-engine/src/scan/type_relaxation_tests.rs` line 75) exists to fail when an arrow-cast upgrade withdraws a pair, and a list generated from the oracle would assert only what the oracle already accepts. The 17 concrete entries at lines 24 to 69 are the pin, and the clause as written instructs their removal.
- Fix: Replace the "SHALL be derived from it rather than restating it" clause in `datafusion-scan/type-relaxation/spec.md` with a clause stating that the test list `supported_relaxation_pairs` STAYS the concrete 17-entry pin and SHALL be asserted AGAINST the production owner, so every listed pair resolves to its wider member and a curated refusal set returns no answer, and that a row added to the table without a matching owner rule fails the suite. State that the owner and the test list are checked against each other rather than one generated from the other, because a generated list would assert only what the generator accepts. Restate task 2.1 to match.
- Escalation: MECHANICAL. The recorded spec and the existing test file settle it.

#### [COMPLETENESS_GAP] ADVISORY
- Location: `specs/_plans/add-direct-storage-catalog-kind/vs-adapter/parquet-directory-seam/spec.md` § Scenario: Footers fold into one schema under the proven-castable widening pairs
- Issue: the recorded relaxation set holds no timestamp-to-timestamp row. Two Parquet files under one directory that declare a column as `TIMESTAMP(MICROS)` and `TIMESTAMP(NANOS)` therefore fail the whole refresh with a conflict error. Mixed timestamp units across writers are common in real object-storage directories. The behaviour follows decision [9] and is defensible, but no scenario, no manual-test row, and no `docs/catalogs.md` line warns an operator about it, so the first encounter is a failed `CREATE VIRTUAL SCHEMA` with no stated remedy.
- Fix: Add the mixed timestamp-unit case to task 6.7's `docs/catalogs.md` recipe as a named limitation, stating that files differing only in timestamp unit fail the fold and that `MERGE_SCHEMA = 'FALSE'` is the available workaround.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: `specs/_plans/add-direct-storage-catalog-kind/vs-adapter/catalog-crate-public-surface-extensions/spec.md` § Scenario, and `decision-log.md` § [6]
- Issue: the Arrow tag string moves a format decision across a crate boundary that cannot enforce it. `lakehouse-catalog` holds `ColumnSourceType::Parquet` carrying a tag whose vocabulary lives in `lakehouse-engine` and whose validity the catalog crate cannot check, because the manifest prohibition keeps `arrow` out. Two modules then assume the same string format with nothing enforcing agreement, which is the back-door leakage shape. The plan justifies the choice, and the alternatives it rejects are worse, so this is a cost to name rather than a design to reverse. It is also the mechanism through which the blocker above stays silent: a tag outside the vocabulary crosses the boundary unremarked.
- Fix: Add a clause to `vs-adapter/catalog-crate-public-surface-extensions/spec.md` requiring the engine-side tag renderer and the engine-side tag parser to be the ONLY producer and consumer of that variant's string, and requiring a test that every tag the direct-storage client emits parses back to the Arrow type it was rendered from.
