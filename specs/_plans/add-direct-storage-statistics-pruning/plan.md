# Plan: add-direct-storage-statistics-pruning

## Summary

The direct-storage reader drops a file from the plan-time file list when the Parquet footer that the directory seam already returned proves that no row group can satisfy the pushed filter (issue #412). The shared partition predicate gains range evaluation, so a partition value and a row group's `[min, max]` share one sound three-valued evaluation path.

## Context

- `DIRECT_STORAGE` has no manifest and no transaction log. Its plan-time file list is every file that partition pruning keeps, and `vs-adapter/direct-storage-table-planning` records the missing statistics pruning as an exception citing #412.
- `resolve_parquet_directory` (`crates/lakehouse-engine/src/adapter/parquet_directory.rs`) returns each read file's parsed `ParquetMetaData` in `ParquetFile.footer`. Under `MergeMode::FoldEveryFile` every kept file carries one. Under `MergeMode::SampleOneFile` only the first listed file does.
- A file that cannot match still costs a shard slot, a UDF invocation, and a second footer read inside the scan.
- `PartitionPredicate` (`crates/lakehouse-engine/src/adapter/pushdown/format/partition_predicate.rs`) translates Exasol's filter JSON into `Node { Compare, IsNull, And, Or, Not, Opaque }` and evaluates it three-valued over one exact partition value per column.
- `PartitionPredicate` has a second caller: `CatalogParquetFormatReader` (`catalog_parquet_format_reader.rs`) serves Unity Parquet and Glue Hive Parquet tables and types their partition columns from the catalog (`partition_column_types`). `vs-adapter/partition-predicate-declared-types` requires a float partition column to keep every file.
- `CatalogParquetFormatReader` reads no footer. Its files come from `list_parquet_files` and `list_location_files` with `footer: None`, and `vs-adapter/unity-parquet-table-planning` and `vs-adapter/glue-table-planning` forbid a plan-time footer read.
- `ParquetFormatReader::resolve_scan` builds each logical field's type tag with `arrow_type_to_tag`. A folded type outside the tag vocabulary, such as `Date64`, `Decimal256`, FLOAT16, or a nested type, gets the `utf8` tag, so the scan compares that column as text.
- Parquet bounds exclude NaN, and `arrow-ord` 58.3.0 compares floats in IEEE 754 total order. Issue #393 tracks the stored-NaN comparison gap as an accepted edge case.
- The scan's DataFusion 54.1 row-group pruning, Delta planning (`delta-kernel-rs` 0.26), and Iceberg planning (`iceberg` 0.10) already prune on float bounds that exclude NaN.
- DataFusion 54.1 `prune_by_statistics` ignores `ColumnOrder` and sets `missing_null_counts_as_zero: true`. The recorded scan scenario states that pruning leaves the emitted rows identical to a scan with pruning disabled.
- `datafusion-scan/nested-json-rendering` requires that no statistics pruning stage prunes on a nested column, proven against a file of several row groups (scenario requirement in `datafusion-scan/nested-json-rendering`; #458 removed the former ADR `nested-pruning-requires-positive-proof`).
- Code reading shows that the scan compares a DECIMAL column against a non-integer exact-numeric literal through the literal's 64-bit float value: `vs-expression` renders the numeral bare (`json_scalar_to_string`), `sql_parser.parse_float_as_decimal` defaults to false in `datafusion-common` 54.1 and `session_config_for_spec` does not set it, and `decimal_coercion` compares in `Decimal128(30,15)`. The scan also cuts a timestamp literal to microseconds (accepted ADR `timestamp-literal-arrow-cast-microsecond`), compares a millisecond or second timestamp column against that literal in the column's coarser unit (DataFusion 54.1 `timeunit_coercion`), and rounds an integer literal to FLOAT against a FLOAT column. Task 1.5 reproduced all four live (decision-log.md [M1]), as AGENTS.md requires before a behavior counts as a bug.
- `handle_pushdown` decides with `classify_where_filter` whether the scan evaluates the pushed filter or the adapter applies it in its own outer `WHERE` (`vs-adapter/pushdown-declined-filter-self-apply`), and it decides this before it calls `TableScanResolver::resolve`. On the N-scan join fallback, `renderable_only`, `leg_local_filter`, and `type_screened_leg_filter` decide per conjunct which leg-local conjuncts each leg's scan carries. Format-level pruning reads the raw filter on both paths.
- When the adapter applies the filter itself, Exasol compares the emitted values, not the stored ones. Direct storage declares a timestamp column `TIMESTAMP(3)` (the existing `ANNOTATED_TYPES` E2E assertion on `C_INT96`), so a stored sub-millisecond value is emitted at millisecond precision. Exasol also reads an emitted empty string as NULL.
- The direct-storage E2E fixtures hold no file of several row groups and no table whose files have disjoint ranges per type. `all_types_batch` holds three fixed rows in one file.
- The locked versions are `parquet` 58.3.0, `datafusion` 54.1.0, `arrow-ord` 58.3.0, `delta_kernel` 0.26.0, and `iceberg` 0.10.0.
- `vs-adapter/delta-file-pruning` (Background) records one independent filter walker per output format and no shared IR.
- Accepted ADRs that bind this plan: `unity-parquet-schema-from-catalog-not-footer` (the catalog-declared Parquet reader reads no footer), `one-catalog-declared-parquet-reader-and-one-iceberg-planner-serve-glue` (direct storage passes `Utf8` partition types to the shared predicate), and `scan-case-folds-identity-binding-refuses-unadmitted-types` (the scan binds a column by exact name, then by uppercase fold).
- `specs/architecture.md` is absent, so the plan writes no architecture delta.

## Impact

- A direct-storage query whose filter excludes a file's footer bounds plans fewer files. Shards balance over files that can match, and the scan opens no file that yields nothing.
- A join leg whose filter prunes files sums fewer bytes, so broadcast side selection and eligibility read the pruned size, as they already do after Iceberg and Delta file pruning.
- A filtered plan drops a file that holds zero row groups. Such a file holds no rows.
- Statistics pruning reads only the part of the filter the scan evaluates. A filter the adapter applies in its own outer `WHERE` prunes no file on footer statistics, and a join leg prunes only on the leg-local conjuncts its own scan carries. Partition pruning still reads the full filter.
- Results do not change for any non-NaN value. A stored float NaN row in a file whose bounds exclude a parity comparison's literal is not returned. The scan's row-group pruning, Delta planning, and Iceberg planning carry the same exposure (#393).
- No breaking change. No new property, wire field, or object-store request. Single-table plans and join plans whose filter the scan does not evaluate keep the file lists they have today.
- Unfiltered plans, Unity Parquet plans, and Glue Parquet plans do not change.
- The scan spec states its existing column-order, deprecated-statistics, and missing-null-count handling as a (#TBD) exception to the Parquet specification. The scan code does not change.
- Plan-time CPU grows by one in-memory evaluation per kept file and row group. The footers are already in memory.
- `docs/catalogs.md` states the new pruning, the cases that keep a file, and a limitation note on stored NaN values that links #393.
- The direct-storage E2E suite gains two tables, `PRUNE_TYPES` (two files) and `NAN_PROBE` (one file), and about 175 small queries per run: two per case of the 76-case table, plus the NaN probe and the three join-leg queries.

## Open Questions

1. The scan's comparison of a DECIMAL column against a non-integer exact-numeric literal (#TBD), and of a timestamp column against a timestamp literal with a non-zero fraction digit past the sixth or finer than the column's millisecond or second unit (#461). Task 1.5 reproduced all of them live (decision-log.md [M1]). Setting `parse_float_as_decimal` fixed the DECIMAL case but cast FLOAT and DOUBLE columns to decimals that overflow on large values and NaN, so it was reverted, and a human decides how an issue tracks the DECIMAL class. The same scan comparison serves Iceberg, Delta, and Glue tables, whose plan-time pruning converts decimal and timestamp literals exactly. This plan records the exception for direct storage only.
2. A stored `-0.0` in a DOUBLE column (#TBD, not verified live). The scan compares floats in IEEE 754 total order, which separates the two zeros, so code reading predicts that `= 0` misses a stored `-0.0` and `< 0` matches it, unlike an IEEE comparison. `PRUNE_TYPES` stores `+0.0` only, so no case pins this outcome. A human decides whether #393 covers it or a separate issue tracks it.
3. The scan's row-group pruning handling of column order, deprecated statistics, and missing null counts (#TBD), recorded as an exception in `datafusion-scan/scan-execution-memory-and-credentials`.
4. The unbounded-file-count exception of `vs-adapter/direct-storage-table-planning` cites #419, which was closed on 2026-09-22. A human decides whether the exception keeps citing #419 or changes to (#TBD).
5. Iceberg manifest pruning and Delta planning read the full raw filter on the self-apply path (`vs-adapter/pushdown-declined-filter-self-apply` Background), where Exasol compares the emitted values (#TBD, not verified live). Exasol reads an emitted empty string as NULL. If that planning drops a file whose null count is zero for `IS NULL`, a self-applied `IS NULL` misses that file's empty-string rows, which Exasol would select. This plan avoids the exposure for direct-storage statistics pruning only (decision-log.md [3]). A human decides whether an issue tracks the other formats.
