# Intent: add-export-adls-storage

Issue: #569, "export Iceberg tables to Azure Data Lake Storage Gen2". The export (`EXPORT ... INTO SCRIPT LAKEHOUSE_EXPORT`) writes Iceberg tables through an Iceberg REST catalog, today only onto S3-compatible storage. It refuses a CONNECTION with Azure storage fields and a table location whose scheme is not `s3` or `s3a`. Virtual schemas already read ADLS Gen2 tables, with static credentials (account key or SAS token) from the CONNECTION or with a SAS the catalog vends.

## Interview

- Q: A vended ADLS SAS expires. The S3 export renews vended keys while a writer runs, through the catalog's `loadCredentials` endpoint, and signs every storage request with the current keys. The writer's FileIO uses opendal's Azure backend, which takes one fixed SAS and offers no hook to renew it. How should an ADLS export handle a vended SAS that expires before a writer finishes? → A: Renew per request, the same as S3. Every storage request of a writer, its commit's manifests included, signs with the current SAS, which is renewed through `loadCredentials` before it expires. The alternatives were rejected: rebuilding the FileIO between data files still fails a file that is being written when the SAS expires, and seeding the SAS once with no renewal would make long ADLS exports fail where S3 exports succeed.

- Q: What should the export do with a CONNECTION that holds Azure storage fields and an IAM role (`aws_assume_role_arn`)? The user asked how the virtual schema handles it, and to reproduce and reuse the read path instead of inventing new rules. Finding: the export already runs the CONNECTION checks every virtual schema runs, and they refuse every role-plus-Azure shape. A role needs the CONNECTION's `access_key` and `secret_key`. With them, the CONNECTION mixes Azure and S3 credential fields and is refused. Without them, the role is refused for its missing key pair. → A: Inherit the virtual schema's refusal. The export drops its own "Azure storage is not supported" refusal, and the shared checks then refuse role plus Azure exactly as `CREATE VIRTUAL SCHEMA` does, before any source row is read. No new check and no new error text.

- Q: opendal's Azure backend has no credential hook. Which mechanism gives a writer per-request SAS renewal? → A: An own Iceberg storage for ADLS, over object_store's Azure client, which accepts a credential provider. The scan already builds that Azure client for its data file reads, so the writer shares its construction. The SAS comes from the same renewing credential source the S3 path uses. The rejected alternative was a credential hook contributed to opendal's Azure backend and to iceberg-storage-opendal: it mirrors the S3 design exactly, but the plan would block on two upstream projects and pin a fork until both merge.

- Q: The S3 export refuses vended credentials that lack `s3.session-token-expires-at-ms`, or so its spec reads. The Iceberg REST key for an ADLS SAS is `adls.sas-token-expires-at-ms.<host>`, and the read path never reads it. What should the export do when a vended SAS comes without that expiry? → A: Treat the SAS as not expiring: use it as vended and never renew it ahead of time. The user's reasoning: an S3-like backend might vend fixed credentials with no expiry, and refusing them would break the export, so the S3 rule as the spec states it is wrong too. Finding: the S3 code already behaves this way. It reads an absent `s3.session-token-expires-at-ms` as "no expiry" and refuses only a value that is present but unreadable (such as `tomorrow` or an empty string) and a missing access key or secret key. Only the spec sentence, "SHALL refuse a missing key or an unreadable `s3.session-token-expires-at-ms`", reads as if an absent expiry were refused. The plan rewords it so it states that an absent expiry means credentials that never expire, for S3 and ADLS alike. The S3 code does not change.

- Q: A virtual schema accepts a static `sas_token` in the CONNECTION, but no E2E suite tests it, because the Azure suite's static arm uses `account_key` only. The export accepts a static `sas_token` too. How is that proved? → A: With an E2E test in the Azure suite. The suite mints a short-lived account SAS from the account key it already holds, an export writes through a CONNECTION that carries that `sas_token`, and the table reads back through a virtual schema. This proves the export path end to end and needs no new cloud credential. The rejected alternative covered only `account_key` and the vended SAS end to end and left the static `sas_token` to a unit test of the shared credential mapping, which matches the read path's current coverage.

- Reuse findings from the read path, which the user directed the plan to follow:
  - The vended SAS is selected by the table location's host (case-insensitive), and the account name is the location host's first label, taken verbatim. The writer already resolves its storage through the same vended resolution the virtual schema uses.
  - Plaintext: a vended `abfs://` location is honoured only under `ALLOW_HTTP`, and a static Azure CONNECTION addresses only `abfss://`. The export applies the same rule with its own `ALLOW_HTTP` option.
  - The CONNECTION's static `sas_token` is supported beside `account_key`, as on the read path. Like the CONNECTION's S3 keys, a static credential is never renewed.
  - The virtual schema never renews a SAS: it seals the vended SAS into the scan spec once per statement. Renewal is export-only, as it is for S3.

- Q (after the plan review): The reviewer flagged D1 as drifting from the third answer, whose option text said the writer shares the scan's Azure client construction. How did the S3 path solve this? → Finding: the S3 writer never shared the scan's object store either. The read path has two storage stacks on both backends: the scan UDF's object_store client for Parquet data files, and the adapter's Iceberg FileIO over opendal for metadata and manifests (`StorageBackend::file_io`). The S3 writer is built on the second: `file_io_with_credential_loader` runs the same FileIO construction as the read path and only adds opendal's S3 credential-loader hook, through which every request asks the writer's credential source for the current keys. opendal's Azure backend has no such hook, and `lakehouse-catalog`, which owns that construction, may not depend on object_store, so the ADLS writer cannot sit beside it. Mirroring S3 exactly would need the upstream hook the user rejected earlier. → A: Keep D1 with that reason, and fix the review findings.

## Directions

- [D1] The writer's ADLS storage builds its own object_store Azure client and takes every credential kind, account key, static SAS, and vended SAS, through one credential provider. It shares no builder with the scan, as the S3 writer shares none: the S3 writer reuses the read path's FileIO construction plus opendal's credential hook, which opendal's Azure backend lacks. The ADLS writer reuses the vended SAS selection, the account name rule, the renewal timing, and `loadCredentials`.
- [D2] The vended-storage scenario "One concept-level call resolves the effective scan storage" is removed. Widening its S3-only export exception means editing it, and with its implementation detail removed nothing observable remains that its Background and other scenarios do not already state.
- [D3] A static Azure CONNECTION is not checked against the account of the table location. The writer takes the account from the location host's first label, as the read path does, and never from the CONNECTION's `account_name`, so a key for another account fails like any wrong storage key.
- [D4] The ADLS expiry is read from `adls.sas-token-expires-at-ms.<host>` for the host of the selected SAS, with the same case-insensitive host match and tie-break as the SAS key.
- [D5] Whether the Azure stack's Lakekeeper vends `adls.sas-token-expires-at-ms.<host>` is unverified. Implementation checks a vended `loadTable` answer first. If the key is absent, Lakekeeper SAS exports are never renewed, and `docs/export.md` says so.
- [D6] The export refuses a vended `abfs://` location itself, before vended storage resolution, so its error names the export option `ALLOW_HTTP` and not the virtual schema property.
- [D7] Each backend gets its own write credential source, the S3 one unchanged and an ADLS one for the account key, static SAS, or vended SAS. Both share the renewal timing and `loadCredentials`, so no source can hand a credential of the wrong backend.
