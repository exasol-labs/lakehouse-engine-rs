## Components

- udf-entry-points (crates/lakehouse-engine/src/lib.rs): exports the four UDF entry points of the single `.so` (VS adapter, `LAKEHOUSE_SCAN`, `LAKEHOUSE_VERSION`, `LAKEHOUSE_EXPORT`) | owns: engine version string | depends on: vs-adapter, datafusion-scan, export
- vs-adapter (crates/lakehouse-engine/src/adapter/): answers Exasol Virtual Schema requests, reads the CATALOG_CONNECTION, lists the catalog tables the table filter exposes into virtual tables with one identifier note per table and one source note per column, answers a `REFRESH TABLES` by listing catalog identifiers and loading only the requested tables the table filter exposes, and routes pushdown requests through each virtual schema's statement state | owns: schema-level adapterNotes and their format (SKIPPED_TABLES, tuning values, CATALOG_PREFIX), written and read in adapter/mod.rs; the statement state (§ Constraints); the engine-side scan load that each catalog kind's client implements | depends on: vs-properties, table-filter, connection-creds, lakehouse-catalog, pushdown-planner, table-identity, column-notes, type-mapping, sealed-storage
- vs-properties (crates/lakehouse-engine/src/adapter/properties.rs): declares every virtual schema property name and the value rule of each tuning property, applies the table-filter value rule to `TABLE_INCLUDE` and `TABLE_EXCLUDE`, rejects unknown names and invalid values in one error for createVirtualSchema, refresh, and setProperties, and parses each tuning value into a fixed-width typed value and the two pattern lists into one table filter; it parses properties only, never adapterNotes | owns: VS property catalog (names and tuning value rules) | depends on: table-filter
- table-filter (crates/lakehouse-engine/src/adapter/table_filter.rs): parses the `TABLE_INCLUDE` and `TABLE_EXCLUDE` glob pattern lists and decides whether a virtual table name is exposed, with exclude winning over include | owns: table pattern syntax and the exposure rule | depends on: none
- pushdown-planner (crates/lakehouse-engine/src/adapter/pushdown/): classifies the pushdown request shape (row scan, top-N, single-group aggregate, grouped aggregate, COUNT DISTINCT, join, fallback wrapper), reads each involved table's catalog identifier from its identifier note and its declared schema from its column notes, and renders the dispatch SQL that carries one scan spec per shard; it builds one per-column type map per involved table when it resolves the table, and every type check, binary comparison, and projection reads that map | owns: dispatch SQL, per-shard scan specs, the per-column type map (each column's Exasol type and raw-byte layout, keyed by relation alias and column) | depends on: format-readers, table-identity, column-notes, sharding, type-mapping, vs-expression, scan-spec, sealed-storage, lakehouse-catalog
- format-readers (crates/lakehouse-engine/src/adapter/pushdown/format/): declares each catalog-listed table's columns at createVirtualSchema from the neutral table metadata the catalog client returned, and at pushdown opens one table's filter-independent state (Iceberg metadata, Delta snapshot, Glue partition list, or Parquet directory listing) for Iceberg, Delta, catalog Parquet, and direct-storage Parquet tables when a catalog client loads the table, then prunes its file list per reference with the reference's filter against the declared schema, failing a query whose declaration disagrees with the table's current schema or log | owns: none | depends on: column-notes, lakehouse-catalog, type-mapping
- table-identity (crates/lakehouse-engine/src/adapter/table_identity.rs): encodes each virtual table's identifier note, a table-level adapterNotes JSON object whose `name` member holds the catalog identifier, and reads the identifier back from an involved table at pushdown | owns: table identifier note format | depends on: lakehouse-catalog
- column-notes (crates/lakehouse-engine/src/adapter/column_notes.rs): encodes, size-checks, and parses the per-column declaration notes, and holds the refused-column type and the refusal helpers the declaration builders share | owns: column note format | depends on: scan-spec
- sharding (crates/lakehouse-engine/src/adapter/sharding.rs): computes the shard count G and partitions the file list into G byte-balanced shards | owns: none | depends on: scan-spec
- scan-spec (crates/lakehouse-engine/src/scan/spec.rs): defines the format-neutral JSON wire format between the adapter and the scan UDF (`CommonScanSpec`, `FileEntry`, `LogicalField`, `ScanStorage`) | owns: scan spec wire format | depends on: lakehouse-catalog
- sealed-storage (crates/lakehouse-engine/src/scan/sealed.rs): encrypts storage credentials into the scan spec with AES-GCM under a key derived by HKDF-SHA256 from the CONNECTION password, and decrypts them in the scan UDF | owns: sealed storage envelope format | depends on: none
- datafusion-scan (crates/lakehouse-engine/src/scan/): runs one shard per invocation as a raw scan, a partial aggregate, or a broadcast join scan, applies Iceberg positional deletes and Iceberg and Delta deletion vectors, and emits results batch by batch | owns: per-invocation Tokio runtime, DataFusion session, memory pool | depends on: scan-spec, sealed-storage, scan-object-store, type-mapping, vs-expression
- scan-object-store (crates/lakehouse-engine/src/scan/object_store.rs): builds S3 or ADLS Gen2 object stores with a connection budget and an admission limit, and routes the two join sides by path prefix | owns: per-invocation HTTP connection pool | depends on: lakehouse-catalog
- connection-creds (crates/lakehouse-engine/src/connection.rs): parses an Exasol CONNECTION password's JSON fields into `ConnectionCreds` and runs the field checks that do not depend on the catalog kind, for vs-adapter and export alike | owns: the mapping from a CONNECTION password's JSON fields to `ConnectionCreds` | depends on: lakehouse-catalog
- export (crates/lakehouse-engine/src/export/): validates an `EXPORT ... INTO SCRIPT` statement, reads the CONNECTION itself through connection-creds, refuses a route it does not write (Azure storage, SigV4 signing) and plain HTTP without its `ALLOW_HTTP` option, checks before any source row is read that the catalog accepts the export and whether the target table exists, refusing an existing table it cannot append to, renders the writer SELECT that calls the same script with a row-number group key, and, as the writer, maps the input columns to an Arrow schema, binds them by name to the table's columns, and streams the rows as Arrow batches into a sink; it does four steps for every target, and the seam sits after the Arrow batch: an `ExportTarget` trait connects and checks, then creates or opens the table and returns an `ExportSink` that the target owns, which takes Arrow batches, writes its files its own way, and commits them, and the first implementation is Iceberg REST | owns: export options, writer spec format, the `ExportTarget` and `ExportSink` traits, the mapping from Exasol types to Arrow types with its refusals, the binding of source columns to table columns and the source types each table column accepts, the check whether an existing Iceberg table takes an append, the Iceberg sink (the derivation of the Iceberg schema from the Arrow schema, the Parquet data files, the commit call), the export's per-call Tokio runtimes | depends on: vs-expression, connection-creds, lakehouse-catalog, lakehouse-catalog-write
- type-mapping (crates/lakehouse-engine/src/types/): maps Arrow, Iceberg, Delta, and Hive types to vs-expression's Exasol SQL type and applies type widening rules | owns: none | depends on: vs-expression
- lakehouse-catalog (crates/lakehouse-catalog/): implements `CatalogClient` for Iceberg REST, Unity Catalog, and AWS Glue (a full listing that drops the identifiers a caller-supplied predicate rejects before it loads any table, an identifier-only listing, and a load of listed tables that classifies each table as the full listing does) with OAuth2, bearer, and SigV4 auth, STS role assumption, vended-storage resolution, and credential redaction, and gives the Unity Catalog and Glue sessions a single-table load outside that trait; its neutral table carries the catalog's table properties verbatim and its neutral column an opaque engine-encoded declaration slot, and it interprets neither; its session has public read methods (table existence, load with all snapshots, `loadCredentials`) and one public method that sends a state-changing request through the one HTTP client and states whether it is safe to repeat, and its Unity and Iceberg REST OAuth2 tokens renew through one expiring-credential holder | owns: catalog sessions, whose lifetime the adapter or the export decides, the expiring-credential holder, the HTTP client's retry rule | depends on: none
- lakehouse-catalog-write (crates/lakehouse-catalog-write/): for the export it creates Iceberg REST namespaces and tables, stages a table, commits a writer's data files exactly once per writer tag, and renews an export table's vended storage credentials inside its FileIO, reading through the catalog session's read methods and sending each state-changing request through its one public request method, marked not safe to repeat; its operations own their retries | owns: the export commit loop and the retry policy of catalog writes, the vended storage credential source built on the expiring-credential holder | depends on: lakehouse-catalog
- vs-expression (crates/vs-expression/): translates VS expression JSON into DataFusion SQL and Exasol SQL fragments, parses and rewrites the `column` nodes of a pushdown request, and defines the Exasol SQL type: it reads the type from VS `dataType` JSON and from UDF input and output column metadata, rejects a type outside Exasol's limits, and renders it as Exasol SQL text and as `dataType` JSON | owns: the Exasol SQL type and its SQL and `dataType` JSON renderings | depends on: none
- distribute-files (deploy/scripts/install.sh): defines the Lua SET script `LAKEHOUSE_DISTRIBUTE_FILES`, which re-emits per-shard file-list rows so `GROUP BY shard_key` spreads them across nodes | owns: none | depends on: none
- installer (deploy/scripts/install.sh): downloads the engine and SLC release assets, uploads them to BucketFS with exapump, creates the scripts, and runs a version and fingerprint smoke test | owns: none | depends on: distribute-files

## Data Flow

- CREATE or REFRESH VIRTUAL SCHEMA -> vs-adapter -> lakehouse-catalog -> catalog service: table listing returns as virtual table definitions, one identifier note per table holding its catalog identifier, and one column note per column holding the declared source shape
- REFRESH TABLES -> vs-adapter -> lakehouse-catalog -> catalog service: the namespace's catalog identifiers are listed without loading any table, only the identifiers whose Exasol name is requested are loaded and collision-checked, the response carries only the requested tables, and Exasol keeps every other virtual table with its notes
- user query -> Exasol -> vs-adapter: one pushdown request JSON per pushed-down query block, with projection, filter, aggregates, ORDER BY, LIMIT, join tree, and each involved table's identifier note and column notes; every request of one statement on one virtual schema reaches the same adapter VM
- vs-adapter -> catalog client -> format-readers -> lakehouse-catalog and object storage: the virtual schema's catalog client loads a table and opens its snapshot or file listing, and each table reference prunes the file list with its own filter against the declared schema the column notes carry; no reader derives a schema
- format-readers -> sharding -> pushdown-planner: the file list becomes G byte-balanced shards, each serialized as `common` and `files` JSON strings in the dispatch SQL
- dispatch SQL -> LAKEHOUSE_DISTRIBUTE_FILES -> GROUP BY shard_key -> LAKEHOUSE_SCAN: Exasol runs one scan VM per node, which scans that node's shard rows one after another
- LAKEHOUSE_SCAN -> datafusion-scan -> scan-object-store -> object storage: Parquet byte ranges stream into one DataFusion plan per invocation
- datafusion-scan -> Exasol: raw and join rows leave through the Arrow C Data Interface via `ctx.emit_batch`, partial aggregates leave as SDK `Value` rows via `ctx.emit`
- Exasol -> result: the dispatch SQL wrapper merges partial aggregates and applies the final ORDER BY and LIMIT
- user `EXPORT ... INTO SCRIPT LAKEHOUSE_EXPORT WITH CATALOG_CONNECTION = '<connection>' ...` -> Exasol -> export: one call with the export specification (options, source column names) before any source row is read
- export -> lakehouse-catalog-write -> lakehouse-catalog -> catalog service: before any source row is read, export checks the CONNECTION's route and plain-HTTP use, then through its target connects and authenticates, and either loads an existing target table and refuses one it cannot append to, or creates missing namespace levels for a new table, with no storage access; export then answers one SELECT over `DUAL`, which Exasol binds to the export source, carrying the CONNECTION name, the table name, whether the table exists, the source column names, the commit mode, the `ALLOW_HTTP` consent, and one export ID per statement
- generated SELECT -> LAKEHOUSE_EXPORT as writer: the source rows are grouped by `MOD(ROWNUM, G)`; Exasol multiplexes the groups, one writer invocation each, onto each node's SET-script VM pool
- LAKEHOUSE_EXPORT writer -> lakehouse-catalog-write -> catalog service: at its first row the writer opens the table through its target, which returns a sink: for a new table the writer maps the input column types to Arrow and Iceberg REST creates the table, loading it when another writer of the same export won the create, or stages it under `SINGLE_COMMIT = 'true'`; for an existing table Iceberg REST loads it and checks again that it takes an append; the writer then binds every table column to a source column by name with the accepted widenings, refuses every mismatch in one error before it writes any data, and builds its Arrow batches against the sink's table schema
- LAKEHOUSE_EXPORT writer -> sink -> object storage: the Arrow batches become Parquet data files under the table location, written with the CONNECTION's storage keys or the credentials the catalog vended for the table
- LAKEHOUSE_EXPORT writer -> lakehouse-catalog-write -> lakehouse-catalog -> catalog service: with vended credentials, the FileIO of the writer's table renews its credentials through the table's credentials endpoint on the CONNECTION's catalog address before they expire, with the writer's one catalog session, whose OAuth2 token renews itself
- LAKEHOUSE_EXPORT writer -> sink -> lakehouse-catalog-write -> catalog service: one commit of the writer's data files in one snapshot tagged with the export ID and the writer's ID, which appends to a new or an existing table, or under `SINGLE_COMMIT = 'true'` for a new table one commit that creates the staged table with its snapshot
- LAKEHOUSE_EXPORT writer -> Exasol: one row count per writer; Exasol reports their sum as the EXPORT statement's row count

## Interfaces

- VS adapter protocol: Exasol calls the adapter entry point with request JSON of type `getCapabilities`, `createVirtualSchema`, `refresh`, `setProperties`, `dropVirtualSchema`, or `pushdown`; a pushdown answer is `{"type":"pushdown","sql":...}`
- VS properties: a closed set of names, the same under every `CATALOG_KIND`, that `vs-properties/property-name-validation` lists; `createVirtualSchema`, `refresh`, and `setProperties` fail with one error on any other name or on an invalid tuning value, and `pushdown`, `getCapabilities`, and `dropVirtualSchema` check neither
- CONNECTION object: the address is the catalog URI (empty allowed for `DIRECT_STORAGE`), and the password is a JSON object of catalog and storage credentials
- adapterNotes: Exasol persists `SKIPPED_TABLES`, the tuning values, and `CATALOG_PREFIX` between CREATE and pushdown, up to 2,000,000 bytes
- table adapterNotes: each virtual table's identifier note is a JSON object string `{"name": <catalog identifier>}`, persisted in `EXA_ALL_VIRTUAL_TABLES.ADAPTER_NOTES` and returned in `involvedTables[].adapterNotes`
- column adapterNotes: each virtual column's note is a JSON object string `{"sourceType": <LogicalField>, "partition": <position>, "refused": <reason>}`, persisted in `EXA_ALL_VIRTUAL_COLUMNS.ADAPTER_NOTES` and returned in `involvedTables[].columns[].adapterNotes`, up to the measured per-column limit
- `LAKEHOUSE_SCAN(common VARCHAR, files VARCHAR)`: scalar UDF that handles one shard row, reads the JSON scan spec halves, and emits the columns that the dispatch SQL declares
- `LAKEHOUSE_DISTRIBUTE_FILES(files VARCHAR(2000000))`: Lua SET script that emits its input rows unchanged
- `LAKEHOUSE_VERSION()`: returns the `lakehouse-engine` crate version string
- `LAKEHOUSE_EXPORT(...)`: SET script with two roles. Exasol calls its export hook for `EXPORT ... INTO SCRIPT <schema>.LAKEHOUSE_EXPORT WITH CATALOG_CONNECTION = '<connection>' TABLE_NAME = '<namespace>.<table>' [WRITERS_PER_NODE = '<n>'] [SINGLE_COMMIT = 'true'|'false'] [ALLOW_HTTP = 'true'|'false']`. The SELECT the hook returns calls it as the writer, `LAKEHOUSE_EXPORT(<writer spec>, <source columns>...)`, which returns its group's row count as `DECIMAL(18,0)`
- Iceberg table that an export creates: format version 2, unpartitioned, every column optional; table property `lakehouse.export-id` names the creating export
- Iceberg table that an export appends to: an existing format-version 2 table whose default partition spec has no field; the export binds every table column to a source column by name and changes none of the table's schema, partition spec, or properties
- Iceberg snapshot that an export commits: its summary carries `lakehouse.export-id` and `lakehouse.export-writer`
- install.sh CLI: `install.sh --account-id <id> --database-id <id> --profile <p>` for SaaS, or `--dsn`, `--host`, `--target`, `--deployment`, `--bfs-*`, `--schema`, `--lakehouse-version`, `--slc-version`, `--arch`, `--skip-slc`
- Release asset: `lakehouse-engine.tar.gz` on GitHub releases, installed to BucketFS at `udf/liblakehouse_engine.so`
- Makefile: `cross-udf-build`, `test`, `test-e2e`, `test-e2e-lakekeeper`, `test-e2e-azure`, `test-e2e-glue`, `test-e2e-unity`, `<stack>-start`, `<stack>-wait`, `<stack>-up`, and `<stack>-down` for the E2E stacks `e2e`, `lakekeeper`, `azure`, `unity`, and `glue`, `install-slc`, `bench`

## Constraints

- The toolchain is pinned in `rust-toolchain.toml`, with edition 2024. Every dependency version is pinned in the workspace manifest, not in the specs.
- The release `.so` builds only in the Makefile's `UDF_BUILDER_IMAGE`, whose rustc and glibc match the SLC, because the SLC rejects a `.so` whose SDK fingerprint (`exasol-udf-sdk` version and rustc hash) differs from its own.
- `exasol-udf-sdk` and `exasol-udf-macros` are pinned in the workspace manifest to the SLC's own version.
- `arrow` and `parquet` stay on the Arrow major that `datafusion` and the SDK depend on, not on the major of the `datafusion` or SDK package itself.
- Arrow types never cross the `.so` boundary. Only SDK `Value`s or the Arrow C Data Interface structs from `ctx.emit_batch` cross it.
- In `lakehouse-engine` and `vs-expression`, an Exasol SQL type travels as vs-expression's Exasol type, never as a string. Each input edge (VS `dataType` JSON, UDF column metadata for the scan and the export alike, Iceberg, Delta, Hive, and Arrow types) reads it once, and only SQL text generation and the VS `dataType` JSON output render it. The `dataType` parser admits only values within Exasol's limits, a DECIMAL outside Exasol's domain cannot be constructed, and one rendering serves `EMITS` columns, column declarations, and Exasol-dialect `CAST` targets.
- The engine supports Exasol 8.29.x and later. Every pushdown request of a supported version carries `selectListDataTypes` with one complete `dataType` per select-list item, and the adapter fails a request without it.
- `lakehouse-catalog` never depends on `lakehouse-engine` or `lakehouse-catalog-write`, and `lakehouse-catalog-write` never depends on `lakehouse-engine`: the engine depends on the write crate, which depends on the catalog crate. The catalog crate's manifest declares no `arrow`, `parquet`, `datafusion`, or `object_store` dependency, and it names no scan-spec type (`FileEntry`, `LogicalField`, `DeleteMechanism`, `CommonScanSpec`). A neutral catalog column carries an Arrow type only as the engine's type-tag string.
- The catalog HTTP client is reachable from `lakehouse-catalog-write` only through the catalog session's one public request method, which carries namespace creation, table creation, stage-create, and the commit. Read calls (listing, loading, table existence, `loadCredentials`, vended-credential resolution) stay in `lakehouse-catalog`, so the method is not a back door for reads.
- The engine reads and writes a `column` node's `name`, `tableName`, and `tableAlias` only through `vs-expression`'s column node type.
- `lakehouse-catalog` declares the shared credential types (`ConnectionCreds`, `StorageProps`, `CatalogProps`, `StorageBackend`) and the credential redaction functions once. The engine re-exports them and declares no copy. Reading and parsing the Exasol CONNECTION object stays in the engine.
- The engine enumerates and declares catalog tables through the `CatalogClient` trait and its neutral table and column types. `CatalogClient` has no single-table load. Each catalog kind's client loads a table for pushdown through its one scan load, declared by an engine-side extension of that trait, so `lakehouse-catalog` gains no file-planning type. The vs-adapter's one catalog-kind match is the only site that names the kind to build a client or load a table, and a scan load matches only the loaded table's format tag. In `lakehouse-catalog`, auth strategies, HTTP and signing helpers, and vended-resolution steps stay crate-private, and no AWS SDK type crosses the crate boundary.
- Each catalog kind's identifier-only listing returns every identifier its full listing would return or skip, in listing order, without loading table metadata. Its load of listed tables admits or skips each given table exactly as the full listing does and loads no other table.
- The Makefile's `VS_SRCS` lists every crate's sources and manifest, so a change in `lakehouse-catalog`, `lakehouse-catalog-write`, or `vs-expression` rebuilds the `.so` before an E2E run.
- The scan UDF and the export script keep no cross-call state and build their Tokio runtimes per call. The adapter keeps cross-call state only for the pushdown requests of one statement, keyed by the virtual schema name: the Tokio runtime, the resolved CONNECTION, the catalog client, the permission-checked tables, and each table's loaded, unpruned state. It therefore loads each table's metadata once per statement and prunes the file list per table reference. It never keeps a pruned file list, a result, or an error.
- The engine owns no persisted metadata. Exasol stores the schema-level adapterNotes values (`SKIPPED_TABLES`, tuning values, `CATALOG_PREFIX`), the table identifier notes, and the column notes between CREATE and pushdown.
- A table's declared schema is decided at CREATE, REFRESH, or SET and read from its column notes at pushdown. No format reader derives a logical schema, a partition column, or a refusal at pushdown.
- Each node scans only its assigned files, with no overlap between shards.
- The shard count is G = node count × `PARALLELISM_FACTOR` (default 1), clamped to at least 1 and at most min(file count, 300).
- The export writer count is G = node count × `WRITERS_PER_NODE` (default 1), clamped to at least 1 and at most 300, or 1 with `SINGLE_COMMIT = 'true'`. Each source row reaches exactly one writer, and a source with at least G rows runs exactly G writers.
- The export has no step after its last writer, so each writer commits on its own and a failed parallel export can leave some writers' commits in the table. `SINGLE_COMMIT = 'true'` makes a new table appear only with its data, and appends to an existing table in exactly one commit or none, by whatever mechanism the target offers.
- An export writer commits its data files at most once. Its commit loop belongs to `lakehouse-catalog-write`, not to iceberg-rust, and commits again after a conflict or an unknown outcome only when no snapshot carries the writer's tag.
- The DataFusion memory pool is max((memory limit − 200 MB overhead) × 0.6, 256 MiB), or 1 GiB when the limit is unknown.
- The scan spills to `/tmp` when `/tmp` is a writable non-tmpfs disk. Otherwise it returns a `ResourcesExhausted` error past the pool budget.
- The scan streams one `RecordBatch` at a time and never collects the full result.
- Errors never contain credentials. Storage credentials reach the scan UDF only as a CONNECTION name or a sealed envelope. The export script receives only the CONNECTION name and emits no script output.
- STS AssumeRole and Glue operations time out after 30 seconds.
- Every Iceberg REST, Lakekeeper, Unity Catalog, and OAuth2 token request goes through the one crate-private catalog HTTP client of `lakehouse-catalog`. It ends an attempt that stays silent for 10 seconds, retries only a transient failure of a request marked safe to repeat (every read and stage-create, never a namespace creation, a table creation, or a commit, whose operation owns its retries), up to 5 attempts, and starts no retry that could wait for its answer past 30 seconds after the first attempt. It reads an answer body for as long as the body keeps arriving.
- Every outbound HTTP client of the adapter, the scan UDF, and the export script honors `HTTPS_PROXY`, `HTTP_PROXY`, and `NO_PROXY` from the process environment, which a script's `%env` lines set. A client that ignores them is a defect.
- Exasol's own dispatcher throttles concurrent UDF VMs at 80% of the per-process memory limit.
- DSNs in the Makefile, bench scripts, and installer include `validateservercertificate=0`.
- The engine must be faster than single-node DataFusion, scale with added Exasol nodes, keep duplicate scanning minimal, and keep metadata overhead acceptable.
