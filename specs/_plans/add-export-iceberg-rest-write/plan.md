# Plan: add-export-iceberg-rest-write

## Summary

`EXPORT ... INTO SCRIPT LAKEHOUSE_EXPORT` writes the source rows as Parquet data files and commits them to a new Iceberg table through the Iceberg REST catalog on S3-compatible storage, creating the namespace and the table (#566, after #565). Each writer commits its files exactly once, `SINGLE_COMMIT = 'true'` makes the table appear only together with its rows, and vended storage credentials are renewed before they expire. The export is a fixed flow of four steps behind a trait, with Iceberg REST as the first implementation (decision [8]).

## Context

- The writer only counts rows (`crates/lakehouse-engine/src/export.rs`, `run_writer`), and its writer spec carries only the CONNECTION name. `ExportSpec` carries source column names, not types, so each writer checks the types itself.
- `lakehouse-catalog` has no catalog write call. Its catalog HTTP client retries a POST after HTTP 408, 429, 502, 503, or 504. `authed_post_json` caps an answer at 64 KiB, which is too small for table metadata, and the table load asks for `snapshots=refs`, which omits the ancestor snapshots that a tag check reads.
- The Exasol SQL type lives in `crates/vs-expression/src/exasol_type.rs`, which reads it from VS `dataType` JSON. `lakehouse-engine` re-exports it and maps only Arrow, Iceberg, Delta, and Hive types to it (ADR `exasol-sql-type-lives-in-vs-expression`).
- The adapter reads the CONNECTION in `adapter/connection.rs`. The scan reads it itself (`scan/storage_ref.rs`, `StorageCreds::from_json`). The catalog address, `oauth2_server_uri`, and the static storage endpoint have no plaintext gate. Only vended-storage resolution and the STS client refuse plain HTTP, and their messages name the virtual schema property.
- iceberg-rust (rev `da5cc19`): `RestCatalog::create_table` hardcodes `stage-create: false`, the `TableCommit` builder is crate-private, and `Transaction::commit` re-applies blindly after HTTP 409. A custom `iceberg::Catalog` whose `update_table` records the commit's requirements and updates obtains them (spike lk_6).
- iceberg-rust's credential hook: `OpenDalStorageFactory::S3 { customized_credential_load }` takes a `CustomAwsCredentialLoader` that replaces the static key provider of each per-path opendal operator, and reqsign calls it again when the cached credential is within 120 s of `expires_in`. iceberg-rust reads neither `client.refresh-credentials-endpoint` nor `s3.session-token-expires-at-ms`.
- Iceberg names: § Reserved Field IDs lists metadata columns (`_file`, `_pos`, ...) "that can be used in user data schemas", and iceberg-rust's `is_metadata_column_name` resolves a scan projection of such a name to the metadata column. For a flat schema the spec and iceberg-rust set no other name rule than uniqueness (`IndexByName` refuses a repeated name), and a `.` in a name is literal.
- Lakekeeper (spike worktree `lakehouse-engine-rs-spike566`, tests lk_0 to lk_6): stage-create answers HTTP 200 with `metadata.location` and vended keys. A staged table is invisible and reserves nothing. An `assert-create` commit creates the table with its rows, and repeating it returns 409. Eight concurrent creates of one name return one 200 and seven 409. Vended credentials live 3,599 s and are refused outside the table location. The local Iceberg REST fixture also accepts stage-create.
- Vended refresh on Lakekeeper v0.13.1: `/v1/config` lists `loadCredentials` in `endpoints`, and each `storage-credentials` entry carries `s3.session-token-expires-at-ms`. `loadCredentials` answers HTTP 200 for a staged table, and its credentials write under the staged location. A stage-create at a location that holds an object answers HTTP 400. Lakekeeper serves a cached credential for half its lifetime. SeaweedFS STS refuses a lifetime below 900 s, reports expired credentials as `InvalidAccessKeyId`, and refuses one table's credentials under another table's location with `AccessDenied`.
- In-UDF spike on the Docker Exasol, one node (`export_spike.rs`, `spike_udf_write.rs`, `spike_udf_write_lakekeeper.rs`): Arrow batches built from SDK values round-tripped 13 columns with static keys and 3 rows with Lakekeeper vended credentials, with 0 differing cells. The edge values were `DATE` 0001-01-01 and 9999-12-31, `TIMESTAMP` 0001-01-01 00:00:00.000001 and 9999-12-31 23:59:59.999999, the largest `DECIMAL(36,6)`, non-ASCII text, and `DOUBLE` extremes. Current-thread and 2-worker Tokio runtimes work inside the UDF.
- SDK values: `DECIMAL(p,0)` arrives as `Int32` for p ≤ 9 and `Int64` for p = 18, other `DECIMAL`s as `Numeric(Decimal { unscaled, scale })`, whose scale is that of the trimmed value: `1.50` in `DECIMAL(18,2)` arrives as unscaled 15 with scale 1 and is stored as `0.15` without rescaling. `DOUBLE`, `BOOLEAN`, `VARCHAR`, `CHAR` (padded), `DATE`, and `TIMESTAMP` arrive as `Double`, `Bool`, `String`, `Date`, and `Timestamp`, and NULL as `None`.
- `ColumnInfo`: `type_name` reads `DECIMAL(18,2)`, `DOUBLE`, `BOOLEAN`, `VARCHAR(20) UTF8`, `CHAR(5) UTF8`, `DATE`, and `TIMESTAMP(3)` (a plain `TIMESTAMP` too) to `TIMESTAMP(9)`. `typ` is `Int32` or `Int64` for `DECIMAL(p,0)` with p ≤ 18, `Numeric { precision, scale }` for every other `DECIMAL`, and `Timestamp { precision }`. `name` is the column position, never the source column name.
- Exasol refuses `TIMESTAMP WITH LOCAL TIME ZONE`, `HASHTYPE`, and `INTERVAL DAY TO SECOND` with `Column type not supported: <type>` (spelled `TIMESTAMP(3) WITH LOCAL TIME ZONE`, `HASHTYPE(16 BYTE)`, `INTERVAL DAY(2) TO SECOND(3)`), and `GEOMETRY` and `INTERVAL YEAR TO MONTH` with `VM error: Unknown data type found`, before any writer code runs. Only `TIMESTAMP(7)` to `TIMESTAMP(9)` reach the writer, and Exasol truncates their values to microseconds without an error. An unaliased expression column fails with `must name expression with a column alias`.
- Read back through a virtual schema, `VARCHAR(n)` and `CHAR(n)` columns have type `VARCHAR(2000000) UTF8` with the `CHAR` padding kept, and `TIMESTAMP(3)` has type `TIMESTAMP(6)` with equal values. Exasol stores `''` as NULL.
- Exasol evaluates the source before the writer reads its first row: a 1,000-row source that divides by zero at row 500 failed with `data exception - division by zero` under each commit mode, and no table existed.
- Tasks 3.1 and 3.2 measure what the spikes left open: the variants of `DECIMAL(p,0)` with 10 ≤ p ≤ 17 and of a nonzero-scale `DECIMAL` with p ≤ 17, the row count of a multi-writer export, the pre-read check inside Exasol, and an export through a forward proxy. The failure ordering on several nodes stays unmeasured.
- Structural changes (connection-creds, the export's target steps, the catalog crate's commit loop and expiring-credential holder, the `ALLOW_HTTP` option): `architecture.md` in this plan directory.

## Impact

- An export now writes data. Its pre-read check makes catalog calls only: it authenticates, refuses an existing table, and creates the missing namespace levels, even when the export then fails or writes no rows. It writes no probe to storage, so a storage error (wrong keys, no write access) shows when the writers write (decision [1]). In parallel mode the first writer may already have created the table, so such a failure can leave an empty table behind. It refuses a table that exists. Appending stays out of scope (#567).
- New export option `ALLOW_HTTP`, default `false`. Breaking for the #565 statements that ran over plain HTTP, the local Docker stacks included.
- The CONNECTION's catalog identity needs the rights to create namespaces and tables and to commit, and static storage keys need write access to the warehouse location. The read-only CONNECTION of the AWS perf stack cannot export.
- Only `SINGLE_COMMIT` needs a catalog that accepts staged table creation, which is how Iceberg REST makes a table appear only with its data (decision [8]). Lakekeeper and the local Iceberg REST fixture accept it. On a catalog that refuses it, a `SINGLE_COMMIT` export fails at its writer's first row, naming the catalog, and creates no table.
- A failed parallel export can leave the commits of some writers in the table. A failed writer deletes its uncommitted data files, best effort. What can remain are the data files of a writer that crashed, was killed, or could not delete them. In parallel mode they lie under the table location, where Iceberg orphan-file removal finds them. After a failed `SINGLE_COMMIT` export no table exists, so they need a storage-level cleanup. A parallel export that fails has no final commit to undo its writers' commits, because Exasol has no step after the last writer (decision [7]).
- With vended credentials, a writer renews them through the catalog's `loadCredentials` endpoint before they expire (decision [6]). Without the endpoint, a writer that outlives the credentials fails, stating their expiry. Static storage keys are never refreshed.
- The export refuses, before any row is read, Azure storage fields, SigV4 signing (AWS Glue's Iceberg REST route), a table location outside S3-compatible storage, a repeated column name, and a column named like an Iceberg reserved metadata column.
- A `GEOMETRY`, `HASHTYPE`, `INTERVAL`, or `TIMESTAMP WITH LOCAL TIME ZONE` column fails with Exasol's own error. A `TIMESTAMP(7)` to `TIMESTAMP(9)` column is refused with a hint to cast it to `TIMESTAMP(6)` (decision [3]), except in a zero-row source, which succeeds with 0 rows and no table.
- The refusal of `TRUNCATE`, `REPLACE`, and `CREATED BY` states that the export never truncates or replaces a table.

## Dependencies

- `lakehouse-catalog` gains direct `async-trait` (the private `iceberg::Catalog` impl) and `rand` (commit back-off jitter) dependencies, pinned in the root `[workspace.dependencies]` if absent.
- `lakehouse-catalog` gains a direct `reqsign-core` dependency, because `ProvideCredential::provide_credential` takes a `reqsign_core::Context` that `iceberg-storage-opendal` does not re-export. Pin it to the version `iceberg-storage-opendal` resolves (3.3.2 in `Cargo.lock`), so both name the same trait.

## Open Questions

- Idempotency of catalog writes (#TBD): the catalog HTTP client retries every POST, and this plan adds the first state-changing requests (create namespace, create table, commit). Which requests may be repeated, who retries them (the client or the commit loop), and how a writer learns what happened after an unknown outcome needs a team decision (decision [2], Open). Reviewer asked to discuss it separately; this plan keeps the loop as written.
- An upstream iceberg-rust change that exposes a commit's requirements and updates (#TBD), so the commit loop no longer needs the private capture `Catalog` of tasks 1.3 and 1.4: needs a human-opened issue (decision [2]).
