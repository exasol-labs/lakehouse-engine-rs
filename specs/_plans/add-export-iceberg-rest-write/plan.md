# Plan: add-export-iceberg-rest-write

## Summary

`EXPORT ... INTO SCRIPT LAKEHOUSE_EXPORT` writes the source rows as Parquet data files and commits them to a new Iceberg table through the Iceberg REST catalog on S3-compatible storage, creating the namespace and the table (#566, after #565). Each writer commits its files exactly once, `SINGLE_COMMIT = 'true'` makes the table appear together with its rows, and a column of an unsupported type fails the export before any data is written, naming the column where the writer refuses it.

## Context

- After #565 the writer only counts rows (`crates/lakehouse-engine/src/export.rs`, `run_writer`). Its writer spec carries only the CONNECTION name.
- The engine has no catalog write call. `lakehouse-catalog` reaches Iceberg REST through its own catalog HTTP client, which retries a POST after HTTP 408, 429, 502, 503, or 504. Its `authed_post_json` caps an answer at 64 KiB, which is too small for table metadata.
- The existing table load asks for `snapshots=refs`, which omits ancestor snapshots. The tag check needs `snapshots=all`.
- iceberg-rust (pinned rev `da5cc19`) writes Parquet data files and builds fast-append snapshots. Its `RestCatalog::create_table` hardcodes `stage-create: false`, its `TableCommit` builder is crate-private, and `Transaction::commit` re-applies blindly after HTTP 409. A custom `iceberg::Catalog` whose `update_table` takes the commit's requirements and updates is the measured way to obtain them (spike lk_6).
- Iceberg REST OpenAPI: `stage-create: true` initializes and returns metadata without creating the table. A commit with requirement `assert-create` then creates it, and HTTP 500, 502, and 504 on a commit mean "the commit state is unknown".
- Live Lakekeeper measurements (spike worktree `lakehouse-engine-rs-spike566`, tests lk_0 to lk_6): vended credentials live 3,599 s and are refused outside the table location. Stage-create returns HTTP 200 with `metadata.location` and vended keys. A staged table is invisible and reserves nothing. A staged commit with `assert-create` creates the table with its rows, and repeating it returns HTTP 409. Eight concurrent creates of one name return one 200 and seven 409. The prefix comes from `defaults.prefix`. The local suite's plain Iceberg REST fixture also answers stage-create with HTTP 200 (spike 8b), so the pre-read check runs on both E2E stacks.
- The next 12 bullets are measurements of an in-UDF spike on the Docker Exasol and the Lakekeeper stack (spike worktree: `crates/lakehouse-engine/src/export_spike.rs`, `crates/lakehouse-e2e/tests/e2e_local/spike_udf_write.rs`, `crates/lakehouse-e2e/tests/spike_udf_write_lakekeeper.rs`).
- A writer inside the UDF built Arrow batches from SDK values, wrote Parquet, and committed. A virtual schema over the new namespace returned 5 rows of 13 columns with 0 differing cells, and an Exasol-side `MINUS` returned 0 rows.
- Through Lakekeeper with vended credentials only, the same round trip returned 3 rows with 0 differing cells.
- A current-thread and a 2-worker multi-thread Tokio runtime both work inside the UDF. `iceberg-rest:8181`, `seaweedfs:8333`, and `lakekeeper:8181` resolve inside the Exasol container, and the `.so` loads.
- An export with `WRITERS_PER_NODE = '4'` succeeded. Its final row count was not checked.
- SDK value variants: `DECIMAL(p,0)` arrives as `Int32` for p ≤ 9 and as `Int64` for p = 18. `DECIMAL(18,2)` and `DECIMAL(36,6)` arrive as `Numeric(Decimal { unscaled, scale })`. `DOUBLE` arrives as `Double`, `BOOLEAN` as `Bool`, `VARCHAR` and `CHAR` as `String` with the `CHAR` padding, `DATE` as `Date(NaiveDate)`, `TIMESTAMP` as `Timestamp(NaiveDateTime)`, and NULL as `None`.
- A `Numeric` value's `scale` is the scale of the trimmed value, not the column scale: `1.50` in a `DECIMAL(18,2)` column arrives as unscaled 15 with scale 1, and `100.00` and `0.00` arrive with scale 0. Written without rescaling to the column scale, `1.50` is stored as `0.15`.
- Edge values round-trip: `DATE` 0001-01-01 and 9999-12-31, `TIMESTAMP` 0001-01-01 00:00:00.000001 and 9999-12-31 23:59:59.999999, the largest `DECIMAL(36,6)`, non-ASCII text, and `DOUBLE` extremes.
- `ColumnInfo.type_name` spellings: `DECIMAL(18,2)`, `DECIMAL(9,0)`, `DOUBLE`, `BOOLEAN`, `VARCHAR(20) UTF8`, `CHAR(5) UTF8`, `DATE`, `TIMESTAMP(3)` (a plain `TIMESTAMP` too), `TIMESTAMP(6)`, and `TIMESTAMP(9)`. `ColumnInfo.typ` is `Int32` or `Int64` for `DECIMAL(p,0)` with p ≤ 18, `Numeric { precision, scale }` for every other `DECIMAL`, and `Timestamp { precision }` for `TIMESTAMP(p)`. `ColumnInfo.name` is the column position (`"0"`, `"1"`, ...), never the source column name.
- Exasol refuses most unsupported types before any writer code runs. `TIMESTAMP WITH LOCAL TIME ZONE`, `HASHTYPE`, and `INTERVAL DAY TO SECOND` fail with `Column type not supported: <type>`, spelled `TIMESTAMP(3) WITH LOCAL TIME ZONE`, `HASHTYPE(16 BYTE)`, and `INTERVAL DAY(2) TO SECOND(3)`. `GEOMETRY` and `INTERVAL YEAR TO MONTH` fail with `VM error: Unknown data type found`, which names no column or type. Issue #566 accepts Exasol's own error. Only `TIMESTAMP(7)` to `TIMESTAMP(9)` reach the writer's own type refusal. An unaliased expression column fails with Exasol's `must name expression with a column alias`.
- Exasol truncates a `TIMESTAMP(9)` value to microseconds before the UDF reads it, without rounding and without an error: `.999999999` arrives as `.999999`, and `.000000500` as `.000000`.
- Read back through a virtual schema, `VARCHAR(n)` and `CHAR(n)` columns have type `VARCHAR(2000000) UTF8` with `CHAR` padding and `LENGTH` kept, and a `TIMESTAMP(3)` column has type `TIMESTAMP(6)` with equal values. `DECIMAL`, `DOUBLE`, `BOOLEAN`, `DATE`, and `TIMESTAMP(6)` keep their types. Exasol stores `''` as NULL.
- Exasol evaluates the source before the writer reads its first row. A source of 1,000 rows that divides by zero at row 500 failed with `data exception - division by zero` under `SINGLE_COMMIT`, the default, and `WRITERS_PER_NODE = '4'`, and no table existed afterwards. The same source without the failing row exported 1,000 rows. Measured on one node.
- Unmeasured: the failure ordering on several nodes; the value variants of `DECIMAL(p,0)` with 10 ≤ p ≤ 17 and of a nonzero-scale `DECIMAL` with p ≤ 17; the row count of a 4-writer export; the stage-create pre-read check inside Exasol; an export through a forward proxy. The E2E tests of tasks 4.1 and 4.2 measure each of them except the multi-node ordering.
- The adapter reads the CONNECTION in `adapter/connection.rs`. The scan reads it itself (`scan/storage_ref.rs`) and parses its storage fields with `lakehouse_catalog::StorageCreds::from_json`. The export follows the scan's pattern, so it does not depend on vs-adapter.
- The CONNECTION's catalog address, `oauth2_server_uri`, and static storage endpoint have no plaintext gate today. Only the vended-storage resolution (`lakehouse-catalog/src/storage.rs`) and the STS client refuse plain HTTP, and their messages name the virtual schema property.
- The local stack's proxy filter (`scripts/proxy/filter`) answers a matching catalog request with HTTP 403. A test that routes its script through the proxy gets a catalog that refuses one request.
- `ExportSpec` carries source column names, not types, so the type check runs in the writer, once per writer.
- The writer builds Arrow batches from SDK values inside the `.so`. No Arrow type crosses the `.so` boundary.
- Structural changes (a new engine module, connection-creds, parses the CONNECTION password for vs-adapter and the export; the export depends on connection-creds, `lakehouse-catalog`, and type-mapping, not on vs-adapter; the catalog crate owns the commit loop; the writer flow; the `ALLOW_HTTP` option): see `architecture.md` in this plan directory.

## Impact

- An export now writes data: it creates the namespace levels and the table that `TABLE_NAME` names, and it refuses a table that already exists. Appending stays out of scope (#567).
- New export option `ALLOW_HTTP`, default `false`. An export through a plain-HTTP catalog or storage, including the local Docker stacks, now needs `ALLOW_HTTP = 'true'`. Breaking for the in-development #565 statements that ran over HTTP without it.
- The CONNECTION's catalog identity needs the rights to create namespaces and tables and to commit, and static storage keys need write access to the warehouse location. The read-only CONNECTION of the AWS perf stack cannot export.
- A missing namespace is created before any row is read, even when the export later fails or writes no rows.
- Every export, parallel mode included, needs a catalog that accepts staged table creation (Iceberg REST `stage-create: true`), because the pre-read check stages the table to find a location for its storage probe (decision [1]). Lakekeeper and the local Iceberg REST fixture accept it. On a catalog that refuses it, every export fails before any row is read, with an error that names the catalog and states that the export needs staged table creation.
- A failed parallel export can leave the commits of some writers in the table. A failed export can leave uncommitted data files and one probe object in storage.
- With vended credentials a writer must finish within the vended lifetime (Lakekeeper: one hour), because the credentials are not refreshed (decision [6]). A `SINGLE_COMMIT` export runs one writer for the whole source, so it reaches the limit first. Refreshing through `client.refresh-credentials-endpoint` is an accepted follow-up outside this plan, and it matters only for a vended-credential export whose writer runs longer than an hour; static credentials are unaffected.
- The export refuses, before any row is read, a CONNECTION with Azure storage fields or SigV4 signing (AWS Glue's Iceberg REST route), a catalog whose table location is not on S3-compatible storage, and a source with a repeated column name.
- A `GEOMETRY`, `HASHTYPE`, `INTERVAL`, or `TIMESTAMP WITH LOCAL TIME ZONE` column fails with Exasol's own error, which for `GEOMETRY` and `INTERVAL YEAR TO MONTH` names no column. A `TIMESTAMP(7)` to `TIMESTAMP(9)` column is refused with a hint to cast it to `TIMESTAMP(6)`, because Exasol truncates its values to microseconds before the export reads them (decision [3]).
- The refusal of `TRUNCATE`, `REPLACE`, and `CREATED BY` now states that the export never truncates or replaces a table, instead of "the export only appends rows".
