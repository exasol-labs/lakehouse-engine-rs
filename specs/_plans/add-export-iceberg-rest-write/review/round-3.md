## Premortem

Six months from now this plan failed catastrophically. Why?

1. Task 2.2 moved the scan's emit type onto `exasol_type_from_column_info`, which matches `type_name` spellings measured on Exasol 2025.1.16 only. CI's `E2E (8.29.x)` leg declares a bare `TIMESTAMP`, the reader calls it unrecognized, the scan emits `Utf8` into a TIMESTAMP column, and `emit_batch` rejects every timestamp scan. The scan's own unit tests failed first, and the implementer bent the test helper instead of the reader. Route: Feasibility [UNSTATED_ASSUMPTION].
2. The write crate grew its own table load, existence check, and `loadCredentials` parser with a copy of the longest-prefix credential rule. A later fix in `vended.rs` missed the copy, and a renewal picked the wrong `storage-credentials` entry an hour into an export. Route: Design Depth [ARCHITECTURE_DRIFT] and [ADR_CONFLICT].
3. Task 1.6 put the Iceberg REST OAuth2 token on the expiring holder with "the same skew rule as Unity's", and Unity refuses a grant without `expires_in`. Every virtual schema on a catalog that omits it failed at its first request, and the recorded specs still promised one grant per statement. Route: Requirement Quality [REQUIREMENT_CONFLICT].

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md § Implementation Tasks 2.2 (both bullets) and 3.3; § Context bullets 20 and 21; architecture.md § Components, vs-expression line
- Issue: Task 2.2 classifies by "`TIMESTAMP(p)` from `Timestamp { precision }` with a `type_name` of exactly `TIMESTAMP(p)`; `DOUBLE`, `BOOLEAN`, and `DATE` by exact `type_name`", and then moves the scan onto that reader with "a `DECIMAL(p,0)` with p ≤ 9 emits as `Int32` and p ≤ 18 as `Int64` ... Its existing tests pass unchanged." Four facts in the repository contradict this. (1) The scan's test helper builds `type_name: format!("{typ:?}")` and sets `precision: None` for `Int32` and `Int64` (`crates/lakehouse-engine/src/scan/declared_columns_test_support_tests.rs:12`). Cases such as `(ExaType::Int32, DataType::Int32)` and `ExaType::Timestamp { precision: 6 }` in `emit_tests.rs` would therefore come back unrecognized and emit as `Utf8`, so the tests cannot pass unchanged. (2) `scan/emit.rs:190` states the scan's rule: "The reported variant IS the bin Exasol chose, so nothing is re-derived from a type string." ADR `declared-output-column-single-authority-emit-type` makes the declared column the single authority. Task 2.2 re-derives the integer bins from p, for the very range that Context bullet 24 calls unmeasured. (3) `crates/vs-expression/src/exasol_type.rs:199` states "Exasol 8.x parses no TIMESTAMP precision". CI runs the local E2E, scans and exports alike, on `exasol/docker-db:8.29.13` (`.github/workflows/ci.yml:343`), where a declared `TIMESTAMP` has no `(p)`. The measured spellings in Context bullets 20 and 21 come from the default 2025.1.16 image only. (4) `ColumnInfo.precision` is an `Option`, and the plan never records what the SLC reports for an `Int32` or `Int64` column. The spike code used `c.precision.unwrap_or(18)`. The scan's partial-aggregate path (`partial_agg.rs:236`, `:363`) also calls `target_arrow_type`, so a wrong bin fails `COUNT` pushdowns too.
- Fix: In task 2.2, classify a column by its reported `typ` and use `type_name` only for the export's own extra check. Accept a bare `TIMESTAMP` as precision 3. Take p for an `Int32` or `Int64` column from `type_name` when `ColumnInfo.precision` is `None`. Keep the scan's integer bins on the reported `ExaType::Int32` and `ExaType::Int64` variants instead of deriving them from p. State that `declared_columns_test_support_tests.rs` keeps `format!("{typ:?}")` spellings, so the scan's tests pass unchanged only under this rule. In task 3.3, add a run of `make e2e-up test-e2e` with `EXASOL_IMAGE=exasol/docker-db:8.29.13`. Add to § Context the `type_name` and `precision` that 8.29.13 and 2025.1.16 report for input and output columns. In architecture.md § Components, change the vs-expression line from "from UDF input column metadata" to "from UDF input and output column metadata".
- Escalation: MECHANICAL (settled by reading the scan's tests and helper, `scan/emit.rs`, `exasol_type.rs`, and `ci.yml`)

- Fix: Add a DELTA:CHANGED scenario to catalog/rest-catalog-oauth-auth. The session sends the granted token on every request until the token reaches its renewal point (`expires_in` minus the skew), then runs one new grant. A grant answer without `expires_in` keeps its token for the session's life. No token the session has held appears in an error. Add a DELTA:CHANGED block to catalog/pushdown-catalog-session that allows one more grant for each token that reaches its renewal point, and changes the Background's redaction sentence to every token the session has held. State the `expires_in` rule in task 1.6. Map the new scenario to task 1.6's renewal unit test in § Scenario Coverage.
