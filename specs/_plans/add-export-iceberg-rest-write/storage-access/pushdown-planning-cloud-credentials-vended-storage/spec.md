# Feature: Vended Storage Resolution

When the CONNECTION sets `use_vended_credentials` to true, the adapter resolves the effective scan storage from a `loadTable` response through one function. The feature covers the `X-Iceberg-Access-Delegation` header, store-address resolution, backend selection from the table location's URI scheme, host-based selection of a vended Azure SAS, the error when the catalog vends no usable credential, and joins whose sides resolve to different backends.

## Background

* The adapter loads a table with one self-issued `loadTable` GET, as often as `file-planning/pushdown-statement-state` states. The raw `LoadTableResult` feeds both Iceberg file planning and vended-credential extraction, because `RestCatalog::load_table` drops the response `config` and `storage_credentials`.
* One credential-source selection serves both backends: the longest `storage_credentials` entry whose non-empty `prefix` prefixes the table location, else the flat `config` map. The Iceberg REST spec says clients choose the longest prefix. A matched entry is authoritative for the whole credential set, so a key it omits does not fall back to `config`. The prefix comparison lowercases the URI scheme on both sides and compares everything after `://` byte-exactly.
* The backend comes from the table location's URI scheme alone: `s3://` and `s3a://` select S3, `abfss://` and `abfs://` select ADLS, and any other or missing scheme is an error naming the scheme. The Iceberg table spec makes `location` an absolute path, so a location without a scheme is a malformed catalog response.
* Under vending, credentials (the S3 key pair and session token, or the ADLS SAS) come from the selected credential source alone and are never backfilled from the CONNECTION. Addressing (`endpoint`, `region`) comes from the CONNECTION when it states a non-empty value, else from the selected source, resolved per field. When neither states one, the field is empty and the AWS default chain applies.
* `path_style` resolves in three ordered steps: the CONNECTION's stated value, else the source's `s3.path-style-access`, else whether an `endpoint` was resolved. The last step stays because `register_side_store` gates `endpoint` on `path_style`. Both catalog kinds share this precedence through `s3_backend`.
* The vended ADLS SAS key is host-suffixed on the wire (`adls.sas-token.<host>`) and flat in the backend (`adls.sas-token`), because the downstream reader accepts only the flat form. The host comparison with the table location's host is case-insensitive (RFC 3986 §3.2.2). The account name is the first dot-separated label of that host, taken verbatim, because `iceberg-storage-opendal` compares it byte-exactly against the account in each file URI as a wrong-account guard.
* A catalog cannot downgrade the transport on its own authority. A resolved plaintext address, either a vended or CONNECTION-configured `http://` S3 endpoint or an `abfs://` ADLS location, is honoured only when the `ALLOW_HTTP` virtual-schema property is true (default false). `ALLOW_HTTP` is resolved outside the catalog crate and passed in as a plain boolean.
* Each side of a join resolves its own effective storage and backend, and the adapter never compares them at plan time. A backend difference or an ADLS storage-account difference yields distinct DataFusion registry keys. Two ADLS containers of one account collapse onto one key, and the scan's store-registration precondition refuses that case (`scan-aggregation/scan-execution-join`).
* A credential never appears in returned SQL or in an error message, except that a vended value appears in the SQL as the sealed envelope's ciphertext (`storage-access/scan-spec-credential-reference`). `redact_credentials` matches the `adls.sas-token` label by case-insensitive substring and truncates to the next delimiter. Every error path returns `Result` and never panics, because a panic in a UDF is an abnormal VM exit that kills every sibling VM of the statement part. Every error names the location's storage host, scheme, or expected config key.
* `file-planning/pushdown-planning-file-resolution` rejects an absent table location before the vended and static split, so this feature never sees one.
* See `storage-access/pushdown-planning-cloud-credentials` for SigV4 catalog signing, the Glue REST prefix, and the static-credential path.
* The export writer reads the S3 credentials a create, stage-create, load, or `loadCredentials` answer vends through `vended_s3_credentials` and `CatalogSession::load_credentials`, which apply the same credential-source selection and return a `VendedS3Credentials` value with the expiry from `s3.session-token-expires-at-ms`.

## Scenarios

### Scenario: One concept-level call resolves the effective scan storage from a loadTable response

* *GIVEN* the vended sequence written out at its single call site, select the credential source for the location, then build the storage backend that source describes, whose steps `vended_credential_config` and the shared per-backend construction functions are the mechanism
* *WHEN* the planning layer resolves the effective storage for a table whose `loadTable` response has been fetched and for which `use_vended_credentials` is enabled
* *THEN* exactly ONE function, `resolve_vended_storage`, SHALL own the whole sequence, taking the `loadTable` response, the location anchor, the resolved `ALLOW_HTTP` value, and the CONNECTION's configured store address, and returning `Result<StorageBackend, UdfError>`
* *AND* `resolve_vended_storage` MUST NOT take a storage backend, a `ConnectionCreds`, or any other value carrying a credential field as a parameter, so "no CONNECTION CREDENTIAL is read under vending" stays enforced by what its parameters CAN carry
* *AND* the store-address parameter SHALL be a type declaring EXACTLY the CONNECTION's `endpoint`, `region`, and `path_style`, with exactly one conversion from `ConnectionCreds` declared beside it, and a source-level probe SHALL assert that its declaration names no field spelled `access_key`, `secret_key`, `session_token`, `token`, `account_key`, `sas_token`, or `password`
* *AND* the type SHALL carry `path_style` as an OPTION of boolean, because the resolution chain branches on whether the CONNECTION stated a value
* *AND* every field of the type SHALL stay non-`pub` and SHALL be read through an accessor, and the existing probe asserting that non-`pub` property SHALL cover the added field without being rewritten to enumerate fields by name
* *AND* the `ALLOW_HTTP` parameter SHALL NOT be read as an exception to that rule: it carries one virtual-schema boolean resolved outside this crate, names no credential, and cannot supply one
* *AND* `resolve_vended_storage` SHALL be the ONLY Iceberg-path vended entry point reachable from outside the `lakehouse-catalog` crate, and EVERY mechanism step, the per-catalog wire extraction and the shared policy and construction functions alike, SHALL stay crate-private
* *AND* the one scoped exception SHALL be the export writer's read of its vended S3 credentials: `vended_s3_credentials`, over the same credential-source selection, and `CatalogSession::load_credentials` SHALL be public, SHALL return a `VendedS3Credentials` value whose `Debug` shows no value, and SHALL refuse a missing key or an unreadable `s3.session-token-expires-at-ms` naming the key and no value, so the vended config keys stay known to the `lakehouse-catalog` crate alone
* *AND* the credential-source selection, the longest `storage_credentials` entry whose non-empty `prefix` prefixes the location, else the flat `config` map, SHALL run EXACTLY ONCE per call, SHALL be the SAME scheme-agnostic selection for both backends, and SHALL supply every value the resolved backend carries
* *AND* that prefix comparison SHALL be made with the URI SCHEME of both the location and the entry `prefix` lowercased, and with everything after `://` compared byte-exactly, because the backend variant is selected from a CASE-INSENSITIVE scheme (RFC 3986 §3.1): a response spelling the location's scheme differently from an entry's `prefix` would otherwise miss the entry that governs that location and silently read the flat `config` map instead, while a bucket, container, or object key stays case-sensitive because two buckets differing only in case are two buckets
* *AND* a matched `storage_credentials` entry SHALL remain authoritative for the whole credential set: a key that entry omits MUST NOT fall back to the flat `config` map, because the Iceberg REST rule is read per credential SET rather than per key
* *AND* `anchor` SHALL be the table's own location, that is what `storage_credentials[*].prefix` matches against AND what the backend variant is selected from, so an HTTPS catalog URI passed as the anchor is rejected as an unsupported scheme rather than silently selecting the flat `config` map
* *AND* the `use_vended_credentials` gate SHALL stay at the call site rather than becoming a parameter of `resolve_vended_storage`, because a boolean that switches a function between "do the work" and "return the input" is a decision the function declined to make
* *AND* that same gate SHALL also select the scan-spec storage wire variant, the SEALED envelope under vending when the sealing key exists, the named plan-time refusal under vending when it does not (no-auth), a connection reference otherwise, through the ONE pure selection function `storage-access/scan-spec-credential-reference` specifies, so the variant can never disagree with the resolver that produced its payload and no site chooses it independently
* *AND* the format readers' own vended/static split SHALL stay separate from that selection and MUST NOT return that wrapper, because each reader uses the concrete backend immediately for its own plan-time manifest or log read
* *AND* the catalog-auth secrets and any minted bearer value MUST NOT appear in any returned SQL string or error message; the vended STS keys, the vended session token, the vended SAS, and any static Azure account key or SAS token MUST NOT appear in any error message, and the VENDED values among them appear in the returned SQL string ONLY as the sealed envelope's ciphertext, never plaintext
