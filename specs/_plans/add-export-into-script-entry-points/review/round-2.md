## Premortem

Six months from now this plan failed. Three stories:

1. **The spec and the installer disagree.** The recorded spec says the template prints the export role block on every install, including SYS. `install.sh --export-connection` suppresses the block once it has run the grants. A later contributor writes a test from the spec, which fails, and "fixes" the installer to print the block again. Operators then re-run statements the installer already ran, or think the grants did not run. Routed to Requirement Quality.
2. **The installer grant path never ran against a real Exasol.** Only the `exapump` stub ever answers the `EXA_ALL_CONNECTIONS` and `EXA_ALL_ROLES` queries. On a real database, `extract_query_value` misreads the answer, so `--export-connection` always warns that the CONNECTION does not exist and prints the block. The acceptance criterion falls back to its round-1 state, and CI stays green. Routed to Intent Fidelity.
3. **The multi-node proof stalls.** The task 1.13 command omits the SQL port and SYS password, so `install-slc` cannot run its `ALTER SYSTEM` on the cluster. After a manual fix, the filtered cloud test exports `AT` a CONNECTION that a fresh cluster does not have. The team raises the Open Question and ships the SINGLE_COMMIT multi-node criterion unverified. Routed to Feasibility.

## Intent Fidelity

#### [SCOPE_REDUCTION] ADVISORY
- Location: plan.md § Verification (Scenario Coverage rows "The installer creates the export scripts and prints the export role" and "The installer grants the export role for a named export CONNECTION", and the third note below the table)
- Issue: #565's last acceptance criterion reads "E2E tests cover every case above". The first case above it is "The installer creates both scripts and grants them access to the catalog CONNECTION." The plan proves the installer's grant path only against the `exapump` stub (`test_export_connection_grants_role`) and through one manual row. The stub encodes the plan's own assumptions about what `exapump` prints for the `EXA_ALL_CONNECTIONS` and `EXA_ALL_ROLES` queries. `export_role_user_exports_rows` proves that the role's statements work, but it runs them by hand, not through `install.sh`. The THEN step "a re-run SHALL grant them again, which restores the script grants that replacing the scripts dropped" describes real database behavior, and the stub cannot show it. The CI job `install-script-e2e` (`.github/workflows/ci.yml:286-326`) already runs this branch's `install.sh` against a real Exasol.
- Fix: Add a Group B task that extends `install-script-e2e`. The task creates a CONNECTION with `exapump sql`, runs `install.sh` with `--export-connection <name>` twice, and after the second run asserts through the privilege system tables that `LAKEHOUSE_EXPORT_ROLE_LHVS` holds `EXPORT`, the `CONNECTION` grant, `EXECUTE` on both export scripts, and `ACCESS` on the CONNECTION for both. Add that job to the two installer rows of § Scenario Coverage. If you skip this, add a plan.md § Context bullet stating that the installer cases are proved by the stub suite and a manual check, as a deviation from "E2E tests cover every case above" for the requester to acknowledge.

## Feasibility

#### [HIDDEN_DEPENDENCY] ADVISORY
- Location: plan.md tasks 1.12 and 1.13
- Issue: (1) Task 1.13 runs `make install-slc bucketfs-upload-so EXASOL_HOST=<cluster> LH_BUCKETFS_PORT=<port> BUCKETFS_WRITE_PASS=<pass>` and cites `bench/run.sh:433-436` as its source. That bench command also passes `LH_EXASOL_PORT` and `EXASOL_SYS_PASSWORD`. `install-slc` runs `ALTER SYSTEM SET SCRIPT_LANGUAGES` through `exasol://sys:$(EXASOL_SYS_PASSWORD)@$(EXASOL_HOST):$(LH_EXASOL_PORT)` (Makefile:146-155), whose defaults are `exasol` and `28563` (Makefile:5, :61). On a real cluster, the alias registration therefore fails, or it reaches the wrong port. (2) Task 1.12 does not name the CONNECTION that `cloud_export_writer_counts` exports `AT`. Both export scripts call `ctx.connection(name)`. Only `setup_cloud_vs` (`cloud_e2e_test.rs:383-399`) creates a CONNECTION, and a run filtered to this one test never calls it. On a fresh ephemeral cluster, the export then fails with "connection ... does not exist". If `LH_EXASOL_USER` is not SYS, both export scripts also need `ACCESS ON CONNECTION ... FOR SCRIPT`, and task 1.13 creates the scripts without that grant.
- Fix: In task 1.13, add `LH_EXASOL_PORT=<sql port> EXASOL_SYS_PASSWORD=<sys password>` to the `make` command, matching `bench/run.sh:433-436`. In task 1.12, name the CONNECTION the test uses (for example `GLUE_CATALOG_CREDS`). Have the test create it with `build_create_connection_sql`, and, when the cloud user is not SYS, grant `ACCESS ON CONNECTION <name> FOR SCRIPT` on both `CLOUD_LHVS` export scripts to that user.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: export/export-into-script/spec.md § Scenario "The installer creates the export scripts and prints the export role" and § Scenario "The installer grants the export role for a named export CONNECTION"; plan.md task 2.2, third bullet
- Issue: The first scenario has no condition on the flag. Its WHEN, "it creates the deployment scripts in the target schema", holds on every install. Its THEN steps require that "the printed next-step template SHALL create one export role ... and SHALL tell the operator to grant that role" and that "the template SHALL print the export role lines for every installing user, including `SYS`". Task 2.2 instead prints the block "unless `grant_export_role` ran the grants". The second scenario's last step, "print the export role lines instead of running them", also makes printing and running mutually exclusive. With `--export-connection` naming an existing CONNECTION, the merged spec therefore requires a block that the installer does not print, and a test written from the first scenario fails against the planned installer. The second scenario also contradicts itself. Its GIVEN is "a CONNECTION that exists in the target database", and its last AND step starts "when the named CONNECTION does not exist". So one scenario holds two incompatible preconditions.
- Fix: In export/export-into-script/spec.md, keep the script-creation THEN step of the first scenario unconditional. Move its two template steps into that scenario's own condition: "the install ran without `--export-connection`, or its named CONNECTION does not exist". In the second scenario, add "*AND* the printed template SHALL print only the line that grants `LAKEHOUSE_EXPORT_ROLE_<schema>` to each exporting user, not the role's statements", matching task 2.2's "Always end with `-- Exporters: GRANT LAKEHOUSE_EXPORT_ROLE_<schema> TO <user>;`". Move its last AND step into a new scenario, "The installer prints the export role when the named export CONNECTION does not exist", whose GIVEN states that the CONNECTION does not exist. Add the new scenario to § Scenario Coverage with `test_export_connection_grants_role`, and update task 2.3's assertion list to match.
- Escalation: MECHANICAL. The plan's own task 2.2 already settles what the installer does, and the fix only aligns the scenario text with it.

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: export/export-into-script/spec.md § Scenario "An export without a named CONNECTION fails before any data is read", THEN step
- Issue: "with an error that asks for `AT <connection>` naming the CONNECTION of the virtual schema" can be read as a requirement that the error names a specific CONNECTION. `LAKEHOUSE_EXPORT` cannot meet that reading: the statement names no virtual schema, and with no `AT` clause the export receives no CONNECTION name. Task 1.3 ("a message asking for `AT <connection>`") shows that the other reading is intended.
- Fix: Change the step to "with an error that asks for `AT <connection>`, where `<connection>` is the CONNECTION the virtual schema uses".

#### [COMPLETENESS_GAP] ADVISORY
- Location: export/export-into-script/spec.md § Background bullet 7; plan.md task 1.9 and § Scenario Coverage row "An empty source exports zero rows"
- Issue: Background bullet 7 states a deviation from #565 that the PR asks the requester to accept: "an empty source with a column of one of these types exports 0 rows without an error". No scenario and no test covers it. The empty-source scenario is restricted to supported types, and the type scenario to sources with at least one row. This behavior changed between SLC versions. On SLC 0.30.0, an empty TIMESTAMP WITH LOCAL TIME ZONE column failed with Exasol's own error (`notes/planning.md:24`). On 0.33.0 it exports 0 rows (`notes/planning.md:72`). Without a test, the next SLC bump can change it again and leave `docs/export.md` wrong.
- Fix: Add a scenario "An empty source with an unsupported column type exports zero rows": GIVEN a query that returns no rows and has one column of each refused type, THEN the statement SHALL succeed with a row count of 0. Prove it in `export_empty_source_reports_zero`, or in a new `export.rs` test, and add the row to § Scenario Coverage.
