## Feasibility

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Risks, bullets 3 and 4 (:119-120); new feature spec:65-75 and :205-209; decision-log § [17]
- Issue: the live spike closed two questions, and neither artifact states the conditions it ran under. Per the run's own description it used the local Docker stack — MinIO, therefore the S3-COMPATIBILITY flavor with path-style addressing — and one registration order (`partsupp` immediately after `part`). The plan makes the storage flavor the single value that differs between the local run and AWS (decision [16], spec:210-212), so the evidence comes from one branch of that fork while the conclusion is asserted for the other: plan.md:119 reads "That is the AWS ordering — data first, warehouse second — which every existing MinIO test inverts", which invites the reader to take the new run as something other than a MinIO run. Neither the order dependence nor the backend appears in spec:65-75, spec:205-209, or decision [17]. Consequence: the plan's only named open risk is the Glue `metadata-location` field, so a reader treats warehouse-creation-over-populated-prefix and the `part`/`partsupp` shape as closed for real S3, and the first AWS-flavor exercise of both is the billable box. Task 4.1's regression test also pins no registration order, so it cannot detect a version that rejects only the reverse order.
- Fix: In plan.md § Risks bullets 3 and 4, decision-log § [17], and new feature spec:65-75 and :205-209, state the spike's conditions in one clause each: Lakekeeper 0.13.1, local Docker, MinIO (S3-compatibility flavor, path-style), registration order `part` then `partsupp`. Delete or rewrite the "which every existing MinIO test inverts" clause so it cannot read as a claim that the new run was not on MinIO. Add one bullet to § Risks naming what stays unexercised off the billable path — the AWS S3 flavor with virtual-hosted addressing — and state that the manual AWS run (§ Manual Testing row 3) is its first exercise. Extend task 4.1 to register the colliding pair in BOTH orders, so the regression test does not depend on the enumeration order the spike happened to use.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: plan.md § Key interfaces, row "No destructive verb" (:64); tasks 3.5 (:138) and 4.1 (:139); new feature spec:59-64 and :172-174
- Issue: two round-1 fixes now forbid what the other requires, inside one crate. Spec:172-174 makes it normative that "the provisioning tool SHALL contain no drop, purge, or delete code path at all — no HTTP `DELETE` request and no purge parameter anywhere in its source", plan.md:64 repeats it as "no HTTP `DELETE` and no `purgeRequested` parameter anywhere in its source", and task 3.5 asserts it by source text over "the crate's own source". Task 4.1, in the same crate, requires the local verification to "Drop each throwaway source table from the source namespace WITHOUT purging its files" — and an Iceberg REST drop IS an HTTP `DELETE` whose purge switch is the `purgeRequested` query parameter (`iceberg-catalog-rest-0.10.0/src/catalog.rs:389` sends `("purgeRequested", "true")`; `drop_table` at :875 is the same `delete_table` call with `false`). So `crates/lakekeeper-provision/tests/provision_local_test.rs` must carry both banned tokens, and task 3.5's assertion either fails as soon as task 4.1 lands or silently scopes itself to `src/` — the plan says which nowhere, and the precedent it cites (`crates/lakehouse-catalog/tests/catalog_crate_boundary.rs`) uses `include_str!` on one named file, so the scanned set is a choice the implementer would have to invent. Secondary defect in the same pair: spec:59-61 gives the drop-without-purge rule the reason "because the same code path runs against the one physical copy of the shared TPC-H data on AWS", which decision [20] has since made false — the tool has no drop path, so no drop code path reaches AWS. The true reason is the one task 4.1 states (no live table may still hold the location under test).
- Fix: In new feature spec:172-174 and plan.md § Key interfaces row "No destructive verb", scope the prohibition to the shipped binary's own module tree — "no drop, purge, or delete code path anywhere under `crates/lakekeeper-provision/src/`" — and add a clause stating that the local-verification test's non-purging drop of its own throwaway tables is the single permitted exception, lives outside `src/`, and never runs against AWS. In task 3.5, name the scanned set explicitly as every file under `crates/lakekeeper-provision/src/` and state that `tests/` is out of scope by design. In spec:59-61, replace the "same code path runs against shared data on AWS" reason with the experiment-design reason task 4.1 already states: a live table still holding the location makes the assertion about exact-location reuse rather than about the location rule.

## Design Depth

No objection — axis checked. The round-1 fixes added no module, interface, or boundary: decision [19] names Terraform resources, decision [20] and [21] record accepted risks with their controls, and decision [17] removes work rather than adding it.
