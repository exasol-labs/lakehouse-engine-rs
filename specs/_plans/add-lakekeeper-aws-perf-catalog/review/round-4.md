## Feasibility

#### [COMPLETENESS_GAP] BLOCKER
- Location: `cloud-e2e-harness` spec:67-70; `plan.md:208` task 6.1 § DEMO RUNBOOK
- Issue: the command sequence the round-3 fix made normative does not produce a Lakekeeper demo, and one of its two forms produces a Glue run. Three defects, all verified against the real scripts. (1) Neither form includes `deploy/scripts/lakekeeper-up.sh <env>`, and the ordering constraint is mandatory: `secrets.sh` emits the Lakekeeper block only "while a Lakekeeper stack workspace exists for that same environment" (`aws-lakekeeper-perf-catalog` spec:449, spec:458), and `BENCH_CATALOG=lakekeeper` then fails naming the first empty variable (`cloud-e2e-harness` spec:25). `bench-remote.sh` runs `secrets.sh` itself at step `[3/4]` (`bench-remote.sh:69-70`), so `lakekeeper-up.sh` must precede the whole wrapper invocation. Task 6.1 names `lakekeeper-down.sh` in the closing teardown and never names `lakekeeper-up.sh` anywhere — the asymmetry marks this as an oversight, not a choice. (2) The wrapper form is written `AWS_PROFILE=... KEEP_ALIVE=1 ./bench-remote.sh <env>` with no `BENCH_CATALOG=lakekeeper`, while the unwrapped alternative in the same clause carries it. `bench/run.sh` defaults `BENCH_CATALOG` to `glue` (decision [10]), and `bench-remote.sh`'s own header records that caller-exported `BENCH_*` flows through untouched — so the two "equivalent" forms select different catalogs, and the first demonstrates Glue at a live customer session. (3) The unwrapped form starts at `cluster-up.sh`, but `cluster-up.sh` does not create the cluster: its header states it runs `c4` against existing nodes, and `bench-remote.sh:61-65` performs the `cluster-stack` `tofu apply` as a separate step `[1/4]` before it. The unwrapped sequence therefore works only against an already-applied cluster stack, which nothing states.
- Fix: Rewrite `cloud-e2e-harness` spec:67-70 and task 6.1's DEMO RUNBOOK to give the full ordered sequence in both forms. Wrapper form: `cluster-stack` `tofu apply` is done by the wrapper, so state `deploy/scripts/lakekeeper-up.sh <env>` FIRST, then `AWS_PROFILE=... BENCH_CATALOG=lakekeeper KEEP_ALIVE=1 ./bench-remote.sh <env>`. Unwrapped form: `tofu apply` in `deploy/cluster-stack` (or a reference to `deploy/README.md`'s numbered step 1), then `deploy/scripts/lakekeeper-up.sh <env>`, then `cluster-up.sh <env>`, then `secrets.sh <env>`, then `BENCH_CATALOG=lakekeeper make bench`. State in both that `lakekeeper-up.sh` MUST run before `secrets.sh`, citing the workspace-exists gate at `aws-lakekeeper-perf-catalog` spec:458. Add to the spec clause the billing obligation task 6.1 already carries — that both forms leave a running cluster and require an explicit `cluster-down.sh <env>` plus `lakekeeper-down.sh <env>`.

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `decision-log.md:250` decision [28] § Rationale; `aws-lakekeeper-perf-catalog` spec:244-250
- Issue: the third bound decision [28] rests on is false, and it is the bound that makes the seam look acceptable. The text reads: "the IN-VPC vantage does not have the exposure at all … so the benchmark run site — the unattended, repeated one — is already clean and only the interactive laptop path is affected." Under the round-3 fix to blocker 3, `lakekeeper-up.sh` is an operator-machine script in BOTH contexts, benchmark included (`decision-log.md:208`, `plan.md:77`), it always runs `lakekeeper-provision.sh` (task 3.1, `plan.md:200`; spec:139), and decision [7] hands that run the PUBLIC-IP URIs because it runs outside the VPC (`decision-log.md:87`). There is therefore no workflow in this plan in which the warehouse's write-and-delete S3 key pair avoids the public cleartext hop: EVERY deployment, benchmark included, is provisioned at least once from the laptop over plain HTTP across the public internet. The EC2 path can only ever be a later, redundant re-provision against a stack that was already provisioned the exposed way. The two round-3 fixes interact — narrowing the run-site claim (blocker 3) invalidated the acceptance rationale written for the cleartext seam (blocker 2) — and neither artifact notices. Secondary: decision [28]'s first bound, "it lasts for the duration of one provisioning run, not for the life of the deployment", describes the transmission window while the captured credential stays valid until teardown; the second bound supplies the real limit, so the first should not be phrased as a denial of it. Also note that of decision [20]'s four compensating controls for the bucket-wide grant, only "created and destroyed with the ephemeral stack" survives against a network observer holding the raw key — the primary control, the absent destructive verb in the script, does not transfer to an attacker running their own code. Decision [28] borrows [20]'s accepted blast radius without noting that.
- Fix: Replace the third bound in `decision-log.md` decision [28] § Rationale with the accurate statement: because `lakekeeper-up.sh` is operator-machine-only in both contexts and always provisions, every deployment — benchmark included — carries one public-vantage cleartext provisioning run, and the in-VPC vantage is clean only for the optional re-provision described in decision [23]. Reword the first bound to say the transmission lasts one run while the captured credential stays usable until `lakekeeper-down.sh` destroys the IAM user. Add one sentence stating that decision [20]'s absent-destructive-verb control does not bound a network observer, so the credential's own lifetime is the only bound that transfers. Add the same "every deployment is provisioned once from the public vantage" fact as an `*AND*` clause to `aws-lakekeeper-perf-catalog` spec:244-250, so the recorded seam cannot be read as avoidable by choosing the in-VPC run site, and mirror it in `plan.md:142` § Impact.

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `aws-lakekeeper-perf-catalog` spec:281-286 vs spec:287-290, one scenario; `decision-log.md:208` decision [23] § Scope; `plan.md:306` § Manual Testing row 5
- Issue: the run-site scenario now contradicts itself about what the EC2 caller can read, and the contradiction sits inside the verification step added to close round-3 blocker 3. Spec:283-284 states the EC2 run site is not required to hold "`tofu`, a deployer-grade IAM principal, and this stack's OpenTofu workspace state" — that is the whole basis for calling the lifecycle pair laptop-only. Spec:288-289 then requires the same EC2 caller's `LK_TARGET_*` values to be "supplied by the caller from that stack's outputs and SSM parameters", and § Manual Testing row 5 spells it out: "export … `LK_TARGET_*` from this stack's outputs and SSM `SecureString` parameters, with `LK_TARGET_CATALOG_URI` and `LK_TARGET_TOKEN_URI` set to the PRIVATE-IP vantage". OpenTofu outputs are reachable only through the workspace state the same scenario says the box does not hold. Checking what SSM actually carries under this plan: task 1.2 and spec:162-165 and spec:234 put the PostgreSQL password, the metadata-encryption key, the Keycloak bootstrap admin password, and the storage key pair in SSM — the catalog URI, the token URI, and the warehouse name are stack OUTPUTS only (task 1.3, `plan.md:195`). So the three values row 5 most needs have no stated route to the EC2 box. The row's other prerequisites are unstated too: it requires an in-VPC box whose instance profile can read the `data-stack` SSM root, this stack's SSM `SecureString` parameters, Glue, and S3, and no stack in this plan creates such a box or such a profile. Round 3's blocker named "its prerequisites are never stated"; the fix stated the lifecycle pair's prerequisites and left the provisioning site's unstated, so the designated closer for the user's run-site requirement cannot be executed as written.
- Fix: Choose one route and state it in both places. Either (a) add the catalog URI, token URI, and warehouse name to the stack's SSM parameters as plain `String` values in task 1.2 and in `aws-lakekeeper-perf-catalog` spec's stack scenario, and amend spec:287-290 to say the EC2 caller reads every `LK_*` value from SSM alone and never from OpenTofu outputs; or (b) amend spec:287-290 and `plan.md:306` to name the transfer explicitly — the operator reads the values on the machine holding the workspace state and carries them to the EC2 box (the `bench/.env` `secrets.sh` already generates with the private-IP URIs is the obvious carrier). Under either route, add one clause to the run-site scenario naming the EC2 box's required instance-profile permissions — `ssm:GetParameter` on both roots plus `kms:Decrypt` for the `SecureString` values, `glue:GetTables`, and `s3:GetObject` on the data prefix — and state in `plan.md:306` that the plan creates no such box.
