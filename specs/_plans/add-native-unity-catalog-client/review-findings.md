### crates/lakehouse-engine/src/adapter/catalog_client_tests.rs

#### [OUTDATED_COMMENT] Single-construction-site probe overstates what it enforces
- Location: lines 3-10 (doc comment on `catalog_kind_is_matched_only_at_the_construction_site`)
- Issue: The comment asserts "the constructor is the sole function typed on `CatalogKind`" and "matching the kind a second time downstream would fail this file's compilation." Both claims are false. `validate_creds(name, creds, kind: CatalogKind)` in `adapter/connection.rs:126` is also typed on `CatalogKind` and matches it exhaustively (authorized by plan task 3.2), and `read_connection`/`resolve_connection_config`/the dispatch pushdown-refusal all consume the kind. The probe only coerces two specific function pointers (`build_listing_virtual_tables`, `construct_catalog_client`) to fixed signatures; it does not and cannot detect a `match kind` added in a new downstream function. The test therefore gives false assurance that the single-construction-site invariant is compiler-enforced when it only pins that the listing pipeline's signature omits `CatalogKind`.
- Fix: In `crates/lakehouse-engine/src/adapter/catalog_client_tests.rs`, rewrite the doc comment on `catalog_kind_is_matched_only_at_the_construction_site` to state only what the probe actually enforces: that `build_listing_virtual_tables` compiles with a signature naming neither `CatalogKind` nor a `CatalogClient` (so the listing pipeline cannot branch on the kind), and that `construct_catalog_client` is the listing path's kind-to-client construction site. Remove the false "sole function typed on `CatalogKind`" and "matching the kind a second time downstream would fail this file's compilation" claims; note that credential validation (`validate_creds`) and the pushdown refusal legitimately consult the kind outside the listing pipeline.

### crates/lakehouse-engine/src/adapter/mod.rs

#### [DUPLICATE_OPERATION] `resolve_catalog_kind` is parsed twice on the createVirtualSchema path
- Location: `mod.rs:232` (`handle_create_virtual_schema`) and `mod.rs:211` (`resolve_connection_config`, called at `mod.rs:235`)
- Issue: `handle_create_virtual_schema` resolves the catalog kind at line 232 (to feed `construct_catalog_client`), then immediately calls `resolve_connection_config`, which resolves the same `CATALOG_KIND` property again at line 211 (to feed `read_connection`). The property is parsed and re-validated twice for one request. It is cheap and idempotent so there is no correctness impact, but `resolve_connection_config` already computes the kind and discards it, forcing the caller to recompute. (The pushdown path's separate resolution at `mod.rs:163` is intentional — it must refuse Unity before any credential resolution — and should stay.)
- Fix: In `crates/lakehouse-engine/src/adapter/mod.rs`, extend `resolve_connection_config` to return the resolved `CatalogKind` as part of its tuple (or accept it as a parameter), and have `handle_create_virtual_schema` reuse that single resolution for `construct_catalog_client` instead of calling `resolve_catalog_kind` a second time at line 232. Leave the pushdown-path early refusal at line 163 unchanged.
