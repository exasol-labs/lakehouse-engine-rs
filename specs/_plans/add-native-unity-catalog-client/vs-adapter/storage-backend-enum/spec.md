# Feature: Storage Backend Enum

Gives the storage-backend decision exactly one home: a `StorageBackend` enum whose variant IS the backend, so every other module asks the enum for what it needs instead of deciding for itself which backend it is talking to.

## Background

This delta admits a third backend-selection site for native Unity Catalog credential vending. It supersedes both the enum's two-selector invariant and its five-module variant-naming list (now six), but does NOT wire a new selector dispatch: `resolve_uc_vended_storage` is unit-tested only, and the catalog-kind-to-credential-family dispatch is deferred to #319/#320. The two existing selectors — `storage_block` (CONNECTION shape, static, when `use_vended` is false) and `resolve_vended_storage` (URI scheme, vended, when `use_vended` is true) — stay unchanged.

### Scenario: A Unity Catalog vended selector is admitted as a third backend-selection site

* *GIVEN* the invariant in "Every consumer holds a backend and no consumer names one" that there SHALL be EXACTLY TWO sites that select a backend from input — `storage_block` when `use_vended` is false and `resolve_vended_storage` when `use_vended` is true — with no third selector added without superseding that clause
* *WHEN* the native Unity Catalog credential-vending path lands, resolving a `StorageBackend` from a Unity Catalog temporary-table-credentials response
* *THEN* a THIRD backend-selection site, `resolve_uc_vended_storage`, SHALL be admitted, reading a DISJOINT input — the Unity Catalog temporary-table-credentials response shape, distinct from both the CONNECTION credential shape and the Iceberg REST `loadTable` response — and this scenario SUPERSEDES the "EXACTLY TWO sites" and "no third selector" clauses accordingly
* *AND* `resolve_uc_vended_storage` SHALL select the backend variant from the table location's URI scheme ALONE and MUST NOT take a `warehouse`, a `region`, an existing `StorageBackend`, or any other CONNECTION-derived value as a parameter, so the three selectors' input disjointness is enforced by its signature
* *AND* the Unity Catalog vended path SHALL terminate in a `StorageBackend` value and is NOT wired into a pushdown dispatch in this plan — Delta scan execution consumes it in #319/#320 — but the invariant is superseded now so the third selector is not a silent breach of the two-site rule
* *AND* the recorded clause naming "these five [modules], exhaustively" as the ONLY modules permitted to match on a `StorageBackend` variant or read its S3 payload — closing with "No other production module SHALL name a variant" — SHALL be SUPERSEDED to admit a SIXTH module, `resolve_uc_vended_storage` in the new `unity` module of `lakehouse-catalog`, which constructs `StorageBackend::S3` or `StorageBackend::Adls` from the Unity Catalog vended response's storage-location URI scheme; the amended exhaustive list is SIX — the enum's own methods (`storage.rs`), the engine's single object-store registration function (`scan/object_store.rs`), `resolve_vended_storage` (`vended.rs`), `storage_block` (`connection.rs`), `CommonScanSpec`'s manual `impl Default` (`scan/spec.rs`), and `resolve_uc_vended_storage` (`unity` module) — and no other production module SHALL name a variant, with the source-level variant probe covering BOTH vended selectors as the compensating gate (pinned in "The three-selector dispatch stays single-homed and probe-guarded" below)

### Scenario: The three-selector dispatch stays single-homed and probe-guarded

* *GIVEN* the admitted third selector `resolve_uc_vended_storage` and the "exactly ONE site chooses between selectors" clause of "Every consumer holds a backend and no consumer names one"
* *WHEN* the shared scheme-to-variant-kind classification and its source probe are wired, and the selector dispatch onto `resolve_uc_vended_storage` is left for #319/#320
* *THEN* the scheme-to-variant-KIND classification SHALL have ONE home shared by `resolve_vended_storage` and `resolve_uc_vended_storage`, mapping `s3`/`s3a` to the S3 variant kind and `abfs`/`abfss` to the ADLS variant kind in exactly one place rather than duplicated across the two vended selectors
* *AND* that shared home SHALL own ONLY the scheme-to-variant-kind classification and MUST NOT construct a `StorageBackend` value, while each vended selector constructs its OWN `StorageBackend` variant from its OWN disjoint credential family — `resolve_vended_storage` from the Iceberg REST vended response and `resolve_uc_vended_storage` from the Unity Catalog temporary-table-credentials response — so the single-home requirement and the probe's requirement that every variant name appear in `resolve_uc_vended_storage`'s own production source are simultaneously satisfiable rather than in conflict
* *AND* this plan SHALL NOT wire a new selector dispatch: `resolve_uc_vended_storage` is admitted and unit-tested but is reached by NO selector-choice site in #318, because a pushdown under the Unity Catalog kind is refused before any credential or file resolution (`catalog-kind-selection` § "A pushdown request under the Unity Catalog kind is refused as not yet executable"); the recorded "exactly ONE site chooses between those two selectors — the `use_vended_credentials` branch in `resolve_file_list`" clause therefore stays INTACT and is NOT superseded here, and the catalog-kind-to-credential-family two-level dispatch that would supersede it is DEFERRED to #319/#320, when Delta scan execution first reaches `resolve_uc_vended_storage` — marked as a deferral exactly as the third selector's scan wiring is deferred in the scenario above
* *AND* a source-level probe SHALL extract the variant list from `enum StorageBackend`'s own source and assert every extracted name appears in `resolve_uc_vended_storage`'s production source (`unity` module), and the existing probe asserting the same over `resolve_vended_storage`'s source (`vended.rs`) SHALL remain — so the source-probe gate covers BOTH vended variant-naming selectors — and a hardcoded variant list SHALL NOT satisfy either probe
