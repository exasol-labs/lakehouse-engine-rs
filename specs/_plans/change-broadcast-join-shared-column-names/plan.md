# Plan: change-broadcast-join-shared-column-names

## Summary

The broadcast inner equi-join serves two legs that share column names, including a table joined to itself (#573). The worker SQL aliases each FROM-tree occurrence with the fallback's `LHS_T{leg}` alias, which the join block carries. The adapter and the scan handle every column as a (relation alias, column) pair. Only the worker's output columns are named `<alias>_<column>`.

## Context

- `render_broadcast_join` declines every two-leg join whose tables share any column name (`disjoint_schema_guard`), so a star schema with a shared key name such as `CUSTOMER_ID`, and every self-join, takes the unaccelerated N-scan fallback.
- The adapter strips `tableAlias` and renders bare names, and the scan wraps each side in an unaliased derived `SELECT "col" AS "COL"`. A name both sides carry is therefore ambiguous in DataFusion.
- Column types are looked up by bare name in the type-rewrite pipeline (`column_exa_type`), `BinaryColumns`, `project_columns`, `bound_sort_key`, and the scan's `combined_type`. With a shared name, the first match wins.
- The fallback already resolves each `column` node to its FROM-tree occurrence through `JoinLegs` (`pushdown-joins/pushdown-planning-join-fallback-self-join`), and `crates/vs-expression` renders a `column` node as `"ALIAS"."NAME"` when it carries a `tableAlias`.
- The scan emits rows by position against the `EMITS` list, and Exasol binds the pushdown result to the select list by position.
- The user's answers that shape this plan are in `decision-log.md` § Interview.
- Iceberg table spec, Column Projection: "Columns in Iceberg data files are selected by field id." The relation aliases and output names apply above the field-ID projection and the name mapping, so the read path and its recorded exceptions stay as they are. No deviation.
- Delta Lake protocol, Reader Requirements for Column Mapping: "In `name` mode, readers must resolve columns in the data files by their physical names as given by the column metadata property `delta.columnMapping.physicalName` in the Delta schema." In `id` mode, "readers must resolve columns by using the `field_id` in the parquet metadata for each file". The scan applies this mapping in `scan/field_id_projection.rs`, below the registered table. The relation aliases and output names apply to the logical, uppercased names that `aliased_select` produces over that table, above the physical-name mapping, so no deviation arises.
- Architecture: no change. The qualified columns travel in the scan spec's existing projection, condition, filter, and ordering fields.

## Impact

- A two-leg inner equi-join whose legs share column names, or that joins a table to itself, now takes the broadcast path when its smaller side is at or below `JOIN_BROADCAST_MAX_BYTES`. Results are unchanged.
- `EXPLAIN VIRTUAL` of every broadcast join shows `"LHS_T0"."…"` and `"LHS_T1"."…"` references in the scan spec's condition and filter, projection items as `{"relation": …, "name": …}` objects, the two aliases in the join block, and `<alias>_<column>` names in the `EMITS` list.
- A broadcast join that projects a column name longer than 121 characters takes the fallback, because its output name would exceed 128 characters.
- Not breaking. No property, CONNECTION field, or advertised capability changes. Single-table scan specs serialize unchanged.

## Verification

`specs/mission.md` § Commands and `specs/testing.md` govern the suites. E2E tests prove the path taken with `EXPLAIN VIRTUAL`.

Every test must exercise the edge cases of this change with a discriminating fixture (`specs/testing.md` § Correctness oracles): it must fail against the bug it exists to catch. For this change that means a same-named column whose two relations differ in value, type, and sort order; the shared column as join key, as a non-key projected column, as a filter subject, as a sort key, and unread; a self-join with both occurrences aliased, with one unaliased, and with a filter on one side only; and a sort key on the other relation's same-named column. A test whose rows would be identical under a mixed-up (relation alias, column) pair does not count as proof for the case. When the implementer finds an edge case of this change that no listed test covers, it adds a test for it.
