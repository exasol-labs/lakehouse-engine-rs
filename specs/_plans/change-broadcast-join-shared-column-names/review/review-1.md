## Why This Plan May Fail

- The spec library contradicts itself after the merge. Three recorded scenarios that this plan does not touch still say that overlapping column names keep a join off the broadcast path, or that the broadcast universe is a "disjoint UNION". Routed to `[REQUIREMENT_CONFLICT]`.
- The E2E checklist cannot pass as planned. `e2e_local/scan.rs::a_join_compares_a_binary_filter_on_the_raw_bytes_on_both_join_paths` asserts the N-scan wrapper for a join whose tables share `ID`. The join will now broadcast, and no task covers the test. The obvious repair, flipping the assertion, drops the only local E2E proof of the binary filter on the N-scan join path. Routed to `[HIDDEN_DEPENDENCY]`.
- Self-join shapes that the broadcast path now serves keep no broadcast E2E coverage. The plan moves the unaliased-occurrence and one-sided-filter self-join tests to `VS_NAME_LOW`. The one-sided filter is the shape where leg pruning breaks the byte tie that the spec says every self-join produces. Routed to `[UNSTATED_ASSUMPTION]` and `[TRACEABILITY_GAP]`.

#### [UNSTATED_ASSUMPTION] FINDINGS
- Location: `pushdown-joins/pushdown-planning-join/spec.md` § Scenario "Legs that share column names are planned as a broadcast fan-out" (third AND step); decision-log.md § Design Decisions [2]
- Issue: The scenario says "on a byte tie, which every self-join produces, the first leg in FROM-tree order SHALL be the dimension leg". The tie claim is false. `plan_join` resolves each leg with its own leg-local WHERE conjuncts (`side_filters` into `resolve_one_join_side`), and pruning shrinks that leg's `total_bytes`. A self-join with a one-sided filter, such as `WHERE a.O_ORDERKEY <= 5`, therefore has unequal byte totals, and either leg can become the dimension. The design handles that case, because 2.2 records the dimension leg. The spec text and Decision [2] state a false invariant, and no test exercises a self-join whose dimension is leg 1.
- Fix: In the scenario step and in Decision [2], replace "which every self-join produces" with "such as a self-join whose legs prune no file differently". Add to task 3.1 a self-join query with a one-sided filter that prunes one leg on `VS_NAME`. One way is to run `e2e_self_join_with_one_sided_filter_matches_single_node` on both virtual schemas (see the `[TRACEABILITY_GAP]` on task 3.2).

## Design Depth

#### [INFORMATION_COUPLING] FINDINGS
- Location: plan.md § Implementation Tasks 1.1 and 2.2; decision-log.md § Design Decisions [2]
- Issue: Distinct (alias, column) pairs get distinct output names only because every alias is `LHS_T` plus decimal digits. `JoinLegs::leg_alias` in `adapter/pushdown/joins/attribution.rs` owns that format. The output-name rule lives on the column reference in `scan/spec.rs`, and "the scan holds no alias constant". Two modules therefore assume one format, and nothing enforces it. The user's stated next step, joins over more than two legs, is the change most likely to touch alias naming. A second, smaller coupling has the same shape: task 1.2 keeps the scan's empty-projection default as "dimension first", while task 2.1 builds the adapter's full row "in leg order". Exasol binds by position, so the two orders must agree whenever the default is reached.
- Fix: In task 1.1, define the relation-alias format once in `scan/spec.rs`, next to the output-name rule, as a function from leg index to alias. State the injectivity invariant in its doc comment. In task 2.2, make `JoinLegs::leg_alias` call that function. In task 1.2, either drop the scan's empty-projection default for join specs, because `project_columns` always sends an explicit projection for a join, or make it list the relations in leg order.
