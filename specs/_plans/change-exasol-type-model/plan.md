# Plan: change-exasol-type-model

## Summary

Move the Exasol SQL type into `vs-expression` so the request parser, the type mapping, and both CAST dialects share one strict model (#584). INTERVAL, GEOMETRY, HASHTYPE, and `TIMESTAMP WITH LOCAL TIME ZONE` select items and CAST targets then run in Exasol SQL over the sharded scan, an invalid DECIMAL cannot be built, and TIMESTAMP precision 3 renders one way on every Exasol version.

## Context

- #582 made `ExasolType` the engine's only Exasol type, but it lives in `lakehouse-engine`, which `vs-expression` cannot depend on. `vs-expression` still parses CAST `dataType` JSON and renders SQL types on its own, and the two copies differ: the Exasol dialect drops ` ASCII` from a VARCHAR target, and no range check applies.
- The issue's last comment ("Spike results and decisions") holds the final design decisions. The spike on branch `spike/584-exasol-type-model` (commit d097963c, on top of #582) is the reference implementation, verified against Exasol 2025.1.16 and 8.29.13. Its rough spots are listed in the tasks that fix them.
- These queries fail or return wrong rows today, per the comment:
  - an INTERVAL select item (`ts - ts`, `GROUP BY ts - ts`, `MIN(ts - ts)`) fails with `Data type mismatch ... got VARCHAR(2000000)`;
  - a CAST to HASHTYPE, GEOMETRY, INTERVAL, or `TIMESTAMP(6) WITH LOCAL TIME ZONE` fails as "rendered by neither dialect" or "could not be rendered";
  - `CAST(NULL AS GEOMETRY)` fails with `Expected GEOMETRY`;
  - on 8.x, a `CAST(ts AS TIMESTAMP)` filter returns wrong rows, because the scan casts to nanoseconds while 8.x `TIMESTAMP` holds milliseconds.
- The adapter defaults, caps, and clamps an incomplete or out-of-range `dataType` and maps an unknown type to `VARCHAR(2000000)`. `VARCHAR(2000000)` therefore also means "no declared type", so a genuine `CAST(x AS VARCHAR(2000000))` is never emitted. The supported floor is Exasol 8.29.x (Interview). A complete `dataType` per select-list item in every request is verified on 8.29.13 and 2025.1.16, where only the 8.x TIMESTAMP precision is missing, and it means 3.
- Exasol omits `characterSet` for a UTF8 CHAR or VARCHAR in every request and sends no `selectList` for `SELECT *`, so the strict parser needs a UTF8 default and a count check that skips a request without a `selectList`.
- `ExasolType::Decimal` accepts precision 0, a negative scale, and a scale above the precision. `Timestamp { precision: None }` and `Some(3)` compare unequal although Exasol treats them as one type.
- Spec check (`AGENTS.md`): the Iceberg spec's Primitive Types table gives `decimal(P,S)` as "Fixed-point decimal; precision P, scale S" with "Scale is fixed, precision must be 38 or less". The Delta protocol's Primitive Types table states for `decimal` that "The precision and scale can be up to 38". Parquet's DECIMAL logical type requires that the scale "must be zero or a positive integer less than or equal to the precision". Exasol's `DECIMAL(1≤p≤36, 0≤s≤p)` is the binding limit, and a decimal outside it keeps the JSON `VARCHAR` fallback (ADR `single-authoritative-datafusion-to-exasol-type-mapping-with-json-fallback`). INTERVAL, GEOMETRY, and HASHTYPE are Exasol-only types that no lakehouse column maps to. Exasol's lack of struct, list, and map stays a named trade-off.
- The type moves between components: see the architecture delta `architecture.md`.
- One PR, because every part changes the same type module. Its title is `fix(types): share one strict Exasol type model`, since the final state fixes failing queries and wrong results.
- Follow-up plans:
  - Typed scan rendering (#587), which depends on this plan:
    - One typed entry point renders every expression sent to the scan: WHERE filter, select list, GROUP BY key, aggregate argument, HAVING and ORDER BY over a merge, broadcast join condition, and per-leg join filter.
    - A conversion to text of a DATE, TIMESTAMP, BOOLEAN, DOUBLE, or DECIMAL with a scale above 0 declines, explicit or implicit. Text and integer operands still push down. The LIKE-subject guard, the string-position coercion, and the decimal trim rewrite go away.
    - A CAST to `CHAR(n)`, to a `VARCHAR(n)` shorter than 2,000,000, or to an ASCII target renders only when the source type guarantees Exasol's result. A text source declines, and an integer source keeps its pushdown when its widest text form fits the target.
    - GROUP BY keys leave the scan in their declared type, and the merge groups on them without a cast.
    - A NULL nested inside an expression keeps the type Exasol declared for it.

## Impact

- The queries listed under Context return the same rows or the same error as native Exasol. Exasol computes the INTERVAL, GEOMETRY, HASHTYPE, and `TIMESTAMP WITH LOCAL TIME ZONE` parts over the parallel scan, so those queries keep less pushdown than queries over ordinary columns.
- For a query that works today, the pushdown SQL that `EXPLAIN VIRTUAL` shows changes in the outer SQL only: an `EMITS` or CAST of precision 3 spells bare `TIMESTAMP`, a MIN or MAX merge loses its redundant CAST, an Exasol-dialect CAST to DOUBLE spells `DOUBLE PRECISION`, and a VARCHAR target keeps ` ASCII`. Results of queries that work today stay identical.
- A pushdown request without `selectListDataTypes` or with an invalid `dataType` now fails instead of being defaulted. The engine supports Exasol 8.29.x and later, and complete types are verified on 8.29.13 and 2025.1.16, the versions the E2E suites run. On an Exasol older than 8.29.x that sends no list, every pushdown now fails (architecture delta § Constraints and § External Dependencies).
- No CONNECTION field, virtual schema property, install step, or advertised capability changes. `docs/capability-matrix.md` updates its `CAST` note, `docs/semantic-differences.md` documents the CAST-to-text deviation, and `docs/install.md` names the Exasol 8.29.x floor.

## Out of scope

- `LITERAL_INTERVAL`, the `HASHTYPE_*`, `ST_*`, and `NUMTO*INTERVAL` functions stay unadvertised.
- `fractional_digits()` keeps answering only for plain TIMESTAMP, because no consumer reads a `TIMESTAMP WITH LOCAL TIME ZONE` precision from it.
- The DataFusion dialect keeps rendering a CAST to `CHAR(n)`, to a `VARCHAR(n)` shorter than 2,000,000, or to an ASCII target as a bare `VARCHAR`, as on `main`. The scan therefore applies no length check, no blank padding, and no ASCII check, and an over-length or non-ASCII value returns rows where native Exasol raises an error. (#587) renders such a CAST only when the source type guarantees Exasol's result. The DataFusion-side blank pad of a CHAR group key stays until then.
- The scan converts a DATE, TIMESTAMP, BOOLEAN, DOUBLE, or DECIMAL value with a scale above 0 to text in DataFusion's fixed form, for example a TIMESTAMP with a `T` separator and a BOOLEAN as `true`. Such a query returns other rows than native Exasol under default settings for TIMESTAMP and BOOLEAN, and under a non-default NLS setting for DATE and DECIMAL. These wrong results exist on `main` and move to (#587).
- GROUP BY keys travel from the scan as text, so a GROUP BY on a DATE, TIMESTAMP, or DECIMAL column returns wrong keys under `NLS_DATE_FORMAT='YYYY-DD-MM'` and fails with `invalid character value for cast` under other non-default NLS settings. (#587) returns the keys in their declared type.
- A wrapper that renders `''`, which Exasol rewrites to NULL, nested in `||` beside a declined item fails with `Data type mismatch ... Expected VARCHAR(12), got VARCHAR(16)`, reproduced on release v0.57.4 and on the spike. Typing a NULL nested inside an expression moves to (#587).
- A CAST of a DECIMAL column to a CHAR or VARCHAR target keeps the adapter's trimmed-text rewrite. (#587) removes that rewrite, after which a DECIMAL with a scale above 0 declines and an integer CAST to a sized target follows the sized-target rule.
