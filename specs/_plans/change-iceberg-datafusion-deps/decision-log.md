Headless mode: no live interview. The orchestrator supplied the current manifest state and intent (move the three iceberg crates from the `v0.10.0-rc.2` git-tag pin to crates.io `0.10.0`; bump `datafusion` from `54` to `54.1.0`). All open points were resolved by research plus conventional defaults; see Design Decisions.

**Q (from brief):** Is iceberg 0.10.0 actually published on crates.io, or still RC-only?
**A (research):** Published 2026-07-21. `iceberg` 0.10.0, `iceberg-catalog-rest` 0.10.0, and `iceberg-storage-opendal` 0.10.0 all appear on the crates.io API with `max_stable_version` / `newest_version` = 0.10.0. `datafusion` 54.1.0 published the same day. The RC-only BLOCKER condition does not apply.

**Q (from brief):** Any breaking API change between `v0.10.0-rc.2` and `v0.10.0`, or between datafusion 54.0.0 and 54.1.0?
**A (research):** None on this repo's code paths. The iceberg rc.2 → final delta (25 commits / 51 files) is CI, transitive dep bumps (reqwest 0.13.3, zeroize 1.9.0, RUSTSEC fixes), iceberg's own datafusion-INSERT integration (unused here), and additive/unused writer constructors. datafusion 54.1.0 is 19 commits of bug fixes and docs with no breaking API, no arrow change (stays `^58.3.0`), no object_store change (stays `^0.13.2`).

**Q (from brief):** Does the version bump change any Iceberg-table-spec-relevant behavior?
**A (research):** No. The delta does not touch scanning, snapshot/manifest reading, positional-delete application, or schema/type mapping. Pure version-pin change; no spec deviation introduced.

## Design Decisions

### [1] No spec deltas — pure dependency-version bump

- **Decision:** Author no `spec.md` deltas. plan.md and decision-log.md only.
- **Alternatives:** Author "no-op" CHANGED deltas on the datafusion-scan / positional-delete features to record the bump. Rejected — deltas capture behavior changes, and there are none.
- **Rationale:** Research shows the rc.2 → final and 54.0.0 → 54.1.0 deltas introduce no observable behavior change on shipped scan/pushdown/schema/positional-delete functionality. Spec text is unchanged; the regression guard is the existing suite passing unchanged.
- **Promotes to ADR:** no

### [2] iceberg pinned as crates.io `"0.10.0"`, not the git source

- **Decision:** Replace `{ git = "…", tag = "v0.10.0-rc.2" }` with `"0.10.0"` (registry, `^0.10.0`) for all three iceberg crates; keep `iceberg-storage-opendal`'s `default-features = false, features = ["opendal-s3"]`.
- **Alternatives:** Keep the git source pinned at the final `v0.10.0` tag; or exact-pin `"=0.10.0"`. Rejected — the release is on crates.io, so a git source is no longer warranted; exact-pinning deviates from the house style (`arrow = "58"`, `roaring = "0.11"`).
- **Rationale:** Registry pins are reproducible and cache-friendly; `^0.10.0` matches how the workspace pins other released crates. This decision is exactly the "explicit, reviewed edit" the git-tag-pin ADR anticipated for a future GA bump: crates.io now publishes `0.10.0`, so the pin ADR's Context premise (never published to crates.io) no longer holds, and this reverses its Decision.
- **Supersedes:** `pin-iceberg-0-10-0-rc-2-via-git-tag-not-a-crates-io-exact-version-pin` (ADR "Pin iceberg 0.10.0-rc.2 via git tag, not a crates.io exact-version pin", `specs/_decision/001-migrate-legacy-decision-log.md:2164`). This decision records the crates.io `0.10.0` pin as the superseding ADR; at `speq record`, the recorder flips the superseded pin ADR's status to `Superseded by <new-slug>` per plan.md task 8.1.
- **Promotes to ADR:** yes

### [3] datafusion constraint tightened `"54"` → `"54.1"`

- **Decision:** Change the manifest constraint to `version = "54.1"` rather than leaving `"54"` and moving only the lock.
- **Alternatives:** Leave `"54"` (already permits 54.1.0) and `cargo update` the lock only. Rejected — a lock-only bump does not document that 54.1.0 is now the required floor; a future lock regeneration could still satisfy `"54"` with 54.0.0.
- **Rationale:** `"54.1"` (`^54.1`) makes the 54.1.0 floor explicit while staying within the 54 line. Reversible.
- **Promotes to ADR:** no

### [4] Update every RC-naming comment, not only the manifests

- **Decision:** Update the rc.2 references in `src/scan/positional_deletes.rs`, `tests/e2e_positional_deletes_test.rs`, and `tests/common/seed.rs` alongside the two `Cargo.toml` files.
- **Alternatives:** Change only the dependency lines and leave the comments. Rejected — the comments would then assert an RC pin the workspace no longer uses, creating a false record.
- **Rationale:** Accuracy. PR #67 set the precedent of retiring stale dependency-rationale comments in the same bump commit.
- **Promotes to ADR:** no

### [5] `Cargo.lock` regenerated by a real `cargo update -p`, committed

- **Decision:** The lockfile is regenerated during implementation via `cargo update -p` (git→registry source switch + datafusion `--precise 54.1.0`) and committed, not treated as a plan-only artifact.
- **Alternatives:** Leave the lock for a later step or let CI regenerate it. Rejected — reproducible builds require the committed lock to reflect the registry source switch, and PR #67 committed its regenerated lock.
- **Rationale:** The source change (git → registry) only lands in the lock through `cargo update`; committing it keeps builds deterministic.
- **Promotes to ADR:** no

### [6] Verify vendored `build_deletes_row_selection` parity

- **Decision:** Include a task to diff this repo's vendored `build_deletes_row_selection` against iceberg 0.10.0 before finalizing the provenance-comment change.
- **Alternatives:** Update the provenance comment to `v0.10.0` without checking. Rejected — positional-delete handling is Iceberg-spec-relevant per CLAUDE.md, and the comment asserts which upstream version the vendored copy matches.
- **Rationale:** The rc.2 → final commit list contains no positional-delete-selection change, so parity is expected; the check is cheap and confirms the correctness-sensitive claim.
- **Promotes to ADR:** no

### [7] Crate version bump and issue linkage handled by the PR/release flow

- **Decision:** Do not add a `lakehouse-engine` crate-version-bump task or a fabricated `Closes #<n>` issue number to this plan.
- **Alternatives:** Add a `chore(release): bump` task and invent an issue number. Rejected — the repo separates release-version bumps into their own step, `speq:implement-pr` bumps the version, and inventing an issue number risks a collision (see the `ae8f38f` stale-issue-number fix in history).
- **Rationale:** Keep the plan to the dependency change; version bump and issue linkage are release-orchestration concerns applied at PR finalization.
- **Promotes to ADR:** no

### [8] DataFusion 54.1.0 leaves the frozen date/interval version anchors valid

- **Decision:** Retain the "DataFusion 54.0.0" verification-epoch anchors in ADR 014 (`014-add-date-arithmetic-pushdown.md:81,100`) and the date-fns spec (`vs-expression-translator-date-fns/spec.md:26-29,31,47,54,58`); author no CHANGED delta against either. Chose the frozen-verification-epoch resolution over delta-correcting the strings to "54.1.0".
- **Verification:** The DataFusion 54.1.0 changelog (`dev/changelog/54.1.0.md`, reviewed 2026-07-22) is 19 bug-fix/docs commits. None touches date/interval type coercion, the `Integer × Interval` multiply kernel, or the arrow-rs version — arrow stays 58.3.0 — so arrow-rs#9030 (the plan-time `Integer × Interval` error) and `is_date_minus_date → Int64` are unchanged. The single type-coercion commit ("handle nulls in type coercion of higher-order UDFs, map_extract, spark array_repeat", backport #23071) is scoped to higher-order UDFs and array ops, not date/interval coercion.
- **Alternatives:** Author CHANGED deltas rewriting "54.0.0" → "54.1.0" in ADR 014 and the date-fns spec. Rejected — the "54.0.0" strings record the exact version each rendering was empirically executed against, so rewriting them would assert a per-function parity run this plan does not perform; ADR 014 is an Accepted historical ADR whose factual content the repo convention preserves; and no behavior delta exists to justify a CHANGED delta.
- **Rationale / guard:** The anchored behaviors still hold under 54.1.0. The `exasol-e2e` `e2e_date_functions_in_filter` and `*_BETWEEN` parity tests (issue #107, `crates/lakehouse-engine/tests/e2e_capability_test.rs`) fail — not skip — if 54.1.0 changed the advertised date/interval pushdown behavior, so the frozen wording stays accurate under the bump.
- **Promotes to ADR:** no
