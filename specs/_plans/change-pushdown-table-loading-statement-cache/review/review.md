## Summary

## Why This Plan May Fail

- The design leaves the defect the user named. `DirectStorageCatalogClient` keeps a `CatalogClient::load_table` that always fails, and the plan adds a working scan load beside it on the same client. The user sees the same special case they called "very bad design". Routed to `[SCOPE_REDUCTION]` BLOCKER.
- The cache is correct only if no adapter VM outlives its statement. The #583 probe never ran nested statements of one `EXECUTE SCRIPT`. If those share a VM, the second statement reads the first statement's snapshot and returns stale rows without an error. Routed to `[UNSTATED_ASSUMPTION]` BLOCKER.
- After `/speq:record`, the spec library contradicts itself. Recorded scenarios that the plan does not change still require "exactly once for the request", and a new scenario promises one OAuth token per statement that the code cannot deliver for a Unity join (perf issue 8). The implementer cannot satisfy both sides. Routed to two `[REQUIREMENT_CONFLICT]` BLOCKERs.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: decision-log.md § Design Decisions [1] Rationale and Consequences; plan.md § Implementation Tasks 4.1
- Issue: Decision [1] rests on "Exasol runs one adapter VM per statement and virtual schema (#583 probe), so the VM lifetime is the statement scope". The #583 probe covers a UNION ALL, a CTE referenced twice, a join, an `EXISTS` subquery, two virtual schemas, and a re-run of the same query. It does not cover several statements in one `EXECUTE SCRIPT`, where a Lua script runs `query()` more than once. The cache key holds only the virtual schema name. If nested statements share one adapter VM, the later statement reuses the earlier statement's snapshot and listing, and returns stale rows without an error. That is the result-parity failure that `specs/mission.md` § Core Capability 12 forbids, and it breaks the interview's "None, except fixing issues 6 and 7, plus #583's statement-scoped reuse". `a_later_statement_reads_a_file_added_after_the_first` covers only two top-level statements. The Consequences line treats VM reuse as a risk of "a later Exasol" only. `AGENTS.md` requires checking Exasol behavior against a live Exasol.
- Fix: In plan.md task 4.1, add the E2E test `a_script_reloads_the_table_for_each_of_its_statements` to `statement_reuse.rs`. The test creates a Lua script that runs the same `SELECT` over `PROXY_ICEBERG_VS` twice through `query()`, runs it once with `EXECUTE SCRIPT`, and asserts two `loadTable` GETs in the proxy log after the mark. Add its row to § Scenario Coverage under "Every reference to one table in a statement loads the table once and prunes it with its own filter". In decision-log.md [1] Rationale, name the statement shapes that the probe and this test cover. Add to plan.md task 4.1: "If the test sees one `loadTable` GET, stop and return the cache-key decision to the user before implementing group B."

#### [NFR_IGNORED] FINDINGS
- Location: plan.md § Impact; plan.md § Out of scope, bullet "Perf issue 15"
- Issue: Peak adapter memory used to be the largest single request. It becomes the sum over every table a statement loads, kept until the VM exits. Task 1.1 keeps each Iceberg table's built `Table` for its manifest `ObjectCache`. The planning notes put that cache's default capacity at 32 MiB per table. Each kept `DeltaSnapshot` holds a `DefaultEngine<TokioBackgroundExecutor>`, which owns a background thread and its runtime (`delta_replay.rs:48-57`). A UNION ALL over 20 Iceberg tables can therefore keep about 640 MiB of manifest cache. The perf document measured an adapter death at 3 GiB, and `specs/mission.md` § Constraints makes safety guards first-class. The perf issue 15 bullet mentions the file list but neither the caches nor the threads.
- Fix: In plan.md § Impact, add one bullet that states the retained state per loaded table (the Iceberg manifest cache up to its capacity, one Delta engine thread, the listing or partition list) and that it lives until the statement ends. In task 1.1, either set an explicit Iceberg cache capacity through the `Table` builder or state why the default is acceptable.

#### [NFR_IGNORED] FINDINGS
- Location: decision-log.md § Design Decisions [1] Consequences, first bullet; plan.md § Implementation Tasks 2.1
- Issue: The Consequence states only that a VM shared across statements "would serve stale metadata". Task 2.1 also caches the `ResolvedConnectionConfig`, which holds the enforced `PermissionGate` and its mapped principal, together with the permission-checked identifiers. On a hit, task 2.1 skips the permission parse and the user mapping. If one VM ever served two users' statements, the second user would be checked as the first user's principal, and the tables the first user was admitted to would not be checked again. That outcome is an access-control bypass, not stale data. Binding the admitted set to the principal guards against it at no I/O cost and leaves the interview's key unchanged.
- Fix: In decision-log.md [1] Consequences, add a bullet that names the permission risk. In plan.md task 2.1, store the mapped principal beside the admitted identifiers. On each request, map `ctx.current_user()` as today and treat a different principal as a miss of the permission state.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: specs/_plans/change-pushdown-table-loading-statement-cache/file-planning/pushdown-format-neutral-resolution/spec.md § "The pushdowns of one statement share one catalog session per virtual schema", THEN step; plan.md § Out of scope, bullet "Perf issue 8"
- Issue: The THEN step reads "the adapter SHALL authenticate to the catalog at most once for the statement: at most one OAuth2 token request under OAuth2 client credentials or Unity Catalog OAuth M2M, and, for an Iceberg REST catalog, one `/v1/config` lookup". The token clause fails for a Unity join of two different tables under OAuth M2M. `OAuthTokenSource::bearer` (`lakehouse-catalog/src/unity/auth.rs`) drops the cache lock before `self.mint().await`, so both legs mint a token. plan.md keeps that defect: "Perf issue 8: concurrent Unity Catalog legs over different tables can still each mint an OAuth token." The token clause also has no E2E proof. The local Iceberg REST fixture and the proxy tests use no OAuth2, so `a_statement_authenticates_once_per_virtual_schema` can count only `/v1/config` lines.
- Fix: In that THEN step, replace the clause with "at most one `/v1/config` lookup for an Iceberg REST catalog, and at most one OAuth2 token request for each Iceberg REST catalog session". Add an AND step: "a Unity Catalog statement under OAuth M2M SHALL request at most one token per table that it loads". In plan.md § Scenario Coverage, map the token clause to an E2E test in a suite that has an OAuth2 server, such as `e2e_lakekeeper_test.rs` with its Keycloak, if its token requests pass the proxy. Otherwise state in plan.md which test proves the clause, or drop the clause.
