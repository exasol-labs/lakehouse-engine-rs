## Premortem

Six months from now this plan failed. Three stories explain why.

1. **The library contradicts itself about Glue store placement.** `vs-adapter/pushdown-planning-cloud-credentials` still records that `use_sigv4` requires `region` and that a Glue CONNECTION's stated `region` always places the vended store. On that basis it discharged the "does Glue vend `client.region`" risk. A later plan trusts that discharge and drops the `client.region` observation. Then a region-less Glue vended CONNECTION reaches `https://<bucket>.s3..amazonaws.com`. Routed to Requirement Quality as `[REQUIREMENT_CONFLICT]` (BLOCKER).
2. **Operators remove `region` and every query breaks.** Operators read "a Glue CONNECTION can omit `region`" and delete the field. `CREATE VIRTUAL SCHEMA` succeeds, but static-key queries fail with a storage error that does not name `region`. Vended queries fail the same way if Glue vends no `client.region`. Routed to Intent Fidelity as `[SCOPE_REDUCTION]` (ADVISORY).
3. **The GovCloud exclusion regresses silently.** An implementer writes the GovCloud test with the interview's `amazonaws-us-gov.com` host. The suffix step rejects that host, so the region-code shape check never runs under test. A later refactor drops the shape check, and `glue.us-gov-west-1.amazonaws.com` starts deriving a region. The user explicitly excluded that outcome. Routed to Task Breakdown as `[TRACEABILITY_GAP]` (ADVISORY).

## Intent Fidelity

#### [SCOPE_REDUCTION] ADVISORY
- Location: plan.md § Summary, § Impact ("Storage region, operator action"), § Migration. decision-log.md [1] Consequences and [10].
- Issue: The user asked that such a CONNECTION "no longer needs to supply `region` explicitly for the common case". The plan executes the user's signing-only answer correctly. The result is still narrower than the Summary suggests. On the static-key path, `build_undecorated_store` calls `.with_region(&storage.region)` unconditionally (`crates/lakehouse-engine/src/scan/object_store.rs:218`). object_store 0.13.2 then builds `https://{bucket}.s3..amazonaws.com` (`src/aws/builder.rs:1086,1218`, verified). So every static-key query still needs `region`. On the vended path, placement depends on Glue vending `client.region`. No suite asserts that, and decision [10] deliberately runs no scan. The interview question described only the vended CONNECTION-wins rule, so the user never saw the static-path consequence. The Impact bullet also says scans "fail at read time". `catalog_storage_props` omits `s3.region` when it is empty (`crates/lakehouse-catalog/src/storage.rs:145-153`), so the first failure can surface in pushdown planning, when FileIO reads the manifest list. Nothing verifies which stage fails.
- Fix: In plan.md § Summary, add one sentence stating that a region-less Glue CONNECTION still needs `region` for static-key scans, and that vended scans depend on Glue's vended `client.region`. In § Impact, replace "scans fail at read time" with "queries that read table data fail", or name the verified failing stage. Ask the orchestrator to surface this narrowed benefit to the user in the final report.

This plan's new scenario "A standard AWS Glue endpoint supplies the SigV4 signing region when the CONNECTION omits region" makes all three false. Line 83 of that scenario even cites "the store-addressing precedence of `vs-adapter/pushdown-planning-cloud-credentials`" as seeing `region` unstated, the exact state line 94 says cannot occur. This plan therefore reopens the risk that line 94 discharged: a region-less Glue vended CONNECTION now places its store from the vended `client.region` alone. Decision [9] requires that "the clauses that the new scenarios contradict ... are corrected in place". Decision [8] exempts this spec anyway. Its reasons do not hold. First, "the brief marks that spec read-only" traces to nothing in the user intent or the interview. Second, "later bullets supersede" line 76, but the superseding bullet (94) rests on the same falsified premise. Third, the size of the Background is effort, not a reason. `notes/planning.md` shows that the planner read lines 70-77 of this spec but not lines 88-95, where bullets 92 and 94 sit. plan.md § Impact also says this spec "records [Glue's vended `client.region`] as unverified". The recorded spec calls the obligation DISCHARGED, and the cloud-e2e suite now only REPORTS the key.
- Fix: Add `specs/_plans/change-sigv4-region-inference/vs-adapter/pushdown-planning-cloud-credentials/spec.md` with a `DELTA:CHANGED` `## Background` block that reproduces the recorded Background verbatim except for these corrections, written as state with no narrative wording. At line 76, delete "— `use_sigv4` REQUIRES it —". At line 92, replace "the static `region` `use_sigv4` already requires" with "a `region` that the Glue CONNECTION states". At line 94, replace "a Glue CONNECTION supplies a static `region` for SigV4 signing, and that value now places the store" with a clause stating that a Glue CONNECTION stating `region` places the store, while one that omits it places the store from the vended `client.region` alone, which stays unverified. Re-read line 77 ("a SigV4 CONNECTION supplies") and correct it if it still presumes a stated `region`. Rewrite decision-log.md [8] to record this delta and delete the "read-only" and "104-line" reasons. Add this spec to plan.md § Features and delete its name from the 4th Non-Goals bullet. Correct the last sentence of the § Impact bullet so it matches the recorded spec's "discharged, observation only" status. Extend task 4.1 so `docs/catalogs.md` tells vended Glue operators that omitting `region` leaves store placement to Glue's vended `client.region`. Run `speq plan validate change-sigv4-region-inference`.
- Escalation: MECHANICAL. The recorded spec text, the new scenario, and decision [9]'s own rule settle the conflict. No requester judgment is needed.

## Task Breakdown

#### [TRACEABILITY_GAP] ADVISORY
- Location: plan.md tasks 1.1 and 3.5. § Verification › Scenario Coverage (host-rule row).
- Issue: Task 1.1 lists the host categories ("GovCloud, China, FIPS, ...") without literal hosts. The interview record's GovCloud example is `amazonaws-us-gov.com` (decision-log.md § Interview, answer 2). A test built from that example is rejected by the suffix step (Design host rule step 3). It never reaches the region-code shape check, which is the only step that excludes real GovCloud hosts (decision [2]). I checked the shape reasoning independently. Every commercial code (`us-east-1`, `ap-southeast-2`, `il-central-1`, `mx-central-1`) has three parts with a two-letter area. The GovCloud codes `us-gov-west-1` and `us-gov-east-1` have four parts. The AWS Glue documentation shows the GovCloud Iceberg REST host on `amazonaws.com`. China codes such as `cn-north-1` do match the shape and are excluded only by the `.amazonaws.com.cn` suffix. Task 1.1 also names none of the three test functions that the Verification table cites.
- Fix: In tasks 1.1 and 3.5, name the literal hosts from the scenario's exclusion clause, including `https://glue.us-gov-west-1.amazonaws.com/iceberg` and `https://glue.us-gov-east-1.amazonaws.com/iceberg`. State that the GovCloud case exists to exercise the region-code shape check. In task 1.1, name `signing_region_derived_from_standard_glue_endpoint`, `signing_region_absent_for_non_standard_hosts`, and `stated_region_wins_over_glue_endpoint_region`.
