## Standard fixes

### crates/lakehouse-catalog/src/vended.rs

#### [OUTDATED_COMMENT] The `abfs://` refusal states a plaintext mechanism this engine does not have
- Location: lines 73-78 (the `"abfs"` arms and their error text), and the module-level claim at lines 71-73 ("an `abfs://` location and a vended plain-`http://` endpoint are honoured only when `allow_http` is true")
- Issue: the refusal text asserts "abfs:// would carry the vended credentials in the clear". That is false for this engine. `object_store` 0.13.2's `azure::builder::parse_url` matches `"az" | "abfs" | "abfss"` in ONE arm and derives the same `https://<account>.{dfs,blob}.core.windows.net` endpoint for all three (`~/.cargo/registry/.../object_store-0.13.2/src/azure/builder.rs:660-682`), and `register_side_store`'s Azure arm (`crates/lakehouse-engine/src/scan/object_store.rs:205-211`) never sets `allow_http` at all. This change's own new test documents exactly that — `register_side_store_registers_an_abfs_scheme_side` (`object_store.rs:900-907`) says `abfs` and `abfss` are "matched identically". So an `abfs://` location is served over TLS whether the gate passes or not, and the operator is being asked to consent to a downgrade that never happens. Two sub-agent sessions wrote contradicting rationales for the same scheme.
- Fix: In `crates/lakehouse-catalog/src/vended.rs`, keep the refusal BEHAVIOUR unchanged (it is plan-mandated) and rewrite only its rationale. Replace the `"abfs" => Err(UdfError::User(format!(...)))` message text at lines 74-78 so it states the true reason: an `abfs://` location names plaintext transport, this engine has no plaintext Azure path and would silently read the location over HTTPS instead, so honouring it requires the operator's explicit `ALLOW_HTTP` acknowledgement rather than a silent scheme upgrade. The rewritten message MUST still contain the literal substrings `ALLOW_HTTP` and `abfs://` and the `{anchor}` value, because `unsatisfied_vended_request_errors_without_static_fallback` (line 1027-1033 region) asserts all three. Then correct the same claim in the doc comment at lines 71-73 to say the two schemes are gated for different reasons — a vended `http://` endpoint IS plaintext on the wire, an `abfs://` location is not but misnames the transport.

#### [MISSING_BOUNDARY_TEST] Anchor scheme is matched case-sensitively while the endpoint scheme beside it is not
- Location: line 68 (`anchor.split_once("://")`) and lines 70-73 (`match scheme`), against lines 130-133 (`scheme.eq_ignore_ascii_case("http")`)
- Issue: one decision — how to compare a URI scheme — is spelled two ways inside one function. The vended endpoint's scheme is compared case-insensitively; the anchor's scheme is matched against bare lowercase literals `"s3" | "s3a" | "abfss" | "abfs"`. RFC 3986 §3.1 makes a scheme case-insensitive, so a legal `S3://bucket/db/t` table location falls to the catch-all and is refused as naming "no storage backend this engine can read" — a hard plan-time error for a valid location. No test covers a case-variant scheme.
- Fix: In `crates/lakehouse-catalog/src/vended.rs`, normalize the scheme before matching in `resolve_vended_storage`: bind `let scheme = anchor.split_once("://").map_or(String::new(), |(scheme, _)| scheme.to_ascii_lowercase());` and match on `scheme.as_str()`. Add one case to the existing `vended_backend_variant_comes_from_the_anchor_scheme` test (line ~1385) asserting `S3://bucket/db/t` resolves the S3 backend and `ABFSS://container@myaccount.dfs.core.windows.net/db/t` resolves the ADLS backend.

### crates/lakehouse-engine/src/adapter/pushdown/file_resolution.rs

#### [OUTDATED_COMMENT] Vended selector's "no CONNECTION-derived value" claim omits the warehouse anchor fallback
- Location: `file_resolution.rs:251-262` (the anchor derivation and its block comment); the claim it contradicts is `crates/lakehouse-catalog/src/vended.rs:42-48`
- Issue: `vended.rs`'s doc states "Taking no [`StorageBackend`], no `ConnectionCreds`, and no other CONNECTION-derived value is the design rather than an omission", and that this makes the invariant a property of the signature. But the call site falls back to `&catalog_props.warehouse` when `result.metadata.location()` is empty (`file_resolution.rs:259-263`), and `CatalogProps.warehouse` is parsed straight from the CONNECTION password (`adapter/connection.rs` `catalog_block`). On that path a CONNECTION-derived string chooses the backend variant, the credential-source prefix match, AND (for ADLS) the SAS host. The plan foresaw the Glue shape (a bare account id → scheme-less → refused, tested at line ~1400) but not a warehouse spelled as a `s3://`/`abfss://` URI, which would silently select a variant from the CONNECTION. The signature-level guarantee therefore holds for storage FIELDS only, and nothing in either comment says so.
- Fix: In `crates/lakehouse-catalog/src/vended.rs`, amend `resolve_vended_storage`'s doc comment (lines 42-48 and 58-60) to state the guarantee precisely: no CONNECTION *storage* field reaches this function, and `anchor` is caller-supplied — when the table metadata carries no location the caller substitutes the CONNECTION's `warehouse`, so on that fallback the variant is selected from a CONNECTION-derived string. Then extend the block comment at `crates/lakehouse-engine/src/adapter/pushdown/file_resolution.rs:249-256` to name that consequence at the site that creates it, instead of only "Fall back to the warehouse when the metadata carries no location".

### crates/lakehouse-catalog/src/vended.rs

#### [INFORMATION_LEAKAGE] Vended `path_style` defaulting to false silently discards the vended `s3.endpoint` at scan time
- Location: `crates/lakehouse-catalog/src/vended.rs:145-154` (`s3_backend_from_vended`'s constructed `StorageProps`), consumed at `crates/lakehouse-engine/src/scan/object_store.rs:170-174`
- Issue: `StorageProps.path_style` is not an independent field to its consumer — `register_side_store` uses it as the gate for whether the endpoint is passed to the builder at all: `if storage.path_style { builder = builder.with_endpoint(&storage.endpoint).with_virtual_hosted_style_request(false); }`. The vended S3 arm now resolves `path_style` to `false` whenever the response omits `s3.path-style-access` (line 152-154), while independently resolving `endpoint` from `s3.endpoint`. A catalog that vends an endpoint but no path-style flag therefore produces `StorageProps { endpoint: "http://minio:9000/", path_style: false, region: "" }`, and the scan silently drops the endpoint, leaving `AmazonS3Builder` to derive `https://<bucket>.s3..amazonaws.com` from the empty region — reading the wrong store, not failing at plan time. This is a REGRESSION, not a latent smell: under the removed rule an absent `s3.path-style-access` preserved the static `path_style`, whose CONNECTION default is `true` ("path_style defaults to true (MinIO behaviour preserved)", `adapter/connection.rs:236-239`), so this exact shape worked before. The two consumers of one resolved backend now also disagree: `StorageBackend::catalog_storage_props` (`storage.rs:120-141`, the plan-time manifest read) inserts `S3_ENDPOINT` whenever it is non-empty, so the manifest read uses the vended endpoint with virtual-hosted addressing while the scan uses no endpoint at all. Nothing catches it: the Lakekeeper gate vends BOTH keys, and the one in-repo fixture that builds the broken shape — `resolve_vended_storage_allow_http_comes_from_the_threaded_parameter`'s `plaintext` result (line 1270-1277, `s3.endpoint` with no `s3.path-style-access`) — asserts only that the `endpoint` field carries the value, never that the scan can use it. Neither the plan's § Impact nor its Migration table names this consequence.
- Fix: In `crates/lakehouse-catalog/src/vended.rs`, change `s3_backend_from_vended` so an absent-or-unparseable `s3.path-style-access` defaults to whether the response vended an `s3.endpoint`, not to a bare `false`: `path_style: vended_config_value(vended, "s3.path-style-access").and_then(|value| value.parse::<bool>().ok()).unwrap_or(endpoint.is_some())`. Extend the function's doc comment to state WHY the default is coupled to the endpoint — `register_side_store` treats `path_style` as the gate on whether the endpoint reaches the builder, so a vended endpoint with `path_style: false` is an address the scan cannot use. Then: (a) add a test in `vended.rs`'s `mod tests` named `vended_endpoint_without_path_style_stays_reachable_by_the_scan`, asserting a response vending `s3.access-key-id`, `s3.secret-access-key`, and `s3.endpoint` (and NO `s3.path-style-access`) resolves `path_style == true` alongside the non-empty endpoint; (b) verify `resolve_vended_storage_unparseable_path_style_is_false` (line 1192) still passes unchanged — its fixture vends `client.region` and no endpoint, so `endpoint.is_some()` is false and the assertion holds — and if the plan-derived name no longer describes the rule, rename it to `resolve_vended_storage_unparseable_path_style_without_an_endpoint_is_false`; (c) update the `plaintext` fixture's assertion in `resolve_vended_storage_allow_http_comes_from_the_threaded_parameter` (line 1279-1283) to also assert `path_style` is true, so the fixture stops encoding a shape the scan cannot serve.
