# Plan Review Findings: change-vended-storage-resolution-scheme-driven (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 15 (Blockers: 5, Advisory: 10)
- Intent Fidelity blockers: 0

## Premortem

Three failure stories drove this review.

1. **The Glue vended path is dead and CI cannot see it.** Glue vends no `s3.access-key-id`, every Glue vended virtual schema returns "vended credentials were requested and the catalog returned none", and the pre-merge green test proved nothing because the shipped preservation rule silently read the CONNECTION's static AWS keys. → BLOCKER 2.
2. **A broadcast join reads the ADLS dimension through an S3 store.** `join_scan_spec` collapses both resolved sides into `primary.effective_storage`, so the dim side's host-matched vended SAS is discarded. → BLOCKER 1.
3. **A catalog downgrades transport to plaintext.** The operator never set `ALLOW_HTTP`; the catalog vends `s3.endpoint = http://…`; vended STS credentials now travel in the clear. → BLOCKER 3.

A fourth story is a recording defect: two renamed `DELTA:CHANGED` blocks cannot be name-matched at `/speq:record`, so the permanent spec ends up asserting both the strict rule and the preservation rule. → BLOCKER 4.

## Intent Fidelity

The interview's three-part rule is operationalized faithfully: `resolve_vended_storage(result, anchor)` cannot read a CONNECTION value (A6), the variant comes from the anchor scheme with a closed mapping and an error otherwise (A7), both arms error on an unsatisfied request (A5), the ADLS arm matches the anchor host (A1) and derives `account_name` from it (A2), the four A4 blast-radius items appear as tasks 2.1 / 5.1 / Non-Goals, and the SAS-TTL clause is correctly absent (A8). `decision-log.md` [11] rejects issue #276's "S3 unaffected" framing openly rather than inheriting it.

## Feasibility

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: `plan.md` § Impact and § Implementation Tasks (no task); `vs-adapter/storage-backend-enum/spec.md` scenario "Every consumer holds a backend and no consumer names one"
- Issue: per-side scheme selection is discarded for a join's dimension side. `crates/lakehouse-engine/src/adapter/pushdown/joins/planning.rs:340` calls `resolve_file_list` once per side, so each side gets its own `ResolvedJoinSide::effective_storage`; but `crates/lakehouse-engine/src/adapter/pushdown/joins/sql_builders.rs:578` sets `storage: primary.effective_storage.clone()` as the spec's single `CommonScanSpec.storage`, and `crates/lakehouse-engine/src/scan/object_store.rs:107-110` declares `StoreRegistration.backend` a "whole-spec value shared identically by every side's registration call". Under the shipped rule both sides always carried the same variant, so the collapse was variant-safe. The delta makes the variant per-table-location, so the collapse is now wrong. Failure scenario: a broadcast-eligible inner equi-join under one vended CONNECTION between an `s3://` fact and an `abfss://` dim resolves `primary` = S3; `register_side_store`'s S3 arm then runs for the dim's `abfss://` files, takes `store_url.host_str()` as an S3 bucket name (`object_store.rs:141`) and builds an `AmazonS3Builder` against the Azure host. `validate_sides_share_one_store` (`object_store.rs:444`) does not catch it — it only errors when two sides share a registry key, and the two schemes produce different keys. The same-variant case fails too: two `abfss://` sides on different accounts (a shape `object_store.rs:851` already tests) get the fact side's account name and its host-matched SAS applied to the dim side, so the ADLS arm's whole host-matching design is defeated for that side. `plan.md` § Impact enumerates the blast radius and never names the join path.
- Fix: Add a task under § Implementation Tasks 2 that makes a per-side backend mismatch a plan-time `UdfError::User` in `crates/lakehouse-engine/src/adapter/pushdown/joins/planning.rs`, comparing the two resolved sides' `effective_storage` (variant, and for `Adls` the `account_name`) before `join_scan_spec` collapses them, naming neither credential value; add a matching `DELTA:NEW` scenario to `vs-adapter/pushdown-planning-cloud-credentials/spec.md` requiring the error; add a § Verification > Scenario Coverage row and a unit test in `joins/planning.rs`; and add a § Impact bullet stating that scheme-driven selection is per-table-location while the scan spec carries one backend per spec.

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `plan.md` § Impact (Glue bullet), § Verification Obligations item 1, task 4.2; `decision-log.md` § [5]; `e2e-harness/cloud-e2e-harness/spec.md` Background bullet 2 and scenario clause 3
- Issue: the plan names the Glue risk as `client.region` alone. The real premise is larger and the plan's own verification instrument does not test it. `crates/lakehouse-engine/tests/cloud_e2e_test.rs:139-159` builds the vended CONNECTION as `catalog_connection_password()` with `use_vended_credentials: true` — so it carries a static `access_key`, `secret_key`, **and** `session_token` from the AWS env. Under the shipped preservation rule (`vended.rs:82-87`) all three are preserved when Glue vends nothing. `cloud_scan_reads_with_vended_credentials` passing today is therefore compatible with Glue vending **zero** storage credentials: the scan would read with the test's own static AWS keys. Task 4.2 asserts only "a non-empty `client.region` or `s3.endpoint`", so it would pass while the key pair is absent and the strict rule kills the whole Glue vended path at plan time. The STS session token is a third unnamed case: an absent vended `s3.session-token` beside a vended temporary key pair now yields `None` instead of the preserved static token, and fails at read time rather than plan time.
- Fix: Extend task 4.2 to assert that Glue's selected credential source carries a non-empty `s3.access-key-id` and a non-empty `s3.secret-access-key`, and to report whether `s3.session-token` is present, failing with the absent key name and no credential value; add the same three keys to `e2e-harness/cloud-e2e-harness/spec.md`'s scenario clause 3 and Background bullet 2; and rewrite `plan.md` § Impact's Glue bullet and § Verification Obligations item 1 to state that the unverified premise is the whole vended S3 credential set, not the region alone, and that the shipped green test cannot evidence it because the preservation rule masks a fully absent vended payload.

#### [NFR_IGNORED] BLOCKER
- Location: `vs-adapter/pushdown-planning-cloud-credentials/spec.md` Background bullet 18 and scenario "Vended S3 credentials are the sole storage source…" clause 5; `decision-log.md` § [3]; `plan.md` § Impact (second secondary consequence)
- Issue: the plan claims the derivation is "strictly NARROWER than the shipped behaviour it replaces". That claim is false in the default configuration, and the default is the secure one. `crates/lakehouse-engine/src/adapter/mod.rs:190-192` defaults `allow_http` to `false` when `ALLOW_HTTP` is absent. Compare per configuration: with `ALLOW_HTTP='true'` the derived value is narrower; with `ALLOW_HTTP` unset the shipped rule permits plaintext to **no** endpoint while the derived rule permits it to any endpoint the catalog names as `http://`. Failure scenario: an operator never sets `ALLOW_HTTP`; a misconfigured or compromised catalog vends `s3.endpoint = http://proxy.internal/`; `register_side_store` builds the S3 store with `.with_allow_http(true)` (`object_store.rs:163`) and the vended STS access key, secret key, and session token travel in cleartext. The operator has no control and receives no error. The plan removes the only operator-facing plaintext control and describes the removal as a narrowing. The `abfs://` half of the A7 mapping compounds this: the Azure backend carries no HTTP knob at all, so a plaintext `abfs://` anchor is accepted with nothing to gate it.
- Fix: Change the derivation to require operator consent: in `plan.md` § Design > Decision step 3, `decision-log.md` [3], and the spec Background bullet plus the scenario clause, specify that a vended plain-`http://` `s3.endpoint` is accepted ONLY when the `ALLOW_HTTP` virtual-schema property is true, and otherwise returns a `UdfError::User` naming the endpoint's scheme and the `ALLOW_HTTP` property with no credential value. Keep the `base` parameter deleted — thread the already-resolved `allow_http: bool` into `resolve_vended_storage` as its own parameter, which is not a CONNECTION-derived value and so does not weaken decision [2]. Delete the "strictly NARROWER" claim from both the spec bullet and `decision-log.md` [3]. Add an error-path test to task 3.3 and a § Verification > Scenario Coverage row.

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: `vs-adapter/pushdown-planning-cloud-credentials/spec.md` scenario "The storage backend under vending is selected from the table location's URI scheme", final clause; `plan.md` § Design > Patterns ("Closed match, no `_` arm")

#### [COMPLETENESS_GAP] ADVISORY

## Design Depth

`resolve_vended_storage` gets genuinely deeper: three parameters and six per-field absence conventions become two parameters and none, while it absorbs variant selection its caller's caller used to make. Decision [1] confronts the superseded "ONE selection site" fence head-on instead of reinterpreting it, and decision [2]'s parameter deletion converts a body-level rule into a signature property. `AdlsCred`'s two-state invariant, `StorageProps`, and the wire encoding are untouched.

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: `plan.md` § Design > Decision step 1 and § Verification Obligations item 2; `vs-adapter/pushdown-planning-cloud-credentials/spec.md` scenario "The storage backend under vending is selected from the table location's URI scheme", clause 1
- Issue: the accepted-scheme set becomes a decision two modules hold independently with nothing enforcing agreement. `resolve_vended_storage` will accept `s3`, `s3a`, `abfss`, and `abfs` and pick a variant; `crates/lakehouse-engine/src/scan/object_store.rs` independently turns each side's file URI into a store, and `abfs://` appears nowhere in the repository — `grep` finds `abfss` in five files and `abfs://` in none. So the plan admits a scheme at plan time that no test anywhere proves the scan can register or read, and § Verification Obligations item 2 reasons only about `MicrosoftAzureBuilder::with_url` for `abfss`. A back-door disagreement here surfaces as a scan-time failure on a path the plan declares supported.
- Fix: Add a unit test to task 3.4 (or a new task under § Implementation Tasks 3) in `crates/lakehouse-engine/src/scan/object_store.rs` proving `register_side_store` builds a store for an `abfs://` file list and an `s3a://` file list, and extend `plan.md` § Verification Obligations item 2 to state that the four accepted schemes must each be registerable on the scan side, naming that test as what discharges it.

#### [BOUNDARY_VIOLATION] ADVISORY
- Location: `decision-log.md` § [3] and § [4]
- Issue: the two decisions apply opposite standards to the same boundary. [4] rejects conditioning the address rule on `s3.path-style-access` because "it would encode the engine's builder logic inside the catalog crate", preferring "a property of the payload alone". [3] then derives `allow_http` inside the same catalog crate from the vended endpoint's scheme — and `allow_http` is consumed at exactly one place, `AmazonS3Builder::with_allow_http` in `crates/lakehouse-engine/src/scan/object_store.rs:163`. "Plaintext is permitted" is not a property of the payload; it is a policy the engine's store builder enforces. By [4]'s own test, [3] is the leak.
- Fix: Add a sentence to `decision-log.md` [3]'s Rationale reconciling it with [4] — either by naming the derivation as a deliberate exception and why, or, if the BLOCKER fix above threads `allow_http` in as a parameter, by recording that the value is resolved outside the catalog crate and only consumed there.
