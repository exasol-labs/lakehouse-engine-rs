Task 5's retarget table (rows 1-6) covered the test-side comments but missed this one.
- Fix: In crates/vs-expression/src/lib.rs, rewrite the third paragraph of `render_expression_exasol`'s doc comment (line 1075 region) so it states that the Exasol dialect renders a `VARCHAR` target as `VARCHAR(n)` and a `CHAR` target as `CHAR(n)` (plus the ` ASCII` suffix when `dataType.characterSet` is ASCII), that Exasol's parser has no length-less character type, and that this supersedes the "CHAR maps to VARCHAR" rule; cross-reference `renders_cast_char_as_exasol_char` and `cast_char_target_diverges_between_dialects` as the guarding tests.

#### [INFORMATION_LEAKAGE] The pad hand-writes DataFusion-dialect SQL outside the crate that owns dialect rendering
- Location: lines 467-503 (`blank_pad_char_group_keys` doc comment and body)
- Issue: every other DataFusion-side fragment that reaches `ScanSpec` (`filter`, `projection`, `group_keys`) is produced by `vs-expression`'s `Dialect::DataFusion` renderer, which owns the knowledge of what datafusion-sql accepts (see the `Dialect` enum doc at crates/vs-expression/src/lib.rs:16-37). `blank_pad_char_group_keys` is the first place the adapter synthesises DataFusion SQL directly, embedding three DataFusion-dialect decisions (`character_length`, `rpad`, and `CASE`/`ELSE` syntax) as a raw `format!` string. ### crates/lakehouse-engine/src/adapter/pushdown/support.rs

#### [INFORMATION_LEAKAGE] The two seams answer "CHAR dataType with no `size`" differently, and the adapter answers it with the maximum width
- Location: lines 824-836 (CHAR arm); compare crates/vs-expression/src/lib.rs lines 154-158
- Issue: one decision — what an absent `size` on a CHAR `dataType` means — is now made independently in two modules with two different answers. `exasol_type_from_json` uses `.unwrap_or(EXASOL_CHAR_MAX_SIZE)` and yields `CHAR(2000)`; `render_cast_target`'s Exasol CHAR arm yields `VARCHAR(2000000)` and its test `renders_cast_char_exasol_dialect_without_size_falls_back_to_varchar_default` documents that as the project's "unknown/incompatible width" convention. Neither doc comment acknowledges the other, so the disagreement is invisible from either site. Independently, defaulting to the *maximum* is the most damaging available default: `CHAR(2000)` makes Exasol blank-pad every value of that column to 2,000 characters, whereas Exasol's own unqualified `CHAR` is `CHAR(1)`. The `.unwrap_or(EXASOL_CHAR_MAX_SIZE)` followed by `.min(EXASOL_CHAR_MAX_SIZE)` also reads as if the default could exceed the cap, which it cannot.
- Fix: In crates/lakehouse-engine/src/adapter/pushdown/support.rs, change the CHAR arm's absent-`size` default (line 828-831) to the project's "unknown width" convention so both seams agree — return `"VARCHAR(2000000)".to_string()` when `size` is absent, and apply `EXASOL_CHAR_MAX_SIZE` only as `.min(...)` on a present `size`; state in the arm's comment that an absent `size` is unreachable from a real Exasol `dataType` and that this matches `vs-expression`'s `render_cast_target` Exasol CHAR arm. Add a unit test `exasol_type_from_json_char_without_size_falls_back_to_unknown_width` asserting `exasol_type_from_json(&json!({"type":"CHAR"}))` returns `"VARCHAR(2000000)"`.

#### [MAGIC_NUMBER] VARCHAR's 2,000,000 ceiling stays a bare literal beside the newly-named CHAR constant

The same literal also appears as the "unknown width" placeholder at grouped_agg.rs:450, 123, 661, 1144, so the number carries two distinct meanings across the module with no name for either.

### crates/lakehouse-engine/tests/e2e_capability_test.rs

#### [ASSERTION_FREE_TEST] Both over-length E2E tests carry an assertion that cannot fail, and neither proves the CHAR pushdown path ran
- Location: lines 1267-1272 and 1313-1318 (`numRows` assertions); lines 1257 and 1303 (`resp["message"]` fallback)
- Issue: two defects in `over_length_char_group_key_raises_truncation_error_like_native` and `over_length_char_projection_fails_cleanly`. First, the closing assertion `resp["responseData"]["results"][0]["resultSet"]["numRows"].as_i64() == None` is vacuous: `ExaConn::try_execute` (crates/lakehouse-engine/tests/common/exasol_ws.rs:121-131) returns the raw WebSocket response, and an error response carries `status`/`exception` with no `responseData` at all, so the index chain is unconditionally `Null` once `status == "error"` has already been asserted two assertions earlier. It reads as "must not return a silently truncated result set" but cannot fail for any implementation. Second, both tests assert only that Exasol raised a 22001/truncation error — which native Exasol raises identically if the adapter *declines* the CHAR pushdown entirely and Exasol computes the query itself. A regression that reverted the `"char"` arm would leave both tests green. The plan's Task 8 asked to "compare against the native control to prove equivalence rather than merely asserting 'some error'"; no native control was implemented. Third, the `.or_else(|| resp["message"].as_str())` fallback at lines 1257 and 1303 reads a field the Exasol WebSocket error envelope never sets (it is always `exception.text`), so it is dead.
- Fix: In crates/lakehouse-engine/tests/e2e_capability_test.rs, in both `over_length_char_group_key_raises_truncation_error_like_native` and `over_length_char_projection_fails_cleanly`: delete the vacuous `numRows` assertion and the dead `.or_else(|| resp["message"].as_str())` fallback; tighten the error assertion to require `sql_code.contains("22001")` (drop the `||` on the message text, keeping the message only in the failure output); and add, before the failing statement, an `EXPLAIN VIRTUAL` assertion on the same query proving the pushdown was taken and carries the CHAR declaration — assert the pushdown SQL contains `CHAR(20)` and does not contain `VARCHAR(20)` — using the same `EXPLAIN VIRTUAL` pattern already used elsewhere in the E2E suite. Then re-run both tests with `make test-e2e` against the running Docker stack and record the output.

## Expert fixes

### crates/lakehouse-engine/src/adapter/pushdown/grouped_agg.rs

#### [SENTINEL_ERROR_VALUE] A CHAR group key that is not in the select list silently skips the pad and returns a wrong row count
- Location: lines 442-464 (`group_key_exasol_types`, placeholder seeded at line 450), consumed at lines 487-503 (`blank_pad_char_group_keys`) and crates/lakehouse-engine/src/adapter/pushdown/mod.rs:386-398
- Issue: `group_key_exasol_types` resolves a declared type only from `GroupedSelectItem::GroupKey` entries — that is, only for group keys that *also* appear in `selectList`. Every other slot keeps the in-band placeholder `"VARCHAR(2000000)"` seeded at line 450, which the module treats as "type unknown" by string comparison at lines 123, 661, and 1144 rather than through the language's optional type. `blank_pad_char_group_keys` inherits that placeholder: `char_width("VARCHAR(2000000)")` returns `None` (the `CHAR(` prefix is anchored), so a group key Exasol declared `CHAR(n)` but did not project is handed to DataFusion **unpadded**.

  That shape is reachable and pushed down today. `detect_group_by_aggregates` (line 171) requires only a non-empty `groupBy` and a non-empty `selectList`, not that every key is projected; `build_grouped_aggregate_scan_sql` emits `GROUP BY "GK_0"` over all `group_keys.len()` staging columns regardless of which are selected (line 705). So `SELECT COUNT(*) FROM char_pad_probe GROUP BY CAST(val AS CHAR(30))` groups on the raw unpadded staging values: `'ab'` and `'ab   '` stay two groups and the query returns 4 rows where native Exasol returns 3. Unlike the projected case there is no outer `CAST("GK_0" AS CHAR(n))` on this path, so nothing raises a type mismatch and nothing surfaces the divergence — this is precisely the silent-wrong-answer failure class the plan states it exists to prevent ("declaring CHAR without padding would convert a clean rejection into a silently wrong answer"). The plan's exposure analysis concluded "the one exposed position is a `CHAR`-declared grouped-aggregate group key" but scoped the fix to keys that carry a `selectListDataTypes` ordinal.

  The `groupBy` node itself carries the type — the plan's own architecture diagram lists "`groupBy` dataType" as an `exasol_type_from_json` input, and the new test helper `char_cast_key` (mod.rs) builds exactly such a node with its `dataType` attached — so the information needed to close the hole is already in the request.
- Fix: In crates/lakehouse-engine/src/adapter/pushdown/grouped_agg.rs, extend `group_key_exasol_types` to take the `groupBy` array into account: after the existing `selectList`-driven pass, for every slot still holding the `"VARCHAR(2000000)"` placeholder, read that slot's `groupBy[slot]["dataType"]` and, when present, resolve it through `exasol_type_from_json`. Keep the `selectList`-derived type authoritative where both exist (Exasol validates the output column positionally against `selectListDataTypes`). Update the function's doc comment to state both sources and the precedence. Add unit tests in the same file: (1) `group_key_exasol_types_resolves_char_type_for_unprojected_group_key` — a request whose `selectList` is `[COUNT(*)]` only and whose `groupBy` is a `CAST(NAME AS CHAR(20))` node, asserting the resolved type is `CHAR(20)`; (2) a dispatcher-level test in crates/lakehouse-engine/src/adapter/pushdown/mod.rs mirroring `grouped_char_declared_group_key_reaches_the_scan_spec_blank_padded` but with the key absent from the select list, asserting the emitted `ScanSpec.common.group_keys` still carries the pad wrapper; (3) a control asserting an unprojected VARCHAR group key stays unpadded. If any residual shape still cannot resolve a declared type (for example a `groupBy` node that carries no `dataType`), record it explicitly in the plan's spec delta as a cited tracked exception per the project's "never a silent gap" rule rather than leaving it undocumented.
