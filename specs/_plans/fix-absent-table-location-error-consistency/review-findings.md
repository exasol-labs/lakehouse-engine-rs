#### [CONTEXTLESS_ERROR] Absent-location error names no table and misdescribes the input shape
- Location: lines 250-256 (the hoisted guard's `UdfError::User` message)
- Issue: two defects in one string.
  (a) The message names no table, although `catalog_props.table` is in scope. Every other table-scoped error in this same file carries it — `"failed to open Iceberg manifest list for '{}'"` (`:450`), `"failed to read Iceberg manifest list for '{}'"` (`:459`), `"failed to parse Iceberg manifest list for '{}'"` (`:471`), `"failed to load Iceberg manifest for '{}'"` (`:480`), `"failed to plan Iceberg files for '{}'"` (`:550`). This matters most on the path the hoist was made to cover: `resolve_one_join_side` (`joins/planning.rs:406`) calls `resolve_file_list` once per join leg, so a join whose dimension side is malformed produces an error that does not say which side failed. Guardrail: "Every error states what was attempted, the input that failed, and the constraint violated."
  (b) The message says the response "carries no table `location`", but the shape that reaches this guard is key-present-value-EMPTY. The omitted-key shape is a different failure with a different owner and a different message (`"failed to parse catalog response: …"` from `iceberg_io.rs:86`) — a distinction the spec delta keeps explicit (`vs-adapter/pushdown-planning/spec.md:112`). Reporting the empty-value shape with absent-key wording sends the reader looking for a missing key.
- Fix: In `crates/lakehouse-engine/src/adapter/pushdown/file_resolution.rs`, change the guard at lines 250-256 from the static `UdfError::User(...into())` to a `format!`-built message that names the table and the empty-value shape, keeping the `warehouse` non-substitute clause verbatim: ``UdfError::User(format!("the loadTable response for table '{}' carries an EMPTY table `location`; the catalog `warehouse` is a routing identifier, not a table location, and is not a valid substitute", catalog_props.table))``. Do not route it through `redact_error_text` — no secret is interpolated, and `secrets` is not yet bound at that point. Then, in the same file's `absent_table_location_errors_on_both_vended_and_static_paths`, add a third assertion inside the existing `for (path, message)` loop requiring `message.contains("db.t")` with the failure text `"{path}-path error must name the table whose loadTable response was malformed: {message}"`, so the join-side diagnosability this fix adds cannot silently regress. Leave the existing `loadTable` / `location` / negative `storage backend cannot be resolved` assertions and the `assert_eq!` two-path identity assertion unchanged.

#### [SWALLOWED_ERROR] Loopback fake's failures are discarded by the dropped `JoinHandle`
- Location: lines 1822-1836 (the `tokio::spawn` block in `resolve_file_list_against_locationless_catalog`)
- Issue: the spawned server task uses `.expect("accept")`, `.expect("read")` and `.expect("write")`, but the `JoinHandle` is dropped, so a panic in the fake is swallowed by the runtime and never surfaces. - Fix: In `crates/lakehouse-engine/src/adapter/pushdown/file_resolution.rs`, bind the `tokio::spawn` result in `resolve_file_list_against_locationless_catalog` to a `server` variable, and after the `resolve_file_list(...)` call — before returning — `server.await.expect("the loopback catalog fake must serve its one response without panicking")`. Restructure the function to capture the `resolve_file_list` result into a local first, then await the handle, then return that local, so the fake's panic is reported as itself rather than as a failed assertion on the code under test. Keep the `.expect(...)` calls inside the task; awaiting the handle is what makes them observable.
