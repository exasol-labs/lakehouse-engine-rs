# Decision Log: fix-broadcast-join-limit-suppression

## Interview

**Q1:** Where should the limit go for a bare `LIMIT` over a broadcast join?
(a) *Outer-wrapper only (minimal)* — mirror the existing fallback's `outer_wrapper_clauses` / `render_limit_offset`, apply `LIMIT` once over the full merged broadcast-join result, no per-shard truncation. Correctness-safe but no join-work savings.
(b) *Per-shard post-join truncation (deeper)* — additionally cap each shard's own joined/emitted output at `n` (post-join, not pre-join, since a pre-join leg cap does not bound output cardinality), requiring an extension to the ScanSpec/JoinSpec contract and UDF-side execution.
**A1:** (b) Per-shard post-join truncation. The point is the actual performance win, not just correctness — each shard's own join execution should stop early / truncate its own output at `n`, not just get truncated later by an outer wrapper.

**Q2:** Should OFFSET be in scope — i.e. should `LIMIT`+`OFFSET` without an `ORDER BY` also broadcast?
**A2:** Exclude — bare `LIMIT` only. `LIMIT`+`OFFSET` without `ORDER BY` stays forced to fallback via the existing guard (unchanged). Record this explicitly as an out-of-scope decision in the decision log — not a silent gap, but also NOT a GitHub issue; a decision-log note is sufficient, since OFFSET-without-ORDER-BY is already nondeterministic SQL and the "any N qualifying rows" correctness argument this fix relies on does not obviously extend to it.

**Q3:** Should observability of the declined-broadcast reason be in this plan or a separate follow-up?
**A3:** Initially "separate follow-up issue"; on a later confirmation round, restricted to filing ONLY the TopN follow-up (Q5). The observability follow-up is explicitly NOT filed as a GitHub issue — record it as an open, named follow-up note in the decision log instead.

**Q (mid-interview, asked inline):** What is the ORDER BY+LIMIT problem with the broadcast join? Can we just have the broadcast join and the ORDER BY+LIMIT rendered in the pushdown Exasol SQL?
**A (answered inline, reproduced here so the reasoning is not lost):** For a broadcast join the join itself executes inside each shard's UDF (node-local DataFusion), not in Exasol's core engine — unlike the fallback path, where Exasol's core engine performs the actual join over two fully-scanned, unioned sides, so an outer `ORDER BY … LIMIT` sitting on top of that complete result is trivially correct. Because of that, there are two distinct ways to get ORDER BY+LIMIT correct over a broadcast join. (1) *Outer-wrapper only* — every shard emits its full, unsorted, untruncated local joined output; Exasol applies `ORDER BY … LIMIT n` once over the full merged result. Correctness-trivial (the same "compute everything, sort once at the end" argument), no per-shard join-work savings. (2) *Per-shard TopK acceleration* — each shard sorts+limits its own joined output to its local top-N before emitting (mirroring the flat-scan TopN pattern in `specs/vs-adapter/pushdown-planning-topn/spec.md`, which requires a per-shard `LIMIT` to always be paired with a matching per-shard `ORDER BY` to be safe), then Exasol re-merges, re-sorts and re-limits over the shard-local top-Ns. That is the option that actually saves join work, but it is harder than the bare-LIMIT case specifically because the ORDER BY key can reference columns from *either side* of the join (a post-join expression, not a pre-join column), so it needs a DataFusion TopK operator threaded through the JoinSpec/UDF contract, plus the outer wrapper has to re-render that exact same expression correctly over the merged/aliased join columns.

**Q4:** Given per-shard truncation was chosen for bare LIMIT, what is the scope for ORDER BY+LIMIT (TopN) over a broadcast join?
(1) in scope, outer-wrapper only; (2) in scope, full TopK acceleration; (3) out of scope, track as follow-up.
**A4:** Option 1 — in scope, outer-wrapper only (reuse `render_order_by` / `render_limit_offset`, no per-shard sort/limit) — AND file a follow-up GitHub issue for the TopK-acceleration variant (option 2), since that is the harder, deferred half.

**Q5:** File the TopN-acceleration follow-up issue?
**A5:** Yes — and only that one ("only report Issue B"). Filed as https://github.com/exasol-labs/lakehouse-engine-rs/issues/309, "Broadcast join TopN (ORDER BY+LIMIT) computes the full per-shard join before truncating". Cite #309 inline in the relevant spec delta following the repo's `(#27)` tracked-exception convention.

**Q6:** Iceberg-spec compliance check (required by this repo's CLAUDE.md for anything touching pushdown). The proposed reasoning was that this change is pure Exasol SQL-rendering / join-planning logic and touches no Iceberg-governed behavior.
**A6:** Agreed — record it as an explicit N/A determination *with reasoning* in the decision log, do not silently skip the check.

**Q7 (confirmation round, after the plan was authored):** Two authoring decisions reached past the literal wording of A4 and A2 and were put back to the user with a worked-example decision matrix. (a) Q4 scoped "ORDER BY+LIMIT (TopN)" — should a bare `ORDER BY` with no `LIMIT` over a broadcast join also be broadcast-eligible, as decision [7] has it? (b) A2 said "exclude OFFSET" — should `ORDER BY`+`LIMIT`+`OFFSET` be served on the broadcast wrapper while bare `LIMIT`+`OFFSET` with no `ORDER BY` stays on the fallback, as decision [8] has it?

**A7:** Both confirmed exactly as authored; no design change, no spec or task change. The reasoning the user reviewed and accepted:

- **(a) Bare `ORDER BY`, no `LIMIT` — in scope.** Unlike a `LIMIT`, a bare `ORDER BY` demands no per-shard behavior change: every row must be visited to sort it regardless, so "full per-shard emission plus an outer `ORDER BY`" is baseline behavior at zero incremental risk. The only difference from a plain broadcast join is the outer wrapper's SQL shape. The per-shard-versus-global ambiguity that makes `LIMIT` delicate has no analogue here, so the arm needs no extra guard.
- **(b) `ORDER BY`+`LIMIT`+`OFFSET` allowed, bare `LIMIT`+`OFFSET` excluded.** Once an `ORDER BY` is present the design is already "full per-shard emission, one outer global sort and paginate" (the TopN case is deliberately unaccelerated — tracked as #309). An `OFFSET` riding on that adds no mechanism: it is the same single, once-materialized global operation `render_limit_offset` already renders. Bare `LIMIT`+`OFFSET` with no `ORDER BY` is different in kind — pushing it per shard returns *wrong* rows, not merely a different valid unordered answer. Worked counterexample the user reviewed: three shards holding 5, 5, and 50 qualifying rows, query `LIMIT 5 OFFSET 5+5`. Pushing `.offset(10).limit(5)` into each shard independently yields shard 2's rows 11-15, while the correct global "skip 10, take 5" — in any consistent cross-shard order — is shard 2's rows 6-10, because shards 0 and 1 already supply the ten skipped rows. `OFFSET` is a skip and does not compose additively across independently offset shards the way `LIMIT`'s cap does (proven for bare `LIMIT` by the sum-of-per-shard-caps ≥ global-total-needed inequality). Serving unordered `LIMIT`+`OFFSET` correctly would need a third, inconsistent outer-only code path that abandons the per-shard acceleration bare `LIMIT` earns — for a combination that is already semantically marginal, since `OFFSET` without a defined order is nondeterministic pagination. It stays on the fallback.

## Design Decisions

### [1] The per-shard post-join LIMIT mechanism already exists; the VS only stops suppressing it — SUPERSEDED by [12]

- **SUPERSEDED after plan review round 2, by decision [12] "The post-join cap is a field of `JoinSpec`, so a join-less spec cannot express one" (user-confirmed).** Kept here as the record of what was tried and why it was reversed.
- **Decision (reversed):** Implement the per-shard cap by setting `spec.common.limit` on the broadcast scan spec. Do NOT extend `JoinSpec`, the scan-spec wire format, or the scan UDF.
- **Alternatives:** Add a dedicated `JoinSpec.post_join_limit` field (would prove "post-join" by type); call `.limit()` on the DataFusion `DataFrame` after the join in the UDF.
- **Rationale (as authored):** `build_join_sql` (`crates/lakehouse-engine/src/scan/join_scan.rs`) already renders `spec.common.limit` after the `INNER JOIN` and the `WHERE`, and `datafusion-scan/scan-execution-join` already requires "no more rows than the limit when one is carried". The interview answer (A1) assumed a ScanSpec/JoinSpec contract extension was needed; verification during planning showed it is not. A new field would duplicate an existing one and change the wire format for no behavioral gain. This *reduces* the scope of the option the user chose without reducing what it delivers.
- **Why that rationale no longer holds:** it weighed the new field against *behavioral* gain only, and on that axis it was correct — the two designs emit the same rows. What it did not weigh is the STRUCTURAL requirement the fallback delta already carried: that a leg spec be unable to express a post-join cap. Round 2 established that `common.limit` cannot deliver that at any field visibility, because the same crate and module tree legitimately writes `limit` on join-less specs from four other paths (round-2 finding, grounds 1 and 2). Once the structural guarantee is a requirement rather than a nicety, the second field is not duplication — it is the only place the guarantee can live. Interview answer A1 had in fact expected exactly this: it chose per-shard truncation while anticipating "an extension to the ScanSpec/JoinSpec contract".
- **Promotes to ADR:** no

### [2] DataFusion will not silently turn the post-join cap into a pre-join cap

- **Decision:** Rely on DataFusion's optimizer, in addition to SQL clause placement, to keep the cap post-join; pin it with a plan-shape assertion rather than only a row-count assertion.
- **Alternatives:** Assume SQL placement alone is sufficient; disable limit pushdown wholesale in the session config.
- **Rationale:** Verified against the pinned vendored source: `push_down_join` (`datafusion-optimizer-54.1.0/src/push_down_limit.rs`) returns `(None, None)` for `JoinType::Inner` unless the join is a CROSS join (`on.is_empty() && filter.is_none()`), which a rendered equi-condition excludes. Two independent levels must both hold, so an accidental pre-join cap requires breaking both. Disabling the rule would cost pushdown elsewhere for a guarantee already given.
- **Promotes to ADR:** no

### [3] Replace the boolean forcing predicate with a window classification

- **Decision:** `join_requires_exasol_postprocessing` becomes a classification returning `Unbounded` / `BareLimit(n)` / `Ordered { keys, limit, offset }` / `ExasolPostProcessed`. `plan_join` dispatches on it.
- **Alternatives:** Keep the boolean and add a second function that separately answers "what window must the broadcast path render".
- **Rationale:** The boolean is a shallow interface: it tells the caller a decision was made but not which one, so the caller cannot act on it. Two functions would put the same "which clause forces what" decision in two owners — the information-leakage failure `/speq:design-philosophy` names. One enum keeps exactly one module owning the rule, and lets the unit test enumerate every arm exhaustively instead of spot-checking a boolean.
- **Amended after plan review round 1:** the classifier reads the `pushdown` REQUEST only, and runs where the boolean runs today — before `select_broadcast_sides` and before `render_broadcast_join`. One arm cannot live there: whether the RENDERED broadcast projection can bind a sort key is unanswerable before the render, and moving the render earlier would reverse `plan_join`'s short-circuit (an aggregate-over-join request would pay a full render, and `render_broadcast_join`'s no-column-metadata `Err` would newly fire for shapes that reach `build_n_scan_join_sql` today). That single arm therefore moves to the broadcast construction site. This is two decision SITES with one decline OUTCOME and a strict split of inputs — the classifier may look only at the request, the builder only at the rendered projection — not the two-owners-of-one-rule leakage this decision rejects.
- **Promotes to ADR:** no

### [4] The join block and the post-join row limit are attached together, by one checked `ScanSpec` constructor — SUPERSEDED by [12]

- **SUPERSEDED after plan review round 2, by decision [12] "The post-join cap is a field of `JoinSpec`, so a join-less spec cannot express one".** The GOAL below survives verbatim — the pre-join/post-join distinction must be structural, not conventional — and decision [12] is what finally delivers it. Only the MECHANISM is retired: no `ScanSpec::with_broadcast_join` constructor is added, and `join_fan_out_scan_spec` KEEPS its `join: Option<JoinSpec>` parameter, because a constructor that can no longer pair anything (the cap now lives inside the join block, which the caller constructs as a literal) would be a shallow two-line setter restating a rule the type already enforces. Kept here as the record of what was tried and why it was reversed.
- **Decision (REVISED after plan review round 1 — option (b) of the reviewer's two; now reversed):** `join_fan_out_scan_spec` LOSES its `join: Option<JoinSpec>` parameter and always returns a join-less, limit-free spec. A new in-crate `ScanSpec::with_broadcast_join(self, join: JoinSpec, post_join_limit: Option<u64>) -> Self` (`crates/lakehouse-engine/src/scan/spec.rs`) is the ONE seam that attaches either, and it attaches them together. The N-scan leg builder has no join block to supply and therefore no way to reach a limit.
- **Alternatives:** Keep the helper's signature and write `spec.common.limit = Some(n)` at the broadcast construction site (the pre-review decision); add a `limit: Option<u64>` parameter to `join_fan_out_scan_spec` that the leg builder passes `None` for; add `ScanSpec::with_post_join_limit(self, n)` guarded by a `debug_assert!(self.common.join.is_some())`; move the limit into `JoinSpec` so the type system proves it can only exist alongside a join block.
- **Rationale (as authored):** The same `CommonScanSpec.limit` field means categorically different things on the two paths — a post-join cap on the broadcast spec, a *pre-join input* cap on a fallback leg. A pre-join leg cap discards rows that would have matched and keeps rows that produce no output: wrong rows, no error. The pre-review decision resolved that with construction-site convention, which is not a boundary: nothing owned the distinction and nothing enforced it, so the fallback delta's "SHALL make that structural" clause promised more than the design delivered. A separate `with_post_join_limit` guarded by a runtime assert is checked only in debug and still leaves the pairing implicit. Taking the join block and the limit in ONE call makes the pairing hold by signature, in release as well as debug, and gives the pre-join/post-join rule a single home — the constructor's doc comment — that the leg builder, the broadcast builder, and the scan-side `build_join_sql` all cross-reference instead of restating. It costs one in-crate method: no wire-format change, no `JoinSpec` change, no UDF change. Pinned additionally by a unit test asserting every fallback leg spec stays limit-free and sort-free.
- **Why that rationale no longer holds:** "the pairing holds by signature" binds only callers that go THROUGH the signature. `build_side_fan_out_sql` is in the same crate and the same module tree as the constructor and as `CommonScanSpec`'s public fields, so `spec.common.limit = Some(n)` there stays legal and unchecked no matter what the constructor's signature says — the constructor makes the safe route convenient, not the unsafe route impossible. Round 2 established that no field visibility closes that gap either (see the R2-B2 findings). A field of `JoinSpec` does close it, and once it exists the constructor has no pairing left to perform.
- **ADR note:** superseded before recording, so decision [12] carries the ADR for this rule instead of this entry.
- **Promotes to ADR:** no

### [5] The ordered broadcast path accepts only bare-column sort keys already in the projection

- **Decision:** An expression sort key, an aggregate sort key, an element missing `isAscending`/`nullsLast`, and a bare column absent from the broadcast projection all decline the broadcast plan and fall through to the unified fallback. Only bare columns present as `ProjectionItem::Column` items are served.
- **Alternatives:** Extend the broadcast projection with hidden sort-key columns, as the declined single-table row-scan path does.
- **Rationale:** Zero regression either way — every one of these shapes reached the fallback before this plan. The hidden-column mechanism would need per-side Exasol type resolution over the two-table column universe and a projection widening that `render_broadcast_join` currently declines outright (#196). Requiring projection membership is what lets the wrapper bind its `ORDER BY` to the fan-out's `emits_ident` output without any of that.
- **Promotes to ADR:** no

### [6] The broadcast decline is a fall-through, never a hard `User` error

- **Decision:** Any ordering or window shape the broadcast wrapper cannot bind classifies `ExasolPostProcessed` and routes to the fallback. It never raises the `User` decline that `vs-adapter/pushdown-planning-topn` specifies for an unrenderable row-scan sort key.
- **Alternatives:** Reuse `ensure_every_sort_key_renders`, which hard-errors on an unrenderable element.
- **Rationale:** That rule exists because on the declined row-scan path no other renderer is left, so returning rows would mean returning them silently misordered. Here the qualified fallback wrapper renders every one of these shapes correctly, table-qualified from its owning side — including expression sort keys (`order_by_expression_renders_qualified_in_unified_wrapper`). Reusing the hard decline would turn currently-working queries into failures.
- **Amended after plan review round 1:** dropping `ensure_every_sort_key_renders` also drops the upstream guarantee `wrap_declined_order_by` documents as its own precondition — if no key renders it returns its input UNCHANGED, which on this path would be a broadcast plan with no `ORDER BY` while `ORDER_BY_COLUMN` is advertised, i.e. silently misordered rows and no error. The broadcast caller therefore supplies that precondition itself (constructing only `ParsedSortKey::Column`) AND verifies it: `debug_assert!` for a loud failure in test builds, and a `None` return — the same fall-through — in release, so the worst outcome is an unaccelerated plan rather than a wrong one.
- **Promotes to ADR:** no

### [7] An ordering with no LIMIT is served by the broadcast path too — user-confirmed (A7a)

- **Decision:** The ordered broadcast arm is gated on "every sort key is a bare projected column", not on "and a `limit` is present". A bare `ORDER BY` with no `LIMIT` therefore also broadcasts, wrapped in an outer `ORDER BY` with an empty window.
- **Alternatives:** Gate the arm on `limit.is_some()`, leaving `ORDER BY`-without-`LIMIT` on the fallback exactly as today.
- **Rationale:** Q4 scoped "ORDER BY+LIMIT (TopN)", so this arm reaches one shape past that wording. Excluding it costs an extra guard condition and creates an asymmetry with no correctness basis: `render_limit_offset(None, 0)` is the empty string, the wrapper is identical, and one broadcast fan-out strictly beats the fallback's two independent scans plus an Exasol-core-engine join. Splitting "ORDER BY forces fallback unless the keys are bare projected columns" into two rules by whether a limit happens to accompany it would be a second, unjustified rule.
- **Confirmation (A7a):** The user was asked whether to hold the literal Q4 scope instead — a single added condition in the classifier and one spec clause. Shown the argument that a bare `ORDER BY` demands no per-shard behavior change at all (every row must be visited to sort it, so full per-shard emission plus an outer `ORDER BY` is zero-incremental-risk baseline behavior, differing from a plain broadcast join only in the outer wrapper's SQL shape) and that the per-shard-versus-global ambiguity making `LIMIT` delicate has no analogue here, the user confirmed the decision as authored. No change.
- **Promotes to ADR:** no

### [8] OFFSET stays out of scope for a bare LIMIT, and is served on the ordered wrapper — user-confirmed (A7b)

- **Decision:** A `limit` with a non-zero `limit.offset` and an absent or empty `orderBy` declines the broadcast plan and stays on the unified fallback, per A2. The ordered broadcast wrapper renders `ORDER BY … LIMIT n OFFSET m` through the shared `render_limit_offset` seam, so an offset arriving with an ordering IS served.
- **Alternatives:** Decline every offset-carrying request from the broadcast path; serve an offset per shard.
- **Rationale (bare-LIMIT exclusion, per A2):** OFFSET-without-ORDER-BY is already nondeterministic SQL, and the "any N qualifying rows" argument that licenses the per-shard cap does not extend to a window — a per-shard `OFFSET m` skips each shard's OWN first `m` rows and the union of those windows is not the global window. Recorded here rather than as a GitHub issue, as the user directed: it is a reasoned scope boundary, not a defect. The shape is additionally unreachable in production (a non-zero offset never arrives without a non-empty `orderBy` — the offset-implies-ordering invariant in `vs-adapter/pushdown-planning-order-by-capability`, verified live across 11 shapes), so the guard is structural. **Rationale (ordered inclusion):** the ordered wrapper sits over the complete merged join, where the window is exact — the same position and the same seam the declined row-scan wrapper already uses for issue #191. A4 named `render_limit_offset` as the seam to reuse, and that function's whole purpose is the offset. `ScanSpec` still has no offset field and gains none.
- **Confirmation (A7b):** The user was asked whether A2's "exclude OFFSET" should also bar the ordered wrapper's `OFFSET`, and confirmed the split as authored. The reasoning shown: with an `ORDER BY` present the design is already full per-shard emission plus one outer global sort and paginate, so an `OFFSET` there is zero new mechanism — the same single, once-materialized operation `render_limit_offset` already renders. Bare `LIMIT`+`OFFSET` differs in kind, demonstrated by counterexample: three shards holding 5, 5, and 50 qualifying rows under `LIMIT 5 OFFSET 10`. Pushing `.offset(10).limit(5)` per shard yields shard 2's rows 11-15; the correct global answer, in any consistent cross-shard order, is shard 2's rows 6-10, since shards 0 and 1 already supply the ten skipped rows. That is a wrong result, not a different-but-valid unordered one. Serving it correctly would need a third, inconsistent outer-only path abandoning the per-shard acceleration bare `LIMIT` earns, for a shape that is nondeterministic pagination to begin with.
- **Promotes to ADR:** no

### [11] Open follow-up, deliberately untracked: declined-broadcast observability

- **Decision:** Record, but do not file, a follow-up for making the declined-broadcast reason observable. Per A3, no GitHub issue is created.
- **Alternatives:** File it alongside #309; build it into this plan.
- **Rationale (recorded so it is not lost):** Neither `EXPLAIN VIRTUAL` nor any log or trace distinguishes which forcing condition sent a join to the unaccelerated fallback — `EXPLAIN VIRTUAL` surfaces only the adapter's returned `sql` field, and `adapter/pushdown/joins/*.rs` emits no tracing at all. ### [12] The post-join cap is a field of `JoinSpec`, so a join-less spec cannot express one

- **Supersedes:** decision [1] "The per-shard post-join LIMIT mechanism already exists; the VS only stops suppressing it" and decision [4] "The join block and the post-join row limit are attached together, by one checked `ScanSpec` constructor".
- **Decision (user-confirmed after plan review round 2):** `JoinSpec` gains `post_join_limit: Option<u64>`, an additive optional field omitted from the wire when absent. The broadcast builder sets it in the `JoinSpec` literal it already constructs; `build_join_sql` (`crates/lakehouse-engine/src/scan/join_scan.rs:205`) renders the post-join `LIMIT` from it. `CommonScanSpec.limit` leaves the join path entirely — never written by the broadcast builder, never read by the join scan. No `ScanSpec` constructor is added, no field visibility is narrowed, and `join_fan_out_scan_spec` keeps its `join: Option<JoinSpec>` parameter.
- **Alternatives:** every mechanism built on the shared `CommonScanSpec.limit` field — a bare field write at the broadcast site; a `limit` parameter on `join_fan_out_scan_spec`; the paired `ScanSpec::with_broadcast_join(self, join, post_join_limit)` constructor of decision [4]; `with_post_join_limit(self, n)` guarded by `debug_assert!(join.is_some())`; narrowing `CommonScanSpec.limit` and `.join` to `pub(crate)` or to module-private. Also: a DataFusion `.limit()` call on the joined `DataFrame` instead of the rendered SQL clause.
- **Rationale:** The requirement is structural, not behavioral — a fallback leg builder must be UNABLE to attach a post-join cap, because the same value on a leg spec caps a pre-join input and returns wrong rows with no error. Every alternative above leaves that possible. `pub(crate)` does not restrict `build_side_fan_out_sql`, which is in-crate; nothing stricter works either, because the row-scan and grouped-aggregate paths legitimately write `limit` on join-less specs from the same module tree in production (`pushdown/mod.rs:337` and its setting sites at `:532`, `:762`, `:791`; the explicit clear at `grouped_agg.rs:785`), and the TopN and raw-scan test fixtures in that same module tree write it too (`topn_tests.rs:95`, `raw_scan_tests.rs:175` — a `_tests.rs` sibling is a child module of its parent, in the same crate and the same module tree, so it inherits whatever visibility the parent has). Any visibility those writers need, the leg builder inherits — the hole relocates rather than closes, at a measured cost of 29 out-of-crate test-file migrations across 12 files for zero protection. A constructor binds only callers that use it, and a `debug_assert!` fires only in debug builds. Moving the cap inside `JoinSpec` makes the guarantee a property of the type: a spec with no join block has no field on which a post-join cap could be set, in-crate and out, in debug and release, with nothing to route through and nothing to remember. Cost: one additive defaulted wire field, nine `JoinSpec { … }` struct-literal updates (Rust cannot default-fill a literal), and one moved read site. Backward-compatible in both directions — `#[serde(default, skip_serializing_if = "Option::is_none")]` keeps older specs deserializing and keeps an unordered broadcast request's emitted SQL byte-identical, and no type in this workspace sets `deny_unknown_fields`, so even a skewed older `.so` would merely ignore the cap and lean on the outer merge `LIMIT n` — slower, never wrong.
- **User confirmation:** the `pub(crate)` route selected for R2-B2 was put back to the user once verification disproved it. The user confirmed adopting `JoinSpec.post_join_limit`, explicitly accepting that it reverses decision [1] and the plan Non-Goal barring a wire-format and `JoinSpec` change. Both are amended accordingly; the Non-Goal now bars any wire-format change BEYOND this one field.
- **Promotes to ADR:** yes

### [plan-review] R2-B2 OPEN: no field visibility change can deliver the structural pairing the fallback delta claims — HISTORY, resolved by the next entry

- **Status:** HISTORY (round 2, escalation pass). Its verification findings are the evidence base for the resolution and are still accurate; its "Direction change: NONE yet" and its three open options are closed by the next entry, where the user selected option (i).
- **Finding:** `[REQUIREMENT_CONFLICT]` BLOCKER, **not resolved at the time this entry was written — escalated.** The fallback delta's scenario clause claims a leg builder "has no way to reach a limit, and the pairing is enforced by the signature". The selected fix was option (b), "make it true", by narrowing `CommonScanSpec.limit` and `CommonScanSpec.join` to `pub(crate)` with `ScanSpec::with_broadcast_join` as the only writer. Verification with Serena's `find_referencing_symbols` plus a compiled probe disproves that mechanism, on two independent grounds.
- **Ground 1 — `pub(crate)` does not restrict the named counterexample.** The review's own example site, `build_side_fan_out_sql`, lives in `crates/lakehouse-engine/src/adapter/pushdown/joins/sql_builders.rs` — inside the crate. A `pub(crate)` field is freely writable from every module of the crate, so `spec.common.limit = Some(n)` there stays legal and uncompiled-against. The change would restrict only out-of-crate writers, which are all tests.
- **Ground 2 — a join-less writer of `limit` is REQUIRED, so no stricter visibility closes the hole either.** In production, the single-table row-scan path sets `limit` on a join-less spec (`adapter/pushdown/mod.rs:337` builds the `base` `CommonScanSpec` that the row-scan sites spread and set `limit` on at `:532`, `:762`, `:791`), and `grouped_agg.rs:785` explicitly clears it. The same module tree's test siblings write it too: the TopN spec fixture at `topn_tests.rs:95`, which then passes it into `build_scan_driving_sql` and `wrap_declined_order_by` at `:114` and `:126`, and `raw_scan_tests.rs:175`. A `_tests.rs` sibling is a child module of its parent, in the same crate and the same module tree, so it inherits exactly the visibility the parent has — no visibility rule separates it from `build_side_fan_out_sql` either. Whatever seam any of those paths use to attach a join-less limit is reachable from `build_side_fan_out_sql`, which sits in the same crate and the same module tree. Making the fields module-private to `scan::spec` therefore relocates the hole rather than closing it, while additionally breaking every `CommonScanSpec { … , ..Default::default() }` literal in the crate.
- **Migration surface, measured (the cost side of the same verification).** Rust rejects functional-update syntax when any field is invisible at the use site — confirmed by compiling a probe, `error[E0451]: field 'b' of struct 'S' is private` on `S { a: 1, ..Default::default() }` from an integration test. So `pub(crate)` breaks every out-of-crate struct literal, not only those naming `limit` or `join`: **21 `common: CommonScanSpec { … }` literals across 12 files** — `scan_plan_shape.rs` (4), `scan_no_head_test.rs` (3), `scan_batch_loop.rs` (2), `scan_two_arg.rs` (2), `scan_positional_deletes.rs` (2), `scan_join_test.rs` (2), and one each in `scan_footer_refetch_observable.rs`, `scan_parquet_pruning.rs`, `scan_name_mapping.rs`, `micro_bench.rs`, `scan_agg_projection_pruning.rs`, `scan_telemetry.rs`. Plus **5 out-of-crate field writes** — `scan_footer_refetch_observable.rs:582`, `scan_plan_shape.rs:345` and `:562` (`common.limit`), `scan_positional_deletes.rs:1285` and `:2110` (`common.join`) — and **3 in-literal sets** — `scan_join_test.rs:223`, `scan_join_test.rs:646`, `scan_plan_shape.rs:645`. `crates/lakehouse-catalog` constructs no scan spec (its only mention is a doc reference in `creds.rs:13`), and no bench, example, or bin target does either. A module-private variant would add the ~52 in-crate literals in `mod.rs` (9), `grouped_agg.rs` (14), `support.rs` (13), `joins/sql_builders.rs` (7), `spec.rs` (5), `test_support_tests.rs` (2+1), `topn.rs` (1). (The per-file distribution is as measured before commit `eb2dd18`; that refactor moved most of these literals into each module's `_tests.rs` sibling without changing the total or the argument — see the `[plan-revision]` entry below.)
- **The one mechanism that would deliver the claim, and why it is not mine to adopt:** move the post-join cap out of `CommonScanSpec.limit` into `JoinSpec` as `post_join_limit: Option<u64>`. A limit that lives inside the join block cannot exist without one, in-crate and out, by the type — exactly the claimed property, at small cost (one additive `#[serde(default, skip_serializing_if = "Option::is_none")]` field on the 7-field `JoinSpec` at `spec.rs:437-491`, and `join_scan.rs:205-206` reading it instead of `spec.common.limit`). It reverses decision [1] and three plan Non-Goals ("any change to the scan-spec wire format, the `JoinSpec` block, or the scan UDF"). Decision [1]'s stated rationale — "a new field would duplicate `common.limit` and change the wire format for no behavioral gain" — no longer holds once the structural guarantee is the requirement; and interview answer A1 chose per-shard truncation while explicitly expecting "an extension to the ScanSpec/JoinSpec contract". Reversing a recorded architectural decision is an irreducible choice, so it is escalated rather than assumed.
- **Direction change:** NONE yet. The fallback delta's clause, decision [4], and the round-1 Review-Findings entry are left exactly as they stand, per the instruction not to silently substitute option (a). Three options are put to the orchestrator: (i) adopt `JoinSpec.post_join_limit` and reverse decision [1]; (ii) narrow the clause to the property the paired constructor does deliver — one seam, one doc comment, one pinning test — i.e. the original option (a); (iii) keep the clause and accept it as aspirational, which leaves a false statement bound for an ADR.
