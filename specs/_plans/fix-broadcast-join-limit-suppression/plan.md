# Plan: fix-broadcast-join-limit-suppression

## Summary

Stop a bare `LIMIT` and a bare-column `ORDER BY` from forcing a broadcast-eligible inner equi-join onto the unaccelerated N-scan fallback (issue #307), and make the bare-`LIMIT` case an actual win by capping each fact-shard's own joined output at `n` inside its DataFusion session before the outer merge truncates to `n`.

## Design

### Context

`join_requires_exasol_postprocessing` (`crates/lakehouse-engine/src/adapter/pushdown/joins/planning.rs`) is a boolean over six forcing conditions. Four of them — an aggregate select item, a non-empty `groupBy`, `aggregationType == "group_by"`, a non-null `having` — are genuine: the broadcast in-UDF join renders only projection, filter, and join condition, so those must execute over a materialized join in Exasol's core engine. Two are not: a pushed `limit` and a non-empty `orderBy` were declined rather than handled. The result is that `SELECT … FROM fact JOIN dim ON … LIMIT 100` runs the most expensive plan the adapter has — two independent sharded fan-outs plus an Exasol-core-engine join — and the suppression is invisible, because `EXPLAIN VIRTUAL` is issued without the limit that a row fetch carries. PR #314 (issue #312) later confirmed this live. Direct capture of the adapter's incoming request showed a declared cap arrives as a `limit` that disqualifies broadcast under the old predicate; `EXPLAIN VIRTUAL`, a separate exchange, never carries it.

Four facts discovered during planning reshape the work relative to the issue's framing:

1. **The per-shard post-join LIMIT rendering already exists — hanging on the wrong field.** `build_join_sql` (`crates/lakehouse-engine/src/scan/join_scan.rs:205`) already renders a `LIMIT` after the `INNER JOIN` and the `WHERE`, and `datafusion-scan/scan-execution-join` already requires "no more rows than the limit when one is carried". What it reads is `spec.common.limit` — the shard-invariant field every join-LESS path also writes. The clause placement is right; its home is not (fact 4).
2. **DataFusion will not turn that into a pre-join cap.** `push_down_join` returns `(None, None)` for `JoinType::Inner` unless the join is a cross join (`on.is_empty() && filter.is_none()`), which a rendered equi-condition excludes (`datafusion-optimizer-54.1.0/src/push_down_limit.rs`).
3. **The outer merge LIMIT needs no new wrapper stage.** `build_row_scan_sql` already appends ` LIMIT n` directly to the outer ungrouped scalar select over the distributor — the exact seam the single-table row-scan path uses for the same "full undivided `n` per shard, `n` again on the merge" pattern.
4. **`CommonScanSpec.limit` cannot host the cap safely, and no visibility narrowing fixes that.** `join_fan_out_scan_spec` is shared by the broadcast builder and the N-scan fallback's per-leg builder, and `CommonScanSpec.limit` means categorically different things on the two. On a broadcast spec it is a post-join cap; on a leg spec it caps a bare table scan's pre-join INPUT, discarding rows that would have matched while keeping rows that produce no output — wrong rows, no error. Making the field `pub(crate)` does not separate the two: `build_side_fan_out_sql` sits in the same crate and the same module tree as every legitimate join-less writer of `limit` — in production, the shared `base` literal at `pushdown/mod.rs:337` and the row-scan sites that set it at `:532`, `:762`, and `:791`, plus the explicit clear at `grouped_agg.rs:785`; and in that same module tree's test siblings, the TopN spec fixture at `topn_tests.rs:95` and `raw_scan_tests.rs:175` — so whatever visibility those writers need, the leg builder has too. Any narrower visibility relocates the hole instead of closing it, and breaks every out-of-crate struct literal besides.

The design answer is therefore to move the cap off the shared field and into the join block: `JoinSpec` gains `post_join_limit`. A cap that is a field of the join block cannot exist on a spec that carries no join block. The guarantee holds by TYPE — in-crate and out, in debug and in release — with no constructor to route through, no assertion to fire, and no convention to get wrong.

- **Goals** — restore broadcast eligibility for a bare `LIMIT` and for a bare-projected-column `ORDER BY`; make the bare-`LIMIT` case save real join work per shard; make the pre-join/post-join asymmetry a property of the type rather than a comment.
- **Non-Goals** — per-shard TopK for the ordered case (issue #309); observability of which forcing condition declined a broadcast; any change to the aggregate / GROUP BY / group-by-aggregation / HAVING arms; any scan-spec wire-format change BEYOND the one additive, defaulted `JoinSpec.post_join_limit` field; any change to how the scan executes the join itself, beyond the one line that reads the cap from the join block instead of the common blob; expression or unprojected sort keys on the broadcast path; `LIMIT`+`OFFSET` without an `ORDER BY`.

### Decision

Replace the boolean predicate with one classification that names what the broadcast path must render, and dispatch on it.

#### Architecture

Two sites decide, one outcome declines. The classifier reads the REQUEST only and runs first, preserving today's short-circuit; the construction site owns the one question the classifier structurally cannot answer — whether the RENDERED projection can bind the sort keys — and answers it by returning `None`, the same fall-through the render decline already uses.

```
plan_join
  │
  ├─ 1. classify_join_window(pushdown_req) ──► JoinWindowPlan      [request only]
  │      Unbounded             no limit, no orderBy
  │      BareLimit(n)          limit, no orderBy, offset 0
  │      Ordered{keys,n,m}     keys: Vec<ParsedSortKey::Column>, every element a
  │                            bare column node with both direction flags
  │      ExasolPostProcessed   aggregate / groupBy / group_by / having
  │                            | non-zero offset without orderBy
  │                            | any orderBy element that is not a flagged bare column
  │
  ├─ ExasolPostProcessed ──► build_n_scan_join_sql   (short-circuit: no sizing,
  │                                                   no render; legs limit-free)
  │
  └─ 2. select_broadcast_sides → render_broadcast_join → rendered.projection
        │
        └─ build_broadcast_join_sql(.., plan) -> Option<String>
             JoinSpec { .., post_join_limit }   ── the cap lives HERE, per shard
             spec = join_fan_out_scan_spec(fact, .., Some(join), ..)
                    common.limit stays None on every join spec, always
             Unbounded  : post_join_limit = None
             BareLimit(n): post_join_limit = Some(n)   ── per-shard POST-join cap
                           + build_scan_driving_sql(limit = Some(n))   merge cap
             Ordered    : any key ∉ rendered.projection ──► None (fallback)
                          post_join_limit = None, order_by = []
                          + topn::wrap_declined_order_by(fan_out, .., n, m)
                          wrapper returned input unchanged ──► None (fallback)
             None ──► build_n_scan_join_sql

   build_side_fan_out_sql (fallback leg) constructs NO JoinSpec, so there is
   no post_join_limit field in reach — the guarantee is the type, not a rule.
```

#### Patterns

| Pattern | Where | Why |
|---------|-------|-----|
| Boolean predicate → classification enum | `joins/planning.rs` | One owner decides which REQUEST clause forces what; the caller only dispatches. A boolean forced the caller to re-derive the reason it never had. |
| Projection-membership downgrade at the construction site, not in the classifier | `build_broadcast_join_sql` | The rendered projection does not exist before the render, and moving the render earlier would reverse `plan_join`'s short-circuit. Two decision sites, but ONE decline outcome (`None` → `build_n_scan_join_sql`) and a strict split of what each may look at: the classifier sees only the request, the builder only the rendered projection. |
| The post-join cap is a field of `JoinSpec`, not of `CommonScanSpec` | `JoinSpec::post_join_limit`, `crates/lakehouse-engine/src/scan/spec.rs` | The single owner of "this cap applies AFTER the node-local join, never to either side's scanned input". A cap that lives inside the join block cannot exist on a spec that carries no join block, so the N-scan leg builder — which constructs no join block — cannot express one. The rule holds by type in every build profile and on both sides of the crate boundary, where a shared `CommonScanSpec.limit` plus a constructor, a `pub(crate)` narrowing, or a comment each leave the leg builder a legal way to write it. |
| Reuse `topn::wrap_declined_order_by` verbatim | broadcast ordered path | The wrapper's select list binds to the fan-out's `emits_ident` and its direction/NULL placement to the one shared `render_ordered` seam, so broadcast ordering cannot drift from any other ordered path. |
| Reuse `build_row_scan_sql`'s existing limit append for the merge | broadcast bare-`LIMIT` path | Byte-identical to `render_limit_offset(Some(n), 0)`; adds no second place that renders a final `LIMIT`. |
| Decline (fall through), never hard-error, for shapes the broadcast wrapper cannot bind | `classify_join_window` and `build_broadcast_join_sql`'s `None` return | Unlike the declined row-scan path, a renderer that CAN express the shape still exists — the qualified fallback wrapper. Both decision sites reach the fallback the same way, so there is one decline outcome even though there are two places it can be reached. |

### Consequences

| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| Carry the per-shard cap in a new `JoinSpec.post_join_limit` field, and keep `CommonScanSpec.limit` out of the join path entirely | Reuse `common.limit` and write it at the broadcast construction site; add a `limit` parameter to `join_fan_out_scan_spec`; a paired `ScanSpec::with_broadcast_join(self, join, post_join_limit)` constructor; `ScanSpec::with_post_join_limit(self, n)` guarded by `debug_assert!(join.is_some())`; narrow `CommonScanSpec.limit` and `.join` to `pub(crate)`; a DataFusion `.limit()` call on the join `DataFrame` | The clause placement and the optimizer guarantee are already right; only the field's HOME is wrong, and it is wrong in a way that makes the fallback delta's structural claim unbuildable on `common.limit`. A field write and a helper parameter are conventions a future leg caller can get wrong. A paired constructor binds only callers that use it, and becomes a shallow two-line setter once the field has a type-level home. A `debug_assert!` holds only in debug builds. `pub(crate)` restricts nothing that matters — `build_side_fan_out_sql` is in-crate, and the single-table, TopN, and raw-scan paths legitimately write `limit` on join-less specs from the same module tree — so the hole relocates rather than closes, at a cost of 29 out-of-crate test migrations. A field of `JoinSpec` closes it by type, for one additive defaulted wire field and nine struct-literal updates. |
| Render the cap from the join block at the existing SQL site, rather than in DataFusion | Call `.limit()` on the joined `DataFrame` in the UDF | `build_join_sql` already binds the join block (`join_scan.rs:146`) before it renders the limit (`:205`), so the read-site change is one line and keeps the cap where the SQL, the optimizer proof (decision [2]), and the existing scenario already put it. |
| Ordered broadcast accepts only bare-column keys present in the projection | Extend the broadcast projection with hidden sort-key columns, as the declined row-scan path does | Zero regression either way (all these shapes fell back before), and the hidden-column machinery would need per-side Exasol type resolution and a projection widening that `render_broadcast_join` currently declines outright (#196). |
| An ordering with no `LIMIT` is served too, not only ORDER BY+LIMIT | Gate the ordered arm on `limit.is_some()` | Excluding it costs an extra guard and creates an asymmetry with no correctness basis: `render_limit_offset(None, 0)` is the empty string, and the shape is strictly better served by one broadcast fan-out than by the fallback's two scans plus an Exasol join. Reaches one shape past Q4's literal wording; confirmed by the user in decision-log A7a. |
| `OFFSET` served on the ordered wrapper, declined on the bare-`LIMIT` path | Serve offset on both; decline offset everywhere | The ordered wrapper sits over the complete merged join, so a window there is exact and uses the seam the interview named. Per-shard offset does not compose, and bare-`LIMIT`-with-offset is unreachable anyway (offset-implies-ordering invariant). |

## Impact

A join query that carries a row limit or a bare-column ordering now runs the broadcast plan instead of the two-scan fallback. Results are unchanged; plans are not. Concretely:

- **Faster.** A bare-`LIMIT` join stops scanning both tables twice and stops materializing the full join in Exasol; each shard now truncates its own joined output at `n`.
- **Plan-shape change visible in `EXPLAIN VIRTUAL`.** Any tooling or test asserting the `LHS_T0`/`LHS_T1` two-scan wrapper for a LIMIT-carrying or ORDER-BY-carrying join will now see the broadcast fan-out instead.
- **Three pre-#307 E2E-harness assertions go stale.** The `capped_result_sets` doc comment (`exasol_ws.rs:144-158`) and the `e2e_join_test.rs:107-116` comment both state that a pushed limit disqualifies broadcast; the `e2e_broadcast_declined_by_explicit_limit_falls_back_to_n_scan` regression test (`e2e_join_test.rs`, added by #314) pins that exact fallback. This plan reverses the behavior all three describe. It rewrites the two comments and deletes the test (§ Dead Code Removal), which `e2e_broadcast_join_bare_limit_stays_broadcast_and_truncates` replaces. (The `ExaConn::unbounded_result_sets()` workaround this bullet previously named was already removed by #314; the harness default is now uncapped.)
- **One additive, backward-compatible wire-format field.** `JoinSpec` gains `post_join_limit`, serialized only when set. A spec written before this change deserializes unchanged, and an unordered broadcast query's emitted SQL stays byte-identical. The VS and the scan UDF ship in the same `.so`, so version skew between them is not a supported configuration; were one to occur, the older side would ignore the unknown field — no type in this workspace sets `deny_unknown_fields` — and lose only the per-shard cap, because the outer merge `LIMIT n` still truncates. Degraded work saved, never a wrong result.
- **No other breaking change.** No capability change, no configuration change, no change to how the scan executes the join. A client that sets a row-limit attribute (`resultSetMaxRows`) no longer silently loses broadcast pushdown for every join in the session.

## Dependencies

None new. Relies on already-pinned DataFusion 54.1 optimizer behavior (`push_down_limit`), verified against the vendored source during planning.
