## Premortem

Three failure stories drove this review.

1. **The recorded library contradicts itself and the bug comes back.** `/speq:record` is a mechanical marker-driven merge. Two recorded statements this plan invalidates are not marked `DELTA:CHANGED`, so after recording `specs/vs-adapter/pushdown-planning-join/spec.md` says both "no `SELECT * FROM (...)` wrapper" and "wrap the broadcast fan-out in ONE outer `SELECT … FROM (…) ORDER BY …`". A later planner reads the older clause, re-adds the guard, and #307 returns. → `[REQUIREMENT_CONFLICT]` (B1).
2. **A broadcast join silently returns unordered rows.** The ordered arm reuses `wrap_declined_order_by`, whose documented precondition — every key renders, guaranteed upstream by `ensure_every_sort_key_renders` — is deliberately NOT reproduced on this path (decision [6]). If the classifier's gate and the wrapper's render predicate ever disagree, the wrapper returns `sql` unchanged: no `ORDER BY`, no error, and `ORDER_BY_COLUMN` is advertised so Exasol does not re-sort. → `[UNSTATED_ASSUMPTION]` (B3).
3. **A fallback leg acquires a pre-join limit.** The plan's mitigation is construction-site scoping; the fallback spec delta promises a *structural* guarantee the design explicitly declines to build. A future contributor writing `spec.common.limit = Some(n)` in `build_side_fan_out_sql` violates no type, no signature, and no compiler check — only a test that asserts today's callers. → `[REQUIREMENT_CONFLICT]` (B2).

Verification performed against the real tree: `join_requires_exasol_postprocessing` (planning.rs:424), `join_fan_out_scan_spec` (sql_builders.rs:555, `limit: None`), `build_broadcast_join_sql` (sql_builders.rs:665), `build_join_sql` (join_scan.rs:125, `LIMIT` after `INNER JOIN` and `WHERE`), `build_row_scan_sql` (support.rs:141, trailing ` LIMIT n`), `wrap_declined_order_by` (topn.rs:404), `push_down_join` (`datafusion-optimizer-54.1.0/src/push_down_limit.rs:241`, `(None, None)` for non-cross `Inner`), `scan/mod.rs:284` (`MayStopEarly` for any join spec), `register_join_tables` (join_scan.rs:63, positional deletes applied per side at registration). Cargo.lock pins `datafusion 54.1.0` / `arrow 58.3.0`. `speq plan validate` passes.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md § Implementation Tasks task 3; decision-log.md § [6]; `crates/lakehouse-engine/src/adapter/pushdown/topn.rs:404-472`
- Issue: task 3 reuses `topn::wrap_declined_order_by` from a caller that does not run `ensure_every_sort_key_renders`. That function's doc states its own safety precondition: "NO key renders an ordering → `sql` is returned UNCHANGED… Reachable ONLY for an absent or empty `orderBy`… a NON-EMPTY `orderBy` carrying an [`ParsedSortKey::Unrenderable`] element never reaches here at all, because [`ensure_every_sort_key_renders`] declines it upstream (#198)." Decision [6] deliberately removes that upstream decline for the broadcast path. The new guarantor is the classifier's bare-projected-column gate, which lives in a different module from the predicate it must agree with (`ParsedSortKey::render_order_by_element`). On disagreement the wrapper returns the bare fan-out: rows with no `ORDER BY`, no error, and `ORDER_BY_COLUMN` advertised — so per this repo's delegation rule Exasol applies no backstop sort and the query returns silently misordered rows. Neither the plan, the spec delta, nor task 7's doc-comment list addresses this; task 7 names `join_fan_out_scan_spec`, `build_join_sql`, and `build_broadcast_join_sql` but not `wrap_declined_order_by`, whose doc is now factually wrong about its caller set.
- Fix: In plan.md § Implementation Tasks task 3, require the ordered broadcast path to assert the wrapper actually rendered an `ORDER BY` — construct only `ParsedSortKey::Column` values and fail loudly (a `debug_assert!` plus an `Ordered`-arm invariant test) if `wrap_declined_order_by` returns its input unchanged. Add `wrap_declined_order_by`'s doc comment to task 7's list, restating the precondition as "every caller MUST guarantee at least one key renders; the row-scan caller does so via `ensure_every_sort_key_renders`, the broadcast caller via `classify_join_window`'s bare-projected-column gate". Add a matching clause to the ordered scenario in `vs-adapter/pushdown-planning-join/spec.md`: the adapter MUST NOT emit a broadcast ordered plan whose outer wrapper renders no `ORDER BY`.

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: plan.md § Implementation Tasks task 1; `vs-adapter/pushdown-planning-join/spec.md` § Scenario "Ordering and window shapes the broadcast wrapper cannot serve decline to the unified fallback"
- Issue: task 1 hands the implementer an unresolved architectural fork: "the broadcast projection is only known after `render_broadcast_join`, so the ordered arm's projection-membership check has to run against the rendered projection rather than the raw request — decide whether to classify in two stages or to pass the rendered projection into the classifier, and keep the decision in ONE function either way." The two options are not interchangeable. Two-stage classification puts the decision in two places, which is exactly the information leakage decision [3]'s rationale sets out to prevent, and cannot satisfy "keep the decision in ONE function". Passing the rendered projection in forces `render_broadcast_join` to run *before* the four postprocessing arms are evaluated, reversing `plan_join`'s current short-circuit at `joins/mod.rs:188` — an aggregate-over-join request would then pay a full condition/filter/projection render it currently skips, and `render_broadcast_join`'s `Err` arm (`project_columns`, support.rs:1156, "pushdown request has no column metadata") would newly fire for shapes that today reach `build_n_scan_join_sql` instead. The spec scenario says only "WHEN the adapter classifies the request's window", so no pass/fail test can be written for the ordering.
- Fix: In plan.md § Implementation Tasks task 1, pick one order and state it: classify the window from `pushdown_req` alone into `Unbounded` / `BareLimit` / `Ordered { keys }` / `ExasolPostProcessed` BEFORE `select_broadcast_sides` and `render_broadcast_join` (preserving today's short-circuit and today's `Err` reachability), then have `build_broadcast_join_sql` — not the classifier — downgrade `Ordered` to the fallback when any key is absent from `rendered.projection`. Add the projection-membership downgrade as an explicit clause in `vs-adapter/pushdown-planning-join/spec.md`'s decline scenario naming *when* it is evaluated, and add a unit test asserting an aggregate-carrying two-table equi-join never reaches `render_broadcast_join`.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Consequences (row 3 rationale) and § Impact ("**Faster.**"); decision-log.md § [7] Rationale
- Issue: "one broadcast fan-out strictly beats the fallback's two independent scans plus an Exasol-core-engine join" is asserted, not shown, and is false in at least two regimes. (a) A non-unique dimension key makes the join output larger than the fact side, so the broadcast path pushes MORE rows across the `MT_EMIT` boundary than the fallback's `|fact| + |dim|` — and synchronous `MT_EMIT` round-trips are a named bottleneck in this repo's CLAUDE.md. (b) For a small `n` against a dimension near the 128 MB default threshold, every one of up to G = 300 shard invocations rebuilds the full dimension hash table before emitting a row, while the fallback scans it once; `resultSetMaxRows` makes this the default path for every join in a capped session. Neither regime is named.
- Fix: In plan.md § Consequences row 3 and § Impact, replace "strictly beats" / unqualified "**Faster.**" with the bounded claim and name the two regimes where it may not hold (dimension-side fan-out inflating emit volume; small `n` against a near-threshold dimension replicated across G shards).

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `vs-adapter/pushdown-planning-join-fallback/spec.md` § Scenario "A fallback leg's fan-out scan spec never carries a row limit", clause 2; decision-log.md § [4]
- Issue: the delta states "the shared fan-out spec helper the broadcast builder and the fallback leg builder both use SHALL make that structural — **the row limit SHALL be attachable only where a join block is also present**, so no future leg caller can acquire one by forgetting to pass it". Decision [4] explicitly declines to build that: `join_fan_out_scan_spec` keeps its signature and its unconditional `limit: None`, and `build_broadcast_join_sql` mutates the returned spec's public `CommonScanSpec.limit` field. Nothing then makes the limit "attachable only where a join block is present" — `spec.common.limit = Some(n)` is a plain field write available at every call site, including `build_side_fan_out_sql` (sql_builders.rs:599). The requirement is also not testable as written: task 2's pinning test asserts that *today's* fallback leg spec carries `limit: None`, which is a behavioral fact about current callers, not the structural property the SHALL demands.
- Fix: Either (a) rewrite the clause in `vs-adapter/pushdown-planning-join-fallback/spec.md` to state what the design delivers — "the row limit SHALL be set only at the broadcast construction site, and every fallback leg spec SHALL carry `limit` = absent, pinned by a test over every fallback shape" — and delete "SHALL make that structural"; or (b) keep the clause and change decision [4] to deliver it with a checked constructor (e.g. `ScanSpec::with_post_join_limit(self, n)` that asserts `self.common.join.is_some()`), which needs no wire-format or UDF change. State which in decision-log.md § [4].

#### [COMPLETENESS_GAP] BLOCKER

- Issue: two arms the user confirmed as in scope have no named test anywhere. (a) **Bare `ORDER BY` with no `LIMIT`** (decision [7], A7a) — the spec scenario admits "an optional `limit`", but the Scenario Coverage table, task 4's classification enumeration, and task 6's E2E list all name only `ORDER BY … LIMIT`. ## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: decision-log.md § [4]; plan.md § Design § Context and § Patterns row 2
- Issue: the plan correctly identifies that "the real design problem left is … **ownership**", then resolves it with convention rather than a boundary. After the change, the meaning of `CommonScanSpec.limit` — post-join cap on a join spec, pre-join input cap on a leg spec — is a single decision reflected in four planned places: `join_fan_out_scan_spec`'s doc comment, `build_broadcast_join_sql`'s field mutation, `build_join_sql`'s doc comment, and a pinning test. No module owns it. Per `/speq:design-philosophy` this is back-door leakage: two builders independently assume what one field means, with nothing enforcing agreement. Decision [4] rejects the two alternatives it considered on wire-format grounds, but never considers the cheap in-crate option that costs neither: a checked constructor on `ScanSpec` that refuses a limit without a join block. This is the design side of the finding recorded above as `[REQUIREMENT_CONFLICT]` on the fallback delta's structural clause.
- Fix: Add the checked-constructor option to decision-log.md § [4]'s Alternatives with an explicit accept/reject, and if rejected, name in plan.md § Design § Patterns row 2 the single artifact that owns the pre-join/post-join distinction after the change.
