## Premortem

Two failure stories drove this round.

1. **The bug returns through the fallback spec instead of the join spec.** `/speq:record` appends a `DELTA:NEW` Background bullet; it does not delete the bullet that bullet argues against. Recorded `specs/vs-adapter/pushdown-planning-join-fallback/spec.md:49-52` — "**Every LIMIT-carrying join reaches this wrapper, never broadcast.** … So every offset-bearing join shape lands here by construction; the broadcast renderer emits no `LIMIT` or `ORDER BY` at all and needs no offset handling" — survives recording verbatim next to a new bullet saying it is withdrawn. Round 1 blocked this exact shape on the join spec; the fallback spec was never named, so it was never fixed. → R2-B1.
2. **A future contributor puts a pre-join limit on a fallback leg and the recorded spec says that is impossible.** The delta will record "a leg builder … has no way to reach a limit, and the pairing is enforced by the signature". `CommonScanSpec.limit` is `pub`. The reviewer of that future change reads the spec, believes the invariant is type-enforced, and does not look for the field write that returns wrong rows with no error. → R2-B2.

#### [COMPLETENESS_GAP] ADVISORY (A1)
- Location: plan.md § Implementation Tasks task 2 (last test) and § Verification § Scenario Coverage row "…(wrapper must render an `ORDER BY`)"; `vs-adapter/pushdown-planning-join/spec.md:68`
- Issue: the spec clause's normative behavior is a *decline* — "a wrapper that returned the fan-out unchanged SHALL instead decline to the unified unaccelerated fallback" — but the only test mapped to it, `broadcast_ordered_plan_rendering_no_order_by_is_a_programming_error`, is `#[should_panic]` and therefore asserts the debug-build panic, i.e. the branch where the decline never executes.
