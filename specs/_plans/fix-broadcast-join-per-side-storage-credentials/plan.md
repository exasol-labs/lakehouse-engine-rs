# Plan: fix-broadcast-join-per-side-storage-credentials

## Summary

Carry each broadcast-join side's own storage credential into the scan spec and read each side through it, by registering one prefix-routing object store per bucket that holds one inner store per side. Closes issue #294, which made a pushed-down join read the dimension table through the fact table's credential.

A second, independent defect discovered while reproducing #294 is folded into this same plan: `render_broadcast_join` preserves Exasol's native table alias when rendering a join's condition, filter, and projection, but the scan's derived sub-SELECTs are unaliased, so any aliased join query (`FROM t1 o JOIN t2 c ON ...` — the common case) fails at scan time before it ever reaches the credential path this plan fixes. Closes issue `#303` (filed by this plan; see task 1.5).

## Design

### Context

`join_fan_out_scan_spec` (`crates/lakehouse-engine/src/adapter/pushdown/joins/sql_builders.rs:556`) sets `CommonScanSpec.storage` from the FACT side and `JoinSpec` (`crates/lakehouse-engine/src/scan/spec.rs:454`) carries no storage at all. `resolve_one_join_side` already resolved a per-side `effective_storage` — `resolve_vended_storage` runs once per side, anchored on that side's own table location — and the fan-out builder throws the dimension side's away. The scan then compounds it: `build_session_context` (`scan/object_store.rs:35`) builds ONE `StoreRegistration` from `spec.common.storage` and hands it to both sides, and `register_join_tables` (`scan/join_scan.rs:68`) passes `&spec.common.storage` to both `register_file_list` calls.

Databricks vends a credential scoped to the table it loaded. The fact side's credential is therefore DENIED on the dimension side's prefix, so the join fails to read. Two smaller defects ride along: the dimension side's `PositionalDeleteScanTable` holds the FACT side's `secret_values()`, so a dimension-side read error is redacted against the wrong secret set; and the spec-sized store's size index is deliberately whole-spec precisely because one store had to answer both sides' `head` calls.

The constraint that shapes every option is DataFusion's. Its object-store registry keys on `scheme://host[:port]` only:

```
get_url_key  (datafusion-execution-54.1.0/src/object_store.rs:266-274)
    format!("{}://{}", url.scheme(), &url[Position::BeforeHost..Position::AfterPort])
ObjectStoreUrl::parse  (:58-72)
    rejects any URL whose BeforePath remainder is neither empty nor "/"
FileScanConfig::open_with_args  (datafusion-datasource-54.1.0/src/file_scan_config/mod.rs:640)
    context.runtime_env().object_store(&self.object_store_url)   // path-less by type
```

One bucket therefore gets exactly one registered store, and no registry-level change can attach two credentials to it. Databricks makes one shared metastore bucket the normal case for two tables of one catalog, so refusing credential-divergent joins or falling back to the N-scan renderer would forfeit broadcast exactly where it is wanted.

- **Goals** — each side reads through the credential resolved for its own table location; one code path for every join, with no credential comparison; the shared-bucket case (the Databricks norm) stays broadcast; an unroutable path is a named error, never a guessed credential; each side's read errors are redacted against that side's own secrets.
- **Non-Goals:**
  - A custom DataFusion `ObjectStoreRegistry`.
  - Joins whose sides span two ADLS containers of one storage account (still refused, see below).
  - Joins whose sides resolve to different backend variants (still refused).
  - A side whose OWN files span more than one bucket (a pre-existing loud refusal, tracked separately).
  - More than two sides — the broadcast contract is exactly two involved tables.
  - Any change to the N-scan fallback renderer, which already gives each leg its own spec and therefore its own storage.
  - **A live Databricks two-table vended broadcast-join E2E** — deferred, not forgotten: Databricks-managed Iceberg is the motivating system for this fix, but no Databricks catalog is reachable from CI, so the Lakekeeper `sts-enabled` warehouse stands in for it under the same per-table vending contract (see decision-log `[13]`).
  - **`join_requires_exasol_postprocessing`'s LIMIT-forces-fallback policy itself** — the test harness's `resultSetMaxRows` attribute turning into a pushdown-request `limit` (discovered during task 1.4's investigation) is worked around in the TEST HARNESS only (task 1.8), never redesigned in production pushdown planning. Whether a real client driver's own default fetch-size attribute similarly suppresses broadcast eligibility in practice is a separate, unstudied question this plan does not resolve.

### Iceberg table-spec compliance

This change decides which credential reads which file path, so it turns on whether a table's files are guaranteed to live under its `location`. They are **not**. Quoted from the Apache Iceberg table specification (`https://iceberg.apache.org/spec/`), fetched during planning:

| Section | Verbatim | Consequence |
|---|---|---|
| Table Metadata Fields | "The table's base location. This is used by writers to determine where to store data files, manifest files, and table metadata files." | `location` is a WRITER target, not a reader containment guarantee. |
| Data File Fields, field 100 | "Full URI for the file with FS scheme" | `file_path` is a self-contained URI with no clause tying it to `location`. |
| Appendix F, Path Construction — **NON-NORMATIVE** | "If `write.data.path` is an absolute path, it is used directly as the base for new data files." … "Otherwise, the absolute path should be stored." | CORROBORATION only, not normative support. Appendix F is titled *Implementation Notes* and opens "This section covers topics not required by the specification but recommendations for systems implementing the Iceberg specification"; Path Construction adds "the specific construction logic is not strictly required by the spec". |
| Appendix E, Version 4 — **the normative support** | "Absolute paths must be used for files that do not share a common prefix with the table location" | v4 legislates FOR out-of-tree files rather than forbidding them. This row alone carries the out-of-tree-files conclusion, so the design does not rest on the non-normative Appendix F row above. |
| Deletion Vectors | "There are no restrictions on the data files that can be referenced by deletion vectors in the same Puffin file." | **Not applicable to this design.** The scan never reads a Puffin file: `ensure_positional_delete` errors on `PuffinDeletionVector` and `EqualityDeletes` before any I/O (`scan/positional_deletes.rs:232-247`, called at `:595`), and the adapter refuses both at plan time (`adapter/pushdown/file_resolution.rs:380-403`). Retained to record that the section was reviewed, not as design support. |
| REST catalog `StorageCredential` | "Indicates a storage location prefix where the credential is relevant. Clients should choose the most specific prefix (by selecting the longest prefix) if several credentials of the same type are available." | Per-prefix credentials are the protocol's own model, and `storage-credentials` is an ARRAY for exactly this reason. |

Two design consequences follow, and neither is left silent:

1. **Routing must not be table-root-only.** A router that matched only `location` prefixes would misroute a spec-legal table. The design therefore routes on each side's OWN enumerated file paths first — data files and their positional-delete files — and falls back to the table root only for a path the spec does not name. Because the scan discovers no files (`datafusion-scan/scan-execution-join`: "MUST NOT resolve or discover any file beyond the two file lists carried in the spec"), the access set is bounded and was VERIFIED against the tree rather than recalled:

   | Access | Evidence | Routed by |
   |---|---|---|
   | **Zero** `head` per data file (production path, `logical_schema` non-empty) | CODE INSPECTION ONLY. Every `PartitionedFile` is built from an `ObjectMeta` synthesized from the spec-carried size — `scan/positional_deletes.rs:663-665` via `object_meta_for` (`:215-225`), whose doc records "built without any object-store HEAD (the size is supplied by the caller)" — and the one `infer_schema` call site in `crates/…/src` (`scan/raw_scan.rs:214`) is skipped on this path. **No test currently guards this zero-head property**: every test in `tests/scan_no_head_test.rs` runs row 2's branch instead (see that row), so the property is asserted by inspection, not by a regression test | n/a — no store call is made |
   | **Exactly one** `head`, FIRST file only, when `logical_schema` is empty | Guarded by `!logical_schema.is_empty()` (`scan/raw_scan.rs:204-205`); the `else` branch (`:207-217`) calls `infer_schema` (`:214`), reaching `store.head` at `datafusion-datasource-54.1.0/src/url.rs:276`. This is the branch ALL THREE `tests/scan_no_head_test.rs` tests exercise — `scan_uses_spec_size_and_issues_no_head` (`:504`), `scan_issues_no_head_for_delete_files` (`:631`), `scan_reads_footer_via_range_get_once` (`:690`) — because the suite's only spec builder, `raw_spec` (`:261-272`), closes with `..Default::default()` and `logical_schema` defaults empty. What the first two prove is that this `head` is answered from the side's own size index instead of reaching the network: `SpecSizedObjectStore::get_opts` short-circuits an `options.head` request for an indexed path with zero I/O (`scan/object_store.rs:350-366`), and the FIRST file is always in its own side's index. That is why the `NotFound` trigger of the `list(Some(prefix))` fallback below cannot fire for a spec-indexed file | Rule 1 — that file's own exact enumerated path |
   | Range reads of each data file's footer, page index, bloom filters | For a DELETE-CARRYING data file the footer is fetched at `scan/positional_deletes.rs:670`, inside the `if let Some(deletes) = … && !deletes.is_empty()` guard (`:667-669`) — so that site fires only for files with deletes; every other data file's footer is read by the Parquet reader during execution. Footer-once verified by `scan_no_head_test.rs::scan_reads_footer_via_range_get_once` | Rule 1 |
   | Range reads of each positional-delete file | Size supplied by the spec, so no `head` | Rule 1 |
   | `list(Some(prefix))` — schema-inference branch ONLY | Two triggers: the single `head` returns `NotFound` (`url.rs:282-291`), or the entry path ends with `/` so `is_collection()` skips the `head` (`url.rs:204-206`, `:266-274`). Both reach `store.list(Some(&full_prefix))` (`url.rs:397-398`) | Rule 1 when the prefix is the first file's own path (the `NotFound` trigger); Rule 2 when it is a directory (the `is_collection()` trigger) |

   **Rule 1 alone covers every access the scan issues on a well-formed spec**, so "fail on an unroutable path" cannot fire on a spec-legal table read through this scan. The earlier draft of this section claimed "one sized `head` per data file"; that was wrong in both directions and is corrected above.

   **Rule 2 is retained as the interviewed prescription's fallback, and is honestly labelled as such rather than as a reachable access.** For a well-formed spec it is unreachable: the one syntactic route to it is a spec `files` entry whose path ends in `/`, which makes `is_collection()` list a directory — and such an entry is itself a malformed spec. Rule 2 is kept because the interview prescribed longest-root-prefix matching and because it converts that one malformed-spec shape into a served read rather than a hard error; it is NOT evidence of completeness. Recorded in decision-log `[2]`.

2. **A pre-existing, accurately-scoped deviation is NAMED, not introduced or fixed here.** `validate_uniform_object_store_files` (`scan/object_store.rs:487`) refuses a side whose data or delete files resolve to a different scheme+host than that side's first file. The v4 absolute-path rule above permits exactly that, so this is a genuine deviation from the table spec — a LOUD refusal, never a wrong-credential read or a wrong row. It predates this plan on both the single-table and the join path and is unchanged by it. Task 6.1 files it as a tracked GitHub issue and cites that number inline in the `datafusion-scan/scan-execution-join` delta, following the `(#83)` citation pattern in `specs/datafusion-scan/scan-execution-field-id-projection/spec.md`.

### Decision

Two changes: carry the dimension side's storage in the wire format, and route by path inside one registered store per bucket.

#### Architecture

```
PLANNING (VS)                             SCAN (UDF)
─────────────                             ──────────
resolve_one_join_side  (per side)         from_parts_json
  └─ resolve_vended_storage(anchor)         └─ ScanSpec
       │                                        ├─ common.storage      ← FACT side
       ▼                                        └─ common.join.storage ← DIMENSION side (REQUIRED)
build_broadcast_join_sql                                    │
  ├─ common.storage      = fact.effective_storage           ▼
  └─ join.storage        = dimension.effective_storage   build_session_context
                                                           │
                          group the two ScanSides by side_store_url
                                                           │
                    ┌──────────────────────────────────────┴──────────────────────────┐
                    │ ONE bucket (Databricks norm)          TWO buckets                │
                    ▼                                       ▼                          │
        register(url, PrefixRoutingObjectStore)   register(url_f, Router[fact])         │
                    │                             register(url_d, Router[dim])          │
       ┌────────────┴────────────┐                                                      │
       ▼                         ▼                                                      │
 SpecSized(S3(fact cred),  SpecSized(S3(dim cred),                                      │
           sizes_fact)               sizes_dim)                                          │
                                                                                        │
  route(path):  1. exact match in a side's own file-path set (fact first on a tie)      │
                2. else longest table-root prefix match                                 │
                3. else Err — names the path and every root tried                      │
```

`register_join_tables` additionally passes `join.storage` to the dimension side's `register_file_list`, so that side's `PositionalDeleteScanTable` carries the DIMENSION side's `secret_values()`.

#### Patterns

| Pattern | Where | Why |
|---|---|---|
| Decorator over `ObjectStore` | `PrefixRoutingObjectStore` in the new `scan/store_router.rs` | The only layer that sees the requested `Path` is the store itself; the registry never does. `object_store` 0.13.2's own `PrefixStore` (`prefix.rs:30-192`) is the in-crate precedent for a path-rewriting decorator that implements every trait method under `#[deny(clippy::missing_trait_methods)]` |
| Router OUTSIDE, spec-sized `head` INSIDE | `Router[SpecSized(inner)…]` | Every operation is routed before the sized-`head` shortcut can answer it, so an unroutable path fails as the plan defect it is rather than as a later credential-shaped denial |
| Exact-membership first, prefix second | `route()` | The spec enumerates every path the scan will request, so exact membership is complete for a well-formed spec and Iceberg-spec-safe. The prefix fallback is UNREACHABLE through the current scan on a well-formed spec — it is retained as the interviewed prescription, and the one shape it covers is a malformed `files` entry ending in `/` that makes `is_collection()` list a directory. See § Iceberg table-spec compliance ¶1 |
| Required field, no serde default | `JoinSpec::storage` | "Every join block names its own dimension backend" becomes a property of the type instead of a rule to audit at each of the 7 `JoinSpec` construction sites. A `#[serde(default)]` would let a storage-less join block deserialize into one that silently reuses the fact backend — the exact collapse being removed |
| Per-side value object | `ScanSide { files, table_root, backend, label }` | After the fix there is no whole-spec registration value except the connection budget, so `StoreRegistration`'s "whole-spec values shared by every side" premise is gone and the struct collapses into the per-side one |
| Construct, don't register | `build_side_store` replaces `register_side_store` | Grouping sides by store URL in the caller makes the old "already registered? return `None`" branch unreachable; the backend dispatch keeps only the decision that is genuinely backend-specific |

### Consequences

| Decision | Alternatives Considered | Rationale |
|---|---|---|
| Prefix-routing decorator per bucket | Custom DataFusion `ObjectStoreRegistry` keyed with userinfo — `object_store` 0.13.2 even ships one (`registry.rs:220-223` keys from position 0, retaining userinfo, over a path-segment prefix tree) that DataFusion 54.1.0 does not use (zero references in any `datafusion-*-54.1.0/src` tree) | The registry never receives a path, so it cannot separate two S3 tables in one bucket — the case that matters. A userinfo-keyed registry would additionally subsume the ADLS-container guard, but that is a strictly larger change against a pluggable DataFusion seam, for a case both existing guards already refuse loudly |
| Route on exact file paths, then table root | Table-root longest-prefix only, as originally prescribed | The Iceberg spec explicitly permits files outside `location` (see § Iceberg table-spec compliance), so root-only routing would misroute a spec-legal table. The prescribed prefix match is kept as the fallback |
| Error on an unroutable path | Fall back to the fact side's store | Silently using a credential that may not be scoped for a path is the class of defect this plan removes. The scan enumerates every path it requests, so the error is reachable only from a defective spec |
| Router on EVERY join, even with identical credentials | Route only when the two backends differ | A comparison is a branch that can be wrong, and it would leave the common Databricks case on a path no test exercises. One code path, always |
| Router even when the two sides are in different buckets | Register each side's sized store directly when buckets differ | Uniformity: a one-entry router enforces the same "this credential serves only these paths" property, and `validate_uniform_object_store_files` already bounds a side's files to one bucket, so the risk surface is identical either way |
| Per-side size index | Keep the whole-spec index | The index was whole-spec only because one store had to answer both sides' `head` calls — the premise this change removes. Per-side restores the property that one side's store cannot answer the other side's metadata lookup |
| `JoinSpec::storage` REQUIRED | `Option<StorageBackend>` with `#[serde(default)]`, matching neighbouring fields | The neighbouring `skip_serializing_if` fields are all optional in MEANING. This one is not: absent must be impossible, and `scan-execution-spec-reconstitution` already records that "the same `.so` produces and consumes the spec within one deploy (there is no cross-version wire-compatibility requirement)", so a required field costs nothing |
| Connection budget applies per inner store (2N warm sockets on a join) | Divide the budget across sides (`N / side_count`) | Dividing would silently halve fact-side fetch parallelism on every join, making a tuning knob's effective value depend on query shape. What doubles is `pool_max_idle_per_host` — warm idle sockets, not a request-rate ceiling — and a different-bucket join already held 2N before this change |
| Keep `validate_sides_share_one_store` | Delete it as subsumed by prefix routing | Not subsumed. An Azure store built from a container-qualified URL is container-scoped and the `Path` its trait methods receive is container-RELATIVE, so two tables in two containers of one account can produce IDENTICAL paths that no path routing can separate — and DataFusion's key drops the userinfo carrying the container (its own test: `s3://username:password@host:123` → `s3://host:123`, `object_store.rs:330-332`) |
| Keep `validate_sides_share_one_backend` at variant + ADLS account | Widen to full backend equality; or delete it | A variant difference is unserveable (an `AmazonS3Builder` cannot address an `abfss://` URI) and an ADLS account difference is unserveable per the row above. A credential difference is now SERVED, so widening would reject exactly what this plan fixes |

### Alias-qualification fix (secondary defect, folded into this plan)

#### Context

Investigating task 1.4's escalation (decision-log "Task 1.4 follow-up investigation") traced a SECOND, independent, pre-existing defect. `render_broadcast_join` (`adapter/pushdown/joins/sql_builders.rs:72`) renders the join condition, the WHERE filter, and any select-list scalar expression via `vs_expression::render_expression_safe` / `project_columns`, both of which qualify a column reference as `"ALIAS"."NAME"` whenever the incoming JSON column node carries a non-empty `tableAlias` — exactly what Exasol sends for any query that aliases a joined table (`FROM fact_orders o JOIN dim_customer c ON ...`, the common case, and every query in `e2e_join_test.rs`). `build_join_sql` (`scan/join_scan.rs:115`) wraps each registered table in an UNALIASED derived sub-SELECT (`SELECT {cols} FROM {registered_table_name}`, no `AS alias`), so an alias-qualified condition or filter fails at scan time with a DataFusion schema error (`No field named "O"."O_CUSTKEY"`). This blocks EVERY aliased broadcast-eligible join query from completing the broadcast path at all, independent of and compounding issue #294's credential defect — and the two compounded is why task 1.4's original reproduction unexpectedly passed (see decision-log).

Two things already in the tree point at the fix. First, the single-table chokepoint (`adapter/pushdown/mod.rs:183-187`) already strips `tableAlias` from the whole pushdown request for exactly this class of problem — but only AFTER the join-detection gate returns, so a join request never reaches that strip; its own comment records this ordering as deliberate ("after the join gate, which returned above on the original, alias-carrying request"). Second, the unified N-scan fallback's per-side scan renderer, `build_side_fan_out_sql`, already strips `tableAlias` before rendering its side-local filter (`sql_builders.rs:627-632`), with the comment: "the fan-out is a single-table scan whose relation exposes bare uppercase column names, so an alias-qualified reference would not resolve — exactly the single-table scan path's contract." `build_join_sql`'s derived sub-SELECTs have the IDENTICAL shape (bare uppercase names, no outer alias), so the same fix applies for the same reason. (The N-scan fallback's OWN join-condition renderer, `build_n_scan_join_sql` → `annotate_columns_with_alias`, is unaffected either way: it OVERWRITES every column's `tableAlias` with its own generated `LHS_T{i}` alias keyed by `tableName`, so it never depended on — or was broken by — whatever native alias Exasol sent.)

#### Decision

`render_broadcast_join` strips Exasol's native `tableAlias` from the join condition JSON, the WHERE filter JSON, and the whole `pushdown_req` it passes to `extract_join_projection` — using the EXISTING `strip_table_alias` helper (`adapter/pushdown/support.rs`, already imported in `sql_builders.rs`) — immediately after the disjoint-schema guard passes and before any render call. `build_join_sql` needs NO change: it already produces bare, unaliased derived relations, so bare rendering is what makes the two sides resolve.

| Decision | Alternatives Considered | Rationale |
|---|---|---|
| Strip `tableAlias` inside `render_broadcast_join`, render everything bare (CHOSEN) | **Thread each side's native alias through the wire** (new `JoinSpec` fields for each side's alias; `build_join_sql` aliases its derived sub-SELECTs to match) | Correct in principle but needs a home for the FACT side's alias too (`JoinSpec` only describes the dimension side, coupling into the credential fix's OWN wire-format work in tasks 2.x), asymmetric-alias handling (one side aliased, one not — legal SQL), and live-Exasol verification of whether Exasol ever omits `tableAlias` or sends it equal to the table name. All solvable, but for a problem the disjoint-column guard already lets bare rendering discharge for free |
| (same) | **Recover the alias by parsing it out of the already-rendered condition string inside `build_join_sql`, at scan time** | String-surgery on an opaque, already-rendered SQL fragment to recover structured information the JSON form already carried cleanly is fragile (quoting, multi-column conditions, two DIFFERENT aliases in one condition), and still cannot tell WHICH alias belongs to WHICH side without wire metadata — converging back to the wire-threading alternative's coupling problem while being harder to get right |
| (same) | Leave `render_broadcast_join` as-is; declare an aliased join ineligible for broadcast (extend the existing decline path) | Would silently forfeit broadcast for the common case (every aliased query) rather than fix the actual defect, and contradicts this plan's own Impact claim that a broadcast join "starts working" |

Safe because `disjoint_schema_guard` (`sql_builders.rs:79-81`) already guarantees the two sides share no column name — the exact precondition `build_side_fan_out_sql`'s identical bare-rendering already relies on.

#### Consequences

- `render_broadcast_join`'s doc comment ("Rendering is side-agnostic: the translator emits bare column names") was FALSE as written — it described an unstated assumption (Exasol never sends `tableAlias`), not an enforced guarantee. It is rewritten (task 1.6) to state that the function explicitly strips the alias to GUARANTEE bare rendering, and names why that is safe.
- `vs-adapter/pushdown-planning-join`'s permanent-spec Background already asserts, in the present tense, "Broadcast rendering is side-agnostic bare-name" — equally false before this fix. The delta makes it true rather than adding a new requirement, the same pattern this delta's Background already uses for its `#215` bullet.
- `rendering.rs::render_broadcast_join_preserves_native_table_alias_unchanged` asserted the OPPOSITE of the corrected behavior as CURRENT NORMATIVE fact, with a comment describing the preservation as deliberate ("the in-UDF `build_join_sql` join resolves it"). That claim was never true — `build_join_sql` does not alias its derived sub-SELECTs at all, so there was nothing for a preserved alias to resolve against. The test is replaced (task 1.7).
- No wire-format change, no new `JoinSpec` field, no change to `build_join_sql` or `register_join_tables` — this fix is confined to the VS planning layer, orthogonal to the credential fix's wire-format work in tasks 2.x-4.x.

## Impact

**A broadcast join against a catalog that scopes vended credentials per table starts working — including when the query aliases the joined tables** (`FROM fact_orders o JOIN dim_customer c ON ...`, how most real client SQL is written). Whether a real client driver's own default row-limit-style attribute reproduces the SAME suppression this plan's own test harness had (see § Non-Goals' `join_requires_exasol_postprocessing` bullet) remains unstudied, so the practical reach of both fixes in production is not fully verified by this plan's test suite. Before this plan, TWO independent defects each blocked this, compounding: the fact side's credential silently served both sides' reads (issue #294), and an aliased join's condition/filter/projection failed to resolve against the scan's unaliased derived relations before the credential defect was even reached (`#303`). Both are fixed here. Against Databricks-managed Iceberg or any Lakekeeper `sts-enabled` warehouse that downscopes to the table location, an unfixed credential defect denies the dimension-side read and the join fails; an unfixed alias defect fails earlier, at the DataFusion planning step, with a schema error. No result was silently wrong under either defect — both failure modes are read/schema errors, not wrong rows — so no previously-returned result set changes.

**No operator-facing configuration changes.** No new VS property, no new adapter note, no CONNECTION field. Every existing single-backend join keeps its plan; the emitted scan-driving SQL differs only by the additional `storage` key inside the common blob's join block.

**Two bounded behaviour changes to name:**

- **A broadcast join's emitted common blob now carries TWO credential sets, one per side.** That blob has always carried the storage credentials the scan UDF consumes, because it is how they reach the UDF; this plan doubles that material on a join. `vs-adapter/pushdown-planning-join`'s recorded "credentials MUST NOT appear in any returned SQL string or error message" bullet is scoped to credential-redacted error surfacing (`redact_error_text` / `redact_credentials` cover error text only), and the delta states the doubling explicitly rather than leaving it implicit.
- **A broadcast join can hold up to 2N warm idle object-store sockets instead of N**, where N is the resolved `S3_MAX_CONNECTIONS` budget, because each side's inner store gets its own HTTP client. This is a socket / file-descriptor bound, not a request-rate bound (`pool_max_idle_per_host`), and a different-bucket join already behaved this way. `datafusion-scan/scan-execution-connection-concurrency`'s delta records it.

**Wire-format change, intra-deploy only.** `JoinSpec` gains a REQUIRED `storage` field, so a common blob whose join block omits it fails to deserialize. `scan-execution-spec-reconstitution` already records that the same `.so` produces and consumes the spec within one deploy, so there is no cross-version compatibility requirement. A non-join common blob is byte-identical to its pre-change encoding, so every non-join golden fixture passes unedited; the two join goldens change by exactly the added key.

**One deviation from the Iceberg table spec is newly NAMED but not newly introduced:** a side whose own files span more than one bucket is refused with a clear error. See § Iceberg table-spec compliance; task 6.1 files the tracked issue.

**Nothing is refused that was previously accepted.** Credential divergence between two sides moves from silently collapsed to correctly served. Backend-variant and ADLS-account divergence keep their existing plan-time and scan-time refusals.

**A pre-existing false characterization is corrected, not newly introduced.** `e2e_join_test.rs`'s 18 tests run against the shared test harness's hardcoded `resultSetMaxRows: 10000`, which Exasol turns into a pushdown-request `limit` that forces every join onto the unaccelerated fallback at ROW-FETCH time — independent of, and unrelated to, the credential or alias fixes. Four of those 18 tests name or rely on the broadcast path specifically being exercised when their rows are fetched; before this plan, all four silently ran on the fallback instead, a fact this plan's own § Test Disposition did not previously state. Task 1.8 adds a scoped opt-out and task 1.10 applies it to exactly those four tests, so their names become true. The other 14 tests are unaffected: each is independently routed to the fallback (or to a decline) by aggregate/GROUP BY, a 3-or-4-table join, an above-threshold dimension side, or a type the broadcast renderer declines — never by the incidental row-limit — so the harness artifact never changed what they characterize.
