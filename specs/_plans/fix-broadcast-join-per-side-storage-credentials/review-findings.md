### crates/lakehouse-engine/src/scan/join_scan.rs

#### [INFORMATION_LEAKAGE] The join scan's redaction set is derived from one side while it guards errors from both
- Location: line 46 (set), lines 56-57 (uses), lines 37-38 (the doc claim)
- Issue: This is the one place where the plan's own fix opens a credential-leak path it then does not close. `run_join_scan_with_session` still builds `let secrets = spec.common.storage.secret_values();` — the FACT side alone — and passes exactly that slice to `classify_scan_error` (line 56) and `emit_stream` (line 57). Before this plan both sides shared `common.storage`, so that set was complete; now `join.storage` can hold a different credential (the whole point of the change, and the golden JSON in `sql_builders.rs` proves the two differ on the wire), and the DIMENSION side's access key, secret key, session token, or SAS token is no longer in the value-based redaction set — while a dimension-side read failure surfaces through precisely those two calls. The label-only fallback does not cover the gap, and `redaction.rs`'s own doc says so: for an Azure SAS the label pass matches the token's own `sig=` and rewrites only from there to the next `&`, "surfacing the token's permission and expiry fields verbatim" (`crates/lakehouse-catalog/src/redaction.rs:88-94`), and for an S3 `SignatureDoesNotMatch` body the raw key carries no label at all (`emit.rs`'s `redact_storage_error` doc: "the value-based pass catches S3 XML / signature error shapes that embed the raw key without a recognizable label"). The same union is already assembled correctly one module away — `object_store.rs:64-67` builds `all_secrets` over every present side precisely because "a function holding one side's backend cannot redact an error against a side it never sees" — so the rule "which secrets must be stripped for this scan" now lives in two modules that disagree, with nothing enforcing agreement. `run_join_scan_with_session`'s own doc comment (lines 37-38) asserts the opposite of the shipped behavior: "Read/deserialization errors for EITHER side route through `classify_scan_error`, so no credential value can leak."
- Fix: In crates/lakehouse-engine/src/scan/spec.rs, add a `pub fn all_secret_values(&self) -> Vec<&str>` to the `ScanSpec`/common-blob type that returns `common.storage.secret_values()` unioned with `common.join.as_ref().map(|j| j.storage.secret_values())`, documented as the single owner of the scan's redaction set. Then in crates/lakehouse-engine/src/scan/join_scan.rs replace line 46's `spec.common.storage.secret_values()` with that call, and in crates/lakehouse-engine/src/scan/object_store.rs replace the hand-rolled `all_secrets` union in `build_session_context` (lines 64-67) with the same call so exactly one module owns the rule — updating the two test helpers that rebuild the union by hand (`build_fact_side`, `each_side_store_gets_the_full_connection_budget`) to call it too. Finally correct `run_join_scan_with_session`'s doc comment so it names the union, not the fact side.
- **Outcome: fixed** — `CommonScanSpec::all_secret_values` (`crates/lakehouse-engine/src/scan/spec.rs`) is now the single owner of the union rule; it is the type that structurally holds both `storage` and `join.storage`, and its own doc already carried the "credentials must never appear in an error" contract. `join_scan.rs`'s `run_join_scan_with_session` and `object_store.rs`'s `build_session_context` both read the set from there, and the two test helpers (`build_fact_side`, `each_side_store_gets_the_full_connection_budget`) no longer rebuild it. `run_join_scan_with_session`'s doc now names the union and why a fact-side-only set leaks. Verified by the new falsifiable test below (RED before this fix with `DIMSECRETVALUE` in the surfaced text, GREEN after).
