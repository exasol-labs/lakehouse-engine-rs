## Premortem

Three failure stories written before scoring, each routed into the taxonomy below.

1. **The fix ships and Databricks joins still fail.** Task 1.2 finds Lakekeeper's vended credentials are whole-bucket, escalates, and the user approves proceeding on host-level proof. But no test asserts the dimension inner store was built from `join.storage` rather than `common.storage` — the mapped test (`each_join_side_reads_through_its_own_store`) hand-wires two stub stores and proves only that routing works. A later refactor silently restores the collapse. → `[TRACEABILITY_GAP]` BLOCKER, Task Breakdown.
2. **A production query that worked now errors "unroutable path".** A logical-schema-less spec's first-file `head` 404s, DataFusion falls back to `store.list(Some(prefix))`, and the router meets an access the plan's enumeration declares impossible. The user accepted the fail-on-unroutable risk *on condition* the enumeration was accurate; it is not. → `[UNSTATED_ASSUMPTION]` BLOCKER, Feasibility.
3. **Implementation stalls for a week inside task 1.** The "only difference is one call" seeder is a 62-line duplicate; the cited E2E ground-truth helpers are private to a different test binary under a different feature gate. Then 1.2 escalates and nobody can tell whether tasks 2+ are unblocked (plan.md:191 says yes, task 1.3 and § Parallelization say no), while seven spec deltas already assert the DENIED outcome normatively. → `[AMBIGUOUS_REQUIREMENT]` + `[UNSTATED_ASSUMPTION]` BLOCKERs, `[EFFORT_MISESTIMATION]` ADVISORY.

## Intent Fidelity

No objection to the substance: every element of the request is present and honoured — `JoinSpec::storage` set from `dimension.effective_storage` (task 2.3), per-side registration replacing `spec.common.storage` (tasks 4.1–4.3), the prefix-routing decorator registered once per bucket over one inner store per side (task 3), the explicit refusal to fix by rejecting divergent joins or falling back to the N-scan renderer (§ Non-Goals, § Consequences), always-route with no credential comparison, error-on-unroutable, both comment rewrites, both guard reconciliations, and the replacement of `s3_sides_differing_in_credentials_are_accepted`. The three widenings the brief flags are each traceable rather than gold-plating: the redaction leak sits on the exact call site the user cited (`join_scan.rs:109`), the connection-budget doubling is a consequence of the user-mandated always-route decision, and naming the multi-bucket refusal is compelled by CLAUDE.md's Iceberg rule.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `datafusion-scan/scan-execution-join/spec.md` Background bullet 5 (line 17); plan.md § Iceberg table-spec compliance ¶1 (line 46)
- Issue: the enumeration of scan accesses is wrong in two directions, and the interview made the fail-on-unroutable decision conditional on exactly this enumeration being right ("the spec must enumerate which access paths the scan actually issues and confirm each falls under one of the two roots"). The delta asserts: "Per side the scan issues exactly: one sized `head` per data file … **No other path is requested**". Both halves are false. (a) The head count is inverted: no `head` is issued per data file. Every `PartitionedFile` is built from a synthesized `ObjectMeta` (`scan/positional_deletes.rs:664-665`), so the production path (`logical_schema` non-empty) issues **zero** heads — a property the repo regression-tests in `tests/scan_no_head_test.rs`. Exactly **one** head exists, on the first file only, in the schema-inference branch (`scan/raw_scan.rs:211-216`). (b) `ObjectStore::list` **is** reachable: `ListingOptions::infer_schema` (`raw_scan.rs:208-217`) reaches `list_prefixed_files`, which on `Err(NotFound)` from that head falls through to `store.list(Some(&full_prefix))` (`datafusion-datasource-54.1.0/src/url.rs:266-294`, `:398`), and which skips the head entirely and lists when the entry path ends with `/` (`is_collection()`, `url.rs:204-206`). Task 3.2 rules only on `list(None)` and leaves `list(Some(..))` unspecified. Both reachable list prefixes are in fact routable (an exact enumerated path, or a root-prefix match), so this is a text-and-rule correction rather than a design change — but as written the plan certifies a completeness property it has not established, and permanently records a false statement about the engine's head behaviour.
- Fix: Rewrite `datafusion-scan/scan-execution-join/spec.md` Background bullet 5 and plan.md § Iceberg table-spec compliance ¶1 to state the verified access set: zero per-data-file `head` calls on the production path (`ObjectMeta` synthesized from the spec sizes, `scan/positional_deletes.rs:664-665`); exactly one `head` on the first file only when `logical_schema` is empty (`scan/raw_scan.rs:211-216`); range reads of each data file's footer, page index, and bloom filters; range reads of each positional-delete file; and — on the schema-inference branch only — a `list(Some(prefix))` fallback when that single head returns `NotFound` or when the entry path ends with `/` (`datafusion-datasource-54.1.0/src/url.rs:266-294`). Then add to task 3.2 an explicit rule that `list`/`list_with_delimiter` with `Some(prefix)` route by the same two-step rule as any other path, and add a `store_router.rs` test for `list(Some(exact_file_path))` and `list(Some(table_root))` to task 3.3.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: plan.md § Implementation Tasks task 3.1; § Migration (`side_size_index` row)
- Issue: "the `object_store::Path` DataFusion will request for this file entry" is one decision that will be reflected in three modules. It already lives twice, by copy: `index_file_sizes` builds it as `ListingTableUrl::parse(reconstruct_abs_uri(path, table_root)).prefix().clone()` (`scan/object_store.rs:283-295`) and `object_meta_for` builds it identically (`scan/positional_deletes.rs:215-225`). Task 3.1 adds a third in the new `store_router.rs`. The plan names the risk ("so file paths and roots share one coordinate system by construction rather than by inspection") but gives the decision no owner, and the invariant is brittle: `Path::from(&str)` percent-*encodes* while `ListingTableUrl::parse().prefix()` percent-*decodes* (`object_store-0.13.2/src/path/mod.rs:260-270` vs `:392-402`), so a router keyed the other way false-errors on any table with encoded partition values. Two secondary gaps: task 3.1 says to derive the owned set "the same derivation `index_file_sizes` already uses", but `index_file_sizes` has no `entry.deletes` loop, so no such derivation exists for delete files; and `DeleteFileRef.path` may be relative (`scan/spec.rs:517-528`), so the router must key the `reconstruct_abs_uri`-resolved path, which task 3.1 never says.
- Fix: Give the decision one home. Add a task exporting a single `pub(crate) fn requested_path(entry_path: &str, table_root: &str) -> Result<ObjectStorePath, UdfError>` from `scan/object_store.rs` that performs `reconstruct_abs_uri` then `ListingTableUrl::parse(..).prefix().clone()`, and restate task 3.1, the § Migration `side_size_index` row, and `scan/positional_deletes.rs`'s `object_meta_for` to call it — for data files and delete files alike — so no module re-derives the convention.

#### [TACTICAL_SHORTCUT] ADVISORY
- Location: plan.md § Iceberg table-spec compliance ¶1; § Patterns ("Exact-membership first, prefix second"); task 3.2
- Issue: the plan argues the root-prefix fallback can never fire and keeps it anyway. § Iceberg table-spec compliance: "that enumeration is complete for every access the scan issues … So 'fail on an unroutable path' cannot fire on a spec-legal table read through this scan." § Patterns: "the prefix fallback exists only for a path no side enumerated." Both cannot hold — if the enumeration is complete, rule 2 is unreachable in production and testable only against synthetic paths. Keeping an unreachable routing rule means a defective spec that should surface as rule 3's named error is instead silently served by whichever credential owns the nearest root, which is the class of behaviour this plan removes.
- Fix: Resolve the contradiction in plan.md § Iceberg table-spec compliance and § Patterns: either soften the completeness claim to name the concrete access that rule 2 serves (the schema-inference `list(Some(root))` case identified in the first Feasibility finding), or state that rule 2 is retained solely as the interviewed prescription's fallback and is unreachable through the current scan, and record which of the two decision-log.md § [2] asserts.

No objection on the remaining Design Depth questions: the decorator hides one coherent decision (which side owns a path) behind an existing framework trait and is noticeably cheaper to call than to reimplement; the ten `ObjectStore` methods task 3.2 enumerates are exactly the base trait's ten in `object_store` 0.13.2 (`lib.rs:746-1134`), and correctly omit `head`/`get`/`get_range`, which are `ObjectStoreExt` blanket methods funnelling through `get_opts` (`lib.rs:1340-1405`) — so decision [3]'s router-outside-sized-store layering is sound and its stated reason holds; the wrapper guidance cited at `lib.rs:655-658` is verbatim; construction stays at the session entry point with the caller owning registration; no cycle is introduced; the VS layer gains only a field assignment, so the thin-VS boundary holds. Decisions [5] and [6] are verified, not assumed: `get_url_key` slices `[BeforeHost..AfterPort]` (`datafusion-execution-54.1.0/src/object_store.rs:268-274`) and its own test asserts `s3://username:password@host:123` → `s3://host:123` (`:330-332`), `side_store_url` deliberately keeps the userinfo (`scan/object_store.rs:401-420`), and `validate_sides_share_one_store` fires only when two sides share a registry key with different derived URLs (`:444-475`) — so it accepts every same-bucket S3 join and still refuses two ADLS containers of one account. The plan's departure from root-only routing is also confirmed necessary rather than defensive: `validate_uniform_object_store_files` compares scheme+authority only (`:487-524`), so a `write.data.path` file outside the table root is already accepted today and would be misrouted by a root-only rule.
