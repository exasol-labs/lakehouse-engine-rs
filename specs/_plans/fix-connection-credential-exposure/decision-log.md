# Decision Log: fix-connection-credential-exposure

## Interview

No live interview. This plan was authored in headless mode (`/speq:plan-pr`), so every decision below was assumed against a conventional or researched default and recorded here rather than asked. The orchestrator supplied the intent, the existing normative context, and the two deliverables; the facts each decision rests on were established by research and by live probes against Exasol, not by a user answer.

**Q (implied by the intent):** Is the `EXPLAIN VIRTUAL` exposure in issue #135 real, or is it a false alarm to reassure the customer about?
**A (established, not asked):** Real. `EXPLAIN VIRTUAL` returns the adapter's `PUSHDOWN_SQL` with no redaction, its documented privilege prerequisite is "Privileges similar to the executed query", and `crates/lakehouse-engine/src/adapter/pushdown/support.rs:441` serializes the resolved `StorageBackend` into that string with no encoding. The committed golden fixture `testdata/dispatch_golden/single_group_row_scan.sql` contains `"access_key":"minioadmin","secret_key":"minioadmin"` in plaintext. Exasol's own `exasol-virtual-schema` issue #24 is the same defect in Exasol's own adapter.

**Q:** Which remediation does the Exasol Virtual Schema contract actually permit?
**A (established):** Exactly one. The pushdown response is `{"type": "pushdown", "sql": <string>}` and nothing else — `virtual-schema-common-java`'s `PushDownResponse` declares one field and `ResponseJsonConverter` emits two keys. There is no bind parameter, no placeholder, and no second field. Schema properties and adapter notes are worse rather than better: `EXA_ALL_VIRTUAL_SCHEMA_PROPERTIES` and `EXA_ALL_VIRTUAL_TABLES.ADAPTER_NOTES` are documented "All users have access to the table". The only channel that delivers a value to the UDF without putting it in the SQL is the CONNECTION indirection — the pattern `hide_access_keys_passwords.htm` documents and the one `exasol-virtual-schema` 4.0.0 used to fix issue #24.

**Q:** Is issue #135 still deferred?
**A (established):** No. The deferral comment on #135 conditioned the work on the Azure ADLS static-credentials slice reworking redaction into a per-variant `secret_values()` seam, with #267 as prerequisite. That seam exists (`crates/lakehouse-catalog/src/storage.rs:106-121`), `abfss://` support is in, and #267 is merged. The deferral is discharged and this plan lands on that seam, as the comment directed.

## Design Decisions

### [1] Reference the CONNECTION by name; the scan UDF resolves it

- **Decision:** The scan spec's storage block carries the value of the `CATALOG_CONNECTION` virtual-schema property plus the resolved `ALLOW_HTTP` value, and the scan UDF obtains the credentials by calling `ctx.connection(name)` and applying the same `parse_creds`/`storage_block` derivation the adapter applies.
- **Alternatives:** (a) Render a redacted placeholder into the SQL shown to `EXPLAIN VIRTUAL` while executing the real string — impossible, because there is one `sql` string and Exasol executes exactly what it is given, and `EXPLAIN VIRTUAL` itself would still show the real value. (Task 1.2 later established live that profiling and audit `SQL_TEXT` never carry the rewritten pushdown SQL in the first place — see decision [16] — so they are not an additional reason this alternative fails, only `EXPLAIN VIRTUAL` and pushdown-path errors are.) (b) Carry the credential in a schema property or adapter note — both are persisted and readable by any user with access to the virtual schema. (c) Bind parameters — no such field exists in the API. (d) Have the UDF re-request credentials from the catalog — forbidden by `datafusion-scan/scan-execution-memory-and-credentials` and by `specs/mission.md`'s resolve-once rule, and it would multiply catalog calls by the shard count, up to 300. (e) Have the adapter create a per-query CONNECTION over connect-back and pass its name — stateful DDL per query, contradicting "no state survives query completion", and it leaves droppings when a query fails.
- **Rationale:** It is the only remedy the contract admits, it is the remedy Exasol documents for this exact problem, and it is the remedy the code's own `ponytail:` marker at `pushdown/mod.rs:128-133` already named as the upgrade path. `ctx.connection()` is not the forbidden catalog round-trip: it is one engine-local metadata request over the SLC protocol (`PB_IMPORT_CONNECTION_INFORMATION`), answered by the database from its own catalog, discovering no file and minting no token.
- **Promotes to ADR:** yes

### [2] Close the static path in this plan; track the vended residual as issue #378

> SUPERSEDED IN PART by decision [14] after the round-2 discussion with the user: the static half stands; the DEFERRAL of the vended half does not. Alternative (a) below — the HKDF + AEAD envelope — is adopted with its guarantee scoped per catalog-auth mode, and alternative (b) — refusing to plan — is adopted for exactly the one combination where the envelope's key material does not exist. The entry is kept unedited below as the design-history record of what was rejected first and why.

- **Decision:** With `use_vended_credentials` false the wire carries a reference and no credential. With it true the resolved backend is carried inline and the vended credential still appears in the SQL, recorded as the tracked exception issue #378 and cited inline in two specs.
- **Alternatives:** (a) Encrypt the storage block under a key derived from the resolved CONNECTION password (HKDF + AEAD) and have the UDF re-derive it — the only candidate that would close it. (b) Refuse to plan a vended query until it is closed. (c) Say nothing about the vended path.
- **Rationale:** Four reasons, in order of weight. First, the static fix is the strict PREREQUISITE of the envelope rather than an alternative to it — the envelope's key derivation needs `ctx.connection()` from the scan UDF, which is exactly what this plan builds — so landing it first composes and forecloses nothing. Second, the envelope's guarantee is CONDITIONAL on the CONNECTION password's entropy: a no-auth OSS catalog whose password is `{"warehouse":"…"}` yields a near-guessable key, and shipping a conditional guarantee in the same change as an unconditional one blurs what the release promises. Third, the severities differ by orders of magnitude: a vended credential expires and is scoped to the prefix the catalog vended it for, while a CONNECTION `secret_key` is long-lived and account-wide — and issue #135 as filed is explicitly about "the `access_key` and `secret_key` from the catalog CONNECTION", the static case. Fourth, option (b) breaks every working vended deployment, and option (c) is the silent gap `CLAUDE.md` forbids. Issue #378 was created during planning so the citation is real rather than a placeholder.
- **Promotes to ADR:** yes

### [3] No fallback when the script-scoped grant is absent

- **Decision:** A deployment that upgrades without `GRANT ACCESS ON CONNECTION <c> FOR SCRIPT <schema>.LAKEHOUSE_SCAN` fails at scan time with an error naming the connection and the missing access. The plan adds no code path that reads an inline credential when the reference cannot be resolved.
- **Alternatives:** Fall back to an inline credential and log a warning; keep the inline form behind a virtual-schema property for one release.
- **Rationale:** A fallback keeps the leak reachable for every deployment that never adds the grant, which is every existing deployment — so the vulnerability would be closed only for operators who already read the release notes. `exasol-virtual-schema` 4.0.0 is the precedent for the opposite choice and states it plainly: "The old variant is intentionally not supported anymore to tighten security." A clear failure is also the only outcome an operator cannot ignore.
- **Promotes to ADR:** yes

### [4] Gate the whole plan on a live check of connection resolution from the scan script

- **Decision:** Task 1.3 verifies, live against the Docker Exasol container, that `ctx.connection(name)` succeeds inside `LAKEHOUSE_SCAN` invoked from generated pushdown SQL, with the name arriving as part of the `common` VARCHAR argument rather than as a literal in the script body, for a user holding only the script-scoped grant — and fails once that grant is revoked. No fix task may start until it passes, and a failure escalates rather than being worked around.
- **Alternatives:** Assume it works because the adapter script already calls `ctx.connection()` and the SLC protocol is language-agnostic; verify it as part of the final E2E suite.
- **Rationale:** Two facts are documented and one is not. Documented: the SLC protocol carries the request for any language, and Exasol states the script-scoped grant's purpose ("This ensures that a user cannot access the details indirectly by creating a new script that extracts and returns the credentials"). Verified live during planning: `GRANT ACCESS ON CONNECTION <c> FOR SCRIPT <s> TO <u>` parses on Exasol 2025.2.1, failing only on object resolution with SQL state `42500`. NOT documented anywhere: the security context for a UDF reached indirectly through a rewritten pushdown statement, and whether the grant applies when the connection name arrives as a runtime argument. If resolution turns out to require the querying user's own `ACCESS ON CONNECTION`, the fix protects nobody — Exasol documents that grant as including "passwords/tokens" — and the design has no channel left. That is a plan-invalidating outcome, so it is checked first, which is also what this repo's verification-discipline rule demands.
- **Promotes to ADR:** no

### [5] Resolve once per invocation, and move the redaction secret set onto the resolved value

- **Decision:** One `resolve_scan_storage` call at the top of `run_scan` resolves both join sides into a `ResolvedScanStorage`, which owns `all_secret_values()`. `CommonScanSpec::all_secret_values` is deleted.
- **Alternatives:** Resolve lazily at each store-construction site; keep the secret set on the spec.
- **Rationale:** Keeping the set on the spec is the plan's one silent-failure trap. `CommonScanSpec::all_secret_values` (`scan/spec.rs:1232-1238`) feeds value-based redaction at `object_store.rs:66` and `join_scan.rs:48`; a spec carrying a connection NAME has no secret to yield, so the set would quietly become empty exactly for the credentials that started being resolved elsewhere — a change that fixed the SQL path while weakening the error path, with every existing test still green. The set must therefore follow the credential. Resolving lazily would additionally read one CONNECTION twice per join invocation and leave the set undefined between the two reads.
- **Promotes to ADR:** yes

### [6] One tagged wrapper enum on the wire, not optional fields

- **Decision:** `enum ScanStorage { Connection { name, allow_http }, Inline(StorageBackend) }`, externally tagged and explicitly not `untagged`, wrapping the existing backend encoding byte-for-byte.
- **Alternatives:** Make `StorageProps`' credential fields optional; add a sibling `connection_name` field beside the existing `storage` field; declare the wrapper `untagged`.
- **Rationale:** Optional fields collapse "absent because referenced" and "absent because empty" into one state, and the second is already a meaningful input on the vended path. A sibling field admits the contradictory combination of a name AND a credential, which the enum makes unrepresentable. `untagged` would decide between a connection reference and an inline S3 backend — both JSON objects — by field-name coincidence. Nesting the existing backend object unchanged is what keeps `catalog_storage_props`, the round-trip guarantee, and the decode-side variant-key pins valid without edit.
- **Promotes to ADR:** no

### [7] The UDF runs the derivation, not the acceptance validation, and the derivation moves inward

> SUPERSEDED IN PART by decision [12] after round-1 review: the validation half stands, the MOVE does not. `parse_creds` and `storage_block` stay in `lakehouse_engine::adapter::connection`.

- **Decision:** The scan side calls `parse_creds` and `storage_block` only. `validate_creds` stays adapter-side. Both moved functions relocate from `crates/lakehouse-engine/src/adapter/connection.rs` into `crates/lakehouse-catalog/src/creds.rs`.
- **Alternatives:** Re-run `validate_creds` in the UDF; call the adapter module from the scan module; duplicate the derivation on the scan side.
- **Rationale:** `validate_creds` is parameterized by the resolved `CatalogKind` and decides whether a CONNECTION may be accepted for a virtual schema — a plan-time question already answered for this query. Re-running it would thread `CatalogKind` onto the wire for no new decision and would report a CONNECTION edited mid-query as a validation error rather than the storage access error it is. On the move: having `scan/` call `adapter/` points business logic at a delivery mechanism, and duplicating the derivation gives one decision two homes free to drift — the precise defect `vs-adapter/connection-credentials-catalog-auth` was written to remove. `lakehouse-catalog` already owns both `ConnectionCreds` and `StorageBackend`, so the dependency points inward.
- **Promotes to ADR:** no

### [8] Assert the guarantee on the rendered SQL string, across a derived builder-path list

> AMENDED after round-1 review: the path count is DERIVED rather than asserted as eight, the template comes from the production selection function rather than from a hand-built fixture, and the fixture set splits 18 regenerated / 6 unchanged. See the `[plan-review]` entry "The headline guarantee test asserted on its own fixture".

- **Decision:** One test drives every builder entry point — every `RequestShape` variant crossed with the join, top-N, and `COUNT(DISTINCT)` sub-paths, plus the `scalar_over_agg.rs` shapes, `group_by_fallback`, `multi_count_distinct_decline`, and `nested_aggregate_decline`, cross-checked against the 18 credential-bearing fixture names — with the spec template produced by `scan_storage_for`, and asserts that sentinel credential values are absent from the returned SQL string while the connection name is present. The 18 credential-bearing golden fixtures are regenerated; the 6 `empty_*` fixtures stay byte-identical.
- **Alternatives:** Assert on the `ScanSpec` structure; assert only at the single chokepoint `build_fan_out_inner`.
- **Rationale:** A structural assertion stays green while the rendered string regresses, and the leak is a property of the string. Asserting only at the chokepoint would miss a later builder that bypasses it — the eight paths all route through `support.rs:441` today, and that is a fact to verify per path rather than to assume permanently.
- **Promotes to ADR:** no

### [9] Close the four adjacent same-class exposures in this change

- **Decision:** Add redacting manual `Debug` impls to `StorageProps` and `StorageBackend`, add `access_key` to `ConnectionCreds`' redacted set, add a label pattern for the `AdlsCred::Sas` wire key to `redact_credentials`, and repoint `auth.rs:93` and `:160` at `redact_error_text`.
- **Alternatives:** Defer all four to a follow-up; fix only the two that are reachable today.
- **Rationale:** All four are the same CWE class on the error path, and `storage-backend-enum`'s own recorded Background already cites issue #135 while noting that the `AdlsCred` redacting `Debug` leaves it "strictly less to fix". Shipping a release described as fixing credential exposure while `{:?}` on `StorageProps` still prints a secret key, a serialized SAS survives nine value-blind redaction call sites, and two sites keep the composition order this crate documents as broken would be inaccurate. Each fix is a few lines and none touches a selection rule.
- **Promotes to ADR:** no

### [10] Rotation guidance ships as `docs/security.md`, not as a spec feature

- **Decision:** The `client_secret` rotation runbook is documentation. The one behavioural consequence this plan introduces — that a CONNECTION rotated mid-query is observed per shard — IS specified, in `vs-adapter/scan-spec-credential-reference`.
- **Alternatives:** A spec feature for rotation; a section inside `docs/install.md`; no artifact, answered in the PR body only.
- **Rationale:** A spec describes behaviour the engine has. The engine holds no state, caches nothing, and re-resolves the CONNECTION on every query, so there is nothing about rotation for it to do and nothing to test — except the mid-query straddle, which is behaviour and is therefore specified rather than documented. `docs/` is where the operator-facing procedure belongs, and it gets its own page rather than a subsection of `docs/install.md` because it also has to carry the privilege model, the leak surfaces, and the sealed vended envelope with its bounded threat model (decision [14]), which are not installation topics. Two runbook facts were verified live rather than assumed: `ALTER CONNECTION … IDENTIFIED BY …` parses on 2025.2.1 (so an in-place rotation exists that cannot drop the connection's grants), and `EXA_DBA_CONNECTIONS` exposes no password column (so a rotated secret leaves nothing behind in the catalog). Whether `CREATE OR REPLACE CONNECTION` preserves grants is recorded as UNVERIFIED rather than guessed, and the runbook recommends `ALTER` to avoid the question.
- **Promotes to ADR:** no

### [12] The CONNECTION-to-backend derivation gains a storage-only projection; nothing moves out of the adapter module

- **Decision:** Supersedes decision **[7] The UDF runs the derivation, not the acceptance validation, and the derivation moves inward** on the move half only; the validation half of [7] stands unchanged. `read_connection`, `validate_creds`, `parse_creds`, `storage_block`, `catalog_block`, and `REQUIRED_KEY` all STAY in `lakehouse_engine::adapter::connection`. `lakehouse-catalog` gains `StorageCreds` (nine storage fields), `StorageCreds::from_json`, `StorageCreds::backend`, and one `From<&ConnectionCreds>`. `parse_creds` reads its nine storage spellings through `from_json`; `storage_block` becomes `StorageCreds::from(creds).backend(allow_http)`; the scan UDF calls `from_json` then `backend` and never constructs a `ConnectionCreds`.
- **Alternatives:** (a) Decision [7]'s original move, with a `DELTA:CHANGED` superseding `catalog-crate-structure:68`. (b) Duplicate the derivation scan-side. (c) Have the scan call into `adapter::connection`.
- **Rationale:** `catalog-crate-structure:68` reads verbatim: "`read_connection`, `validate_creds`, `parse_creds`, `storage_block`, `catalog_block`, and `REQUIRED_KEY` SHALL stay in `lakehouse_engine::adapter::connection`, because they interpret the Exasol CONNECTION object and the catalog crate MUST NOT name that delivery mechanism." That reason is substantive, not formal — `parse_creds` reads `REQUIRED_KEY` and the CONNECTION password schema including its catalog-auth half — so option (a) would reverse a coherent recorded decision and, worse, would run `parse_creds` inside the UDF and materialize `token` and `client_secret` there. This shape SATISFIES the clause instead: what crosses the boundary is a credential TYPE, the same boundary `StaticStoreAddress` already sits on, and the selection rule keeps exactly one home. Option (b) gives one decision two homes free to drift, the defect `connection-credentials-catalog-auth` was written to remove; option (c) points the scan at a delivery mechanism. The cost is that `storage_block` becomes a one-line projection-and-delegate rather than the rule's home, which is stated in the spec and in § Migration rather than left for a reader to discover.
- **Promotes to ADR:** yes

### [13] The wire type stays the spec's own field; no parallel resolved-spec type

- **Decision:** `CommonScanSpec.storage` and `JoinSpec.storage` keep holding the `ScanStorage` wire value after resolution, and the resolved pair is threaded beside the spec. No `ResolvedScanSpec` owning a spec whose storage is already resolved is introduced.
- **Alternatives:** The round-1 INFORMATION_LEAKAGE advisory's preferred shape — a `ResolvedScanSpec` constructed only by `resolve_scan_storage` and taken by every downstream function in place of `&ScanSpec`, making the unresolved variant unreachable by construction.
- **Rationale:** The advisory's concern is real and is addressed, but by the blocker fix rather than by a parallel type. The failure mode it names — a site silently reading the unresolved value and getting an empty secret set — is made a COMPILE error by `ScanStorage` exposing no `secret_values()` and no payload accessor, which is what the COMPLETENESS_GAP blocker's fix requires; and the two sites that take a `&StorageBackend` parameter cannot reach the wire value at all. A `ResolvedScanSpec` would additionally touch the 28 files that construct `CommonScanSpec` — 15 of them integration binaries — for an invariant already unrepresentable. Recorded as considered and bounded rather than dismissed, so a later planner does not re-litigate it without knowing the compile-time guard exists.
- **Promotes to ADR:** no

### [14] Close #378 in this plan: seal the vended storage block under a key derived from the CONNECTION; refuse no-auth + vending at plan time

- **Decision:** Supersedes decision **[2]** on the vended half only; the static half of [2] stands unchanged. Under `use_vended_credentials`, the resolved effective `StorageBackend` is serialized as before and then SEALED — AES-256-GCM under a 32-byte key derived via HKDF-SHA256 from the CONNECTION password bytes exactly as `ctx.connection()` returns them (empty salt, info `"lakehouse-engine scan-storage sealed v1"`), fresh random 96-bit nonce per encryption, wire form `base64(nonce ‖ ciphertext)` beside the connection NAME in a `Sealed` wire variant. The scan UDF resolves the SAME CONNECTION — the one the operator already creates for catalog access; no second CONNECTION, no new provisioning concept — derives the identical key from the password bytes without parsing them, and opens the envelope. The key exists iff the catalog-auth mode carries genuine secret material (bearer `token`, OAuth2 `client_secret`, or SigV4 `access_key`/`secret_key`); for a no-auth catalog with vending enabled, `scan_storage_for` REFUSES to plan with a named `UdfError` stating the combination and both remedies. Decision taken live with the user during the round-2 revision.
- **Alternatives:** (a) Keep [2]'s deferral — vended values inline in plaintext under a tracked issue. (b) Encrypt unconditionally, no-auth included. (c) Refuse ALL vended queries. (d) A second, dedicated high-entropy CONNECTION as key material.
- **Rationale:** [2] rejected the envelope on one objection: its guarantee is CONDITIONAL on the CONNECTION password's entropy — a no-auth catalog password of `{"warehouse":"…"}` yields a near-guessable key, a false guarantee. This decision scopes the guarantee correctly instead of abandoning it: every auth mode except no-auth carries genuine secret material in that password, and the one mode that does not is refused for vending. The refusal breaks no real or tested deployment: the recorded orthogonality bullet (`specs/vs-adapter/pushdown-planning-cloud-credentials/spec.md:21-27`) states vending's independence from the auth mode as a code-path gating rule ("the catalog-auth mode selects only how the table-load request is authenticated"), not as an endorsement of every combination as a deployment shape; the E2E matrix exercises vending only against authenticated stacks (Lakekeeper+Keycloak OAuth2, Unity, Azure, SigV4 Glue), while the no-auth `iceberg-rest-fixture` stack pins `use_vended_credentials: false` and static MinIO credentials (`crates/lakehouse-engine/tests/common/seed.rs:279`, `tests/common/stack.rs:410`); and a catalog vending real temporary cloud credentials to unauthenticated callers is itself broken, independent of this engine. [2]'s prerequisite argument ("the envelope needs `ctx.connection()` from the scan UDF") now argues FOR doing it here: this plan builds exactly that. The threat model is deliberately bounded and stated as such in plan.md § Sealed vended envelope: defeat a plaintext read of `EXPLAIN VIRTUAL` output or pushdown-path error text (task 1.2/decision [16] established live that profiling and audit `SQL_TEXT` never carry the rewritten pushdown SQL, so they are not a surface the envelope needs to defeat), not offline cryptanalysis — acceptable because vended values are short-lived and prefix-scoped, and the key material is what `ACCESS ON CONNECTION` already reveals. Alternative (b) ships the false guarantee [2] refused; (c) breaks every working vended deployment; (d) adds an operator-facing provisioning step and a second grant for marginal entropy gain over passwords that already carry secrets. Deriving from the password BYTES rather than from parsed auth fields keeps the catalog-auth structural exclusion intact — the UDF hashes the text it already receives and parses nothing new. Cost, named: the first direct crypto dependency of the `.so` (plan.md § Dependencies — `hkdf` is the only crate new to `Cargo.lock`; `aes-gcm` and `sha2` are already there transitively), the scan-script grant now binds vended deployments too, and a mid-query rotation fails in-flight vended shards with a named error.
- **Promotes to ADR:** yes

### [15] `StorageCreds` publishes its nine fields as `pub`, mirroring `StorageProps`

- **Decision:** Resolves the round-2 REQUIREMENT_CONFLICT on `StorageCreds` field visibility (open-questions.md), in the shape decision [14]'s design leaves unchanged: the nine storage fields are declared `pub`, mirroring `StorageProps` (`crates/lakehouse-catalog/src/creds.rs:181-195`), which already carries credentials with public fields. The § Verification test `storage_creds_fields_are_not_public` is DELETED and replaced by `storage_creds_declares_exactly_the_nine_pub_storage_fields`; the payload is guarded by task 5.1's redacting manual `Debug`, not by visibility.
- **Alternatives:** Private fields plus nine accessors (fails the probe's enumerated `pub` set and adds surface for no guarantee); private fields with `parse_creds` duplicating the nine key spellings (loses the one-reader property decision [12] rests on).
- **Rationale:** `parse_creds` stays in `lakehouse-engine` and must read the nine values across the crate boundary into its `ConnectionCreds` literal, so some `pub` reachability is unavoidable; fields are the smallest honest form and match the sibling type that already models this exact trade-off. The sealed-envelope design needs nothing further from `StorageCreds` — its key material is the raw password, not the projection — so no wider shape is required.
- **Promotes to ADR:** no

### [plan-review] Task 1.3's gate was circular and unexecutable

- **Direction change:** Split into 1.3a and 1.3b. 1.3a is the gate and needs no engine change, and it was RUN LIVE during this revision rather than left as a task: a throwaway Lua SCALAR script `CONN_PROBE (cname VARCHAR(200))` calling `exa.get_connection(ctx.cname)`, a CONNECTION carrying a JSON credential document, and a user holding only `CREATE SESSION`, `EXECUTE ON SCRIPT`, and `GRANT ACCESS ON CONNECTION <c> FOR SCRIPT <schema>.CONN_PROBE TO <u>`. Result: `SELECT <schema>.CONN_PROBE('<c>')` returned `OK addr=… user=… pwlen=142`, so the script-scoped grant DOES cover a connection name arriving as a runtime VARCHAR argument. - **Promotes to ADR:** no

### [plan-review] Catalog-auth secrets would have materialized inside the scan UDF

- **Finding:** [NFR_IGNORED] BLOCKER. Task 4.1 ran the moved `parse_creds` over the whole CONNECTION password inside the UDF. `parse_creds` populates all seventeen `ConnectionCreds` fields — verified: no `..Default::default()`, every field written explicitly — so `token`, `client_secret`, `client_id`, `oauth2_server_uri`, and `scope` would materialize on every shard invocation, up to 300 per query, outside the storage-only redaction set. That falsifies `connection-credentials-catalog-auth`'s recorded "they never cross the UDF boundary", with no delta — and the new spec cited that very sentence as still true.
- **Direction change:** The scan side now deserializes a STORAGE-ONLY projection, `StorageCreds`, declaring exactly `endpoint`, `region`, `access_key`, `secret_key`, `session_token`, `path_style`, `account_name`, `account_key`, `sas_token` — nine fields, no catalog-auth field to hold a secret in. ### [16] Task 1.2, live-verified: profiling and audit `SQL_TEXT` never carry the rewritten pushdown SQL — the profiling positive control is removed, not merely satisfied

- **Decision:** Live probe against Exasol 2025.2.1 (full stack: Exasol + MinIO + `iceberg-rest-fixture`, a real `MY_LAKEHOUSE` VS over the seeded `EVENTS` table, real seeded `minioadmin`/`minioadmin` CONNECTION credentials): `ALTER SESSION SET PROFILE = 'ON'` plus a marked query plus a DBA-issued `FLUSH STATISTICS` populated `EXA_DBA_PROFILE_LAST_DAY` with 9 rows (one per execution-graph part — `COMPILE / EXECUTE`, `PUSHDOWN`, `INSERT`, two `SCAN`, two `GROUP BY`) and `EXA_DBA_AUDIT_SQL` with a matching row. Every row's `SQL_TEXT`, in BOTH views, was byte-identical to the user's own literal `SELECT ... COUNT(*) FROM MY_LAKEHOUSE.EVENTS` statement — no `LAKEHOUSE_SCAN` call, no `access_key`/`secret_key` — while the SAME query's `EXPLAIN VIRTUAL` output carried both, in `PUSHDOWN_SQL`, verbatim. **Result: the VS-rewritten pushdown SQL never reaches profiling or audit; only the user's own literal statement does.** This corrects the plan's and every affected spec delta's claim that profiling/audit are leak surfaces (they are not, for either the standing or the sealed-vended credential) and removes the profiling-based positive control the round-1 fix above added to `e2e-harness` and task 7.3 — that control's own positive check (a row matching the query's embedded comment) is satisfied by the row that ALWAYS exists regardless of whether the credential fix is present, because it is the user's unrewritten statement, which structurally cannot carry the credential. `EXPLAIN VIRTUAL` and pushdown-path error text (tasks 1.1, 4.1, 4.5) are unaffected and remain the two real, verified surfaces.
- **Alternatives:** (a) Keep the profiling assertion as an additional, redundant check alongside `EXPLAIN VIRTUAL` — rejected: an assertion that passes identically on a fixed and a vulnerable build is not redundant coverage, it is a false claim of coverage that misleads a future reader auditing the test. (b) Weaken it to assert only that the row exists, dropping the credential-absence half — rejected: same vacuity restated, not resolved.
- **Rationale:** The positive-control PRINCIPLE the round-1 fix established (`[plan-review] Every absence assertion could pass on an empty surface`, above) is correct and remains applied everywhere else (task 6.1, task 3.4) — those check strings the adapter itself generates, which genuinely differ between a fixed and a vulnerable build. Profiling/audit `SQL_TEXT` is different in kind: it is Exasol's record of the OUTER statement the CLIENT submitted, not of the internal pushdown SQL the VS protocol generates and the UDF receives — the two were never the same string, with or without this plan's fix, so no assertion against profiling/audit can distinguish the two states. This was exactly the open question round-2 review raised against task 1.2's original "Record whether…" wording and left unresolved pending a live probe; the probe above answers it. Every citation of `EXA_USER_PROFILE_LAST_DAY.SQL_TEXT` / `EXA_DBA_AUDIT_SQL.SQL_TEXT` as a credential leak surface or assertion target is corrected in plan.md (§ Summary, § Design, § Impact, task 1.2, task 7.3, task 7.4, § Manual Testing), `scan-spec-credential-reference/spec.md`, and `e2e-harness/spec.md`.
- **Promotes to ADR:** no — this corrects a factual claim and a test's design under decisions [1] and [14], which remain the architectural decisions of record.
