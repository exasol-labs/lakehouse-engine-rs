# Plan: fix-connection-credential-exposure

> **Status:** all round-2 open questions resolved live with the user; two further adversarial review rounds (round-3, round-4 — see `review/`) found and fixed 11 more BLOCKERs, including two design decisions worth a second look (facade-visibility widening, entropy-gate criterion — see decision-log entries in the round-3/round-4 `[plan-review]` set). `speq plan validate` passes. Ready for `/speq:implement-pr`.

## Summary

Replace the storage credentials the adapter embeds verbatim in the scan-driving SQL with a reference to the Exasol CONNECTION that supplies them, resolved by the scan UDF through `ctx.connection()`. Closes issue #135 for CONNECTION-supplied standing credentials — a user holding only `SELECT` on a virtual schema can today read a standing `access_key` and `secret_key` out of `EXPLAIN VIRTUAL` output and out of any error raised on the pushdown path. Verified live (task 1.2) that profiling and audit `SQL_TEXT` do NOT carry it: both record only the user's own literal statement, never the VS-rewritten pushdown SQL, so those two surfaces were never a real leak vector for either credential kind. Also closes issue [#378](https://github.com/exasol-labs/lakehouse-engine-rs/issues/378), the vended residual: a credential the catalog vends per query has no name to reference, so it still travels in the SQL — but now ONLY inside an AES-256-GCM envelope whose key is derived (HKDF-SHA256) from the same CONNECTION's password, sealed at plan time and unsealed by the scan UDF after its own `ctx.connection()` read, never in plaintext. The envelope's threat model is deliberately bounded (§ Design). The one configuration the envelope cannot cover — `use_vended_credentials` enabled on a CONNECTION whose password carries no secret material at all — is REFUSED at plan time with a named error rather than shipped under a weakened guarantee.

## Design

### Context

`crates/lakehouse-engine/src/adapter/pushdown/support.rs:441` serializes the resolved `StorageBackend` into a SQL string literal:

```rust
let common_literal = sql_string_literal(&spec_template.to_common_json());
```

`to_common_json` is plain `serde_json` — no encoding, no compression, no obfuscation anywhere on the path. The committed golden fixture `testdata/dispatch_golden/single_group_row_scan.sql` therefore contains:

```
"storage":{"s3":{"endpoint":"http://minio:9000","region":"us-east-1","access_key":"minioadmin","secret_key":"minioadmin",…}}
```

That string is what the adapter returns as the pushdown response's single `sql` field, and Exasol echoes it verbatim. `crates/lakehouse-engine/src/adapter/pushdown/mod.rs:128-133` records the leak as a `ponytail:` debt marker and names the two candidate fixes; this plan takes the first of them.

**The contract permits exactly one remedy.** The relevant findings, each with its source:

| Question | Finding |
|---|---|
| Does `EXPLAIN VIRTUAL` redact? | No. Returns `PUSHDOWN_ID`, `PUSHDOWN_INVOLVED_TABLES`, `PUSHDOWN_SQL`; prerequisite is "Privileges similar to the executed query". Exasol's own `exasol-virtual-schema` issue #24 shows a password echoed verbatim. |
| Can the adapter hand Exasol a value out of band? | No. `virtual-schema-common-java`'s `PushDownResponse` has ONE field; `ResponseJsonConverter` emits `{"type":"pushdown","sql":<string>}` and nothing else. No bind parameter, no placeholder, no second field. |
| Could a property or adapter note carry it? | No. `EXA_ALL_VIRTUAL_SCHEMA_PROPERTIES` and `EXA_ALL_VIRTUAL_TABLES.ADAPTER_NOTES` are documented "All users have access to the table" — worse than the SQL, not better. |
| Is `EXPLAIN VIRTUAL` the only surface? | Yes, for a rendered credential value. Verified live on 2025.2.1 (task 1.2), naming which principal read which view. **`EXA_USER_PROFILE_LAST_DAY`** — read by the LEAST-PRIVILEGE user itself, holding neither `ACCESS ANY CONNECTION` nor `SELECT ANY DICTIONARY` (both confirmed absent through `EXA_DBA_OBJ_PRIVS`): after `ALTER SESSION SET PROFILE = 'ON'`, its own marked query, and a DBA-issued `FLUSH STATISTICS`, that user selected 9 rows (one per execution-graph part: `COMPILE / EXECUTE`, `PUSHDOWN`, two `INSERT`, three `SCAN`, two `GROUP BY`), every row's `SQL_TEXT` byte-identical to its own literal statement, with no `LAKEHOUSE_SCAN` call and no credential value. **`EXA_DBA_AUDIT_SQL`** — NOT readable by that user at all: the same query was refused with `insufficient privileges for accessing view EXA_DBA_AUDIT_SQL`, SQL state `42500`. It requires `SELECT ANY DICTIONARY`, so it was never a least-privilege-reachable surface; read as `sys` it carried the same negative result. Both negatives confirmed against the SAME query's `EXPLAIN VIRTUAL` output, which DID carry both credential values. So `EXPLAIN VIRTUAL` and pushdown-path errors are the leak surfaces; profiling is reachable and carries nothing, and audit carries nothing and is not reachable either. |
| Can a UDF read a CONNECTION by name? | Yes, and it is the documented remedy. `hide_access_keys_passwords.htm`: a hardcoded secret is "visible in the audit tables, profiling tables, and in the `EXA_ALL_SCRIPTS` table"; carry the name and read it with `get_connection`. The SLC protocol request is `PB_IMPORT_CONNECTION_INFORMATION` (`zmqcontainer.proto`), language-agnostic; `exasol-udf-sdk` 0.23.0 exposes it as `UdfContext::connection` (`context.rs:217`) on the same trait the scan UDF receives. |
| Can the grant be narrowed to one script, and does it work with a RUNTIME-argument name? | Yes to both, verified live end to end on 2025.2.1 — see task 1.3a. A user holding only `CREATE SESSION`, `EXECUTE ON SCRIPT`, and `GRANT ACCESS ON CONNECTION c FOR SCRIPT s.p TO u` resolved the connection from inside the script with the name arriving as a VARCHAR argument; after the revoke the same call failed with `insufficient privileges for using connection c in script p`, SQL state `22001`. |
| Precedent for the change? | `exasol-virtual-schema` 4.0.0 closed issue #24 the same way — inline connection string replaced by a named `EXA_CONNECTION` — recording "The old variant is intentionally not supported anymore to tighten security." |

Two consequences follow. First, **redaction-at-render is not a fix**: there is one pushdown string, Exasol executes exactly the string it is given, so a placeholder for `EXPLAIN VIRTUAL` would still ship the real value into that same output and into pushdown-path error text — the two surfaces task 1.2 confirmed actually carry it (profiling and audit `SQL_TEXT` do not; they record only the user's own literal statement). Second, **a vended credential cannot be referenced at all**: it comes from the `loadTable` response, the UDF may not re-request it, and no name identifies it. It CAN, however, be SEALED: the reference machinery this plan builds gives the scan UDF an independent read of the same CONNECTION, and that read supplies key material both sides can derive identically — so the vended value crosses the one `sql` field as AES-GCM ciphertext instead of plaintext. That is how issue #378 is closed WITHIN this plan rather than deferred (§ Sealed vended envelope below).

**Sequencing.** Issue #135 was deferred behind the Azure ADLS work, whose static-credentials slice was to rework redaction into a per-variant `secret_values()` seam. That seam has landed (`crates/lakehouse-catalog/src/storage.rs:106-121`), `abfss://` support is in, and the named prerequisite #267 is merged, so the deferral condition is discharged and this plan lands on that seam.

- **Goals** — no CONNECTION-supplied storage credential in any generated SQL, on any builder path; no VENDED storage credential in PLAINTEXT in any generated SQL — the #378 residual closed by a sealed envelope keyed from the same CONNECTION, with the one uncoverable configuration (vending on a CONNECTION whose password carries no secret material) refused at plan time as a named decision; the guarantee enforced by a test on the rendered string, driven through the production selection function rather than through a hand-built fixture; the error-path redaction no weaker after the change than before, at every one of its seven feed sites; no catalog-authentication field constructible inside the scan UDF; the four adjacent same-class `Debug`/redaction exposures closed in the same change; every recorded feature whose credential claim this change falsifies given its own delta.
- **Non-Goals** — a cryptographic envelope guaranteeing confidentiality against a determined offline attacker holding the ciphertext: the sealed envelope's threat model is deliberately bounded to defeating plaintext reads of the pushdown SQL surfaces (§ Sealed vended envelope states the bound and why it is acceptable). Changing any credential SELECTION rule (SigV4 gate, vending gate, credential-source selection, longest-`prefix` match, CONNECTION-wins addressing, scheme-driven backend, plaintext consent gates); changing the scan-driving SQL's shape, the shard fan-out, or the per-shard file encoding; re-running CONNECTION acceptance validation inside the UDF; moving any function that interprets the Exasol CONNECTION object out of the adapter module; supporting a deployment that declines the new grant. Two earlier Non-Goals are REVERSED by this revision: "closing the vended residual (#378)" is now IN scope — the envelope's key derivation needs `ctx.connection()` in the scan UDF, which this plan builds anyway, so the prerequisite objection is gone; and "adding a cryptography dependency to the `.so`" no longer holds — the envelope needs AEAD + HKDF primitives, and § Dependencies names the crates and why the surface increase is small (`aes-gcm` and `sha2` are already in `Cargo.lock` transitively; only `hkdf` is new to the tree).

### Decision

Put the connection NAME where the credential used to be. Resolve it once, in the UDF, before any store is built, through a storage-only projection that cannot hold a catalog secret. Where a name cannot stand in for the value — the vended path — seal the value under a key both sides derive from that same CONNECTION, and refuse at plan time the one configuration where no key material exists.

The wire gains one wrapper. The catalog crate gains one storage-credential projection type and the one backend selector over it. The engine crate gains one sealing module (HKDF key derivation, AES-GCM seal/unseal) used by exactly two callers — the selection function at plan time and the resolution function at scan time. The scan gains one resolution step and one owner of the redaction secret set. Everything downstream of `ResolvedScanStorage` receives the same `StorageBackend` it receives today.

#### Sealed vended envelope (#378)

**Mechanism.** Under `use_vended_credentials`, the effective `StorageBackend` the planning layer resolves from the `loadTable` / Unity temporary-credentials response is serialized exactly as today, then encrypted with AES-256-GCM under a 32-byte key derived as HKDF-SHA256 over ikm = the CONNECTION password bytes exactly as `ctx.connection()` returns them, salt = empty, info = `"lakehouse-engine scan-storage sealed v1"` — with a fresh random 96-bit nonce per encryption operation. The wire carries `base64(nonce ‖ ciphertext)` beside the connection NAME in the `Sealed` variant. The scan UDF resolves the SAME CONNECTION through `ctx.connection(name)` — the identical grant-gated read the `Connection` variant already requires — derives the identical key from the password bytes, and opens the envelope. Key derivation reads the password BYTES without parsing them, so the structural exclusion of catalog-auth fields from the UDF (`StorageCreds` and its probe) is untouched: no `token`, `client_id`, or `client_secret` value is ever constructed inside the UDF.

**Wire shape, per mission.md's format-neutral rule.** The `Sealed` variant is format-neutral: its plaintext is the same `StorageBackend` encoding every format shares, its fields (`name`, `payload`) name no table format, and the scan side dispatches on the variant, never on format identity. Widening the existing `Inline` variant to carry the ciphertext was considered and declined: `Inline`'s plaintext payload remains the construction surface for the 28 host-test spec sites (task 3.1), and reusing one tag for two payload semantics would make "plaintext by design" and "ciphertext by design" indistinguishable on the wire — the same collapse of meaningful states decision [6] rejects for optional fields.

**Threat model — deliberately bounded, and stated as such wherever the guarantee is described.** This is NOT a maximum-security cryptographic envelope. The goal is to defeat a casual plaintext read or grep of the pushdown SQL — via `EXPLAIN VIRTUAL` output or pushdown-path error text (task 1.2 established live that profiling and audit `SQL_TEXT` carry only the user's own literal statement, never the VS-rewritten pushdown SQL, so those two surfaces were never a vector for either credential kind) — not to withstand a determined cryptanalytic attacker holding the ciphertext and unlimited compute against a low-entropy password. Two facts make the bound an acceptable, deliberate trade-off rather than an oversight: the protected values are SHORT-LIVED and SCOPE-LIMITED (vended per query, expiring on the catalog's own schedule, scoped to the prefix the catalog vended them for), and the key material is exactly the secret an attacker would need `ACCESS ON CONNECTION` to read — a grant whose holder can already read the credential outright.

**The gate that decides whether the envelope ships tests NON-EMPTINESS, not entropy.** One named predicate, `connection_password_carries_key_material` (`crates/lakehouse-engine/src/scan/sealed.rs`, beside `derive_sealed_storage_key`), reports TRUE iff at least one of the CONNECTION password's six secret-bearing fields is non-empty: `token`, `client_secret`, `secret_key`, `session_token`, `account_key`, or `sas_token`. A non-empty `access_key` alone does NOT satisfy it — an AWS access key id is an identifier, not a secret. A `token` of `"x"` DOES satisfy it, so the bound rests on two things: the threat model above AND the operator's own secret strength. The engine cannot measure the entropy of an arbitrary password without rejecting legitimate secrets, so it tests the property it can test and names the residual here rather than implying more.

**The criterion is the password's secret content, not the catalog-auth MODE — a deliberate widening of decision [14]'s original wording.** `deploy/scripts/install.sh:1425`'s own next-step template creates `LAKEHOUSE_CATALOG_CREDS` with `{"warehouse", "region", "access_key", "secret_key"}` and no catalog authentication. A mode-based criterion would classify that high-entropy password as no-auth and refuse the installer's own default shape as if it carried no key material. The password-content criterion admits it, refuses strictly less, and matches the rationale the refusal is sold on.

**Vending without key material is refused at plan time — a named decision, not a silent gap.** A CONNECTION password carrying none of the six secret-bearing fields — a no-auth catalog whose password holds only `{"warehouse":"…"}` is the canonical shape — yields a guessable key and would make the envelope a false guarantee, the exact objection under which decision-log entry [2] originally rejected the envelope. The refusal scopes the guarantee correctly instead of abandoning it, and it breaks no real or tested deployment: (a) the recorded orthogonality bullet (`specs/vs-adapter/pushdown-planning-cloud-credentials/spec.md:21-27`) states that vended extraction is gated solely on `use_vended_credentials` and that "the catalog-auth mode selects only how the table-load request is authenticated" — a code-path-uniformity statement, not an endorsement of every combination as a deployment shape; (b) this repo's own E2E matrix never exercises no-auth + vending together — vending is exercised only against the OAuth2-authenticated Lakekeeper + Keycloak stack, the authenticated Unity/Azure stacks, and the SigV4 Glue path, while the plain no-auth `iceberg-rest-fixture` stack uses static MinIO credentials with `use_vended_credentials: false` (`crates/lakehouse-engine/tests/common/seed.rs:279`, `tests/common/stack.rs:410`); (c) a catalog that vends real temporary cloud credentials to UNAUTHENTICATED callers is itself a broken catalog design, independent of this engine. The refusal is a clear `UdfError` at pushdown-planning time naming the combination and both remedies (configure catalog authentication, or disable `use_vended_credentials`) — never a silent fallback to plaintext, never a weakened key.

#### Patterns

| Pattern | Where | Why |
|---|---|---|
| Indirection by name | `ScanStorage::Connection` | The only channel the Exasol pushdown contract leaves open, and the one Exasol documents and used to fix its own leak |
| One pure function owns the variant choice | `scan_storage_for` | A choice made at three sites is a choice three sites can get wrong, and a test driving a hand-built template asserts on its own fixture rather than on the selection |
| Storage-only projection at the boundary | `StorageCreds` | A type with no catalog-auth field cannot carry one into the UDF; the guarantee is structural rather than a discipline six modules must honour |
| Resolve-once-at-the-boundary | `resolve_scan_storage` at the top of `run_scan` | Both join sides resolved in one step, so the redaction set is defined before any store exists and one CONNECTION is read once per invocation |
| Single owner of the secret set, and no way to read the wrong one | `ResolvedScanStorage::all_secret_values`; no `secret_values()` on `ScanStorage` | The set must follow the credential, and a wrapper accessor returning empty would compile at all five spec-reading sites and silently disarm redaction |
| Sealed envelope keyed by the same reference | `ScanStorage::Sealed`, `scan/sealed.rs` | A vended value has no name to reference, but the UDF's grant-gated `ctx.connection()` read — which the reference design builds anyway — supplies key material both sides derive identically, so the value crosses the one `sql` field unreadably instead of in plaintext |
| Refuse the configuration the guarantee cannot cover | `scan_storage_for` returning the named vending-without-key-material error | A guarantee conditional on key material must not ship for a password that carries none; a plan-time refusal is explicit where a weakened key would be a false promise |
| One home for the criterion the guarantee rests on | `connection_password_carries_key_material` in `scan/sealed.rs` | The question "is there key material here" and the derivation it gates belong to one module; splitting the test from the derivation lets a later change to one silently change what the other's error means |
| Guard on the type, not the site | redacting `Debug` on `StorageProps`, `StorageBackend`, `ConnectionCreds` | A `{:?}` added later cannot be caught by a test that does not exist yet |
| Positive control on every absence assertion | § Verification | An assertion that a secret is absent is satisfied by an empty surface; each one first proves its surface is populated |
| Assert on the rendered string | § Verification, all builder paths | A structural assertion stays green while the rendered SQL regresses |

### Consequences

| Decision | Alternatives Considered | Rationale |
|---|---|---|
| Reference the CONNECTION by name; UDF resolves it | Render a placeholder for `EXPLAIN VIRTUAL`; carry the credential in a property or adapter note; bind parameters | Placeholder rendering fixes only the demo surface — one `sql` string is both explained and executed, so profiling and audit still get the real value. Properties and adapter notes are documented readable by all users with access to the virtual schema. Bind parameters do not exist in the API: `PushDownResponse` has one field. |
| The scan derives from a storage-only projection; `parse_creds`/`storage_block` do NOT move | Move both into `lakehouse-catalog` and run `parse_creds` in the UDF; duplicate the derivation scan-side | `catalog-crate-structure:68` records that those six functions "SHALL stay in `lakehouse_engine::adapter::connection`, because they interpret the Exasol CONNECTION object and the catalog crate MUST NOT name that delivery mechanism". | No addressing on the wire for a referenced credential | Carry `endpoint`, `region`, `path_style`, `account_name` on the `Connection` variant beside the name | Two sources for one backend is how the "field-for-field EQUAL" guarantee breaks. ## Impact

**Breaking — every user that queries a virtual schema must hold the scan script's grant, directly or through a role.** The installer's template creates one deployment-scoped role (`LAKEHOUSE_ENGINE_ROLE_<schema>`), grants `ACCESS ON CONNECTION <connection> FOR SCRIPT <schema>.LAKEHOUSE_SCAN` to that role ONCE, and grants the role to the installing user; adding a further user is one `GRANT <role> TO <user>` statement, not a repeat of the connection grant. A direct per-user `GRANT ACCESS ON CONNECTION ... TO <user>` remains possible and is documented as the exception path, not the default. Either way it is per grantee, not once per deployment: every user needs the grant or the role, or their queries start failing at scan time. `PUBLIC` was evaluated and rejected as the grantee: live-verified that the script-scoped form (`FOR SCRIPT`) correctly denies a `PUBLIC`-granted user's OWN script from using the connection, so `PUBLIC` would have been SAFE on that axis, but it was rejected anyway because it grants every current AND FUTURE user on the instance access with no way to scope it later — a role can be revoked from one user without touching everyone else; `PUBLIC` cannot. No `ACCESS ON CONNECTION` grant is emitted or documented anywhere in this repository today — `deploy/scripts/install.sh`, `docs/install.md`, `docs/catalogs.md`, the E2E harness, and the recorded spec library contain none — so this is a new statement operators have no existing line to copy, not an addition beside one they already run. Whether the ADAPTER script also needs its own grant for a non-owning user is settled by task 1.3b. A deployment that upgrades without the grant plans successfully and fails at scan time with an error naming the connection and the missing access. There is deliberately no fallback. The grant now binds VENDED deployments too: the scan UDF resolves the CONNECTION on the sealed path to derive the envelope key, so a vended-only deployment is not exempt. The installer's next-step template emits the statement, and `docs/security.md` carries the grant model.

**Breaking — `use_vended_credentials` on a CONNECTION whose password carries no secret material no longer plans.** The gate tests the PASSWORD, not the catalog-auth mode: it passes when any of `token`, `client_secret`, `secret_key`, `session_token`, `account_key`, or `sas_token` is non-empty, so the installer's own default template (`{"warehouse", "region", "access_key", "secret_key"}` under a no-auth catalog) is admitted rather than refused. A password holding only `{"warehouse":"…"}` is refused, with a named error stating the configuration and both remedies (configure catalog authentication or supply the CONNECTION's own storage secret, or disable vending). § Sealed vended envelope records why this breaks no real or tested deployment; the refusal is a deliberate, named decision, not a silent gap.

**Breaking — `CREATE OR REPLACE CONNECTION` now silently revokes access.** Verified live on Exasol 2025.2.1: `CREATE OR REPLACE CONNECTION` DROPS a `GRANT ACCESS ON CONNECTION ... FOR SCRIPT` grant, while `ALTER CONNECTION ... IDENTIFIED BY` PRESERVES it. `deploy/scripts/install.sh`'s next-step template and `crates/lakehouse-engine/tests/common/stack.rs:370` both provision with `CREATE OR REPLACE CONNECTION`, so re-running the repo's own documented provisioning after this change breaks every scan until the grants are re-issued. The installer template carries a warning line, the harness issues its grant after the connection, and the rotation runbook recommends `ALTER`.

**Fixed — a `SELECT`-only user can no longer recover standing storage credentials from a query plan.** With vending disabled, the CONNECTION's `access_key`, `secret_key`, `session_token`, `account_key`, and `sas_token` no longer appear in the generated SQL, so they no longer appear in `EXPLAIN VIRTUAL` output or in an error raised on the pushdown path — the two surfaces task 1.2 confirmed actually carry it; profiling and audit `SQL_TEXT` never did. A user holding `ACCESS ON CONNECTION` gains nothing from the change: Exasol documents that grant as including "passwords/tokens", so such a user could already read the credential.

**Fixed, with a bounded guarantee — a vended credential no longer appears in plaintext in the generated SQL.** Under `use_vended_credentials` the credential comes from the `loadTable` or Unity temporary-credentials response, the UDF may not re-request it, and no name identifies it — so it still travels in the SQL, but ONLY inside the AES-GCM-sealed envelope of § Sealed vended envelope, keyed from the same CONNECTION the reference path resolves. This closes issue #378 within this plan. The guarantee is explicitly bounded: it defeats a plaintext read or grep of `EXPLAIN VIRTUAL` output and pushdown-path error text; it does not claim to withstand offline cryptanalysis of the ciphertext against a low-entropy password. Profiling and audit `SQL_TEXT` were verified live never to carry the rewritten pushdown SQL, so they are not a surface the envelope needs to defeat — acceptable because the vended values are short-lived and prefix-scoped, and because the key material is exactly what `ACCESS ON CONNECTION` already reveals. Issue #135 as filed names "the `access_key` and `secret_key` from the catalog CONNECTION" and quotes an `AKIA...` key — the standing-credential case the reference path closes — so #135's closure is against the case the issue reports and #378's closure is verified separately on the vended E2E path (task 1.5).

**Not contained, and named — the script-scoped grant delegates USE of the credential.** The connection name, the table root, and the file list all arrive as runtime arguments the caller controls, so a user who can query the virtual schema and holds the grant can point the UDF at an arbitrary path inside that storage account. The grant stops the grantee READING the credential through a script of their own, not USING it through this one. The delegated population is exactly the population that can query the virtual schema: `EXECUTE ON SCRIPT <schema>.LAKEHOUSE_SCAN` is NOT a separate prerequisite, verified live on 2025.2.1 (task 1.3a) by a user holding only `CREATE SESSION`, `SELECT ON SCHEMA <vs-schema>`, and the script-scoped connection grant — no `EXECUTE` privilege on anything, confirmed absent through `EXA_DBA_OBJ_PRIVS` — whose VS-pushdown query reached `LAKEHOUSE_SCAN` and returned rows. So the CONNECTION's credential should be scoped to the warehouse prefix. This is not a regression — today the same user can read the credential outright — but it is the boundary the fix leaves, and `docs/security.md` states it.

**Behavioural — a CONNECTION rotated mid-query is now observable per shard.** Previously a query's credentials were fixed when the adapter returned its SQL. Now each shard resolves the CONNECTION itself, so an `ALTER CONNECTION` landing between the adapter's read and a shard's read can leave one query reading some shards with the old values and others with the new — for the store `endpoint` and `region` as much as for the secret, because both are re-derived from the same read. The engine cannot close the window; a rotation is safe for in-flight queries only while the storage provider accepts both secrets. On the SEALED path the consequence is sharper: the envelope key is derived from the password, so a shard unsealing after a mid-query rotation fails with a named error rather than reading stale or wrong credentials — rotate when no vended query is in flight. `docs/security.md` § Rotation carries both procedures.

**Wire-format change.** The `storage` key of the shard-invariant common argument becomes a tagged wrapper with three variants: `connection` (static path), `sealed` (vended path, base64 nonce ‖ AES-GCM ciphertext of the backend encoding), and `inline` (host-test construction only; the adapter never emits it). The `.so`, SLC, and adapter deploy together and the scan script DDL is recreated per deployment, so no in-flight spec crosses a version boundary and no compatibility path is kept. Eighteen of the twenty-four committed golden pushdown-SQL fixtures are regenerated; the six `empty_*` fixtures carry no `storage` value and stay byte-identical.

**Unchanged.** Every credential selection rule; the scan-driving SQL's shape; the shard fan-out and its cap; the per-shard file encoding; projection, filter, LIMIT, aggregate, and join pushdown; the memory pool, batch size, and Parquet pruning flags; the CONNECTION password schema; the location of every function that interprets the Exasol CONNECTION object. No existing CONNECTION needs editing.

## Dependencies

The sealed vended envelope adds this repository's FIRST direct dependency on cryptographic primitives — a real, if small, new dependency surface, not free — to `crates/lakehouse-engine/Cargo.toml` `[dependencies]` (the sealing module and both its callers live in that crate; `lakehouse-catalog` gains nothing):

- `aes-gcm = "0.10"` (AES-256-GCM AEAD) — ALREADY in `Cargo.lock` transitively as 0.10.3 (via `iceberg`), so this pins no new code into the tree, only makes the use direct and reviewed.
- `hkdf = "0.12"` (HKDF key derivation) — the ONLY crate genuinely new to the dependency tree.
- `sha2 = "0.10"` (the HKDF hash) — already in `Cargo.lock` transitively as 0.10.9.
- `base64 = "0.22"` and `rand = "0.8"` — both already declared in this crate's `[dev-dependencies]` and already in `Cargo.lock`; PROMOTED to `[dependencies]` for the wire encoding and the per-encryption nonce respectively (`rand::rngs::OsRng` implements the `rand_core` 0.6 traits `aes-gcm` 0.10 consumes).

`ring` 0.17.14 is also already present transitively via the rustls TLS chain, but is not used here — the RustCrypto crates above match what the tree already carries and what the `rand`/`base64` pins compose with. This reverses the earlier Non-Goal "adding a cryptography dependency to the `.so`": that constraint existed to keep the deferred-#378 plan minimal, and it no longer holds once #378 is closed here. `exasol-udf-sdk` 0.23.0 already exposes `UdfContext::connection`, used today by the adapter at `crates/lakehouse-engine/src/adapter/connection.rs:57`; no other dependency changes.

## Rotation Runbook

Content for `docs/security.md` § Rotation, delivered as documentation because the engine holds no state to migrate. The one behavioural consequence is specified in `vs-adapter/scan-spec-credential-reference`, not here.

| Fact | Basis |
|---|---|
| Rotate in place with `ALTER CONNECTION <c> TO '<uri>' USER '<u>' IDENTIFIED BY '<json>'` | Verified live on Exasol 2025.2.1: the statement succeeded against a real CONNECTION and the `ACCESS ON CONNECTION ... FOR SCRIPT` grant SURVIVED — the least-privilege user resolved the rotated connection immediately afterwards. |
| Do NOT rotate with `CREATE OR REPLACE CONNECTION` | Verified live on the same container: the replacement DROPPED the script-scoped grant, and the same user's next call failed with `insufficient privileges for using connection <c> in script <p>`, SQL state `22001`. This is the form `deploy/scripts/install.sh` and `tests/common/stack.rs:370` use for PROVISIONING, so a re-provision requires re-issuing every grant. |
| No cache to invalidate, no restart, no redeployment | UDFs are stateless and every query re-resolves the CONNECTION. |
| The secret is not recoverable from the catalog afterwards | `EXA_DBA_CONNECTIONS` exposes `CONNECTION_NAME`, `CONNECTION_STRING`, `USER_NAME`, `PUBLIC_KEY`, `CREATED`, `CONNECTION_COMMENT` and no password column — verified live, and a least-privilege user is refused the view outright with SQL state `42500`. |
| Zero-downtime rotation requires the PROVIDER to accept both secrets | Exasol holds exactly one password per CONNECTION, so there is no overlap window on the Exasol side. Register the new secret at the identity provider or cloud account first, `ALTER` the CONNECTION second, revoke the old secret third. |
| In-flight queries may straddle the switch | Each scan shard resolves the CONNECTION itself, so both values must be valid for the duration of the longest running query. An `ALTER` that changes the store `endpoint` or `region` rather than the secret should be made when no query is in flight, because a later shard would read a different store. |
| A rotation invalidates the sealed envelopes of in-flight VENDED queries | The envelope key is derived from the password, so a shard unsealing after the rotation fails with a named error carrying no plaintext — it cannot read stale or wrong credentials. Rotate when no vended query is in flight. |
| A `client_secret` rotation is narrower than a storage-credential rotation | The catalog-auth secret never crosses the UDF boundary (`vs-adapter/connection-credentials-catalog-auth`), so only the adapter reads it, once per pushdown request. An already-minted bearer token stays valid for its own lifetime — that is the provider's contract, not the engine's. |
