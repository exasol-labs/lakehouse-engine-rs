## Summary

Stops the adapter leaking storage credentials through the generated pushdown SQL, closing **#135** (standing CONNECTION credentials) and **#378** (per-query vended credentials) in one plan.

**The defect.** The adapter serializes the resolved storage backend verbatim into the scan-driving SQL string (`adapter/pushdown/support.rs:441`), and Exasol echoes that one string verbatim to `EXPLAIN VIRTUAL` output and to any error raised on the pushdown path — a user holding only `SELECT` on the virtual schema can read a standing `access_key`/`secret_key` from either. (Verified live, task 1.2: profiling and audit `SQL_TEXT` — `EXA_USER_PROFILE_LAST_DAY`, `EXA_DBA_AUDIT_SQL` — do NOT carry it; both record only the user's own literal statement, never the VS-rewritten pushdown SQL.) The pushdown contract offers no second channel — the response is one `sql` field — so redaction-at-render cannot fix it.

**Standing credentials (#135) — reference, don't carry.** The scan spec's `storage` block now carries the NAME of the Exasol CONNECTION plus the resolved `ALLOW_HTTP` flag, nothing else. Each scan-UDF invocation resolves the CONNECTION itself via `ctx.connection()` — the remedy Exasol documents for exactly this problem — and derives the backend through a new storage-only, nine-field `StorageCreds` projection shared with the adapter, so no catalog-auth field (`token`, `client_secret`, …) is constructible inside the UDF and both readers derive field-for-field equal backends. Error-path redaction moves onto the resolved credentials (`ResolvedScanStorage::all_secret_values`, all seven feed sites); the wire type exposes no secret accessor, so a site left reading the unresolved value fails to compile.

**Vended credentials (#378) — seal what cannot be referenced.** A credential the catalog vends per query (`loadTable` / Unity temporary credentials) has no name to reference. It now travels in the SQL only inside an **AES-256-GCM envelope** keyed via HKDF-SHA256 from the same CONNECTION's password bytes (fresh random 96-bit nonce per encryption, `base64(nonce ‖ ciphertext)` on the wire beside the connection name). The scan UDF re-derives the identical key from its own grant-gated `ctx.connection()` read and opens the envelope; the password bytes feed HKDF unparsed, keeping the catalog-auth exclusion structural. **The threat model is deliberately bounded**: this defeats a plaintext read or grep of `EXPLAIN VIRTUAL` output and pushdown-path error text — it is not a maximum-security envelope against offline cryptanalysis of a low-entropy password. That bound is an acceptable, named trade-off because vended credentials are short-lived and scoped to the prefix the catalog vended them for, and the key material is exactly what the `ACCESS ON CONNECTION` grant already reveals.

**Vending on a CONNECTION whose password carries no secret material is refused at plan time.** The gate tests the PASSWORD content, not the catalog-auth mode: it refuses only when the password holds none of `token`, `client_secret`, `secret_key`, `session_token`, `account_key`, or `sas_token` (a bare `access_key` alone does not count — it's an identifier, not a secret). That combination fails the pushdown request with a named error stating all three remedies: configure catalog authentication, supply the CONNECTION's own storage secret, or disable `use_vended_credentials`. It breaks no real or tested deployment: the repo's E2E matrix exercises vending only against connections carrying real secret material, and this widened gate admits the installer's own default template shape (`{"warehouse","region","access_key","secret_key"}`) rather than refusing it. Recorded as a deliberate scoped decision, not a silent gap.

**Breaking changes for operators.**
- Every user needs the scan script's grant, directly or through a role. The installer template creates one deployment-scoped role, grants `ACCESS ON CONNECTION <c> FOR SCRIPT <schema>.LAKEHOUSE_SCAN` to it once, and grants the role to the installing user; a further user needs only `GRANT <role> TO <user>`. `PUBLIC` was evaluated and rejected live (safe on script-scoping, but ungovernable at scale — see decision-log [17]). Missing grant → clear scan-time error; deliberately no fallback. Vended deployments are included — the sealed path resolves the CONNECTION for its key too.
- `CREATE OR REPLACE CONNECTION` silently DROPS that grant (verified live on 2025.2.1); rotate with `ALTER CONNECTION` instead. Installer template, E2E harness, and a new `docs/security.md` carry the grant model and rotation runbook.
- Vending on a CONNECTION password with no secret material no longer plans (see above).
- A CONNECTION rotated mid-query is observable per shard; on the sealed path an in-flight vended shard fails decryption with a named error rather than reading mixed credentials.

**Dependencies.** First direct crypto dependency of the `.so`: `aes-gcm` 0.10 + `hkdf` 0.12 + `sha2` 0.10 in `crates/lakehouse-engine` (`aes-gcm` and `sha2` are already in `Cargo.lock` transitively; `hkdf` is the only crate new to the tree; `base64`/`rand` are promoted from dev-dependencies).

**Guarantees under test.** One selection-driven test drives every builder path under both vending settings with positive controls (connection name present for static; the sealed envelope present AND unsealing to the sentinel backend for vended) before asserting the sentinel absent; 18 golden fixtures regenerate to the reference encoding (the 6 `empty_*` stay byte-identical); a least-privilege E2E binary proves the query works and recovers no credential from `EXPLAIN VIRTUAL` or the revoked-grant error (profiling and audit are not asserted — verified live that neither ever carries the rewritten pushdown SQL); adjacent `Debug`/redaction exposures on `StorageProps`, `StorageBackend`, `ConnectionCreds`, and the SAS wire key are closed in the same change.
