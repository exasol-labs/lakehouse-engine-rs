## Premortem

Three ways this plan fails after shipping, each routed into a finding below.

1. **The library now lies.** Six deltas are recorded; roughly twenty recorded features keep asserting "Credentials MUST NOT appear in any returned SQL string", that the common blob "carries storage credentials", and that `parse_creds`/`storage_block` "SHALL stay in `lakehouse_engine::adapter::connection`". The next planner reads the library, plans on a false premise, and `speq audit` reports drift on a security feature. → R1, R2.
2. **The fix reopens the leak one field over.** `ctx.connection()` returns the whole CONNECTION password. Task 4.1 runs `parse_creds` over it inside the scan UDF, so `token` and `client_secret` — which `vs-adapter/connection-credentials-catalog-auth` records as never crossing the UDF boundary — now materialize on every shard, outside the storage-only redaction set the plan builds. → F2.
3. **The guarantee test was green from day one.** `no_connection_credential_reaches_the_generated_sql` builds its own spec template, so it asserts that its own fixture holds no sentinel. The adapter's join path (`joins/sql_builders.rs:603`, `:762`) still emits the static credential inline and no test sees it, because task 3.3 pointed at a file that does not exist. → T1, T2, F3.

#### [NFR_IGNORED] BLOCKER
- Location: plan.md § Implementation Tasks 4.1 and 2.1; `vs-adapter/scan-spec-credential-reference/spec.md` § Scenario "The scan UDF resolves the referenced CONNECTION", clause 1
- Issue: the plan moves the catalog-authentication secrets into the scan UDF process and never notices. `ctx.connection()` returns the whole CONNECTION password JSON, and task 4.1 applies "the moved `parse_creds`/`storage_block`" to it; `parse_creds` (`crates/lakehouse-engine/src/adapter/connection.rs:310-339`) populates `token`, `client_secret`, `client_id`, `oauth2_server_uri`, and `scope` on the resulting `ConnectionCreds`. - Fix: In plan.md § Key interfaces and task 4.1, make the scan-side derivation parse a storage-only projection of the CONNECTION password — a type declaring exactly `endpoint`, `region`, `access_key`, `secret_key`, `session_token`, `path_style`, `account_name`, `account_key`, `sas_token` — so no catalog-auth field is ever constructed inside the UDF, and add a source-level probe asserting that type names no field spelled `token`, `client_secret`, `client_id`, `oauth2_server_uri`, or `scope` (mirror the probe `pushdown-planning-cloud-credentials` already requires of `StaticStoreAddress`). Add a `DELTA:CHANGED` scenario to `vs-adapter/connection-credentials-catalog-auth` recording that the scan UDF reads the same CONNECTION and that the catalog-auth fields are structurally excluded from what it parses. Add the corresponding clause to `vs-adapter/scan-spec-credential-reference` § Scenario "The scan UDF resolves the referenced CONNECTION" and delete the now-false citation of that feature "already keeping them off the UDF boundary". Add a unit test asserting the scan-side derivation over a password carrying `client_secret` yields no value equal to it.

#### [NFR_IGNORED] ADVISORY
- Location: `vs-adapter/scan-spec-credential-reference/spec.md` § Background bullet 15 and § Scenario "The scan script requires its own script-scoped connection access grant", clause 3; plan.md § Impact
- Issue: the new privilege model delegates USE of the credential, and the residual is never named. The connection name and the file list both arrive as runtime arguments the caller controls, so any user who can execute `LAKEHOUSE_SCAN` and holds the script-scoped grant can hand-craft a `common` argument naming that CONNECTION with an arbitrary `table_root` and `files` list, and the UDF will resolve the credential and read whatever it is pointed at inside that storage account. The spec meanwhile asserts that the script-scoped form is chosen "because the script-scoped grant is what stops a user reading the credential through a script of their own" — true for reading the credential, false for using it. This is not a regression (today the same user can read the credential outright), but it is the boundary the fix leaves, and the plan's Impact presents the grant as a containment rather than a delegation.
- Fix: Add a `docs/security.md` section to task 7.4 stating that the script-scoped grant authorises the grantee to have `LAKEHOUSE_SCAN` use the credential on any path they name, that `EXECUTE` on `LAKEHOUSE_SCAN` therefore becomes security-relevant, and that the CONNECTION's credential should be scoped to the warehouse prefix. Add a corresponding Background bullet to `vs-adapter/scan-spec-credential-reference` naming the residual, so the spec does not overstate what the grant contains.
