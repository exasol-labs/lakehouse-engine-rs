# Feature: Connection-Object Credential Source

Lets the Virtual Schema read its catalog endpoint and object-storage credentials from a named Exasol CONNECTION object instead of plain VS properties, so credentials are managed and access-controlled by Exasol (never typed inline into `CREATE VIRTUAL SCHEMA`), and so the engine can authenticate to a cloud Iceberg REST catalog (AWS Glue, Databricks) and its backing object storage. The credential set carried by the CONNECTION selects WHICH storage backend the scan reads through whenever `use_vended_credentials` is false, selects whether requests to the catalog are AWS SigV4-signed, and selects whether the engine requests short-lived vended credentials at table-load time. Under vending, the CONNECTION's storage CREDENTIALS are ignored while its configured store `endpoint` and `region` participate in ADDRESSING; `vs-adapter/pushdown-planning-cloud-credentials` specifies the effective storage and the precedence between the two sources. The REST-catalog authentication
mode (none / static bearer token / OAuth2 client-credentials) is carried on the same
CONNECTION and specified by the sibling feature `connection-credentials-catalog-auth`.

## Background

* **This delta is issue #135. It adds no CONNECTION field, no parsing rule, and no guard, and changes no error text.** `ConnectionCreds` gains nothing and loses nothing; `validate_creds` gains no rule; the CONNECTION-to-backend selection rule keeps its behaviour. What changes is that the CONNECTION's NAME becomes part of the resolved configuration, and that the CONNECTION is read at SCAN time as well as at plan time whenever vending is disabled.
* **The description's standing promise is SATISFIED for the first time, by mechanism.** "The resolved password value MUST NEVER appear in any error message, returned SQL, or log line" was true for the password TEXT and false for the credentials parsed out of it: the selected backend was serialized verbatim into the scan-driving SQL literal. `vs-adapter/scan-spec-credential-reference` closes that for the vending-disabled path; the vended residual is issue [#378](https://github.com/exasol-labs/lakehouse-engine-rs/issues/378).
* **The connection NAME is added to the resolved configuration because it was being DISCARDED, not because it was unavailable.** `PROP_CATALOG_CONNECTION` is read at `crates/lakehouse-engine/src/adapter/mod.rs:208` on every request, and `get_properties` merges the request's properties with the persisted `schemaMetadataInfo.properties`. `ResolvedConnectionConfig` (`adapter/mod.rs:182-188`) simply carries no field for it. One field and one assignment.
* **A connection name is not a secret.** Exasol documents `EXA_ALL_VIRTUAL_SCHEMA_PROPERTIES` as "All users have access to the table", so the same name is already readable by any user with access to the virtual schema. Putting it in the generated SQL exposes nothing new — and the same fact is why a property or an adapter note cannot be the credential channel.
* **The CONNECTION is now read TWICE per query on the vending-disabled path, and the second read is a different actor under a different grant.** The adapter reads it to authenticate to the catalog and to resolve addressing; each scan shard reads it to reach object storage. Exasol's `ACCESS ON CONNECTION ... FOR SCRIPT` grant is per script, so a deployment must grant the SCAN script as well as the adapter script. `vs-adapter/scan-spec-credential-reference` owns that requirement and the mid-query-rotation consequence; this feature CITES it.
* **The scan-side read applies the DERIVATION and not the VALIDATION, deliberately.** `validate_creds` is parameterized by the resolved `CatalogKind` and decides whether a CONNECTION may be ACCEPTED for a virtual schema — a plan-time question the adapter already answered for this query. Re-running it in the UDF would require threading `CatalogKind` onto the wire for no new decision, and would turn a CONNECTION edited mid-query into a validation error rather than the storage access error it actually is.
* **The scan side reads a STORAGE-ONLY projection of the password, and the functions that interpret the Exasol CONNECTION object do NOT move.** `specs/vs-adapter/catalog-crate-structure/spec.md:68` records: "`read_connection`, `validate_creds`, `parse_creds`, `storage_block`, `catalog_block`, and `REQUIRED_KEY` SHALL stay in `lakehouse_engine::adapter::connection`, because they interpret the Exasol CONNECTION object and the catalog crate MUST NOT name that delivery mechanism." That clause is SATISFIED rather than superseded: all six stay. What the crate that already owns `ConnectionCreds`, `StorageProps`, and `StorageBackend` gains is a storage-credential PROJECTION type declaring exactly the nine storage fields, plus the ONE backend selector over it. `parse_creds` reads the nine storage spellings through that projection and `storage_block` becomes a projection-and-delegate, so one decision keeps one home and the scan path depends inward on a credential type rather than on the adapter module.
* **The projection is what keeps the catalog-auth fields out of the UDF.** `parse_creds` populates all seventeen `ConnectionCreds` fields, `token` and `client_secret` among them. A scan side that ran `parse_creds` would materialize those on every shard invocation. Deserializing a nine-field projection instead excludes them structurally — see `vs-adapter/connection-credentials-catalog-auth`.
* **No CONNECTION password field changes meaning, so every existing CONNECTION keeps working without edit.** An operator's only required change is the added grant.

### Scenario: Adapter reads catalog and storage credentials from a CONNECTION object

* *GIVEN* a `CREATE VIRTUAL SCHEMA` that supplies `CATALOG_CONNECTION = '<conn_name>'`
* *AND* an Exasol CONNECTION named `<conn_name>` whose address is the Iceberg REST catalog URI and whose password is a JSON object holding `warehouse`, `endpoint`, `region`, `access_key`, and `secret_key`
* *WHEN* the adapter handles a `createVirtualSchema` or `pushdown` request
* *THEN* the adapter SHALL call `ctx.connection('<conn_name>')` to obtain the credentials
* *AND* the adapter SHALL use the resolved address as the catalog URI and the parsed JSON password to build the catalog and storage configuration
* *AND* the adapter SHALL carry `<conn_name>` itself on the resolved configuration, so the pushdown planning layer can reference the CONNECTION by name under `vs-adapter/scan-spec-credential-reference` instead of embedding the credentials it supplied
* *AND* the adapter MUST NOT read `ACCESS_KEY`, `SECRET_KEY`, `SESSION_TOKEN`, `CATALOG_URI`, `S3_ENDPOINT`, or `S3_REGION` from plain VS properties when `CATALOG_CONNECTION` is present
* *AND* neither the resolved password text nor any credential parsed out of it SHALL appear in any error message or log line, and — when `use_vended_credentials` is false — neither SHALL appear in the returned SQL

### Scenario: One storage-credential projection and one selector serve both readers

* *GIVEN* the two readers of a CONNECTION on the vending-disabled path — the adapter at plan time, and the scan UDF at execution time under `vs-adapter/scan-spec-credential-reference`
* *WHEN* either reader turns a resolved CONNECTION password into a storage backend
* *THEN* exactly ONE storage-credential projection type — declaring EXACTLY `endpoint`, `region`, `access_key`, `secret_key`, `session_token`, `path_style`, `account_name`, `account_key`, and `sas_token` — and exactly ONE selector over it SHALL serve both readers, and neither reader SHALL carry its own copy of either
* *AND* that pair SHALL live in the crate that already owns `ConnectionCreds`, `StorageProps`, and `StorageBackend`, while `read_connection`, `validate_creds`, `parse_creds`, `storage_block`, `catalog_block`, and `REQUIRED_KEY` SHALL ALL STAY in the adapter module where `vs-adapter/catalog-crate-structure` pins them, so the scan path depends inward on a credential type and no function interpreting the Exasol CONNECTION object crosses the crate boundary
* *AND* the adapter's own CONNECTION-to-backend entry point SHALL reach that selector through the projection rather than re-implementing the selection, and the nine storage field spellings SHALL have exactly ONE reader, so the two readers cannot normalise an empty or absent field differently
* *AND* the backend the two readers derive from one CONNECTION password and one `allow_http` value SHALL be field-for-field EQUAL, asserted by a test over a password carrying every storage field, over one carrying empty strings, and over one omitting fields
* *AND* the scan-side reader SHALL apply the DERIVATION only and MUST NOT re-run the acceptance validation the adapter applies, because that validation is parameterized by the resolved `CatalogKind` and answers a plan-time question the adapter already answered for this query
* *AND* the selection rule — Azure when `account_name` is present with exactly one of `account_key` and `sas_token`, S3 otherwise — SHALL be UNCHANGED, so a CONNECTION resolves to the same backend it resolved to before this delta
* *AND* no supplied credential value SHALL appear in any error message, returned SQL, or log line from either reader
