# Feature: Scan-Spec Credential Reference

Replaces the storage credentials the adapter embedded verbatim in the scan-driving SQL with a REFERENCE to the Exasol CONNECTION that supplies them: the scan spec carries the connection NAME, and the scan UDF resolves the credentials at execution time through `ctx.connection()`. Closes issue #135 — a user holding only `SELECT` on the virtual schema could read a standing `access_key` and `secret_key` out of `EXPLAIN VIRTUAL` output, out of `EXA_USER_PROFILE_LAST_DAY.SQL_TEXT`, and out of any error raised on the pushdown path. A credential the planning layer resolves from the `loadTable` response rather than from the CONNECTION cannot be referenced this way and still travels inline; that residual is the tracked exception #378.

## Background

This feature is the ONE home for the four facts the other deltas of this change cite rather than restate: the pushdown response has exactly one `sql` field; profiling and audit carry that same SQL; the vended residual is #378; and the scoped credential claim that replaces every unscoped one.

* **The pushdown response carries exactly one field.** `virtual-schema-common-java`'s `PushDownResponse` serializes `{"type": "pushdown", "sql": <string>}` and nothing else. Every value the scan UDF needs either travels in that string or is resolved by the UDF itself. There is no bind parameter and no second field.
* **`EXPLAIN VIRTUAL` returns that string verbatim with no redaction.** Its documented privilege prerequisite is "Privileges similar to the executed query", and Exasol's own `exasol-virtual-schema` issue #24 shows a password echoed in that output.
* **`EXPLAIN VIRTUAL` is not the only surface, which is why redaction-at-render was rejected.** `EXA_USER_PROFILE_LAST_DAY` carries a `SQL_TEXT` column and Exasol documents it as "All users have access to the table", holding the user's OWN sessions with profiling enabled; `EXA_DBA_AUDIT_SQL` carries `SQL_TEXT` under `SELECT ANY DICTIONARY`, with auditing enabled by default. Both were confirmed live on Exasol 2025.2.1: a user holding neither `ACCESS ANY CONNECTION` nor `SELECT ANY DICTIONARY` selected its own profiled statement's full `SQL_TEXT` from `EXA_USER_PROFILE_LAST_DAY`, while the same user was refused `EXA_DBA_CONNECTIONS` with SQL state `42500`.
* **The scoped credential claim.** A CONNECTION-supplied storage credential MUST NOT appear in any returned SQL string. A VENDED storage credential DOES appear there, the tracked exception issue [#378](https://github.com/exasol-labs/lakehouse-engine-rs/issues/378). No credential of either kind appears in an error message. Every recorded feature whose Background carried an UNSCOPED "credentials MUST NOT appear in any returned SQL" claim is superseded by its own delta in this plan and reads as scoped by this bullet.
* **An unscoped guarantee in a security spec is worse than a scoped one**, because the next reader trusts it and stops looking. This is why the claim above names the exception instead of asserting the stronger sentence.
* **The remedy is the pattern Exasol documents for this problem, and the pattern Exasol used to fix its own leak.** `hide_access_keys_passwords.htm` states that hardcoded credentials "are stored in cleartext and are visible in the audit tables, profiling tables, and in the `EXA_ALL_SCRIPTS` table", and directs that a script carry only the connection NAME and read the secret through `get_connection`. `exasol-virtual-schema` 4.0.0 closed issue #24 by deleting an inline connection-string property in favour of a named `EXA_CONNECTION`.
* **This feature discharges the `ponytail:` debt marker that named it.** `crates/lakehouse-engine/src/adapter/pushdown/mod.rs:128-133` records the leak as a "PoC-accepted tradeoff" and names the upgrade path as passing "credentials via a CONNECTION object (referenced by name, never inlined)". The marker is DELETED rather than reworded, because the tradeoff it accepted no longer stands.
* **The scan UDF resolving a CONNECTION is NOT the forbidden catalog round-trip.** `ctx.connection()` contacts neither the catalog nor object storage: it is one engine-local metadata request over the script-language-container protocol (`PB_IMPORT_CONNECTION_INFORMATION` in Exasol's `zmqcontainer.proto`), answered by the database from its own catalog. No file is discovered, no snapshot is read, and no token is minted, so `datafusion-scan/scan-execution-memory-and-credentials`' prohibition and `specs/mission.md`'s resolve-once rule are both satisfied.
* **One engine-local lookup per shard invocation replaces a credential carried in every copy of the SQL.** Shard count is capped at 300 (`specs/udf-context.md`) and the lookup is synchronous and local. The alternative — resolving once and broadcasting the result — is the leak itself.
* **The reference is `CATALOG_CONNECTION`'s value, a virtual-schema property the adapter already reads on every pushdown request.** `PROP_CATALOG_CONNECTION` is read at `crates/lakehouse-engine/src/adapter/mod.rs:208` and `get_properties` merges the request's properties with the persisted `schemaMetadataInfo.properties`. `ResolvedConnectionConfig` currently DISCARDS it, so this feature adds one field and one assignment.
* **A connection NAME is not a secret.** The same name is already readable by any user with access to the virtual schema through `EXA_ALL_VIRTUAL_SCHEMA_PROPERTIES`, documented as "All users have access to the table". This is also why a schema property and an adapter note are NOT usable as the credential channel: both are persisted server-side and readable at that same level.
* **The grant that makes the reference safe is `ACCESS ON CONNECTION ... FOR SCRIPT`, and the whole mechanism was verified live on Exasol 2025.2.1.** A user holding `CREATE SESSION`, `EXECUTE` on one script, and `GRANT ACCESS ON CONNECTION <c> FOR SCRIPT <schema>.<script> TO <u>` — and holding neither `ACCESS ON CONNECTION` nor `ACCESS ANY CONNECTION` — resolved that CONNECTION from inside the script with the connection name arriving as a RUNTIME VARCHAR ARGUMENT, obtaining the address, the user, and the password. After `REVOKE ACCESS ON CONNECTION <c> FOR SCRIPT <schema>.<script> FROM <u>`, the same call failed with `insufficient privileges for using connection <c> in script <script>`, SQL state `22001`, naming the connection and the script and carrying no credential value.
* **The plain `ACCESS ON CONNECTION` grant "includes passwords/tokens"**, so a user holding it can already read the credential and gains nothing from the leak. A user holding only `SELECT` on the virtual schema is the attacker issue #135 describes.
* **The script-scoped grant delegates USE of the credential, and that residual is named rather than presented as containment.** The connection name, the table root, and the file list all arrive as runtime arguments the caller controls. A user who can execute `LAKEHOUSE_SCAN` and holds the script-scoped grant can hand-craft a `common` argument naming that CONNECTION with an arbitrary `table_root` and `files` list, and the UDF will resolve the credential and read whatever it is pointed at inside that storage account. The grant stops the grantee READING the credential through a script of their own; it does not stop them USING it through this one. `EXECUTE` on `LAKEHOUSE_SCAN` is therefore security-relevant, and the CONNECTION's credential SHOULD be scoped to the warehouse prefix. This is not a regression — today the same user can read the credential outright — but it is the boundary the fix leaves, and `docs/security.md` carries it.
* **The required grant is a BREAKING deployment change.** A deployment that upgrades without granting the scan script access to the CONNECTION gets a clear scan-time error, not a wrong result and not a silent fall back to inline credentials. A fallback was rejected: a code path that reads inline credentials when the grant is absent keeps the leak reachable for every deployment that never adds the grant, which is every existing one.
* **`CREATE OR REPLACE CONNECTION` DROPS the script-scoped grant; `ALTER CONNECTION` PRESERVES it.** Both verified live on Exasol 2025.2.1 against a real grant and a real least-privilege user. This matters because `deploy/scripts/install.sh` and `crates/lakehouse-engine/tests/common/stack.rs:370` both provision with `CREATE OR REPLACE CONNECTION`, so re-running the repo's own provisioning after this feature lands revokes the grant and breaks every scan until it is re-issued.
* **The redaction secret set MOVES from the wire spec to the RESOLVED credentials, and this is the feature's one correctness trap.** SEVEN sites in `crates/lakehouse-engine/src/scan/` build a redaction secret set today. Two read the union off the spec — `object_store.rs:66` and `join_scan.rs:48`, both `spec.common.all_secret_values()`. Three read the fact side off the spec directly — `partial_agg.rs:70`, `partial_agg.rs:125`, and `raw_scan.rs:54`, each `spec.common.storage.secret_values()`. Two already take a `&StorageBackend` parameter and are fed by their callers — `raw_scan.rs:224` (`register_file_list`) and `positional_deletes.rs:629` (`PositionalDeleteScanTable::new`). Once the spec's storage block holds a NAME, the five spec-reading sites have no secret to yield, and the natural way to make them compile — a `secret_values()` on the wire wrapper returning empty for the reference variant — compiles, keeps every existing test green, and silently disarms value-based redaction on the raw-scan and partial-aggregate error paths. The wire wrapper therefore exposes no such method at all, so those five sites fail to COMPILE rather than yielding an empty set.
* **Resolution happens ONCE per scan invocation, before any store is built, for both join sides.** A join spec carries a storage block per side (`datafusion-scan/scan-execution-join`), so a resolved PAIR is what the scan path threads. Resolving lazily at each store-construction site would read the same CONNECTION twice per invocation and leave the redaction set undefined between the two reads.
* **The scan side derives the backend from a STORAGE-ONLY projection of the CONNECTION password, so no catalog-auth field is ever constructed inside the UDF.** `parse_creds` populates all seventeen `ConnectionCreds` fields, `token`, `client_id`, `client_secret`, `oauth2_server_uri`, and `scope` among them. Applying it inside the UDF would materialize those five values on every shard invocation, outside the storage-only redaction set, and would falsify `vs-adapter/connection-credentials-catalog-auth`'s recorded "they never cross the UDF boundary". The UDF instead deserializes a type declaring EXACTLY the nine storage fields and derives the backend from that.
* **A CONNECTION read at plan time and again at scan time can be read across a rotation, and the widening is deliberate.** Before this feature a query's credentials were fixed when the adapter returned its SQL. Now the planning layer reads the CONNECTION to authenticate to the catalog and each shard reads it again to reach storage, so an `ALTER CONNECTION` landing between those reads is observable and different shards of one query may read different values. The engine cannot close the window: it holds no state, and pinning a credential for the query's lifetime means carrying it in the SQL, which is the leak.
* **A vended credential cannot be referenced, so it stays inline, TRACKED as issue #378.** Under `use_vended_credentials` the effective credentials come from the `loadTable` or Unity temporary-credentials response and the UDF may not re-request them, so no name identifies them. The residual is materially narrower than what closes: a vended credential expires and is scoped to the prefix the catalog vended it for, while a CONNECTION `secret_key` is long-lived and account-wide. Issue #378 records the candidate remediations and why none is chosen here.
* **The two variants are selected by the gate that ALREADY decides which resolver runs.** `use_vended_credentials` chooses between the static derivation and `resolve_vended_storage` today. It now also chooses the wire variant, through ONE pure function, so a variant that disagreed with the resolver that produced it is unreachable.
* Adjacent same-class exposures on the ERROR path are closed by this feature rather than left standing beside a fixed SQL path: `StorageProps` and the `StorageBackend::S3` arm derive `Debug` and print `access_key`, `secret_key`, and `session_token` verbatim (`crates/lakehouse-catalog/src/creds.rs:182`, `storage.rs:80`) where the `Adls` arm has a redacting manual `Debug`; `redact_credentials`' label list omits the `AdlsCred::Sas` wire key, which `serde(rename_all = "snake_case")` spells `sas`, so a serialized SAS reaching one of the nine value-blind call sites survives the label pass; and `crates/lakehouse-catalog/src/auth.rs:93` and `:160` compose the two redaction passes in the order `crates/lakehouse-catalog/src/redaction.rs:91-97` documents as broken for SAS tokens.
* The scan-driving SQL's shape, the shard fan-out, the per-shard file encoding, projection, filter, LIMIT, aggregate, and join pushdown are all UNCHANGED. Only the `storage` block of the shard-invariant common argument changes shape.

## Scenarios

### Scenario: The scan spec references the CONNECTION by name instead of carrying its credentials

* *GIVEN* a virtual schema whose CONNECTION credentials omit `use_vended_credentials` or set it to false, supplying either static S3 storage fields or `account_name` plus exactly one of `account_key` and `sas_token`
* *WHEN* the adapter builds the scan-driving SQL for any pushdown request shape
* *THEN* the shard-invariant common scan-spec argument SHALL carry the value of the `CATALOG_CONNECTION` virtual-schema property as the storage reference, together with the resolved `ALLOW_HTTP` value, and SHALL carry no other field
* *AND* the generated SQL MUST NOT contain the CONNECTION's `access_key`, `secret_key`, `session_token`, `account_key`, or `sas_token` value, in any encoding
* *AND* the store `endpoint`, `region`, `path_style`, and ADLS `account_name` MUST NOT appear in the generated SQL for a referenced credential either, and SHALL be re-derived by the UDF from the same CONNECTION, so the addressing and the secret cannot come from two different reads
* *AND* the reference SHALL be carried ONCE in the shard-invariant common argument and MUST NOT be repeated per shard, because it is invariant across the fan-out
* *AND* a join spec SHALL carry a storage reference PER SIDE, so the fact side's and the dimension side's references travel independently even when both name the same CONNECTION

### Scenario: One pure function selects the wire variant for every builder path

* *GIVEN* the resolved connection configuration for a pushdown request — its `ConnectionCreds`, its `CATALOG_CONNECTION` name, and the resolved `ALLOW_HTTP` value — and the effective storage backend the format reader resolved for one side
* *WHEN* the adapter populates a scan spec's storage block, on the single-table path or on either side of a join
* *THEN* exactly ONE pure function SHALL make the choice, taking those four inputs and returning the wire wrapper, and every site that populates a storage block SHALL call it rather than construct a variant itself
* *AND* that function SHALL return the REFERENCE variant when `use_vended_credentials` is false and the INLINE variant carrying the effective backend when it is true, so the variant can never disagree with the resolver that produced its payload
* *AND* the format readers' own vended/static split SHALL be UNCHANGED and MUST NOT return the wrapper, because each reader uses the concrete backend immediately for its own plan-time manifest or log read
* *AND* the guarantee test SHALL drive every builder path with a spec template produced by THAT function from credentials carrying sentinel values, under both settings of `use_vended_credentials`, so the assertion observes the SELECTION rather than its own fixture

### Scenario: The scan UDF resolves the referenced CONNECTION without contacting the catalog

* *GIVEN* a scan UDF invocation whose shard-invariant common spec argument carries a storage reference naming a CONNECTION
* *WHEN* the UDF prepares to read its assigned files
* *THEN* the UDF SHALL call `ctx.connection()` with the referenced name and SHALL deserialize the returned `password` into a STORAGE-ONLY projection declaring EXACTLY `endpoint`, `region`, `access_key`, `secret_key`, `session_token`, `path_style`, `account_name`, `account_key`, and `sas_token`
* *AND* the UDF MUST NOT construct any value carrying a catalog-authentication field, so `token`, `client_id`, `client_secret`, `oauth2_server_uri`, and `scope` are structurally excluded from what the UDF parses rather than parsed and discarded, and a source-level probe SHALL assert that the projection's own declaration names no field with any of those five spellings
* *AND* the UDF SHALL derive the storage backend from that projection and the carried `ALLOW_HTTP` value through the SAME single backend selector the adapter reaches, so a referenced and an inline backend for one CONNECTION are field-for-field equal
* *AND* the UDF SHALL perform this resolution EXACTLY ONCE per invocation, before it builds any object store, and SHALL resolve BOTH sides of a join spec in that one step
* *AND* when the referenced CONNECTION cannot be resolved — it does not exist, or the invoking user's grants do not reach it through this script — the UDF SHALL return a `UdfError` naming the connection name and the missing access, MUST NOT fall back to any inline credential, and MUST NOT panic, because a panic inside a UDF is an abnormal VM exit that makes the engine SIGKILL every sibling VM of the statement part

### Scenario: Error redaction reads its secret set from the resolved credentials, not from the wire spec

* *GIVEN* a scan invocation whose storage reference resolves to a backend holding a credential, on a single-table spec or on either side of a join spec
* *WHEN* the UDF raises any error while building an object store, running a raw scan, running a partial aggregate, reading a data file, reading a positional-delete file, or applying a deletion vector
* *THEN* the value-based redaction applied to that message SHALL take its secret set from the RESOLVED storage backends and MUST NOT take it from the scan spec's own storage block, at EVERY site that builds such a set
* *AND* the wire wrapper MUST NOT expose any method returning secret values or a credential payload, so a site left reading the unresolved wire value fails to COMPILE rather than yielding an empty set
* *AND* the secret set for a join spec SHALL be the UNION of both sides' resolved secrets, so a message raised while either side's credential is in scope is redacted for both
* *AND* the raw-scan and partial-aggregate error paths SHALL each be covered by a test asserting that a resolved credential value is stripped from an error raised on that path, because those two paths read the fact-side set directly and are where an empty set would go unnoticed
* *AND* no resolved credential value SHALL appear in any error message the UDF returns

### Scenario: A vended credential still travels inline and the residual is a tracked exception

* *GIVEN* a virtual schema whose CONNECTION credentials set `use_vended_credentials` to true
* *WHEN* the adapter builds the scan-driving SQL after resolving the effective scan storage from the `loadTable` or Unity temporary-credentials response
* *THEN* the common scan-spec argument SHALL carry the resolved storage backend INLINE, and the vended credential SHALL appear in the generated SQL
* *AND* this residual exposure SHALL be recorded as the tracked exception issue [#378](https://github.com/exasol-labs/lakehouse-engine-rs/issues/378), cited here, and MUST NOT be presented as closed by this feature
* *AND* the adapter MUST NOT emit a reference variant under vending, because no CONNECTION name identifies a credential the catalog vended for one table
* *AND* the scan UDF MUST NOT call `ctx.connection()` for an inline variant, because the inline payload is complete and a lookup would impose the new grant requirement on a path that does not need it

### Scenario: The generated SQL is asserted credential-free at every builder path

* *GIVEN* the single site that interpolates the serialized common scan spec into the scan-driving SQL, and the builder paths that reach it — every `RequestShape` variant crossed with the join, top-N, and `COUNT(DISTINCT)` sub-paths, cross-checked against the eighteen credential-bearing golden fixtures
* *WHEN* the adapter renders the SQL for a CONNECTION supplying static storage credentials whose values are distinctive test sentinels
* *THEN* a test SHALL assert, for every one of those builder paths, that no sentinel credential value appears anywhere in the returned SQL string, and SHALL assert POSITIVELY that the connection NAME is present in that same string, so a path whose fixture seeded nothing fails instead of passing vacuously
* *AND* that assertion SHALL be made on the returned SQL STRING rather than on the scan-spec structure alone, because the structure is what a later change would keep valid while the rendered string regressed
* *AND* the eighteen credential-bearing golden pushdown-SQL fixtures SHALL be regenerated so that each contains the reference encoding and no credential value, while the six `empty_*` fixtures carry no `storage` value at all and SHALL stay byte-identical and be asserted unchanged
* *AND* the builder-path list SHALL be DERIVED and stated in this feature rather than asserted as a count, so a later reader can verify coverage against the fixture names instead of trusting a number
* *AND* the assertion MUST NOT be weakened to a claim that the SQL contains no credential AT ALL, because a vended credential still appears there under issue #378

### Scenario: The scan script requires its own script-scoped connection access grant

* *GIVEN* a deployment whose adapter script already holds access to the catalog CONNECTION, which `vs-adapter/connection-credentials` requires for the adapter to resolve it at all
* *WHEN* an operator installs or upgrades to a build carrying this feature
* *THEN* the deployment SHALL additionally require that the scan script reach the same CONNECTION, granted as `GRANT ACCESS ON CONNECTION <connection> FOR SCRIPT <schema>.LAKEHOUSE_SCAN TO <user-or-role>`, held by EVERY user or role that queries the virtual schema rather than once per deployment
* *AND* the installer's next-step template SHALL emit that grant beside the `CREATE CONNECTION` and `CREATE VIRTUAL SCHEMA` statements it already emits, and SHALL warn that re-running the `CREATE OR REPLACE CONNECTION` drops the grant and requires re-issuing it
* *AND* the script-scoped form SHALL be the form documented and emitted, and the blanket `ACCESS ANY CONNECTION` system privilege MUST NOT be, because the script-scoped grant is what stops a user reading the credential through a script of their own — while USE of the credential through this script is delegated to the grantee, as this feature's Background states
* *AND* a deployment missing that grant SHALL fail with the scan-time error named above, and MUST NOT silently read through an inline credential
* *AND* a user who holds `SELECT` on the virtual schema but holds neither `ACCESS ON CONNECTION` for that connection nor `ACCESS ANY CONNECTION` SHALL be able to run the query and MUST NOT be able to recover any credential value from `EXPLAIN VIRTUAL` output, from `EXA_USER_PROFILE_LAST_DAY.SQL_TEXT` for their own session, or from any error the query returns

### Scenario: A CONNECTION rotated while a query is in flight is observed per shard

* *GIVEN* a query whose adapter has returned its pushdown SQL and whose shard invocations have not all completed
* *AND* an `ALTER CONNECTION` that replaces the referenced CONNECTION's password, its address, or its storage addressing between the adapter's read and a shard's read
* *WHEN* the remaining shards resolve the reference
* *THEN* each shard SHALL read whichever value the CONNECTION holds at the moment of ITS OWN resolution, so one query MAY read some shards with the pre-rotation values and others with the post-rotation values — for the store `endpoint` and `region` as much as for the secret, because both are re-derived from the same read
* *AND* the engine MUST NOT pin either the credential or the addressing for the query's lifetime, because pinning them means carrying them in the generated SQL, which is the exposure this feature closes
* *AND* a shard whose resolved credential or addressing the storage provider rejects SHALL fail with the storage backend's own access error carrying no credential value, rather than retrying with another value
* *AND* the operator-facing consequence — that a rotation is safe for in-flight queries only while the storage provider accepts BOTH the old and the new secret, and that an addressing change should be made when no query is in flight — SHALL be stated in the operator documentation, because the engine holds no state with which to make it safe on its own
