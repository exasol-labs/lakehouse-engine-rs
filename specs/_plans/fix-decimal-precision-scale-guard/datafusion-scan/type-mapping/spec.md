# Feature: DataFusion-to-Exasol Type Mapping

Defines the single authoritative mapping from DataFusion/Arrow column types to Exasol SQL types, and the companion Iceberg-to-Arrow mapping used to build the logical schema the scan registers, so that every column an Iceberg table exposes is queryable through Exasol.

## Background

* **This delta adds ONE scenario and is issue #329.** It records the guard that decides whether a CATALOG-DECLARED decimal — an Iceberg `PrimitiveType::Decimal` or a Unity Catalog `DECIMAL` — becomes an Exasol `DECIMAL(p,s)` or the `VARCHAR(2000000)` fallback. Before this delta the guard admitted two precision/scale pairs Exasol cannot express, so `createVirtualSchema` declared an invalid column type instead of falling back.
* **The catalog-sourced guard is NARROWER than the Arrow row of the recorded mapping table, and the two are deliberately different.** The table's `Decimal128(p,s) where p≤36 and s≤36` row governs `arrow_to_exasol_type` and stays byte-identical; it is NOT amended. The catalog-sourced guard additionally requires `1 ≤ p` and `s ≤ p`. A reader MUST NOT read the Arrow row as governing catalog wire input.
* **Exasol's `DECIMAL(p,s)` domain is `1 ≤ p ≤ 36` and `0 ≤ s ≤ p`.** The `p ≤ 36` half was already enforced; the `1 ≤ p` and `s ≤ p` halves were not. `p = 0` yielded the invalid `DECIMAL(0,0)` and `s > p` yielded an invalid shape such as `DECIMAL(5,10)`. Both are rejected by Exasol, so the enumeration failed rather than falling back — the failure mode the VARCHAR fallback exists to prevent. This delta's implementation is gated on a live capture of both rejections against the Docker Exasol container, per CLAUDE.md § Verification discipline, rather than on documented limits alone.
* **Apache Iceberg spec check — the spec does NOT forbid either bad pair, which is why the guard cannot assume a well-formed catalog.** The Primitive Types table states `decimal(P,S)` as "Fixed-point decimal; precision P, scale S" with the single constraint "Scale is fixed, precision must be 38 or less". That row states NO lower bound on `P` and NO relation between `S` and `P`. Schema evolution adds only "`decimal(P, S)` … `decimal(P', S)` if `P' > P` … Widen precision only". Appendix A maps `decimal(P,S)` to Avro `{ "type": "fixed", "size": minBytesRequired(P), "logicalType": "decimal", "precision": P, "scale": S }` and to Parquet `P <= 9`: `int32`, `P <= 18`: `int64`, `fixed` otherwise annotated `DECIMAL(P,S)`; Appendix C serializes the type as the JSON string `"decimal(<P>,<S>)"`. On the spec's own normative text a catalog serving `decimal(0,0)` or `decimal(5,10)` violates nothing, so "only a misbehaving catalog produces it" is NOT a sound basis for the guard — the Exasol target-type limitation is.
* **Mapping such a decimal to `VARCHAR(2000000)` is an Exasol target-type trade-off, named here rather than left silent.** It is the same class as the already-recorded `p > 36 → VARCHAR` fallback: Exasol has no `DECIMAL` with `p = 0` or `s > p`, exactly as it has none with `p > 36`. The column stays queryable as a JSON-serialized string, so nothing is dropped or left untyped, and this is NOT a tracked exception requiring a follow-up issue.
* **iceberg-rust does not enforce the bound on the deserialization path, verified in the vendored source.** `iceberg 0.10.0`'s `Type::decimal` and `Type::decimal_required_bytes` (`src/spec/datatypes.rs`) both assert `precision > 0 && precision <= MAX_DECIMAL_PRECISION`, but `deserialize_decimal` (same file) bypasses both: it splits the `decimal(P,S)` string and builds `PrimitiveType::Decimal { precision, scale }` directly from two `u32` parses with no bound check, so `"decimal(0, 0)"` and `"decimal(5, 10)"` in table metadata deserialize without complaint. Because both fields are `u32`, a NEGATIVE scale cannot be represented at all and needs no guard.
* **Reachability is low and stated as such, not as impossible.** Delta requires `s ≤ p`, and Unity Catalog documents `type_precision`/`type_scale` as required for a decimal — but the Unity client's `neutral_column` (`crates/lakehouse-catalog/src/unity/client.rs`) resolves an absent `type_precision` through `.unwrap_or(0)`, so a `DECIMAL` column with a null `type_precision` on the wire reaches the mapping as `p = 0` with no misbehaving catalog required beyond an omitted field.
* **Two same-shaped guards elsewhere are deliberately left alone, so their omission reads as a decision rather than an oversight.** `arrow_to_exasol_type`/`compatible_exasol_type` take Arrow `Decimal128(u8, i8)`, whose scale is SIGNED and legitimately negative, and are fed by DataFusion's own schema rather than by catalog wire input — a shared helper over `(u32, u32)` cannot express that domain, so folding them in needs casts and buys nothing. `exasol_type_from_json` reads `u64` precision and scale out of Exasol's own `dataType` JSON on a pushdown request; Exasol produces that JSON from a type it already accepted, and once this delta lands no invalid decimal can be declared for it to echo back.

### Scenario: A catalog-declared DECIMAL outside Exasol's DECIMAL domain falls back to VARCHAR

* *GIVEN* a column whose catalog-declared type is a decimal carrying an unsigned precision `p` and an unsigned scale `s` — an Iceberg `PrimitiveType::Decimal { precision, scale }` or a Unity Catalog `DECIMAL` whose `type_precision`/`type_scale` the neutral column carries
* *WHEN* the adapter resolves that column's Exasol type for the `createVirtualSchema` declaration
* *THEN* the resolver SHALL return `DECIMAL(p,s)` if and only if `1 ≤ p ≤ 36` AND `s ≤ p`, and SHALL return `VARCHAR(2000000)` otherwise, so `p = 0` yields `VARCHAR(2000000)` rather than the invalid `DECIMAL(0,0)` and `s > p` yields `VARCHAR(2000000)` rather than an invalid shape such as `DECIMAL(5,10)`
* *AND* exactly ONE function in `crates/lakehouse-engine/src/types/mapping.rs` SHALL own that predicate and both returned strings, and BOTH catalog kinds SHALL read their answer from it rather than each carrying its own copy — the guard is the significant design decision here, and a second copy is what let the two kinds agree by coincidence rather than by construction — and that function SHALL be declared PRIVATE to `types/mapping.rs`, because its only consumers are the Iceberg and Unity arms in that same file and hiding the predicate entirely is what makes the module deep
* *AND* the guard MUST NOT carry a separate `s ≤ 36` test, because `s ≤ p` and `p ≤ 36` already imply it and a redundant third condition invites the halves to drift, and MUST NOT carry a lower-bound test on `s`, because both catalog-sourced fields are unsigned and a negative scale is unrepresentable — unlike the Arrow `Decimal128(u8, i8)` path, which this scenario does NOT govern
* *AND* the resolver MUST NOT fail, return a `Result`, or abort the enumeration on either bad pair — the `VARCHAR(2000000)` fallback absorbs them exactly as it absorbs `p > 36`, keeping `column_source_type_to_exasol` and `build_listing_virtual_tables` infallible
* *AND* every pair already mapped SHALL keep its recorded answer byte-identical: `(18,4)` and `(10,2)` stay `DECIMAL(18,4)` and `DECIMAL(10,2)`, the boundary pair `(36,36)` stays `DECIMAL(36,36)` because `s ≤ p` holds there, `(1,0)` stays `DECIMAL(1,0)`, and `(38,10)` and `(18,37)` stay `VARCHAR(2000000)`
