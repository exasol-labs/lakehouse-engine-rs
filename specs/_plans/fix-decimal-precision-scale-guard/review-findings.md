## Standard fixes

### crates/lakehouse-engine/src/types/mapping_tests.rs

#### [MISSING_BOUNDARY_TEST] The guard's two off-by-one edges are unpinned
- Location: lines 885-894 (the `cases` matrix in `catalog_decimal_guard_is_shared_by_both_source_kinds`)
- Issue: the matrix exists specifically to pin the new two-clause predicate, but neither clause's rejecting edge is covered, so two off-by-one mutations of `decimal_to_exasol` pass every assertion in the file. (a) Precision jumps from `36` (accepted) straight to `38` (rejected) — `37` is absent, so widening the guard to `(1..=37)` is undetected. (b) `(36,36)` pins the accepting edge `s == p`, and `(5,10)` sits five past the boundary, but `s == p + 1` is absent, so loosening the guard to `scale <= precision + 1` is undetected: `(5,10)` still rejects because `10 > 6`, and `(36,36)` still accepts. The `(0,5)` and `(18,37)` rows do not close either gap.
- Fix: In crates/lakehouse-engine/src/types/mapping_tests.rs, add two rows to the `cases` array in `catalog_decimal_guard_is_shared_by_both_source_kinds`: `(37, 0, "VARCHAR(2000000)")` immediately after the `(36, 36, ...)` row, and `(5, 6, "VARCHAR(2000000)")` immediately after the `(5, 10, ...)` row. Do not edit or reorder any existing row. Run `cargo test -p lakehouse-engine catalog_decimal_guard_is_shared_by_both_source_kinds` and confirm it passes.

### CLAUDE.md

#### [OUTDATED_COMMENT] The Exasol-type enumeration still states the disproven `s≤36` domain, and the new paragraph misattributes an Exasol limit to the catalog path
- Location: line 222 (the `Exasol types:` enumeration) and lines 242-244 (the paragraph added by this change)
- Issue: two defects in one section. (a) Line 222 declares `DECIMAL(p≤36, s≤36)` as Exasol's type domain. The live capture recorded in this plan's `decision-log.md` § Live Captures disproves it: `SELECT CAST(1 AS DECIMAL(5,10))` is rejected with `illegal scale value: 10` and `SELECT CAST(1 AS DECIMAL(0,0))` with `illegal precision value: 0`, both SQL state `42000`. The change established this fact and left the line that contradicts it. (b) The added paragraph says a catalog-declared decimal "additionally requires `1 ≤ p` and `s ≤ p`", framing an Exasol type-domain constraint as a catalog-path-specific extra requirement. A reader following this file — the project's authoritative instruction set — concludes that the Arrow direction may legitimately declare `DECIMAL(5,10)`, which Exasol rejects outright. plan.md task 3.1 barred editing the table *rows*; line 222 is prose, not a table row, so correcting it is in scope.
- Fix: In CLAUDE.md § Data types, change `DECIMAL(p≤36, s≤36)` on line 222 to `DECIMAL(1≤p≤36, 0≤s≤p)`. Then replace the whole paragraph on lines 242-244 with: "Exasol's own `DECIMAL` domain is `1 ≤ p ≤ 36` and `0 ≤ s ≤ p`: `DECIMAL(0,0)` is rejected with *illegal precision value: 0* and `DECIMAL(5,10)` with *illegal scale value: 10* (both SQL state `42000`, captured live). The two `Decimal128` table rows describe only the Arrow-input direction and are looser than that domain; a catalog-declared decimal (Iceberg or Unity) is checked against the full domain and otherwise maps to `VARCHAR(2000000)`." Leave every table row unchanged.

## Expert fixes

### crates/lakehouse-engine/src/types/mapping.rs

#### [INFORMATION_LEAKAGE] A third copy of the Exasol-decimal-domain predicate survives in `iceberg_primitive_to_arrow`, and this change made the two copies disagree
- Location: lines 245-267 (`iceberg_primitive_to_arrow`, guard at line 264), against lines 204-217 (`decimal_to_exasol`) and line 229 (`iceberg_primitive_to_exasol`'s new arm)
- Issue: this is the exact defect the plan set out to eliminate, surviving in a function the plan never considered. `iceberg_primitive_to_arrow` still carries the pre-change predicate `Decimal { precision, scale } if *precision <= 36 && *scale <= 36`, and its own doc comment (lines 248-250) asserts parity: "Matches the Exasol mapping in [`iceberg_primitive_to_exasol`]: in-range Decimal128 maps to `Decimal128(p, s)`, out-of-range Decimal and types with no Arrow equivalent (Time, Fixed, Binary) map to `Utf8`". After this change that claim is false for precisely the two pairs the fix targets: Iceberg `decimal(0,0)` and `decimal(5,10)` now yield `VARCHAR(2000000)` from `iceberg_primitive_to_exasol` but `Decimal128(0,0)` / `Decimal128(5,10)` from `iceberg_primitive_to_arrow`.

  This is not confined to the comment. `build_logical_schema` (crates/lakehouse-engine/src/adapter/pushdown/mod.rs:812) feeds `iceberg_type_to_arrow` into `arrow_type_to_tag`, so for such a column `ScanSpec::logical_schema` carries the tag `decimal128(5,10)` while `createVirtualSchema` declares the same column `VARCHAR(2000000)` — the mismatch `exasol_type_to_arrow`'s "single source of truth" doc comment (lines 81-125) exists to prevent. Worse, arrow-rs rejects `scale > precision` and `precision == 0` when a `Decimal128Array` is built with that precision/scale, so the tag names an Arrow type the scan cannot instantiate.

  plan.md's non-goal "no change to the Arrow `Decimal128` path" and decision-log decision [7] do not cover this function: both are argued from `Decimal128(u8, i8)`'s legitimately-signed scale and from the input being "DataFusion's own schema, not catalog wire input". `iceberg_primitive_to_arrow` takes catalog wire input, with both fields `u32` — identical to `iceberg_primitive_to_exasol`. It is an unaddressed gap, not a settled scoping decision. No existing test catches it: `iceberg_type_to_arrow_maps_all_families` (lines 405-443) covers `(18,4)`, `(36,36)`, `(36,0)`, `(38,10)`, `(18,37)` and no `(0,0)` or `(5,10)`.
- Fix: In crates/lakehouse-engine/src/types/mapping.rs, give the Exasol-decimal-domain decision exactly one owner that both directions read. (1) Add a private predicate `fn exasol_representable_catalog_decimal(precision: u32, scale: u32) -> bool` holding `(1..=EXASOL_DECIMAL_MAX_PRECISION).contains(&precision) && scale <= precision`, with a doc comment stating that it is the sole owner of Exasol's `DECIMAL` domain for a *catalog-declared* decimal, citing the captured rejections (`illegal precision value: 0`, `illegal scale value: 10`, SQL state `42000`), and stating why the Arrow-input guards in `compatible_exasol_type` and `exasol_type_from_json` deliberately do not read it (signed Arrow scale, and an already-Exasol-accepted type respectively — per decision-log decision [7]). (2) Rewrite `decimal_to_exasol` to branch on that predicate, and rename it to `catalog_decimal_to_exasol` so the name states the restricted domain rather than inviting a future reader to route the Arrow or JSON decimal paths through it; update the call sites at line 229 and line 404, and the prose reference in `unity_type_name_to_exasol`'s doc comment (line 392). (3) Replace `iceberg_primitive_to_arrow`'s two decimal arms (lines 264-267) with a single arm that returns `DataType::Decimal128(*precision as u8, *scale as i8)` when the predicate holds and `DataType::Utf8` otherwise. (4) Rewrite `iceberg_primitive_to_arrow`'s doc comment so its parity claim names the shared predicate and its actual domain (`1 ≤ p ≤ 36`, `s ≤ p`) instead of "in-range". (5) In crates/lakehouse-engine/src/types/mapping_tests.rs, add to `iceberg_type_to_arrow_maps_all_families` assertions that `Decimal { precision: 0, scale: 0 }` and `Decimal { precision: 5, scale: 10 }` both map to `DataType::Utf8`; append only, edit no existing assertion. Write those two assertions first and confirm they fail before step 3. Run `cargo test -p lakehouse-engine types::mapping` and `cargo clippy -p lakehouse-engine --all-targets -- -D warnings`.

#### [MAGIC_NUMBER] Exasol's maximum decimal precision is a bare literal in the new guard
- Location: line 212 (`if (1..=36).contains(&precision) && scale <= precision`)
- Issue: `36` is an Exasol-specific, live-verified limit written as a bare literal, while this same file names every comparable Exasol limit as a documented constant — `EXASOL_CHAR_MAX_SIZE: u64 = 2000` (line 488, whose doc comment cites the live `CAST('a' AS CHAR(2001))` rejection), `DECIMAL_INT32_MAX_PRECISION` (line 167), and `DECIMAL_INT64_MAX_PRECISION` (line 170). The new guard is the one place the number carries a captured error message behind it and the only one that states it anonymously. The lower bound `1` needs no name: it is the intrinsic "at least one digit" bound, not an Exasol-chosen ceiling.
- Fix: In crates/lakehouse-engine/src/types/mapping.rs, add a module-scope `const EXASOL_DECIMAL_MAX_PRECISION: u32 = 36;` beside the existing `DECIMAL_INT64_MAX_PRECISION` constant, with a doc comment reading "Exasol's maximum DECIMAL precision. `CAST(1 AS DECIMAL(0,0))` fails live with \"illegal precision value: 0\" and a precision above this ceiling is rejected the same way (SQL state 42000), so a catalog-declared decimal outside `1..=36` is declared VARCHAR(2000000) instead." Use the constant in place of the literal `36` in the predicate, keeping the `1` as a literal. Apply this in the same edit as the `[INFORMATION_LEAKAGE]` finding above so the predicate is rewritten once.
