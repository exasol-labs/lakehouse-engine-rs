- capabilities (crates/lakehouse-engine/src/adapter/capabilities.rs): holds the advertised capability list, parses the `EXCLUDED_CAPABILITIES` entry list, and answers getCapabilities with the advertised list less the excluded names | owns: advertised capability list, `EXCLUDED_CAPABILITIES` entry syntax | depends on: none
- vs-properties (crates/lakehouse-engine/src/adapter/properties.rs): declares every virtual schema property name and the value rule of each tuning property, applies the table-filter value rule to `TABLE_INCLUDE` and `TABLE_EXCLUDE` and the advertised-name rule to `EXCLUDED_CAPABILITIES`, parses every property once per request, rejects unknown names and invalid values in one error for createVirtualSchema, refresh, and setProperties, reads a rejected value as absent for pushdown and getCapabilities, and parses each tuning value into a fixed-width typed value and the two pattern lists into one table filter; it parses properties only, never adapterNotes | owns: VS property catalog (names and tuning value rules) | depends on: table-filter, capabilities

- distribute-files (deploy/scripts/install.sh): defines the Lua SET script `LAKEHOUSE_DISTRIBUTE_FILES`, which re-emits per-shard file-list rows so `GROUP BY shard_key` spreads them across nodes | owns: none | depends on: none

## Data Flow

- CREATE or REFRESH VIRTUAL SCHEMA -> vs-adapter -> lakehouse-catalog -> catalog service: table listing returns as virtual table definitions, one identifier note per table holding its catalog identifier, and one column note per column holding the declared source shape
- REFRESH TABLES -> vs-adapter -> lakehouse-catalog -> catalog service: the namespace's catalog identifiers are listed without loading any table, only the identifiers whose Exasol name is requested are loaded and collision-checked, the response carries only the requested tables, and Exasol keeps every other virtual table with its notes
- user query -> Exasol -> vs-adapter: one pushdown request JSON per pushed-down query block, with projection, filter, aggregates, ORDER BY, LIMIT, join tree, and each involved table's identifier note and column notes; every request of one statement on one virtual schema reaches the same adapter VM, and Exasol starts a separate adapter VM for each virtual schema of the statement
- vs-adapter -> catalog client -> format-readers -> lakehouse-catalog and object storage: the virtual schema's catalog client loads a table and opens its snapshot or file listing, and each table reference prunes the file list with its own filter against the declared schema the column notes carry; no reader derives a schema
- format-readers -> sharding -> pushdown-planner: the file list becomes G byte-balanced shards, each serialized as `common` and `files` JSON strings in the dispatch SQL
- dispatch SQL -> LAKEHOUSE_DISTRIBUTE_FILES -> GROUP BY shard_key -> LAKEHOUSE_SCAN: Exasol runs one scan VM per node, which scans that node's shard rows one after another
- LAKEHOUSE_SCAN -> datafusion-scan -> scan-object-store -> object storage: Parquet byte ranges stream into one DataFusion plan per invocation
- datafusion-scan -> Exasol: raw and join rows leave through the Arrow C Data Interface via `ctx.emit_batch`, partial aggregates leave as SDK `Value` rows via `ctx.emit`
- Exasol -> result: the dispatch SQL wrapper merges partial aggregates and applies the final ORDER BY and LIMIT
- user `EXPORT ... INTO SCRIPT LAKEHOUSE_EXPORT WITH CATALOG_CONNECTION = '<connection>' ...` -> Exasol -> export: one call with the export specification (options, source column names) before any source row is read; export answers one SELECT over `DUAL`, which Exasol binds to the export source
- generated SELECT -> LAKEHOUSE_EXPORT as writer: the source rows are grouped by `MOD(ROWNUM, G)`; Exasol multiplexes the groups, one writer invocation each, onto each node's SET-script VM pool
- LAKEHOUSE_EXPORT writer -> storage, catalog: each writer writes its rows as Parquet data files by the table's write properties, as they arrive for an unpartitioned table and split by the table's current partition spec otherwise, and commits them in one tagged snapshot (with `SINGLE_COMMIT`, one writer commits all rows: as the staged table it creates, or as one append to an existing table)
- LAKEHOUSE_EXPORT writer -> Exasol: one row count per writer; Exasol reports their sum as the EXPORT statement's row count

## Constraints

- The toolchain is pinned in `rust-toolchain.toml`, with edition 2024. Every dependency version is pinned in the workspace manifest, not in the specs.
- The release `.so` builds only in the Makefile's `UDF_BUILDER_IMAGE`, whose rustc and glibc match the SLC, because the SLC rejects a `.so` whose SDK fingerprint (`exasol-udf-sdk` version and rustc hash) differs from its own.
- `exasol-udf-sdk` and `exasol-udf-macros` are pinned in the workspace manifest to the SLC's own version.
- `arrow` and `parquet` stay on the Arrow major that `datafusion` and the SDK depend on, not on the major of the `datafusion` or SDK package itself.
- Arrow types never cross the `.so` boundary. Only SDK `Value`s or the Arrow C Data Interface structs from `ctx.emit_batch` cross it.
- In `lakehouse-engine` and `vs-expression`, an Exasol SQL type travels as vs-expression's Exasol type, never as a string. Each input edge (VS `dataType` JSON, Iceberg, Delta, Hive, and Arrow types) reads it once, and only SQL text generation and the VS `dataType` JSON output render it. The `dataType` parser admits only values within Exasol's limits, a DECIMAL outside Exasol's domain cannot be constructed, and one rendering serves `EMITS` columns, column declarations, and Exasol-dialect `CAST` targets.
- The engine supports Exasol 8.29.x and later. Every pushdown request of a supported version carries `selectListDataTypes` with one complete `dataType` per select-list item, and the adapter fails a request without it.
- Planning reads a pushdown request only through the parsed request type. A rewrite of the request goes through that type and keeps its guarantees: checked select-list types, and no constant sort key.
- `lakehouse-catalog` never depends on `lakehouse-engine`. Its manifest declares no `arrow`, `parquet`, `datafusion`, or `object_store` dependency, and it names no scan-spec type (`FileEntry`, `LogicalField`, `DeleteMechanism`, `CommonScanSpec`). A neutral catalog column carries an Arrow type only as the engine's type-tag string.
- The engine reads and writes a `column` node's `name`, `tableName`, and `tableAlias` only through `vs-expression`'s column node type.
- The pushdown-planner renders every expression the scan computes through one scan translator that reads the per-column type map, so a type rule such as the text-conversion decline (`pushdown-types/pushdown-planning-scan-text-conversion`) is written once for every path.
- One type inference in vs-expression decides each expression node's Exasol type. It serves the scan translator's checks and every type the pushdown-planner declares (split-aggregate partials and merges, group keys, wrapper casts), and no path derives a type another way.
- Where Exasol versions type an expression differently, the type inference returns the running version's type, read from the pushdown context's version.
- `lakehouse-catalog` declares the shared credential types (`ConnectionCreds`, `StorageProps`, `CatalogProps`, `StorageBackend`) and the credential redaction functions once. The engine re-exports them and declares no copy. Reading and parsing the Exasol CONNECTION object stays in the engine.
- The engine enumerates and declares catalog tables through the `CatalogClient` trait and its neutral table and column types. `CatalogClient` has no single-table load. Each catalog kind's client loads a table for pushdown through its one scan load, declared by an engine-side extension of that trait, so `lakehouse-catalog` gains no file-planning type. The vs-adapter's one catalog-kind match is the only site that names the kind to build a client or load a table, and a scan load matches only the loaded table's format tag. In `lakehouse-catalog`, auth strategies, HTTP and signing helpers, and vended-resolution steps stay crate-private, and no AWS SDK type crosses the crate boundary.
- Each catalog kind's identifier-only listing returns every identifier its full listing would return or skip, in listing order, without loading table metadata. Its load of listed tables admits or skips each given table exactly as the full listing does and loads no other table.
- The Makefile's `VS_SRCS` lists every crate's sources and manifest, so a change in `lakehouse-catalog` or `vs-expression` rebuilds the `.so` before an E2E run.
- Each pushdown request builds one pushdown context from its UDF handshake and its parsed properties: the CONNECTION, the scan UDF names, the node count, the tuning values, the Exasol version, and the statement clock with its two zones (`TZ` and `SESSION_TIME_ZONE`). Planning reads these values only from that context.
- The adapter folds every clock function of a pushdown request into a date or timestamp literal, and every `TIMESTAMP WITH LOCAL TIME ZONE` literal outside a select-list item of that type into the plain timestamp of its wall-clock time in the folding zone, before planning, so no planning path and no scan reads a clock or a session zone.
- The adapter moves every conjunct of an inner join's condition other than a join equality into the request's top-level filter before join planning, except in a join on an outer join's null-supplying side, so every join planning path reads a join's filters from the top-level filter alone. One planner module owns the test that decides which conjuncts stay in a join's condition, the move, and the join-key test that broadcast eligibility asks, and the three change independently.
- The scan UDF keeps no cross-call state and builds its Tokio runtime per call. The adapter keeps cross-call state only for the pushdown requests of one statement, keyed by the virtual schema name: the Tokio runtime, the resolved CONNECTION, the catalog client, the permission-checked tables, and each table's loaded, unpruned state. It also keeps one clock reading, which every virtual schema of the VM's statement folds. It therefore loads each table's metadata once per statement and prunes the file list per table reference. It never keeps a pruned file list, a result, or an error.
- The engine owns no persisted metadata. Exasol stores the schema-level adapterNotes values (`SKIPPED_TABLES`, `CATALOG_PREFIX`), the table identifier notes, and the column notes between CREATE and pushdown.
- A table's declared schema is decided at CREATE, REFRESH, or SET and read from its column notes at pushdown. No format reader derives a logical schema, a partition column, or a refusal at pushdown.
- Each node scans only its assigned files, with no overlap between shards.
- The shard count is G = node count × `PARALLELISM_FACTOR` (default 1), clamped to at least 1 and at most min(file count, 300).
- The export writer count is G = node count × `WRITERS_PER_NODE` (default 1), clamped to at least 1 and at most 300, or 1 with `SINGLE_COMMIT = 'true'`. Each source row reaches exactly one writer, and a source with at least G rows runs exactly G writers.
- An export writer into a partitioned table buffers each partition's rows and keeps their Arrow memory within min(max((memory limit − 200 MB) × 0.5, 64 MiB), 512 MiB), or 512 MiB when the limit is unknown. At the budget it writes the partition with the most buffered rows into one data file, so it has at most one data file open at a time. A writer into an unpartitioned table buffers no rows beyond the Parquet row group in progress.
- The DataFusion memory pool is max((memory limit − 200 MB overhead) × 0.6, 256 MiB), or 1 GiB when the limit is unknown.
- The scan spills to `/tmp` when `/tmp` is a writable non-tmpfs disk. Otherwise it returns a `ResourcesExhausted` error past the pool budget.
- The scan streams one `RecordBatch` at a time and never collects the full result.
- Errors never contain credentials. Storage credentials reach the scan UDF only as a CONNECTION name or a sealed envelope. The export script receives only the CONNECTION name and emits no script output.
- STS AssumeRole and Glue operations time out after 30 seconds.
- Every Iceberg REST, Lakekeeper, Unity Catalog, and OAuth2 token request goes through the one crate-private catalog HTTP client of `lakehouse-catalog`. It ends an attempt that stays silent for 10 seconds, retries only a transient failure, up to 5 attempts, and starts no retry that could wait for its answer past 30 seconds after the first attempt. It reads an answer body for as long as the body keeps arriving.
- Every outbound HTTP client of the adapter and the scan UDF honors `HTTPS_PROXY`, `HTTP_PROXY`, and `NO_PROXY` from the process environment, which a script's `%env` lines set. A client that ignores them is a defect.
- Exasol's own dispatcher throttles concurrent UDF VMs at 80% of the per-process memory limit.
- DSNs in the Makefile, bench scripts, and installer include `validateservercertificate=0`.
- The engine must be faster than single-node DataFusion, scale with added Exasol nodes, keep duplicate scanning minimal, and keep metadata overhead acceptable.
