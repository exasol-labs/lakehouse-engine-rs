### crates/lakehouse-engine/src/scan/checked_div.rs

#### [OUTDATED_COMMENT] The error doc claims a stored non-finite operand can only reach `NonFiniteResult`
- Location: lines 40-41 (`CheckedFloatDivError` doc comment: "only the first is the user's own division by zero, and only the second can come from a value the source table stored")
- Issue: `checked_quotient` (lines 275-288) tests finiteness first and then classifies on `divisor == 0.0`, so a stored `NaN` or `±Inf` numerator divided by zero is reported as `ZeroDivisor`, not `NonFiniteResult`. Measured: `NaN/0.0` gives `is_finite() == false` and `divisor == 0.0 == true`; same for `INFINITY/0.0`. The doc's claim is the one a support engineer would act on, and it does not hold.
- Fix: In crates/lakehouse-engine/src/scan/checked_div.rs, rewrite the last sentence of the `CheckedFloatDivError` doc comment to state that `ZeroDivisor` is raised whenever the divisor is zero, including when the numerator is a non-finite value read from the source table, and that `NonFiniteResult` covers a non-finite result under a non-zero divisor only.

#### [UNTESTED_ERROR_PATH] The arity guard in `invoke_with_args` has no test
- Location: lines 210-215
- Issue: the `else` arm returning `DataFusionError::Execution("{CHECKED_FLOAT_DIV_FN} takes exactly two arguments, got {n}")` is never exercised. `Signature::any(2, ...)` makes DataFusion reject a wrong arity at plan time, so the only reachable caller is a direct `invoke_with_args` call, which every existing test makes with exactly two arguments.
- Fix: In crates/lakehouse-engine/src/scan/checked_div_tests.rs, add `checked_float_div_refuses_an_argument_count_other_than_two`: build `ScalarFunctionArgs` with one argument and with three arguments, call `udf.invoke_with_args` directly for each, and assert each returns an error whose message contains `takes exactly two arguments`.

### crates/lakehouse-engine/tests/e2e_scan_test.rs

#### [MISSING_BOUNDARY_TEST] `pushed_scan_filter` panics with an index underflow on an empty filter value
- Location: lines 4202-4207 (the byte scan in `pushed_scan_filter`)
- Issue: the loop condition reads `bytes[end - 1]` before checking `end > 0`. When the ScanSpec's `filter` value is the empty string, `end` is 0 on the first iteration, `bytes[0] == b'"'` is true, and `bytes[end - 1]` underflows `usize`, so the helper panics with a subtract overflow instead of the clear assertion failure its `panic!` message above it was written to give. Every current caller pushes a non-empty filter, so the path is latent rather than failing today.
- Fix: In crates/lakehouse-engine/tests/e2e_scan_test.rs, change the loop condition in `pushed_scan_filter` to `!(bytes[end] == b'"' && (end == 0 || bytes[end - 1] != b'\\'))` so an empty filter value returns an empty string and the caller's own assertion reports the real problem.

## Expert fixes

### crates/lakehouse-engine/src/scan/emit.rs

#### [SWALLOWED_ERROR] `reframe_checked_division` discards the error that actually failed the scan
- Location: lines 233-250 (`reframe_checked_division`), called from crates/lakehouse-engine/src/scan/mod.rs lines 323-325
- Issue: whenever the session recorded a division failure, the incoming `UdfError` is dropped whole and replaced by `checked_division_error(&division, secrets)`. A scan can fail for two independent reasons in one query: DataFusion evaluates partitions concurrently and surfaces only the first error to reach the caller. If partition A raised the checked division and partition B raised something else, the something else disappears with no trace. Two concrete losses. First, `classify_scan_error` turns a `ResourcesExhausted` into the clean memory-exhaustion error the mission's bounded-execution guarantee rests on; the reframing overwrites it, so a query that both divided by zero and exhausted the memory pool reports only the division and the operator loses the pool-sizing signal. Second, a redacted storage error such as an S3 403 from another partition is replaced, so the user fixes the division, re-runs, and meets an unrelated failure they were never shown. The doc comment's defence ("naming it is never a false report") answers a different question: the report is true but incomplete, and it is the only one the user gets. `reframe_checked_division_leaves_an_unrelated_failure_untouched` only covers the case where NO division was recorded, so the collision is pinned by no test. Composing the two messages is safe but must not paste unredacted text: the incoming error is not guaranteed to have passed `classify_scan_error`, because the run paths also surface `UdfError::User(format!("DataFusion SQL error: {e}"))` and `"partial aggregate SQL error: {e}"` directly.
- Fix: In crates/lakehouse-engine/src/scan/emit.rs, change `reframe_checked_division` so the `Some(division)` arm composes instead of replacing: build the division message with `checked_division_error`, then append the incoming error's own message passed through `redact_credentials(&redact_secret_values(&error.to_string(), secrets))`, with the division named first and the appended part introduced by a fixed phrase such as `the scan also surfaced:`. Keep the `None` arm returning `error` unchanged. Then add two tests to crates/lakehouse-engine/src/scan/emit_tests.rs: `reframe_checked_division_keeps_a_concurrent_memory_exhaustion_failure_visible`, which registers the UDF on a session, raises a zero divisor through it, passes `classify_scan_error(DataFusionError::ResourcesExhausted("pool of 100 bytes".into()), &[])` to `reframe_checked_division`, and asserts the result contains both `division by zero` and the memory-exhaustion text; and `reframe_checked_division_redacts_secrets_from_the_appended_failure`, which does the same with an unclassified `UdfError::User(format!("DataFusion SQL error: reading s3://b/f.parquet?key={secret}"))` and asserts the literal secret is absent while `division by zero` is present.
