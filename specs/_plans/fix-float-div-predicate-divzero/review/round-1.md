# Plan Review Findings: fix-float-div-predicate-divzero (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 15 (Blockers: 6, Advisory: 9)

## Premortem

Three failure stories, written before scoring.

1. **The fix broke working queries.** Six months on, `WHERE QTY <> 0 AND PRICE / QTY > 100` fails on some shards and succeeds on others. DataFusion 54.1 evaluates the right conjunct over the whole batch unless the left conjunct passes 20% or fewer rows, so the checked division raises for rows the guard already excluded. The failure is data-dependent and looks intermittent. Routed to Feasibility.
2. **The permanent spec library contradicts itself.** The recorder merged the deltas. Two `DELTA:CHANGED` scenarios carried new headings, so nothing was replaced, and the library now states both `SHALL return (CAST(<left> AS DOUBLE) / <right>)` and `MUST NOT return (CAST(<left> AS DOUBLE) / <right>)` for the same node. `specs/_decision/079-fix-float-div-truncation.md` still carries the cast rendering as Accepted. Routed to Requirement Quality.
3. **The tracked exceptions evaporated.** The two follow-up issues were never filed, the spec deltas carry no citation token, and the same defect class still reaches production through `SQRT`, `LN`, `ACOS`, `EXP`, `POWER`, and `MOD`. The library names deviations that no issue tracks. Routed to Requirement Quality.

## Intent Fidelity

The plan fixes the problem issue #370 reports. `crates/vs-expression/src/lib.rs:1032` renders `cast_to_double(&left)` for the `FLOAT_DIV` DataFusion arm, and the plan replaces that one arm, which is the layer every scan path splices. The plan does not drift into #246: decision [9] and the delta at `sql-comprehension/vs-expression-translator-float-div/spec.md:270-273` withdraw the widening claim and keep #246 open. The "supersedes ADR 079" claim is defensible on the merits: the Options Considered table of `float-div-zero-behaviour-from-measurement-not-emulation` (`specs/_decision/079-fix-float-div-truncation.md:79-87`) lists `NULLIF` rendering, `arrow_value_at` widening, declining `FLOAT_DIV`, and one blanket issue, and never evaluates a rendering-layer function. The mechanical half of that supersession is defective and is filed under Requirement Quality.

#### [SCOPE_CREEP] ADVISORY
- Location: decision-log.md § Design Decisions [2]; `sql-comprehension/vs-expression-translator-float-div/spec.md:139-146`
- Issue: decision [2] raises on ANY non-finite result, not only on a zero divisor. Issue #370 reports a zero divisor. The extension adds two user-visible failure modes no part of the intent asks for: an overflow to `±Inf` from finite operands, and a source column that legitimately stores `±Inf` or `NaN` fed into a division. The second one also contradicts the plan's own central safety argument. plan.md:35 states "The check sees only the two operands of a division the pushdown itself synthesised, so it never inspects a value read straight out of a column", yet `vs_checked_float_div(<nan_col>, 2)` raises precisely because of a value read out of a column, while the bare `WHERE <nan_col> > 0` still succeeds. The spec names the trade-off at line 139, but plan.md § Decision and decision-log [1] state the safety claim without the caveat.
- Fix: In plan.md § Decision, qualify the sentence at line 35 to say the check raises on the RESULT of the synthesised division, and add the stored-operand case as a named exception to that claim. Add the same qualification to decision-log.md entry [1] § Rationale. In plan.md § Impact, state explicitly that a query dividing a stored non-finite operand inside a predicate changes from success to failure.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md § Impact "Tracked exceptions this plan does not fix" item 1; decision-log.md [7]; `sql-comprehension/vs-expression-translator-float-div/spec.md:259`
- Issue: the plan models only ONE direction of divergence, that the error may be SUPPRESSED. The opposite direction is unmodelled and is a regression on queries that work today. Verified in the pinned dependency: `datafusion-physical-expr-54.1.0/src/expressions/binary.rs:739` defines `const PRE_SELECTION_THRESHOLD: f32 = 0.2`, and `check_short_circuit` at line 760 returns `PreSelection` for an AND only when the left side's `true_count as f32 / len as f32 <= PRE_SELECTION_THRESHOLD`. Above that ratio it returns `None`, and `BinaryExpr::evaluate` evaluates the right side over the FULL batch, including rows the left conjunct excluded. Nothing protects the division conjunct at all when it is the LEFT operand. Consequence: `WHERE L_LINENUMBER <> 0 AND L_ORDERKEY / L_LINENUMBER > 3` succeeds today and, after this change, raises or succeeds depending on per-batch selectivity and on conjunct order. plan.md:95 claims "It is a correctness change that converts silent wrong answers into loud failures" and plan.md:93 claims "No pushdown is refused that was accepted before"; neither names the converse, that a correct answer becomes an intermittent failure. Native Exasol's behaviour for the guarded shape is not measured, so parity is unknown in this direction too. CLAUDE.md § Verification discipline forbids assuming it.
- Fix: Add a sub-task under plan.md task 1.1 measuring the guarded shape live against the native oracle, in both conjunct orders: `WHERE L_LINENUMBER <> 0 AND L_ORDERKEY / (L_LINENUMBER - L_LINENUMBER) > 0` and the reversed order, recording whether native Exasol raises. Add a `DELTA:NEW` clause to the scenario "A division by zero inside a filter predicate fails the query rather than changing the row count" in `sql-comprehension/vs-expression-translator-float-div/spec.md` stating the measured outcome for a guarded division, naming the batch-selectivity dependence and its DataFusion 54.1 mechanism. Add a matching E2E test to plan.md task group 4 and to § Verification § Scenario Coverage. Extend decision-log.md [7]'s proposed issue scope, or file a third issue, to cover the over-raise direction; the current scope covers only suppression.

#### [EFFORT_MISESTIMATION] ADVISORY
- Location: plan.md task 3.4; decision-log.md [6]
- Issue: task 3.4 states "Recognise it by type through a dedicated error carried on the DataFusion error chain" as one bullet. `crates/lakehouse-engine/src/scan/emit.rs:199` currently matches `e.find_root()` against `DataFusionError::ResourcesExhausted` only, a variant `find_root` resolves natively. A custom Rust error must travel as `DataFusionError::External(Box<dyn Error + Send + Sync>)`, which `find_root` does not unwrap into a non-`DataFusionError` type, and a `FilterExec` or `ProjectionExec` boundary can rewrap it through `ArrowError::ExternalError`. The task therefore hides a multi-level downcast plus a live check that the type survives every one of the three scan paths, not a single match arm.
- Fix: Split plan.md task 3.4 into two tasks: one that defines the dedicated error type and pins, with a unit test per scan path, which `DataFusionError` variant nesting it arrives in; one that adds the `classify_scan_error` arm against that pinned nesting. State the downcast depth as an open question the first task answers.

## Design Depth

The new module passes the `/speq:design-philosophy` quick diagnostic on responsibility, depth, and dependency direction: `scan/checked_div.rs` has one responsibility, it hides the coercion and finiteness rules a caller would otherwise repeat, and it depends only on DataFusion and Arrow, which the scan layer already owns. Decision [5]'s refusal to consolidate the two registrations is correct, not a tactical shortcut: `build_session_context` already is the single registration site. One leakage finding stands.

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: decision-log.md [3]; plan.md task 2.2 and task 3.2; `sql-comprehension/vs-expression-translator-float-div/spec.md:204-205`
- Issue: the design splits one decision, the semantics of `vs_checked_float_div`, across two crates with nothing enforcing agreement. `crates/vs-expression` states the contract in a doc comment on a constant; `crates/lakehouse-engine` implements it independently. This is the back-door form of leakage in `/speq:design-philosophy`: two modules assume the same protocol, and no artifact holds both sides. The plan's only guard, task 3.3, asserts a session resolves the NAME, never that the behaviour matches the documented contract. `specs/mission.md` states `crates/vs-expression` "is designed to be shared with the sibling project", so a sibling that registers a function with different NULL or non-finite handling diverges silently. Decision [3] addresses only the missing-registration case, which does fail loudly.
- Fix: Add a clause to the scenario "A checked float division raises rather than producing a non-finite value" in `datafusion-scan/scan-execution-expression-pushdown/spec.md` requiring the unit tests to cover, one test per clause, every obligation the exported constant's doc comment states. Add to plan.md task 2.2 that the doc comment MUST enumerate its obligations as a numbered list, and to task 3.2 that each numbered obligation MUST have a named test. State in decision-log.md [3] § Rationale that a consumer registering different semantics is out of contract and fails silently.
