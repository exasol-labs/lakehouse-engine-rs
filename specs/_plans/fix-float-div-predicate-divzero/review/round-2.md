## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md task 1.2; plan.md task 4.5; `sql-comprehension/vs-expression-translator-float-div/spec.md:285`
- Issue: the query task 1.2 measures cannot exercise a guard, so it cannot answer the question the task exists to answer. Task 1.2 names `SELECT COUNT(*) FROM ... WHERE L_LINENUMBER <> 0 AND 0 < L_ORDERKEY / (L_LINENUMBER - L_LINENUMBER)`. The divisor `(L_LINENUMBER - L_LINENUMBER)` is identically zero for every non-null row, whatever `L_LINENUMBER` holds. The conjunct `L_LINENUMBER <> 0` therefore excludes no zero-divisor row: every row that survives the guard still divides by zero. Both conjunct orders raise for the trivial reason that no guarded row exists, so the run reproduces task 1.1's unguarded result with one inert extra conjunct, and it distinguishes "the guard protects the division" from "the guard does not protect the division" in neither direction. The fixture makes this exact: `crates/lakehouse-engine/tests/common/seed.rs:1345` generates `L_LINENUMBER` as `((r - 1) % 2) + 1` over the 20 rows, so the column holds only `{1, 2}`, ten rows each, and no fixture column takes zero on any row. `L_LINENUMBER <> 0` is satisfied by all 20 rows. The identically-zero divisor is also already the shape two existing tests use (`crates/lakehouse-engine/tests/e2e_scan_test.rs:4033` and `:4067`), so task 1.2 as written re-runs a covered case. Task 4.5's E2E test inherits the same shape and pins the same non-result. Task 1.2 then writes that outcome into the scenario clause at `spec.md:285`, which states the guarded outcome "SHALL have its outcome MEASURED live against the native Exasol oracle by task 1.2 and RECORDED here rather than assumed", so the permanent library would carry a measurement labelled as the guarded shape that measured an unguarded one. `/speq:writing-guardrails` forbids claiming project behaviour without evidence, and CLAUDE.md § Verification discipline requires the claimed SQL behaviour to be verified against a live Exasol system. Round 1's own Fix line prescribed this query; the defect originates there and is corrected here.
- Fix: In plan.md task 1.2, replace the divisor `(L_LINENUMBER - L_LINENUMBER)` with `(L_LINENUMBER - 1)` and the guard with `(L_LINENUMBER - 1) <> 0`, giving `SELECT COUNT(*) FROM ... WHERE (L_LINENUMBER - 1) <> 0 AND 0 < L_ORDERKEY / (L_LINENUMBER - 1)` plus the reversed conjunct order. That divisor is zero on the ten `L_LINENUMBER = 1` rows and one on the ten `L_LINENUMBER = 2` rows, so the guard excludes exactly the zero-divisor rows and the left conjunct's true ratio over the 20-row batch is 0.5, above the `PRE_SELECTION_THRESHOLD` of 0.2 the delta cites, which is what makes the over-raise direction observable rather than assumed. Add to task 1.2 that the run MUST record the guarded row count and the unguarded row count separately, so the guard is shown to remove rows. Apply the identical shape to plan.md task 4.5 and to its § Verification § Scenario Coverage row. In `sql-comprehension/vs-expression-translator-float-div/spec.md:285`, name the concrete guarded divisor and guard the measurement uses, so a later reader can tell the guarded case from the unguarded one.
