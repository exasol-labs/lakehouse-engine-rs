# Code Review Findings: fix-join-fallback-self-join-attribution

## Summary
- Files reviewed: 16
- Total findings: 12 (standard: 9, expert: 3)

Verified clean, no findings raised:
- No golden-SQL expected literal was edited. `dispatch_golden_tests.rs`, `pushdown/testdata/`, and the existing `golden_n_scan_join_sql_unchanged` / `golden_n_scan_render_decline_messages_unchanged` expectations are byte-unchanged; only their `alias_of` → `JoinLegs` call-shape moved.
- No call site outside `attribution.rs` reads a `column` node's `tableName` to decide leg identity. `grep -rn tableName crates/lakehouse-engine/src` leaves exactly one non-attribution reader, `possible_side_column_names` (`rendering.rs:323`), which the plan deliberately keeps name-keyed; its rewrite is logically identical to the deleted `collect_side_column_names` + untagged-column double walk (insert iff `tableName` is absent or matches), so the refused-column check does behave exactly as before.
- The N = 1 wrapper is behaviour-preserving: `JoinLegs::for_single_scan` maps every `involvedTables[].name` onto leg 0 with ASCII-case-insensitive matching and `unwrap_or_default()` on an absent `involvedTables`, matching the deleted `alias_of` map exactly; because all keys share leg 0, `resolve_column`'s alias branch is unreachable there and `Unattributable` can never arise.
- `strip_table_alias` still runs only after the join gate returns (`pushdown/mod.rs:193`), so the leg key survives to `plan_join`.
- All five deleted functions from the plan's Dead Code Removal table are gone; `cargo clippy --all-targets` and `--all-targets --features exasol-e2e` are both warning-free, and `cargo test -p lakehouse-engine --lib` is 1123 passed / 0 failed.
- The mixed aliased/unaliased premise holds. Captured live during this review against the running Docker stack for `FROM MY_LAKEHOUSE.FACT_ORDERS JOIN MY_LAKEHOUSE.FACT_ORDERS b ON …`: the unaliased leaf is `{"name":"FACT_ORDERS","type":"table"}` with no `alias` key and its columns are `{"name":"O_CUSTKEY","tableName":"FACT_ORDERS","type":"column"}` with no `tableAlias`, so `self_join_request(&[None, Some("B")])` models production correctly and the shape resolves to two legs rather than erroring.

### crates/lakehouse-engine/src/adapter/pushdown/joins/sql_builders.rs

#### [SHALLOW_MODULE] `build_n_scan_join_from` re-derives an attribution decision from `LegReferences`' raw fields
- Location: lines 137-148 (`build_n_scan_join_from`), reading `LegReferences`' three `pub` fields declared at `attribution.rs:25-35`
- Issue: `JoinLegs` is meant to absorb the whole attribution decision, and it already does exactly this job for the one-leg case (`conjunct_leg`, which encapsulates "no column ⇒ no leg", "any unattributed ⇒ no leg", "exactly one leg ⇒ that leg"). The FROM-chain site instead pulls the three raw fields out and reimplements the policy in the caller: `let resolvable = referenced.any_column && !referenced.has_unattributed;` plus `referenced.legs.iter().next_back()` for the attach point. A caller must know that `next_back()` on a `BTreeSet` means "the highest-indexed leg", that the highest-indexed leg is the greedy attach point, and that `NoLeg` and `Unattributable` are deliberately merged into one flag — three internals the plan's Quick Diagnostic asserts "never appear outside the module". The failure mode of getting this wrong is a condition attached at the wrong join point or demoted to the outer WHERE: correct-looking SQL, wrong or over-broad rows, with the golden fixtures still green.
- Fix: In crates/lakehouse-engine/src/adapter/pushdown/joins/attribution.rs, add `pub(super) fn attachment_leg(&self, expr: &Json) -> Option<usize>` returning `None` when the tree references no column or any column is unattributed and otherwise the highest leg index referenced, with a doc comment stating that the highest-indexed leg is the earliest join point at which every referenced leg is in scope. Make `legs_referenced` and the `LegReferences` struct private to `attribution.rs`. In crates/lakehouse-engine/src/adapter/pushdown/joins/sql_builders.rs, rewrite `build_n_scan_join_from`'s per-condition body to `match legs.attachment_leg(raw) { Some(m) if last_join_point >= 1 => on_at[m.clamp(1, last_join_point)].push(...), _ => residual.push(...) }`, deleting the local `resolvable` derivation. Add unit tests in `attribution_tests.rs` for `attachment_leg` covering a cross-leg condition, a single-leg condition, a column-free condition, and an unattributed condition, and confirm `golden_n_scan_join_sql_unchanged` and the three- and four-leg wrapper tests stay byte-identical.

#### [TACTICAL_SHORTCUT] The FROM-chain loop bound is decoupled from the slice it indexes, guarded only by a `debug_assert`
- Location: lines 137-148 (`build_n_scan_join_from`, `for k in 1..leg_count { … fan_outs[k] … }`) and line 438 (`debug_assert_eq!(legs.leg_count(), sides.len(), …)`)
- Issue: `build_n_scan_join_from` previously took `aliases`, whose length was constructed from `sides.len()` and therefore from the same source as `fan_outs`. It now takes `legs` and drives both `vec![Vec::new(); leg_count]` and `1..leg_count` off `legs.leg_count()`, i.e. `join.tables.len()`, while still indexing `fan_outs[k]` and `on_at[m]`. The two lengths agreeing is now a cross-function assumption asserted only in debug builds; in a release `.so` a mismatch is an index-out-of-bounds panic inside a UDF (or, in `n_full_row_qualified_items`, a leg qualified to an `LHS_T{i}` subquery the FROM chain never emits). The same shortcut makes `cols_per_side[i]` indexable by a leg index a documented convention rather than a structural fact.
- Fix: In crates/lakehouse-engine/src/adapter/pushdown/joins/sql_builders.rs, make the chain bound come from the slice it indexes: size `on_at` as `vec![Vec::new(); fan_outs.len()]`, derive `last_join_point` from `fan_outs.len().saturating_sub(1)`, and build the chain by iterating `fan_outs.iter().enumerate().skip(1)` so `legs.leg_alias(k)` is only ever used for a leg the chain actually emits. Replace the `debug_assert_eq!` at line 438 with a real guard that returns `join_render_decline` naming both counts when `legs.leg_count() != sides.len()`, so a future drift is a client-visible decline rather than a release-mode panic, and add a unit test in `sql_builders_tests.rs` that drives `build_n_scan_join_sql` with a `sides` vec shorter than `join.tables` and asserts the decline.
