# Code Review Findings: fix-join-filter-type-rewrites

## Summary
- Files reviewed: 4
- Total findings: 8 (standard: 6, expert: 2)

Verified clean, no findings raised: both production wirings are correct. The
broadcast site's `classify_where_filter` call sits after `disjoint_schema_guard`
and before `extract_join_projection`, and its declined half short-circuits to
`Ok(None)`. The N-scan restructure keeps the leg/residual partition total and
disjoint (`declined_only` ⊥ `leg_eligible` ⊇ per-side `type_declined`), and the
fail-closed arm returns the whole `side_local` set so nothing is dropped from
both halves. The REWRITTEN tree never reaches Iceberg manifest pruning —
`plan_join` (`joins/mod.rs:123-127`) still calls `side_local_filter` on the RAW
request filter, independently of `build_n_scan_join_sql` — so the spec's
"leaving the raw filter tree forwarded to Iceberg file pruning unchanged"
clause holds. The residual is rendered by `render_df_filter_qualified`, which
despite its name uses `render_df_filter_exasol_safe`, so a declined 3-argument
`INSTR` reaches the outer `WHERE` as Exasol's verbatim `INSTR(a, b, 3)`
(`vs-expression` `ExasolForm::VerbatimCall`), not the argument-dropping
`strpos(a, b)` the DataFusion dialect emits. `cargo test -p lakehouse-engine
--lib joins::` = 94 passed; `cargo clippy -p lakehouse-engine --all-targets
--features exasol-e2e` = 0 warnings.

### crates/lakehouse-engine/src/adapter/pushdown/joins/rendering.rs

#### [INFORMATION_LEAKAGE] The type-acceptance rule now lives in two modules, held in agreement only by a doc comment
- Location: line 318
- Issue: `type_screened_leg_filter`'s `accepts` closure encodes the rule "a tree is pushable iff `apply_type_rewrites` yields `Some(rw)` AND `datafusion_renderable(&rw)`" — `apply_type_rewrites(c, col_types).is_some_and(|rewritten| datafusion_renderable(&rewritten))`. `support.rs:1089-1093` `classify_where_filter` encodes the same rule as two match arms (`(Some(raw), None)` plus `(Some(raw), Some(tree)) if !datafusion_renderable(tree)`). One design decision, two owning modules: adding a fourth guard to the pipeline, or changing which renderability check gates a push, requires editing both or the two surfaces silently disagree — the broadcast site accepting what an N-scan leg rejects, or the reverse. Nothing enforces the agreement except `type_screened_leg_filter`'s own doc comment, which pins the coupling in prose ("`classify_where_filter` carries the same arm at the broadcast site (its `(Some(raw), Some(tree)) if !datafusion_renderable(tree)` case)") and even cites the line number. The plan's own § Patterns row states the principle this violates: "Re-deriving the sequence at a second site would create the second owner that decision exists to prevent." It justified a second CLASSIFICATION (three-way absent/declined/rendered vs. per-conjunct partition), which is genuinely different — but the acceptance predicate underneath is identical and was duplicated with it.
- Fix: In `crates/lakehouse-engine/src/adapter/pushdown/support.rs`, add `pub(super) fn type_accepted_rewrite(expr: &Json, col_types: &[(String, String)]) -> Option<Json>` returning `apply_type_rewrites(expr, col_types).filter(datafusion_renderable)` (adjust for `filter`'s `&Json` argument), with a doc comment naming it the SOLE owner of "a tree the DataFusion scan may be handed": type-rewritten and renderable in that rewritten form, `None` for anything either half rejects.
