## Background

* The feature covers the shared `col_types` lookup helper, the merged `col_types` builder, and the type-aware consumers' use of the Exasol-type-string classifier (issues #265 and #270). The consumers are `guard_like_subject` and the string-conversion decline check `string_conversion_declined`, both in `pushdown/support.rs`.
* `datafusion-scan/type-mapping-module-structure` owns `ExaTypeClass`, `classify_exa_type`, and the classifier's contract in `types/mapping.rs`. This feature consumes that contract and does not restate it.
* Resolving a bare column node's Exasol type is TWO decisions with two owners: node → uppercased name → `col_types` scan belongs to `support`, and type string → type family belongs to `types::mapping`. Keeping them apart holds the column-lookup MISS out of the classifier, which the classifier scenario requires by taking a NON-optional `&str`.
* The `col_types` list is both CONSUMED and PRODUCED with a single fold, the Unicode `to_uppercase`: the shared `column_exa_type` lookup applies it for every type-aware consumer, and the shared `column_types` builder applies it for both wrappers. Issue #265 shipped the builder with a `fold_case` parameter so `involved_table_columns` could keep the ASCII-only `to_ascii_uppercase` it had always applied; issue #270 removes that parameter as dead flexibility, because the two folds cannot produce different output on any name the adapter can receive. Removing it is a SIMPLIFICATION, not a correctness fix. There is consequently no asymmetry left to preserve byte-for-byte and no separate reconciling change to defer.
* The divergence is UNREACHABLE through the real Virtual Schema path, for every column name and every table, and that is a measured finding rather than an assumption. This crate uppercases each Iceberg field name ITSELF before Exasol ever sees it. `resolve_table_schema` (`adapter/pushdown/file_resolution.rs:610-644`) maps every field through `(f.name.to_uppercase(), exasol_ty)` at line 640, and that pair list is the sole input to the per-column `"name"` that `build_virtual_tables` declares in the `createVirtualSchema` response (`adapter/mod.rs:551`, the `json!` at `:576`). Exactly ONE production site declares a column name, reached from exactly ONE caller (`adapter/mod.rs:255`) whose resolver is `resolve_table_schema`, so no column name reaches Exasol un-uppercased.
* LIVE CAPTURE, the plan's task 3 gate, against the local Docker Exasol container per CLAUDE.md § Verification discipline: an Iceberg column named `straße` added to the `typed_distinct_probe` fixture is served by `SELECT COLUMN_NAME FROM SYS.EXA_ALL_COLUMNS WHERE COLUMN_SCHEMA='MY_LAKEHOUSE' AND COLUMN_TABLE='TYPED_DISTINCT_PROBE'` as `STRASSE`, NOT `STRAßE`. The full served list is `ID, C_DECIMAL_A, C_DECIMAL_B, C_DOUBLE, C_VARCHAR, C_DATE, C_TS, C_BOOL, C_PRICE, C_QTY, STRASSE`. `STRASSE` is exactly `"straße".to_uppercase()`, which is what this crate declared: Rust's full-Unicode uppercase maps `ß` to `SS`. The `ß` is therefore erased one layer UPSTREAM of anything Exasol does.
* The agreement argument STANDS unchanged and is what makes #270 byte-identical rather than merely equivalent: a name already produced by `to_uppercase` is a fixed point of both folds — `to_ascii_uppercase` changes only ASCII `a-z`, of which `to_uppercase` output contains none, while `to_uppercase` is itself idempotent, swept exhaustively over all 1,112,064 Unicode scalar values with zero exceptions. What ceases to be true is the earlier closing clause, "the guards' Unicode-folding lookup can never miss a name the ASCII-folding join-side builder produced": after #270 there is no ASCII-folding join-side builder. The lookup and BOTH wrappers now fold identically by construction, so the guards' lookup cannot miss a name either wrapper produced for a structural reason rather than an input-domain one.
* The earlier two-captures-plus-one-inference chain is REFUTED, not merely unmeasured, and both captures are re-scoped rather than deleted. CAPTURE (2) stands as fact: `CREATE TABLE FOLDPROBE.T (nüm INT, straße INT, "nüm_q" INT)` stores `NÜM`, `STRAßE`, and `nüm_q`, so Exasol's fold of a NATIVE unquoted DDL identifier is Unicode SIMPLE (one-to-one) uppercasing and preserves `ß`. It does NOT govern adapter-declared column names, because such a name never reaches Exasol carrying a `ß`. CAPTURE (1) is withdrawn as evidence that Exasol normalizes an adapter-declared name: the names it read (`ID`, `C_VARCHAR`, `C_DECIMAL_A`) are exactly what `resolve_table_schema` declared, so that observation is equally consistent with Exasol echoing the declared name verbatim. The INFERENCE joining the two — that Exasol applies its native-identifier fold to an adapter-declared JSON `"name"` — is contradicted by the live capture, which served the `ß`-collapsed form.
* ONE narrow residual remains, far weaker than the one the refuted chain carried. The agreement argument needs Exasol not to de-normalize an already-uppercase declared name back toward lowercase. Exasol's own identifier fold uppercases, so it cannot introduce lowercase, and the live capture confirms the served form IS the declared form for the one non-ASCII column measured. Every ASCII name captured earlier is consistent with the same conclusion.
* Nothing survives: #270 removes the divergence rather than naming it, and the follow-up issue the earlier bullet cited is CLOSED by this change. That bullet also carried a DESIGN REFUSAL that #270 reverses, and the reversal is recorded here rather than left implicit. The refusal was that "making either builder's fold depend on `resolve_table_schema`'s uppercasing would put one module's decision inside another module's body, which is the information leakage this plan exists to remove" (`specs/_decision/042-refactor-col-types-guard-dedup.md:158` records the same rejection in its options table). That objection no longer decides, for two reasons. FIRST, the surviving fold is selected to match the list's CONSUMER, `support::column_exa_type`, which lives in the same module as the builder — so the builder encodes its OWN module's decision, not a foreign module's, and the alternative (ASCII) is what would leave the in-module consumer's fold unpaired. SECOND, `resolve_table_schema`'s uppercasing is a BEHAVIOR-PRESERVATION premise guarded by a live test, not a fold-selection rule: the fold would still be `to_uppercase` if that premise were dropped, and only the byte-identity claim would weaken. The unreachable-input-domain STANDARD invoked above — an unnamed divergence is indistinguishable from a regression — is unchanged and is applied below to the one new cross-fold pairing #270 creates.
* ONE `col_types` fold test remains, `support.rs`'s `column_exa_type_resolves_unicode_folded_list_and_misses_ascii_folded_list`, and it characterizes no DELIVERED column name. Its two `col_types` slices are CONSTRUCTED literals, `STRASSE` and `STRAßE`, chosen because Rust's two folds disagree on `STRAßE` — which is what makes the miss assertion falsifiable. Neither literal is a list any builder produces: since #270 both builders emit Unicode-folded names only. The builder-side companion test that pinned the two wrappers' divergent folds is deleted with the parameter, because it asserted a disagreement that no longer exists.
* Four further `col_types` linear scans in the pushdown tree are NOT targets of the lookup helper, because their input is an already-resolved column-name `&str` rather than a JSON node: `project_columns`'s `type_by_upper` closure (`support.rs`), the declined-`ORDER BY` hidden-column appender (`topn.rs`), `col_type_for` (`grouped_agg.rs`), and the logical-field scan in `scan/join_scan.rs`. Three of them also answer a different question, returning an owned `String` behind a default (`VARCHAR(2000000)`, `DOUBLE PRECISION`) rather than an `Option`.
* `parse_sort_key_element` (`topn.rs`) is likewise NOT a target even though it performs the node → `type == "column"` → `name` → Unicode-fold half verbatim: it reads an `orderBy` ELEMENT wrapper rather than an expression node, it also parses the `isAscending` and `nullsLast` flags off that wrapper, and it never touches `col_types`. It resolves an identifier, not a type.
* Neither builder wrapper becomes a pass-through of the kind the sibling `datafusion-scan/type-mapping-module-structure` feature rejects. The pass-through RULE is unchanged: a pass-through calls another function with the SAME arguments, and a wrapper supplying an argument the shared builder does not choose is a partial application naming a decision. Only the EXAMPLE narrows. After #270 each wrapper here supplies a different table selection and NOTHING else — `tables.first()` versus the find-by-name closure — so that selection ALONE is what keeps each wrapper a partial application rather than a pass-through, and both wrappers survive under the same exception.
* Removing `fold_case` creates exactly ONE new cross-fold pairing, and it is named here rather than left silent. `joins/rendering.rs::referenced_side_columns` narrows `involved_table_columns`' column list by membership in the set `collect_side_column_names` builds with `to_ascii_uppercase`; both sides folded ASCII before #270 and fold differently after it. They agree for exactly ONE reason, this feature's standing one: both read only names Exasol declared, `resolve_table_schema` already Unicode-uppercased every one of them, and such a name is a fixed point of both folds. There is NO second safety net, and the failure mode if that premise ever broke is a DROPPED column rather than a wider projection. `referenced_side_columns` (`joins/rendering.rs:316-325`) falls back to `full_cols` only when narrowing yields NOTHING: a side whose `full_cols` is `[STRASSE, ID]` measured against an ASCII-folded reference set `{STRAßE, ID}` narrows to `[ID]`, which is non-empty, so the fallback does NOT fire and the fan-out leg loses `STRASSE` while the outer wrapper still renders a reference to it. Only the ALL-MISS case widens a projection; the MIXED case drops a column and yields an erroring or wrong-result wrapper.
* The collect walks' fold divergence is NOT touched by #270 and is a different divergence: `column_tables` and `collect_side_column_names` keep `to_ascii_uppercase` while `collect_all_column_names` keeps `to_uppercase`, which `vs-adapter/pushdown-module-structure`'s "One blind traversal primitive backs every column-collecting walk" scenario forbids unifying. #270 removes a builder parameter, not that.
* `tests/e2e_non_ascii_identifier_test.rs::non_ascii_table_and_column_stay_queryable` is the standing live guard on that premise, not merely a past capture: it seeds an Iceberg `straße` column against a Docker Exasol container and asserts `SYS.EXA_ALL_COLUMNS` serves `STRASSE`. If `resolve_table_schema` ever stopped Unicode-uppercasing declared names, that test fails before any fold could matter.
* `pub(super)` on an item of `adapter::pushdown::support` reaches `adapter::pushdown` and every descendant, including `adapter::pushdown::joins::planning`. The shared builder therefore reaches the joins side at the visibility ceiling `vs-adapter/pushdown-joins-module-structure` already imposes, so no `use` path widens and no PRODUCTION item's visibility widens — the same reasoning this feature's collect-walk scenario records for the blind traversal primitive. No item's visibility widens in the other direction either, and this delta adds NO test-only item: it reaches that outcome by placing each new test where the items it needs are already visible, not by exporting anything.
* That reasoning does NOT run in the opposite direction, which is what decides WHERE each new test is declared. `involved_table_columns` is `pub(super)` in `joins/planning.rs`, `joins/mod.rs` declares `mod planning;` PRIVATE, and `joins/mod.rs` re-imports the name with a plain private `use planning::{involved_table_columns, …}` — so the name is scoped to `adapter::pushdown::joins` and its descendants, and `support` is a SIBLING of `joins`, not a descendant. A test in `support` therefore cannot call it, and neither a `use` re-export nor a test-only wrapper is needed to work around that, because neither test has to sit in `support`. The builder-divergence test SHALL be declared in `joins/planning.rs`'s OWN `#[cfg(test)] mod tests`, where `involved_table_columns` is declared in the same file and `support`'s `pub(super)` items are already reachable — that file's production code already imports two of them. The lookup-helper test stays in `support` and needs no builder at all, because it takes its `col_types` slices as literals. NO item's visibility changes in either direction, and no `#[cfg(test)]`-only export is introduced.
* The joins-side verification asset is already scoped to this change and is consumed rather than restated: `vs-adapter/pushdown-joins-module-structure`'s "Generated join SQL is byte-identical across the split" scenario captures a golden-SQL baseline over "any duplication extraction", and its in-code gate carries the instruction to re-run after every dedup extraction. `vs-adapter/pushdown-joins-module-structure` therefore needs no delta.
* One import removal is a compile-enforced proof that the builder merge actually moved the mapping rather than copying it: `joins/planning.rs` calls `exasol_type_from_json` at exactly ONE site, inside `involved_table_columns`. Once that call lives in the shared builder, the file's `use crate::types::mapping::exasol_type_from_json` is unused, and this crate's `cargo clippy --workspace --all-targets -- -D warnings` gate fails until it is deleted.
* This feature carves the scan spec's `storage` value out of the golden-fixture gate of the builder scenario, "One builder produces the column-type list for both the first-table and the named-table selection". It changes no type-resolve, fold, builder, or classifier rule.
* `vs-adapter/storage-backend-enum` (issue #274) wraps the scan spec's `storage` value in an externally-tagged backend variant. That value is embedded in the scan-driving SQL, so five `dispatch_golden` fixtures and three join golden-SQL assertions change by exactly one substring each.
* The carve-out permits an edit to the `storage` value ALONE. Every other byte of every golden stays unedited, which is what keeps this feature's gate a working proof rather than a retired one.

## Scenarios

<!-- DELTA:CHANGED -->
### Scenario: One helper resolves a bare column node's Exasol type for every type-rewrite guard

* *GIVEN* the per-node type decisions in `pushdown/support.rs` that resolve a bare `column` node against the per-request `col_types: &[(String, String)]` list: `guard_like_subject` and the string-conversion decline check
* *WHEN* either decides what to do with a bare `column` node
* *THEN* exactly ONE helper in `support`, `column_exa_type`, SHALL own that resolve: it SHALL read the node's `name`, fold it with the Unicode `to_uppercase`, scan `col_types`, and return `Option<&str>`, and neither consumer SHALL fold a name or scan `col_types` itself
* *AND* the helper MUST NOT test the node's `type` tag, because a non-`column` node is a pass-through for both consumers while a failed lookup is a decline, so each consumer SHALL keep its own `type == "column"` test ahead of the call
* *AND* the helper SHALL return `None` for both a nameless column node and a name absent from `col_types`, and SHALL be private to `support`
* *AND* the unit test `column_exa_type_resolves_unicode_folded_list_and_misses_ascii_folded_list` SHALL pin the fold over CONSTRUCTED literal lists, calling neither builder: the helper MUST resolve `STRAßE` against a list carrying `STRASSE` and MUST return `None` against a list carrying `STRAßE`, and the test MUST NOT be read as a claim that Exasol delivers such a name

### Scenario: The three type-rewrite guards read their type family from the shared classifier

* *GIVEN* the same three guards' hand-written Exasol type-string predicates — `starts_with("VARCHAR") || starts_with("CHAR")`, the exact match `== "DATE"`, and `starts_with("DECIMAL")` — spelled out once per guard against the family vocabulary `datafusion-scan/type-mapping-module-structure` already records as the `ExaTypeClass` enum and the `classify_exa_type` function in `types/mapping.rs`
* *WHEN* a guard decides what to do with a resolved Exasol type string
* *THEN* each of the three guards SHALL obtain its type family by calling `classify_exa_type` and SHALL retain NO `starts_with` test and NO string equality test against an Exasol type string
* *AND* the classifier's contract SHALL remain owned by `datafusion-scan/type-mapping-module-structure` and is consumed here, NOT restated — in particular its `Decimal` predicate stays `starts_with("DECIMAL")` with no open paren, so the bare argumentless string `DECIMAL` keeps classifying as DECIMAL in all three guards exactly as it does today
* *AND* the two `Option<Json>`-returning guards SHALL each match EXHAUSTIVELY over `Option<ExaTypeClass>` with NO wildcard arm, so a variant added to `ExaTypeClass` later becomes a compile error at each guard rather than a silent decline
* *AND* those two guards' arm sets SHALL differ in exactly ONE arm, `Decimal`: `guard_like_subject` SHALL decline it alongside `Other` and the lookup miss, while `coerce_string_position_arg` SHALL coerce it through `wrap_decimal_to_varchar`; that difference SHALL remain a visible match arm and MUST NOT be abstracted behind a coercion-policy trait, a shared dispatch table, or a parameter, because one closed variation between two functions reads better as two arms than as an indirection
* *AND* `is_bare_decimal_column` SHALL remain a two-way `Decimal`-versus-everything-else test and MAY use a non-exhaustive form, because a family added later genuinely IS "not DECIMAL" for this guard, so exhaustiveness would force an edit that could only restate the same answer
* *AND* the column-lookup miss SHALL stay each guard's OWN branch and MUST NOT be routed through the classifier: no guard SHALL pass a placeholder or sentinel string in place of an absent type, per the recorded requirement that `classify_exa_type` take a non-optional `&str`
* *AND* `wrap_decimal_to_varchar` and `wrap_cast_to_varchar` SHALL be unchanged, and the `decimal_to_varchar_exasol` synthetic node and its `vs-expression` rendering SHALL be unchanged — only the dispatch that ROUTES to them moves
* *AND* the scan-driving SQL generated for every pushdown request MUST be byte-identical to its pre-substitution output EXCEPT for the scan spec's `storage` value, which `vs-adapter/storage-backend-enum` re-encodes as an externally-tagged backend variant over a byte-identical payload, and which `vs-adapter/scan-spec-credential-reference` then replaces with a connection reference or a sealed envelope over that same payload, and every existing guard unit test in `support.rs` MUST pass with NO change to any test assertion or expected value — the per-family tests of all three guards, covering a `VARCHAR` subject, a `CHAR` subject, a `DATE` subject, a `DECIMAL` subject, an integer `DECIMAL(p,0)` subject, a `DOUBLE PRECISION` or `BOOLEAN` or `TIMESTAMP` subject, and an unresolvable column, embedding no scan spec and therefore being unedited, and being the gate that makes this substitution's behavior-preservation falsifiable

### Scenario: The type-aware consumers read their type family from the shared classifier

* *GIVEN* `guard_like_subject` and the string-conversion decline check, which each branch on the family of a resolved Exasol type string
* *WHEN* either decides what to do with a resolved type
* *THEN* each SHALL obtain the family by calling `classify_exa_type` (`datafusion-scan/type-mapping-module-structure`), SHALL retain NO `starts_with` or equality test against an Exasol type string, and SHALL match EXHAUSTIVELY over `Option<ExaTypeClass>` with NO wildcard arm, so a variant added later is a compile error at each consumer
* *AND* the two arm sets SHALL differ in exactly ONE arm, `Decimal`: `guard_like_subject` declines it with `Other` and the lookup miss, while the decline check passes it with `Character` and `Date`; that difference SHALL stay a visible match arm, not a policy trait, a shared table, or a parameter
* *AND* the lookup miss SHALL stay each consumer's own `None` arm and MUST NOT reach the classifier as a placeholder string
