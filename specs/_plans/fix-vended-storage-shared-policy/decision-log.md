# Decision Log: fix-vended-storage-shared-policy

## Interview

**Q:** For the S3 address rule fix (defect 2), when BOTH the vended response and the CONNECTION carry a non-empty endpoint/region, which one wins? The issue text says "use what was vended" but also says the CONNECTION value "overrides what it states" — those two clauses conflict as written.
**A:** CONNECTION always wins when set. A static CONNECTION endpoint/region, when the operator has configured one, always takes precedence over whatever the catalog vends; vended addressing fills in only when the CONNECTION is silent. Concretely, for `endpoint` and `region` independently: if `ConnectionCreds.endpoint` / `ConnectionCreds.region` is non-empty use it, otherwise fall back to whatever the vended response states (which may also be empty). `path_style` keeps its existing derivation from whichever endpoint won, unless a `path_style`/`s3.path-style-access` value is explicitly stated. How the existing vended-only `s3.path-style-access` override key and any CONNECTION path-style setting compose was left open and needed a recorded design decision.

**Q:** Scope: this fix spans a mechanical part (share scheme classification + construction, fix the abfs consent gate) and a policy-changing part (the credentials/addressing split, which supersedes "MUST NOT read CONNECTION value" clauses in two specs). One plan or two?
**A:** One plan covering both. Author one `plan.md` covering shared scheme/host/account-name extraction, shared S3/ADLS construction with the abfs gate, AND the credentials/addressing split with its spec supersessions.

## Design Decisions

### [1] CONNECTION-wins-when-set addressing, resolved per field

- **Decision:** Resolve the vended S3 store address per field, independently: `endpoint` from `ConnectionCreds.endpoint` when non-empty, else the vended `s3.endpoint`, else empty; `region` from `ConnectionCreds.region` when non-empty, else the vended `client.region`, else empty. A backend with both empty is returned successfully and resolves through the AWS default chain. The plaintext-transport consent gate applies to the RESOLVED endpoint regardless of which source supplied it.
- **Alternatives:** Vended-wins-when-present (the issue's first clause), which the interview overruled; whole-source precedence, where one source wins both fields together — rejected because a CONNECTION stating only a region beside a response stating only an endpoint would then discard one usable value for no reason.
- **Rationale:** An operator who configured a store address means it, and a per-field rule loses no information. Making the gate follow the resolved endpoint rather than its origin keeps the rule a statement about the transport the store will actually use, which is the only thing plaintext consent is about.
- **Promotes to ADR:** yes

### [2] `path_style` does not read the CONNECTION, because the field cannot express "unstated"

- **Decision:** `path_style` = the vended `s3.path-style-access` when the response states a parseable boolean, else whether an endpoint was RESOLVED at all (the CONNECTION's when it won, the vended one otherwise). `ConnectionCreds.path_style` does NOT participate in the CONNECTION-wins rule and is not passed to the vended selectors.
- **Alternatives:** Admit `ConnectionCreds.path_style` under the same CONNECTION-wins rule — rejected: it is a plain `bool` defaulting to `true` (`connection.rs` parses `json.get("path_style").and_then(as_bool).unwrap_or(true)` and discards whether the key was present), so it cannot distinguish "the operator set false" from "the operator said nothing", and admitting it would make the vended `s3.path-style-access` override unreachable on every CONNECTION that omits the key. Widening the field to `Option<bool>` — rejected: it ripples into the static `storage_block` path, whose `true` default is shipped behaviour this plan must not change, and into every `ConnectionCreds` literal in the suites, for a knob whose vended derivation already has a correct answer.
- **Rationale:** The composition question the interview left open resolves on a type limitation, not a preference. Recording it as such stops the next reader re-opening it as an oversight. The derivation is also load-bearing rather than cosmetic: `register_side_store` treats `path_style` as the gate on whether `endpoint` reaches `AmazonS3Builder` at all, so an endpoint beside `path_style: false` is silently dropped for a virtual-hosted host — which is why the default couples to the resolved endpoint rather than to a constant.
- **Promotes to ADR:** yes

### [3] Extraction stays forked; policy does not — stated as a rule, not left to be re-derived

- **Decision:** Record the principle in the spec library, not only in this plan: a catalog kind MAY fork on HOW a value is read off the wire; it MUST NOT fork on WHAT makes the resulting value acceptable. Consent gates, address rules, and target-variant decisions get exactly one home both kinds call. The per-catalog wire extraction (`select_credential_source` plus flat-map reads for Iceberg REST; typed `TemporaryTableCredentials` field reads for Unity) stays forked because the two wire shapes genuinely differ.
- **Alternatives:** Fix the two defects in place in `unity/vended.rs` — rejected: it re-copies the gate rather than removing the seam that lost it, and defect 1 exists precisely because a copy was incomplete. Unify the wire extraction too, behind a trait — rejected as a shallow abstraction: a flat `HashMap` with longest-prefix credential-source selection and a typed three-family response have nothing in common above the neutral values they produce.
- **Rationale:** The next catalog kind's author needs the rule stated where they will read it. Both defects came from a copy that stayed consistent in five places and diverged in two; naming the seam is what makes the sixth and seventh divergence a build or test failure instead of a silent gap.
- **Promotes to ADR:** yes

### [4] The shared home is `storage.rs`, and moving construction there SHRINKS the variant-naming invariant

- **Decision:** Put the shared derivations, the neutral `VendedS3` value, both construction functions, and both consent gates in `crates/lakehouse-catalog/src/storage.rs`, beside `classify_vended_scheme`. The recorded exhaustive list of modules permitted to name a `StorageBackend` variant goes from SIX to FOUR: `storage.rs`, `scan/object_store.rs`, `storage_block` (`connection.rs`), and `CommonScanSpec`'s `impl Default` (`scan/spec.rs`).
- **Alternatives:** A new `vended_policy.rs` module, on the "group by reason to change" reading — rejected: the enum's own module already owns which module may name a variant, so construction there removes two entries from that list instead of adding a fifth, and `VendedBackendKind`/`classify_vended_scheme` already live there. Keeping construction in the selectors and sharing only the gates — rejected: it leaves two construction sites that can disagree about which fields the variant carries, which is the same seam one level down.
- **Rationale:** The invariant this feature exists to hold gets narrower, not wider, which is the opposite of the last two deltas to it. That is the strongest available evidence the seam moved to the right place.
- **Promotes to ADR:** no

### [5] Addressing arrives as a capability-narrowed type, and the credential guarantee moves from the signature to a probe

- **Decision:** Add `pub struct StaticStoreAddress` carrying exactly two addressing fields, `endpoint` and `region`, with `Default` and exactly one `impl From<&ConnectionCreds>`, and pass `&StaticStoreAddress` to both vended selectors. Both fields are declared NON-`pub` and read through `pub fn endpoint(&self) -> &str` / `pub fn region(&self) -> &str`, so outside `storage.rs` the type admits only `Default` and that one conversion and a field-by-field literal does not compile. Two source-level probes back it: one asserting the struct's own declaration names no field spelled `access_key`, `secret_key`, `session_token`, `token`, `account_key`, `sas_token`, or `password`, and one asserting the declaration keeps both fields non-`pub`.
- **Alternatives:** Pass `&ConnectionCreds` — rejected outright: it makes "a vended credential never falls back to a static one" unenforceable, which is the guarantee the plan must preserve. Pass two bare `&str` parameters — rejected: two adjacent same-typed parameters let an endpoint/region transposition compile silently. Build the value at each call site — rejected: it would put "which CONNECTION fields may cross into vended resolution" in as many places as there are callers. Keep both fields `pub` and enforce the one-construction rule with a source-level probe forbidding a `StaticStoreAddress {` literal outside `storage.rs` — rejected: a text probe can only see the sources it enumerates and can be defeated by formatting, while field privacy is checked by the compiler at every call site in both crates; the probe form also has to carve out `storage.rs` itself, which is exactly the file whose literals matter least.
- **Rationale:** The superseded clauses carried the credential guarantee on the SIGNATURE. Superseding them without a replacement mechanism would leave the guarantee as prose. Half of the replacement — "the type cannot carry a credential" — is checkable by a probe over the declaration; the other half — "there is EXACTLY ONE construction from the CONNECTION" — is not, because a probe reading field names cannot see what flows INTO a `String` field named `endpoint`. Field privacy closes that half at the compiler rather than at review, and the accessors keep the reading side honest: `s3_backend` reads the address through them, so they are the production read path rather than dead surface. The type's field list remains the readable whitelist, and one conversion keeps that whitelist single-homed.
- **Promotes to ADR:** yes

### [6] Consent gates live inside the construction functions, not at the classification step

- **Decision:** Put the `abfs://` gate inside `adls_backend` and the plaintext-endpoint gate inside `s3_backend`, rather than in a widened `classify_vended_scheme`.
- **Alternatives:** Gate at classification, so any caller that classifies is gated — rejected: a caller that reaches a construction function directly would then bypass it, and construction is the operation this plan is making shared and reusable.
- **Rationale:** No selector can construct an ADLS backend without the `abfs` gate having run, which is the exact class of failure defect 1 was. Placing the gate at the last step before the value exists is the placement that cannot be routed around.
- **Promotes to ADR:** no

### [7] Probe repointing: three rules, not one target

- **Decision:** Replace the two per-selector `StorageBackend`-variant probes with (a) one probe asserting every extracted `StorageBackend` variant appears as a `StorageBackend::<Variant>` construction in `storage.rs`'s production source, (b) one per-selector probe asserting every extracted `VendedBackendKind` variant appears in each selector's production source, and (c) one probe asserting the two enums' extracted variant-name SETS are equal. All three extract from the enums' own sources through one shared extractor; a hardcoded list satisfies none.
- **Alternatives:** Repoint to `storage.rs` alone, as the issue's "one probe target instead of two that can drift" suggests — rejected: it stops forcing each selector to dispatch every kind, which is weaker than today's gate. Delete the probes as redundant now that construction is shared — rejected: the selectors still match on a URI scheme rather than on a `StorageBackend`, so a third variant would still not break their build, and that compile-time hole is the whole reason the probes exist.
- **Rationale:** The probe over `storage.rs` is non-vacuous because the enum's own method arms spell themselves `Self::<Variant>` — only a construction expression spells the qualified form. Chaining the three rules means a third `StorageBackend` variant fails at every level: set-equality until a third kind exists, per-selector dispatch until both selectors handle it, construction until the shared home builds it.
- **Promotes to ADR:** no

### [8] Shared error texts name no catalog kind

- **Decision:** The `abfs://` refusal, the plaintext-endpoint refusal, and the ADLS account-name refusal each get ONE neutral text in the shared home, naming the location, the offending value, and `ALLOW_HTTP` where relevant — no "the Unity Catalog" or "vended credentials were requested" framing. Per-kind extraction errors (missing `aws_temp_credentials`, missing `s3.access-key-id`, missing `adls.sas-token.<host>`) keep their existing kind-specific texts, because extraction is where the kinds genuinely differ.
- **Alternatives:** Keep both texts and parameterise the shared function with a catalog-kind label — rejected: two texts for one rule are two things to drift, and a label parameter is a decision the shared home declined to make.
- **Rationale:** Every existing assertion on these paths is on neutral tokens — the table location, `ALLOW_HTTP`, the endpoint value — verified against `assert_refused` in `vended_tests.rs` and the three `assert!`s in `unity/vended_tests.rs::plaintext_endpoint_requires_allow_http`, so a neutral text passes both suites unedited.
- **Promotes to ADR:** no

### [9] The Iceberg table-spec compliance rule is not triggered; the REST-spec check is, and passes

- **Decision:** Record explicitly that `CLAUDE.md`'s mandatory Apache Iceberg table-spec check does NOT apply to this plan, and that the Iceberg REST OpenAPI check DOES and finds no deviation.
- **Alternatives:** Run the table-spec check anyway to be safe — declined as noise: it would produce quotations about `location` and `file_path` that this plan does not touch, diluting the rule for plans that do.
- **Rationale:** The `CLAUDE.md` rule is scoped to a plan "that touches scanning, pushdown, or schema/type handling". This plan touches storage credential and address resolution only: no file pruning, no snapshot or manifest reading, no delete-file handling, no projection, no type mapping. The one table-spec dependency this area has — a table `location` is absolute and therefore scheme-bearing — is untouched, because the backend variant still comes from that scheme alone. On the REST side the normative text `pushdown-planning-cloud-credentials` already records as fetch-verified governs which RESPONSE map a credential is read from (`StorageCredential.prefix` longest-prefix selection; `storage-credentials` checked before `config`); `select_credential_source` implements both and this plan does not touch it. Neither rule speaks to a client's own static configuration, and `s3.endpoint` is not in the document's enumerated `## AWS Configurations` list at all — it is read under the `additionalProperties: string` allowance. Letting an operator-configured endpoint or region take precedence over a vended one is therefore an unconstrained client configuration choice. No new normative text is relied on: the quotations are the recorded, previously fetch-verified ones.
- **Promotes to ADR:** no

### [10] Scope: eight spec deltas, and two specs deliberately left alone

- **Decision:** Author deltas to `vs-adapter/storage-backend-enum`, `vs-adapter/unity-catalog-vended-credentials`, `vs-adapter/pushdown-planning-cloud-credentials`, `vs-adapter/catalog-crate-structure`, `vs-adapter/connection-credentials`, `e2e-harness/cloud-e2e-harness`, `e2e-harness/lakekeeper-e2e-harness`, and `azure-e2e/azure-e2e-harness`. Leave `vs-adapter/pushdown-module-structure` and `vs-adapter/rest-catalog-oauth-auth` alone.
- **Alternatives:** The issue's spec-delta table named only two specs (`storage-backend-enum` and `unity-catalog-vended-credentials`). A search of the live library found five more places the change makes a clause false or a citation stale: `pushdown-planning-cloud-credentials` carries a SECOND copy of the "MUST NOT take any other CONNECTION-derived value" clause plus four scenario clauses forbidding CONNECTION `endpoint`/`region` reads and one requiring the deleted store-address error; `catalog-crate-structure` enumerates the crate's `pub` set exhaustively and a new public type must be admitted by a superseding scenario; `cloud-e2e-harness` asserts the vended address as a pass/fail gate; `lakekeeper-e2e-harness` frames its vended scenario as reading no CONNECTION storage field at all; `azure-e2e-harness` points at `vended.rs` for the `abfs` gate's unit coverage. An EIGHTH spec, `vs-adapter/connection-credentials`, was MISSED by that search and added in review round 1: it carries a second copy of the SigV4-static-values rule in its Background and, more directly, a normative scenario clause naming `endpoint` and `region` in the list of fields the adapter "MUST NOT read … into the effective scan storage".
- **Rationale:** `pushdown-module-structure` says only that `resolve_vended_storage` MUST NOT be added to the pushdown façade and stays reachable as `lakehouse_catalog::resolve_vended_storage` — both remain true, so it needs no delta. Every other spec above would otherwise be left carrying a normative clause the implementation contradicts. Three adjacent statements were re-checked one by one in the same pass, and each got its own answer:
  - `connection-credentials` scenario "Static storage credentials are ignored, not rejected, when vending is requested" — SUPERSEDED. Its clause names `endpoint`, `region`, and `path_style` explicitly in a `MUST NOT read … into the effective scan storage` list, so the implementation contradicts it outright. The delta reproduces the scenario with that clause split into a credential half (unchanged) and an addressing half, and CITES `pushdown-planning-cloud-credentials` for the precedence rule instead of restating it, so the rule keeps one home.
  - `connection-credentials` description sentence "Under vending, the CONNECTION's storage credentials are ignored" — SUPERSEDED. This feature owns the CONNECTION's field vocabulary and elsewhere groups `endpoint` and `region` with the key pair under "static S3 credentials", so leaving the summary as written would contradict the corrected scenario inside the SAME file.
  - `rest-catalog-oauth-auth` clause "each `ScanSpec` storage block SHALL carry only the S3 storage credentials — the vended STS credentials when `use_vended_credentials` is enabled and they were resolved, otherwise the static credentials" — ACCURATE AS WRITTEN, no delta. Its scenario's subject is that catalog-auth props never reach a `ScanSpec`; the clause names no addressing field, the credential half it states is exactly what this plan preserves, and it closes with the explicit deferral "exactly as in `vs-adapter/pushdown-planning-cloud-credentials`", which is where the effective-storage rule is single-homed. Authoring a ninth delta to restate a citation would recreate the duplication this plan removes.
- **Promotes to ADR:** no

### [11] The behaviour change is a breaking change and is named as one

- **Decision:** Record in `plan.md` § Impact that a deployment setting `use_vended_credentials: true` alongside a non-empty CONNECTION `endpoint` or `region` changes behaviour: the CONNECTION value now wins where the vended one used to. Also record that the new plaintext gate on a CONNECTION-supplied endpoint tightens an existing path.
- **Alternatives:** Frame the whole change as a bug fix — rejected: defect 2's fix is a bug fix, but the precedence direction the interview chose changes a shipped resolution on configurations that work today.
- **Rationale:** Both in-repo vended fixtures carry an empty CONNECTION `endpoint` and `region`, so no suite can observe the regression; that is exactly why it must be written down rather than discovered by an operator. The `lakekeeper-e2e-harness` delta promotes its empty-`endpoint` assertion to a stated precondition for the same reason.
- **Promotes to ADR:** yes

### [12] Delta form: retitle by REMOVED + NEW, and reproduce a scenario verbatim when only a cross-reference moves

- **Decision:** Where a scenario's own TITLE asserts the superseded rule — "Vended-credentials request advertises access delegation and takes every S3 transport value from the response" — mark the old title `DELTA:REMOVED` (with steps stating why it goes and what replaces it, so the validator's GIVEN/WHEN/THEN requirement is met) and add the retitled scenario as `DELTA:NEW`. Where only a cross-reference moves — the `azure-e2e-harness` pointer to where the `abfs://` gate is unit-covered — mark the affected scenario `DELTA:CHANGED` and reproduce every other clause VERBATIM.
- **Alternatives:** Keep the stale title under `DELTA:CHANGED` and rewrite only its clauses — rejected: the title would keep asserting "takes every S3 transport value from the response", which is the rule this plan deletes, and titles are what a reader scans. A Background-only delta for `azure-e2e-harness` — rejected because `speq plan validate` fails a delta with no scenario, and because leaving the stale `crates/lakehouse-catalog/src/vended.rs` pointer standing in the library is the drift this plan exists to remove.
- **Rationale:** `storage-backend-enum` uses `DELTA:NEW` with explicit in-clause supersession, matching how its own clauses were superseded in the two preceding deltas to that feature; the other five use `DELTA:CHANGED` so no false clause is left physically standing in a scenario body. The form follows what the recorder must do to leave the library internally consistent, not a single house rule applied uniformly.
- **Promotes to ADR:** no
