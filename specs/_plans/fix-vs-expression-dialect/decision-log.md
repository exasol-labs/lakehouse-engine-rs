## Design Decisions

### [1] One guarded match arm owns the Exasol-dialect rule

- **Decision:** State one rule, "in the Exasol dialect, render what Exasol sent", and give it a single owner: the `if dialect == Dialect::Exasol` guarded `function_scalar` arm that issue #210 already added for the string-function family, promoted to a gate ahead of the whole `function_scalar` dispatch and driven by one declaration (decision [12]). The math family, the field-shortcut date functions, `WEEK`, the `*_BETWEEN` family, `DATE_TRUNC`, `TO_DATE`, `TO_TIMESTAMP`, `GREATEST`, `LEAST`, `NULLIF`, `NULLIFZERO`, and `ZEROIFNULL` are declared there instead of gaining private dialect branches. The now-family is the one family removed from the declaration rather than added to it, per decisions [14] and [15]. Constructs the declaration marks `Shaped`, and node types outside `function_scalar` (`function_scalar_extract`, `predicate_like_regexp`, the two timestamp literals), branch inline with `match dialect`, which is the shape issue #197's `MOD` fix uses.
- **Alternatives:** (a) A per-dialect name lookup table keyed by function name. Rejected: it adds a second mechanism and an indirection for a rule whose content is "do not translate", and a table cannot express the `EXTRACT`, `REGEXP_LIKE`, or timestamp-literal shape changes anyway. (b) A `Dialect` trait with two implementations. Rejected: the two dialects differ at roughly a dozen of some fifty arms, so two full implementations would duplicate the other thirty-eight and invite exactly the silent drift this plan exists to end. (c) A private `match dialect` inside each affected arm, following #197 literally everywhere. Rejected: it scatters one decision across ten arms, so a reader cannot see the rule and the next arm added has no obvious place to inherit it.
- **Rationale:** Per `/speq:design-philosophy`, the defect is a design decision with no owner: the same "which parser reads this fragment" question was answered independently in `render_cast_target`, in the `MOD` arm, and in the #210 string arm, and left unanswered in the rest. Giving the decision one home is the fix. The exclusions are stated as a declared per-name form (decision [12]) rather than implied by arm ordering, because arm ordering is invisible to a reader scanning a 500-line `match` and was itself the mechanism that left `SIGN` broken.
- **Promotes to ADR:** yes

### [2] Scope extended to two failure paths issue #209 does not name

- **Decision:** Fix, in the same plan, two further Exasol-dialect renderings verified during planning to fail on live Exasol 2025.2.1 (the image pinned in `docker-compose.yml`): `predicate_like_regexp` — and its `function_scalar` `REGEXP_LIKE` alternate encoding — rendering `regexp_like(s, p)` (`syntax error, unexpected REGEXP_LIKE_`, since `REGEXP_LIKE` is an infix predicate in Exasol, not a function), and `literal_timestamp` / `literal_timestamp_utc` rendering `arrow_cast(...)` (`function or script ARROW_CAST not found`).
- **Alternatives:** Restrict the plan to the arms issue #209 enumerates and file two follow-up issues. Rejected: both are the same defect class on the same code path, both are reachable today (`FN_PRED_REGEXP_LIKE`, `LITERAL_TIMESTAMP`, and `LITERAL_TIMESTAMP_UTC` are all advertised), and each fix is a few lines inside an arm this plan already edits. Splitting them would ship a "systemic remainder" fix that still leaves a systemic remainder.
- **Rationale:** Issue #209 frames itself as the systemic fix for every renamed or re-shaped rendering, not as a list of seven queries. A fix that leaves two verified compilation errors in place would not satisfy that framing, and the regression test in decision [7] would fail on them anyway. A third candidate, the adapter-synthesized `decimal_to_varchar_exasol` node, was dropped from scope after review: it is unreachable from every Exasol-dialect consumer today (see the `[plan-review]` entry below).
- **Promotes to ADR:** no

### [3] Uniformity over minimal diff: functions that already parse in Exasol are folded into the verbatim rule

- **Decision:** Apply the verbatim rule to every Exasol-native scalar function, including the ones whose current rendering already parses in Exasol: `NULLIFZERO`, `ZEROIFNULL`, `GREATEST`, `LEAST`, `DATE_TRUNC`, `TO_DATE`, `TO_TIMESTAMP`, `DAYS_BETWEEN`, and the whole math family apart from `SIGN`. For most of these the emitted string changes only in name case; `NULLIFZERO` and `ZEROIFNULL` stop being rewritten to `nullif(x, 0)` and `coalesce(x, 0)`.
- **Alternatives:** Change only the arms that currently produce a compilation error, which is the smaller and lower-risk diff. Rejected on maintainability: a rule applied to some arms and not others is not a rule a future reader can apply. They would have to test each name against live Exasol to learn whether its current rendering is principled or merely lucky, which is how the `*_BETWEEN` family shipped broken in the first place.
- **Rationale:** The whole value of the verbatim rule is that it needs no per-function verification. Verified on live Exasol 2025.2.1 that every math name in the arm exists natively (`ABS`, `FLOOR`, `CEIL`, `SQRT`, `EXP`, `LN`, `DEGREES`, `RADIANS`, `SIN`, `COS`, `TAN`, `ASIN`, `ACOS`, `ATAN`, `SINH`, `COSH`, `TANH`, `COT`, `ROUND`, `TRUNC`, `LOG`, `POWER`, `ATAN2`), so folding them in changes no result.
- **Promotes to ADR:** yes

### [4] The now-family renders as bare Exasol keywords, correcting a latent wrong answer

> **SUPERSEDED by decision [14].** The human chose to withdraw the four capabilities instead. The four names are no longer rendered in either dialect, so the `BareKeyword` form this entry decided is not implemented. This entry does NOT promote to an ADR. Its research is carried forward by decision [14], which promotes, so the permanent library records the withdrawal rather than the abandoned rendering. Read the bullets below as the pre-supersession position: the zone-and-clock research they establish still holds, but every forward-looking statement in them has been replaced by decisions [14] and [15].

- **Decision:** Render `CURRENT_DATE`, `SYSDATE`, `CURRENT_TIMESTAMP`, and `SYSTIMESTAMP` as their own bare Exasol keywords in the Exasol dialect, with no parentheses and no collapsing of one name onto another. The mechanism is a declared `ExasolForm::BareKeyword` row per name, not a special case inside the verbatim branch; see decision [13].
- **Alternatives:** Leave `current_date()` and `now()` in place. Issue #209 claims Exasol rejects the parenthesised form, but that claim is false: both `SELECT current_date()` and `SELECT now()` execute successfully on live Exasol 2025.2.1, so neither is a compilation error and neither is required by the issue's stated scope.
- **Rationale:** The current mapping collapses `SYSDATE` onto `CURRENT_DATE` and `SYSTIMESTAMP` onto `CURRENT_TIMESTAMP`, erasing Exasol's database-time versus session-time distinction. That is a silent wrong answer rather than a loud failure, which is worse. The verbatim rule removes it for two lines of change, and this is the one behavior change in the plan that an operator could observe as a different value rather than as an error becoming a result. It is called out in `plan.md`'s Impact for that reason.
- **Residual gap, as it stood before decision [14] (no longer current):** this entry's fix reached the Exasol dialect only. The DataFusion dialect would have kept `SYSDATE` → `current_date()` and `SYSTIMESTAMP` → `now()`, so the two dialects would have disagreed for these four names and the wrong-answer path would have survived on the scan path. That residual gap no longer exists: task 2 deletes both DataFusion arms, § Requirements excepts the four names from the DataFusion freeze, and § Non-Goals now names the option-C restoration instead of this collapse. No GitHub issue is required for the collapse. The one required issue is stated once, in decision [14].
- **Why the DataFusion dialect cannot distinguish the four names (researched after the human asked to fix both sides):** Renaming them in the DataFusion dialect would fix nothing, because the scan layer holds no clock context to distinguish. Exasol's distinction is a time-zone interpretation of one instant, not two clocks. `CURRENT_TIMESTAMP` returns the current timestamp interpreted in the session time zone, typed `TIMESTAMP(3) WITH LOCAL TIME ZONE`. `SYSTIMESTAMP` returns the same instant interpreted in the database time zone, typed `TIMESTAMP(3)`. `CURRENT_DATE` evaluates `TO_DATE(CURRENT_TIMESTAMP)` and `SYSDATE` evaluates `TO_DATE(SYSTIMESTAMP)`. Rendering the distinction therefore requires the two zone values, `SESSIONTIMEZONE` and `DBTIMEZONE`. Neither value reaches the scan UDF, and no path can obtain them:
  - Exasol's pushdown request carries no zone. `withLocalTimeZone` is a boolean type flag on a `dataType` node, not a zone value (`adapter/pushdown/support.rs:1308-1312`).
  - `CommonScanSpec` (`scan/spec.rs:588`) carries nineteen fields and none is temporal. `ScanSpec` (`:773`) adds only `files`. `StorageProps.session_token` (`:225`) is an AWS STS credential, not an Exasol session.
  - The scan script declares exactly two VARCHAR arguments: the shard-invariant common blob and the per-shard file list (`scan/mod.rs:165-173`). No environment or session value is passed.
  - The scan UDF opens no connect-back session, so it cannot query either zone. `grep -rn "connect_back(" crates/` returns zero matches. The adapter calls only `ctx.connection(name)`, which reads a CONNECTION object's credentials.
  - The SDK's `UdfContext` metadata surface exposes no clock and no zone (`exasol-udf-sdk-0.21.0/src/context.rs:122-232`). It offers `session_id`, `statement_id`, `node_id`, `node_count`, `vm_id`, `database_name`, `database_version`, `script_name`, `script_schema`, `current_user`, `current_schema`, `scope_user`, `memory_limit`, and `cluster_ip`.
  - `session_config_for_spec` (`scan/mod.rs:129-151`) never sets `datafusion.execution.time_zone`, so DataFusion's `+00:00` default governs.
  - DataFusion holds one clock and one zone knob. `now()` (alias `current_timestamp`) and `current_date()` both read `datafusion.execution.time_zone`, and DataFusion models no database-versus-session zone pair. One session therefore cannot render both.
- **A larger defect the collapse hides:** All four names are wrong on the scan path, not only the collapsed pair. The scan evaluates `now()` against the UDF container's clock in UTC, never in Exasol's session or database zone. The fan-out invokes the scan once per shard (`adapter/pushdown/support.rs:425`), and each call builds and drops its own `SessionContext` (`scan/mod.rs:225-238`). A rendered clock call is therefore evaluated G times independently, with no statement-level anchor. Exasol's now-family is statement-constant.
- **Reachability of the scan-side gap:** All four names are advertised (`adapter/capabilities.rs:113-114`, `:122-123`), so Exasol can push them. A filter-position clock node reaches the DataFusion dialect through `render_df_filter_safe` (`adapter/pushdown/mod.rs:214`). A select-list `CURRENT_TIMESTAMP` does not: its declared `TIMESTAMP WITH LOCAL TIME ZONE` fails `is_valid_emits_output_type` (`adapter/pushdown/support.rs:1016-1018`) and widens to the full-row fallback.
- **How the follow-up was resolved (this bullet's earlier "narrowed, not closed" position is superseded):** the real subject was never "the DataFusion dialect keeps the collapse". The scan layer has no Exasol clock context at all, so the collapse was a symptom. Three options were escalated to the human with each option's cost: withdraw the four capabilities, plumb both zones plus a statement anchor into the scan spec, or accept the divergence. The human chose withdrawal. Decision [14] records that choice, and § Requirements, § Non-Goals, and § Impact all changed accordingly, so this entry's earlier claim that those three sections were unchanged no longer holds.
- **Superseded, so it does not promote:** decision [14] carries this entry's research into the permanent library instead.
- **Promotes to ADR:** no

### [5] The Exasol dialect imposes no arity check

- **Decision:** The Exasol-dialect verbatim arm forwards the argument list unchanged and does not validate argument count, even where the DataFusion-dialect arm does.
- **Alternatives:** Keep each family's existing arity check in both dialects. Rejected: Exasol's compiler emitted a call its own engine accepts, so a translator-side arity check on that path can only reject valid input.
- **Rationale:** This is not new; it is the rule the #210 string arm already follows, and it is load-bearing there. `vs-adapter/pushdown-planning-string-fn-type-coercion` declines a three-argument `INSTR(s, sub, start)` from the DataFusion scan precisely because the Exasol wrapper can still evaluate it verbatim. Extending the same rule to the other families keeps one behavior instead of two.
- **Promotes to ADR:** yes

### [7] A per-node name-equality sweep test enforces the rule, so a future arm cannot silently forget it

- **Decision:** Add `exasol_dialect_renders_declared_verbatim_surface`, a unit test whose `function_scalar` rows are iterated from `TRANSLATED_SCALAR_FNS` (decision [12]) rather than hand-written. Each declared name is looked up in a fixture map of representative nodes; the test fails naming any declared name with no fixture, and any fixture whose name is not declared. Per row it derives the expected Exasol string from the declared form: `VerbatimCall` → `<NAME>(<rendered args>)` from the node's own uppercased `name`. Six constructs sit outside that `<NAME>(<args>)` shape and each asserts the expected string its fixture declares: (1) the operator wire names `ADD`, `SUB`, `MULT`, `FLOAT_DIV`, `NEG`; (2) `MOD` → `MOD(<a>, <b>)`; (3) `CONCAT` → chained `||`; (4) `CAST` → `render_cast_target`'s per-dialect target; (5) the `function_scalar` `REGEXP_LIKE` alternate encoding (`lib.rs:678`) → `(<subject> REGEXP_LIKE <pattern>)`; (6) `function_scalar` named `CASE` (`lib.rs:893`) → `CASE WHEN <cond> THEN <res> [ELSE <else>] END`. The now-family was a seventh construct until decision [15] removed the four names from the declaration; an undeclared name has no sweep row. Each dialect-branching node type outside `function_scalar` gets its own explicit row and expected per-dialect string. The DataFusion-only token list (`signum`, `date_part`, `strpos`, `arrow_cast`, `character_length`, `octet_length`, `regexp_like(`, `current_date()`, `now()`, `nullif(`, `coalesce(`) is kept as a secondary assertion.
- **Alternatives:** (a) Rely on the per-family paired-dialect tests alone. Rejected: those only cover arms someone remembered to test, which is the failure mode that produced this issue. The `*_BETWEEN` family had per-function E2E parity tests and still shipped a broken Exasol rendering, because every one of those tests exercised the DataFusion path. (b) A deny-list of DataFusion-only tokens as the primary assertion, which was this plan's first shape. Rejected on review: a deny-list can only catch the arms already known today, so a future `SUBSTRING`, `NVL`, or `DATE_BIN` arm passes it. "Every DataFusion-only token" is also not a testable set, because it is unbounded. (c) Keep the table hand-written and assert declared-set membership over its rows, which was round 1's shape. Rejected on review: that only checks the names someone already listed, so a name absent from both the table and the set passes.
- **Rationale:** Deriving the rows from the declaration is what makes coverage structural rather than reviewed. A hand-written table can only assert things about names it already contains, which is why round 1's membership assertion did not deliver the guarantee the artifacts claimed. Iterating the declaration inverts that: the test enumerates what the crate translates, so a name cannot be swept-over by being forgotten twice. Name equality remains the right per-row assertion, because it is a property of the node, checkable without enumerating what the other dialect might emit, so it holds for names that do not exist yet.
- **Bounds of the guarantee:** The test enforces that every *declared* name has a fixture and renders as declared. It cannot enforce that every *node type* outside `function_scalar` has a row, because node types are matched on the `type` string in the outer walker and are not declared anywhere. Those five rows (`function_scalar_extract`, `function_scalar_cast`, `predicate_like_regexp`, `literal_timestamp`, `literal_timestamp_utc`) are named in the `Dialect` doc comment (task 6) and reviewed, not derived.
- **Promotes to ADR:** yes

### [10] Translator scenarios map to unit tests, wrapper-compilation scenarios to E2E

- **Decision:** Every scenario that asserts a rendered string maps to a unit test in `crates/vs-expression/src/lib.rs`; every scenario whose truth depends on Exasol actually compiling the SQL maps to an integration test in `crates/lakehouse-engine/tests/e2e_capability_test.rs` using the in-session native-oracle idiom already used in that file's section 8.16.

### [12] One declaration gates the dispatch and drives the sweep table

- **Decision:** Declare the translated `function_scalar` surface exactly once in `crates/vs-expression/src/lib.rs`: `const TRANSLATED_SCALAR_FNS: &[(&str, ExasolForm)]`, one row per name the arms match today (76 names once decision [15] removes the four now-family names), where `enum ExasolForm { VerbatimCall, Shaped }` states what the Exasol dialect does with that name. Two readers sit on it — `declared_scalar_fn(name) -> Option<ExasolForm>` and `is_exasol_verbatim(name) -> bool`. The declaration then does three jobs. (a) It **gates** the dispatch: the lookup happens at the head of the `"function_scalar"` arm, before `match fn_name.as_str()`, and a name absent from it returns the existing `unsupported scalar function: <name>` error. A per-name arm added without a declaration row is therefore unreachable in both dialects. (b) It **renders** the Exasol dialect for `VerbatimCall` names directly, so those names never reach a per-name arm on the Exasol path, and arm ordering stops carrying dialect precedence. (c) It **drives** decision [7]'s sweep table, which iterates the declared names and fails naming any declared name that has no fixture.
- **Alternatives:** (a) Spell the eligible names inline in the guarded arm's pattern list, which is the shape #210 shipped and which decision [1] originally carried forward. Rejected in round 1: an inline list is a second copy of the translated-name set. (b) A flat `const EXASOL_VERBATIM_FNS: &[&str]` read by the guard and by a hand-written sweep table, which is the shape round 1's revision produced. Rejected in round 2: it removed the duplicate name list but left two independent ways to forget a name — omit it from the set, or omit its sweep row — and the artifacts claimed an enforcement guarantee neither link delivered. (c) Replace the string dispatch with an enum carrying one variant per translated name, making `exasol_form`, the DataFusion dispatch, and the sweep fixture provider all exhaustive `match`es, so every link is a compile error. Rejected on cost: about 160 lines of mechanical `wire_name`/`from_wire_name` boilerplate plus a rewrite of all 80 arm patterns inside a 3,351-line file, to convert one test failure into one compile failure. The gate already delivers the stronger half, because an undeclared name cannot render at all.
- **Rationale:** The one-owner test from `/speq:design-philosophy` is not "is the list written once" but "can the rest of the system disagree with it". A flat set written once could still disagree with the dispatch, because nothing consulted it on the way in. Gating on the declaration makes disagreement impossible in that direction: the dispatch cannot translate a name the declaration does not know. Iterating the declaration closes the other direction: the sweep cannot omit a name the declaration does know. What remains reviewed rather than derived is narrow and stated in decision [7] — the five non-`function_scalar` node types, which are matched on the `type` string in the outer walker.
- **Guarantee delivered, stated precisely:** A `function_scalar` name added to a DataFusion arm without a declaration row cannot be translated in either dialect, so the author's own test for the new function fails immediately. A declared name without a sweep fixture fails `exasol_dialect_renders_declared_verbatim_surface` by name. A declared `VerbatimCall` name cannot diverge from what Exasol sent, because its Exasol rendering comes from the declaration's branch, which no per-name arm can reach. A declared `Shaped` name's Exasol rendering still lives in its arm and rests on the sweep row the test forces it to have. No claim stronger than these appears in `plan.md` or the spec deltas.
- **Supersedes in part:** "One guarded match arm owns the Exasol-dialect rule" — that decision stands, but its inline-pattern-list mechanism is replaced by the gated declaration.
- **Promotes to ADR:** yes

### [14] The four now-family capabilities are withdrawn, because no rendering can be correct

- **Decision:** Withdraw `FN_CURRENT_DATE`, `FN_CURRENT_TIMESTAMP`, `FN_SYSDATE`, and `FN_SYSTIMESTAMP` from `CAPABILITIES` (`adapter/capabilities.rs:113-114`, `:122-123`), so Exasol evaluates all four itself. Update `docs/capabilities.md` in the same plan: the four names leave the § Scalar functions Date / time row and gain a § Handled by Exasol row. This is option B of the three decision [4] left open, chosen by the human.
- **Alternatives:** (a) Option A — accept the divergence and file an issue. Rejected by the human: it leaves an advertised capability that returns a wrong value, and a silent wrong answer is worse than a lost optimization. (b) Option C — plumb `SESSIONTIMEZONE`, `DBTIMEZONE`, and a statement-level anchor into `CommonScanSpec` over a new adapter-side connect-back call. Not rejected on merit; it is the only route to correct pushdown, and it is a scan-spec and connect-back change far outside a rendering fix. `plan.md` § Non-Goals records it as future work with a required GitHub issue. (c) Withdraw only the two collapsed names, `SYSDATE` and `SYSTIMESTAMP`, keeping `CURRENT_DATE` and `CURRENT_TIMESTAMP`. Rejected: all four are wrong on the scan path, not only the collapsed pair, because the scan reads a UTC container clock in no Exasol zone. Keeping two would leave two advertised wrong answers and a harder rule to state.
- **Reachability and wrongness verified live, not argued from the capability list (round-3 requirement):** the earlier revisions of this entry inferred "the scan reads its container clock" from the advertised capability strings alone, with no captured pushdown request. That inference is now measured. Against the pinned `exasol/docker-db:2025.2.1` container, `DBTIMEZONE` and `SESSIONTIMEZONE` are both `EUROPE/BERLIN` while the container OS clock is UTC, a two-hour offset, so the comparison is not vacuous. Three observations follow, each from `EXPLAIN VIRTUAL` or a returned value:
  - **Exasol does push the now-family to the node-local scan.** `EXPLAIN VIRTUAL SELECT id FROM <vs>.EVENTS WHERE event_ts > CURRENT_TIMESTAMP` pushes `"filter":"(now() < \"EVENT_TS\")"`. A select-list `SYSTIMESTAMP` pushes `"projection":[{"expr":"now()"},"ID"]` with `"emit_exa_types":["TIMESTAMP(3)","DECIMAL(20,0)"]`, and a select-list `CURRENT_DATE` or `SYSDATE` pushes `{"expr":"current_date()"}` with `"emit_exa_types":["DATE",...]`. The scan-path defect is reachable in both the filter and the select-list position.
  - **The pushed value is wrong by the zone offset.** `SELECT SYSTIMESTAMP FROM <vs>.EVENTS WHERE id = 1` returned `2026-07-28T15:02:02.716` while `SELECT SYSTIMESTAMP FROM DUAL` in the same session returned `2026-07-28T17:02:03.141`. The scan read UTC; Exasol reads the database zone.
  - **The pushed value is also re-read per shard.** `SELECT SYSTIMESTAMP, COUNT(*) FROM <vs>.EVENTS GROUP BY SYSTIMESTAMP` returned two distinct timestamps over a two-file table, `15:02:03.627` and `15:02:03.658`, ten rows each. The native oracle returns one value for the whole statement. Exasol's now-family is statement-constant; the pushed form is not.
  - **Why a pure-constant predicate is not a usable probe:** `WHERE CURRENT_TIMESTAMP > TIMESTAMP '<t>'` is constant-folded by Exasol before the pushdown request is built, so no `filter` is pushed. Only a now-family node combined with a column reference, or one in the select list, reaches the scan. This is why the E2E test in task 10 uses a select-list position rather than a constant predicate.
  - **Method caveat, learned the hard way: verify against a `.so` rebuilt from HEAD, never the one already in BucketFS.** The first pass ran against the deployed artifact and reported that a select-list `CURRENT_TIMESTAMP` hard-fails with `Column type not supported: TIMESTAMP(3) WITH LOCAL TIME ZONE` (SQL state 22002). That result was an artifact of a stale `.so` predating commit `2920ffad` (2026-07-24), which added the `is_valid_emits_output_type` gate to the `function_scalar` select-list arm. After `make cross-musl-udf-build` plus `make bucketfs-upload-so`, the same query succeeds and returns Exasol's own session-zone value, confirming the widening this entry claims. Every number quoted above comes from the rebuilt HEAD artifact. The four other observations are unaffected by that gate, because `SYSTIMESTAMP` declares `TIMESTAMP(3)` and `CURRENT_DATE`/`SYSDATE` declare `DATE`, none of which the gate rejects.
- **Why withdrawal is safe — the correctness question, resolved rather than assumed:** The risk to rule out was that an Exasol predicate the adapter does not advertise might be silently dropped instead of re-applied, turning a wrong timestamp into wrong result rows. It is not dropped, and the evidence converges from four independent directions.
  - **The engine contract, stated in the project's own operator docs.** `docs/capabilities.md` § Handled by Exasol: "The adapter does not push these capabilities to the scan. Exasol computes them on the returned partial results. The results are correct and fast." § Filtering adds: "Exasol re-checks only the predicates that the adapter cannot translate." `docs/debugging-pushdown.md` names the cause explicitly — "a function that the list does not name" — and the effect: "Exasol then filters that predicate after the scan instead of before the scan."
  - **Normative spec text for the capabilities already absent.** `vs-adapter/pushdown-planning-capability-extensions` states "Exasol SHALL post-process regexp scalar functions rather than pushing them to the node-local scan" and the same clause for the eleven bitwise functions. `vs-adapter/pushdown-planning-topn` states that because `LIMIT_WITH_OFFSET` is unadvertised, "Exasol never pushes an offset and one cannot structurally appear".
  - **A live E2E test that measures the outcome.** `untranslatable_aggregate_argument_falls_back_to_row_scan` (`crates/lakehouse-engine/tests/e2e_scan_test.rs:999-1041`) runs `SELECT SUM(BIT_AND(id, 7))` through the virtual schema over an unadvertised function. It asserts via `EXPLAIN VIRTUAL` that no `aggregates` field is pushed, and that the result equals the arithmetically derived 66. Unadvertised, not pushed, computed by Exasol, correct.
  - **The project has already performed this exact operation.** ADR `specs/_decision/014-add-date-arithmetic-pushdown.md` withdrew `FN_ADD_HOURS` and `FN_ADD_MINUTES` and deleted their translator arms, recording the consequence as "all five fall through to Exasol's own evaluation" and, for `CONVERT_TZ`, "queries continue to execute correctly via Exasol's own post-processing." No correctness regression is recorded against it.
- **The safety property, stated precisely, because the naive version is wrong:** it is NOT "Exasol re-applies whatever the adapter did not do". It is **"Exasol never delegates what the adapter did not advertise."** The distinction matters, and this codebase paid for it: advertising `ORDER_BY_EXPRESSION` with no backing path made Exasol stop re-sorting, and the repro "returned rows in raw file order with no error (a silent wrong-order regression)" (`specs/vs-adapter/pushdown-planning-order-by-capability/spec.md`). An `orderBy` pushed together with a `limit` is fully delegated and once shipped wrong rows. So the dangerous operation is advertising without a faithful path; withdrawal is its inverse and moves these four names from the delegated side to the Exasol-evaluated side. No shape in this plan relies on Exasol re-applying a clause the adapter accepted and then dropped.
- **What the withdrawal costs, quantified (corrected in round 3 against the measured pushdown specs):** the filter position loses real pushdown for all four names. A predicate containing one of the four is no longer pushed, so it prunes no Iceberg files, skips no row groups, and is applied by Exasol over the returned rows. The select-list position also loses pushdown, for three of the four, which the earlier revision of this bullet had wrong. `SYSTIMESTAMP` declares plain `TIMESTAMP(3)` and `CURRENT_DATE`/`SYSDATE` declare `DATE`, all of which pass `is_valid_emits_output_type`, and `EXPLAIN VIRTUAL` confirms each was pushed as a projection item (`{"expr":"now()"}` with `"emit_exa_types":["TIMESTAMP(3)", …]`, and `{"expr":"current_date()"}` with `DATE`). Only a select-list `CURRENT_TIMESTAMP` loses nothing, because it alone declares `TIMESTAMP(3) WITH LOCAL TIME ZONE`, fails that check, and already widened to the full-row fallback (`adapter/pushdown/support.rs:1016-1018`, widened at `:1223-1227`). Every other date/time capability stays advertised — `FN_DATE_TRUNC`, `FN_EXTRACT`, the six field shortcuts, `FN_WEEK`, `FN_TO_DATE`, `FN_TO_TIMESTAMP`, and the four `*_BETWEEN` names — because each takes its datetime from its own arguments rather than from a clock. The pushdown being given up was producing wrong values, so the cost is a lost wrong optimization.
- **Rationale:** The plan's rule is "in the Exasol dialect, render what Exasol sent". That rule works because Exasol's compiler emitted the call and Exasol's engine will evaluate it. It cannot help a function whose value depends on context the scan never receives, and the now-family is the one family in this plan where the defect is upstream of rendering. Per `/speq:design-philosophy`, the honest fix for a module that cannot answer a question is to stop claiming it can, not to answer it differently. `capabilities.rs` is where the claim lives.
- **Supersedes:** "The now-family renders as bare Exasol keywords, correcting a latent wrong answer" (decision [4]) and, in part, "No capability is added or withdrawn" (decision [6]).
- **Promotes to ADR:** yes

### [15] The now-family's translations are deleted, not kept as unreachable arms

- **Decision:** Remove `CURRENT_DATE`, `SYSDATE`, `CURRENT_TIMESTAMP`, and `SYSTIMESTAMP` from `TRANSLATED_SCALAR_FNS` and delete the two arms at `lib.rs:1041-1042`, so the gate declines all four in both dialects. `ExasolForm` therefore ships with two variants, `VerbatimCall` and `Shaped`; the `BareKeyword` variant decision [13] introduced is not built, and the four sweep rows, the four spec steps, and the `renders_now_family_as_bare_keywords_in_exasol_dialect` test that would have covered it are dropped from the plan. `renders_now_family` (`lib.rs:2664-2684`) is replaced by `now_family_falls_through`, modelled on `bitwise_operator_functions_fall_through`.
- **Alternatives:** (a) Keep the `BareKeyword` form and withdraw only the capability. Rejected: the Exasol-dialect rendering would be unreachable the moment the capability is gone, which is precisely the situation the human already ruled on for `decimal_to_varchar_exasol` — drop it, do not keep it as relabelled hardening. (b) Declare the four names `Shaped` and keep the existing DataFusion arm, withdrawing only the capability. Rejected on two counts: it leaves an advertised-set-exceeds-translated-set inversion inverted the wrong way round, and it forces the sweep test to assert `current_date()` and `now()` as *Exasol-dialect* renderings, contradicting the same test's secondary token deny-list, which names both. Resolving that would mean weakening the deny-list to accommodate dead code. (c) Leave the arms and add a comment marking them unreachable. Rejected: the plan already deletes the #210 string guard for being unreachable after the gate lands, and applying the rule to one arm and not another is the inconsistency this plan exists to remove.
- **Reachability verified, not assumed:** The four names appear in exactly two Rust files repo-wide — `capabilities.rs` (the strings being withdrawn, plus its own test) and `vs-expression/src/lib.rs` (the arm, plus its own test). No E2E test, no `dispatch_golden` fixture, and no `bench/` script mentions them. Every production call site of all six translator entry points is fed raw pushdown-request JSON; the only nodes the adapter synthesizes itself are `decimal_to_varchar_exasol` (`support.rs:776-781`), `function_scalar_cast` (`support.rs:788-795`), a sentinel `column` (`grouped_agg.rs:331-333`), and a `predicate_and` (`joins/rendering.rs:208-211`). Every tree transformer is structure-preserving and cannot introduce a function name. So once the capability is withdrawn, nothing can deliver such a node.
- **A second reason beyond hygiene:** deleting the arms changes the failure mode of a hypothetical stray node from a silently wrong timestamp to a loud `unsupported scalar function` decline. That is the direction this plan pushes everywhere else, and it is worth more than the arms.
- **Scope note:** `crates/vs-expression` is a standalone crate intended for reuse by a sibling project. This removes a translation that a future consumer with a different capability list might want. ADR `014-add-date-arithmetic-pushdown` already set that precedent by withdrawing the `ADD_HOURS`/`ADD_MINUTES` arms from the same crate, and restoring a `VerbatimCall` row is a one-line change if a consumer ever has the clock context to justify it.
- **Supersedes:** "The now-family is declared `BareKeyword`, not a member of the verbatim-call set" (decision [13]).
- **Promotes to ADR:** yes
