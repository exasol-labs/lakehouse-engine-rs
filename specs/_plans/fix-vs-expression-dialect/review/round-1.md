# Plan Review Findings: fix-vs-expression-dialect (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 13 (Blockers: 6, Advisory: 7)

## Premortem

Three failure stories, each routed into the taxonomy below.

1. **The rule does not hold.** A future arm adds `SUBSTRING` (or `NVL`, `DATE_BIN`) to the DataFusion name table and forgets the Exasol allow-list. `exasol_dialect_renders_no_datafusion_only_token` passes, because `substring(` is not in its hardcoded token list. Twelve months later a customer's `COUNT(DISTINCT SUBSTRING(...))` fails with the same 42000 error this plan exists to close. → Design Depth [INFORMATION_LEAKAGE], Requirement Quality [AMBIGUOUS_REQUIREMENT].
2. **Green tests, unfixed path.** The REGEXP_LIKE fix ships with a passing E2E test that never exercised it, and the second REGEXP_LIKE encoding was never branched. A HAVING or ORDER BY over a pushed `REGEXP_LIKE` still aborts. → Requirement Quality [COMPLETENESS_GAP] ×2.
3. **Two clocks.** `SYSTIMESTAMP` evaluates as database time in a wrapper and session time in a scan. A cutoff comparison drifts by hours with no error. → Intent Fidelity [SCOPE_CREEP].

## Verification performed by this review

Every rendering claim in `plan.md` § Context was re-executed independently against the project's pinned Exasol container (`exasol/docker-db:2025.2.1`, `docker-compose.yml:115`). All seven failure claims reproduce, and both "issue premise is wrong" claims about the now-family hold: `signum`, `date_part`, `strpos`, `arrow_cast` return `function or script <NAME> not found` (42000); `regexp_like(s, p)` returns `syntax error, unexpected REGEXP_LIKE_`; `CAST(1.5 AS VARCHAR)` returns `syntax error, unexpected ')', expecting '('`; `TIMESTAMP '2020-01-01 00:00:00+00:00'` returns 22018; `SELECT current_date()` and `SELECT now()` both succeed. Every name in the proposed verbatim arm exists natively (`SIGN`, `COT`, `DEGREES`, `RADIANS`, `TRUNC`, `ATAN2`, `CEIL`, `LOG`, `WEEK`, `DATE_TRUNC`, `TO_DATE`, `TO_TIMESTAMP`, `GREATEST`, `LEAST`, `NULLIFZERO`, `ZEROIFNULL`, `SYSDATE`, `SYSTIMESTAMP`, `EXTRACT(F FROM x)`, `(s REGEXP_LIKE p)`), `CAST(1.500 AS VARCHAR(2000000))` returns `1.5` and `CAST(100.000 AS VARCHAR(2000000))` returns `100`, and `CAST(d1 AS DATE) - CAST(d2 AS DATE)` returns a day count. The ten `dispatch_golden` fixtures contain none of the affected tokens. The four-row Exasol-dialect consumer map is accurate: the only production call sites are `topn.rs:138`, `joins/rendering.rs:103`, `joins/rendering.rs:116`, and `grouped_agg.rs:424` (`sql_builders.rs:892` and `:2225` are inside `mod tests`). The findings below are what did not survive.

#### [SCOPE_CREEP] ADVISORY
- Location: `decision-log.md` § [4]; `plan.md` § Consequences row 3, § Impact ¶4; `sql-comprehension/vs-expression-translator-date-fns/spec.md` § "CURRENT_DATE and CURRENT_TIMESTAMP translate to DataFusion now-family calls"
- Issue: decision [4] concedes the now-family change is "not a compilation fix" and that neither form "is required by the issue's stated scope", then makes it anyway — de-aliasing `SYSDATE` from `CURRENT_DATE` and `SYSTIMESTAMP` from `CURRENT_TIMESTAMP`. Issue #209 asks only that `CURRENT_DATE` stop rendering as `current_date()`. Two consequences go undisclosed. First, the plan fixes the collapse on the Exasol path only; the DataFusion path keeps `SYSDATE → current_date()` and `SYSTIMESTAMP → now()`, frozen by the "DataFusion output frozen" requirement, with no tracked issue — so the defect decision [4] calls "a silent wrong answer" survives on the path that executes most scans. Second, one expression can now evaluate two ways in one query, since the same name renders session-time in a scan and database-time in a wrapper. § Impact's claim "Results change only where a query previously returned an error" is false for these four names, and its framing ("an operator comparing wrapper output against a prior run could see a different timestamp source") reads as an observability note rather than a divergence. This review could not construct a concrete query that evaluates one `SYSTIMESTAMP` node on both sides — group keys render scan-side only, select items wrapper-side only, and a residual conjunct is disjoint from a pushed one — which is why this is ADVISORY, not BLOCKER.
- Fix: In `plan.md` § Impact ¶4, replace the sentence "The prior mapping was silently wrong, so this narrows divergence rather than widening it" with a statement that the DataFusion dialect keeps the collapse, that the two dialects therefore disagree for these four names, and that no query is known to evaluate one such node on both paths. Add a bullet to `plan.md` § Non-Goals naming the DataFusion-side collapse as out of scope, and add a line to `decision-log.md` [4] recording that a GitHub issue MUST be filed for it before recording, per the project's no-silent-gap rule in `CLAUDE.md`.

## Requirement Quality

#### [COMPLETENESS_GAP] BLOCKER
- Location: `plan.md` § Implementation Tasks task 3 and § Design Architecture; `sql-comprehension/vs-expression-translator/spec.md` both REGEXP_LIKE scenarios
- Issue: `regexp_like(...)` is rendered at two sites, not one. `crates/vs-expression/src/lib.rs:678-693` handles `function_scalar` with `name == "REGEXP_LIKE"` — the alternate encoding the code comment calls "defensive" — and ends `Ok(Some(format!("regexp_like({subject}, {pattern})")))`, dialect-blind. Task 3 branches only `predicate_like_regexp` (`lib.rs:497-509`), the architecture diagram lists only `predicate_like_regexp`, and both delta scenarios are written `GIVEN a VS expression node of type predicate_like_regexp`. The second site therefore keeps emitting a form Exasol rejects. This also puts task 3 in conflict with task 7, which must "render one representative node per translated function and node type" and "assert the output contains none of ... `regexp_like(`": `function_scalar` REGEXP_LIKE is a translated function, so either task 7's table includes it and the test fails, or the table omits it and the guard is incomplete by construction.
- Fix: Extend `plan.md` task 3 to cover both encodings: "Branch `predicate_like_regexp` (`lib.rs:497`) **and** the `function_scalar` `REGEXP_LIKE` alternate encoding (`lib.rs:678`) on dialect; Exasol renders the infix `(<subject> REGEXP_LIKE <pattern>)` from both, DataFusion keeps `regexp_like(<subject>, <pattern>)` from both." In `sql-comprehension/vs-expression-translator/spec.md`, widen the GIVEN of both REGEXP_LIKE scenarios to "a node of type `predicate_like_regexp`, or of type `function_scalar` named `REGEXP_LIKE` (the alternate encoding)", and add an `AND` step requiring both encodings to render byte-identically within a dialect. Add the second encoding as a row in task 7's node table.

#### [COMPLETENESS_GAP] BLOCKER
- Location: `plan.md` § Verification row `e2e_count_distinct_regexp_like_matches_native_oracle`; § Manual Testing row 4
- Issue: both acceptance tests for the REGEXP_LIKE fix place the predicate in a WHERE clause: `SELECT COUNT(DISTINCT c_name) FROM <vs>.CUSTOMER WHERE c_name REGEXP_LIKE '^C'`. That WHERE never reaches the Exasol dialect. `build_qualified_single_table_fallback_sql` (`adapter/pushdown/joins/sql_builders.rs:744-828`) states it in its own doc comment: "The WHERE filter is applied inside the scan (via `fan_out_spec.filter`), so no outer WHERE is needed", and the filter is rendered by the DataFusion trio, where `regexp_like(...)` is correct and unchanged. Both tests therefore pass identically with and without the fix, so the plan ships its REGEXP_LIKE change with no test that can fail. The Exasol dialect sees `predicate_like_regexp` only as a select-list item, a GROUP BY key, a HAVING operand, an ORDER BY element, or an N-scan cross-side residual.
- Fix: In `plan.md` § Verification, respecify `e2e_count_distinct_regexp_like_matches_native_oracle` to put the predicate in a select-list position — `SELECT COUNT(DISTINCT (c_name REGEXP_LIKE '^C')) FROM <vs>.CUSTOMER WHERE c_custkey <= 10000` (verified to compile natively: `SELECT COUNT(DISTINCT ('abc' REGEXP_LIKE 'a'))` succeeds on 2025.2.1) — and rewrite § Manual Testing row 4 to the same shape. Add one sentence to the row noting that a WHERE-clause `REGEXP_LIKE` is pushed into the scan and does not exercise the Exasol dialect.

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: `plan.md` § Requirements row 3 ("Rule must be enforced, not documented"); § Implementation Tasks task 7; `decision-log.md` § [8]
- Issue: the requirement reads "A single unit test MUST render the full translated surface in the Exasol dialect and assert the absence of every DataFusion-only token, so a future arm that forgets the dialect fails a test." Task 7 implements it as a fixed deny-list of twelve tokens (`signum`, `date_part`, `strpos`, `arrow_cast`, `character_length`, `octet_length`, `regexp_like(`, `current_date()`, `now()`, `nullif(`, `coalesce(`, bare `%`). A deny-list cannot detect "a future arm that forgets the dialect": the only arms it catches are the ones already known today. Any new DataFusion-only name — `substring`, `nvl`, `date_bin`, `to_char` — passes. "Every DataFusion-only token" is also not a testable set, since it is unbounded. The requirement as written is therefore unverifiable, and `decision-log.md` [8]'s claim that the guard keeps "the cost of keeping the guard current" near zero conceals that the guard must be manually extended per future arm — the same manual step whose omission caused issue #209.
- Fix: Rewrite `plan.md` § Requirements row 3 to a checkable invariant: "For every `function_scalar` node in the sweep table, the Exasol-dialect rendering MUST equal `<NODE NAME>(<rendered args>)` — the node's own uppercased `name` — except for the named excluded constructs, and every node type outside `function_scalar` MUST match its per-dialect expected string." Rewrite task 7 to assert that name equality per row rather than scanning for tokens, and add a row to the table for every name in each dialect-branching arm. Keep the token deny-list as a secondary assertion. Update `decision-log.md` [8] to state that name equality, not token absence, is what makes the rule structural.

## Design Depth

#### [INFORMATION_LEAKAGE] BLOCKER
- Location: `plan.md` § Design Decision ("Parity on that path becomes structural rather than tested: there is no mapping left that can drift"); § Consequences row 1; `decision-log.md` § [1]
- Issue: the design does not remove the mapping — it adds a second copy of it. After task 1, the set of translated function names exists twice in `lib.rs`: once as the guarded Exasol arm's pattern list (~40 names) and once spread across the DataFusion arms' pattern lists. Nothing enforces agreement, and the guarded arm sits ahead of the DataFusion arms, so a name present in the DataFusion lists and absent from the Exasol list silently falls through to the DataFusion rendering — exactly the back-door leakage class that produced issue #209 and the day-one `*_BETWEEN` break the plan cites as its motivation. Decision [1] rejects a name table on the grounds that it "adds a second mechanism", but the guarded arm *is* the second copy; the alternative that removes the duplication — deriving both dialects from one declared name set, so the translated set and the verbatim-eligible set cannot diverge — is never considered. Per `/speq:design-philosophy`'s diagnostic, "is there exactly one module that owns each significant design decision?" is answered no: the decision "which names does this translator translate" now has two owners in one file.
- Fix: Add a decision to `decision-log.md` and a row to `plan.md` § Consequences recording one declared source for the name set — a `const` slice (or one `matches!` helper) naming the verbatim-eligible Exasol functions, referenced by the guarded arm's guard and asserted in task 7 to be a superset of every name the DataFusion arms match. Update `plan.md` § Design Decision to drop "there is no mapping left that can drift" and state instead that the two dialects read one declared name set, so drift fails a test. Update task 1 to build that shared set rather than an inline pattern list.
