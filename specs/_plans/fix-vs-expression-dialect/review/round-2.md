## Premortem

Four failure stories, each routed into the taxonomy below.

1. **The rule silently stops holding anyway.** Twelve months on, someone adds a DataFusion arm for `SUBSTRING`. They touch neither `EXASOL_VERBATIM_FNS` nor the sweep table. `exasol_dialect_renders_declared_verbatim_surface` passes, because it only checks names already in its own table. A customer's `COUNT(DISTINCT SUBSTRING(...))` fails with 42000 — the error this plan exists to close. → Requirement Quality [AMBIGUOUS_REQUIREMENT].
2. **Task 6 cannot be written as specified.** The implementer builds the sweep table with one row per translated `function_scalar` name, reaches `CURRENT_DATE` (Exasol form `CURRENT_DATE`, not `CURRENT_DATE()`) and `CASE` (Exasol form `CASE WHEN … END`), and must either delete those rows — holing the sweep — or invent exceptions the plan never authorised. → Requirement Quality [COMPLETENESS_GAP].
3. **The headline bug ships unfixed.** Task 1 widens the guard in place at `lib.rs:819`. The math arms at `lib.rs:699-752` still precede it, so `SIGN` keeps rendering `signum(x)` on the Exasol path. → Feasibility [EFFORT_MISESTIMATION].
4. **The plan never starts.** `plan.md` line 3 still reads "Status: blocked — see open-questions.md", and that file's only question — the one the human answered — is still an unticked checkbox inviting a re-answer. → Requirement Quality [REQUIREMENT_CONFLICT].

## Requirement Quality

#### [COMPLETENESS_GAP] BLOCKER
- Location: `plan.md` § Requirements row 3, § Implementation Tasks task 6; `decision-log.md` § [7]; `sql-comprehension/vs-expression-translator/spec.md` § Background DELTA:NEW ¶4; `sql-comprehension/vs-expression-translator-scalar-fns/spec.md` § Background ("Four constructs are deliberately EXCLUDED from the verbatim rule")
- Issue: the rewritten sweep requirement is not satisfiable, because its exception set is missing two non-call-shaped `function_scalar` families. § Requirements row 3 reads "For each `function_scalar` row the rendering MUST equal `<NAME>(<rendered args>)` using the node's own uppercased `name`, except for the four constructs the verbatim rule excludes (the operator wire names, `MOD`, `CONCAT`, `CAST`) and the `REGEXP_LIKE` alternate encoding". Two `function_scalar` name groups violate that shape and appear in no exception list. First, the four now-family names — `CURRENT_DATE`, `SYSDATE`, `CURRENT_TIMESTAMP`, `SYSTIMESTAMP` (`lib.rs:1041-1042`) — which this plan renders "as bare keywords with no parentheses" (task 1, § Design Architecture, and the `-date-fns` delta scenario), so `CURRENT_DATE` ≠ `CURRENT_DATE()`. Second, `function_scalar` named `CASE` (`lib.rs:893-926`), Exasol's interleaved-argument CASE encoding, which renders `CASE WHEN … THEN … END` in both dialects and is documented nowhere in the delta set — the `-scalar-fns` CASE scenario covers node type `function_scalar_case`, not this name. Task 6 requires "one row per translated function name", so the implementer either includes those five rows and the name-equality assertion fails, or omits them and the sweep is incomplete by construction — verbatim the either/or that made round 1's REGEXP_LIKE-encoding finding a BLOCKER. The `-scalar-fns` count "Four constructs" is wrong for the same reason: `CASE` is a fifth construct outside the verbatim rule, and that text is destined for the permanent library.
- Fix: In `plan.md` § Requirements row 3 and task 6, and in `decision-log.md` [7], replace the exception set with all seven exceptions and give each non-call shape its expected Exasol string: the four verbatim-rule exclusions (operator wire names, `MOD`, `CONCAT`, `CAST`); the `REGEXP_LIKE` alternate encoding → `(<subject> REGEXP_LIKE <pattern>)`; the four now-family names → the bare keyword `<NAME>` with no parentheses; and `function_scalar` named `CASE` (`lib.rs:893`) → `CASE WHEN <cond> THEN <res> [ELSE <else>] END`. Add to task 1 an explicit statement of whether the four now-family names are members of `EXASOL_VERBATIM_FNS` or rendered by their own arm, and make task 6's shape assertion match that choice. Mirror the same seven-exception list in `sql-comprehension/vs-expression-translator/spec.md` § Background DELTA:NEW ¶4. In `sql-comprehension/vs-expression-translator-scalar-fns/spec.md` § Background, change "Four constructs" to "Five constructs" and add a `CASE` row: "`function_scalar` named `CASE` — Exasol's interleaved-argument CASE encoding; both dialects render `CASE WHEN … THEN … END`, so there is no call form to render verbatim."

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: `plan.md` § Goals ("a regression test that fails when a future arm forgets the dialect"), § Design Decision ¶1, § Consequences row 2; `sql-comprehension/vs-expression-translator/spec.md` § Background DELTA:NEW ¶4 ("With one declaration the sweep test MUST fail instead"); `sql-comprehension/vs-expression-translator-date-fns/spec.md` § Background DELTA:NEW ("so no divergence is possible") and the parity-gate bullet ("whose verbatim rendering cannot diverge"); `decision-log.md` § [12]
- Issue: the declared name set removes the duplication round 1 flagged, but the artifacts claim an enforcement guarantee the specified test does not deliver, and the half of round 1's Fix that would have delivered it was dropped silently. § Design Decision states "A name that joins a DataFusion arm without joining that set fails the sweep test rather than silently rendering DataFusion SQL"; § Consequences row 2 states "One declared set turns that omission into a test failure"; the `vs-expression-translator` delta states it normatively — "a name present in a DataFusion arm but absent from the Exasol list falls through to the DataFusion rendering with no error — the failure mode that produced issue #209. With one declaration the sweep test MUST fail instead". None of that holds. Task 6 asserts only that "every `function_scalar` name **in the table**" is in the set or an exception. Nothing derives the table or the set from the DataFusion arms, so a future `SUBSTRING`, `NVL`, or `DATE_BIN` arm added without a sweep row and without joining the set passes every test and renders DataFusion SQL on the Exasol path — round 1's premortem story 1, unchanged. Round 1's Fix asked for the set to be "asserted in task 7 to be a superset of every name the DataFusion arms match"; that clause is absent from task 6, from decision [12], and from the `[plan-review]` entry that reports the fix as applied. § Goals' promise is therefore unverifiable as written, and the same overstatement is being written into two spec deltas bound for the permanent library.
- Fix: In `plan.md` § Goals, replace "a regression test that fails when a future arm forgets the dialect" with the guarantee the test delivers: "a regression test that fails when a name in the sweep table is missing from `EXASOL_VERBATIM_FNS`". Delete the sentence "A name that joins a DataFusion arm without joining that set fails the sweep test rather than silently rendering DataFusion SQL" from § Design Decision ¶1 and "One declared set turns that omission into a test failure" from § Consequences row 2, replacing both with a statement that the sweep table is the enforcement surface, so a `function_scalar` arm added without its sweep row leaves the gap undetected. In `sql-comprehension/vs-expression-translator/spec.md` § Background DELTA:NEW ¶4, replace "With one declaration the sweep test MUST fail instead" with the same scoped statement. In `sql-comprehension/vs-expression-translator-date-fns/spec.md` § Background, delete "so no divergence is possible" and "whose verbatim rendering cannot diverge". Then close the gap one of two ways and record which in `decision-log.md`: (a) add a task declaring every translated `function_scalar` name exactly once and driving both dialects' dispatch and the sweep table from that one declaration, so a new arm cannot exist without a row; or (b) add a decision-log entry recording the sweep table's manual-row dependency as an accepted tactical shortcut, with a GitHub issue that MUST be filed before this plan is recorded, per `CLAUDE.md`'s no-silent-gap rule.
