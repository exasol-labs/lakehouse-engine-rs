## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `plan.md` § Manual Testing, rows 2 and 3 of the `pushdown-planning-capability-extensions` group (lines 273-274); `decision-log.md` [14] "What the withdrawal costs"
- Issue: both verification rows assume the Exasol container runs a session and database time zone that differ from UTC, and the plan never states that precondition. Row 274 reads `SELECT SYSTIMESTAMP, CURRENT_TIMESTAMP FROM <vs>.<table> LIMIT 1`, then the same select with no virtual schema, expecting "Both values match the non-virtual-schema oracle in the same session, so the database and session zones are applied by Exasol rather than read from the UDF container's UTC clock". The whole defect the plan claims to fix is that the scan reads UTC instead of `SESSIONTIMEZONE`/`DBTIMEZONE`. If the pinned `exasol/docker-db:2025.2.1` instance has both zones at their UTC default — which the plan neither pins nor checks — the pre-withdrawal and post-withdrawal values are identical, the row passes in both states, and the stated conclusion does not follow from the observation. A second load-bearing belief is equally unvalidated: nothing in the repo shows Exasol actually pushing a now-family node. Decision [15]'s own reachability sweep confirms there is no captured pushdown request, no `dispatch_golden` fixture, and no E2E test containing any of the four names, so "the scan reads its container clock" is argued from the capability string alone, never observed. If Exasol constant-folds `CURRENT_TIMESTAMP` before building the pushdown request, § Impact's "The now-family becomes correct" and "An operator ... SHOULD expect it to change, and to become right" are false, and the `-date-fns` and capability deltas record a live defect that never existed into the permanent library.
- Fix: In `plan.md` § Manual Testing, add a pre-withdrawal baseline row that runs `EXPLAIN VIRTUAL` over a now-family expression against the current build and records whether the pushed scan spec contains `now()` or `current_date()`. State the outcome in `decision-log.md` [14] as observed evidence. Then state the time-zone precondition explicitly in rows 273-274 — name the DDL that sets a non-UTC session zone (and the database zone, or record that only the session zone is settable on the pinned image) — and state that with both zones at UTC the comparison is vacuous. If the baseline `EXPLAIN VIRTUAL` shows no now-family node is ever pushed, replace § Impact ¶4's "return wrong values today" and "SHOULD expect it to change, and to become right" with the weaker true claim (no faithful evaluation exists if pushed), and make the same correction in the `-date-fns` Background ¶3 and the capability delta's Background ¶1.
