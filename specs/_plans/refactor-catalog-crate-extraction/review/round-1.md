## Premortem

Three failure stories, each routed into the taxonomy below.

1. **The E2E gate rots silently.** A vended-credentials regression ships. Cause: `Makefile`'s `VS_SRCS` never listed `crates/lakehouse-catalog/src`, so catalog-only edits left `target/release/liblakehouse_engine.so` untouched. `make test-e2e` and `make test-e2e-lakekeeper` — the plan's named behavior-parity gates for `resolve_vended_storage` — passed against a stale `.so` for months. → Feasibility `[HIDDEN_DEPENDENCY]`.
2. **Task 3.2 stalls on a self-contradictory spec.** The implementer reaches `catalog_auth_secrets_never_in_scan_spec_with_vending`, which builds `ScanSpec`/`CommonScanSpec`/`FileEntry` — types the same delta forbids the crate from naming — and 15 calls into `pushdown/test_support.rs`, which cannot move. Under pressure the test is deleted, and the "no catalog secret in the scan spec" guarantee loses its only regression test. → Requirement Quality `[REQUIREMENT_CONFLICT]`, Task Breakdown `[TRACEABILITY_GAP]`.
3. **The advertised speedup was never real.** An operator reports createVirtualSchema is no faster. Cause: `list_namespace_tables` still builds its own `RestCatalog`, so `iceberg-catalog-rest` runs its own `client_credentials` grant and `/v1/config` handshake before the schema loop starts. "At most ONCE for the whole request" was never achievable, and the plan states grants are enforced "STRUCTURALLY, not counted" — so no test could have caught it. → Requirement Quality `[REQUIREMENT_CONFLICT]`.

## Design Depth

#### [SHALLOW_DESIGN] ADVISORY
- Location: `vs-adapter/catalog-crate-structure` § Scenario 3; plan.md § Design § Architecture
- Issue: the crate's public set is 4 types plus 9 functions, and the functions are the steps of one sequence the engine must still orchestrate: `CatalogSession::resolve` → `load_table_any_auth` → `build_s3_file_io` → `resolve_vended_storage`. `file_resolution.rs` calls all four in order and holds the ordering knowledge. Measured against the Quick Diagnostic's "Is calling the module noticeably easier than reimplementing it would be?", the interface is close to the caller's own code — the crate hides `CatalogAuth`, the OAuth grant, and the prefix lookup, which is real depth, but exposes the four-step recipe on top of it. The plan's own pattern table claims "Concept-level façade over a private mechanism", which holds for `resolve_vended_storage` but not for the crate boundary itself. Decision [3] considered and rejected the deeper alternative (moving `resolve_file_list` in) for a stated reason — dragging the scan-spec wire types across — so this is a knowingly accepted shallowness, not an oversight; it just is not named as one.
- Fix: Add a row to plan.md § Design § Consequences — "Decision: the crate exposes the four-step catalog-access sequence rather than one entry point. Alternative considered: a single `load_table_for_scan(&CatalogSession, ...)` returning the loaded table plus effective storage. Rationale: rejected because the return type would name `FileEntry`/`LogicalField`" — or, if the single entry point is in fact expressible without those types, adopt it and narrow Scenario 3's `pub` set accordingly.
