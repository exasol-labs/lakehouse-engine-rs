## Requirement Quality

#### [REQUIREMENT_CONFLICT] ADVISORY
- Location: `vs-adapter/pushdown-catalog-session` § "createVirtualSchema resolves every table's schema on one shared session", 3rd AND-clause; the same file's Background bullet 18; decision-log.md § [6] "Residual benefit"
- Issue: the new clause reads "the namespace-enumeration `RestCatalog` SHALL retain its own independent catalog-auth handshake, so a createVirtualSchema request still performs TWO grants and TWO `/v1/config` lookups in total rather than one of each". That holds in one of four auth modes. `inject_catalog_auth_props` (`credentials.rs:101-123`) inserts `REST_CATALOG_PROP_CREDENTIAL` only when `client_id` AND `client_secret` are both non-empty; otherwise it inserts a static bearer token or nothing, and `iceberg-catalog-rest` runs no `client_credentials` exchange. In SigV4 mode `list_namespace_tables` (`namespace.rs:36-38`) takes the `list_in_namespace_signed` branch and builds no `RestCatalog` at all, so neither the grant nor the config lookup the clause asserts exists. This plan's own `pushdown-planning-cloud-credentials` Background states there are four modes: "no-auth, static bearer `token`, OAuth2 client-credentials ... and AWS SigV4". The preceding clause is correctly hedged ("at most ONCE"); this one is not, and it is stated as a normative SHALL that will be recorded permanently. No test binds it — the plan enforces grant counts structurally — so nothing would catch it. Background bullet 18 and decision-log [6] carry the weaker version of the same imprecision ("on the non-SigV4 path", which still includes bearer-token and no-auth mode).
- Fix: Rewrite that clause to "on the OAuth2 client-credentials mode the namespace-enumeration `RestCatalog` SHALL retain its own independent grant and `/v1/config` handshake, so such a request still performs TWO grants in total rather than one; on the static-token and no-auth modes it performs no grant and one extra `/v1/config` lookup, and on the SigV4 mode `list_namespace_tables` builds no `RestCatalog` at all. Folding namespace enumeration onto the session is out of scope." Qualify Background bullet 18 and decision-log [6]'s residual-benefit paragraph the same way, replacing "on the non-SigV4 path" with "when `client_id` and `client_secret` are both set".

## Task Breakdown

#### [TRACEABILITY_GAP] ADVISORY
- Location: plan.md § Implementation Tasks 3.0 and 3.2; `vs-adapter/catalog-crate-structure` § Scenario 4, 4th AND-clause
- Issue: task 3.0 and the matching Scenario 4 clause treat `base_creds` and `static_storage` as the complete set of shared fixtures. They are the complete set of fixtures reached through `use super::super::test_support::*`, but not the complete set the four-way split creates. `credentials.rs`'s flat test module also declares its own shared helpers, and task 3.2 splits that module across `auth`, `session`, `iceberg_io`, and `vended`, which turns every one of them into a cross-module helper: nine sentinel constants at `1545-1553` (`STATIC_AK`, `STATIC_SK`, `VENDED_AK`, `VENDED_SK`, `VENDED_TOK`, `BEARER_TOK`, `CLIENT_SECRET`, `OAUTH_ACCESS_TOKEN`, `VENDED_REGION`, read 50 times for the VENDED group alone), `AUTH_PROP_KEYS` at `1356`, and three builders — `make_load_table_result` (`911`), `creds_no_auth` (`1556`), and `vended_result_flat_config` (`1578`). The recorded `vs-adapter/pushdown-module-structure` rule "a test helper shared across submodules MUST live in one shared `#[cfg(test)]` support module rather than being duplicated" binds these exactly as it binds the two named fixtures. An implementer following task 3.0 literally provisions the support module with two items and then has to invent a home for thirteen more, most likely by duplicating them per module — the outcome the rule forbids and the outcome Background bullet 22 claims the plan avoids. Secondary, same task: Group C runs 2.2 and 3.0 concurrently, and both add a `mod` line to the crate's `lib.rs`; the plan flags that conflict for Group B's 2.1/3.1 pair but not here.
- Fix: Extend task 3.0 to "declare the crate-local `#[cfg(test)]` support module with the two engine-side fixtures (`base_creds`, `static_storage`) AND the helpers the four-way split of `credentials.rs`'s flat test module turns into cross-module helpers: the nine sentinel constants at `credentials.rs:1545-1553`, `AUTH_PROP_KEYS` (`:1356`), `make_load_table_result` (`:911`), `creds_no_auth` (`:1556`), and `vended_result_flat_config` (`:1578`) — one declaration each, no per-module duplicate." Change Scenario 4's 4th AND-clause from "the two fixtures the moved tests share" to "every fixture, sentinel constant, and builder that more than one moved test module reaches, declared exactly once". Add to plan.md § Parallelization's Group C note that 2.2 and 3.0 both add a `mod` line to `crates/lakehouse-catalog/src/lib.rs`, the same conflict point already noted for 2.1 and 3.1.
