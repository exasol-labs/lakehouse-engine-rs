# Feature: Pushdown Module Structure

Decomposes the virtual-schema pushdown-planning code into single-responsibility submodules behind a preserved public façade, keeps behavior byte-identical, and co-locates each submodule's tests.

## Background

* The refactor changes code organization only. It changes no query, pushdown, file-pruning, or type-handling behavior, so every scenario in the `vs-adapter/pushdown-planning*` and `vs-adapter/pushdown-file-pruning` features stays accurate and unedited.
* The pushdown planning layer decomposes into cohesive capability submodules (catalog credentials, file resolution, single-group aggregate, grouped aggregate, joins, top-N, namespace listing) plus one shared support submodule for cross-cutting SQL-builder and utility helpers. The exact submodule list is a design decision recorded in the plan, not a normative contract.
* `crate::adapter::pushdown` becomes a directory module (`pushdown/mod.rs` plus sibling files), so the import path `crate::adapter::pushdown::<name>` is unchanged for every consumer.
* A cross-submodule private helper widens to the narrowest visibility that compiles (`pub(super)`), never to a broader public than it had before.
* The CI/lint file-size guardrail (the second half of issue #129) is out of scope for this feature and remains open under issue #129.
* This delta amends one clause set of the shared-classifier scenario: the classifier now
  resolves the grouped HAVING's merge-rendering as part of the routing decision, and returns
  the rendered fragment instead of the raw `having` node. Every other module-structure
  scenario is unchanged.
* The reason the rendering moves into the classifier is a routing reason, not a rendering
  one: whether the HAVING can be rewritten over the `PARTIAL_*` merge columns decides WHICH
  shape is available (partial/merge grouped, or the qualified single-table wrapper), so the
  decision cannot be deferred to a path that has already committed to one shape. See
  `vs-adapter/pushdown-planning-grouped-agg-wrapper-fallback` for the fallback behavior this enables
  (issue #195).
* Each path still renders its own SQL: the non-empty dispatch path splices the classifier's
  rendered HAVING fragment into the outer merge wrapper without re-rendering it, and the
  empty path ignores it because a zero-row result satisfies any HAVING.
* One rendering-level decline remains in the dispatcher — a grouped ORDER BY whose sort key
  resolves to no grouped output column — because it does not change the reachable shape set.
* This delta also removes the classifier's LAST grouped-tier hard error, the non-numeric
  aggregate column type carrying a HAVING. It rested on the same disproven premise: the
  qualified single-table wrapper renders the HAVING natively, so nothing is dropped. Both
  grouped declines — gate failure and unmergeable HAVING — now share the one fall-through exit
  to the wrapper, so the grouped tier returns `Ok` for every input.
* This delta adds ONE scenario, the blind column-collecting traversal primitive (issue #177). Every existing scenario of this feature is unchanged, and no scenario of any `vs-adapter/pushdown-planning*` feature changes, because the extraction moves no decision and alters no generated SQL.
* `pub(super)` on an item of `adapter::pushdown::support` makes it visible in `adapter::pushdown` AND every descendant of `adapter::pushdown`, including `adapter::pushdown::joins::rendering`. The primitive therefore reaches both joins-side walks at the visibility ceiling the `vs-adapter/pushdown-joins-module-structure` feature already imposes, so no `use` path and no visibility widens on the joins side.
* The joins-side verification asset already exists and is already scoped to this change: `vs-adapter/pushdown-joins-module-structure`'s "Generated join SQL is byte-identical across the split" scenario captures a golden-SQL baseline over "any duplication extraction" across the broadcast, N-scan-fallback, grouped-qualified-fallback, and ineligible-decline paths, and the in-code gate carries the instruction to re-run after every dedup extraction. This delta consumes that baseline rather than restating it, so `vs-adapter/pushdown-joins-module-structure` needs no delta.
* The two case-folding calls this codebase uses are NOT interchangeable. `str::to_uppercase` applies full Unicode case mapping; `str::to_ascii_uppercase` leaves every non-ASCII byte alone. The three walks disagree today (`collect_all_column_names` uses the Unicode form, both joins walks use the ASCII form), and reconciling that disagreement is a behavior change outside this feature's scope.
* Issue #257 owns a SECOND, different traversal primitive: a curated-field, post-order rewrite walker for the three type-rewrite guards. The two primitives stay separate because a rewrite MUST NOT descend into and rebuild `dataType` or `name` sub-objects, whereas a collect is read-only and so must traverse every field. Neither issue merges them.
* Scope boundary of this delta: the rewrite-shaped walks are untouched — `annotate_columns_with_alias`, `strip_table_alias`, and the three `support` type-rewrite guards keep their own recursion, none of which is a column-collecting traversal.
* This delta also adds a further scenario: the three type-aware expression-tree rewriters in
  `pushdown/support.rs` collapse onto one shared post-order rewrite primitive. Every other
  module-structure scenario is unchanged.
* The three rewriters are `like_subject_type_guard` (`vs-adapter/pushdown-planning-like-type-coercion`),
  `string_function_arg_type_guard` (`vs-adapter/pushdown-planning-string-fn-type-coercion`), and
  `rewrite_decimal_stringifications` (`vs-adapter/pushdown-planning-decimal-string-format`). Each
  hand-rolled its own post-order recursion over the untyped `serde_json` pushdown expression
  grammar, and the two wide walkers duplicated the curated child-field list verbatim, kept in
  sync only by comment. A fourth type-blind fix would have copied it a third time (issue #257).
* The child-field list is curated on purpose: a rewrite descends into expression children only
  and must never descend into a node's `dataType` or `name` sub-objects and rebuild them.
* The primitive is a free function taking a per-node closure, not a visitor trait or a typed
  AST. The pushdown IR is deliberately untyped `serde_json`, and a typed AST would contradict
  `vs-expression`'s no-SQL-parser property.
* The blind, collect-style JSON walk that issue #177 also dedups stays a SEPARATE primitive — it
  recurses over every map value, which is exactly what the curated list must not do.
* This delta adds ONE scenario: the ordered type-rewrite pass sequence moves out of its call sites into two named pipeline functions in `pushdown/support.rs`. Every other module-structure scenario is unchanged. Exactly one `vs-adapter/pushdown-planning*` scenario changes — `vs-adapter/pushdown-planning-string-fn-type-coercion-composition`'s composition scenario, amended to name the pipeline function as the pass-order owner — and no `pushdown-planning*` per-node decision or generated SQL changes.
* This delta SUPERSEDES the preceding Background bullet "Ordering the three guards into a pass pipeline is NOT part of this scenario. The one production chain site that sequences them (`like` → `string` → `decimal`) keeps its explicit composition and its load-bearing order comment." Issue #257 deferred the pipeline deliberately; issue #259 delivers it, so the chain site no longer holds its own composition or its order comment.
* The pass ORDER is the decision being relocated, not the traversal. Issue #257 gave the three guards one shared post-order traversal; each remains a per-node closure over it. This delta changes only WHERE the sequence of those guards is written down.
* The order is load-bearing in one direction: `string_function_arg_type_guard` MUST run before `rewrite_decimal_stringifications`, because the guard wraps a bare DECIMAL string-function argument into a `decimal_to_varchar_exasol` node, after which the rewriter sees a wrapped node rather than a bare column and correctly leaves it alone. Reversing the two would emit two trim wrappers. `vs-adapter/pushdown-planning-string-fn-type-coercion-composition` owns the verification of that interaction.
* The two pipelines carry DIFFERENT pass lists, which is why they are two functions rather than one function with a flag. The filter pipeline runs three passes; the select-list pipeline runs two, omitting the LIKE-subject pass. A boolean parameter would be a decision the module declined to make, and the omission carries a reason that belongs in a doc comment rather than at a caller's argument list.
* That omission is a TRACKED GAP, not an invariant. A select-list item CAN carry a `predicate_like` — directly (`SELECT c_date LIKE '2024%' FROM …`) or nested in a `function_scalar_case` — whose subject is a non-string column, and such an item still reaches the same DataFusion coercion failure the filter-side guard exists to prevent. The LIKE-subject pass is absent from the select-list pipeline only because that wiring is not yet done; it is tracked by issue #219 (#215 tracks the same absence on the broadcast-join per-leg filter path). Relocating the sequence is what makes #219 a one-line change inside one function body, which is the outcome #219 itself anticipates.
* Neither pipeline's doc comment nor any test SHALL record the select-list omission as intended behavior. A test pinning the current two-pass list MUST cite `(#219)`, so that when the LIKE pass is added its failure reads as "the tracked gap is closed", not "an invariant broke".
* The three passes disagree on fallibility, and the pipeline absorbs that disagreement: `like_subject_type_guard` and `string_function_arg_type_guard` return `Option<Json>` (a decline), `rewrite_decimal_stringifications` returns `Json` (never declines). Every caller previously spelled that asymmetry out as `.and_then(…).and_then(…).map(…)`.
* Pass-list COUNT, not call-site count, is what this delta reduces. Before this delta the production filter chain existed at exactly ONE site (`handle_pushdown`) and the select-list chain at exactly ONE site (`project_columns`); the remaining filter-chain occurrences were unit tests in `pushdown/mod.rs` replicating the production wiring by hand. Issue #259's "seven surfaces" counts those test replicas as production surfaces. The win is therefore single ownership of the order plus test replicas that call the real pipeline instead of re-deriving it — not the removal of duplicated production code.
* A decline from EITHER pass of the select-list pipeline MUST keep setting the existing full-row fallback flag, exactly as the two separate guard calls did. `vs-adapter/pushdown-planning-string-fn-type-coercion`'s select-list fallback scenario is the gate on that.
* Relocating the sequence removes every caller of the three passes outside `support`, so all three narrow from `pub(super)` to private. This inverts the feature's existing visibility rule — that rule caps how far a cross-submodule helper may widen and forbids widening past its prior visibility; it does not forbid narrowing once the cross-submodule callers are gone. The narrowing is what makes the order compiler-enforced rather than convention: outside `support` the pipeline is the only reachable entry point. Inside `support` the passes stay directly callable, which is how each pass's own isolation unit tests keep working.
* The two pipeline functions take the narrowest visibility that compiles, matching the rule this feature already records. The filter pipeline is `pub(super)` because `pushdown/mod.rs` calls it; the select-list pipeline is private because its only caller, `project_columns`, lives in `support` itself.
* The filter pipeline MUST NOT name the Iceberg file-pruning call. That the raw filter tree stays unmodified for pruning is a fact about the call site, not about the pass order, so that note stays at the call site while the order rationale moves into the pipeline's doc comment. For the same reason the select-list pipeline MUST NOT name the full-row fallback flag or `project_columns`' caller set — it reports a decline and the caller decides what a decline means.
* This delta SUPERSEDES the preceding Background bullet "The two pipelines carry DIFFERENT pass lists, which is why they are two functions rather than one function with a flag. The filter pipeline runs three passes; the select-list pipeline runs two, omitting the LIKE-subject pass. A boolean parameter would be a decision the module declined to make, and the omission carries a reason that belongs in a doc comment rather than at a caller's argument list." Both render surfaces now carry the SAME three-pass list, so the two functions become ONE — `apply_type_rewrites`. A pass-selection parameter remains rejected, now for a stronger reason: there is nothing left to select.
* This delta SUPERSEDES the preceding Background bullet "That omission is a TRACKED GAP, not an invariant. A select-list item CAN carry a `predicate_like` — directly (`SELECT c_date LIKE '2024%' FROM …`) or nested in a `function_scalar_case` — whose subject is a non-string column, and such an item still reaches the same DataFusion coercion failure the filter-side guard exists to prevent. The LIKE-subject pass is absent from the select-list pipeline only because that wiring is not yet done; it is tracked by issue #219 (#215 tracks the same absence on the broadcast-join per-leg filter path). Relocating the sequence is what makes #219 a one-line change inside one function body, which is the outcome #219 itself anticipates." The wiring is now done and issue #219 is closed; the prediction that it would reduce to one line inside one function body held.
* This delta SUPERSEDES the preceding Background bullet "Neither pipeline's doc comment nor any test SHALL record the select-list omission as intended behavior. A test pinning the current two-pass list MUST cite `(#219)`, so that when the LIKE pass is added its failure reads as "the tracked gap is closed", not "an invariant broke"." That rule did its job: the pinning test's `(#219)` citation is what identified the single assertion the fix flips. No pass omission remains to record.
* This delta SUPERSEDES the preceding Background bullet "A decline from EITHER pass of the select-list pipeline MUST keep setting the existing full-row fallback flag, exactly as the two separate guard calls did. `vs-adapter/pushdown-planning-string-fn-type-coercion`'s select-list fallback scenario is the gate on that." A decline from ANY of the THREE passes MUST keep setting the existing full-row fallback flag on the select-list path — the pass count went two → three and the two functions became one, but the caller's handling of a decline is unchanged. That same fallback scenario remains the gate.
* This delta SUPERSEDES the preceding Background bullet "The two pipeline functions take the narrowest visibility that compiles, matching the rule this feature already records. The filter pipeline is `pub(super)` because `pushdown/mod.rs` calls it; the select-list pipeline is private because its only caller, `project_columns`, lives in `support` itself." There is ONE pipeline function, and it takes the narrowest visibility that compiles under the same rule: `pub(super)`, because `pushdown/mod.rs` calls it. No private per-surface function remains — `project_columns` calls the same `pub(super)` function from inside `support`.
* This delta SUPERSEDES the preceding Background bullet "The filter pipeline MUST NOT name the Iceberg file-pruning call. That the raw filter tree stays unmodified for pruning is a fact about the call site, not about the pass order, so that note stays at the call site while the order rationale moves into the pipeline's doc comment. For the same reason the select-list pipeline MUST NOT name the full-row fallback flag or `project_columns`' caller set — it reports a decline and the caller decides what a decline means." The ONE pipeline function MUST NOT name the Iceberg file-pruning call, the full-row fallback flag, `project_columns`' caller set, or the SQL renderer. Both `MUST NOT`s now bind one function instead of one each, and that single caller-agnostic rule is what lets it serve two callers whose decline meanings differ: it reports a decline and each caller decides what a decline means.
* ONE function now owns the pass sequence for BOTH render surfaces, because equalizing the pass lists left the two functions with identical bodies and nothing to enforce their continued agreement. The function is named for what it does, not for one of its callers, and it is the same change as the #219 fix rather than a follow-up: that fix is what created the duplicate, so removing it in a later change would mean introducing a redundancy in one change and deleting it in the next.
* Two callers, one pipeline, two decline meanings. The caller-agnostic doc rule below is what makes a single function possible: because the pipeline never names what a decline means, one function can serve a caller that omits the whole filter and a caller that widens the projection to the full base row. Collapsing the functions therefore removes a duplicate body WITHOUT merging the two callers' semantics.
* Issue #215 is now the ONE render surface no pipeline guards: the broadcast-join PER-LEG filter path (`pushdown/joins/sql_builders.rs`), which builds its per-leg SQL without calling either pipeline. It is a distinct surface from the join SELECT list, which the select-list pipeline already reaches through `project_columns`.
* This delta adds ONE scenario: the frozen `crate::adapter::pushdown::<name>` façade is redrawn ONCE, deliberately, when the catalog access layer leaves the crate (issue #204). Every other scenario of this feature is unchanged, and no `vs-adapter/pushdown-planning*` scenario changes, because the redraw removes items rather than altering any decision or any generated SQL.
* The façade stays FROZEN after the redraw. This delta changes what the baseline IS, not whether there is one: the two probe files still fail the build on any unplanned narrowing, and a further change to the item set still needs its own spec delta.
* Because a Background bullet cannot override a normative scenario clause, the recorded scenario "Public pushdown façade resolves at every pre-refactor path" is AMENDED in place by this delta rather than left to contradict the new one. Its "diff empty against the captured baseline" and "every pre-refactor path MUST still resolve" clauses are re-anchored on the post-redraw 22-item and 12-item probe lists. This is the same treatment `vs-adapter/pushdown-catalog-session` applies to its two superseded scenarios; the marker differs only because this scenario is amended, not removed.
* The baseline the two probes cite, `specs/_plans/refactor-adapter-pushdown-modules/public-surface-baseline.txt`, no longer exists. `/speq:record` archived it with plan `refactor-adapter-pushdown-modules` into `specs/_recorded/`, which this project gitignores, so both probes point at a path that cannot be read. The probes' own `use` lists are the only surviving baseline and are promoted to being it.
* The `credentials` submodule named in this feature's second Background bullet is dissolved by the extraction, not merely renamed: its catalog HTTP, auth, session, and vended code becomes the `lakehouse-catalog` crate. `vs-adapter/catalog-crate-structure` owns the new boundary. The submodule list stays "a design decision recorded in the plan, not a normative contract", exactly as that bullet already says, so no bullet is superseded.
* `resolve_vended_storage` is deliberately NOT added to the pushdown façade as a replacement for the two items it retires. Adding it would re-create the coupling the redraw removes: a probe test in `lakehouse-engine` asserting a `lakehouse-catalog` concept through a re-export. The new crate carries its own probe instead.
* This feature's `pub(super)` visibility rule is unaffected. `redact_catalog_error` narrows out of `pushdown/support.rs` entirely by moving to another crate, which the rule permits — it caps how far a cross-submodule helper may WIDEN and does not forbid a helper leaving once its callers move.
