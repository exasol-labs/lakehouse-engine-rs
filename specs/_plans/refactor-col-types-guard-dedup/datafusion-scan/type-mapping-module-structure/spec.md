# Feature: Type Mapping Module Structure

Gives each repeated type-classification shape in the Arrow/Exasol mapping exactly one implementation, so a type added or reclassified has one place to land instead of several that can silently disagree. Behavior is unchanged: this feature constrains where the mapping lives, never what it returns.

This is the type-mapping layer's structural feature, the sibling of `vs-adapter/adapter-module-structure`, `vs-adapter/pushdown-module-structure`, and `datafusion-scan/scan-module-structure`. It exists because the duplication it removes spans `datafusion-scan/type-mapping`, `datafusion-scan/scan-execution`, `vs-adapter/create-virtual-schema`, and the pushdown-planning features at once — so no single behavioral feature can own it without leaking a structural decision across a boundary. It implements issue #176 and its follow-up comment; issue #265 owns the pushdown-guard rewiring this feature deliberately leaves undone.

## Background

* Every scenario is a pure refactor. Every scenario of `datafusion-scan/type-mapping`, `datafusion-scan/scan-execution`, `vs-adapter/create-virtual-schema`, and the `vs-adapter/pushdown-planning*` family stays behaviorally accurate and unedited, and those suites are the characterization gate that makes "behavior unchanged" falsifiable.
* Three recorded scenarios name `exasol_type_from_json` with a `vs-adapter/pushdown-planning` ownership parenthetical — `specs/datafusion-scan/type-mapping/spec.md` lines 123 and 128, and `specs/vs-adapter/pushdown-planning/spec.md` line 117. Those parentheticals stay correct and are NOT retargeted, because this feature moves the function's physical location without claiming its behavioral contract; see the relocation scenario's closing clause.
* The Arrow-to-Exasol table is a compliance surface (CLAUDE.md § Data types), so "behavior unchanged" means byte-identical output, not merely equivalent output.
* "Byte-identical" is asserted over the reachable input domain — every string this repo's producers emit. The unreachable inputs where consolidation changes the answer are named PER PARSER in the DECIMAL-parser scenario rather than left silent, because an unnamed divergence is indistinguishable from a regression. The two parsers have different divergence profiles: `exasol_type_to_json`'s is a closed three-class enumeration, while `sum_emit_type`'s is stated as two invariants over an open input set plus a list of representative inputs.
* A helper whose whole body is a call to another helper with the same arguments is a pass-through, the shallow-module red flag from `/speq:design-philosophy`. Every consolidation below deletes the duplicate rather than keeping it as a wrapper.
* This delta SUPERSEDES the preceding Background bullet "A helper whose whole body is a call to another helper with the same arguments is a pass-through, the shallow-module red flag from `/speq:design-philosophy`. Every consolidation below deletes the duplicate rather than keeping it as a wrapper." The pass-through definition is unchanged — SAME arguments — but the deletion rule gains one exception: a consolidation MAY keep a wrapper that supplies arguments the shared helper does not choose, because that is a partial application naming a decision rather than a pass-through forwarding the same arguments. The two `col_types` wrappers this delta's relocation scenario retains are that case: `extract_all_column_types` and `involved_table_columns` each supply their own table selection and case fold to `support::column_types`.
* `Json` in the adapter modules is an alias for `serde_json::Value`. Relocating the two JSON-shaped mapping functions gives `types/mapping.rs` a `serde_json` import it does not have today; the dependency direction stays correct, because `adapter` depends on `types` and never the reverse.
* This crate's CI gate is `cargo clippy --workspace --all-targets -- -D warnings`, under which an unused non-`pub` item is a build failure. That gate, not preference, fixes the visibility of an item added ahead of its consumer.
* No new dependency is introduced and no dependency version changes.
* This delta amends FOUR clauses across TWO scenarios of this feature and supersedes ONE Background bullet — the pass-through bullet, whose deletion rule gains the partial-application exception above — and nothing else. THREE of the four clauses are in the classifier scenario, all of them clauses that existed only because the classifier had no in-crate caller when issue #176 landed it: the `pub` visibility rationale, the "the three guards MUST NOT be rewired here" clause, and the doc-comment traceability clause naming issue #265 as an intended FUTURE consumer. Issue #265 has now rewired the three pushdown guards onto `classify_exa_type`, so none of the three still describes the code. The FOURTH is in the relocation scenario, "The Exasol type string and VS dataType JSON conversions live in the type-mapping module": the clause forbidding `extract_all_column_types` and `involved_table_columns` from being merged into one table-selector-parameterized builder, which deferred that merge to issue #265 — the merge this plan performs. Every other scenario of this feature is unchanged, and the classifier's PREDICATES are unchanged.
* The rewiring itself is specified by `vs-adapter/pushdown-module-structure`, which owns the guards' file set. This feature keeps owning WHAT `classify_exa_type` returns; that feature owns which guards call it and how each branches on the result. The division is the one this scenario's own "#265's substitution replaces each guard's type-string match arms only and never its lookup handling" clause already drew, and that clause stays accurate and is NOT amended.
* This delta SUPERSEDES two SCENARIO CLAUSES of the classifier scenario — not Background bullets — and the third is superseded in the `pub`-visibility bullet below. (a) The doc-comment clause "*AND* the doc comment on `classify_exa_type` SHALL name issue #265 as its intended first consumer, so an item with no in-crate caller is traceable rather than unexplained": the consumers now exist, so the doc comment names them instead of predicting them. (b) The rewiring clause "*AND* the three guards MUST NOT be rewired here, because issue #265 owns that file set and splitting it across two changes would leave neither reviewable on its own": issue #265 is this plan, so the rewiring happens now. The amended clause keeps that reason but scopes it to the change that INTRODUCED the classifier, and names `vs-adapter/pushdown-module-structure` as the rewiring's owner so the prohibition reads as the one-change-per-file-set rule it was, rather than as a standing ban.
* This delta also SUPERSEDES a clause of the relocation scenario, "*AND* `extract_all_column_types` (`support.rs`) and `involved_table_columns` (`joins/planning.rs`) MUST NOT be merged into one table-selector-parameterized builder, because that deduplication is issue #265's scope and only their import path changes here": that `MUST NOT` was a scope fence around the relocation change, not a permanent prohibition, and the scope it fenced off — issue #265 — is what this plan delivers. Leaving it standing would put a `MUST NOT` in the permanent library that the shipped code violates. The merge itself is specified by `vs-adapter/pushdown-module-structure`, which owns the two functions' file set; this feature records only that its own fence is lifted.
* This delta SUPERSEDES a third scenario clause of the classifier scenario, the `pub`-visibility clause "*AND* both items SHALL be declared `pub`, because `types::mapping` is a public module and a `pub(crate)` item with no consumer fails this crate's `-D warnings` clippy gate as dead code". That reason is DISCHARGED: issue #265 supplied the consumers, so a `pub(crate)` item would no longer be dead code.
* `pub` is RETAINED for both items regardless, and the reason is NOT that this feature's own "public API gains exactly two items" clause forbids narrowing — this delta amends four clauses of this feature, so that clause is amendable too, and citing it would settle nothing. The honest reason is narrower. `lakehouse-engine` ships as a UDF `.so` with no out-of-crate consumer, so both items are public API that nothing outside the crate can call, and narrowing them to `pub(crate)` removes real surface and is the right end state. It is simply not this change's: issue #265's whole contract is that no behavior and no API changes, every other edit in it is provably byte-identical, and a visibility change is not. `pub` is therefore retained SOLELY to keep the issue #265 diff API-neutral, and the narrowing is deferred to a separate API-pruning change. This feature's "public API gains exactly two items" clause consequently stays TRUE and is NOT amended — the deferral is what keeps it true.

### Scenario: The Exasol type string and VS dataType JSON conversions live in the type-mapping module

* *GIVEN* `exasol_type_to_json` (private in `adapter/mod.rs`) and its inverse `exasol_type_from_json` (`pub(super)` in `adapter/pushdown/support.rs`) — a matched pair over one grammar, neither reading any adapter or protocol state
* *WHEN* the adapter declares a `createVirtualSchema` column type, or reads a declared column or select-list type back off a pushdown request
* *THEN* both functions SHALL live in `crates/lakehouse-engine/src/types/mapping.rs` beside `arrow_to_exasol_type` and `exasol_type_to_arrow`, each declared `pub(crate)` — the narrowest visibility that reaches every call site
* *AND* every call site SHALL name the relocated path: the one `exasol_type_to_json` site in `adapter/mod.rs`, and the eight `exasol_type_from_json` sites spread across `adapter/pushdown/support.rs`, `adapter/pushdown/grouped_agg.rs`, `adapter/pushdown/file_resolution.rs`, and `adapter/pushdown/joins/planning.rs`
* *AND* the five existing unit tests for the two functions SHALL move to the `types/mapping.rs` test module with every test name and every asserted value unchanged
* *AND* the module doc comment of `types/mapping.rs` SHALL name all three representations the module now owns — the Arrow `DataType`, the Exasol SQL type string, and the VS `dataType` JSON object — so a reader landing in the module reads its scope there
* *AND* `extract_all_column_types` (`support.rs`) and `involved_table_columns` (`joins/planning.rs`) SHALL NOW be expressed on ONE shared builder, `support::column_types`. This clause's earlier `MUST NOT be merged` was a SCOPE FENCE around the relocation change, deferring the merge to issue #265; issue #265 has delivered the merge, so the fence no longer holds. `vs-adapter/pushdown-module-structure` owns the shared builder's contract — its parameters, what it absorbs, and each wrapper's signature and file — and this feature SHALL neither restate that contract nor forbid it, exactly as it keeps owning WHAT `classify_exa_type` returns while that feature owns how each guard branches on the result
* *AND* the BEHAVIORAL contract of both relocated functions SHALL remain owned by the features that already specify it, because only the physical location moves — this feature claims where the code lives, never what it returns. For `exasol_type_from_json` that owner is `vs-adapter/pushdown-planning`, which names the function directly in three recorded clauses; those `vs-adapter/pushdown-planning` parentheticals stay correct and MUST NOT be retargeted at this feature. `exasol_type_to_json` is named by no recorded scenario at all — its output is specified behaviorally as the `createVirtualSchema` column `dataType` JSON by `vs-adapter/create-virtual-schema`, and that indirect ownership is likewise unchanged by the move

### Scenario: One classifier names the Exasol type-string families the pushdown guards branch on

* *GIVEN* the three pushdown guards `guard_like_subject`, `is_bare_decimal_column`, and `coerce_string_position_arg` (`adapter/pushdown/support.rs`), which each branch over the same coarse Exasol-type-string family vocabulary — a `VARCHAR` or `CHAR` prefix, the exact string `DATE`, a `DECIMAL` prefix, and everything else — but each consume a DIFFERENT subset of it: `coerce_string_position_arg` uses all four families; `guard_like_subject` uses three, collapsing `DECIMAL` into the same declining branch as everything else; and `is_bare_decimal_column` is a two-way `DECIMAL`-versus-rest test
* *WHEN* a later change needs that family split
* *THEN* `types/mapping.rs` SHALL expose an `ExaTypeClass` enum with exactly the variants `Character`, `Date`, `Decimal`, and `Other`, and a `classify_exa_type` function taking an Exasol type string and returning that enum
* *AND* the function SHALL reproduce the guards' present predicates EXACTLY, pinned literally so no equivalent-looking variant can pass: `Character` iff the string `starts_with("VARCHAR")` OR `starts_with("CHAR")`; `Decimal` iff it `starts_with("DECIMAL")` with NO open paren — an implementation testing `starts_with("DECIMAL(")` MUST be rejected, because it silently diverges from all three guards on the bare string `DECIMAL`; `Date` iff the string EQUALS `DATE` exactly; `Other` otherwise. Adopting it is then a behavior-preserving substitution rather than a rewrite
* *AND* `classify_exa_type` SHALL take a NON-optional `&str`, because the column-lookup miss that all three guards ALSO decline on is not a type family and cannot be expressed by the classifier; that `Option<&str>` stays the caller's own branch, so #265's substitution replaces each guard's type-string match arms only and never its lookup handling
* *AND* both items SHALL be declared `pub`. The original reason was that a `pub(crate)` item with no consumer fails this crate's `-D warnings` clippy gate as dead code; that reason is DISCHARGED, because issue #265 supplied the consumers. `pub` is RETAINED regardless, and NOT because this feature's "public API gains exactly two items" clause forbids narrowing — that clause is amendable and settles nothing. `lakehouse-engine` ships as a UDF `.so` with no out-of-crate consumer, so both items are public API nothing outside the crate can call, and narrowing them to `pub(crate)` is the right end state; it is simply not issue #265's, whose contract is that no behavior and no API changes. `pub` is retained SOLELY to keep that diff API-neutral, and the narrowing SHALL be deferred to a separate API-pruning change rather than smuggled into a refactor that promises byte-identity
* *AND* the three guards MUST NOT be rewired in the change that introduces the classifier, because issue #265 owns that file set and splitting it across two changes would leave neither reviewable on its own; that rewiring is specified by `vs-adapter/pushdown-module-structure`, which owns the guards, and this feature SHALL NOT restate how any guard branches
* *AND* a unit test SHALL pin these representative strings: `VARCHAR(4) ASCII` and `CHAR(2)` as `Character`; `DECIMAL(20,0)` AND bare `DECIMAL` with no arguments as `Decimal` — the bare case is what separates the correct predicate from `starts_with("DECIMAL(")`, so omitting it leaves the contract untested; `DATE` as `Date`; and `TIMESTAMP` and `DOUBLE PRECISION` as `Other`, so #265's substitution is verifiable against a fixed contract
* *AND* the doc comment on `classify_exa_type` SHALL name its actual consumers — the three `adapter/pushdown/support.rs` guards — and SHALL NOT state that the guards run their own predicates independently nor that the classifier is not yet wired into them, because both ceased to be true when issue #265 landed; the guards' own `starts_with` and equality tests are gone, so a comment predicting a future consumer would misdescribe the code
