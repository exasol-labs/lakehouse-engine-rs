# Decision Log: refactor-col-types-guard-dedup

## Interview

**Q:** Issue #265 explicitly deferred the type-string classifier work to #176 and said only "once #176 lands" would the three guards collapse into matches differing solely in their Decimal arm. #176 has already landed on this branch — `classify_exa_type`/`ExaTypeClass` already exist in `types/mapping.rs`, and the recorded spec for that work states verbatim that "#265's substitution replaces each guard's type-string match arms." Should this plan do the full scope now (lookup helper + builder merge + wiring the three guards onto `classify_exa_type`), or hold the classifier-wiring back for a separate follow-up and only do the two extractions #265's body names directly?

**A:** Full scope now. Extract the col_types lookup helper, merge the two builders, AND rewire all three guards onto `classify_exa_type`/`ExaTypeClass`. The blocking dependency is gone and the recorded #176 spec already mandates this as #265's job.

## Design Decisions

### [1] The lookup helper does not test the node's `type` tag

- **Decision:** `column_exa_type(node, col_types) -> Option<&str>` owns only the resolve — read `name`, fold, scan `col_types`. Each of the three guards keeps its own `type == "column"` test ahead of the call.
- **Alternatives:** Fold the tag test into the helper, which would let `is_bare_decimal_column` collapse to a single line. Rejected.
- **Rationale:** The tag test and the lookup answer different questions, and the guards' handling of the two answers differs. `guard_like_subject` and `coerce_string_position_arg` return a non-`column` node UNCHANGED, but decline on a lookup miss. A helper mapping both to `None` would convert every literal and computed argument from a pass-through into a decline — silently dropping pushdown the guards accept today. The cost of keeping the tag test out is one retained early return per guard, which is the correct price.
- **Promotes to ADR:** yes

### [2] The helper returns `Option<&str>`, conflating a nameless column with an absent one

- **Decision:** `None` covers both a column node with no `name` string and a name not present in `col_types`.
- **Alternatives:** A three-state enum distinguishing "not a column", "nameless", and "not found".
- **Rationale:** All three guards already collapse those two cases — decline, decline, `false`. A third state would have no reader, and `/speq:design-philosophy` treats an interface distinction no caller uses as interface cost with no depth bought.
- **Promotes to ADR:** no

### [3] The helper folds with the Unicode `to_uppercase`, not `to_ascii_uppercase`

- **Decision:** `column_exa_type` uses `str::to_uppercase`.
- **Alternatives:** `to_ascii_uppercase`, which would match the join-side builder and make the join path resolve non-ASCII names.
- **Rationale:** All three guards fold Unicode today, and an extraction MUST NOT change which fold they apply. No reachable name distinguishes the two folds (decision [12]), but that equivalence rests on `resolve_table_schema`'s uppercasing — a decision this helper cannot observe and must not encode. Switching therefore buys nothing and would make a `support` helper depend silently on a `file_resolution` fold. The change belongs in the tracked follow-up (decision [12]) rather than smuggled into a refactor.
- **Promotes to ADR:** no

### [4] The merged builder takes table selection and case fold as two separate parameters

- **Decision:** `column_types(request, select_table, fold_case)`. `extract_all_column_types` passes a first-table selector plus `str::to_uppercase`; `involved_table_columns` passes a find-by-name selector plus `str::to_ascii_uppercase`.
- **Alternatives:** (a) One `Option<&str>` table-name argument — `None` meaning first table — with the fold derived from it. (b) One unified fold for both callers. (c) A builder taking the already-selected table `&Json`, leaving each caller its own `involvedTables` navigation.
- **Rationale:** (a) rejected because the selection and the fold correlate 1:1 by accident, not by design; deriving one from the other would record an unreconciled divergence as intended behavior and make a third selection-plus-fold combination inexpressible. (b) rejected as a behavior change. (c) rejected because issue #265's own direction is "one builder taking a table selector", and (c) leaves the `involvedTables` navigation duplicated — the smaller parameter list buys back less duplication than it costs. `fold_case` is nonetheless a parameter that exists ONLY to preserve a divergence this plan itself schedules for removal: closing the follow-up issue task 4 files removes `fold_case` from `column_types` and collapses the builder to a single fold. Task 4 requires the issue to say so, so the two-parameter shape reads as a preserved divergence with a known end date rather than as intended generality. Decision [12] rescoped that issue from a correctness reconciliation to a dead-flexibility removal, which strengthens the end-date argument rather than weakening it: the parameter now provably preserves nothing observable.
- **Promotes to ADR:** yes

### [5] Both builder wrappers are retained, and `involved_table_columns` stays in `joins/planning.rs`

- **Decision:** Neither wrapper is deleted; `involved_table_columns` keeps its file, its name, and its `pub(super) fn(&Json, &str)` signature.
- **Alternatives:** Delete both wrappers and call `column_types` directly at all ~19 sites; or move `involved_table_columns` into `support` beside the builder.
- **Rationale:** Each wrapper supplies arguments the builder does not choose, so neither is the same-arguments pass-through `/speq:design-philosophy` flags — each is a partial application naming a decision. Deleting them would edit roughly nineteen call sites inside a pure refactor. No recorded clause constrains either signature — the only recorded clause naming the two functions together is `datafusion-scan/type-mapping-module-structure`'s scope fence forbidding the merge (superseded by this plan's delta, decision [11]) — so holding both signatures is this plan's own choice, made to keep every call site untouched. Moving `involved_table_columns` would churn five joins-side import sites for no gain.
- **Promotes to ADR:** no

### [6] The two builders' case-fold divergence is pinned and tracked, not reconciled — SUPERSEDED by decision [12]

> SUPERSEDED in its REACHABILITY claim only. The task 3 live capture refuted the inference this entry rests on: an Iceberg column `straße` is served as `STRASSE`, not `STRAßE`, because `resolve_table_schema` uppercases every field name before Exasol sees it. The decision to preserve both folds and pin them with a test STANDS, for the reasons decision [12] gives. Everything below about the two captures, the inference, and the `nüm` counter-example is retained as the record of what was believed and how it was tested. See decision [12] "The fold divergence is unreachable, and the divergence is preserved for a design reason rather than a behavioral one".

- **Decision:** Preserve both folds byte-for-byte. Write the characterization test BEFORE the merge (task 4, ahead of task 5), and file a GitHub issue tracking reconciliation, cited in the test.
- **Alternatives:** Unify the folds in this plan; or preserve them silently as the pre-existing behavior they already are.
- **Rationale:** Unifying changes which non-ASCII join requests decline, which the "pure refactor" invariant excludes. Preserving them silently fails CLAUDE.md's "never a silent gap" standard, because the divergence has a real consequence. That consequence rests on TWO captures against the Docker Exasol container PLUS ONE inference — three parts, not a single measurement, and the plan states it that way because the third part is reasoning. Capture (1): Exasol normalizes an adapter-declared column name at all (`c_varchar` → `C_VARCHAR` in `SYS.EXA_ALL_COLUMNS` for four live virtual schemas, while `build_virtual_tables` uppercases nothing). Capture (2): that normalization is Unicode SIMPLE uppercasing, which leaves `ß` intact (`CREATE TABLE FOLDPROBE.T (nüm INT, straße INT, "nüm_q" INT)` → `NÜM`, `STRAßE`, `nüm_q`). The INFERENCE joining them is that Exasol applies the same Unicode SIMPLE fold to an adapter-supplied JSON `"name"` as to the native unquoted DDL identifier capture (2) probed — capture (2) measured a `CREATE TABLE` identifier, not an adapter-declared JSON name, so that link is not measured. Given it, `straße` is delivered as `STRAßE`, where Rust's Unicode fold yields `STRASSE` and its ASCII fold yields `STRAßE`; such a column resolves the `col_types` lookup on the single-table path and misses it on the join path, declining LIKE and string-function pushdown. Task 3 closes the FOLD link, and only that link, through a real `createVirtualSchema`. It reads the SERVED name of a `straße` column from `SYS.EXA_ALL_COLUMNS` for that virtual table. That served name is Exasol's own fold of an adapter-declared JSON `"name"`, which is the inference's content. The generated `EXPLAIN VIRTUAL` payload cannot discriminate and is not the channel: its `"projection"` entry and its `EMITS (…)` list both fold with `str::to_uppercase` and print `STRASSE` either way. The task is stated as a gate that halts the plan if the served form differs. One residual stays unmeasured, and it is NOT which form the request field carries. `STRAßE` and `straße` both fold to `STRASSE` under `to_uppercase` and both retain `ß` under `to_ascii_uppercase`, so either form yields the divergence. The residual is whether that name carries `ß` at all rather than arriving collapsed to `SS` or `ss`. Capture (1) cannot bear on it, because every name it read is ASCII, where the two folds agree. A `ü`-only name does NOT reach it — Exasol delivers `NÜM` pre-folded — so the pinning test and the filed issue must name `straße`, not `nüm`. Test ordering is load-bearing — the merge's failure mode is passing silently, so the test must exist before the merge. The citation convention mirrors this feature's existing `(#219)` tracked-gap pattern, so a later unification reads as "the tracked divergence is closed" rather than "an invariant broke".
- **Promotes to ADR:** yes

### [7] The four-way guards match exhaustively; the two-way guard need not

- **Decision:** `guard_like_subject` and `coerce_string_position_arg` match `Option<ExaTypeClass>` with no wildcard arm. `is_bare_decimal_column` stays a two-way `matches!` test.
- **Alternatives:** Wildcard arms everywhere (smaller diff, preserves the current `_ => None` shape); or exhaustiveness in all three.
- **Rationale:** For the four-way guards a variant added to `ExaTypeClass` is a real unanswered question, and a wildcard would answer it as "decline" silently. For a two-way `Decimal`-versus-rest test a new family genuinely IS "not DECIMAL", so exhaustiveness would force an edit that could only restate the same answer — ceremony without a decision.
- **Promotes to ADR:** yes

### [8] The one `Decimal` arm the two guards disagree on stays a visible match arm

- **Decision:** `guard_like_subject` declines `Decimal` alongside `Other` and the miss; `coerce_string_position_arg` coerces it through `wrap_decimal_to_varchar`. No abstraction over the difference.
- **Alternatives:** A coercion-policy trait, a shared per-family dispatch table, or a parameter selecting the DECIMAL behavior.
- **Rationale:** Issue #265's own non-goal, and correct: one closed variation between two functions is an interface with one real distinction. An abstraction here would be the single-implementation interface `/speq:design-philosophy` rejects.
- **Promotes to ADR:** no

### [9] `classify_exa_type` and `ExaTypeClass` stay `pub`

- **Decision:** Retain `pub` on both. Update only the doc comment, which currently predicts #265 as a future consumer. Record the narrowing as deliberately deferred to a separate API-pruning change, named in § Non-Goals and in § Dead Code Removal.

- **Rationale:** The reason first given for retaining `pub` was circular and is dropped: it appealed to `datafusion-scan/type-mapping-module-structure`'s "public API gains exactly two items" clause as binding, when this plan's own delta already amends four clauses of that same feature — so that clause is amendable too, and citing it settles nothing. "Buys nothing" was also unestablished: `lakehouse-engine` ships as a UDF `.so` with no out-of-crate consumer, so both items are public API nothing outside the crate can call, and narrowing them removes real surface. The narrowing is therefore right, but not here. It is an API change inside a diff whose whole promise is that no API and no behavior changes — every other edit in this plan is provable byte-identical, and a visibility change is not. `pub` is retained SOLELY to keep this refactor's diff API-neutral. No GitHub issue is filed for the deferral, because there is no gap, no deviation, and no user-visible consequence to track — this decision entry is the record, and it promotes with the plan.

### [12] The fold divergence is unreachable, and the divergence is preserved for a design reason rather than a behavioral one

- **Decision:** Keep both folds byte-for-byte and keep task 4's test, on new grounds. Supersedes decision [6]'s reachability claim. Record in the deltas that no column name the adapter can declare distinguishes the two folds, and rescope the follow-up issue from reconciling a divergence to deleting `column_types`' `fold_case` parameter as dead flexibility.
- **Alternatives:** (a) Unify the folds in this plan, now that no reachable input distinguishes them, deleting `fold_case` and one test in the same change. (b) Keep the divergence and say nothing further, on the grounds that nothing observable changed.
- **Rationale:** The task 3 live capture measured `STRASSE` where the plan expected `STRAßE`. The root cause is this crate's own code, not Exasol's: `resolve_table_schema` (`file_resolution.rs:610-644`) maps every Iceberg field through `f.name.to_uppercase()` at line 640, and that list is the sole input to the per-column `"name"` `build_virtual_tables` declares (`adapter/mod.rs:551`, `json!` at `:576`). One production site declares a column name, one caller reaches it (`adapter/mod.rs:255`), so this holds for every table. Rust's full-Unicode uppercase maps `ß` to `SS`, so the `ß` is erased upstream of anything Exasol does. Both folds are then no-ops on the result, verified rather than argued: `to_ascii_uppercase` changes only ASCII `a-z`, which `to_uppercase` output cannot contain, and a sweep of all 1,112,064 Unicode scalar values found zero cases where a second `to_uppercase` or a `to_ascii_uppercase` alters `to_uppercase` output. (a) is rejected because unifying still changes `involved_table_columns`' output for a non-ASCII input, which the pure-refactor invariant excludes, and because its harmlessness rests on a fold `resolve_table_schema` owns — encoding that dependency inside `column_types` is the information leakage this plan exists to remove. (b) is rejected on CLAUDE.md's never-a-silent-gap standard: `fold_case` is a parameter preserving nothing observable, which reads as intended generality unless something says otherwise. The surviving framing is the one the sibling `datafusion-scan/type-mapping-module-structure` delta already uses for its DECIMAL parsers — a divergence over an unreachable input domain, named rather than left silent.
- **Promotes to ADR:** yes

### [13] Task 4's test survives the refutation, reframed rather than inverted or dropped

- **Decision:** Keep the test's code, its name, its file, and its position ahead of the merge. Change only its recorded justification: a constructed literal on which Rust's two folds disagree, not the form Exasol delivers. Its doc comment must say so and must say why the test is still required.
- **Alternatives:** (a) Invert it to assert the two folds AGREE on every reachable, already-uppercased input. (b) Drop it, letting task 5's merge rest on the pre-existing suite.
- **Rationale:** Both alternatives remove the plan's only guard on task 5's fold-preservation contract. (a) fails on its own logic: an agreement assertion also holds after a unified merge, so it detects nothing. (b) fails on a checked fact — every column name reaching either builder in production is already Unicode-uppercased, so no pre-existing test distinguishes the two folds and a silent unification passes the whole suite. That is exactly the failure mode decision [6] called load-bearing, and the refutation does not touch it: what changed is whether the divergence has a user consequence, not whether the merge can alter a function's output undetected. Task 1's test needs the same wording correction and no code change, for the same reason — it was always a pure-function unit test over literal slices, and only its justification claimed a delivered form.

### [plan-review] The fold divergence is reachable via `ß`, not `ü` — captured live

- **Finding:** round 1, BLOCKER 2, `[UNSTATED_ASSUMPTION]` (Feasibility). The delta asserted as normative fact, from code inspection alone, that a non-ASCII column name resolves on the single-table path and misses on the join path. CLAUDE.md § Verification discipline requires such a claim be checked against a live Exasol system. Nothing in the plan checked what casing Exasol delivers in `involvedTables[].columns[].name`, and the plan's own example (`nüm`) would have pinned an unreachable input.
- **Direction change:** Captured against the local Docker Exasol container during this revision. (1) `SELECT COLUMN_SCHEMA, COLUMN_TABLE, COLUMN_NAME FROM SYS.EXA_ALL_COLUMNS` shows the `typed_distinct_probe` fixture's lowercase Iceberg names (`id`, `c_varchar`, `c_decimal_a`) served as `ID`, `C_VARCHAR`, `C_DECIMAL_A` for all four live virtual schemas, while `adapter/mod.rs::build_virtual_tables` declares them verbatim and uppercases nothing — so Exasol normalizes the declared name.
