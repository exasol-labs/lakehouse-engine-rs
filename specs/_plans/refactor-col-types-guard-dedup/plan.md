# Plan: refactor-col-types-guard-dedup

## Summary

Give the pushdown type-rewrite guards' `col_types` handling one owner per decision, per issue #265; the generated SQL stays byte-identical. Three substitutions do it — one lookup helper, one builder, one classifier — plus new E2E coverage for a `straße`-named table and column.

## Design

### Context

`col_types: Vec<(UPPERCASE_NAME, EXASOL_TYPE_STRING)>` is the per-request column-type list the three type-rewrite guards branch on. Three decisions about it live in more than one place, and nothing structurally enforces their agreement — the agreement rests on doc-comment notes each guard carries asserting it mirrors the other two, one of them citing a line number (`support.rs:411`) that no longer points at the code it names.

Issue #265 deferred one third of the work to issue #176, which has since landed on this branch: `ExaTypeClass` and `classify_exa_type` already exist in `types/mapping.rs`, built for this consumer and recorded with a doc comment naming #265 as their intended first caller. The blocking dependency is gone, so this plan does the full scope.

- **Goals** — one owner per decision: one `col_types` lookup, one `col_types` builder, one Exasol-type-family classifier. Byte-identical generated SQL. Every existing test passes with no assertion edited.
- **Non-Goals**
  - A `HashMap` for `col_types`. The scan is tens of entries; lookup cost is not the pain (issue #265 non-goal).
  - A coercion-policy trait or shared dispatch table for the one `Decimal` arm two guards disagree on (issue #265 non-goal) — a visible match arm says it better.
  - Reconciling the two builders' case folds. `extract_all_column_types` folds Unicode, `involved_table_columns` folds ASCII-only, and preserving that divergence is a hard requirement of this plan. The task 3 live capture proved the divergence unobservable through the adapter, so a follow-up issue tracks removing `column_types`' `fold_case` parameter as dead flexibility rather than as a correctness fix (task 4).
  - Documenting or changing the `ß`-to-`SS` expansion itself. Task 7 adds three `vs-adapter/create-virtual-schema` clauses stating that column names are declared through the same full-Unicode `to_uppercase` as table names, plus a live E2E scenario proving a `straße`-named table and column stay queryable. Neither changes the fold or adds a collision check for the expansion; the expansion is named as a deliberate Exasol-target trade-off.
  - Absorbing the four `col_types` scans that take an already-resolved `&str` name rather than a JSON node — `project_columns`'s `type_by_upper`, `topn.rs`'s hidden-column appender, `col_type_for`, and `scan/join_scan.rs`'s logical-field scan. Named in the spec delta with the reason.
  - Extracting `parse_sort_key_element`'s node-to-uppercased-name half (`topn.rs`), which resolves an identifier from an `orderBy` element wrapper, not a type.
  - Narrowing `classify_exa_type` or `ExaTypeClass` from `pub` to `pub(crate)` now that a caller exists. Deferred to a separate API-pruning change — not because a recorded clause forbids it, but to keep this pure refactor's diff free of an API change. See § Consequences and decision [9].

### Decision

Split the guards' work into the two questions it actually asks, and give each question one owner.

#### Architecture

```
  pushdown/support.rs                                  types/mapping.rs
  ┌───────────────────────────────────────┐            ┌──────────────────────┐
  │ column_types(request, select, fold)   │───────────▶│ exasol_type_from_json│
  │   ▲ pub(super), the ONE builder       │            │                      │
  │   │                                   │            │ classify_exa_type    │
  │   ├── extract_all_column_types(req)   │            │ ExaTypeClass         │
  │   │      (first table, to_uppercase)  │            └──────────▲───────────┘
  │   └── joins/planning.rs::             │                       │
  │         involved_table_columns(req,n) │                       │ family
  │          (find-by-name, to_ascii_…)   │                       │
  │                                       │                       │
  │ column_exa_type(node, col_types)      │                       │
  │   -> Option<&str>   ▲ private         │                       │
  │        ┌────────────┼────────────┐    │                       │
  │  guard_like_subject │            │    │                       │
  │  is_bare_decimal_column          │    │───────────────────────┘
  │  coerce_string_position_arg ─────┘    │
  └───────────────────────────────────────┘
```

Two seams, deliberately not one. `column_exa_type` answers "what type is this node's column, if any"; `classify_exa_type` answers "what family is this type string". Fusing them would force the lookup miss into the classifier, which the recorded #176 contract forbids by taking a non-optional `&str`.

Each guard keeps two things of its own: the `type == "column"` test and the meaning of a miss. That is not leftover duplication — a non-`column` node passes through in two guards but a miss declines, so a helper that absorbed the tag test would turn every literal and computed argument from a pass-through into a decline.

Dependency direction is unchanged: `adapter` depends on `types`, never the reverse.

#### Patterns

| Pattern | Where | Why |
|---------|-------|-----|
| Resolve and classify as two helpers | `column_exa_type` in `support`, `classify_exa_type` in `types::mapping` | Keeps the column-lookup miss out of the classifier, per the recorded #176 contract; each helper answers one question |
| Partial application over a mode flag | `column_types(request, select_table, fold_case)`, wrapped twice | Table selection and case fold are independent decisions; one mode argument would encode "first table implies Unicode fold" as intentional |
| Exhaustive match, no wildcard | the two `Option<Json>` guards over `Option<ExaTypeClass>` | A fifth `ExaTypeClass` variant becomes a compile error at each guard instead of a silent decline |
| Visible variation over abstraction | the one `Decimal` arm where the two guards differ | One closed variation between two functions reads better as two arms (issue #265 non-goal) |
| Characterization test before merge | the wrapper-fold test (task 4) precedes the merge (task 5) | The merge's failure mode is passing silently, and it is the ONLY change here that can pass the whole pre-existing suite while altering a function's output. Every name reaching either builder in production is already Unicode-uppercased, so no existing test distinguishes the two folds; task 4's constructed literal is the sole assertion that does |
| Gate a reachability claim before a test asserts it | the live capture (task 3) ran ahead of tasks 1 and 4 and REFUTED the claim | The gate did its job. It replaced an inferred developer-facing consequence with a measured "no reachable input", which is why § Impact reads None and task 4's framing changed rather than its code |

### Consequences

| Decision | Alternatives Considered | Rationale |
|----------|------------------------|-----------|
| `column_exa_type` does NOT test the node's `type` tag | Absorb the tag test so `is_bare_decimal_column` collapses to one line | The tag test and the lookup answer different questions. Two guards pass a non-`column` node through and decline a miss; one helper returning `None` for both would convert pass-through to decline for every literal and computed argument. Cost of keeping it out: one retained early return per guard |
| Helper returns `Option<&str>`, conflating nameless-column and absent-from-list | A three-state enum distinguishing them | All three guards already treat the two identically — decline, decline, `false`. A third state would have no reader |
| Helper folds with the Unicode `to_uppercase` | `to_ascii_uppercase`, matching the join-side builder | All three guards fold Unicode today, and an extraction MUST NOT change which fold they apply. No reachable name distinguishes the two, but that equivalence rests on `resolve_table_schema`'s uppercasing — a decision this helper cannot see and must not encode |
| Builder takes selection AND fold as two parameters | One `Option<&str>` table-name argument deriving the fold from it | The two correlate 1:1 by accident, not by design. Deriving one from the other would record an unreconciled divergence as intended behavior and make a third combination inexpressible |
| `involved_table_columns` stays in `joins/planning.rs` | Move it to `support` beside the builder | Its name and its four production plus nine test call sites are joins-side; moving it churns five import sites for no gain. Keeping its signature is this plan's own choice, made to leave every call site untouched — no recorded clause constrains it |
| Both wrappers are retained, not deleted as pass-throughs | Delete them and call the builder directly at all sites | Each supplies arguments the builder does not choose, so neither is the same-arguments pass-through `/speq:design-philosophy` flags. Deleting them would edit ~15 call sites for a pure refactor |
| Fold divergence is pinned by test and tracked by a new issue, not fixed | Unify the two folds in this plan, now that the live capture shows no reachable input distinguishes them | Unifying still changes `involved_table_columns`' output for a non-ASCII input, which the "pure refactor" invariant excludes. Its harmlessness would rest on a fold `resolve_table_schema` owns, so the merged builder would silently depend on another module's decision. The precedent is this feature's own collect-walk scenario, which ruled the same divergence out of scope; the sibling `type-mapping-module-structure` delta's precedent is naming an unreachable divergence rather than acting on it |
| Task 4's test survives the refutation, reframed rather than rescoped | (a) Invert it to assert the two folds AGREE on every reachable input; (b) drop it and let the pre-existing suite guard task 5 | Both remove the plan's only guard on task 5's fold-preservation contract. (a) fails because an agreement assertion also holds under a unified fold; (b) fails because every column name reaching either builder in production is already Unicode-uppercased, so a silent unification passes the entire existing suite. The test's code is unchanged; only its recorded justification moves from "the form Exasol delivers" to "a constructed literal on which the two folds disagree" |
| New E2E coverage is a `create-virtual-schema` scenario, not a `pushdown-module-structure` one | Add it under `pushdown-module-structure`, the feature this plan otherwise extends | The property is that a declared identifier survives the `createVirtualSchema` round trip and stays queryable. That feature owns declaring names to Exasol; `pushdown-module-structure` is a code-organization feature that owns no live identifier behavior. The column-casing documentation gap the capture surfaced lives in the same clause, so one delta covers both |
| `classify_exa_type` and `ExaTypeClass` stay `pub` | Narrow to `pub(crate)` now that the dead-code reason for `pub` is discharged | No recorded clause forbids the narrowing — this plan's delta already amends three clauses of that same feature, so the API-count clause is amendable too. The crate ships as a UDF `.so` with no out-of-crate consumer, so both items are public API nothing outside the crate can call. `pub` is retained solely to keep this pure refactor's diff free of an API change; the narrowing is deferred to a separate API-pruning change, recorded in decision [9] |
| `is_bare_decimal_column` may match non-exhaustively where the other two may not | Require exhaustiveness in all three | A family added later genuinely IS "not DECIMAL" for a two-way test, so exhaustiveness there forces an edit that can only restate the same answer. For the four-way guards a new variant is a real unanswered question |

## Impact

None for users or operators. Generated scan SQL, join SQL, and every declared column type are byte-identical, so no query result changes. No breaking change.

No developer-facing consequence either. The two `col_types` builders' case-fold divergence is unreachable for every column name and every table. This crate uppercases each Iceberg field name itself before Exasol sees it (`resolve_table_schema`, `file_resolution.rs:640`), so every name reaching a builder is already Unicode-uppercased, where the two folds provably agree. The task 3 live capture measured it: an Iceberg column `straße` is served as `STRASSE`, refuting the earlier inference that Exasol would deliver `STRAßE`. Evidence and the refutation sit in `vs-adapter/pushdown-module-structure`'s captured-evidence Background bullets.

Two additions, neither a behavior change. Task 4's characterization test is retained on a constructed literal, because it is the only assertion in the repository that distinguishes the two folds and therefore the only guard against task 5's merge unifying them silently; its follow-up issue is rescoped from a correctness fix to removing `column_types`' `fold_case` parameter as dead flexibility. Task 7 adds the permanent E2E coverage a `straße`-named table and column deserve, plus the three `create-virtual-schema` clauses stating the column-name fold the library never documented.
