# Plan Review Findings: refactor-col-types-guard-dedup (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 11 (Blockers: 3, Advisory: 8)
- Intent Fidelity blockers: 0

## Premortem

Three failure stories, each routed to a finding below.

1. **The load-bearing test never existed.** Both new tests are specified to live in `support.rs` and to call `involved_table_columns`, which `support` cannot reach. An implementer hits `E0603`, drops or weakens the assertion, and the builder merge lands with both callers folding the same way — the exact silent-pass failure mode task 3 exists to catch. → BLOCKER 1.
2. **The spec library records a divergence nobody ever observed.** The delta asserts as normative fact that a non-ASCII column name resolves single-table and misses on the join path. Nothing in the plan checks what casing Exasol actually delivers in `involvedTables[].columns[].name`. A later engineer chases a phantom, or closes the filed issue as not reproducible. → BLOCKER 2.
3. **The proof gates are theater.** Of the eight Manual Testing rows, one is unsatisfiable against the delta's own doc-comment preservation clause, one greps a regex that can never match, and one asserts a line-count outcome the command cannot measure and the diff will contradict. The plan leans on these as the substitute for a red test phase. → BLOCKER 3, ADVISORY 5.

## Intent Fidelity

No objection — axis checked. Issue #265's body (fetched live) names exactly the lookup helper, the builder merge, and its two non-goals (`HashMap`, coercion-policy trait); the plan carries both non-goals verbatim and executes the full scope the interview authorized, including the classifier wiring #265 deferred to #176. #265 asks for nothing the plan drops: the four other `col_types` scans are absent from #265's body, so naming them out of scope removes nothing from the ask. Filing the fold-reconciliation issue is CLAUDE.md's "never a silent gap" rule, not gold-plating.

## Feasibility

#### [COMPLETENESS_GAP] BLOCKER
- Location: plan.md § Implementation Tasks tasks 1 and 3; § Verification rows 1-2; `vs-adapter/pushdown-module-structure/spec.md` clauses at lines 102 and 118
- Issue: neither new test can compile where the plan puts it. Both are specified in `crates/lakehouse-engine/src/adapter/pushdown/support.rs` and both call `involved_table_columns` — task 1: "returns `None` against an `involved_table_columns` list"; the spec clause: "MUST return `None` against a list built by `involved_table_columns`". That function is unreachable from `support` twice over: `joins/mod.rs:10` declares `mod planning;` **private**, and `joins/mod.rs:28-31` re-imports the name with a plain private `use planning::{involved_table_columns, …}`. Its own `pub(super)` at `planning.rs:359` scopes it to `adapter::pushdown::joins` and that subtree only — `support` is a sibling, not a descendant. The delta's own visibility reasoning covers only the opposite direction (`support` → `joins`), which is why the gap went unnoticed. The three escapes all contradict a clause the plan wrote: widening `involved_table_columns` contradicts "`involved_table_columns` SHALL keep its `pub(super) fn(&Json, &str)` signature" and "NO item's visibility widens"; relocating the test contradicts "the helper SHALL be declared private to `support`"; hand-building the ASCII list contradicts "a list built by `involved_table_columns`". The plan calls task 3's test the thing that makes the merge "fail loudly" instead of passing silently, so this is the plan's primary safety mechanism failing to exist.
- Fix: In plan.md task 3 and in the `vs-adapter/pushdown-module-structure` delta, add the test-only re-export this repo already uses for the same problem: `#[cfg(test)] pub(super) use planning::involved_table_columns;` in `joins/mod.rs`, matching the existing block at `joins/mod.rs:21-27` (`#[cfg(test)] pub(super) use sql_builders::{build_qualified_single_table_fallback_sql, referenced_column_projection};`, reached from `support.rs:2951` by `use super::super::joins::{…}`). Add a Background bullet to that delta recording the widening as `#[cfg(test)]`-only, and amend the "NO item's visibility widens" clause to except it, so the clause stays true of production visibility. State in tasks 1 and 3 that both tests import `involved_table_columns` through `super::super::joins`.

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `vs-adapter/pushdown-module-structure/spec.md` line 79; plan.md § Impact paragraph 2; decision-log.md decision [6]; plan.md task 3 (the issue to be filed)
- Issue: the delta records as normative fact a limitation no one measured — "a non-ASCII column name resolves on the single-table path and MISSES on the join path, so the guards decline a LIKE or string-function pushdown they would accept for the same column reached through the single-table request". That is reachable only if Exasol delivers a column name containing a **lowercase non-ASCII letter** in `involvedTables[].columns[].name`; on an already-uppercased name both folds are no-ops and the divergence is unreachable. Nothing in the plan or decision log checks which is true. The evidence available cuts both ways: `adapter/mod.rs::build_virtual_tables` declares each column as `"name": name` **verbatim** from the Iceberg schema (no uppercasing, unlike the table name, which `specs/vs-adapter/create-virtual-schema/spec.md:61` requires be uppercased), yet every captured request fixture in `dispatch_golden.rs:38-45` carries already-uppercased column names. CLAUDE.md § Verification discipline binds exactly this claim: "A claimed SQL capability gap or limitation MUST be verified against a live Exasol system (`EXPLAIN VIRTUAL`, an actual pushed query, or an E2E test), not assumed from documentation, memory, or a capability registry". The plan asserts it from code inspection, records it in the permanent spec library, publishes it in § Impact as a developer-facing consequence, and files a GitHub issue on it.
- Fix: Add a task before task 3 that determines, against the Docker Exasol container, whether a pushdown request can carry a column name whose Unicode and ASCII uppercase folds differ — create an Iceberg table with a lowercase non-ASCII column name, `createVirtualSchema` over it, and capture the delivered `involvedTables[].columns[].name`. Cite the captured evidence inline in the `vs-adapter/pushdown-module-structure` delta beside the line-79 claim. If the name arrives already uppercased, rewrite that clause and plan.md § Impact to state the divergence is a code-level difference with no reachable request today, pinned defensively, and scope the filed issue to that finding instead of to a user-visible decline.

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: plan.md § Manual Testing row 3 versus `vs-adapter/pushdown-module-structure/spec.md` clause at line 101; plan.md task 2
- Issue: the gate and the preservation clause cannot both hold. Row 3 runs `grep -rn 'starts_with("VARCHAR")\|starts_with("CHAR")\|starts_with("DECIMAL")\|== "DATE"' crates/lakehouse-engine/src/adapter/` and expects "No hits outside tests". `support.rs:811` is such a hit and is not a test — it is `is_bare_decimal_column`'s doc comment: "Integer columns are wire-encoded as `DECIMAL(p,0)`, so `.starts_with("DECIMAL")` also matches them". The delta simultaneously requires "each guard's doc comment SHALL otherwise be preserved". After task 2 that predicate lives only in `classify_exa_type`, so the preserved sentence describes code the function no longer contains — a fresh instance of the defect this plan exists to delete (`guard_like_subject`'s stale `support.rs:411` citation). Verified by running the gate's own grep against the current tree: five hits, one of them the doc comment.
- Fix: In plan.md task 2, add: reword `is_bare_decimal_column`'s doc comment so the integer-`DECIMAL(p,0)` rationale names `ExaTypeClass::Decimal` instead of `.starts_with("DECIMAL")`. In the `vs-adapter/pushdown-module-structure` delta, amend the line-101 preservation clause to except any sentence naming a predicate that moves to `classify_exa_type`, and keep the rationale itself required.

#### [EFFORT_MISESTIMATION] ADVISORY
- Location: plan.md task 4; § Design → Architecture (`column_types(request, select, fold)`)
- Issue: the builder's signature is stated only as `column_types(request, select_table, fold_case)`, with no bound for `select_table`. The selector returns a reference borrowed from its argument, so the parameter needs a higher-ranked bound (`impl Fn(&[Json]) -> Option<&Json>`), the closure needs its parameter annotated (`|tables: &[Json]| …`) for inference to land, and the return type needs an explicit lifetime tying `Option<&str>`/the vec to `col_types` where elision cannot. `involved_table_columns`' selector also captures `table_name`, so a plain `fn` pointer will not serve. Task 4 is `[expert]`, so this is a thrash risk rather than a wall — but the plan states the shape as if it were obvious.
- Fix: In plan.md task 4, state the signature with its bounds: `pub(super) fn column_types(request: &Json, select_table: impl FnOnce(&[Json]) -> Option<&Json>, fold_case: impl Fn(&str) -> String) -> Vec<(String, String)>`, and note that both wrappers annotate their closure parameter as `&[Json]`.

## Requirement Quality

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: plan.md § Manual Testing rows 2 and 6
- Issue: two gates cannot produce the stated result. Row 2 pairs `grep -c 'col_types' …support.rs` with `grep -n 'iter()' -A1 …support.rs | grep -c 'find(|(n, _)| *n == name)'` under one expectation, "Exactly 1". The first command counts dozens of `col_types` occurrences (the parameter appears in every guard signature and in the test corpus), and the second can never match: in a POSIX basic regex the `*` after `| ` is a quantifier over the space, so the pattern demands `n == name)` where the code has `*n == name)` — it returns 0 both before and after the refactor. Row 6 runs `git diff --stat -- crates/lakehouse-engine/src` expecting "`support.rs` and `joins/planning.rs` both shrink in production code", but `--stat` reports one insertion/deletion pair per file with no production/test split, and this plan adds two test blocks **and** a relocated ~20-line builder to `support.rs` — so the row's own command will show `support.rs` growing.
- Fix: In plan.md § Manual Testing, replace row 2's second command with a fixed-string count, `grep -cF 'find(|(n, _)| *n == name)' crates/lakehouse-engine/src/adapter/pushdown/support.rs`, expected `1`, and delete the `grep -c 'col_types'` command from that row. Replace row 6 with `grep -c 'exasol_type_from_json\|to_ascii_uppercase' crates/lakehouse-engine/src/adapter/pushdown/joins/planning.rs`, expected `1`, and drop the net-line-count expectation for `support.rs`.

## Design Depth

#### [TACTICAL_SHORTCUT] ADVISORY
- Location: plan.md task 3 and task 4; decision-log.md decisions [4] and [6]
- Issue: `fold_case` is a configuration parameter that exists only to preserve a divergence the plan itself calls a defect to be reconciled. `/speq:design-philosophy` treats a parameter as a decision the module declined to make, and this one is scheduled to disappear — once the folds unify, the builder takes one fold and the parameter is dead weight. #### [SHALLOW_DESIGN] ADVISORY
- Location: decision-log.md decision [9]; plan.md § Non-Goals and § Consequences (final row); `datafusion-scan/type-mapping-module-structure/spec.md` line 20
