# Feature: Type Mapping Module Structure

Gives each repeated type-classification shape in the Arrow/Exasol mapping exactly one implementation, so a type added or reclassified has one place to land instead of several that can silently disagree. Behavior is unchanged: this feature constrains where the mapping lives, never what it returns.

### Scenario: The Exasol type string and VS dataType JSON conversions live in the type-mapping module

* *GIVEN* `exasol_type_to_json` (private in `adapter/mod.rs`) and its inverse `exasol_type_from_json` (`pub(super)` in `adapter/pushdown/support.rs`) — a matched pair over one grammar, neither reading any adapter or protocol state
* *WHEN* the adapter declares a `createVirtualSchema` column type, or reads a declared column or select-list type back off a pushdown request
* *THEN* both functions SHALL live in `crates/lakehouse-engine/src/types/mapping.rs` beside `arrow_to_exasol_type` and `exasol_type_to_arrow`, each declared `pub(crate)` — the narrowest visibility that reaches every call site
* *AND* every call site SHALL name the relocated path: the one `exasol_type_to_json` site in `adapter/mod.rs`, and the eight `exasol_type_from_json` sites spread across `adapter/pushdown/support.rs`, `adapter/pushdown/grouped_agg.rs`, `adapter/pushdown/file_resolution.rs`, and `adapter/pushdown/joins/planning.rs`
* *AND* the five existing unit tests for the two functions SHALL move to the `types/mapping.rs` test module with every test name and every asserted value unchanged
* *AND* the module doc comment of `types/mapping.rs` SHALL name all three representations the module now owns — the Arrow `DataType`, the Exasol SQL type string, and the VS `dataType` JSON object — so a reader landing in the module reads its scope there
* *AND* `extract_all_column_types` (`support.rs`) and `involved_table_columns` (`joins/planning.rs`) SHALL NOW be expressed on ONE shared builder, `support::column_types`. This clause's earlier `MUST NOT be merged` was a SCOPE FENCE around the relocation change, deferring the merge to issue #265; issue #265 has delivered the merge, so the fence no longer holds. `vs-adapter/pushdown-col-types-consolidation` owns the shared builder's contract — its parameters, what it absorbs, and each wrapper's signature and file — and this feature SHALL neither restate that contract nor forbid it, exactly as it keeps owning WHAT `classify_exa_type` returns while `vs-adapter/pushdown-module-structure` owns how each guard branches on the result. That owner name SHALL be `vs-adapter/pushdown-col-types-consolidation` and MUST NOT stay `vs-adapter/pushdown-module-structure`, because issue #265 split the builder's contract out into that feature, which is also where issue #270's removal of the builder's `fold_case` parameter is recorded — so a reader following this clause reaches the current owner rather than a superseded one
* *AND* the BEHAVIORAL contract of both relocated functions SHALL remain owned by the features that already specify it, because only the physical location moves — this feature claims where the code lives, never what it returns. For `exasol_type_from_json` that owner is `vs-adapter/pushdown-planning`, which names the function directly in three recorded clauses; those `vs-adapter/pushdown-planning` parentheticals stay correct and MUST NOT be retargeted at this feature. `exasol_type_to_json` is named by no recorded scenario at all — its output is specified behaviorally as the `createVirtualSchema` column `dataType` JSON by `vs-adapter/create-virtual-schema`, and that indirect ownership is likewise unchanged by the move
