### crates/lakehouse-engine/src/adapter/pushdown/support.rs

#### [OUTDATED_COMMENT] `column_exa_type` doc says "the two lookups" where there is exactly one
- Location: line 664 (paragraph spans 659-666)
- Issue: the reworded agreement paragraph reads `…so no declarable name can differ between the two lookups`. This is the pre-refactor phrase "between the two folds" with the noun swapped, and it now contradicts the same doc comment two sentences earlier, which declares this function `The ONE col_types lookup for the type-rewrite guards`. There is one lookup (`column_exa_type`) and one fold; the two things that could once differ were the two *builders*. Separately, the retained `resolve_table_schema` clause is now presented as the reason the two builders agree (`…lists agree for every column name the adapter can declare — resolve_table_schema Unicode-uppercases names before declaring them, so…`), which is a non-sequitur: once both builders share one fold their key sets agree for **every** input name, not merely every declarable one. The premise is still worth stating — it is why the Unicode-vs-ASCII question is moot at this lookup at all, and it is what `non_ascii_table_and_column_stay_queryable` guards — but it no longer supports the agreement claim it is attached to.
- Fix: In crates/lakehouse-engine/src/adapter/pushdown/support.rs, rewrite the second paragraph of `column_exa_type`'s doc comment so that (a) the agreement between `extract_all_column_types` and `involved_table_columns` is attributed to their now-shared single fold and stated as holding for every name, not only declarable ones, and (b) the `resolve_table_schema` premise is stated as its own separate fact — that no lowercase non-ASCII name can reach this lookup, guarded by `non_ascii_table_and_column_stay_queryable` — rather than as the reason the two builders agree. Delete the phrase "between the two lookups" entirely; there is one lookup. Keep the `None`-means-unresolvable sentence and the `type`-tag paragraph unchanged.

## Expert fixes

### crates/lakehouse-engine/src/adapter/pushdown/joins/planning.rs

#### [INFORMATION_LEAKAGE] Fold change makes the fan-out narrowing an unenforced cross-fold string match
- Location: line 361 (`involved_table_columns`); the affected comparison is crates/lakehouse-engine/src/adapter/pushdown/joins/rendering.rs:316-319
- Issue: switching `involved_table_columns` from `to_ascii_uppercase` to `to_uppercase` changes one side of a string-equality comparison whose other side stays ASCII-folded, and the plan names no site where the two meet. The chain is live: `build_n_scan_sql` builds `cols_per_side` from `involved_table_columns` (sql_builders.rs:364) and passes it as `full_cols` into `referenced_side_columns` (sql_builders.rs:413), which narrows with `full_cols.iter().filter(|(name, _)| names.contains(name))` (rendering.rs:318) where `names` comes from `collect_side_column_names` — still `to_ascii_uppercase`, deliberately so, and forbidden from unification by `vs-adapter/pushdown-module-structure`'s blind-traversal scenario and by this plan's own non-goals. Before this change both sides of that `contains` were ASCII-folded and agreed **by construction** on any input, non-ASCII included; after it they agree only **by premise** — that `resolve_table_schema` Unicode-uppercases every declared name, so nothing lowercase or non-ASCII ever arrives. No behavior changes today (703 lib tests green, premise E2E-guarded), so the refactor is behavior-preserving as claimed; the defect is that a by-construction invariant silently became a premise-dependent one at an undocumented site. The failure mode if the premise ever weakens is a passing test over wrong SQL, not an error: `full_cols` would hold `STRASSE` while `names` holds `STRAßE`, the filter would drop a column the outer wrapper still references, and the end-of-function fallback rescues only a *fully* empty narrowing — a partial mismatch narrows a referenced column away silently. The two doc comments that inventory this codebase's fold landscape (`walk_column_nodes`, support.rs:1305-1312, and `referenced_clause_values`, rendering.rs:253-259) both describe the collect walks' divergence and neither mentions that a `column_types`-built list is now compared against an ASCII-folded set.
- Fix: In crates/lakehouse-engine/src/adapter/pushdown/joins/planning.rs, add a paragraph to `involved_table_columns`' doc comment recording that its output is compared as `full_cols` against `collect_side_column_names`' ASCII-folded name set in `referenced_side_columns`, that the two folds are now different by design and MUST NOT be reconciled by changing either one, and that their agreement rests on `resolve_table_schema` Unicode-uppercasing every declared name (guarded by `non_ascii_table_and_column_stay_queryable`). Then add a matching paragraph to `referenced_side_columns`' doc comment in crates/lakehouse-engine/src/adapter/pushdown/joins/rendering.rs naming the cross-fold comparison at the `names.contains(name)` filter, the premise it depends on, and the silent-narrowing consequence if that premise breaks. Change no fold, no signature, and no assertion; this is documentation of a seam the refactor introduced, and unifying the folds is spec-forbidden.
