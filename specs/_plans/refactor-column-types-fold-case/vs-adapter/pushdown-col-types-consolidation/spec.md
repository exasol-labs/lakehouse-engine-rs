# Feature: Pushdown Col Types Consolidation

Gives the pushdown type-rewrite guards' `col_types` handling one owner per decision — one lookup helper, one builder, one Exasol-type-family classifier substitution — split out of `vs-adapter/pushdown-module-structure` as issue #265's own cohesive scope.

## Background

<!-- DELTA:CHANGED -->
* This bullet SUPERSEDES the preceding Background bullet "The `col_types` list is consumed with the Unicode `to_uppercase` by all three guards but PRODUCED with two different folds …". The `col_types` list is both CONSUMED and PRODUCED with a single fold, the Unicode `to_uppercase`: the shared `column_exa_type` lookup applies it for all three type-rewrite guards, and the shared `column_types` builder applies it for both wrappers. Issue #265 shipped the builder with a `fold_case` parameter so `involved_table_columns` could keep the ASCII-only `to_ascii_uppercase` it had always applied; issue #270 removes that parameter as dead flexibility, because the two folds cannot produce different output on any name the adapter can receive. Removing it is a SIMPLIFICATION, not a correctness fix. There is consequently no asymmetry left to preserve byte-for-byte and no separate reconciling change to defer.
* This bullet SUPERSEDES the preceding Background bullet "Both folds consequently AGREE on every name that can reach either builder. A name already produced by `to_uppercase` is a fixed point of both …". The agreement argument STANDS unchanged and is what makes #270 byte-identical rather than merely equivalent: a name already produced by `to_uppercase` is a fixed point of both folds — `to_ascii_uppercase` changes only ASCII `a-z`, of which `to_uppercase` output contains none, while `to_uppercase` is itself idempotent, swept exhaustively over all 1,112,064 Unicode scalar values with zero exceptions. What ceases to be true is that bullet's CLOSING clause, "the guards' Unicode-folding lookup can never miss a name the ASCII-folding join-side builder produced": after #270 there is no ASCII-folding join-side builder. The lookup and BOTH wrappers now fold identically by construction, so the guards' lookup cannot miss a name either wrapper produced for a structural reason rather than an input-domain one.
* This bullet SUPERSEDES the preceding Background bullet "What survives is a divergence over an UNREACHABLE input domain, named rather than left silent …". Nothing survives: #270 removes the divergence rather than naming it, and the follow-up issue that bullet cited is CLOSED by this change. That bullet also carried a DESIGN REFUSAL that #270 reverses, and the reversal is recorded here rather than left implicit. The refusal was that "making either builder's fold depend on `resolve_table_schema`'s uppercasing would put one module's decision inside another module's body, which is the information leakage this plan exists to remove" (`specs/_decision/042-refactor-col-types-guard-dedup.md:158` records the same rejection in its options table). That objection no longer decides, for two reasons. FIRST, the surviving fold is selected to match the list's CONSUMER, `support::column_exa_type`, which lives in the same module as the builder — so the builder encodes its OWN module's decision, not a foreign module's, and the alternative (ASCII) is what would leave the in-module consumer's fold unpaired. SECOND, `resolve_table_schema`'s uppercasing is a BEHAVIOR-PRESERVATION premise guarded by a live test, not a fold-selection rule: the fold would still be `to_uppercase` if that premise were dropped, and only the byte-identity claim would weaken. The unreachable-input-domain STANDARD that bullet invoked — an unnamed divergence is indistinguishable from a regression — is unchanged and is applied below to the one new cross-fold pairing #270 creates.
* This bullet SUPERSEDES the preceding Background bullet "Neither of this delta's two `col_types` fold tests characterizes a DELIVERED column name …". ONE `col_types` fold test remains, `support.rs`'s `column_exa_type_resolves_unicode_folded_list_and_misses_ascii_folded_list`, and it characterizes no DELIVERED column name. Its two `col_types` slices are CONSTRUCTED literals, `STRASSE` and `STRAßE`, chosen because Rust's two folds disagree on `STRAßE` — which is what makes the miss assertion falsifiable. Neither literal is a list any builder produces: since #270 both builders emit Unicode-folded names only. The builder-side companion test that pinned the two wrappers' divergent folds is deleted with the parameter, because it asserted a disagreement that no longer exists.
* This bullet SUPERSEDES the preceding Background bullet "Neither builder wrapper becomes a pass-through of the kind the sibling `datafusion-scan/type-mapping-module-structure` feature rejects …". The pass-through RULE is unchanged: a pass-through calls another function with the SAME arguments, and a wrapper supplying an argument the shared builder does not choose is a partial application naming a decision. Only the EXAMPLE narrows. After #270 each wrapper here supplies a different table selection and NOTHING else — `tables.first()` versus the find-by-name closure — so that selection ALONE is what keeps each wrapper a partial application rather than a pass-through, and both wrappers survive under the same exception.

<!-- DELTA:NEW -->
* Removing `fold_case` creates exactly ONE new cross-fold pairing, and it is named here rather than left silent. `joins/rendering.rs::referenced_side_columns` narrows `involved_table_columns`' column list by membership in the set `collect_side_column_names` builds with `to_ascii_uppercase`; both sides folded ASCII before #270 and fold differently after it. They agree for exactly ONE reason, this feature's standing one: both read only names Exasol declared, `resolve_table_schema` already Unicode-uppercased every one of them, and such a name is a fixed point of both folds. There is NO second safety net, and the failure mode if that premise ever broke is a DROPPED column rather than a wider projection. `referenced_side_columns` (`joins/rendering.rs:316-325`) falls back to `full_cols` only when narrowing yields NOTHING: a side whose `full_cols` is `[STRASSE, ID]` measured against an ASCII-folded reference set `{STRAßE, ID}` narrows to `[ID]`, which is non-empty, so the fallback does NOT fire and the fan-out leg loses `STRASSE` while the outer wrapper still renders a reference to it. Only the ALL-MISS case widens a projection; the MIXED case drops a column and yields an erroring or wrong-result wrapper.
* The collect walks' fold divergence is NOT touched by #270 and is a different divergence: `column_tables` and `collect_side_column_names` keep `to_ascii_uppercase` while `collect_all_column_names` keeps `to_uppercase`, which `vs-adapter/pushdown-module-structure`'s "One blind traversal primitive backs every column-collecting walk" scenario forbids unifying. #270 removes a builder parameter, not that.
* `tests/e2e_non_ascii_identifier_test.rs::non_ascii_table_and_column_stay_queryable` is the standing live guard on that premise, not merely a past capture: it seeds an Iceberg `straße` column against a Docker Exasol container and asserts `SYS.EXA_ALL_COLUMNS` serves `STRASSE`. If `resolve_table_schema` ever stopped Unicode-uppercasing declared names, that test fails before any fold could matter.

## Scenarios

<!-- DELTA:CHANGED -->
### Scenario: One builder produces the column-type list for both the first-table and the named-table selection

* *GIVEN* `column_types` (`pushdown/support.rs`), the ONE `col_types` builder, which takes `fold_case: impl Fn(&str) -> String` alongside its table selection so that `extract_all_column_types` can pass `str::to_uppercase` and `involved_table_columns` (`pushdown/joins/planning.rs`) can pass `str::to_ascii_uppercase`, preserving a fold divergence this feature's Background records as UNREACHABLE — `resolve_table_schema` (`adapter/pushdown/file_resolution.rs:640`) maps every Iceberg field through `f.name.to_uppercase()` before `build_virtual_tables` declares it, so no name carrying a lowercase non-ASCII letter reaches either wrapper, and `tests/e2e_non_ascii_identifier_test.rs::non_ascii_table_and_column_stay_queryable` pins that live against a Docker Exasol container by serving an Iceberg `straße` column as `STRASSE`
* *WHEN* the adapter builds the `(UPPERCASE name, Exasol type)` list for a single-table request, or for one named table of a join
* *THEN* `column_types` SHALL take exactly ONE parameter besides `request` — the table selection — and the `fold_case` parameter SHALL be REMOVED, because a parameter whose two arguments cannot produce different output is a decision the builder declined to make with nothing to decide
* *AND* `column_types` SHALL apply the Unicode `str::to_uppercase` in its OWN body, and MUST NOT apply `str::to_ascii_uppercase`, because `to_uppercase` is the fold every reachable name already carries — it is `resolve_table_schema`'s own fold, and the fold the shared `column_exa_type` lookup applies on the consuming side, inside the SAME module as the builder — so the builder converges on its own module's consumer rather than leaving that consumer's fold unpaired
* *AND* both wrappers SHALL survive with UNCHANGED signatures and declaration sites — `extract_all_column_types` as `pub(super) fn(&Json) -> Vec<(String, String)>` in `support.rs`, `involved_table_columns` as `pub(super) fn(&Json, &str) -> Vec<(String, String)>` in `joins/planning.rs` — so NO call site of either changes: for the former the production sites `support::extract_projection` and `pushdown::handle_pushdown` plus the test sites in `grouped_agg.rs` and `topn.rs`; for the latter the production sites `joins/mod.rs::plan_join`, `joins/sql_builders.rs::render_broadcast_join` (twice), `joins/sql_builders.rs::build_n_scan_join_sql`, and `joins/rendering.rs::extract_join_projection` (twice), plus the test sites in `sql_builders.rs` and `rendering.rs`
* *AND* neither wrapper SHALL be deleted as a shallow pass-through, because each still supplies a table selection the shared builder does not choose — `tables.first()` versus the find-by-name closure — so each remains a partial application that names a decision rather than a body forwarding the same arguments
* *AND* `column_types`' selection parameter SHALL stay a selection CLOSURE and MUST NOT be reshaped into an `Option<&str>` table name or any other data-shaped mode argument, because reshaping it edits a parameter this scenario is not removing and would change both call sites for no observable gain
* *AND* the unit test `each_builder_keeps_its_own_case_fold_on_a_constructed_non_ascii_literal` (`joins/planning.rs`) SHALL be DELETED together with the `// Case-fold characterization` section banner above it and the `#[cfg(test)]`-scoped `use crate::adapter::pushdown::support::extract_all_column_types` inside its body, of which it is the sole consumer, because with one fold the test has nothing left to distinguish: it asserts that two wrappers of one builder disagree, which after this change is a false statement rather than a weakened one
* *AND* NO replacement unified-fold test SHALL be added, because an agreement assertion over two wrappers that now share one fold restates `str::to_uppercase`'s stdlib behavior and guards nothing — the same reasoning by which the superseded scenario rejected an agreement test over already-uppercased names. Coverage of the surviving fold stays where it already is: `support.rs`'s `column_exa_type_resolves_unicode_folded_list_and_misses_ascii_folded_list` pins the consuming lookup's Unicode fold, and the pushdown, joins, top-N, and `dispatch_golden` suites exercise both wrappers end to end over real already-uppercased names
* *AND* every comment asserting the removed divergence SHALL be reworded or deleted rather than left standing, because a preserved sentence naming a fold that no longer exists is a fresh instance of the stale-citation defect this feature deletes. FIVE carriers exist and all five are in scope: (1) `column_types`' doc comment paragraph justifying selection and fold as two parameters plus its `(#270)` tracking note SHALL be deleted; (2) `involved_table_columns`' doc-comment claim that it "maps its columns with the ASCII-only `to_ascii_uppercase` fold" SHALL be reworded to name the shared Unicode fold; (3) `involved_table_columns`' CLOSING partial-application paragraph, "A partial application of `support::column_types`, supplying the find-by-name selection and the ASCII-only fold this side has always applied", SHALL DROP "and the ASCII-only fold this side has always applied" while KEEPING its find-by-name selection clause, because after the change this side supplies no fold at all; (4) `column_exa_type`'s doc sentence "`involved_table_columns`' ASCII-folded keys agree for every column name the adapter can declare — `resolve_table_schema` Unicode-uppercases names before declaring them, so no declarable name can differ between the two folds" SHALL be reworded so the agreement claim names the SINGLE fold both builders now apply instead of an ASCII-folded key set no builder produces, KEEPING the `resolve_table_schema` premise and leaving the `type`-tag paragraph intact; and (5) the sentence in `column_exa_type_resolves_unicode_folded_list_and_misses_ascii_folded_list`'s doc comment naming `involved_table_columns` as the producer of the ASCII-folded list SHALL be reworded to describe its `col_types` literal as a CONSTRUCTED ASCII-folded list that no builder produces, keeping the test's own falsifiability rationale intact
* *AND* the fold PAIRING this change alters SHALL be named rather than left silent: `joins/rendering.rs::referenced_side_columns` narrows `involved_table_columns`' names by membership in the set `collect_side_column_names` builds with `to_ascii_uppercase`, so a pair that folded identically before now folds differently, and its agreement rests SOLELY on the same upstream normalization as the rest of this scenario — both sides read only names Exasol declared, which `resolve_table_schema` already Unicode-uppercased, and every such name is a fixed point of both folds. The bound if that premise ever broke SHALL be recorded accurately and MUST NOT be recorded as "a wider projection, never a dropped column": `referenced_side_columns` falls back to `full_cols` only when narrowing yields NOTHING, so a MIXED side — one column's folds disagreeing while another's agree — narrows to a non-empty subset, the fallback does not fire, and the diverging column is DROPPED from the fan-out leg while the outer wrapper still references it. A wider projection is the ALL-MISS case only
* *AND* the ASCII folds of `column_tables` and `collect_side_column_names` SHALL be left UNCHANGED, because `vs-adapter/pushdown-module-structure`'s "One blind traversal primitive backs every column-collecting walk" scenario forbids unifying the collect walks' folds and this scenario removes a builder parameter, not that separate divergence
* *AND* the scan-driving SQL for every single-table pushdown request and the join SQL for every join shape MUST each be byte-identical to their pre-removal output, and every existing pushdown, joins, top-N, and `dispatch_golden` test MUST pass with NO change to any test assertion and NO change to any expected value — the only permitted test-file edits being the deletion named above and the comment rewords named above
