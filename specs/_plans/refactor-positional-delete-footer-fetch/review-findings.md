### crates/lakehouse-engine/src/scan/mod.rs

#### [PERFORMANCE_ISSUE] The re-fetch observable is not level-gated, so it snapshots the whole metadata cache on every scan at the production default level
- Location: line 312
- Issue: `emit_footer_refetch_diagnostic` calls `list_entries()` unconditionally on every successful scan invocation before it knows whether anything was recorded, and with no `debug_level()` check — unlike its sibling `emit_phase_telemetry` (line 288), which returns early on `diagnostics::telemetry_enabled(ctx.debug_level())` before doing any work. `DefaultFilesMetadataCache::list_entries` (`datafusion-execution-54.1.0/src/cache/file_metadata_cache.rs:219-236`) walks EVERY cached entry — not only the delete-carrying ones — cloning each `ObjectMeta`, allocating a `HashMap<String,String>` per entry via `extra_info()`, and calling `ParquetMetaData::memory_size()` (`parquet-58.3.0/src/file/metadata/mod.rs:290-302`), which is a full `heap_size()` traversal of every `RowGroupMetaData` and every `ColumnChunkMetaData`, i.e. O(columns × row_groups) per entry. A delete-free scan records nothing and can therefore never report anything, yet still pays that traversal over every footer the opener cached; on this plan's own calibrated fixture that is 22 × 4,096 column chunks per invocation. The `scan-execution-memory-and-credentials` DELTA:NEW scenario requires the observable to "stay inert otherwise: at the production default debug level it MUST NOT emit output" — it emits nothing, but it is not inert. No wall-clock measurement was taken; the cost above is read off the vendored source.
- Fix: In crates/lakehouse-engine/src/scan/mod.rs, add a guard clause at the top of `emit_footer_refetch_diagnostic` that returns immediately unless `diagnostics::telemetry_enabled(ctx.debug_level())` is true, so the `list_entries()` snapshot never runs at the production default `info` level. Place it before the `session_ctx.runtime_env()` chain. Update the function's doc comment to state that the level gate — not only the non-zero-count check — is what makes it inert at `info`, and to name `telemetry_enabled` as the shared gate it reuses from `emit_phase_telemetry`. Do not change `record_access_plan_cached_footer`'s call site in `positional_deletes.rs`: that site holds no `UdfContext` and its cost is bounded at one mutex lock plus one `Path` clone per delete-carrying file.

### crates/lakehouse-engine/src/scan/diagnostics.rs

#### [SENTINEL_ERROR_VALUE] `hits == 0` is overloaded: a footer the opener never opened is counted as a re-fetch
- Location: line 158
- Issue: `footer_refetch_count` counts a recorded path present in the entry map with `hits == 0` as a re-fetch, on the stated reasoning that "the opener's lookup missed and re-`put` the entry, which resets `hits` to zero". `put` does zero `cache_hits` (`datafusion-execution-54.1.0/src/cache/file_metadata_cache.rs:75`), so that reading is correct — but `hits == 0` is equally the state of an entry Phase B `put` and the opener NEVER LOOKED UP, and the opener does not open every assigned file. `PositionalDeleteScanTable::scan` pushes the LIMIT into the scan (`positional_deletes.rs:773`, `.with_limit(limit)`), which `raw_scan.rs:410-411` populates from `spec.common.limit`. DataFusion's `FileStream` then stops before opening later files: `scan_state.rs:166-186` returns `ScanAndReturn::Done` as soon as `remain` hits 0, and the upstream regression test is named `morsel_limit_prevents_second_file` — "Verifies that a global limit can stop the stream before a second file is opened", with the snapshot comment "the snapshot should not ever see planner id2" (`datafusion-datasource-54.1.0/src/file_stream/mod.rs:978-1009`). Failure scenario: `SELECT * FROM <vs>.<delete-carrying table> LIMIT 10` over a shard of 8 delete-carrying data files whose first file satisfies the limit — Phase B fetches, caches and records all 8 footers, the opener reads back only the first, the other 7 sit in the cache with `hits == 0`, and the observable reports 7 re-fetches although nothing was evicted and no footer was fetched twice. That directly violates the `scan-execution-memory-and-credentials` DELTA:NEW clause "a scan whose footers all stay cached SHALL report a re-fetch count of ZERO, so the signal distinguishes eviction from normal operation rather than firing on every delete-carrying scan". The same false positive is reachable through the join path when an inner `HashJoinExec` finds an empty build side and never polls the probe side, leaving every fact-side recorded footer at `hits == 0`. No shipped test catches this: `scan_footer_refetch_observable.rs` builds its spec with `limit: None` and a single data file, so the unopened-file case is never exercised.
- Fix: In crates/lakehouse-engine/src/scan/diagnostics.rs, split the two causes `footer_refetch_count` currently conflates. Keep counting a recorded path ABSENT from the entry map as an unconditional re-fetch (evicted, or never admitted — the case the shipped test covers). Make the `hits == 0` clause conditional on the scan shape being one where the opener is guaranteed to open every assigned file: add a parameter carrying that condition and count `hits == 0` only when it holds. In crates/lakehouse-engine/src/scan/mod.rs, compute that condition at the `emit_footer_refetch_diagnostic` call site from the `spec` `run_scan_dispatch` already holds — `spec.common.limit.is_none() && spec.common.join.is_none()` — and pass it through; keep the function at three parameters or fewer. Document on `footer_refetch_count` why a pushed LIMIT or a join makes `hits == 0` ambiguous, citing `datafusion-datasource-54.1.0/src/file_stream/scan_state.rs:166-186`. Then add a regression test to crates/lakehouse-engine/tests/scan_footer_refetch_observable.rs — inside the existing single test function, so the process-global record cannot be raced by a sibling test — that runs a delete-carrying scan over at least three data files with `spec.common.limit = Some(1)` on a DEFAULT-cache-limit session and asserts `footer_refetch_count` is 0 for it. Update that file's module-level doc comment to record that the file now holds one test covering both the eviction signal and the limit-pushdown false positive.
