#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Implementation Tasks task 1.7, the sentence "Assert the total count of non-HEAD `get_opts` against the K DATA-file locations is EQUAL between the two runs"
- Issue: the oracle counts every non-HEAD `get_opts` against a data file, not only footer reads — so it also counts the opener's execute-time column-chunk reads. The two runs differ in exactly one respect that can change those reads: the delete-carrying run attaches a `ParquetAccessPlan` with a `RowSelection`, which changes what the Parquet reader requests and how it coalesces ranges. If that shifts the column-read count by even one, the test fails for a reason unrelated to footer reuse, and the natural repair is to relax the assertion — re-vacuating the guard the round-1 fix was written to restore. The existing `scan_reads_footer_via_range_get_once` avoids this by comparing RANGES, not raw counts.
- Fix: In plan.md task 1.7, replace the equality oracle with a footer-scoped one: count only non-HEAD `get_opts` whose requested range ends at the file's known size (the footer-shaped read), and assert that count is EQUAL between the delete-free and delete-carrying runs and equals K. State that column-chunk reads are excluded on purpose, because the access plan legitimately changes them and only the footer count is the reuse property.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: plan.md § Implementation Tasks task 1.7b part (b); `datafusion-scan/scan-execution-memory-and-credentials/spec.md` § Scenarios, DELTA:NEW "A metadata-cache eviction that re-fetches a footer is observable", clauses 3 and 4
- Issue: the design contradicts two normative clauses of the scenario it is written to satisfy. (1) Task 1.7b says "Each detected re-fetch increments it and writes one `debug_checkpoint` line." `debug_checkpoint` (`crates/lakehouse-engine/src/scan/diagnostics.rs:128-160`) takes no level, checks no level, writes to stderr, and appends to `/tmp/lakehouse_udf_debug.<pid>.log` with `flush()` + `sync_all()` per line. It has no production caller today — its own module header marks the whole block "DIAGNOSTIC (temporary)". Wiring it into `SpecSizedObjectStore::get_opts` therefore emits output at the production default `info` level, violating "at the production default debug level it MUST NOT emit output", and adds one fsync per re-fetched footer inside the read path of a performance refactor. The report half is safe by contrast: `udf_log!` self-gates on `ctx.debug_level()` (`exasol-udf-sdk-0.20.3/src/lib.rs:39-45`). (2) The counter is "a process-global `AtomicU64`" whose `reset_footer_refetch_count()` the task scopes to "test isolation". Per CLAUDE.md § UDF parallelization, groups are multiplexed onto a fixed per-node VM pool, so one process serves many scan invocations in sequence; an unreset global makes invocation 2 report invocation 1's count and violates "a scan whose footers all stay cached SHALL report a re-fetch count of ZERO", which the scenario requires precisely so the signal distinguishes eviction from normal operation.
- Fix: In plan.md task 1.7b part (b), delete the `debug_checkpoint` call entirely — state that per-re-fetch logging is prohibited by the scenario's inertness clause and that the ONE level-gated `udf_log!` at the report site is the whole output surface. In the same part, require the counter to be reset at the START of every scan invocation (name the reset call site: `crates/lakehouse-engine/src/scan/mod.rs`, alongside `PhaseTimers::start()` at line ~27), and delete the words "the reset exists for test isolation". Update plan.md § Impact's third observable consequence to match.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: plan.md § Design § Patterns, row "Detect the failure at the store, report it at the entry point"; plan.md § Implementation Tasks task 1.7b part (a)
- Issue: the design puts a Parquet-layout decision inside an object-store decorator. `SpecSizedObjectStore`'s documented responsibility is one sentence — answer per-file metadata from a spec-supplied size index (`crates/lakehouse-engine/src/scan/object_store.rs:297-307`). Task 1.7b gives it a second, unrelated one: knowing that "a non-HEAD `get_opts` whose requested range ENDS at that location's spec size is a footer read; a column-chunk read never ends at EOF because the footer follows it". That fact is owned by `positional_deletes.rs`, which is what issues the fetch and what chooses the size hint and page-index policy that determine the range shape. Two modules must now agree on an unenforced convention, and nothing links them: change the hint to a suffix-form `GetRange::Suffix` request, or add any other EOF-anchored read, and the counter silently mis-reports with no compile error and no failing test. This is the same recurrence-of-one-decision defect the round-1 review already flagged for `PageIndexPolicy::Skip`, now added a second time.
- Fix: In plan.md § Design § Patterns, replace the "Detect the failure at the store" row with one that keeps the decision in a single owner: `partitioned_files` records the set of paths it cached, and the report site reads `FileMetadataCache::list_entries()` to find which of those the opener did not reuse. State in the Why column that this removes both the object-store hook and the EOF-range heuristic, so no module outside `positional_deletes.rs` needs to know what a footer read looks like. Add a matching row to § Consequences naming the rejected alternative (store-level range detection) and why.
