# Decision Log: refactor-pushdown-agg-dedup

## Interview

No live interview was run. This plan was authored headless via `/speq:plan-pr`, so the body of GitHub issue [#179](https://github.com/exasol-labs/lakehouse-engine-rs/issues/179) stands in for the interview. The issue supplied the intent, four named duplications with line references, a suggested approach for each, the no-behavior-change constraint, the verification instruments, and one item explicitly marked "fold in if cheap".

**Q (from the issue, § Suggested approach):** Should `AggKind` (or `AggregatePlan`) get a `partial_column_count()` or a column-kind descriptor?
**A (resolved during planning):** A column-kind descriptor, on `AggKind`, and NOT a bare count. See decisions [1] and [2].

**Q (from the issue, § Duplicated / drift-prone code, item 4):** The column-count contract is "independently encoded in three scan-side functions". Is three the real number?
**A (corrected during planning):** No, it is five, spanning two modules. See decision [3].

**Q (from the issue, closing note):** The stat branch of `partial_agg.rs` bypasses `agg_arg_sql` and falls back to an empty-string identifier — "route it through `agg_arg_sql` or make the 'expression-arg stats unsupported' limit explicit". Which?
**A (resolved during planning, not escalated):** Both, for different reasons, and the decline is the substantive fix. See decision [7].

**Q (from the issue, § Constraints):** "the generated aggregate SQL and the partial-row column layout must be identical before/after" — do the existing tests prove that?
**A (measured during planning):** No. The instrument exists but is not aimed at the arities at risk. See decision [4].

## Design Decisions

### [1] The single source of truth is a per-column descriptor, not a column count

- **Decision:** Add `AggKind::partial_columns(&self) -> &'static [PartialAggColumn]` in `crates/lakehouse-engine/src/scan/spec.rs`, with `PartialAggColumn` enumerating the ten distinct partial columns the contract admits, and drive all five contract sites from it.
- **Alternatives:** (a) The issue's literal suggestion, `partial_column_count() -> usize`. (b) A `&'static [(&'static str, bool)]` of (name suffix, is-counter) pairs rather than an enum.
- **Rationale:** A count alone drives exactly one of the five sites. `partial_row_from_batch` needs only the arity, but `emit_null_partial_row` needs the 0-versus-NULL identity of each column, `partial_select_items` needs each column's DataFusion aggregate expression, `partial_emits_items` needs each column's Exasol `EMITS` type, and `merge_select_items` needs each column's name. A count leaves four sites still matching on `AggKind`, which is four places the arity can drift back apart. Option (b) was rejected because a tuple of primitives cannot be matched exhaustively: the renderers would fall back to string comparison on the suffix, and a new column would be a silent default instead of a compile error. The enum makes "extend by adding a case" mechanical.
- **Promotes to ADR:** yes

### [2] No `partial_column_count()` wrapper, per the recorded pass-through rule

- **Decision:** Do not add `partial_column_count()`. `partial_row_from_batch` reads `partial_columns().len()` directly.
- **Alternatives:** Add it anyway for call-site readability, as the issue suggests.
- **Rationale:** `datafusion-scan/type-mapping-module-structure` and `vs-adapter/pushdown-col-types-consolidation` both record the rule this repository already applies: a function whose entire body forwards to another with the same arguments is a shallow pass-through and does not earn its place. `partial_columns().len()` is not less readable than `partial_column_count()`, and the wrapper would give the arity a second name that a future edit could desynchronize from the descriptor. This deliberately declines part of the issue's suggested approach.
- **Promotes to ADR:** no

### [3] The contract is quintuplicated, not triplicated, and the fifth site is in the other module

- **Decision:** Treat `partial_emits_items` and `merge_select_items` in `adapter/pushdown/grouped_agg.rs` as in-scope contract sites alongside the three the issue names in `scan/partial_agg.rs`.
- **Alternatives:** Scope the change to the three scan-side functions the issue lists, leaving the adapter's `EMITS` builder to keep its own per-`AggKind` arity match.
- **Rationale:** The issue's own failure statement is "partial rows misalign with the UDF `EMITS` contract" — and `partial_emits_items` IS the `EMITS` contract. Giving the scan side one owner while the adapter keeps a hand-written arity match leaves the exact cross-module disagreement the plan exists to remove, now split across a module boundary where no compiler and no unit test spans it. `merge_select_items` joins for the narrower reason that it hand-formats the same `PARTIAL_*` names the other four produce; the name is a third decision that also had no owner. The dependency direction permits this: both modules already import `scan::spec`, so no edge is added.
- **Promotes to ADR:** yes

### [4] Capture the missing golden baselines before touching production code

- **Decision:** Task 1.1 adds two pre-refactor `dispatch_golden` fixtures — one single-group, one grouped — each rendered from a select list covering every `AggKind` and therefore every arity, and no production edit lands before they are committed.
- **Alternatives:** (a) Rely on the ten existing fixtures and the six statistical merge tests. (b) Add the fixtures afterwards, as regression cover for future changes.
- **Rationale:** Measured, not assumed: `grep PARTIAL_avg` and `grep PARTIAL_stat` over `testdata/dispatch_golden/` both return nothing, so the existing gate watches only the single-column arities. The two multi-column arities are precisely the ones a contract refactor can break. The six statistical merge tests are all `.contains(...)` probes — `NULLIF`, `<= 1`, `CASE`, `SQRT(`, `IS NULL`, `GREATEST`, and one negative `!contains("- 1")` — so a fragment extraction that dropped a parenthesis, reordered the numerator, or swapped a denominator would leave every one of them green. Option (b) is strictly worse than useless here: a fixture captured after the refactor pins whatever the refactor produced, which is the claim under test.
- **Promotes to ADR:** yes

### [5] Home the descriptor in `scan/spec.rs`, and keep that module serde-only

- **Decision:** Declare `PartialAggColumn`, `AggKind::partial_columns`, `is_counter`, and the shared `partial_column_name` in `crates/lakehouse-engine/src/scan/spec.rs`. Express the empty-shard identity as a boolean rather than an SDK `Value`.
- **Alternatives:** (a) A new module owning the contract. (b) `adapter/pushdown/support.rs`, where the pushdown tree's shared primitives already live. (c) Return `Value::Int64(0)` / `Value::Null` from the descriptor directly.
- **Rationale:** `scan::spec` is the scan-spec wire-format module both consumers already import, so the descriptor adds no dependency edge and no cycle, and it sits beside the `AggKind` whose contract it states. Option (a) adds a module for one enum and two methods. Option (b) is unreachable from the scan and would invert the dependency, making the wire format depend on the adapter. Option (c) would drag `exasol_udf_sdk` into a module whose only current import is `serde`, coupling the wire format to the UDF runtime for a two-value mapping the emit site can do itself.
- **Promotes to ADR:** yes

### [6] The shared CAST helper takes `Option<&str>`, lives in `support`, and excludes two arms on purpose

- **Decision:** Move the canonical declared-type cast to `adapter/pushdown/support.rs` as `pub(super) fn cast_to_declared_type(expr: &str, declared: Option<&str>) -> String`, delegate six sites to it, and leave the `GroupKey` and `Aggregate` arms of `empty_grouped_sql` untouched.
- **Alternatives:** (a) Keep the existing `&str` signature and add a separate `Option`-taking wrapper. (b) Keep the helper private in `grouped_agg.rs` and duplicate it for `file_resolution.rs`. (c) Fold all eight cast sites in, including the two unconditional `CAST(NULL AS <ty>)` arms.
- **Rationale:** Five of the six sites read their declared type from a `.get(i)` on a possibly-shorter list and already treat absence as no-cast, so `Option<&str>` is the general case and the current `&str` form is the special one; option (a) would leave two names for one rule. Option (b) reintroduces the duplication one module over. Option (c) is a correctness regression, and this is the one place the "same rule" reading is wrong: `empty_grouped_sql`'s group-key and aggregate arms cast even to `VARCHAR(2000000)` because a bare `NULL` in `SELECT … FROM DUAL WHERE 1=0` carries no `VARCHAR` type and would fail the positional `selectListDataTypes` validation the cast exists to satisfy. Naming the exclusion in the spec is what stops a later reader from "finishing" the dedup.
- **Promotes to ADR:** yes

### [7] Make the expression-argument statistical-aggregate limit explicit, accepting one behavior change

- **Decision:** `parse_agg_item` declines a statistical aggregate whose argument is not a bare `column` node, and the scan's statistical branch additionally routes through `agg_arg_sql`. Record the change in `plan.md` § Impact and gate it on a live capture (task 1.2) before the fix (task 1.7).
- **Alternatives:** (a) Route through `agg_arg_sql` only, as the issue's first option — a clearer error message, still an erroring query. (b) Leave both and file a follow-up issue, honoring "pure refactor, no behavior change" literally. (c) Extend the statistical family to accept expression arguments.
- **Rationale:** Measured against the running Docker Exasol container by task 1.2 (captured 2026-07-31), not inferred. The current code emits an `AggregatePlan` with neither `column` nor `arg_expr` for `STDDEV(<expression>)`; `validate_agg_col_types` admits it on the `DOUBLE PRECISION` default, `partial_emits_items` sizes three `EMITS` columns from the same default, and the scan then renders `COUNT("")`, which DataFusion rejects. The capture ran all FOUR reachable paths, and every one is BOTH pushed by Exasol AND broken today. `EXPLAIN VIRTUAL` returned status `ok` and rendered the wrapper SQL for the ungrouped `detect_aggregates` shape (`SELECT STDDEV(score + id)`, `SELECT VARIANCE(score * 2)`), for the grouped `detect_group_by_aggregates` shape (`SELECT MOD(id, 4), STDDEV(score + id) … GROUP BY MOD(id, 4)`), and for the grouped `classify_scalar_over_aggregate` shape (`SELECT MOD(id, 4), SQRT(STDDEV(score + id)) … GROUP BY MOD(id, 4)`); each then failed at execution with `sqlCode 22002` and `Schema error: No field named .`, prefixed `partial aggregate SQL error:` on the two ungrouped paths and `grouped partial aggregate SQL error:` on the two grouped ones. So the whole query fails today, and the shape is reachable rather than theoretical: `capabilities.rs:176-178` advertises the three `FN_AGG_STDDEV*` capabilities with no argument-shape constraint anywhere between the advertisement and the scan, and the capture confirms Exasol exercises that unconstrained advertisement instead of leaving the shape unpushed. The capture also corrected one inspection prediction: DataFusion surfaces the empty identifier as an empty field name, not as `column "" not found`; the rendered `COUNT("")` claim itself stands. Option (a) keeps a failing query. Option (b) leaves a defect standing in the one plan whose whole subject is these functions, and the issue explicitly sanctions making the limit explicit. Option (c) is new behavior with its own correctness story: the sufficient statistics would need `SUM(<expr> * <expr>)` over a doubly-evaluated fragment and partial types derived from the declared result type rather than a source column. The escalation bar was considered and not met: the change is reversible, architecturally uncontroversial, touches no security surface, and moves a failing query to a correct one rather than altering any working result. It is nonetheless a user-observable change, so it is in § Impact and carries its own scenario rather than hiding inside a refactor.
- **Promotes to ADR:** yes

### [8] Reproduce against the container before fixing, and keep the guard either way

- **Decision:** Task 1.2 runs `SELECT STDDEV(score + id)` against the Docker Exasol container and records the verbatim outcome before task 1.7 changes any code. If the query succeeds, the decline ships anyway as a structural guard and the capture goes into the delta's Background. **Outcome (2026-07-31):** the capture ran on all four reachable paths and every query FAILED with `sqlCode 22002`, so the structural-guard fallback was never needed and the decline ships as a bug fix. See § [7] and plan.md task 1.2.
- **Alternatives:** (a) Fix from code inspection, since the failure is derivable by reading `parse_agg_item`, `validate_agg_col_types`, and `partial_select_items` in sequence. (b) Drop the fix if the capture shows Exasol does not push the shape.
- **Rationale:** CLAUDE.md § Verification discipline is unambiguous: a reported bug MUST be reproduced against the container before it is fixed, and a claimed capability limitation MUST be verified against a live system rather than inferred from a capability registry. The inference chain here is three functions long and each link is plausible, which is exactly when it should be measured. Option (b) was rejected on this repository's own standard, recorded in `vs-adapter/pushdown-col-types-consolidation`: an unnamed divergence is indistinguishable from a regression, so an unreachable malformed plan still earns a guard and a named reason.
- **Promotes to ADR:** no

### [9] Two separate name tables in `parse_agg_item`, and `COUNT` stays its own branch

- **Decision:** Resolve `SUM`/`MIN`/`MAX`/`AVG` through one `[(&str, AggKind)]` table and the six statistical names through a second. Keep `COUNT` as a hand-written branch.
- **Alternatives:** One merged table covering all ten names, with a per-kind argument rule looked up separately.
- **Rationale:** Each table's members share an argument-resolution rule the other's do not: the first resolves through `arg_column_or_expr` and admits a bare column or a rendered expression, the second admits a bare column only. Merging them would need a third column in the table encoding which resolver to use, which restates the split as data instead of removing it. `COUNT` is the only name whose `AggKind` depends on its argument rather than its name — no argument yields `Count`, an argument yields `CountCol` — so it is not a name-to-kind mapping at all.
- **Promotes to ADR:** no

### [10] Two new features rather than deltas on the four behavior features

- **Decision:** Record the consolidation as `datafusion-scan/scan-partial-agg-column-contract` and `vs-adapter/pushdown-agg-sql-consolidation`, both NEW, and delta only `vs-adapter/pushdown-planning-aggregate-extensions`.
- **Alternatives:** (a) Add ownership scenarios to the four features that record the behavior — `scan-execution-partial-agg`, `scan-execution-grouped-agg`, `pushdown-planning-single-group-agg`, `pushdown-planning-grouped-agg`. (b) One combined consolidation feature spanning both domains.
- **Rationale:** This repository already has the precedent: `vs-adapter/pushdown-col-types-consolidation` is a dedup refactor with its own feature recording who owns each decision, while the behavior it preserves stays owned by the features that record it. Option (a) would mix "what the aggregate does" with "which function owns the arity" inside four features whose scenarios do not change by a single word, and `scan-execution-partial-agg` and `scan-execution-grouped-agg` already carry 6 and 10 scenarios. Option (b) was rejected because the two halves live in different domains and different crates' module trees, and the column contract's owner is a wire-format type while the SQL-assembly consolidation is adapter-internal. Splitting them keeps each feature's one-sentence responsibility intact. `pushdown-planning-aggregate-extensions` is deltaed because the statistical family's argument boundary is behavior it already owns.
- **Promotes to ADR:** no

### [11] Keep every existing test, including the six `.contains` merge probes

- **Decision:** Delete no test. Keep the six statistical merge probes, keep `stat_aggregate_emits_three_partial_columns`, and keep `parse_agg_item_recognises_stat_functions`' own stat-family table (`single_group_agg.rs:839-846`) with its literal pairs.
- **Alternatives:** (a) Delete the six probes as redundant once the golden fixtures assert full-string equality. (b) Rewrite the test-side table and the arity assertions to read the production descriptor and constant.
- **Rationale:** The probes and the goldens answer different questions. A golden diff reports that some byte moved; each probe names why one guard exists, so a failing probe localizes the defect to the `N <= 1` divisor or the `IS NULL` passthrough. Option (b) is the more serious error: a test that derives its expectation from the code under test asserts the descriptor against itself and would pass any self-consistent renaming or mis-mapping. Keeping the literals is what makes the byte-identity claim falsifiable rather than self-certified, which is the same standard `vs-adapter/pushdown-col-types-consolidation` applies to its own fold-pinning tests.
- **Promotes to ADR:** yes
