## Premortem

Three failure stories, each routed into the taxonomy below.

1. **A query returns silently wrong aggregate values.** Task 1.3 rewrote `partial_select_items` and shipped with the scan's DataFusion SELECT list altered in content or order. Nothing caught it: the two new `dispatch_golden` fixtures contain the `EMITS` clause, the merge SELECT, and the serialized scan spec, but never the scan's rendered DataFusion SQL (verified against `crates/lakehouse-engine/src/adapter/pushdown/testdata/dispatch_golden/grouped_aggregate.sql`); every existing scan-side test is a `.contains(...)` probe; and the `EXPLAIN VIRTUAL` manual diffs show only adapter output. → Task Breakdown, `[TRACEABILITY_GAP]`.
2. **`HAVING STDDEV(a + b) > 1` and `SELECT SQRT(STDDEV(a + b)) … GROUP BY` change behavior unnoticed.** Task 1.7 edits `parse_agg_item`, which has five callers, not the two the plan models. → Feasibility, `[UNSTATED_ASSUMPTION]`.
3. **The recorded spec permanently documents a bug that never existed.** `STDDEV(<expression>)` was never reachable because Exasol never pushed the shape, but the delta Background and § Impact already assert as fact that it "reached the scan and FAILED there". → Feasibility, `[UNSTATED_ASSUMPTION]`.

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: datafusion-scan/scan-partial-agg-column-contract/spec.md § Scenarios, "One in-crate test pins the scan-to-adapter column alignment per aggregate kind"
- Issue: the plan gives the column *count*, *order*, and *name* one owner but leaves the fourth dimension of the same cross-module decision — the partial column's **type** — with none, and its new alignment test cannot see it. Each partial column's meaning is still split three ways: the scan chooses the DataFusion aggregate expression (`SUM(x * x)`), the adapter independently chooses the Exasol `EMITS` type (`DOUBLE PRECISION`, `grouped_agg.rs:774-778`), and nothing enforces that the two agree. The alignment test asserts only "the same number of columns in the same `PARTIAL_*` order". Per CLAUDE.md, Exasol validates `EMITS` types strictly, and the plan's own § Context names an `EMITS`-arity error as a failure mode — so the type half of the contract carries the same back-door-leakage risk the count half did, and the refactor closes one and not the other.
- Fix: In datafusion-scan/scan-partial-agg-column-contract/spec.md § Background, add a bullet naming the `EMITS` type as a fourth dimension of the same per-column contract that this feature deliberately leaves with the adapter's renderer, and state why (the type depends on the plan's source column and declared type, not on the `PartialAggColumn` alone). In plan.md § Consequences, add a row recording that the type dimension was considered for the descriptor and excluded, with the rationale.
