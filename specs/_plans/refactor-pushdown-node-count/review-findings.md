## Standard fixes

### crates/lakehouse-engine/tests/e2e_scan_test.rs

#### [OUTDATED_COMMENT] E2E test doc claims a proof the test cannot deliver on any cluster size
- Location: lines 1254-1265
- Issue: the doc comment on `pushdown_shards_from_handshake_node_count_without_note` says the test proves "the shard count is derived live from `UdfContext::node_count()` ... rather than from any adapterNotes-carried value". It proves nothing of the kind, and not merely because the suite runs single-node. The `events` fixture commits exactly two data files (`crates/lakehouse-engine/tests/common/seed.rs:652` and `:658` each write one), so `shard_count(node_count, parallelism_factor, 2)` = `clamp(node_count * 8, 1, min(2, 300))` = **2 for every `node_count >= 1`** (`support.rs:46-50`). `shard_count(1, 8, 2) == shard_count(4, 8, 2) == 2`, so the `LAKEHOUSE_DISTRIBUTE_FILES` / `AS shards(shard_key, files) GROUP BY shard_key)` markers are insensitive to the node count by construction — the file-count clamp saturates before the node count can matter. The plan's own § Manual Testing states the four-node staging check "is the only check that distinguishes a correctly read four-node count from the `0 => 1` floor", directly contradicting this comment. The comment also hardcodes a cross-reference line number (`e2e_scan_test.rs:1088`) that will rot on the next edit above it; the same file cites tests by bare name elsewhere (`:1160`, `:3647`).
- Fix: In crates/lakehouse-engine/tests/e2e_scan_test.rs, rewrite the doc comment on `pushdown_shards_from_handshake_node_count_without_note` (lines 1254-1265) to state only what the test guards: that dropping the persisted `CLUSTER_NODES` note did not break shard-fan-out emission, i.e. `pushdown` still plans a `LAKEHOUSE_DISTRIBUTE_FILES` fan-out with no adapterNotes node count available. Add an explicit sentence stating the test CANNOT distinguish the handshake node-count source from the pre-refactor absent-note default, because the two-file `events` fixture clamps `shard_count` to 2 for every node count >= 1, and name the plan's four-node staging gate (§ Manual Testing, `parallelism/work-unit-sharding (GATE: four-node staging)`) as the only check that does. Delete the claim that the test proves live derivation. Replace the `(`e2e_scan_test.rs:1088`)` citation with a bare reference to `ordered_topn_pushes_down_matches_single_node` by name, no line number.

#### [IMPLEMENTATION_COUPLED_TEST] Shard-fan-out test routes through the unrelated ORDER-BY-without-LIMIT fallback
- Location: line 1271
- Issue: `pushdown_shards_from_handshake_node_count_without_note` builds its query as `SELECT id, name, score FROM {} ORDER BY id` — an ORDER BY with no LIMIT. Per `order_by_without_limit_falls_back_correctly` (same file, line 1152), that shape makes the adapter **decline** the ordered-top-N pushdown and emit the unmatched-shape fallback. The test asserts nothing about ordering, so the clause contributes no coverage while coupling the test's pass/fail to an internal pushdown-shape decision unrelated to its subject. The mission lists "a safe fallback to an unaccelerated wrapper" as an existing pattern; if the declined-shape fallback is later changed to wrap the scan without the distributor, this test fails with "multi-file scan must push down as a LAKEHOUSE_DISTRIBUTE_FILES shard fan-out" and points a maintainer at node-count handling when the cause is the ORDER BY path.
- Fix: In crates/lakehouse-engine/tests/e2e_scan_test.rs line 1271, drop the `ORDER BY id` clause so the test exercises the plain projection-scan pushdown shape: change the statement to `let sql = format!("SELECT id, name, score FROM {}", vs_table());`. Leave both existing `assert!` markers unchanged — the two-file fixture still yields 2 shards, so `build_fan_out_inner`'s single-shard short-circuit (`support.rs:398`) is not reached and the distributor is still emitted.

### crates/lakehouse-engine/src/adapter/mod.rs

#### [OUTDATED_COMMENT] dispatch comment attributes a host-blocking constraint to plain handshake-metadata reads
- Location: lines 151-158
- Issue: the comment concludes "all three must happen before the runtime is built", extending the `ctx.connection()` host-blocking rationale to `ctx.script_schema()` and `cluster_nodes_from_context(ctx)`. Only `ctx.connection()` is a connect-back round-trip. In `exasol-udf-sdk` 0.20.3 `src/context.rs`, `node_count()` (line 131) is documented as "Number of nodes in the Exasol cluster, from the handshake metadata", in the same plain-metadata family as `node_id()`, `session_id()`, `vm_id()`, and `script_schema()` (line 161) — and `memory_limit()`'s doc in that same block states explicitly "This is plain metadata — no connect-back feature gate applies." The plan's own § Design confirms it: `SingleCallContext::node_count()` returns `self.handshake.node_count`. So the comment states a constraint that does not exist for two of its three subjects, and omits the actual reason the plan gives in § Consequences (keeping async planning code free of ambient-state reads and of a delivery-mechanism dependency).
- Fix: In crates/lakehouse-engine/src/adapter/mod.rs, rewrite the comment at lines 151-158 in the `Some("pushdown")` arm so it separates the two distinct reasons: (a) `ctx.connection()`, reached via `resolve_connection_config`, is a connect-back round-trip that may block on the UDF host and therefore must not run inside the tokio runtime; (b) `ctx.script_schema()` and `cluster_nodes_from_context(ctx)` are plain handshake-metadata field reads, captured here not because they block but so the async planning body reads no ambient state and takes no dependency on the UDF delivery mechanism. Delete the "all three must happen before the runtime is built" clause. Keep the existing note that `script_schema` is the schema qualifying the scan/distributor/merge UDF names in the generated pushdown SQL.

#### [REDUNDANT_COMMENT] resolve_nr_of_cores doc keeps vestigial cluster-topology framing
- Location: lines 952-953
- Issue: the doc comment opens "Per-node CPU core count `nr_of_cores`, resolved entirely in-process — no SQL round-trip, no connect-back session." The "no SQL round-trip, no connect-back session" contrast was load-bearing when this function resolved cluster *topology*, where the node count plausibly could have come from `NPROC()` over connect-back (the mission glossary still draws exactly that contrast). Now that the function returns only a core count from `std::thread::available_parallelism()`, the clause distinguishes nothing — no reader would expect a SQL round-trip for a local CPU count. The leading "Per-node CPU core count `nr_of_cores`" also just restates the function name and return type. This is leftover framing from the removed `resolve_cluster_nodes`, which the refactor otherwise cleaned up.
- Fix: In crates/lakehouse-engine/src/adapter/mod.rs, replace the first paragraph of the `resolve_nr_of_cores` doc comment (lines 952-953) with a single sentence stating the promise without the vestigial contrast, e.g. `/// Per-node CPU core count used to derive the AUTO parallelism, DataFusion threading, and S3 connection budgets.` Keep the second paragraph (lines 955-959) unchanged — the override-then-auto-detect precedence and the `0` = "unknown, caller applies the floor" contract are both still accurate and non-obvious.

### crates/lakehouse-engine/src/adapter/mod.rs

#### [ASSERTION_FREE_TEST] pushdown_ignores_persisted_cluster_nodes_note passes regardless of production behavior
- Location: lines 2614-2647
- Issue: the test claims to verify that "shard-count derivation uses only the `cluster_nodes` parameter threaded in from `dispatch`'s live handshake capture ... never a value read back from adapterNotes". It cannot detect that regression, because it never calls `handle_pushdown_request` — or any production function that reads a node count. It builds `pushdown_req` carrying `CLUSTER_NODES: "9"`, then uses that request only for a `NOTE_PARALLELISM_FACTOR` lookup that misses (so `parallelism_factor` is `DEFAULT_PARALLELISM_FACTOR`); the `CLUSTER_NODES` fixture value is never read by anything. It then hardcodes `let cluster_nodes = 1usize;` and asserts `shard_count(1, DEFAULT_PARALLELISM_FACTOR, 1000) == 1 * DEFAULT_PARALLELISM_FACTOR` — both sides derived from the same two literals and one constant. Its own doc comment concedes the defect: "this **exercises the same** parallelism_factor-from-notes + threaded-cluster_nodes computation it performs", i.e. it re-implements production logic in the test body instead of invoking it. The surviving live assertion is `shard_count` arithmetic already covered by `shard_count_oversubscribes_and_caps_at_300` and `shard_count_clamped_to_file_count_no_empty_shards` (`adapter/pushdown/support.rs:1763`, `:1781`). The plan's § Verification credits this test with covering two scenarios ("Pushdown reads the cluster node count from the UDF handshake" and "Recorded parallelism factor drives later work-unit sharding"); it covers neither, so the plan overstates verified coverage of the refactor's central claim.
- Failure scenario: re-add `let cluster_nodes = adapter_note(request, NOTE_CLUSTER_NODES).and_then(|s| s.parse::<usize>().ok()).filter(|&n| n >= 1).unwrap_or(1);` to the top of `handle_pushdown_request` (line 379), shadowing the parameter. Production fully regresses to the pre-refactor persisted-note read — a pre-refactor virtual schema carrying `CLUSTER_NODES: "9"` would plan a 9x-too-large fan-out, and a resized cluster would again shard against its create-time size — and `pushdown_ignores_persisted_cluster_nodes_note` still passes, along with every other unit test in the crate.
- Fix: In crates/lakehouse-engine/src/adapter/mod.rs, delete the test `pushdown_ignores_persisted_cluster_nodes_note` together with its doc comment (lines 2614-2647). Do NOT substitute another `shard_count` call: the invariant the test names is already enforced statically — `cluster_nodes: usize` is a required parameter of `handle_pushdown_request` and no `NOTE_CLUSTER_NODES` read remains in its body — and it cannot be asserted by any test that does not call `handle_pushdown_request`, which requires live catalog and object-storage I/O. After deleting, run `grep -n "NOTE_CLUSTER_NODES" crates/lakehouse-engine/src/adapter/mod.rs` and confirm the only non-test occurrences left are the constant definition (line 48), the `build_adapter_notes` doc reference (line 666), and the `notes.remove(NOTE_CLUSTER_NODES)` call (line 685). Then run `cargo test -p lakehouse-engine --lib adapter::` and confirm `cluster_nodes_from_context_defaults_to_one_when_node_count_zero`, `cluster_nodes_from_context_passes_through_reported_node_count`, and `refresh_notes_drop_inherited_cluster_nodes` still pass. Finally, update `specs/_plans/refactor-pushdown-node-count/plan.md` § Verification § Scenario Coverage: remove `pushdown_ignores_persisted_cluster_nodes_note` from the two rows that name it (the "Pushdown reads the cluster node count from the UDF handshake" Unit row and the "Recorded parallelism factor drives later work-unit sharding" row) so the table stops crediting coverage that does not exist, and remove its entry from § Implementation Tasks task 1.3.
