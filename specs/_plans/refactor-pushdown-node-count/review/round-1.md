## Premortem

Three failure stories, six months out:

1. **The key never left.** An operator upgrades, runs `ALTER VIRTUAL SCHEMA ... REFRESH`, and `SYS.EXA_ALL_VIRTUAL_SCHEMAS.ADAPTER_NOTES` still shows `CLUSTER_NODES` — forever, on every pre-existing schema. `build_adapter_notes` merges the incoming notes, so deleting the *insert* never deletes the *key*. The plan's Migration table promised the opposite. Routes to Feasibility `[UNSTATED_ASSUMPTION]`.
2. **The spec library contradicts itself.** After `/speq:record`, `vs-adapter/create-virtual-schema` still requires preserving `CLUSTER_NODES` on refresh, `parallelism/work-unit-sharding` § Background still says the node count comes from `adapterNotes`, and `specs/mission.md` still says it is captured at `createVirtualSchema`. Decision [7] set out to prevent "a spec that lies" and left three of them. Routes to Requirement Quality `[REQUIREMENT_CONFLICT]`.
3. **The implement loop stalls on task 1.3.** Task 1.3 changes `build_adapter_notes`'s arity and deletes `NOTE_CLUSTER_NODES` while 18 test call sites and five test references are only repaired in 1.4. `cargo test` cannot build between the two, contradicting plan.md's own per-group green invariant. Routes to Task Breakdown `[TASK_GRANULARITY]`.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md § Impact item 3 and § Migration row 1; `vs-adapter/create-virtual-schema-adapter-notes/spec.md` § "createVirtualSchema adapterNotes omit the cluster node count"; task 1.3
- Issue: the plan assumes dropping the `NOTE_CLUSTER_NODES` *insert* removes the *key*. It does not. `build_adapter_notes` opens with `let mut notes = parse_adapter_notes(request);` (`crates/lakehouse-engine/src/adapter/mod.rs:677`), and `parse_adapter_notes` (line 500) reads `request.schemaMetadataInfo.adapterNotes` — the persisted notes Exasol round-trips on every `refresh` and `setProperties`. The doc comment at line 657 states the contract outright: "Any pre-existing notes on the request are preserved (merge, not clobber)." Three consequences: (a) plan.md § Impact item 3's "the next `REFRESH` or `ALTER VIRTUAL SCHEMA SET` drops it" and § Migration's "Key is ignored, then removed by the next `REFRESH` / `setProperties`" are false — the stale key survives every refresh indefinitely; (b) the new scenario's THEN, "the `adapterNotes` of the returned response MUST NOT carry a `CLUSTER_NODES` entry", is unsatisfiable for the `refresh`/`setProperties` request types its own WHEN names, on any schema created before this change; (c) no task removes the key, and § Dead Code Removal deletes the `NOTE_CLUSTER_NODES` constant that a removal would need. Task 1.4 also hides the defect: it retargets `build_adapter_notes_merges_existing`'s probe key to `NOTE_PARALLELISM_FACTOR` while leaving that test's fixture injecting `"CLUSTER_NODES":"1"` (`adapter/mod.rs:1477`), so no test observes the survival.
- Fix: Choose one branch and make plan.md, the spec delta, and the tasks agree. Either (a) add `notes.remove(NOTE_CLUSTER_NODES);` to `build_adapter_notes` in task 1.3, keep the `NOTE_CLUSTER_NODES` constant (delete its row from § Dead Code Removal), and add a unit test `refresh_notes_drop_inherited_cluster_nodes` to task 1.4 asserting a request whose incoming `adapterNotes` carry `CLUSTER_NODES` yields a response without it; or (b) narrow the new scenario's WHEN to a `createVirtualSchema` request on a schema with no pre-existing notes, add an explicit `DELTA:NEW` scenario stating that a pre-refactor `CLUSTER_NODES` entry is preserved-but-ignored on refresh, and rewrite plan.md § Impact item 3 and § Migration row 1 to say the key persists and is never read rather than that a refresh drops it.

[no other objection — axis checked: threading `cluster_nodes: usize` through `dispatch` is confirmed feasible. The pushdown arm at `adapter/mod.rs:151-170` already performs two synchronous handshake captures before `rt.block_on` (`resolve_connection_config(ctx, &props)` line 159, `ctx.script_schema()` line 160); `node_count(&self)` takes `&self` (per the `StubCtx` impl at line 1326), so a `&dyn UdfContext` reborrow from `dispatch`'s `&mut dyn UdfContext` composes with the existing borrows without conflict. `handle_pushdown_request` (line 363) already carries a `script_schema: &str` value parameter of exactly this shape, and its consumer `handle_pushdown` already takes `cluster_nodes: usize` (`adapter/pushdown/mod.rs:108`), so the new parameter meets an existing `usize` sink with no conversion beyond the widening the plan names.]

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `vs-adapter/create-virtual-schema-adapter-notes/spec.md` § "createVirtualSchema adapterNotes omit the cluster node count" vs. two recorded specs the plan does not touch
- Issue: the new scenario forbids `CLUSTER_NODES` in the response `adapterNotes` for `createVirtualSchema`, `refresh`, and `setProperties`. Two recorded normative clauses require the opposite and are absent from plan.md § Features. `specs/vs-adapter/create-virtual-schema/spec.md:111`: "the adapter SHALL preserve every other pre-existing `adapterNotes` entry (`CLUSTER_NODES`, `NR_OF_CORES`, `PARALLELISM_FACTOR`, and the DataFusion threading and memory-budget entries) when writing `TABLE_MAP`". `specs/vs-adapter/refresh-and-set-properties/spec.md:33` § "Refresh rebuilds the table map and preserves other adapter notes" opens "*GIVEN* a `refresh` request whose `schemaMetadataInfo.adapterNotes` carries the persisted notes from creation (`CLUSTER_NODES`, `NR_OF_CORES`, ...)" and then requires preserving "every other pre-existing `adapterNotes` entry". After record the library both mandates and forbids `CLUSTER_NODES` in a refresh response.
- Fix: Add `vs-adapter/create-virtual-schema` and `vs-adapter/refresh-and-set-properties` to plan.md § Features and create both spec deltas. In `create-virtual-schema`, apply `DELTA:CHANGED` to § "Create virtual schema records the Exasol-name to Iceberg-identifier map in adapterNotes", deleting `CLUSTER_NODES` from the line-111 enumeration. In `refresh-and-set-properties`, apply `DELTA:CHANGED` to § "Refresh rebuilds the table map and preserves other adapter notes", deleting `CLUSTER_NODES` from the line-33 GIVEN enumeration. Keep both edits to the enumerated key lists alone, matching decision [7]'s narrow-deletion rule, and add a decision-log entry recording the two added features.
