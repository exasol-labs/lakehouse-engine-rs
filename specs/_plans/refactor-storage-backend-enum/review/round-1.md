## Premortem

Three ways this plan fails after it ships:

1. **The repo's behavior-preservation gate dies silently.** Five prior refactors recorded "the `dispatch_golden` goldens and the join golden-SQL full-string assertions pass unedited" as the normative proof of no behavior change. This plan edits five goldens and three join golden strings and amends only one of the four features that pin them. Six months on, nobody can tell whether an edited golden is an accepted wire change or a regression, and the next refactor's reviewer has no gate.
2. **The implementation stalls mid-lane.** Task 2.2 changes `resolve_file_list`'s type; the implementer then discovers `plan_join`, `resolve_one_join_side`, `ResolvedJoinSide::effective_storage`, `register_file_list`, `PositionalDeleteScanTable::new`, and `minimal_spec` all need converting and none is in the task list. The `[expert]` tagging, the "9 signatures" estimate, and the Group B lane split were all sized against the wrong file set.
3. **The dedup regresses invisibly in slice C.** `register_side_store`'s "skip the dimension side when its store key equals the fact side's" is not observable through DataFusion's registry, so the test the plan names for it cannot fail. A slice-C edit that registers the dimension store twice — doubling the warm connection pool against the connection budget — ships green.

## Intent Fidelity

No BLOCKER. Verified against the original intent and the interview:

- `StorageBackend::S3(StorageProps)` wrapping is the interview's chosen answer and the plan operationalizes it faithfully — `StorageProps`' 7 fields, `Default`, `secret_values`, and 3 unit tests are untouched (`crates/lakehouse-catalog/src/creds.rs:93-215`).
- **`resolve_vended_storage`'s signature change is NOT scope creep.** Confirmed at `crates/lakehouse-engine/src/adapter/pushdown/file_resolution.rs:248-257`: the vended result feeds straight into `build_s3_file_io(&effective_storage)` and into the scan spec. Leaving vending on `StorageProps` forces `file_resolution.rs` to write `match backend { StorageBackend::S3(p) => StorageBackend::S3(resolve_vended_storage(..., p, ...)) }` — a variant match plus a variant construction in the planning layer, i.e. exactly the knowledge the slice removes. Decision-log [4]'s reasoning holds.
- **The externally-tagged choice is sound and is correctly landed now, not deferred.** External tagging is serde's *default* for enums, so "landing the tag in slice B" is the zero-work option; deferring it would require adding `#[serde(untagged)]` now and deleting it in slice C. The error-degradation argument is independently valid. One premise is overstated but harmless: `StorageProps`' `endpoint`/`region`/`access_key`/`secret_key` carry no `#[serde(default)]`, so an untagged Azure payload would usually fail S3 deserialization rather than silently mis-pick — the decision is still right, the reasoning just leans on the weaker of two arguments.
- **"Byte-identical S3 behavior" is scoped correctly.** `spec.md` scenario 5 says "byte-identical … EXCEPT for the `storage` value's variant tag" and `plan.md § Impact` names the one wire change explicitly. No overclaim.
- The one-variant scope fence (decision-log [7]) matches issue #274's slice split.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `plan.md` § Impact ("Deploying the new `.so` requires no coordinated step beyond the normal upload")
- Issue: the "same `.so` produces and consumes the spec" argument holds within one *statement*, not one *query*. The VS adapter returns the scan-driving SQL as a string; Exasol then executes it as a separate statement that loads the `.so` again. A `.so` replaced between those two steps means an old-adapter untagged `storage` value hits a new-`.so` `SCAN` that requires the tag, producing an `unknown variant`/`invalid type` deserialization error rather than a clean failure. The window is narrow and a mid-query redeploy is already hazardous, but the plan states the stronger claim unconditionally.
- Fix: In `plan.md` § Impact, qualify the sentence: state that no coordinated step is needed provided no query spans the `.so` upload, and that a query whose pushdown was planned by the pre-upload `.so` fails on the tag.

## Design Depth

Deep-module and dependency checks pass on evidence: the enum absorbs four independently-S3-aware engine sites into one (`extract_bucket`, `build_s3_store`, `register_bucket_store`, the `build_s3_file_io` call), the two key-mapping sites are genuinely identical and collapse soundly (see below), the second owner is boundary-forced by a recorded constraint rather than chosen, the dependency edge stays engine → catalog with no cycle, and no dependency is added.

**The `catalog_storage_props` collapse is behavior-preserving.** Verified line by line: `build_s3_file_io` (`crates/lakehouse-catalog/src/iceberg_io.rs:25-45`) and `build_rest_catalog`'s inline block (`crates/lakehouse-catalog/src/session.rs:49-67`) insert the same six keys under the same conditions — `S3_ENDPOINT`/`S3_REGION`/`S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` only when non-empty, `S3_SESSION_TOKEN` only when `Some`, `S3_PATH_STYLE_ACCESS` always as `path_style.to_string()`. Both targets are keyed inserts (`FileIOBuilder::with_prop`, `HashMap::insert`), so the `HashMap` return order cannot change either result, and `inject_catalog_auth_props` runs after and shares no key. The new unit test `catalog_storage_props_carries_the_six_s3_keys_only_when_present` is the right gate — `build_rest_catalog`'s own path has no host-suite coverage, and the E2E MinIO path exercises only the all-keys-present branch.
