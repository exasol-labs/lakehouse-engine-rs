## Feasibility

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: `vs-adapter/storage-backend-enum/spec.md` scenario 3, clause at line 57; `plan.md` § Design > Architecture line 36, task 3.2, § Verification > Scenario Coverage rows at lines 186-187
- Issue: the new signature makes the size index's scope ambiguous, and the two integration suites the plan names as its gate do not exercise the registration path at all. Today `build_session_context` computes ONE whole-spec index — `build_spec_size_index` (`object_store.rs:140-150`) indexes `spec.files` AND `join.files` into a single map — and passes the same `&sizes` to both `register_bucket_store` calls (`object_store.rs:53-80`). That is load-bearing: in the shared-bucket case only the FACT registration happens, so the fact store must answer the DIMENSION files' HEADs from that map. `register_side_store(ctx, backend, files, table_root, budget, sizes)` now takes a per-side `files` parameter beside `sizes`; an implementer deriving `sizes` from `files` — the natural reading once every other parameter is per-side — leaves the shared-bucket join's dimension HEADs to the network, breaking `datafusion-scan/scan-execution-file-metadata`'s "the UDF MUST NOT issue a per-file object-store metadata (`HEAD`) request" (`specs/datafusion-scan/scan-execution-file-metadata/spec.md:34`, `:50`). Neither spec clause 57 ("the caller-supplied-size HEAD decorator … unchanged for both sides") nor task 3.2's "preserve the sized-HEAD wrapper … VERBATIM" states the map's scope. No test catches it: `crates/lakehouse-engine/tests/scan_no_head_test.rs` builds only `raw_spec(...)` and contains no join spec, and `crates/lakehouse-engine/tests/scan_join_test.rs` declares itself "`file://` Parquet fixtures — no S3 / MinIO" (line 5), so its scanning tests cannot reach `build_session_context` at all — `extract_bucket_from_files` errors "file URI has no bucket/host" on a `file://` first entry (`object_store.rs:340-342`). The four new unit tests pin only the returned `Option<Url>` sequence, never the registered store's size map. So `plan.md` rows 186-187 claim integration coverage that does not exist for these clauses.
- Fix: In `vs-adapter/storage-backend-enum/spec.md` scenario 3, add a clause requiring the size index handed to EVERY side's registration to be the WHOLE-spec index spanning the fact files AND the join dimension files, computed once per `build_session_context` call, because the shared-bucket case registers one store that must answer both sides' HEADs; state that the per-side `files` parameter selects the store KEY only and MUST NOT narrow the size map. In `plan.md` task 3.2, name `build_spec_size_index` (`object_store.rs:140`) as unedited and its result as passed to both calls. Add a unit test row to § Verification > Scenario Coverage — `shared_bucket_join_store_answers_both_sides_sizes_from_the_spec`, asserting the registered store's size map contains a dimension-side file key — and correct rows 186-187 to state that neither existing suite exercises the S3 registration path.
