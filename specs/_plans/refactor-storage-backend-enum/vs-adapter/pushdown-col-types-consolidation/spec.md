# Feature: Pushdown Col Types Consolidation

Collapses the duplicated column-type resolve, column-type list builder, and Exasol type classifier of the pushdown type-rewrite guards into one owner each.

## Background

<!-- DELTA:NEW -->
* This delta carves the scan spec's `storage` value out of THREE clauses, the golden-fixture gate of each of this feature's three scenarios: "One helper resolves a bare column node's Exasol type for every type-rewrite guard", "One builder produces the column-type list for both the first-table and the named-table selection", and "The three type-rewrite guards read their type family from the shared classifier". It amends no other clause, supersedes no Background bullet, and changes no type-resolve, fold, builder, or classifier rule.
* `vs-adapter/storage-backend-enum` (issue #274) wraps the scan spec's `storage` value in an externally-tagged backend variant. That value is embedded in the scan-driving SQL, so five `dispatch_golden` fixtures and three join golden-SQL assertions change by exactly one substring each.
* The carve-out permits an edit to the `storage` value ALONE. Every other byte of every golden stays unedited, which is what keeps this feature's gate a working proof rather than a retired one. The guard unit tests in `support.rs` — leaf, non-`column`, nameless-column, unresolvable-column — embed no scan spec and are unedited.
<!-- /DELTA:NEW -->

## Scenarios

<!-- DELTA:CHANGED -->
### Scenario: One helper resolves a bare column node's Exasol type for every type-rewrite guard

* *GIVEN* the three per-node type decisions in `pushdown/support.rs` — `guard_like_subject`, `is_bare_decimal_column`, and `coerce_string_position_arg` — which each hand-roll the same two-step resolve against the per-request `col_types: &[(String, String)]` list: read the node's `name`, fold it with the Unicode `to_uppercase`, then linear-scan `col_types` for a tuple whose first element equals it; and which each carry a doc-comment note asserting that it mirrors the other two's convention
* *WHEN* any of the three decides what to do with a bare `column` node
* *THEN* exactly ONE helper in the shared `support` submodule SHALL own that resolve, taking the node and the `col_types` slice and returning `Option<&str>` — the resolved Exasol type string, or nothing — and each of the three guards SHALL retain NO name-folding and NO `col_types` scan of its own
* *AND* the helper MUST NOT test the node's `type` tag, because a non-`column` node is NOT a failed lookup: `guard_like_subject` and `coerce_string_position_arg` return such a node UNCHANGED whereas a failed lookup makes them decline, so absorbing the tag test would convert a pass-through into a decline and silently drop pushdown for every computed expression and literal argument
* *AND* each guard SHALL therefore keep its own `type == "column"` test ahead of the call — the pass-through for the two `Option<Json>` guards, `false` for `is_bare_decimal_column` — so the helper owns the resolve and nothing else
* *AND* the helper SHALL fold the name with the Unicode `to_uppercase` and MUST NOT use `to_ascii_uppercase`, because all three guards fold that way today and the extraction MUST NOT change which fold they apply. The two folds agree on every name the adapter can declare, per the captured evidence above, so switching would be a gratuitous edit — and its harmlessness would rest on a normalization `resolve_table_schema` owns rather than on anything this helper can observe
* *AND* the helper SHALL return `None` for BOTH a nameless column node and a name absent from `col_types`, because all three guards already treat those two cases identically — a decline in the two `Option`-returning guards, `false` in the boolean one — so no third state is needed and none SHALL be introduced
* *AND* the helper SHALL be declared private to `support`, because its only three consumers live there
* *AND* every mirror-note comment SHALL be deleted, because the shared helper now enforces by construction what those notes asserted by convention: the three guards' doc-comment notes AND `guard_like_subject`'s INLINE BODY COMMENT above the lookup block the helper replaces, which is the sole carrier of the stale line-number citation; each guard's doc comment SHALL otherwise be preserved, in particular `coerce_string_position_arg`'s four-row per-type dispatch table and its `(#223)` non-`column`-argument exception — EXCEPT any sentence that names a predicate moving to `classify_exa_type`, which SHALL be reworded to name the classifier's family while KEEPING its rationale intact: `is_bare_decimal_column`'s "Integer columns are wire-encoded as `DECIMAL(p,0)`, so `.starts_with("DECIMAL")` also matches them (harmless: the trim is a no-op on a scale-0 value)" SHALL still record that integer columns classify as DECIMAL and that the trim is a harmless no-op at scale 0, but SHALL name `ExaTypeClass::Decimal` instead of the literal predicate, because after the substitution the guard no longer contains that predicate and a preserved sentence naming it would be a fresh instance of the stale-citation defect this delta deletes
* *AND* a unit test SHALL pin the helper's fold SENSITIVITY at this boundary, over a CONSTRUCTED column name whose Unicode and ASCII folds differ — `STRAßE`, chosen because `to_uppercase` yields `STRASSE` while `to_ascii_uppercase` leaves it unchanged: the helper MUST resolve a type against a Unicode-folded `col_types` list and MUST return `None` against an ASCII-folded one, so the fold the extraction preserves is asserted rather than assumed. That test MUST NOT be read as a claim that Exasol delivers such a name. The captured evidence above records that it does not, because this crate uppercases every Iceberg field name before declaring it
* *AND* that test SHALL construct both `col_types` slices as LITERALS — one carrying the Unicode-folded `STRASSE`, one carrying the ASCII-folded `STRAßE` — and SHALL call NEITHER builder, so it exercises the lookup alone and stays inside `support`. Calling the builders here would couple a lookup unit test to the builder contract the merged-builder scenario below already pins, and would require reaching a `pub(super)` item of `joins::planning` from a sibling module, which no test-only export SHALL be added to enable
* *AND* the scan-driving SQL generated for every pushdown request MUST be byte-identical to its pre-extraction output EXCEPT for the scan spec's `storage` value, which `vs-adapter/storage-backend-enum` re-encodes as an externally-tagged backend variant over a byte-identical payload; every existing guard unit test in `support.rs`, every join golden-SQL assertion, and every `dispatch_golden` fixture MUST pass with NO change to any test assertion or expected value outside that `storage` value — the leaf, non-`column`, nameless-column, and unresolvable-column tests of all three guards embedding no scan spec at all and therefore being unedited, and being the gate that makes the pass-through-versus-decline distinction falsifiable here

### Scenario: One builder produces the column-type list for both the first-table and the named-table selection

* *GIVEN* `extract_all_column_types` (`pushdown/support.rs`) and `involved_table_columns` (`pushdown/joins/planning.rs`), byte-for-byte the same walk — reach `involvedTables`, take a table, map each column's `name` and its `dataType` through `exasol_type_from_json` — differing in exactly two respects: which `involvedTables[]` entry they select (the FIRST, versus the one whose `name` equals an argument) and which case-fold they apply to each column name (the Unicode `to_uppercase`, versus the ASCII-only `to_ascii_uppercase`)
* *WHEN* the adapter builds the `(UPPERCASE name, Exasol type)` list for a single-table request, or for one named table of a join
* *THEN* exactly ONE builder in the shared `support` submodule SHALL own the common walk, and both existing functions SHALL be expressed on it rather than repeating it
* *AND* that builder SHALL take the table selection and the case-fold function as TWO SEPARATE parameters, and MUST NOT derive either from the other nor collapse them into one mode argument, because they are independent decisions: a single mode argument would encode "first-table selection implies Unicode folding" as though it were intended, when it is an unreconciled divergence, and would leave a third selection-plus-fold combination inexpressible
* *AND* the builder SHALL apply the case-fold function its caller supplies and SHALL contain NO fold of its own, so `extract_all_column_types` keeps emitting Unicode-folded names and `involved_table_columns` keeps emitting ASCII-folded names, byte-for-byte as before; unifying the two folds SHALL NOT happen under this scenario
* *AND* `extract_all_column_types` SHALL keep its `pub(super) fn(&Json) -> Vec<(String, String)>` signature, `involved_table_columns` SHALL keep its `pub(super) fn(&Json, &str) -> Vec<(String, String)>` signature, and `involved_table_columns` SHALL remain declared in `joins/planning.rs`, so NO call site of either changes — for the former the two production sites `support::extract_projection` and `pushdown::handle_pushdown` plus the test sites in `grouped_agg.rs` and `topn.rs`; for the latter the four production sites `joins/mod.rs::plan_join`, `joins/sql_builders.rs::render_broadcast_join` (twice), `joins/sql_builders.rs::build_n_scan_join_sql`, and `joins/rendering.rs::extract_join_projection` (twice), plus the test sites in `sql_builders.rs` and `rendering.rs`
* *AND* the builder SHALL be declared `pub(super)` in `support`, which already reaches `pushdown` and its `joins::planning` descendant, so NO production item's visibility widens and no join-module `use` path widens; this delta adds NO test-only item and changes NO item's visibility in either direction — every test it requires is declared where the items it calls are already visible
* *AND* neither wrapper SHALL be deleted as a shallow pass-through, because each supplies arguments the shared builder does not choose — a table selection and a case-fold — so each is a partial application that names a decision rather than a body forwarding the same arguments
* *AND* `joins/planning.rs`'s `use crate::types::mapping::exasol_type_from_json` SHALL be deleted, because the merge moves its ONE remaining call site into the shared builder and this crate's `-D warnings` clippy gate rejects the unused import — so the compiler, not review, proves the mapping moved rather than being copied
* *AND* a unit test SHALL pin each wrapper's OWN fold as the merge's contract, over a CONSTRUCTED request field whose two folds differ — `STRAßE`, yielding `STRASSE` from the Unicode fold and `STRAßE` from the ASCII fold — asserting from a SINGLE request that `extract_all_column_types` yields the Unicode-folded name and `involved_table_columns` yields the ASCII-folded name, so a merge that picks either fold for both callers fails this test instead of passing silently, which is the one outcome an "obviously correct" merge is most likely to produce
* *AND* that test SHALL remain REQUIRED even though no request the adapter can receive carries such a name, because it is the ONLY assertion in the repository that distinguishes the two folds: every column name reaching either builder in production is already Unicode-uppercased by `resolve_table_schema`, so a silent unification passes the entire pre-existing suite. It MUST NOT be restated as an agreement test over already-uppercased names — an agreement assertion holds under a unified fold too, and would therefore guard nothing
* *AND* that test SHALL be declared in `joins/planning.rs`'s OWN `#[cfg(test)] mod tests`, because that is where BOTH builders are already reachable with no new item: `involved_table_columns` is declared in that same file, and `support`'s `pub(super)` items reach it as a descendant of `adapter::pushdown` — the file's production code already imports two of them. It SHALL NOT be declared in `support`, which is a SIBLING of `joins` and cannot call a `pub(super)` item of `joins::planning`; no `use` re-export and no `#[cfg(test)]`-only wrapper SHALL be added to make a `support`-side placement compile, because relocating the test removes the need for either. While no production code in `planning.rs` calls `support::extract_all_column_types`, any import of it this test needs SHALL be declared INSIDE the `#[cfg(test)] mod tests` block rather than at `planning.rs`'s module level, because a module-level import used only under `cfg(test)` is an unused import that this crate's `-D warnings` gate rejects in the non-test build
* *AND* that test MUST cite the tracked follow-up issue for removing `column_types`' `fold_case` parameter, filed as part of this plan, so a later unification reads as "the tracked dead flexibility is removed" rather than "an invariant broke" — the citation convention this feature already applies to a pinned tracked gap. That issue SHALL be scoped as a SIMPLIFICATION, not a correctness fix, because the divergence it removes is unobservable through the adapter
* *AND* the scan-driving SQL for every single-table pushdown request and the join SQL for every join shape MUST each be byte-identical to their pre-merge output EXCEPT for the scan spec's `storage` value, and every existing pushdown, joins, and top-N test MUST pass with NO change to any test assertion or expected value outside that value — the two fold-pinning tests above, which construct their own requests and assert names rather than SQL, being unedited by this carve-out

### Scenario: The three type-rewrite guards read their type family from the shared classifier

* *GIVEN* the same three guards' hand-written Exasol type-string predicates — `starts_with("VARCHAR") || starts_with("CHAR")`, the exact match `== "DATE"`, and `starts_with("DECIMAL")` — spelled out once per guard against the family vocabulary `datafusion-scan/type-mapping-module-structure` already records as the `ExaTypeClass` enum and the `classify_exa_type` function in `types/mapping.rs`
* *WHEN* a guard decides what to do with a resolved Exasol type string
* *THEN* each of the three guards SHALL obtain its type family by calling `classify_exa_type` and SHALL retain NO `starts_with` test and NO string equality test against an Exasol type string
* *AND* the classifier's contract SHALL remain owned by `datafusion-scan/type-mapping-module-structure` and is consumed here, NOT restated — in particular its `Decimal` predicate stays `starts_with("DECIMAL")` with no open paren, so the bare argumentless string `DECIMAL` keeps classifying as DECIMAL in all three guards exactly as it does today
* *AND* the two `Option<Json>`-returning guards SHALL each match EXHAUSTIVELY over `Option<ExaTypeClass>` with NO wildcard arm, so a variant added to `ExaTypeClass` later becomes a compile error at each guard rather than a silent decline
* *AND* those two guards' arm sets SHALL differ in exactly ONE arm, `Decimal`: `guard_like_subject` SHALL decline it alongside `Other` and the lookup miss, while `coerce_string_position_arg` SHALL coerce it through `wrap_decimal_to_varchar`; that difference SHALL remain a visible match arm and MUST NOT be abstracted behind a coercion-policy trait, a shared dispatch table, or a parameter, because one closed variation between two functions reads better as two arms than as an indirection
* *AND* `is_bare_decimal_column` SHALL remain a two-way `Decimal`-versus-everything-else test and MAY use a non-exhaustive form, because a family added later genuinely IS "not DECIMAL" for this guard, so exhaustiveness would force an edit that could only restate the same answer
* *AND* the column-lookup miss SHALL stay each guard's OWN branch and MUST NOT be routed through the classifier: no guard SHALL pass a placeholder or sentinel string in place of an absent type, per the recorded requirement that `classify_exa_type` take a non-optional `&str`
* *AND* `wrap_decimal_to_varchar` and `wrap_cast_to_varchar` SHALL be unchanged, and the `decimal_to_varchar_exasol` synthetic node and its `vs-expression` rendering SHALL be unchanged — only the dispatch that ROUTES to them moves
* *AND* the scan-driving SQL generated for every pushdown request MUST be byte-identical to its pre-substitution output EXCEPT for the scan spec's `storage` value, which `vs-adapter/storage-backend-enum` re-encodes as an externally-tagged backend variant over a byte-identical payload, and every existing guard unit test in `support.rs` MUST pass with NO change to any test assertion or expected value — the per-family tests of all three guards, covering a `VARCHAR` subject, a `CHAR` subject, a `DATE` subject, a `DECIMAL` subject, an integer `DECIMAL(p,0)` subject, a `DOUBLE PRECISION` or `BOOLEAN` or `TIMESTAMP` subject, and an unresolvable column, embedding no scan spec and therefore being unedited, and being the gate that makes this substitution's behavior-preservation falsifiable
