### crates/lakehouse-engine/src/types/mapping.rs

#### [SHRINKABLE] The classifier splits the arm list back into two constructs
- Location: lines 35-69 (`compatible_exasol_type`), specifically the pre-match `if let` at 36-40
- Issue: the scenario this task implements requires "exactly one classifier SHALL own that arm list", but `Decimal128` is decided in an `if let` *before* the `match`, so the arm list now lives in two constructs inside the one function — the same two-places shape the refactor exists to remove. It is also longer than the single-match form: the early return plus its 2-line explanatory comment add 5 lines that a guarded match arm expresses in one. The pre-refactor code already had `Decimal128` as a guarded arm in the same match, so this split was introduced, not inherited.
- Fix: In crates/lakehouse-engine/src/types/mapping.rs, delete the pre-match `if let DataType::Decimal128(p, s)` block and its 2-line comment at lines 36-40 of `compatible_exasol_type`, and instead add `DataType::Decimal128(p, s) if *p <= 36 && *s <= 36 => return Some(format!("DECIMAL({p},{s})")),` as an arm of the existing `match dt`, placed immediately after the `DataType::Timestamp(_, _)` arm and before the `_ => return None` arm. Run `cargo test -p lakehouse-engine --lib` and confirm 704 tests still pass.

#### [MISSING_DOC_COMMENT] The module doc comment is a `///` attached to a `use`, so rustdoc drops it
- Location: lines 1-17
- Issue: task 7's deliverable — a module doc naming the three representations the module owns — was written as `///` outer doc comments on lines 1-16, which bind to the `use arrow::datatypes::{DataType, TimeUnit};` item on line 17. That item is a private import, so the 16 lines are silently discarded and `types::mapping` renders with no module documentation at all. The spec clause "the module doc comment of `types/mapping.rs` SHALL name all three representations ... so a reader landing in the module reads its scope there" is therefore unmet for anyone reading the docs rather than the file. No compiler warning fires (doc comments on `use` are legal), so the gate did not catch it.
- Fix: In crates/lakehouse-engine/src/types/mapping.rs, convert every `///` line in the leading block (lines 1-16) to an inner doc comment `//!` so the block documents the module rather than the `use` item on line 17. Change no wording. Then run `cargo doc -p lakehouse-engine --no-deps` and confirm the module page for `types::mapping` shows the three-representation text.

#### [OUTDATED_COMMENT] `parse_decimal_args`' stated "already trimmed" precondition is untrue at two of its three call sites
- Location: lines 164-166 (doc comment) with call sites at line 405 (`exasol_type_to_json`) and `adapter/pushdown/grouped_agg.rs:831` (`sum_emit_type`)
- Issue: the doc says "The input is expected to be already upper-cased and trimmed." Now that the parser is `pub(crate)` and shared, two of its three in-crate callers pass an untrimmed string: `exasol_type_to_json` does `exasol_type.to_uppercase()` with no `trim()`, and `sum_emit_type` passes `col_ty` raw. Only `exasol_type_to_arrow` trims (line 117). The stated precondition is thus unenforced and describes no caller contract, while the function's actual behaviour is narrower and more specific: the `DECIMAL(` prefix must sit at offset 0 (a leading space yields `None`), whereas whitespace around each *argument* is trimmed. A reader trusting the doc could either add a whole-string `trim()` at a call site — silently changing which inputs are accepted — or assume leading whitespace is already handled.
- Fix: In crates/lakehouse-engine/src/types/mapping.rs, replace the "The input is expected to be already upper-cased and trimmed." sentence in `parse_decimal_args`' doc comment with a statement of the actual contract: the input must be upper-cased and the `DECIMAL(` prefix must start at offset 0 (leading or trailing whitespace around the whole string yields `None`), while whitespace around each argument is trimmed before parsing.
