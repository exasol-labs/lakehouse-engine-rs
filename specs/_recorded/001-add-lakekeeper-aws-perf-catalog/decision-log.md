# Decision Log: add-lakekeeper-aws-perf-catalog

## Interview

Planned in headless mode (`/speq:plan-pr`), so there was no live clarifying interview. Two decisions were confirmed with the user directly before planning started and are recorded here verbatim in intent; every other decision below was assumed and documented per the headless escalation rule.

**Q:** Should the AWS Lakekeeper stack include Keycloak, or run Lakekeeper with authentication disabled for simplicity, given the security group already restricts ingress to allowlisted IPs?
**A:** Include Keycloak. It matches the existing local E2E stack and is more representative of the customer's real deployment.

**Q:** Should the stack be persistent like `data-stack`, or ephemeral with explicit apply/destroy scripts like `trino-stack`?
**A:** Ephemeral — `lakekeeper-up.sh` / `lakekeeper-down.sh`, explicit apply and destroy, same cost-safety posture as the rest of `deploy/`.

**Q:** Is Glue being replaced?
**A:** No. Lakekeeper is an additional option. `BENCH_CATALOG` defaults to `glue` and existing runs stay byte-for-byte unchanged.

One accepted exception to that last answer is on the record. The Glue arm's report header gains a `catalog=` line, so a Glue report differs from a pre-change report by exactly that one line and in nothing else — the required variables, catalog URI, CONNECTION password, virtual-schema properties, query set, and row counts are all unchanged. The docker target keeps strict byte-for-byte parity: the field is emitted on the remote target only.

### Second interview — the bash redirection

After two adversarial review rounds passed and PR #380 was opened as a draft, with zero code written, the user redirected the design. This interview WAS live. It supersedes the Rust deliverable those two rounds reviewed.

**Statement (not a question):** "I do not want lakekeeper provisioning being part of the Rust code."
Treated as a hard requirement: no Rust crate, no `[[bin]]`, no manifest change.

**Statement:** "lets have an e2e test suite and a demo suite. Both will be started/configured via a Bash script (parameter for up- and down)."
Later refined by the user into three run contexts — e2e (local Docker, existing, out of scope), benchmark (programmatic, AWS), and demo (interactive, AWS) — sharing one AWS stack with a bash up/down lifecycle pair.

**Q:** Benchmark and Demo both run against the AWS cluster with a Lakekeeper catalog. Do they share ONE AWS Lakekeeper stack/provisioning script, or do you want two separate stacks?
**A:** "share stack; but the configuration is different, e.g. lakekeeper required for the demo. Maybe we define 'suites' as part of the config?"

**Q:** Where should the bash provisioning script (Glue read + Lakekeeper bootstrap/register) run from? Offered: (a) operator's laptop with static AWS keys and no instance role; (b) the new Lakekeeper EC2 box itself with an IAM instance profile, requiring `lakekeeper-up.sh` to SSH in and run it remotely.
**A:** "The script shall either be used on the laptop for demo, or from this EC2 to perform the performance benchmark."
Neither offered option alone. The script must work from BOTH locations depending on which context is running. See decision [23].

**Q:** What actually differs between the Benchmark suite and the Demo suite, on the shared AWS Lakekeeper stack? Offered as a multi-select: query set/workload; warehouse/namespace naming; report/output format; nothing else beyond query set.
**A:** "The benchmark is programmatic, the demo is interactive."
No option was selected. The user restated the distinction in their own words instead, and that restatement is the authoritative answer. It is taken to mean the difference is WHO runs the commands, not WHAT the tooling does. No separate query set, warehouse name, namespace, or report format is confirmed, so none is planned. See decision [22].

## Design Decisions

### [1] Ephemeral stack lifecycle, modeled on `trino-stack`

- **Decision:** `deploy/lakekeeper-stack/` is a separate OpenTofu stack layered on the persistent `data-stack`, applied and destroyed only by `deploy/scripts/lakekeeper-up.sh` and `lakekeeper-down.sh`, never by another stack's apply.
- **Alternatives:** Fold Lakekeeper into the persistent `data-stack` behind a toggle, as EMR Serverless is. Rejected: an EC2 box bills continuously, unlike an idle EMR Serverless application, and a toggle in `data-stack` puts a billable resource one forgotten variable away from every `data-stack` apply.
- **Rationale:** User-confirmed. Table registration is cheap and idempotent, so re-provisioning on each `up` costs nothing and buys the same cost-safety posture the Trino stack already has.
- **Promotes to ADR:** no

### [2] Keycloak is part of the AWS stack

- **Decision:** The AWS box runs the same four-container set as `docker-compose.lakekeeper.yml` — PostgreSQL, Keycloak importing `scripts/keycloak-realm-iceberg.json`, Lakekeeper `migrate`, Lakekeeper `serve` — with the same realm, client id, client secret, and audience.
- **Alternatives:** Run Lakekeeper unauthenticated, relying on the security group. Rejected by the user.
- **Rationale:** The customer's own catalog is OIDC-secured, and the OAuth2 client-credentials CONNECTION contract is the one `e2e-harness/lakekeeper-e2e-harness` already proves. Reusing it means no new CONNECTION field and no engine change.
- **Promotes to ADR:** no

### [3] The provisioning tool is a separate binary-only workspace member — SUPERSEDED by [26]

- **Status:** SUPERSEDED by decision [26], "Provisioning is bash, not Rust". Retained for the record because it was reviewed across two adversarial rounds; nothing in it is implemented. No `crates/lakekeeper-provision` is created. The question this decision answered — how to keep a provisioning binary out of the `.so`'s dependency graph — no longer exists, because there is no binary. The `Makefile`'s package-scoped UDF build line and the shared `Cargo.lock` are therefore untouched by this plan, and the `tests/dependency_direction.rs` it proposed is not written.
- **Decision (as reviewed, not implemented):** Add `crates/lakekeeper-provision`, a binary-only workspace member depending on `lakehouse-catalog`. Neither shipped crate names it.
- **Alternatives:** A `[[bin]]` inside `lakehouse-catalog`. Rejected: Cargo applies a crate's `[dependencies]` to every target, so the bin's HTTP-client and runtime needs would enter the library build too. `lakehouse-catalog` compiles into the `.so`, whose SLC fingerprint depends on exactly what builds it, and `cargo` feature unification would let a bin-only feature reach the shipped artifact. A `required-features` gate narrows but does not remove that coupling.
- **Rationale:** The shipped artifact is built by a package-scoped `cargo build --release -p lakehouse-engine` (`Makefile:52`), so no other workspace member's features enter its graph. That, not the manifest test alone, is what holds: the manifest test rules out a direct edge, while feature unification happens per build-graph. The workspace sets `resolver = "2"` and leaves `default-members` unset, so a bare root `cargo build` would put the new member and the cdylib in one graph — hence the test also asserts the `Makefile`'s UDF build line stays package-scoped. `Cargo.lock` is shared, so a dependency the new member adds must not raise a shared version; such a bump is a reviewed change to the `.so`. A known boundary seam is left unchanged: every public function of `lakehouse-catalog` returns `exasol_udf_sdk::error::UdfError`, so a laptop-only tool links the Exasol UDF runtime's error type. Fixing that would mean a public-surface change to a shipped crate, which is out of scope here.
- **Promotes to ADR:** yes

### [4] The Lakekeeper write side is raw authenticated HTTP, not an `iceberg_catalog_rest::RestCatalog` — PARTLY SUPERSEDED by [24]

- **Status:** The "raw authenticated HTTP over one client holding one token" half SURVIVES unchanged and is now `curl` rather than `reqwest`. The "library owns wire shapes, tool owns transport" half is SUPERSEDED by decision [24]: bash cannot import `RegisterTableRequest` or `CreateNamespaceRequest`, so every JSON key is hand-spelled and the compile-time guarantee is gone. Decision [24] states what replaces it. The rejected alternative below is now doubly moot — a bash script could not configure a `RestCatalog` at all.
- **Decision:** The provisioning script issues the Lakekeeper Management API calls and the Iceberg REST namespace-create and register-table calls itself, over one HTTP client holding one Keycloak token.
- **Alternatives:** Build a `RestCatalog` and call `Catalog::register_table`. Rejected: configuring it for OAuth2 means re-declaring the REST auth property keys (`credential`, `oauth2-server-uri`, `scope`) that `lakehouse-catalog` holds crate-private precisely because `iceberg-catalog-rest` 0.10.0 exports no constants for them. A second copy of those literals is one decision with two independent owners. Widening the catalog crate's public surface instead would force an edit to its guarded reachability probe and a delta on `vs-adapter/catalog-crate-public-surface-extensions` for a caller that lives outside the `.so`.
- **Rationale:** The tool already must speak raw HTTP for bootstrap and warehouse creation, and Lakekeeper accepts the same Keycloak token for both API surfaces. One client, one token, one owner of the provisioning protocol. The wire shapes still come from the library, so no JSON key is hand-spelled.
- **Promotes to ADR:** yes

### [5] The warehouse's bucket and key prefix are derived from the tables, not configured

- **Decision:** The tool reads every table's `metadata_location` and its metadata document's recorded `location` from the source catalog first, derives a bucket and key prefix that both values of every table sit STRICTLY below, and only then creates the warehouse. A prefix equal to some table's own root is shortened to its parent. Two tables in different buckets is a hard error. A derived key prefix that would be EMPTY — tables directly under the bucket root, or the shorten-to-parent rule firing at the top level — is also a hard error naming the bucket, rather than a bucket-root warehouse: an empty prefix makes the warehouse base the bucket itself and leaves the derivation nothing to shorten for the next table.
- **Alternatives:** A `key-prefix` variable on the stack, defaulting to the Glue database directory. Rejected: a configuration parameter here is a decision the tool declined to make, and a stale value silently produces a warehouse whose storage profile does not cover the locations it is then asked to register.
- **Rationale:** Verified against the Lakekeeper v0.13.1 source: register-table applies the sublocation test TWICE — once to the submitted metadata location and once to the `location` field read out of the metadata document — and treats equality with the warehouse base as a failure. No configuration relaxes either check. Deriving both bounds from the same values that are about to be checked makes disagreement impossible; the shorten-to-parent rule is what keeps a single-table namespace from producing a base-equal prefix. Reading the recorded root from the metadata document rather than parsing the metadata file's path removes a path-shape guess from the derivation.
- **Promotes to ADR:** no

### [6] The catalog gets its own write-capable storage credential; the engine keeps read-only keys

- **Decision:** The stack creates an IAM user named with the `<project>-<env>-lakekeeper` prefix, granting object read, write, and delete on the `data-stack` bucket only, and stores its key pair in SSM `SecureString`. That key pair is the warehouse's storage credential. The Exasol CONNECTION keeps the existing read-only `engine-reader` key pair.
- **Alternatives:** Reuse `engine-reader` for both — rejected: its policy grants `GetObject`, `ListBucket`, and `GetBucketLocation` only. Disable Lakekeeper's storage validation with its runtime skip setting so a read-only credential suffices — also rejected: upstream documents that setting as unsuitable for production, it hides a credential or prefix misconfiguration until the first register call, and it does not relax the location rule anyway.
- **Rationale:** Verified against the Lakekeeper v0.13.1 source: warehouse creation writes, reads back, and deletes a probe object under a random path inside the warehouse prefix, then asserts that prefix is empty. So the credential needs object put, get, and delete plus bucket list, and a read-only credential cannot create a warehouse at all. The probe's random identifiers mean it cannot collide with the TPC-H data. Splitting the two credentials keeps the query path at read-only permission, which is the property that matters since the query path is what the demo exercises. No `deploy/iam/deployer-policy.json` change is required: the deployer's IAM statement already covers `<project>-*`-named users, policies, and access keys.
- **Promotes to ADR:** yes

### [7] Two URI vantages, keyed on WHERE THE CALLER RUNS, not on which script calls

- **Decision:** The stack outputs both vantages. The vantage a caller gets is determined by its LOCATION: a caller inside the VPC receives the PRIVATE-IP catalog and token URIs, a caller outside it receives the PUBLIC-IP ones. Three callers exist and each follows that one rule. `secrets.sh` writes the PRIVATE-IP URIs into `bench/.env`, because the consumer is the Exasol UDF inside the VPC. `lakekeeper-up.sh` passes the PUBLIC-IP URIs to the provisioning script, because it runs from the operator's machine outside the VPC. An in-VPC EC2 caller running `lakekeeper-provision.sh` directly (decision [23]) passes the PRIVATE-IP URIs, for the same routing reason the UDF does. `lakekeeper-provision.sh` itself reads `LK_TARGET_*` verbatim and derives, rewrites, or vantage-corrects nothing, so the caller is the single owner of the choice. Lakekeeper's primary OIDC issuer is the private-IP one and its additional-issuers setting names the public-IP one, so both vantages' tokens are accepted.
- **Supersedes its own earlier wording:** the rule was previously keyed on WHICH SCRIPT was calling — "`lakekeeper-up.sh` passes the PUBLIC-IP URIs, because the consumer is the operator's machine". That conflated script identity with location and left `LK_TARGET_CATALOG_URI` undefined for decision [23]'s second run site, which is a different location running the same script. Cross-reference decision [23].
- **Alternatives:** One public-IP URI for both. Rejected: `deploy/trino-stack/outputs.tf` records that a same-VPC client reaching another instance's public IP routes out through the internet gateway and back, which is unreliable for a long-lived connection — and Keycloak stamps the token's `iss` from the request host, so a single-issuer configuration rejects one of the two callers.
- **Rationale:** Same asymmetry the Trino stack already hit and documented. Encoding it in the outputs and in the OIDC configuration means neither caller can be pointed at the wrong vantage by accident.
- **Promotes to ADR:** yes

### [8] The Keycloak realm export reaches the box through S3, not user-data

- **Decision:** The stack uploads `scripts/keycloak-realm-iceberg.json` to the `data-stack` bucket as a managed object under a Lakekeeper-specific key, and the instance fetches it on boot with its instance profile. That key MUST sit outside any prefix the provisioning tool can derive from the table locations — a dedicated `lakekeeper/` top-level key, never under the TPC-H data prefix — so the object cannot land inside the warehouse prefix Lakekeeper's creation probe operates on.
- **Alternatives:** Inline the file into the user-data template. Rejected: the realm export is 21 KB and EC2 user-data is capped at 16 KB, so inlining cannot work.
- **Rationale:** OpenTofu owns the object's lifecycle, so teardown removes it. The instance role's `s3:GetObject` is scoped to that one key. The file's contents are already committed to this repository and hold no live secret.
- **Promotes to ADR:** no

### [9] The bench harness gets a Lakekeeper-specific password builder, not a parameterized one

- **Decision:** Add `build_conn_password_lakekeeper` beside the existing `build_conn_password_cloud` and `build_conn_password_local`, and dispatch on `BENCH_CATALOG` inside the existing `remote)` arm.
- **Alternatives:** Add flags to `build_conn_password_cloud`. Rejected: `docs/catalogs.md` states the adapter rejects a CONNECTION combining `use_sigv4` with `client_id` or `client_secret`, so the two payloads are mutually exclusive by adapter rule, not two settings of one payload.
- **Rationale:** Mirrors the split the file already uses for docker versus cloud, keeps each builder's offline self-check assertions independent, and leaves the Glue payload byte-identical.
- **Promotes to ADR:** no

### [10] `BENCH_CATALOG` defaults to `glue`; an unknown value is a hard error

- **Decision:** Unset means Glue, with the same required-variable list, catalog URI, password JSON, and virtual-schema properties as before. Any value other than `glue` or `lakekeeper` exits with an error naming the accepted values.
- **Alternatives:** Infer the catalog from which variables are present. Rejected: `bench/.env` will carry both catalogs' variables at once, so presence cannot select, and CLAUDE.md already records that a stray `bench/.env` silently redirecting a run is a debugging trap worth avoiding.
- **Rationale:** An explicit default preserves today's behavior exactly, and an explicit rejection stops a typo from producing a Glue run labeled as a Lakekeeper one.
- **Promotes to ADR:** no

### [11] Spec placement: one new feature plus a delta on the harness that owns the toggle

- **Decision:** The AWS deployment, the provisioning tool, and the secrets wiring go in a new feature `e2e-harness/aws-lakekeeper-perf-catalog`. The `BENCH_CATALOG` selection goes in a CHANGED delta on `e2e-harness/cloud-e2e-harness`.
- **Alternatives:** One new feature covering both. Rejected: `cloud-e2e-harness` already owns the remote bench target's CONNECTION and virtual-schema construction, including the recorded remote-parallelism scenario. Adding a second catalog arm changes behavior that feature owns.
- **Rationale:** Keeps one owner per decision. A reader asking "what does the remote bench target do" finds one feature, not two. No new domain is created for a single feature.
- **Promotes to ADR:** no

### [12] The Lakekeeper bootstrap and warehouse idempotency rules are duplicated on purpose, with a follow-up

- **Status:** CARRIED FORWARD, and the deferral is now stronger than when it was written. Under decision [26] the two copies are in DIFFERENT LANGUAGES — bash and Rust — so extracting a shared implementation is not merely costly but impossible without reintroducing the Rust tool the user removed. The follow-up issue changes from "extract shared code" to "keep the two copies' classification rules in sync, cited in both".
- **Decision:** `deploy/scripts/lakekeeper-provision.sh` re-derives the bootstrap and warehouse-create idempotency classification that `crates/lakehouse-engine/tests/common/lakekeeper.rs` already encodes, rather than extracting a shared implementation now.
- **Alternatives:** Extract the classification into shared code the E2E harness also calls. Rejected outright now that the caller is bash: the harness is test-only Rust, targets MinIO and ADLS, uses the blocking HTTP client, and panics rather than returning errors, and no shared artifact can serve a bash script and a Rust test module.
- **Rationale:** A tactical duplication, taken knowingly. The one live-observed rule at risk of drifting — Lakekeeper 0.13.1 reporting a duplicate warehouse as `400` with a storage-profile overlap rather than `409` — is cited in both the new spec and the tool's own documentation, and the plan schedules a follow-up issue to consolidate. The duplication does NOT extend to that classification's caveat: `crates/lakehouse-engine/tests/common/lakekeeper.rs:395-399` states that for warehouses sharing a bucket the 400-means-already-present reading is an unverified inference and that a caller needing certainty must read the warehouse back. The provisioning tool needs that certainty — the whole design turns on the warehouse prefix equalling the derived one — so it confirms every already-present classification with a storage-profile read-back, which the E2E harness only offers as an optional helper.
- **Promotes to ADR:** yes

### [13] Offline verification uses a stubbed-PATH bash harness; the AWS run is manual

- **Status:** AMENDED for the bash design. The harness now carries the load the Rust sibling `_tests.rs` files were going to carry, so its scope grows from "recorded arguments and generated files" to "recorded arguments, generated files, AND every emitted JSON request body". A second test script is added for the Docker integration half. Decision [24] explains why the request-body assertions are load-bearing rather than nice to have.
- **Decision:** Two test scripts, one offline and one against Docker. `deploy/scripts/tests/lakekeeper.test.sh` stubs `tofu`, `aws`, `ssh`, and `curl` on a temporary PATH and asserts recorded arguments, generated file contents, credential hygiene, and each request body's exact JSON structure. `deploy/scripts/tests/lakekeeper-local.test.sh` drives the real provisioning script against `docker-compose.lakekeeper.yml` and fails, never skips, when that stack is down. The bench toggle is verified by `bench/run.sh selftest`. The real AWS path is a manual verification step.
- **Alternatives:** One test script covering both. Rejected: the offline half must run with no network and no Docker, and merging them would make the cheap check depend on the expensive one. An automated end-to-end run in CI — rejected: the stack bills real money per run and needs cluster credentials CI does not hold.
- **Rationale:** `deploy/scripts/tests/install.test.sh` already establishes the stubbed-PATH pattern for a shell deliverable, down to the `pass`/`fail`/`assert_*` helpers (`install.test.sh:29-36`), wired into `make test-install`. The split into offline and Docker halves mirrors the split that file's own header documents between `make test-install` and the separate compose-based `install-script-e2e` CI job (`Makefile:217-219`).
- **Promotes to ADR:** no

### [14] `ConnectionCreds` gains no `Default` — SUPERSEDED by [26], now moot

- **Status:** MOOT under decision [26]. No Rust caller of `lakehouse-catalog` is added, so the question of whether `ConnectionCreds` needs a `Default` never arises. The outcome the decision protected is unchanged and now automatic: the shipped crate's public surface is untouched, and its reachability probe at `crates/lakehouse-catalog/tests/catalog_public_surface.rs` is not edited.
- **Decision (as reviewed, not implemented):** The provisioning tool constructs both of its `ConnectionCreds` values field by field in one place.
- **Alternatives:** Add `impl Default for ConnectionCreds` to `lakehouse-catalog`. Rejected: the field-absent defaults encode MinIO semantics (`path_style` true, `use_sigv4` false), so a `Default` would make a wrong-for-AWS credential set the easy one to write, and it would widen a public surface guarded by a reachability probe for one external caller's convenience.
- **Rationale:** Explicit construction at a single site is honest about what the tool sends and keeps the shipped crate's surface untouched.
- **Promotes to ADR:** no

### [15] The provisioning script names its two catalogs "source" and "target", not "Glue" and "Lakekeeper"

- **Status:** CARRIED FORWARD to the bash design, with one amendment recorded in decision [27]. The neutral naming survives; what changes is that the source's auth mode is no longer the only thing configuration selects, because the Glue reader and the Iceberg REST reader are now two different readers rather than two branches of one client.
- **Decision:** Every environment variable the script reads is prefixed `LK_SOURCE_` or `LK_TARGET_`, and the source reader is selected by configuration. `lakekeeper-up.sh` maps the environment's Glue values onto the source variables.
- **Alternatives:** Read `GLUE_*` and `LAKEKEEPER_*` directly, matching `bench/.env`. Rejected: nothing downstream of the source read depends on the source being Glue, and hardcoding the name would force a local verification run to set variables called `GLUE_*` while pointing them at Lakekeeper.
- **Rationale:** The neutral naming is what makes the derivation, warehouse, and registration path runnable against the existing local Docker Lakekeeper stack, which is the only way to falsify the register-by-reference assumption before spending money on EC2. The operator never types these variables — the up-script sets them from `data-stack`'s SSM parameters and this stack's own outputs.
- **Promotes to ADR:** no

### [16] The target warehouse's S3 flavor is derived from whether an endpoint is configured

- **Decision:** An empty target S3 endpoint means real AWS S3: the storage profile uses the AWS flavor with virtual-hosted addressing. A non-empty endpoint means an S3-compatible store: the profile uses the compatibility flavor with path-style addressing.
- **Alternatives:** Separate flavor and path-style variables. Rejected: three variables that must agree are three chances to disagree, and the endpoint alone already determines the answer.
- **Rationale:** Auto-detection over configuration. It also makes the local MinIO verification run and the AWS run differ by exactly one variable.
- **Promotes to ADR:** no

### [17] The `part`/`partsupp` collision does not reproduce, so the plan carries no mitigation for it

- **Decision:** No mitigation for the `part`/`partsupp` location collision is in this plan — no second warehouse, no per-table warehouse override, no excluded table. All eight TPC-H tables register into one warehouse under one warehouse name. The tool still classifies a location-already-taken rejection as its own named failure, separate from already-registered success, and task 4.1 keeps the collision pair as a permanent regression test.
- **Alternatives:** (a) Pre-commit a second Lakekeeper warehouse for the colliding table, with `bench/run.sh` and `secrets.sh` carrying a per-table warehouse override. Rejected: it contradicts the single-warehouse `bench/.env` and CONNECTION shape this plan fixes, and it is unnecessary complexity for a risk that does not manifest. (b) Exclude the colliding table from the demo set. Rejected outright: `bench/run.sh:442-443` unconditionally runs `check_count PART` and `check_count PARTSUPP`, and `bench/run.sh:559-562` runs NQ3 as `PART` joined to `PARTSUPP`, so a seven-table registration makes `make bench` fail rather than produce comparable numbers. (c) Defer the choice until task 4.1 runs. Superseded by the live verification below. (d) Treat every non-success 4xx on register as already-registered. Rejected: that would silently drop a table and report a complete registration.
- **Rationale:** A live run settled the question with the production location shape, not a synthetic one. **The run's exact conditions were: Lakekeeper 0.13.1, the local Docker stack, MinIO as the object store — therefore the S3-COMPATIBILITY storage flavor with path-style addressing — and the registration order `part` then `partsupp`.** An unauthenticated Iceberg REST catalog derived `s3://warehouse/tpch_src/part` and `s3://warehouse/tpch_src/partsupp` from its own default location rule — one location a non-slash-delimited prefix of the other. A Lakekeeper warehouse was then created over that same, already-populated `tpch_src` key prefix, and both tables registered by reference into its `tpch` namespace: HTTP `200` each, `partsupp` immediately after `part`, both listed afterwards by `GET .../namespaces/tpch/tables`. The upstream `LocationAlreadyTaken` report does not apply to this version, so the correct engineering answer is no code and no configuration. Two limits of this evidence are named rather than left implicit. First, the run used one registration order, so task 4.1 registers the pair in BOTH orders and the regression test does not inherit that gap. Second, the run used the S3-compatibility flavor, so the AWS flavor with virtual-hosted addressing is still unexercised — plan.md § Risks carries that as its own open bullet, first exercised by the manual AWS run. Task 4.1 keeps the pair as a regression test — the right shape of test for a risk resolved by verification — so a future Lakekeeper version that reintroduces the rejection fails on a laptop rather than on a billable cluster.
- **Promotes to ADR:** yes

### [18] The management API is addressed per its version-pinned contract, not per the rendered docs

- **Decision:** The bootstrap decision reads the server-info response's `bootstrapped` boolean; the Keycloak token is obtained before the first management call; the bootstrap body accepts the terms of use; the storage credential uses the canonical `access-key-id` and `secret-access-key` field names; the storage profile declares the AWS flavor and omits any STS role identifier.
- **Alternatives:** Follow the shapes `crates/lakehouse-engine/tests/common/lakekeeper.rs` and the rendered documentation use. Rejected in three specifics: the harness uses aliased credential field spellings, the server-info response's server id is always populated so it cannot stand in for the bootstrapped flag, and the published doc site is not pinned to the deployed image's version.
- **Rationale:** All five points were verified against the v0.13.1 source tree and its version-pinned OpenAPI document. Two are outright traps: an anonymous server-info call answers `401` once authentication is enabled, and an STS role identifier is required only when AWS-flavored vending is on, which this warehouse disables.
- **Promotes to ADR:** no

### [19] The catalog credential's IAM resources use an attached managed policy, never an inline user policy

- **Decision:** The stack builds the write-capable IAM user from `aws_iam_user`, `aws_iam_policy`, `aws_iam_user_policy_attachment`, and `aws_iam_access_key`, mirroring `deploy/data-stack/main.tf:94-136`. `aws_iam_user_policy` MUST NOT be used.
- **Alternatives:** An inline `aws_iam_user_policy`, the shortest way to express "a user with a policy". Rejected: `deploy/iam/deployer-policy.json` § `IamForEngineReaderAndInstanceProfiles` grants `iam:CreateUser`, `iam:CreateAccessKey`, `iam:CreatePolicy`, and `iam:AttachUserPolicy`, but no `iam:PutUserPolicy`, `iam:GetUserPolicy`, `iam:DeleteUserPolicy`, or `iam:ListUserPolicies`.
- **Rationale:** An inline policy fails with AccessDenied at apply time — after the EC2 instance is already billing, which is the worst moment for this stack to fail. The plan's "no IAM policy change" requirement only holds on the attached-managed-policy route, and `data-stack` already establishes it for the sibling `engine-reader` user.
- **Promotes to ADR:** no

### [20] Bucket-wide write is an accepted, named risk; the warehouse is soft-delete and the tool has no destructive path

- **Status:** CARRIED FORWARD with the scope of control 1 retargeted for bash, and WIDENED. The scanned artifact changes from `crates/lakekeeper-provision/src/` to the single file `deploy/scripts/lakekeeper-provision.sh`, and the ban now covers the AWS CLI's destructive verbs as well as HTTP `DELETE`, because bash reaches `aws s3 rm` and `aws s3api delete-object` from the same PATH as its read calls — a route the Rust design could not take without adding a dependency. The other three controls are unchanged.
- **Decision:** The catalog's storage credential grants object put, get, and delete plus bucket list across the whole `data-stack` bucket, recorded as a named, accepted risk. Where decision 5's provisioning-time prefix derivation conflicts with decision 6's apply-time IAM policy, **decision 6 yields**: the policy stays bucket-wide and the derivation is unchanged. ### [25] Credentials reach `curl` through a file descriptor, never through argv

- **Decision:** The rule binds EVERY process the script spawns, not `curl` alone: no credential appears in ANY spawned command's argv. The client secret, the bearer token, and the S3 key pair reach `curl` through a configuration read from standard input or a body supplied by process substitution, never a `-u`, `-d`, `--data`, `-H`, or URL-query token. A credential-bearing `jq -n` body reads its value from jq's ENVIRONMENT (`env.LK_TARGET_ACCESS_KEY_ID`, `env.LK_TARGET_SECRET_ACCESS_KEY`), never through `--arg` or `--argjson`. `set -x` appears nowhere in the script. Response bodies captured for classification go to a file under a `mktemp -d` directory removed by an `EXIT` trap, and are never printed on an error path.
- **Alternatives:** (a) `curl -H "Authorization: Bearer $token"`, the ordinary form. Rejected: argv is world-readable through the process listing, so any local user on a shared benchmark box can read the token while the request is in flight. (b) Write the credential to a temp file and pass its path. Rejected where avoidable: it puts the secret on disk, and a crash between creation and the trap leaves it there. Process substitution passes a pipe instead, so the argv shows only a `/dev/fd/` path and nothing is written. (c) Rely on the environment variable alone and interpolate it at the call. Rejected: interpolating into an argv token is exactly the exposure being avoided.
- **Rationale:** The plan already carried "no secret on stdout or in argv" as a hard requirement, but the Rust design satisfied it for free — `reqwest` takes a header as a function argument, so there was no argv to leak into. Bash has no such property, so the requirement needs a stated mechanism or it is decorative. The `set -x` ban matters for the same reason and is easy to violate by habit: `set -euxo pipefail` is a common reflex, and it prints every expanded command including the credential-bearing ones.

  **Interaction with decision [24], which this decision now resolves.** Decision [24] mandates `jq -n` for every request body, and the obvious form of that mandate — `jq -n --arg secret-access-key "$SECRET"` — reintroduces the exact exposure this decision exists to close: jq's `/proc/<pid>/cmdline` is world-readable on precisely the terms curl's is, so the warehouse body's S3 secret would sit in a process listing while the request is in flight. Scoping the rule to `curl` made the hole invisible to the test written to catch it. The fix is cheap and weakens neither decision: `jq` reads the environment, and `/proc/<pid>/environ` is owner-restricted, so a credential-bearing body uses `env.<VAR>` and every non-credential field keeps `--arg` with decision [24]'s well-formedness guarantee intact. The general rule is therefore stated over processes rather than over `curl`, and the offline harness stubs `jq` as a recording wrapper alongside `curl`, `aws`, `tofu`, and `ssh`, asserting no secret in any recorded argv from any of them. Without the `jq` stub the assertion cannot see the one body that carries the highest-value secret.
- **Threat model boundary, stated so it is not overclaimed:** this decision addresses a LOCAL observer — another user on the same machine reading `/proc`. It says nothing about a NETWORK observer, and the same credentials travel unencrypted to the box on a public-vantage run. Decision [28] records that separately as an accepted seam. The two are not in tension once both are on the record; they were only in tension while one was unstated.
- **Alternatives for the jq half:** (a) write the credential into a temp file and pass it to `jq --rawfile`. Rejected for the same reason temp files were rejected for `curl`: it puts the secret on disk. (b) Pipe a pre-built JSON fragment into `jq --slurpfile /dev/stdin`. Rejected as more machinery than `env.<VAR>` for the same result. (c) Keep `--arg` and narrow the claim to "no secret in curl's argv". Rejected: the threat is the process listing, and it does not care which binary is running.
- **Promotes to ADR:** yes

### [29] A register outcome is confirmed by a read-back, because Lakekeeper 0.13.1 cannot distinguish a location conflict from a name conflict by response text

- **Decision:** `register_table` no longer trusts response-text sniffing as the sole disambiguator between "already registered" and "location already taken". After ANY classification that is not already a definitive failure (a fresh `2xx`, or a `409` not otherwise identified), it performs a `loadTable` read-back of the just-registered table and compares the returned `metadata-location` against the value this run submitted. A match confirms the outcome; a mismatch becomes a new, distinct, always-failing outcome, `location-mismatch`. `response_reports_location_already_taken`'s text match is kept only as a documentation aid on top of this, not as the mechanism the exit code rests on.
- **Alternatives:** (a) Trust the response-text classification alone, as task 2.2 originally specified. Rejected — task 5.2's live verification against Lakekeeper 0.13.1 disproved it directly: registering a different table name at a location a live table already held returned `409 {"error":{"type":"AlreadyExistsException","message":"Tabular with the same name already exists in the namespace",...}}`, byte-identical in shape and wording to an ordinary already-registered re-run. Neither `location` nor `taken` appears in that body, so the regex cannot separate the two, and a real location collision with a different table would be silently folded into success — exactly the outcome the original requirement forbade. (b) Widen the response-text pattern to also catch this `AlreadyExistsException` shape. Rejected — that shape is ALSO the exact response an idempotent already-registered re-run produces, so widening the pattern would misclassify every legitimate repeat run as a failure instead.
- **Rationale:** This is the same problem decision [12] already solved for warehouse creation — a `2xx`/`409` status alone is not proof of the intended end state — and it gets the same answer: read the resource back and compare it against what this run expected, rather than parse a server's own error prose. The read-back is one additional bearer-authenticated GET per table (already-registered tables were already going to be the common case on a re-run, so this adds no new failure mode, only a stricter confirmation of success). Task 5.2's own round-trip verification already relies on exactly this technique — a post-register `loadTable` asserting the metadata pointer is unchanged — so this decision generalizes what the test already assumed into the tool itself, rather than leaving the tool weaker than the check that verifies it.
- **Refinement found during implementation:** live probing of Lakekeeper 0.13.1 turned up two distinct read-back-failure shapes, not one. Registering a target name already held at a DIFFERENT metadata-location (e.g. a moved source snapshot) reads back `200` with a stale pointer — `location-mismatch`. Registering a location already held under ANOTHER table name reads back `404 NoSuchTableException`, because the table was never created — `readback-http-<status>`. Collapsing both into one label would misreport the second case as "the location doesn't match" when the true state is "the table doesn't exist at all," sending an operator to look for a discrepancy that isn't there. Both are DISTINCT, always-failing outcomes, satisfying this decision's requirement without being the single outcome name originally assumed. `location-already-taken` (the original response-text classification) is kept in the `case` statement for a future Lakekeeper version that reports the conflict with distinguishing text, even though it is currently unreachable on 0.13.1 — every conflict that version reports arrives as `409`, which now routes through the read-back instead.
- **Promotes to ADR:** no — this is an implementation-level fix within an already-decided design ([12], [17]), not a new architectural choice.

### [live-verification] `aws_s3_object.keycloak_realm` failed a real `tofu apply` on the AWS S3 10-tag object limit
