# Plan Review Findings: add-lakekeeper-aws-perf-catalog (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 23 (Blockers: 9, Advisory: 14)
- Intent Fidelity blockers: 1

## Premortem

Three failure stories drove this review.

1. **Demo day, `partsupp` missing.** `lakekeeper-up.sh test1` applies, the tool reports "7 registered, 1 failed: location already taken", and `make bench` dies at `bench/run.sh:443` (`check_count PARTSUPP`) and query NQ3 (`bench/run.sh:559-562`, `PART` joined to `PARTSUPP`). Neither mitigation the plan names was pre-decided, and both break something the plan already fixed. Routed to Intent Fidelity and Feasibility.
2. **Second `up` run silently reuses a stale warehouse.** Warehouse creation answers `400 StorageProfileOverlap` for a *different* overlapping warehouse or a shifted prefix, the tool classifies it as already-present, and registration proceeds against a warehouse whose storage profile does not match the derived prefix. The cited source file warns about exactly this and the plan drops the warning. Routed to Requirement Quality.
3. **Blast radius on the one physical copy of the data.** A write-and-delete IAM credential scoped to the whole `data-stack` bucket, no stated delete profile, and a public-IP Keycloak whose admin credential and OAuth2 client secret are both repo-committed constants. Routed to Feasibility (NFR).

## Intent Fidelity

Certified where not challenged: `BENCH_CATALOG` defaults to `glue` with an unchanged require list, catalog URI, password builder, and VS properties (delta spec:23); no engine, adapter, catalog-crate, or CONNECTION-field change (verified: `lakehouse-catalog`'s public API already exposes `CatalogSession::resolve` at `src/session.rs:199`, `load_table_any_auth` at `src/session.rs:234`, and `ConnectionCreds` with all 17 fields `pub` at `src/creds.rs:28-58`, so the tool needs no widening); the four-container set and the ephemeral up/down lifecycle match both pre-confirmed user decisions (`docker-compose.lakekeeper.yml`, `deploy/trino-stack/`); no `deployer-policy.json` edit for EC2/S3/SSM (all three are `Resource: "*"` in `CoreInfra`).

#### [SCOPE_REDUCTION] BLOCKER
- Location: plan.md § Risks and open verification points, final paragraph; decision-log.md § [17]
- Issue: the plan defers the `part`/`partsupp` mitigation: "If the local test reproduces it, the mitigation is a scope decision (register under per-table prefixes, or exclude the colliding table from the demo set) that belongs in a follow-up rather than being pre-committed here." Both named options contradict commitments this plan already makes. "Exclude the colliding table" fails the benchmark outright: `bench/run.sh:442-443` unconditionally runs `check_count PART` and `check_count PARTSUPP`, and `bench/run.sh:559-562` runs NQ3 as `PART` joined to `PARTSUPP`, so a seven-table registration makes `make bench` fail rather than produce comparable numbers, and the user asked to register "the already-loaded TPC-H Iceberg tables". "Register under per-table prefixes" needs more than one warehouse (a warehouse has one `key-prefix`), which contradicts the single-warehouse CONNECTION shape the delta spec fixes (`bench/.env` carries one warehouse name, delta spec:35) and cannot be reached by moving data (§ Requirements "No data rewrite"). The plan therefore leaves a live branch whose every named outcome breaks a stated goal, on the one risk it admits is unresolved.
- Fix: In plan.md § Risks and open verification points and decision-log.md § [17], replace the deferral with a pre-committed mitigation that keeps all eight tables reachable under one warehouse name, and add a matching `*AND*` clause to the new feature spec's registration scenario. State the fallback order explicitly, for example: (1) if Lakekeeper's containment check treats a trailing path separator as the location boundary, no mitigation is needed and task 4.1 records that; (2) otherwise register the colliding table into a second Lakekeeper warehouse and extend the bench Lakekeeper arm plus `secrets.sh` to carry a per-table warehouse override. Name which one governs if task 4.1 reproduces the rejection, and add the corresponding task to plan.md § Implementation Tasks. Do not leave "exclude the colliding table" as an option without stating that it makes `make bench` fail at `bench/run.sh:442-443`.

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md § Risks and open verification points, third bullet; new feature spec, scenario "The catalog's storage credential is separate from the engine's read-only credential"; task 4.1
- Issue: warehouse creation on AWS happens over a prefix that already holds every TPC-H table's data and metadata. Every existing verification runs the opposite order. `crates/lakehouse-engine/tests/common/lakekeeper.rs:363-364` creates each warehouse with `"key-prefix": profile.name` over a freshly created MinIO bucket, so the prefix is empty at creation and the tables appear afterwards; task 4.1 as written has Lakekeeper create the throwaway tables, which again means warehouse first, data second. The two plan artifacts also describe the validation differently on the load-bearing point: plan.md:110 says the probe runs "under a random path inside the warehouse prefix, then asserts that prefix is empty", while the spec says "asserting the probe prefix is empty" (spec:119). Under plan.md's wording the AWS warehouse cannot be created at all. Nothing in either artifact states "warehouse creation succeeds over a prefix that already contains data" as an assumption, and no planned test exercises that ordering. A related hazard falls out of the same gap: decision 8 uploads the realm export "to the `data-stack` bucket as a managed object under a Lakekeeper-specific key" with no requirement that the key sit outside the derived warehouse prefix.
- Fix: In the new feature spec's warehouse scenario, add an explicit `*AND*` clause stating that warehouse creation SHALL succeed over a key prefix that already contains the source tables' data and metadata files, and that the probe object's random path is the only thing required to be empty after validation. Correct plan.md:110 to match that wording. Extend task 4.1 to pre-populate the target prefix with objects before creating the warehouse, so the AWS ordering is the ordering under test. Add a clause to decision 8 and to task 5.2 requiring the realm object's S3 key to be outside any prefix the tool can derive from the table locations.

#### [HIDDEN_DEPENDENCY] BLOCKER
- Location: plan.md § Implementation Tasks, task 4.1; new feature spec, Background bullet on local verification (spec:48-55)
- Issue: the one test guarding the one admitted risk is confounded and cannot distinguish the two hypotheses. Task 4.1 says "round-trip Lakekeeper-created throwaway tables through register-table into a second namespace, including a `part`/`partsupp`-shaped pair whose locations differ only by a non-slash-delimited suffix". The source tables still exist in that same warehouse and still own those exact locations, so a location-already-taken rejection is guaranteed by exact-location reuse alone, independent of whether the non-slash-delimited-prefix rule exists. A green run and a red run both prove nothing about the risk. There is also no positive control: nothing in the task registers a *non*-colliding pair through the same path, so a blanket failure cannot be separated from the specific collision.
- Fix: Rewrite task 4.1 in plan.md to (a) drop each throwaway source table from the source namespace without purging its files before registering it into the target namespace, so no live table holds the location, (b) assert a non-colliding pair registers successfully as the positive control, and (c) assert the colliding pair's outcome as the recorded result of the experiment. Mirror the drop-without-purge requirement in the new feature spec's local-verification Background bullet, and state there that a purge-drop MUST NOT be used because the same code path runs against shared data on AWS.

#### [NFR_IGNORED] BLOCKER
- Location: decision-log.md § [6]; new feature spec, scenario "The catalog's storage credential is separate from the engine's read-only credential"; plan.md § Architecture diagram ("TPC-H Iceberg tables, one copy")
- Issue: the blast radius of the new write credential is unbounded, and two decisions in this plan pull against each other. The spec grants "object put, get, and delete, plus bucket list ... scoped to the `data-stack` bucket and its objects", which is delete permission over every TPC-H data file the Glue path also depends on, on the plan's own account a single physical copy. It cannot be narrowed as written, because decision 5 derives the warehouse prefix at *provisioning* time while decision 6 creates the IAM policy at *apply* time, so the policy literally cannot name the prefix it is meant to cover. Separately, the design brief's `delete-profile: hard` is gone from both plan and spec with no decision recorded, and `crates/lakehouse-engine/tests/common/lakekeeper.rs:400` shows the existing harness sends `"delete-profile": {"type": "hard"}`, under which a drop-with-purge against a registered table would delete the shared source data. No artifact forbids a purge path or names the delete profile.
- Fix: Add a decision to decision-log.md and matching `*AND*` clauses to the storage-credential scenario that (a) name the warehouse's `delete-profile` explicitly and require the soft profile, stating that a hard profile plus register-by-reference puts the shared TPC-H copy one purge-drop away from deletion, (b) require that the provisioning tool has no drop or purge code path at all, and (c) bound the credential: either scope `s3:PutObject`/`s3:DeleteObject` to a stack-configured prefix and reconcile that with decision 5 by having the tool fail when the derived prefix falls outside it, or state bucket-wide write as an accepted, named risk with the compensating control spelled out. Record which of decision 5 and decision 6 yields.

#### [NFR_IGNORED] BLOCKER
- Location: new feature spec, scenario "Keycloak issues tokens both issuers accept"; task 5.3; decision-log.md § [2]
- Issue: the plan hardens two secrets and leaves the two that matter as repo constants on a box with a public IP. Task 5.3 and the spec require the AWS box to mirror `docker-compose.lakekeeper.yml`, which sets `KC_BOOTSTRAP_ADMIN_USERNAME=admin` / `KC_BOOTSTRAP_ADMIN_PASSWORD=admin` and runs Keycloak in `start-dev` over plain HTTP; the spec requires the OAuth2 client id, client secret, and audience to "be the values `scripts/keycloak-realm-iceberg.json` already defines", and that file's client secret is committed to the repository. The stack generates only the PostgreSQL password and the metadata-encryption key, and the spec's own clause "no generated secret SHALL appear in any script's standard output" shows secret hygiene is in scope. The security group is the sole control, and Keycloak's port is deliberately opened to the operator allowlist as well as the VPC CIDR. The user's confirmed decision was to *include* Keycloak, not to ship it unhardened.
- Fix: Add `*AND*` clauses to the Keycloak scenario requiring (a) the Keycloak bootstrap admin password to be stack-generated and stored as an SSM `SecureString`, never the compose file's literal, and (b) the OAuth2 client secret to be treated as a repo-committed, non-secret value: either state that in the spec and in `deploy/README.md` § Known seams as a named seam whose only control is the security group, or have the stack overwrite the realm's client secret with a generated value at boot and publish it through SSM. Extend task 5.3 accordingly, and add the assertion to task 8.1's shell harness.

#### [COMPLETENESS_GAP] BLOCKER
- Location: new feature spec, scenario "Provisioning bootstraps Lakekeeper and creates the S3-backed warehouse idempotently" (spec:160-165); decision-log.md § [12]
- Issue: the spec mandates treating `400` with a storage-profile overlap as already-present success, and cites `crates/lakehouse-engine/tests/common/lakekeeper.rs` as the source, but drops that file's own caveat. `lakekeeper.rs:395-399` reads: "Idempotent: Lakekeeper 0.13.1 reports an already-provisioned warehouse as HTTP 400 `CreateWarehouseStorageProfileOverlap`, NOT 409 ... For warehouses sharing a bucket/filesystem this is an unverified inference, so callers needing certainty should read the warehouse back via `lakekeeper_warehouse_storage_profile`". The name of the error is about *overlapping storage profiles*, not about an identical warehouse, so on a re-run whose derived prefix differs at all, or against any other warehouse in the same bucket, the tool swallows the 400 and then registers tables into a warehouse whose actual bucket and prefix it never confirmed. That is precisely the case the plan needs certainty for, since the whole design turns on the warehouse prefix matching the derived one.
- Fix: Add an `*AND*` clause to the warehouse scenario requiring that after any already-present classification the tool SHALL read the warehouse back and fail unless its storage profile's bucket and key prefix equal the derived values, naming both. Add the read-back to plan.md § Key interfaces "Provisioning order" and to task 3.2, and cite `lakekeeper.rs:395-399`'s caveat in decision-log.md § [12] as the reason.

#### [AMBIGUOUS_REQUIREMENT] ADVISORY
- Location: new feature spec:32-33 and :201-202
- Issue: the spec says the request body carries "an `overwrite` flag that defaults to false" and that the tool "SHALL leave the register request's overwrite flag at its default of false". In the pinned crate, `RegisterTableRequest::overwrite` is `Option<bool>` with no `skip_serializing_if` (`iceberg-catalog-rest-0.10.0/src/types.rs:309`), so `None` serializes as `"overwrite": null` on the wire rather than being omitted, and a server treating the field as a non-nullable boolean rejects it. The crate's own call site sends `Some(false)` (`catalog.rs:955-958`).
- Fix: Reword new feature spec:201-202 to require the flag be sent explicitly as false rather than left at a default, and note in :32-33 that `None` would serialize as an explicit JSON null because the field carries no `skip_serializing_if`.
