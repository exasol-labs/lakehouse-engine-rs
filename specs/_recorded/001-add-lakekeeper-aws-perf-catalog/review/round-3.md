## Premortem

Three failure stories drove this review.

1. **Demo day, dead connection.** The operator runs the repo's own documented one-command remote sequence, `AWS_PROFILE=... ./bench-remote.sh test1`. The benchmark completes, `trap teardown EXIT` fires, `cluster-down.sh test1` destroys the Exasol cluster, and the virtual schema and CONNECTION the demo was going to query go with it. `selftest: vs_teardown_is_recreate_only` passed, because it only reads `bench/run.sh`'s own text. Routed to Feasibility.
2. **The write credential on the wire.** Every `lakekeeper-up.sh` run from a laptop POSTs the warehouse body — carrying the dedicated S3 **write-and-delete** secret access key — to a public IP over plain HTTP, along with the OAuth2 client secret and the bearer token. Decision [25] spends four alternatives keeping those values out of a process listing readable by local users, while the same values cross the public internet in cleartext. Routed to Feasibility (NFR).
3. **Benchmark night, nothing starts.** The EC2 orchestrator the architecture diagram names has no stack, no task, no prerequisites, and no source for its `LK_*` values or its region; and the URIs `lakekeeper-up.sh` is specified to hand the provisioning script are the PUBLIC-IP ones, the vantage decision [7] exists to keep a same-VPC caller away from. Routed to Feasibility and Requirement Quality.

#### [NFR_IGNORED] BLOCKER
- Location: `aws-lakekeeper-perf-catalog` spec:288 and spec:315-318; `decision-log.md` [7] § Decision and [25]; `plan.md:35-71` § Architecture
- Issue: the plan transmits its highest-value secret in cleartext over the public internet and never names the risk. Spec:288 states the target is "reachable over plain HTTP at its management endpoint"; spec:315-318 requires the warehouse-creation body to carry "the dedicated write-capable key pair under the canonical `access-key-id` and `secret-access-key` field names"; decision [7] states "`lakekeeper-up.sh` passes the PUBLIC-IP URIs to the provisioning tool, because the consumer is the operator's machine". Combined: on every laptop-driven `lakekeeper-up.sh`, the S3 write-and-delete secret key, the OAuth2 client secret, and the resulting bearer token travel unencrypted from the operator's network to an EC2 public IP. Grepping all three artifacts for `TLS`, `https://`, `cleartext`, and `tunnel` returns no hit for the Lakekeeper endpoints — the only plaintext discussion (`cloud-e2e-harness` spec:10, spec:42) scopes it to "plain HTTP **inside the VPC**", which is not the vantage decision [7] assigns the provisioning script. The security-group `/32` allowlist controls who may connect, not who may observe traffic in transit. The three Known-seams entries task 6.1 records (static credentials, repo-committed client secret, bucket-wide write grant) do not include this one, so the plan's own risk register is incomplete on the largest item.
- Fix: Add an `*AND*` clause to the storage-credential scenario in `aws-lakekeeper-perf-catalog` spec requiring the provisioning script's target endpoints to be reached over a private-IP or tunnelled path, OR — if the cleartext public path is accepted — recording it as a fourth NAMED, ACCEPTED SEAM that states exactly which credentials cross the public internet unencrypted. Add the matching entry to task 6.1's `deploy/README.md` § Known seams list and to `plan.md` § Impact. Add a decision to `decision-log.md` recording which of the two routes was chosen and why, beside decision [25], whose argv threat model this contradicts.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `aws-lakekeeper-perf-catalog` spec:56-62; `plan.md:110` § Consequences; `decision-log.md` [27] § Alternatives (a)
- Issue: the rejection of `curl --aws-sigv4` is stated as a verified hard constraint — "it requires `--user <access-key>:<secret-key>` and emits no `x-amz-security-token` header, so it cannot use the temporary credentials an EC2 instance profile supplies" — and is recorded that way in a spec Background bullet that will enter the permanent library. The claim is unverified and questionable: curl 8.14.1's `--aws-sigv4` documentation says nothing about session tokens either way, and curl's signer includes caller-supplied headers carrying the provider prefix (`x-amz-`) in the canonical header set, which is the documented community workaround (`-H "x-amz-security-token: $AWS_SESSION_TOKEN"`). I could not confirm or refute it without a live signed call, which is exactly the state the claim should be recorded in. The decision itself survives regardless: decision [25]'s argv rule independently rules out `--user <key>:<secret>`, and the plan's other claim here does check out — no `--aws-sigv4` call exists in this repo's shell today.
- Fix: Rewrite `aws-lakekeeper-perf-catalog` spec:56-62 and decision [27] § Alternatives (a) to lead with the verified reason — `--aws-sigv4` requires the secret in a `--user` argv token, which decision [25] forbids outright — and demote the session-token claim to an explicitly unverified secondary note, or verify it and cite the evidence.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `plan.md:142` § Requirements row "No secret on stdout or in argv" vs `plan.md:187` task 2.2; `decision-log.md` [24] vs [25]; `aws-lakekeeper-perf-catalog` spec:270-278; `plan.md:193` task 5.1
- Issue: two of the plan's own normative rules cannot both be satisfied for the one request body that carries a secret. `plan.md:142` states the requirement without qualification — "Every credential travels by environment variable, SSM `SecureString`, or a `curl` file descriptor" — while task 2.2 mandates "EVERY request body MUST be built with `jq -n --arg` … `--data @<(jq -n ...)` for the warehouse body that carries the S3 secret key". `jq -n --arg secret-access-key "$SECRET"` places the secret in **jq's** argv, world-readable through `/proc/<pid>/cmdline` exactly as a `curl -H` token would be. Decision [25]'s stated threat — "argv is world-readable through the process listing, so any local user on a shared benchmark box can read the token while the request is in flight" — applies unchanged to the jq process. The spec's clause (spec:270-273) and the offline harness's assertion (task 5.1: "no stubbed-`curl` argv token ever contains a secret value") are both scoped to `curl`, so the hole is not merely unaddressed, it is invisible to the test that exists to catch it. The fix is cheap and does not weaken decision [24]: `jq` reads the environment through `env`/`$ENV`, and `/proc/<pid>/environ` is owner-restricted where `/proc/<pid>/cmdline` is not.
- Fix: Amend `aws-lakekeeper-perf-catalog` spec:270-278 so the no-argv rule names EVERY process the script spawns, not `curl` alone, and require any credential-bearing `jq -n` body to read the value from the environment (`env.LK_TARGET_SECRET_ACCESS_KEY`) rather than through `--arg`. Amend `plan.md` task 2.2 to state that construction for the warehouse body. Amend `plan.md` task 5.1 so the harness stubs `jq` as well as `curl` and asserts no secret value in any recorded argv from either. Record the interaction in decision [25] § Rationale, since decision [24]'s `jq -n --arg` mandate is what introduces it.

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `decision-log.md` [7] § Decision vs [23] § Decision; `aws-lakekeeper-perf-catalog` spec:110-113 vs spec:242-263
- Issue: the two-vantage rule and the two-run-site rule contradict each other, and no artifact resolves which URI the EC2 run uses. - Fix: Add an `*AND*` clause to the run-site scenario in `aws-lakekeeper-perf-catalog` spec stating that the target URIs are a property of the RUN SITE, not of the caller — private-IP from inside the VPC, public-IP from outside — and that the script reads them from `LK_TARGET_*` without deriving or rewriting them. Amend decision [7] § Decision so the vantage rule is keyed on where the caller runs rather than on which script invokes it, and cross-reference decision [23].
