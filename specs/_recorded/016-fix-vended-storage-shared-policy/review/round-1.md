## Intent Fidelity

The issue's target shape — shared `scheme_of`, `location_host`, ADLS account-name extraction, and shared `s3_backend`/`adls_backend` in `storage.rs`, both applying the gates — is reproduced literally in plan.md § Key interfaces. The interview's two decisions are honoured: CONNECTION-wins-when-set is stated per field in decision-log [1] and in every affected scenario, and no "vended wins" phrasing survives anywhere in the artifacts (grep-verified). One plan, not two: the mechanical share and the policy change land in one plan.md with one task list and one Parallelization graph, not two plans wearing one file. The two named defects are verified real against the code — `adls_from_vended` (`crates/lakehouse-catalog/src/unity/vended.rs:178`) takes no `allow_http`, and `AwsTempCredentials` (same file, lines 43-50) declares no region field, so `s3_from_vended` can emit `StorageBackend::S3` with `region: String::new()` and no endpoint.

#### [SCOPE_REDUCTION] ADVISORY
- Location: plan.md § Non-Goals; decision-log.md § Design Decisions [2]
- Issue: The issue defines addressing as `endpoint`, `region`, **and** `path_style`, and says a CONNECTION-configured value may "participate in addressing". The interview answer likewise closes with "unless a `path_style`/`s3.path-style-access` value is explicitly stated". The plan implements only two of the three: `path_style` never reads the CONNECTION, so the CONNECTION half of that clause is permanently unreachable, and plan.md § Non-Goals fences the enabling change out ("widening `ConnectionCreds.path_style` to an `Option<bool>`"). The type limitation is real and verified — `parse_creds` at `crates/lakehouse-engine/src/adapter/connection.rs:294-297` is exactly `json.get("path_style").and_then(|v| v.as_bool()).unwrap_or(true)`, discarding presence — but the rejection's cost is overstated: `storage_block` (same file, line 356) reads `creds.path_style` at exactly one production site, so `Option<bool>` there plus `.unwrap_or(true)` preserves the shipped `true` default byte for byte, and the remaining ripple is test-literal churn. No behaviour regresses either way (today's vended path already ignores a CONNECTION `path_style`), which is why this is advisory rather than blocking.
- Fix: In decision-log.md [2] § Alternatives, replace the ripple-cost sentence with the measured cost — one production read site (`storage_block`, `crates/lakehouse-engine/src/adapter/connection.rs:356`) plus `ConnectionCreds` literals in the suites — and state explicitly that the interview clause "unless a `path_style` … value is explicitly stated" is implemented for the vended `s3.path-style-access` half only and deliberately not for the CONNECTION half. Add that scoping sentence to plan.md § Non-Goals beside the existing bullet.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md § Impact, fourth bullet ("**Tightened — a plaintext CONNECTION `endpoint` reaching a vended S3 store now requires `ALLOW_HTTP`.**")
- Issue: The bullet's justification is factually wrong, and it is the justification that makes the bullet non-breaking. It reads "Such a CONNECTION previously either hit the deleted address error or fell through to the AWS default, so no working configuration regresses." Today `s3_backend_from_vended` (`crates/lakehouse-catalog/src/vended.rs:114-168`) reads the endpoint from `vended_config_value(vended, "s3.endpoint")` **only** — the CONNECTION's `endpoint` is never read on the vended path, so it neither triggers the address error nor reaches the AWS default; it is simply ignored. Therefore a CONNECTION carrying `use_vended_credentials: true`, a stale plaintext `endpoint` (e.g. `http://minio:9000`, the default shape of every MinIO CONNECTION in this repo's own fixtures), and `ALLOW_HTTP` false works today whenever the response vends an HTTPS `s3.endpoint` or a `client.region` — and becomes a plan-time `UdfError::User` after this change. Under `ALLOW_HTTP = 'true'` the same configuration silently redirects the store from the vended endpoint to the stale CONNECTION one, failing at read time instead. Neither failure mode appears in § Impact or § Migration, so the approver is told a regressing class does not exist.
- Fix: Rewrite plan.md § Impact's fourth bullet to state the real prior behaviour (a CONNECTION `endpoint` was ignored outright on the vended path, never read) and name both new failure modes: a plaintext CONNECTION `endpoint` under `ALLOW_HTTP` false is now a plan-time refusal on a configuration that worked, and under `ALLOW_HTTP` true the store address moves from the vended endpoint to the CONNECTION's. Delete the clause "so no working configuration regresses". Add a matching row to plan.md § Migration: `CONNECTION endpoint ignored under vending` → `CONNECTION endpoint wins; clear it to keep the vended endpoint`.

Otherwise no objection — axis checked: `resolve_file_list` returns the effective `StorageBackend` (`crates/lakehouse-engine/src/adapter/pushdown/file_resolution.rs:176-327`), and `file_resolution_tests.rs:991-1004` already drives it against a single-shot loopback catalog, so every task the plan proposes is buildable and observable with machinery that exists; `probe_vended_credential` already receives `creds: &ConnectionCreds` (`crates/lakehouse-engine/tests/e2e_lakekeeper_test.rs:660-663`), so task 6.2 needs no new plumbing; `speq plan validate fix-vended-storage-shared-policy` passes with warnings only; no new dependency is required.

#### [COMPLETENESS_GAP] BLOCKER
- Location: decision-log.md [5]; `vs-adapter/storage-backend-enum/spec.md` clause 49; `vs-adapter/catalog-crate-structure/spec.md` clause 21
- Issue: The plan supersedes a signature-level credential guarantee and promises a strictly checkable replacement — decision-log [5]: "A type that cannot carry a credential plus a probe over its declaration is strictly checkable". Only half of the replacement is checkable. The struct is specified with **public** fields (`pub struct StaticStoreAddress { pub endpoint: String, pub region: String }`) plus a `Default` impl, so any module in either crate may write `StaticStoreAddress { endpoint: <anything>, region: <anything> }` or mutate a `Default`. The probe of task 5.3 inspects the struct's **declaration** for credential-spelled field names; it cannot see what flows into a `String` field named `endpoint`. The clause that actually carries the guarantee — "the type SHALL have EXACTLY ONE construction from the CONNECTION" (storage-backend-enum 49) and "the conversion from `ConnectionCreds` SHALL be the ONE place that decides which CONNECTION fields are permitted to cross into vended resolution, so no call site builds that value field-by-field" (catalog-crate-structure 21) — is normative in two specs, has no task, no test, and no type-level mechanism. The plan's own standard ("Superseding them without a replacement mechanism would leave the guarantee as prose") is not met for that half.
- Fix: Choose and encode one enforcement mechanism. Either (a) make the two fields private and add `pub fn endpoint(&self) -> &str` / `pub fn region(&self) -> &str`, so `From<&ConnectionCreds>` and `Default` are the only constructions the type admits, or (b) keep the fields public and add a source-level probe asserting no `StaticStoreAddress {` struct-literal appears in any production source outside `crates/lakehouse-catalog/src/storage.rs` (covering both `CATALOG_SOURCES` and the engine call sites). Record the choice in decision-log [5] § Decision, add it as a numbered task under plan.md § Implementation Tasks 5, and add its test name to plan.md § Verification > Scenario Coverage.

## Design Depth

#### [SHALLOW_DESIGN] ADVISORY
- Location: decision-log.md [7] § Rationale; `vs-adapter/storage-backend-enum/spec.md` clauses 36-37
- Issue: The per-selector `VendedBackendKind`-dispatch probe is justified by a claim the compiler already discharges. Decision-log [7] rejects repointing to `storage.rs` alone because that "stops forcing each selector to dispatch every kind, which is weaker than today's gate", and clause 36 promises "a third vended kind still forces BOTH selectors to dispatch it". Both selectors match exhaustively on `Option<VendedBackendKind>` (`vended.rs:49-65`, `unity/vended.rs:112-121`), so adding a third `VendedBackendKind` variant already breaks both builds — with or without the probe. The probe's only marginal value is preventing a collapse to a `Some(kind) => …` catch-all, which is not what the rationale claims. Compounding this, the set-equality probe of clause 37 pins `VendedBackendKind`'s variant set permanently equal to `StorageBackend`'s, which makes `VendedBackendKind` a mirror maintained by a test rather than a distinct concept — and the mirroring is not obviously right, since `TemporaryTableCredentials` already declares a `gcp_oauth_token` field, so a future GCS `StorageBackend` variant would be forced into `VendedBackendKind` whether or not the Iceberg REST path vends it.
- Fix: In decision-log.md [7] § Rationale, replace the "forces BOTH selectors to dispatch it" claim with the accurate one — Rust's exhaustive match on `Option<VendedBackendKind>` already forces both arms, and the probe's marginal value is forbidding a catch-all collapse — and amend `vs-adapter/storage-backend-enum/spec.md` clause 36 to state that narrower purpose. In [7] § Alternatives, add the option of deleting `VendedBackendKind` in favour of the compiler-enforced match plus the construction probe, and record why the mirror is kept.

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: decision-log.md [6]; `vs-adapter/unity-catalog-vended-credentials/spec.md`, "A plaintext abfs:// location" scenario
- Issue: Moving the `abfs` gate from before extraction to inside `adls_backend` changes which error a doubly-invalid input produces, and no artifact records it. The existing suite does not catch it: `unsatisfied_vended_request_errors_without_static_fallback` (`vended_tests.rs:1151`) uses `satisfiable_sas` for its `abfs` block and `abfss_anchor` for its missing-SAS blocks, so both keep passing.
- Fix: Add a Rationale sentence to decision-log.md [6] stating the accepted trade-off — the gate now runs after credential extraction, so an extraction failure masks the plaintext refusal on an `abfs://` location with no usable credential — and add a clause to the `vs-adapter/unity-catalog-vended-credentials/spec.md` "A plaintext abfs:// location is honored only with operator consent" scenario fixing the precedence explicitly (either "an extraction error takes precedence over the plaintext refusal" or the reverse), with the corresponding case listed in plan.md § Test Disposition.

Otherwise no objection — axis checked against the Quick Diagnostic: the shared home is the enum's own module, so the "which module may name a variant" decision keeps exactly one owner and the recorded exhaustive list genuinely shrinks (verified: `specs/vs-adapter/storage-backend-enum/spec.md:156` records SIX, and removing both vended selectors leaves precisely the four the delta names — `storage.rs`, `scan/object_store.rs`, `storage_block` in `crates/lakehouse-engine/src/adapter/connection.rs:336`, and `CommonScanSpec`'s `impl Default` in `scan/spec.rs`); the extract-normalise-construct seam puts the fork at the wire boundary where the two inputs genuinely differ (flat `HashMap` with longest-prefix selection vs typed `TemporaryTableCredentials`), and decision-log [3] rejects unifying extraction behind a trait for the right reason; dependency direction holds, since `ConnectionCreds` and `StaticStoreAddress` both live in `lakehouse-catalog` and no catalog source names `lakehouse-engine`; `vs-adapter/pushdown-module-structure` is correctly left alone — its only two claims about this area (`resolve_vended_storage` MUST NOT join the façade, and stays reachable as `lakehouse_catalog::resolve_vended_storage`, lines 84 and 112) both survive, and the façade item counts frozen at line 200 are untouched because `file_resolution.rs` imports from `lakehouse_catalog` directly.
