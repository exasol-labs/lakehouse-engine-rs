## Design Decisions

### [1] Root cause of the `SUM(col*col)` gap is missing capability advertisement, not missing machinery

- **Decision:** Fix the two-column arithmetic aggregate gap by advertising the arithmetic binary-operator capabilities (`FN_ADD`/`FN_SUB`/`FN_MULT`/`FN_FLOAT_DIV`) and reconciling the translator's operator-name matching, reusing the existing expression-argument SUM partial/merge machinery unchanged.
- **Alternatives:** (a) Assume the vs-expression translator lacked binary-arithmetic support and build it — rejected: reading the code showed lib.rs already renders `ADD/SUB/MUL/FLOAT_DIV` and `arg_column_or_expr` already carries any renderable argument. (b) Build a dedicated two-column-product decomposition path — rejected as a redundant new subsystem; `AggKind::Sum` + `arg_expr` already covers it.
- **Rationale:** The blocker is that Exasol never *pushes* an aggregate whose argument uses an unadvertised operator; it requests raw operand columns instead. Advertising the operators unblocks the already-built path. This is the smallest sound change.
- **Promotes to ADR:** yes

### [2] Operator-name reconciliation (`MUL` vs `MULT`) must be verified live before coding

- **Decision:** Make live `EXPLAIN VIRTUAL` capture of the exact Exasol `function_scalar` name for `*`/`+`/`-`/`/` (task 1.1) a hard gate on the translator/capability change, and keep the capability set and the translator's matched-name set in lockstep.
- **Alternatives:** Trust the existing unit tests / scalar-ops spec, which use `"MUL"` — rejected: those tests used hand-crafted JSON and the arithmetic ops were never exercised live (they were unadvertised), so the assumed name is unverified. A wrong name silently degrades to row-scan fallback (correct but no speedup).
- **Rationale:** The whole perf win hinges on the translator recognizing what Exasol actually sends. Verifying first avoids shipping an advertised-but-declined operator.
- **Promotes to ADR:** yes

### [3] DECIMAL two-column-product partial type is derived from the declared SUM type, not the operands

- **Decision:** Size the partial/merge column from the SUM item's declared `selectListDataTypes` result type via the existing `col_type_for`/`sum_emit_type`, widening DECIMAL to `DECIMAL(36,s)`; verify it stays within Exasol's `DECIMAL(p<=36,s<=36)` limits and does not overflow per-shard partial sums.
- **Alternatives:** Derive the product type from the two source columns' types in the adapter — rejected: duplicates Exasol's own type inference, risks divergence from the positional `selectListDataTypes` validation Exasol enforces, and the machinery already reads the declared type for single-column expression arguments.
- **Rationale:** Exasol's declared result type is authoritative and already the sole source for expression-argument aggregates; reusing it keeps one code path.
- **Promotes to ADR:** no

### [4] Parallelism-factor sweep is evidence-gated with a no-op as an acceptable outcome

- **Decision:** Ship the sweep (factor 8/16/24 vs Q2/Q3/Q5 + Q9b regression) as an explicit validation task that precedes any default change; record the finding either way; only change `bench/.env` / `resolve_parallelism_factor` (and add a `parallelism/work-unit-sharding` delta) if the evidence is a real, repeatable improvement without a Q9b regression.
- **Alternatives:** Hardcode `BENCH_PARALLELISM_FACTOR=16`/change the code default now — rejected: the diagnostic flagged the 10-30% gain as UNVERIFIED (plausible only if emit-ack-latency-bound; zero if CPU-decode-bound). `bench/.env` currently pins `8`, defeating the code's own `max(cores*2,8)=16` oversubscription default.
- **Rationale:** Changing a parallelism default without evidence is speculative and could regress non-join queries. A validated no-op is a legitimate, documented result.
- **Promotes to ADR:** yes

### [5] New bench queries are bench-script-only, not a spec feature

- **Decision:** Wire NQ1-NQ5 into `bench/run.sh` + `trino_compare.sh` + `athena_compare.sh` + `spark_queries.py` as bench-harness tasks with `selftest` + `pushdown_check` verification, with no spec feature.
- **Alternatives:** Author a `packaging` spec feature for the bench harness — rejected: the repo explicitly treats the bench harness as "NOT a spec feature" (sweep.sh header) and separate from CI `make test-e2e` (README), so adding a spec feature would break that established convention.
- **Rationale:** Follow the codebase's own tracking convention; keep the bench harness a manually-invoked perf tool.
- **Promotes to ADR:** no

### [6] Scope held to SUM only; join-shaped and high-cardinality queries deliberately untouched

- **Decision:** Limit the code fix to `SUM(col OP col)`; make no spec delta for Q2/Q3/Q5 (structural, join-pushdown-only) or Q7 (inherent 45M-group shuffle both engines pay).
- **Alternatives:** Extend to COUNT/AVG/MIN/MAX arithmetic arguments — allowed only if the shared `arg_column_or_expr` seam makes it trivially free; otherwise deferred. "Optimize the join" — rejected: PROFILE evidence shows Exasol's join execution is already correct.
- **Rationale:** Matches the required scope and mission.md's join-pushdown non-goal; avoids re-litigating structural losses.
- **Promotes to ADR:** no

### [7] Live capture (task 1.1): arithmetic ops are not observable via EXPLAIN VIRTUAL until advertised — naming resolved indirectly via FN_MOD

- **Setup:** Ran `EXPLAIN VIRTUAL` for the exact NQ1 shape (`SUM(l_extendedprice * l_discount)` with the NQ1 filters) plus ad-hoc `SUM(l_extendedprice OP l_discount)` probes for `+`, `-`, `/` against the live `TPCH` virtual schema on test1 (2-node Glue/Iceberg `lineitem`, already provisioned from prior bench runs — no new infra stood up).
- **Finding A — chicken-and-egg confirmed, all four operators fall back identically:** None of `*`, `+`, `-`, `/` appear as a `function_scalar` node in the pushdown JSON. Because `FN_ADD`/`FN_SUB`/`FN_MULT`/`FN_FLOAT_DIV` are not in the adapter's advertised capability list, Exasol's optimizer never constructs a scalar-function pushdown node for them at all — it silently falls back to projecting the two raw operand columns (`L_EXTENDEDPRICE`, `L_DISCOUNT`) unchanged and evaluates the arithmetic + `SUM` locally in Exasol. This reproduced byte-for-byte identically for `*`, `+`, `-`, `/` (same `selectList`, same fallback shape) — i.e., the literal `function_scalar` name Exasol *would* send for these operators is fundamentally not observable by capturing the current adapter's live traffic, since advertising the capability is the precondition for ever seeing the node.
- **Finding B — naming convention established via `FN_MOD` (already advertised):** Ran `EXPLAIN VIRTUAL SELECT MOD(l_extendedprice, l_discount) FROM TPCH.LINEITEM WHERE l_quantity < 24`. Since `FN_MOD` **is** advertised, Exasol *did* push it, and the pushdown JSON's `selectList` contained exactly `{"type":"function_scalar","name":"MOD","arguments":[...]}`. This proves the operating convention: capability `FN_<X>` corresponds 1:1 to `function_scalar` node name `"<X>"` (the capability name with the `FN_` prefix stripped, nothing renamed). Cross-checking the codebase: `crates/vs-expression/src/lib.rs` already matches `"ADD"`, `"SUB"`, `"FLOAT_DIV"`, and `"MOD"` — all following this exact convention — but matches multiplication as `"MUL"` (line 345), which is the *only* outlier. Given `FN_MULT` is the capability name (not `FN_MUL`), the convention says Exasol will send `"MULT"`, not `"MUL"`. **Conclusion: `"MUL"` is confirmed wrong and must become `"MULT"` in task 1.3.** `ADD`/`SUB`/`FLOAT_DIV` need no renaming.
- **Finding C — DECIMAL type inference for the two-column product (native-SQL type probe, since the VS path can't produce it while `FN_MULT` is unadvertised):** Created a throwaway scratch schema/table (`SCRATCH_TYPE_PROBE.T(A DECIMAL(15,2), B DECIMAL(15,2))`, no data needed — type inference is schema-only) and inspected `EXA_ALL_COLUMNS.COLUMN_TYPE` on views over real (non-constant-folded) column references, then dropped the schema:
  - `A * B` → **`DECIMAL(30,4)`** (precision doubles 15+15=30 capped under 36, scale doubles 2+2=4)
  - `A + B` / `A - B` → `DECIMAL(16,2)` (precision +1, scale unchanged)
  - `A / B` → **`DOUBLE`**, not `DECIMAL` — Exasol's `/` on two DECIMALs promotes to float, which is exactly why the capability/node is named `FLOAT_DIV` rather than `DIV`
  - `SUM(A * B)` → **`DECIMAL(36,4)`** — precision widened to Exasol's max (36), scale held at the product's natural scale (4, not 2). This directly confirms decision [3]'s "widen to `DECIMAL(36,s)`" and pins `s=4` for the NQ1 shape (`L_EXTENDEDPRICE`/`L_DISCOUNT` are both `DECIMAL(15,2)`), well within the `DECIMAL(p≤36,s≤36)` limit.
  - `MOD(A,B)` (captured live via the VS, Finding B) → `DECIMAL(15,2)`, i.e. same as the operand type (unlike `*`/`+`/`-`, no widening) — noted for contrast, not used by this plan.
- **Rationale:** task 1.1 as literally scoped ("observe the exact name live") is structurally unsatisfiable for an unadvertised capability — Exasol won't generate the node to observe. The `FN_MOD`-based convention proof plus the native-SQL DECIMAL-inference probe together give the same evidentiary strength (verified against the live cluster's actual Exasol version/behavior, not assumed from memory) without requiring a speculative capability deploy. This unblocks 1.2/1.3/1.4 with verified facts instead of assumptions.
- **Impact on downstream tasks:** 1.2 should advertise `FN_ADD`, `FN_SUB`, `FN_MULT`, `FN_FLOAT_DIV` (capability names already correctly cased in the plan). 1.3 must rename the `"MUL"` match arm to `"MULT"` in `crates/vs-expression/src/lib.rs:345` and its rendering arm (`"MUL" => "*"` → `"MULT" => "*"`); `"ADD"`/`"SUB"`/`"FLOAT_DIV"` are unchanged. 1.4 should assume/verify the declared `selectListDataTypes` for `SUM(L_EXTENDEDPRICE * L_DISCOUNT)` arrives as `DECIMAL(36,4)` once `FN_MULT` is advertised, and that the widening path (`col_type_for`/`sum_emit_type`) handles a product scale of 4 (not just 2) correctly.
- **Promotes to ADR:** yes

### [8] (task 1.3) Lockstep enforced translator-side; cross-crate runtime assertion deferred until 1.2 lands

- **Decision:** Renamed the `"MUL"` match/rendering arm to `"MULT"` in `crates/vs-expression/src/lib.rs` (the only outlier; `ADD`/`SUB`/`FLOAT_DIV` already matched the live vocabulary per decision-log [7]), updated the hand-crafted `renders_arithmetic_mul` fixture to `"MULT"` (no dead `"MUL"` fixture left), and added: a two-column-product render test (`("L_EXTENDEDPRICE" * "L_DISCOUNT")`), a `legacy_mul_name_is_not_recognized` regression guard (obsolete `"MUL"` must fall back, not translate), and `arithmetic_operator_set_matches_advertised_capabilities` — a translator-side lockstep table asserting each of `FN_ADD`/`FN_SUB`/`FN_MULT`/`FN_FLOAT_DIV` minus its `FN_` prefix is the node name the translator renders (`+`/`-`/`*`/`/`).
- **Why the lockstep test lives in `vs-expression`, not `capabilities.rs`:** at the time 1.3 ran, task 1.2 was incomplete — the `FN_ADD`/`FN_SUB`/`FN_MULT`/`FN_FLOAT_DIV` test assertions existed in `capabilities.rs` (lines 260, 473) but the `CAPABILITIES` const did NOT yet contain those entries, so 1.2's own capability tests were failing (red). `capabilities.rs` is 1.2's file and was being edited concurrently, so 1.3 did not touch it (scope + edit-conflict risk). The verified capability names (`FN_MULT`, etc.) were taken as fixed inputs from decision-log [7] and confirmed by reading `capabilities.rs` directly.
- **Deferred (TODO-free, tracked here):** the *authoritative* cross-crate lockstep — a test in the `lakehouse-engine` crate that reads `capabilities::CAPABILITIES` at runtime, filters the arithmetic `FN_*` entries, strips `FN_`, and asserts `vs_expression::render_expression` renders each as a binary operator (and that no unadvertised arithmetic arm exists) — should be added once 1.2 populates the const. Until then the two halves are kept in sync by construction: the translator-side table above plus 1.2's `CAPABILITIES`-membership assertions. `lakehouse-engine` already depends on `vs-expression` (path dep), so the runtime assertion is mechanically straightforward when 1.2 is green.
- **Promotes to ADR:** no

### [9] (task 1.6) Raw-scan projection regression fixed with an explicit `ProjectionItem` tag, mirroring `AggregatePlan`'s `column`/`arg_expr` split — not a syntactic heuristic

- **Root cause (verified, not assumed):** Confirmed by reading `extract_projection` (`adapter/pushdown.rs`): a `"column"` select-list node pushes the bare uppercase name (e.g. `SCORE`) into `proj_names`, while a `function_scalar`/`predicate_*` node pushes `render_expression_safe`'s rendered fragment (e.g. `("SCORE" * 2)`) into the SAME `Vec<String>` — the two kinds were structurally indistinguishable downstream. `scan/mod.rs::build_scan_sql` then treated EVERY `spec.projection` entry as a bare identifier: `quote_ident(&col_name.to_uppercase())` wrapped the whole fragment, producing `"(""SCORE"" * 2)"` — a phantom column name. Reproduced live before fixing: `e2e_selectlist_expression_pushdown` failed with `F-UDF-CL-RUST-9001 ... Schema error: No field named "(""SCORE"" * 2)". Valid fields are "ID","NAME","SCORE","EVENT_DATE","EVENT_TS"`. The EMITS side (`build_row_scan_sql`) was already correct because emission is positional — the ugly quoted name only names a slot there, so only the UDF-side SELECT builder was wrong.
- **Decision:** Change `ScanSpec.projection` / `CommonScanSpec.projection` from `Vec<String>` to `Vec<ProjectionItem>`, a new enum with `Column(String)` and `Expr { expr: String }` — the exact analog of `AggregatePlan`'s separate `column` vs `arg_expr` fields, which exist for this identical "column-vs-rendered-expression looks the same as a string" reason. `extract_projection` now tags each entry at the point the distinction is known (the `match item_type` arms). `build_scan_sql` matches the variant: a `Column` keeps its existing CAST-for-JSON-fallback + `quote_ident` behavior unchanged; an `Expr` is spliced VERBATIM (like `spec.filter` and `agg_arg_sql`), resolving against the uppercase-aliased inner scan.
- **Alternatives rejected:** (a) A syntactic heuristic in `build_scan_sql` (entry contains `(`/quote/operator → treat as expression, else identifier). Rejected: fragile exactly as the task warned — an exotic quoted Exasol column name (spaces, parens) would be misclassified, and it re-derives a fact already known upstream. (b) "Is it a field in the Arrow schema?" as the discriminator. Rejected: implicit, and it silently changes the defensive path for a bare column absent from the schema. (c) A parallel `Vec<bool>`/`Vec<Option<String>>` alongside the string vec. Rejected: positional-alignment fragility, worse than a single tagged type.
- **Why low-risk despite touching a widely-used field:** `#[serde(untagged)]` makes a `Column` serialize as a bare JSON string and an `Expr` as `{"expr":...}`, so the wire format for the common all-columns case is byte-for-byte unchanged and any legacy string-array projection still deserializes (as all-`Column`). `From<&str>`/`From<String>` for `ProjectionItem` (→ `Column`) keep the ~30 `projection: vec!["ID".into(), …]` test/call sites compiling unchanged; `PartialEq<&str>` keeps the round-trip assertion (`assert_eq!(back.projection, vec!["id","name"])`) unchanged. Only the two adapter row-scan test helpers, the five `build_scan_driving_sql` call sites passing `&["X".to_string()]`, and three `extract_projection`-output assertions needed edits. `agg_arg_sql`'s `arg_expr` splice and the grouped-key `select_items` path were untouched (they were never affected).
- **Verification (waited-for, real output):** repro'd the failure, applied the fix, rebuilt the `.so` via `make cross-musl-udf-build`, then: `e2e_selectlist_expression_pushdown` passes; full `make test-e2e` green — `e2e_scan_test 41/0`, `e2e_capability_test 7/0`, `e2e_count_distinct_test 3/0` (51 passed, 0 failed, exit 0); host `cargo test -p lakehouse-engine --lib` 370/0; added a Docker-free host regression test `scan_plan_shape::raw_scan_projects_mixed_column_and_expression_items` (bare `ID` + `("SCORE" * 2)` + `UPPER("NAME")`, asserts the plan builds and evaluates to `(1,10,EVENT-01),(2,20,EVENT-02),(3,30,EVENT-03)`) plus an `Expr`-variant assertion in the existing `extract_projection` expression test; `cargo clippy --all-targets --features exasol-e2e -p lakehouse-engine` clean; `cargo fmt --check` clean.
- **Promotes to ADR:** yes — the `column`/`arg_expr`/`ProjectionItem` pattern (never overload one string field for both a bare identifier and rendered SQL) is now the established convention for anything crossing the adapter→scan spec boundary.

### [10] (tasks 3.1/3.2) Parallelism-factor sweep result: validated no-op — factor 16 is flat, factor 24 regresses; `bench/.env` and `resolve_parallelism_factor` left unchanged

- **Setup:** Added `bench/parallelism_sweep.sh` (sibling to `sweep.sh`, same config-row driver pattern) sweeping `BENCH_PARALLELISM_FACTOR` ∈ {8 (baseline), 16, 24} against the live test1 cluster (2 nodes × 8 cores; `BENCH_NR_OF_CORES=8`), measuring Q2/Q3/Q5 (raw-emit-heavy joins the hypothesis targets) and Q9b (non-join wide-projection regression check). Ran the full 3-config sweep **twice** to rule out a fluke. G = node_count(2) × factor: pf8→G=16 (1 shard/core, no oversubscription), pf16→G=32 (2 shards/core), pf24→G=48 (3 shards/core).
- **Blocking issue found and fixed first (operational, not code):** The cluster's deployed SLC was pinned at 0.19.1 (`bench/.env`'s `BENCH_SLC_VERSION=0.19.1`, generated by `deploy/scripts/secrets.sh`), but `Cargo.toml` has since moved to `exasol-udf-sdk 0.20.1` — the freshly built `.so` was rejected with `F-UDF-CL-RUST-9001: Fingerprint mismatch: expected 0.19.1:..., found 0.20.1:...` the moment it was uploaded (the previously-staged `.so` on BucketFS was correspondingly stale, predating even Group A's `FN_MULT` capability advertisement — its absence caused an unrelated `NQ1 arithmetic aggregate pushdown` check failure that had nothing to do with parallelism). Fixed by running `make install-slc` (defaults to `SLC_VERSION=0.20.1`, matching `Makefile`'s own default) against test1 and bumping `bench/.env`'s `BENCH_SLC_VERSION` to `0.20.1` (gitignored file, fixed locally with an explanatory comment; `deploy/scripts/secrets.sh` does not currently regenerate this value in lockstep with `Cargo.toml` — worth a follow-up outside this plan's scope). After the fix, `./bench/run.sh` at `PARALLELISM_FACTOR=8` passed clean (rc=0, all pushdown checks including NQ1 green), confirming the sweep evidence below is measured against the current, correct code.
- **Results (elapsed seconds; two independent full-sweep runs):**

  | Query | pf8 run1 | pf8 run2 | pf16 run1 | pf16 run2 | pf24 run1 | pf24 run2 |
  |---|---|---|---|---|---|---|
  | Q2 (3-way join scan) | 16.87 | 17.25 | 16.46 | 17.37 | 17.08 | 17.15 |
  | Q3 (join + filter + GROUP BY) | 14.90 | 14.85 | 14.90 | 15.13 | 15.89 | 16.21 |
  | Q5 (join + GROUP BY, no filter) | 18.86 | 19.01 | 18.63 | 18.23 | 19.44 | 19.30 |
  | Q9b (wide projection, no join) | 11.55 | 10.81 | 10.92 | 10.74 | 12.57 | 12.45 |

  Averaged: pf8 = {Q2 17.06, Q3 14.88, Q5 18.94, Q9b 11.18}; pf16 = {Q2 16.92 (‑0.8%), Q3 15.02 (+0.9%), Q5 18.43 (‑2.7%), Q9b 10.83 (‑3.1%)}; pf24 = {Q2 17.12 (+0.4%), Q3 16.05 (+7.9%), Q5 19.37 (+2.3%), Q9b 12.51 (+11.9%)}. These numbers are consistent with the pre-sweep historical baseline (`bench/reports/bench-report-20260703-215449.txt`, pf8: Q2 16.54/Q3 14.45/Q5 18.03/Q9b 10.76), confirming ~2-5% is normal run-to-run noise on this cluster.
- **Finding:** **pf16 is flat** — every delta is within the ~2-5% noise band established by the historical baseline and the two runs' own spread, with mixed sign (no consistent direction). The "second shard queued up per core hides emit-ack stall" hypothesis is **not supported**: if emit-ack latency were the bottleneck, pf16 should show a large, consistent, one-directional gain on the emit-heavy joins (Q2/Q3/Q5) — it shows neither magnitude nor consistent direction. **pf24 is a real, repeatable regression**, not noise: Q3 is worse in both runs (+6.6%, +9.2%) and Q9b is worse in both runs (+8.8%, +15.2%) — over-oversubscription (3 shards/core) adds scheduling/context-switch overhead that outweighs any stall-hiding benefit, and it regresses the non-join Q9b control query exactly as the task's regression-check was designed to catch.
- **Decision:** **Validated no-op.** Change nothing: `bench/.env`'s `BENCH_PARALLELISM_FACTOR=8` and `resolve_parallelism_factor`'s `max(nr_of_cores*2, DEFAULT_PARALLELISM_FACTOR)=16` default in `crates/lakehouse-engine/src/adapter/mod.rs` are both left as-is. No `cargo test` run needed since no source file changed. No `parallelism/work-unit-sharding` spec delta — the spec's existing text (G computation, capping, distribution) is unaffected by this finding; it never asserted a specific tuned factor value.
- **Rationale:** Decision [4] gated any default change on "a real, repeatable improvement... without a Q9b regression." The evidence shows the opposite of an improvement at pf24 (repeatable Q9b regression) and no improvement at all at pf16. Changing the default on this evidence would make things worse, not better — ruling out this optimization is the valuable outcome, exactly as decision [4] anticipated as an acceptable result.
- **Promotes to ADR:** no (a negative/no-op finding on a knob whose default was already correct doesn't need an architectural record; the sweep tooling itself — `bench/parallelism_sweep.sh` — is the durable artifact, same non-spec-feature status as `sweep.sh`).
