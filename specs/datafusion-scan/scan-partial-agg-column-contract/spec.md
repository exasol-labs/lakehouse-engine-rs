# Feature: Partial-Aggregate Column Contract

Gives the partial-aggregate COLUMN CONTRACT — how many columns each `AggKind` contributes, in what order, under what `PARTIAL_*` name, and what an empty shard puts in each one — exactly one owner, `AggKind::partial_columns()` in `crates/lakehouse-engine/src/scan/spec.rs`, split out of `datafusion-scan/scan-execution-partial-agg` as issue [#179](https://github.com/exasol-labs/lakehouse-engine-rs/issues/179)'s correctness-sensitive scope. The contract's behavior is owned by `datafusion-scan/scan-execution-partial-agg` (single-group) and `datafusion-scan/scan-execution-grouped-agg` (grouped) and is consumed here, not restated: this feature records only who owns the per-`AggKind` column arity and naming, and that no generated SQL, EMITS clause, or emitted partial row changes.

## Background

* The contract is encoded independently at FIVE sites today, four of which must agree on the column COUNT and all five on the column NAME. Scan side, in `scan/partial_agg.rs`: `partial_select_items` (the DataFusion SELECT list, lines 365-405), `emit_null_partial_row` (the empty-result fallback row, lines 261-280), and `partial_row_from_batch` (the batch-column walk, lines 413-439). Adapter side, in `adapter/pushdown/grouped_agg.rs`: `partial_emits_items` (the Exasol `EMITS` declaration, lines 724-784) and `merge_select_items` (the outer merge expressions, lines 902-962). Nothing enforces the agreement.
* A count disagreement is silent and wrong, not a compile error. `partial_row_from_batch` walks batch columns by an index it advances itself, and `emit_null_partial_row` builds a `Vec<Value>` by length alone, so a site that advances by 2 where the SELECT list produced 3 shifts every subsequent aggregate's value into the wrong `EMITS` slot for the rest of the row.
* The four kinds' arities are Count/CountCol/Sum/Min/Max = 1, Avg = 2 (sum then count), and the STDDEV/VARIANCE family = 3 (cnt, sum, sumsq). Those numbers are what this feature moves behind one owner; it does not change any of them.
* `AggKind` lives in `scan/spec.rs`, the scan-spec wire-format module both the scan and the adapter already import (`scan/partial_agg.rs:17`, `adapter/pushdown/grouped_agg.rs:5`). The descriptor therefore adds no new dependency edge and no cycle: both consumers already depend inward on the wire-format module, and that module depends on neither.
* `scan/spec.rs` imports `serde` and nothing else. It MUST NOT gain a dependency on `exasol_udf_sdk`, so the descriptor expresses "what an empty shard puts here" as a boolean COUNTER property and leaves the `Value::Int64(0)` / `Value::Null` mapping to the emit site.
* Two other per-`AggKind` matches in the pushdown tree are NOT targets, because each answers a different question and neither is per partial column. `empty_agg_literal` (`file_resolution.rs:703`) yields ONE zero-row literal per aggregate for the outer result column — `0` for the COUNT family, `NULL` otherwise — and knows nothing about partial columns. `validate_agg_col_types`' `needs_numeric` match (`grouped_agg.rs:855`) decides which kinds require a numeric source column. Folding either into the column descriptor would put an unrelated decision inside it.
* The grouped emit path in `run_grouped_partial_aggregate` (`partial_agg.rs:159-184`) is NOT a sixth site and needs no change: it walks `n_group_keys..batch.num_columns()` positionally and never consults `AggKind`, so it trusts the SELECT list's own column count rather than re-deriving it.
* The refactor is byte-identical by requirement, and the repository already owns the instrument that proves it: `adapter/pushdown/dispatch_golden.rs` asserts full-string equality against committed fixtures under `testdata/dispatch_golden/`. None of its ten fixtures covers an AVG or a statistical aggregate today (`grep PARTIAL_avg` and `grep PARTIAL_stat` over the fixture directory both return nothing), so the multi-column arities — the two this feature is most at risk of breaking — are exactly the ones the existing gate does not watch. New pre-refactor fixtures for them are a prerequisite, not a nicety.
* Iceberg spec compliance: checked, not engaged. This feature moves a per-`AggKind` column-count and naming decision between Rust functions inside one crate. It touches no manifest read, snapshot resolution, field-id projection, delete-file application, or type-mapping surface, so no normative requirement of the Apache Iceberg table spec applies and there is no deviation to fix or track.

## Scenarios

### Scenario: One descriptor owns every aggregate's partial column set

* *GIVEN* the five sites that independently encode which partial columns an `AggKind` contributes — `partial_select_items`, `emit_null_partial_row`, and `partial_row_from_batch` in `scan/partial_agg.rs`, and `partial_emits_items` and `merge_select_items` in `adapter/pushdown/grouped_agg.rs`
* *WHEN* any of the five needs to know how many partial columns an aggregate produces, in what order, or under what `PARTIAL_*` name
* *THEN* exactly ONE item SHALL own that answer: `AggKind::partial_columns(&self) -> &'static [PartialAggColumn]` declared in `crates/lakehouse-engine/src/scan/spec.rs` alongside `AggKind`, returning the ordered partial columns for that kind
* *AND* `PartialAggColumn` SHALL enumerate the TEN distinct partial columns the contract admits — `CountStar`, `CountArg`, `Sum`, `Min`, `Max`, `AvgSum`, `AvgCnt`, `StatCnt`, `StatSum`, `StatSumSq` — and `AggKind::partial_columns` SHALL map `Count` to `[CountStar]`, `CountCol` to `[CountArg]`, `Sum`/`Min`/`Max` each to their single matching column, `Avg` to `[AvgSum, AvgCnt]`, and each of `VarPop`, `VarSamp`, `StddevPop`, `StddevSamp` to `[StatCnt, StatSum, StatSumSq]`
* *AND* `CountStar` and `CountArg` SHALL be two variants rather than one, because they share a column name and an `EMITS` type but render DIFFERENT DataFusion SQL — `COUNT(*)` versus `COUNT(<arg>)` — so collapsing them would force the scan's renderer to re-consult the `AggKind` the descriptor exists to abstract
* *AND* `AggKind::partial_columns` SHALL match EXHAUSTIVELY over `AggKind` with NO wildcard arm, and each renderer SHALL match exhaustively over `PartialAggColumn` with no wildcard arm, so a new `AggKind` variant is a compile error at the descriptor and a new `PartialAggColumn` variant is a compile error at every renderer — the contract is extended by adding a case, never by editing a dispatch that silently defaults
* *AND* NO `partial_column_count()` method SHALL be added, even though issue #179 suggests one: a function whose whole body forwards to `partial_columns().len()` is the shallow pass-through this repository's recorded rule rejects, and `partial_row_from_batch` reads `.len()` directly
* *AND* the descriptor MUST NOT depend on `exasol_udf_sdk`, so it SHALL express the empty-shard identity as `PartialAggColumn::is_counter(&self) -> bool` — `true` for the four counter columns `CountStar`, `CountArg`, `AvgCnt`, and `StatCnt`, and `false` for the six value columns `Sum`, `Min`, `Max`, `AvgSum`, `StatSum`, and `StatSumSq` — and the emit site SHALL map `true` to `Value::Int64(0)` and `false` to `Value::Null`, keeping `scan/spec.rs` a serde-only module

### Scenario: The partial column name has one owner across the scan and the adapter

* *GIVEN* the `PARTIAL_<role>_<ordinal>` column name, hand-formatted at three sites that must agree byte-for-byte — the scan's `AS "PARTIAL_…"` aliases, the adapter's `"PARTIAL_…" <type>` `EMITS` items, and the adapter's `SUM("PARTIAL_…")` merge expressions
* *WHEN* any of the three renders a partial column name
* *THEN* the name SHALL be produced by ONE function taking the `PartialAggColumn` and the aggregate's ordinal and returning the UNQUOTED name, and each of the three sites SHALL apply its own quoting as it does today — the scan and the merge wrapping it in double quotes, the `EMITS` item wrapping it in double quotes ahead of its type
* *AND* the per-column name fragment SHALL be `count` for both `CountStar` and `CountArg`, `sum`, `min`, `max`, `avg_sum`, `avg_cnt`, `stat_cnt`, `stat_sum`, and `stat_sumsq` respectively, reproducing every name the pre-refactor code emits
* *AND* no site SHALL retain a `format!` literal containing the text `PARTIAL_`, so a renamed column can never be renamed at one site only

### Scenario: The statistical-aggregate partial argument routes through the shared argument renderer

* *GIVEN* the stat-family branch of `partial_select_items` (`partial_agg.rs:395-403`), which bypasses `agg_arg_sql` and instead reads `plan.column.as_deref().unwrap_or("")` — falling back to an EMPTY identifier that DataFusion rejects with an opaque `Schema error: No field named .` (captured live, plan `refactor-pushdown-agg-dedup` task 1.2) rather than to `agg_arg_sql`'s self-describing `__MISSING_AGG_ARGUMENT__` sentinel
* *WHEN* the scan renders the `COUNT`, `SUM`, and `SUM(col*col)` sufficient statistics for a statistical aggregate
* *THEN* all three SHALL take their argument from `agg_arg_sql(plan)`, the same helper every other kind uses, and the branch SHALL retain NO `plan.column` read and NO local `quote_ident` call of its own
* *AND* the rendered SQL for a bare-column statistical aggregate MUST be byte-identical to the pre-refactor output, because `agg_arg_sql` returns `quote_ident(column)` for a plan with no `arg_expr` — which is exactly what the branch computes today
* *AND* routing through `agg_arg_sql` SHALL NOT be treated as making expression-argument statistical aggregates work: the plan shape it improves the error message for is declined upstream instead, per `vs-adapter/pushdown-planning-aggregate-extensions`, so this clause changes only which identifier a plan that can no longer reach the scan would have produced

### Scenario: Generated SQL, EMITS clauses, and partial rows are byte-identical across the refactor

* *GIVEN* pre-refactor golden baselines captured through the production seams for every arity the contract admits — the single-column kinds, `AVG`'s two-column pair, and the statistical family's three-column triple — in both the single-group and the grouped shape
* *WHEN* the same requests and specs are rendered against the refactored code
* *THEN* the scan's partial-aggregate DataFusion SQL, the grouped partial-aggregate DataFusion SQL, the `EMITS` clause, and the outer merge SELECT MUST each be byte-identical to the captured baseline, asserted by full-string equality and NEVER by `.contains(...)`
* *AND* the emitted partial row for a non-empty shard and the fallback row for an empty single-group shard MUST carry the same values, in the same order, with the same lengths, as the pre-refactor code for every `AggKind`
* *AND* the baselines for the AVG and statistical arities SHALL be captured and committed BEFORE any contract site is edited, because `dispatch_golden.rs`'s ten existing fixtures cover neither arity and would pass a change that shifted a multi-column aggregate's values
* *AND* every existing unit and integration test covering the partial-aggregate paths MUST pass with NO change to any test assertion or expected value — in particular `partial_agg.rs`'s `partial_agg_sql_stat_emits_cnt_sum_sumsq`, `stat_aggregate_null_fallback_row_has_three_values`, `stat_aggregate_index_follows_plan_order`, `partial_agg_sql_avg_emits_sum_count_pair`, `partial_agg_sql_mixed_column_order_and_indices`, and `partial_sql_uses_rendered_expression_argument`, and `grouped_agg.rs`'s `stat_aggregate_emits_three_partial_columns`
* *AND* those tests SHALL keep their LITERAL expected column names and arities and MUST NOT be rewritten to read `partial_columns()` or the shared name function, because a test that derives its expectation from the code under test asserts the descriptor against itself and would pass any consistent renaming

### Scenario: One in-crate test pins the scan-to-adapter column alignment per aggregate kind

* *GIVEN* that the scan's SELECT list and the adapter's `EMITS` clause are produced in two different modules and validated against each other only at query time inside Exasol, where a mismatch surfaces as a wrong value or an `EMITS` arity error rather than as a test failure
* *WHEN* the test suite runs
* *THEN* ONE test SHALL assert, for EVERY `AggKind` variant, that the scan's partial SELECT list and the adapter's `EMITS` item list contain the same number of columns in the same `PARTIAL_*` order
* *AND* that test SHALL reach both sides through the visibility that already exists — `crate::scan::build_partial_agg_sql` is re-exported under `#[cfg(test)]` in `scan/mod.rs` and `partial_emits_items` is `pub(super)` in `adapter::pushdown::grouped_agg` — so it SHALL be declared inside the crate, and NO production item's visibility SHALL widen and NO `#[cfg(test)]`-only export SHALL be added to enable it
* *AND* the test SHALL enumerate the `AggKind` variants it covers as an explicit literal list, and a variant added later that the list omits SHALL be caught by the compile error `partial_columns` raises rather than by this test, so the test asserts alignment and never doubles as an exhaustiveness check it cannot enforce
