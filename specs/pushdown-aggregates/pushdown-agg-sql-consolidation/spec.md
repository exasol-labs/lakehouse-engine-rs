# Feature: Pushdown Aggregate SQL Consolidation

Gives three hand-repeated pieces of the aggregate-pushdown SQL assembly one owner each — the STDDEV/VARIANCE merge expressions, the "CAST to the declared type unless it is the `VARCHAR(2000000)` default" rule, and the aggregate-function-name to `AggKind` mapping — split out of `pushdown-grouped-agg/pushdown-planning-grouped-agg` and `pushdown-aggregates/pushdown-planning-single-group-agg` as issue [#179](https://github.com/exasol-labs/lakehouse-engine-rs/issues/179)'s SQL-assembly scope. Every merge formula, cast decision, and detection outcome those features record is unchanged and is consumed here, not restated: this feature records only who owns each repeated construction, and that the generated SQL is byte-identical.

## Background

* Three separate duplications, three separate owners, no shared mechanism between them. They are collected in one feature because they are one issue's cleanup of one file pair (`grouped_agg.rs`, `single_group_agg.rs`) and share one verification gate, not because they share a design.
* Duplication one, the statistical merge expressions. They merge `(cnt, mean, m2)` partials with Chan's parallel formula (`pushdown-aggregates/pushdown-planning-aggregate-extensions`). Every term of the merged `M2` is non-negative and `SQRT(NULL)` is NULL, so the merge carries no `GREATEST(0.0, …)` clamp and no `IS NULL` guard.
* Duplication two, the declared-type CAST rule, is written SIX times, and one of the six is a doc comment claiming to BE the shared rule. `constant_projection_sql` (`grouped_agg.rs:117-127`), the `gk_select` closure (`:626-633`), `cast_merge_items` (`:1099-1111`), `cast_to_declared_type` (`:1113-1124`), `empty_agg_sql` (`file_resolution.rs:728-745`), and the `ScalarOverAggregate` arm of `empty_grouped_sql` (`file_resolution.rs:777-783`) each re-derive "wrap in `CAST(<expr> AS <ty>)` unless `<ty>` is `VARCHAR(2000000)`". Five of the six treat an absent declared type as "no cast"; `cast_to_declared_type` alone takes a non-optional `&str`, which is why the canonical form takes an `Option`.
* The `GroupKey` and `Aggregate` arms of `empty_grouped_sql` (`file_resolution.rs:766-772`) are deliberately EXCLUDED from that consolidation and MUST stay as they are. They render `CAST(NULL AS <ty>)` UNCONDITIONALLY, with no `VARCHAR(2000000)` guard, and applying the guard there would emit a bare `NULL` whose Exasol type is not `VARCHAR` — which is the positional `selectListDataTypes` validation the cast exists to satisfy. That divergence is a correctness requirement of the zero-row shape, not a missed dedup, and this feature names it rather than folding it in.
* Duplication three, `parse_agg_item`'s arms (`single_group_agg.rs:226-301`). `SUM`, `MIN`, `MAX`, and `AVG` are four bodies identical but for the `kind:` field. The six statistical names are six bodies identical but for `kind:`. `COUNT` is genuinely different — it splits on argument presence to distinguish `COUNT(*)` from `COUNT(<arg>)` — and stays its own branch.
* A `[(name, AggKind)]` table for the statistical family already exists in this repository, in a TEST (`parse_agg_item_recognises_stat_functions`, `single_group_agg.rs:839-846`). Promoting the table into production makes that test's own table a second copy, and the test SHALL keep its literal table rather than read the production constant, because reading it would assert the constant against itself.
* The verification instrument already exists and is already scoped to this kind of change: `adapter/pushdown/dispatch_golden_tests.rs` asserts full-string equality against committed fixtures under `testdata/dispatch_golden/`, and its module doc records that "every subsequent dedup task MUST leave these ten fixtures byte-identical; a diff here is a regression, never an expected update". None of the ten covers an `AVG` or a statistical aggregate, so this feature's own gate depends on adding fixtures for those shapes first.
* Iceberg spec compliance: checked, not engaged. This feature restructures SQL string assembly and one JSON-node-to-enum mapping inside the adapter. It touches no manifest read, snapshot resolution, field-id projection, delete-file application, or type-mapping surface, so no normative requirement of the Apache Iceberg table spec applies and there is no deviation to fix or track. The same holds for the Delta Lake protocol, and for this delta specifically: correcting a doc comment about Exasol's `GREATEST` reads no table format at all.
* **This delta is issue #135. It amends TWO scenarios — one clause each — and changes no consolidation rule.** The single-owner statistical merge, the single declared-type CAST owner, the two unconditional `CAST(NULL AS …)` arms, and the aggregate-name-to-`AggKind` tables are all UNCHANGED.
* **SUPERSEDES this feature's two byte-identity gates for the `storage` value alone, through the mechanism the merge tool actually has.** Both falsified sentences are SCENARIO clauses — recorded `:33` in "The sufficient-statistics fragments have one owner per denominator" and recorded `:46` in "The declared-type CAST rule has one owner" — not `## Background` prose, so they are carried as two `DELTA:CHANGED` reproductions rather than as a Background supersession the merge procedure would silently drop or as a new scenario the recorded library does not have. Both hold for every byte of the rendered SQL EXCEPT the `storage` value of the common scan-spec literal, which becomes the tagged wrapper of `storage-access/scan-spec-credential-reference`.
* **Each reproduction changes exactly ONE clause and preserves every other verbatim**, including the `Option<&str>` signature rationale, and the two unconditional `CAST(NULL AS …)` arms — so the reproductions cannot become a back door for weakening a clause this delta has no business touching.
* **The carve-out is one value, not a waiver, and the fixture split is exact.** Eighteen of the twenty-four committed `dispatch_golden` fixtures carry a `storage` value and are REGENERATED; the six `empty_*` fixtures carry none and MUST stay byte-identical. Naming the split is what stops "regenerate the goldens" from silently accepting a diff in a fixture that must not change.
* **Every merge assertion and every aggregate-name assertion is unaffected**, because none of them reads the `storage` value: the consolidation this feature records is about the outer merge expression and the declared-type CAST, neither of which touches the common scan-spec literal.
* **`storage-access/scan-spec-credential-reference` owns the reference contract and the fixture-regeneration requirement.** This feature CITES it and restates none of it.

## Scenarios

### Scenario: The statistical merge has one owner

* *GIVEN* the six statistical aggregate kinds `VAR_POP`, `VAR_SAMP`, `VARIANCE`, `STDDEV_POP`, `STDDEV_SAMP`, and `STDDEV`
* *WHEN* the adapter builds the outer merge expression for any of them
* *THEN* one function SHALL build the merged count `N`, the merged `M2`, and the three variance forms once per aggregate ordinal, and each standard deviation SHALL be `SQRT` of its matching variance
* *AND* the partial column names the merge references SHALL come from the single name owner recorded in `scan-aggregation/scan-partial-agg-column-contract`, so `merge_select_items` retains NO `PARTIAL_` string literal of its own

### Scenario: The declared-type CAST rule has one owner

* *GIVEN* six sites that each re-derive "wrap in `CAST(<expr> AS <ty>)` unless `<ty>` is the `VARCHAR(2000000)` default" — `constant_projection_sql`, the `gk_select` closure, `cast_merge_items`, and `cast_to_declared_type` in `grouped_agg.rs`, plus `empty_agg_sql` and the `ScalarOverAggregate` arm of `empty_grouped_sql` in `file_resolution.rs` — one of which documents itself as being that shared rule
* *WHEN* any of the six decides whether to cast an outer-wrapper expression to its Exasol-declared type
* *THEN* exactly ONE helper SHALL own that decision, taking the rendered expression and an `Option<&str>` declared type and returning the expression cast or uncast, and each of the six sites SHALL retain NO `VARCHAR(2000000)` comparison and NO `CAST(` format of its own
* *AND* the helper SHALL take an `Option<&str>` rather than a `&str`, because five of the six sites read their declared type from a `.get(i)` on a possibly-shorter list and already treat absence as "no cast"; the sixth passes `Some(declared_type)` and its behavior is unchanged
* *AND* the helper SHALL be declared `pub(super)` in `adapter/pushdown/support.rs`, the submodule that already owns the pushdown tree's shared primitives, because its consumers live in two SIBLING submodules (`grouped_agg` and `file_resolution`) rather than in one
* *AND* the `GroupKey` and `Aggregate` arms of `empty_grouped_sql` MUST NOT be routed through the helper and SHALL keep their UNCONDITIONAL `CAST(NULL AS <ty>)`, because those arms deliberately cast even to `VARCHAR(2000000)`: a bare `NULL` in a zero-row `SELECT … FROM DUAL WHERE 1=0` carries no `VARCHAR` type and would fail the positional `selectListDataTypes` check the cast exists to satisfy
* *AND* every comment asserting the rule by convention SHALL be replaced by a reference to the helper rather than left standing — in particular `cast_to_declared_type`'s doc sentence naming `cast_merge_items`, `constant_projection_sql`, and the group-key cast as the sites it mirrors, and `constant_projection_sql`'s "mirrors the group-key and aggregate cast discipline" and "matching `group_key_exasol_types`" clauses — because a preserved sentence asserting a convention the code now enforces is the stale note this consolidation deletes
* *AND* the generated SQL for every single-group, grouped, and empty-result pushdown request MUST be byte-identical to its pre-consolidation output EXCEPT for the scan-spec `storage` value, which `storage-access/scan-spec-credential-reference` re-encodes and which this consolidation does not touch, and every existing `dispatch_golden` fixture and grouped-aggregate assertion MUST pass with NO change to any expected value outside that one value — the empty-result response carries no scan spec at all and MUST therefore stay byte-identical with NO exception, which is why the six `empty_*` fixtures are asserted unchanged rather than regenerated

### Scenario: Aggregate function names map to AggKind through two tables

* *GIVEN* `parse_agg_item` (`adapter/pushdown/single_group_agg.rs`), where `SUM`, `MIN`, `MAX`, and `AVG` are four bodies differing only in their `kind:` field, and the six STDDEV/VARIANCE names are six bodies differing only in their `kind:` field
* *WHEN* the adapter resolves a `function_aggregate` select-list item's function name to an `AggKind`
* *THEN* the expression-capable names SHALL be resolved through ONE `[(&str, AggKind)]` table — `SUM`, `MIN`, `MAX`, `AVG` — and the statistical names through a SECOND such table — `STDDEV` and `STDDEV_SAMP` to `StddevSamp`, `STDDEV_POP` to `StddevPop`, `VARIANCE` and `VAR_SAMP` to `VarSamp`, `VAR_POP` to `VarPop`
* *AND* the two tables SHALL stay SEPARATE and MUST NOT be merged into one, because each table's members share an argument-resolution rule the other's do not: the first resolves its argument through `arg_column_or_expr`, admitting either a bare column or a rendered expression, while the second admits a bare column only (see `pushdown-aggregates/pushdown-planning-aggregate-extensions`)
* *AND* `COUNT` SHALL remain its own branch and MUST NOT be folded into either table, because it is the only name whose `AggKind` depends on its ARGUMENT rather than on its name — no argument yields `Count`, an argument yields `CountCol`
* *AND* an unrecognized function name SHALL still decline the aggregate pushdown by returning `None`, and a `distinct: true` item SHALL still decline ahead of any table lookup, so the two tables change how a recognized name is resolved and never which names are recognized
* *AND* the existing test `parse_agg_item` stat-family table (`parse_agg_item_recognises_stat_functions`, `single_group_agg.rs:839-846`) SHALL keep its own LITERAL `[(name, AggKind)]` pairs and MUST NOT be rewritten to iterate the production table, because a test reading the table it verifies asserts the table against itself and would pass any consistent mis-mapping
* *AND* the `AggregatePlan` produced for every function name and argument shape MUST be identical to the pre-refactor plan, and every existing detection test in `single_group_agg.rs`, `grouped_agg.rs`, and `support.rs` MUST pass with NO change to any expected value
