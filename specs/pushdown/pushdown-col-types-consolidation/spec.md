# Feature: Pushdown Col Types Consolidation

Gives the pushdown type-rewrite guards' `col_types` handling one owner per decision: one lookup helper, one builder, and one Exasol-type-family classifier.

## Background

* Resolving a bare column node's Exasol type is two decisions in two owners. `support` owns node, uppercased name, and `col_types` scan. `types::mapping` owns type string to type family. The column-lookup miss stays out of the classifier, which takes a non-optional `&str`. `scan-types/type-mapping-module-structure` owns `ExaTypeClass` and `classify_exa_type`.
* The `col_types` list is produced and consumed with one fold, the Unicode `to_uppercase`. The ASCII fold would differ only for a name with a lowercase non-ASCII letter, and no such name reaches the adapter: `resolve_table_schema` (`adapter/pushdown/file_resolution.rs:640`) uppercases every Iceberg field name with `f.name.to_uppercase()` before `build_virtual_tables` declares it. Exasol serves an Iceberg `straße` column as `STRASSE`. `tests/e2e_non_ascii_identifier_test.rs::non_ascii_table_and_column_stay_queryable` guards that premise against a Docker Exasol container.
* A name already produced by `to_uppercase` is a fixed point of both `to_uppercase` and `to_ascii_uppercase`, so the folds agree on every declared name.
* `joins/rendering.rs::referenced_side_columns` narrows `involved_table_columns`' names by membership in the set `collect_side_column_names` builds with `to_ascii_uppercase`. If the premise broke, a mixed side would drop a diverging column from the fan-out leg while the outer wrapper still references it. `referenced_side_columns` falls back to `full_cols` only when narrowing yields nothing.
* Four other `col_types` scans are not targets of the lookup helper, because their input is an already-resolved column name rather than a JSON node: `project_columns`'s `type_by_upper` closure, the declined-`ORDER BY` hidden-column appender in `topn.rs`, `col_type_for` in `grouped_agg.rs`, and the logical-field scan in `scan/join_scan.rs`. `parse_sort_key_element` in `topn.rs` resolves an identifier, not a type.
* Each builder wrapper supplies one table selection and nothing else (`tables.first()` or the find-by-name closure), so it is a partial application and not a pass-through.
* The generated SQL stays byte-identical except for the scan spec's `storage` value, which `storage-access/scan-spec-credential-reference` re-encodes.

## Scenarios

### Scenario: One helper resolves a bare column node's Exasol type for every type-rewrite guard

* *GIVEN* the three per-node type decisions in `pushdown/support.rs` — `guard_like_subject`, `is_bare_decimal_column`, and `coerce_string_position_arg` — which each hand-roll the same two-step resolve against the per-request `col_types: &[(String, String)]` list: read the node's `name`, fold it with the Unicode `to_uppercase`, then linear-scan `col_types` for a tuple whose first element equals it; and which each carry a doc-comment note asserting that it mirrors the other two's convention
* *WHEN* any of the three decides what to do with a bare `column` node
* *THEN* exactly ONE helper in the shared `support` submodule SHALL own that resolve, taking the node and the `col_types` slice and returning `Option<&str>` — the resolved Exasol type string, or nothing — and each of the three guards SHALL retain NO name-folding and NO `col_types` scan of its own
* *AND* the helper MUST NOT test the node's `type` tag, because a non-`column` node is NOT a failed lookup: `guard_like_subject` and `coerce_string_position_arg` return such a node UNCHANGED whereas a failed lookup makes them decline, so absorbing the tag test would convert a pass-through into a decline and silently drop pushdown for every computed expression and literal argument
* *AND* each guard SHALL therefore keep its own `type == "column"` test ahead of the call — the pass-through for the two `Option<Json>` guards, `false` for `is_bare_decimal_column` — so the helper owns the resolve and nothing else
* *AND* the helper SHALL fold the name with the Unicode `to_uppercase` and MUST NOT use `to_ascii_uppercase`, because all three guards fold that way today and the extraction MUST NOT change which fold they apply. The two folds agree on every name the adapter can declare, per the captured evidence above, so switching would be a gratuitous edit — and its harmlessness would rest on a normalization `resolve_table_schema` owns rather than on anything this helper can observe
* *AND* the helper SHALL return `None` for BOTH a nameless column node and a name absent from `col_types`, because all three guards already treat those two cases identically — a decline in the two `Option`-returning guards, `false` in the boolean one — so no third state is needed and none SHALL be introduced
* *AND* the helper SHALL be declared private to `support`, because its only three consumers live there
* *AND* every mirror-note comment SHALL be deleted, because the shared helper now enforces by construction what those notes asserted by convention: the three guards' doc-comment notes AND `guard_like_subject`'s INLINE BODY COMMENT above the lookup block the helper replaces, which is the sole carrier of the stale line-number citation; each guard's doc comment SHALL otherwise be preserved, in particular `coerce_string_position_arg`'s four-row per-type dispatch table and its `(#223)` non-`column`-argument exception — EXCEPT any sentence that names a predicate moving to `classify_exa_type`, which SHALL be reworded to name the classifier's family while KEEPING its rationale intact: `is_bare_decimal_column`'s "Integer columns are wire-encoded as `DECIMAL(p,0)`, so `.starts_with("DECIMAL")` also matches them (harmless: the trim is a no-op on a scale-0 value)" SHALL still record that integer columns classify as DECIMAL and that the trim is a harmless no-op at scale 0, but SHALL name `ExaTypeClass::Decimal` instead of the literal predicate, because after the substitution the guard no longer contains that predicate and a preserved sentence naming it would be a fresh instance of the stale-citation defect this delta deletes
* *AND* for a column name whose Unicode and ASCII folds differ, such as `STRAßE` (`to_uppercase` yields `STRASSE` while `to_ascii_uppercase` leaves it unchanged), the helper MUST resolve a type against a Unicode-folded `col_types` list and MUST return `None` against an ASCII-folded one. Exasol never delivers such a name, per the captured evidence above, because this crate uppercases every Iceberg field name before declaring it
* *AND* the scan-driving SQL generated for every pushdown request MUST be byte-identical to its pre-extraction output EXCEPT for the scan spec's `storage` value, which `storage-access/storage-backend-enum` re-encodes as an externally-tagged backend variant over a byte-identical payload, and which `storage-access/scan-spec-credential-reference` then replaces with a connection reference or a sealed envelope over that same payload

### Scenario: One builder produces the column-type list for both the first-table and the named-table selection

* *GIVEN* `column_types` (`pushdown/support.rs`), the ONE `col_types` builder, which takes `fold_case: impl Fn(&str) -> String` alongside its table selection so that `extract_all_column_types` can pass `str::to_uppercase` and `involved_table_columns` (`pushdown/joins/planning.rs`) can pass `str::to_ascii_uppercase`, preserving a fold divergence this feature's Background records as UNREACHABLE — `resolve_table_schema` (`adapter/pushdown/file_resolution.rs:640`) maps every Iceberg field through `f.name.to_uppercase()` before `build_virtual_tables` declares it, so no name carrying a lowercase non-ASCII letter reaches either wrapper, and `tests/e2e_non_ascii_identifier_test.rs::non_ascii_table_and_column_stay_queryable` pins that live against a Docker Exasol container by serving an Iceberg `straße` column as `STRASSE`
* *WHEN* the adapter builds the `(UPPERCASE name, Exasol type)` list for a single-table request, or for one named table of a join
* *THEN* `column_types` SHALL take exactly ONE parameter besides `request` — the table selection — and the `fold_case` parameter SHALL be REMOVED, because a parameter whose two arguments cannot produce different output is a decision the builder declined to make with nothing to decide
* *AND* `column_types` SHALL apply the Unicode `str::to_uppercase` in its OWN body, and MUST NOT apply `str::to_ascii_uppercase`, because `to_uppercase` is the fold every reachable name already carries — it is `resolve_table_schema`'s own fold, and the fold the shared `column_exa_type` lookup applies on the consuming side, inside the SAME module as the builder — so the builder converges on its own module's consumer rather than leaving that consumer's fold unpaired
* *AND* both wrappers SHALL survive with UNCHANGED signatures and declaration sites — `extract_all_column_types` as `pub(super) fn(&Json) -> Vec<(String, String)>` in `support.rs`, `involved_table_columns` as `pub(super) fn(&Json, &str) -> Vec<(String, String)>` in `joins/planning.rs` — so NO call site of either changes: for the former the production sites `support::extract_projection` and `pushdown::handle_pushdown` plus the test sites in `grouped_agg.rs` and `topn.rs`; for the latter the production sites `joins/mod.rs::plan_join`, `joins/sql_builders.rs::render_broadcast_join` (twice), `joins/sql_builders.rs::build_n_scan_join_sql`, and `joins/rendering.rs::extract_join_projection` (twice), plus the test sites in `sql_builders.rs` and `rendering.rs`
* *AND* neither wrapper SHALL be deleted as a shallow pass-through, because each still supplies a table selection the shared builder does not choose — `tables.first()` versus the find-by-name closure — so each remains a partial application that names a decision rather than a body forwarding the same arguments
* *AND* `column_types`' selection parameter SHALL stay a selection CLOSURE and MUST NOT be reshaped into an `Option<&str>` table name or any other data-shaped mode argument, because reshaping it edits a parameter this scenario is not removing and would change both call sites for no observable gain
* *AND* every comment asserting the removed divergence SHALL be reworded or deleted rather than left standing, because a preserved sentence naming a fold that no longer exists is a fresh instance of the stale-citation defect this feature deletes. FIVE carriers exist and all five are in scope: (1) `column_types`' doc comment paragraph justifying selection and fold as two parameters plus its `(#270)` tracking note SHALL be deleted; (2) `involved_table_columns`' doc-comment claim that it "maps its columns with the ASCII-only `to_ascii_uppercase` fold" SHALL be reworded to name the shared Unicode fold; (3) `involved_table_columns`' CLOSING partial-application paragraph, "A partial application of `support::column_types`, supplying the find-by-name selection and the ASCII-only fold this side has always applied", SHALL DROP "and the ASCII-only fold this side has always applied" while KEEPING its find-by-name selection clause, because after the change this side supplies no fold at all; (4) `column_exa_type`'s doc sentence "`involved_table_columns`' ASCII-folded keys agree for every column name the adapter can declare — `resolve_table_schema` Unicode-uppercases names before declaring them, so no declarable name can differ between the two folds" SHALL be reworded so the agreement claim names the SINGLE fold both builders now apply instead of an ASCII-folded key set no builder produces, KEEPING the `resolve_table_schema` premise and leaving the `type`-tag paragraph intact; and (5) the sentence in `column_exa_type_resolves_unicode_folded_list_and_misses_ascii_folded_list`'s doc comment naming `involved_table_columns` as the producer of the ASCII-folded list SHALL be reworded to describe its `col_types` literal as a CONSTRUCTED ASCII-folded list that no builder produces, keeping the test's own falsifiability rationale intact
* *AND* the fold PAIRING this change alters SHALL be named rather than left silent: `joins/rendering.rs::referenced_side_columns` narrows `involved_table_columns`' names by membership in the set `collect_side_column_names` builds with `to_ascii_uppercase`, so a pair that folded identically before now folds differently, and its agreement rests SOLELY on the same upstream normalization as the rest of this scenario — both sides read only names Exasol declared, which `resolve_table_schema` already Unicode-uppercased, and every such name is a fixed point of both folds. The bound if that premise ever broke SHALL be recorded accurately and MUST NOT be recorded as "a wider projection, never a dropped column": `referenced_side_columns` falls back to `full_cols` only when narrowing yields NOTHING, so a MIXED side — one column's folds disagreeing while another's agree — narrows to a non-empty subset, the fallback does not fire, and the diverging column is DROPPED from the fan-out leg while the outer wrapper still references it. A wider projection is the ALL-MISS case only
* *AND* the ASCII folds of `column_tables` and `collect_side_column_names` SHALL be left UNCHANGED, because `pushdown/pushdown-module-structure`'s "One blind traversal primitive backs every column-collecting walk" scenario forbids unifying the collect walks' folds and this scenario removes a builder parameter, not that separate divergence
* *AND* the scan-driving SQL for every single-table pushdown request and the join SQL for every join shape MUST each be byte-identical to their pre-merge output EXCEPT for the scan spec's `storage` value

### Scenario: The three type-rewrite guards read their type family from the shared classifier

* *GIVEN* the same three guards' hand-written Exasol type-string predicates — `starts_with("VARCHAR") || starts_with("CHAR")`, the exact match `== "DATE"`, and `starts_with("DECIMAL")` — spelled out once per guard against the family vocabulary `scan-types/type-mapping-module-structure` already records as the `ExaTypeClass` enum and the `classify_exa_type` function in `types/mapping.rs`
* *WHEN* a guard decides what to do with a resolved Exasol type string
* *THEN* each of the three guards SHALL obtain its type family by calling `classify_exa_type` and SHALL retain NO `starts_with` test and NO string equality test against an Exasol type string
* *AND* the classifier's contract SHALL remain owned by `scan-types/type-mapping-module-structure` and is consumed here, NOT restated — in particular its `Decimal` predicate stays `starts_with("DECIMAL")` with no open paren, so the bare argumentless string `DECIMAL` keeps classifying as DECIMAL in all three guards exactly as it does today
* *AND* the two `Option<Json>`-returning guards SHALL each match EXHAUSTIVELY over `Option<ExaTypeClass>` with NO wildcard arm, so a variant added to `ExaTypeClass` later becomes a compile error at each guard rather than a silent decline
* *AND* those two guards' arm sets SHALL differ in exactly ONE arm, `Decimal`: `guard_like_subject` SHALL decline it alongside `Other` and the lookup miss, while `coerce_string_position_arg` SHALL coerce it through `wrap_decimal_to_varchar`; that difference SHALL remain a visible match arm and MUST NOT be abstracted behind a coercion-policy trait, a shared dispatch table, or a parameter, because one closed variation between two functions reads better as two arms than as an indirection
* *AND* `is_bare_decimal_column` SHALL remain a two-way `Decimal`-versus-everything-else test and MAY use a non-exhaustive form, because a family added later genuinely IS "not DECIMAL" for this guard, so exhaustiveness would force an edit that could only restate the same answer
* *AND* the column-lookup miss SHALL stay each guard's OWN branch and MUST NOT be routed through the classifier: no guard SHALL pass a placeholder or sentinel string in place of an absent type, per the recorded requirement that `classify_exa_type` take a non-optional `&str`
* *AND* `wrap_decimal_to_varchar` and `wrap_cast_to_varchar` SHALL be unchanged, and the `decimal_to_varchar_exasol` synthetic node and its `vs-expression` rendering SHALL be unchanged — only the dispatch that ROUTES to them moves
* *AND* the scan-driving SQL generated for every pushdown request MUST be byte-identical to its pre-substitution output EXCEPT for the scan spec's `storage` value, which `storage-access/storage-backend-enum` re-encodes as an externally-tagged backend variant over a byte-identical payload, and which `storage-access/scan-spec-credential-reference` then replaces with a connection reference or a sealed envelope over that same payload
