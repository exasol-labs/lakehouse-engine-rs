# Feature: Type Mapping Module Structure

Gives each repeated type-classification shape in the Arrow/Exasol mapping one implementation, so a type added or reclassified lands in one place. The feature constrains where the mapping lives, not what it returns.

## Background

* Every scenario is a pure refactor. The scenarios of `scan-types/type-mapping`, `datafusion-scan/scan-execution`, `datafusion-scan/scan-execution-value-conversion`, `vs-adapter/create-virtual-schema`, and the `pushdown-planning*` family stay accurate and unedited, and their suites are the characterization gate for "behavior unchanged".
* The Arrow-to-Exasol table is a compliance surface (CLAUDE.md § Data types), so "behavior unchanged" means byte-identical output. The byte-identity holds over the reachable input domain, which is every string this repo's producers emit. The unreachable inputs where consolidation changes the answer are named per parser in the DECIMAL-parser scenario.
* A helper whose whole body calls another helper with the same arguments is a pass-through, a shallow-module red flag. Each consolidation deletes the duplicate instead of keeping a wrapper. A wrapper that supplies arguments the shared helper does not choose is a partial application and may stay. `extract_all_column_types` and `involved_table_columns` each supply their own table selection to `support::column_types` and supply no case fold, so both survive. `pushdown/pushdown-col-types-consolidation` owns the shared builder's contract.
* `Json` in the adapter modules is an alias for `serde_json::Value`. Relocating the two JSON-shaped mapping functions gives `types/mapping.rs` a `serde_json` import. The dependency direction stays correct, because `adapter` depends on `types` and never the reverse.
* This crate's CI gate is `cargo clippy --workspace --all-targets -- -D warnings`, under which an unused non-`pub` item fails the build.
* `classify_exa_type` is `pub` to keep the change API-neutral. Narrowing it to `pub(crate)` is deferred to a separate API-pruning change, which is what keeps the "public API gains exactly two items" clause true. `lakehouse-engine` ships as a UDF `.so` with no out-of-crate consumer.
* `pushdown/pushdown-module-structure` owns the three pushdown guards' file set and which guards call `classify_exa_type`. This feature owns what `classify_exa_type` returns.
* The shared catalog-decimal guard `(1..=36).contains(&precision) && scale <= precision` is strictly narrower than `precision <= 36 && scale <= 36`, so `0 <= p,s <= 36` still holds and every `DECIMAL` string reaching `exasol_type_to_json` and `sum_emit_type` stays inside the parser's `u8`/`i8` range. The Iceberg and Unity Catalog producers (`iceberg_primitive_to_exasol`, `spark_primitive_to_exasol`) share that one guard.

## Scenarios

### Scenario: One arm list decides both the Exasol type string and the JSON-fallback flag

* *GIVEN* `arrow_to_exasol_type` and `needs_json_fallback` in `crates/lakehouse-engine/src/types/mapping.rs`, which each walk their own copy of the same Arrow arm list — Boolean, Int8/16/32/64, UInt8/16/32/64, Float32/64, Utf8, LargeUtf8, Date32, `Timestamp(_, _)`, in-range `Decimal128` — and each close with the same wildcard fallback
* *WHEN* the adapter resolves a column's Exasol type, or the scan decides whether a column needs JSON serialization
* *THEN* exactly one classifier in `types/mapping.rs` SHALL own that arm list, and both functions SHALL read their answer from it rather than re-matching on `DataType`
* *AND* the classifier SHALL encode the JSON-fallback flag EXPLICITLY rather than deriving it from the returned type string, because `Utf8` and `LargeUtf8` map to `VARCHAR(2000000)` with NO JSON fallback while an out-of-range `Decimal128` maps to the SAME string WITH one — the string alone cannot separate them
* *AND* the classifier SHALL be declared private to `types/mapping.rs`, because `arrow_to_exasol_type` and `needs_json_fallback` are its only consumers and hiding the arm list entirely is what makes the module deep
* *AND* `arrow_to_exasol_type` SHALL keep its `fn(&DataType) -> String` signature and `needs_json_fallback` its `fn(&DataType) -> bool`, so none of `needs_json_fallback`'s FOUR call sites changes — `adapter/pushdown/topn.rs` (lines 337 and 1230), `scan/join_scan.rs` (line 233), and `scan/raw_scan.rs` (line 367)
* *AND* `arrow_to_exasol_type` SHALL be retained as `pub` because it is the only public name for the Arrow-to-Exasol-string direction that CLAUDE.md § Data types documents as a compliance surface, and its inverse `exasol_type_to_arrow` is public and paired with it. This SUPERSEDES the clause's earlier reason — that the function has NO call site anywhere in the crate, every reference to it outside its own definition being a doc comment or a test, so removing it would be a scope ADD beyond issue #176's deduplication mandate. The direct-storage catalog kind declares its columns from Parquet footers, which carry Arrow types, so the function now HAS an in-crate consumer and is retained because it is used
* *AND* `arrow_value_at` (`scan/convert.rs`) SHALL NOT consume the classifier, because its dispatch key is the Arrow `DataType` and its arms carry conversion logic the classifier does not model — the NaN domain error for `Float32`/`Float64` and the `i64::MAX` overflow fallback for `UInt64` — so routing it through the classifier would add indirection without removing duplication
* *AND* every existing assertion in the `types/mapping.rs` test module MUST pass unedited, because the new consumer changes no arm, no guard, and no returned string

### Scenario: One DECIMAL parser serves every Exasol type-string consumer

* *GIVEN* the canonical private `parse_decimal_args` in `types/mapping.rs` and the two hand-rolled `strip_prefix("DECIMAL(")` copies that re-derive it — one in `exasol_type_to_json`, one in `sum_emit_type` (`adapter/pushdown/grouped_agg.rs`)
* *WHEN* any of the three reads the precision and scale out of an Exasol `DECIMAL` type string
* *THEN* `parse_decimal_args` SHALL be the only implementation, declared `pub(crate)`, and both copies SHALL be deleted rather than retained as wrappers
* *AND* the parser SHALL keep its present contract unchanged — an already-uppercased and already-trimmed input, `(p, s)` returned as `(u8, i8)`, an absent scale defaulting to `0`, and `None` for anything that is not a well-formed `DECIMAL` declaration
* *AND* `sum_emit_type` MUST NOT gain an uppercasing step, because every producer of its `col_ty` argument already emits uppercase and adding one would change the result for a lowercase input
* *AND* `exasol_type_to_json` SHALL serialize the parsed scale as a SIGNED JSON number, so a negative Arrow decimal scale can never wrap into a large unsigned value
* *AND* a unit test SHALL pin the NEW answer at EVERY input class where consolidation changes it, stated separately per parser because the two profiles differ. For `sum_emit_type` the divergence set is defined by two INVARIANTS rather than by enumeration, because today it echoes the raw scale slice verbatim and discards the precision entirely. Over an input of the form `DECIMAL(<precision>,<scale>)`: (a) every scale whose text is not the canonical `i8` rendering diverges — untrimmed whitespace, a leading `+`, leading zeros, non-numeric text, a further comma, empty — because today that raw text is interpolated unchanged where after consolidation only a canonical rendering can emerge; and (b) every precision `parse_decimal_args` rejects diverges — outside `u8`, negative, non-numeric, empty — because today the precision is bound as `_p` and never read, so an unparseable precision still yields a `DECIMAL(36,…)` answer. The representative inputs below MUST each be pinned, and any further input satisfying either invariant is a divergence of the same class
* *AND* `exasol_type_to_json` SHALL have exactly THREE such classes: an absent scale (`DECIMAL(10)`) moves from a VARCHAR object to a decimal object of scale `0`; a precision or scale outside the parser's `u8`/`i8` range (`DECIMAL(300,2)`, `DECIMAL(10,200)`) moves from a decimal object to a VARCHAR object; and a negative scale (`DECIMAL(10,-2)`) moves from a VARCHAR object to a decimal object of scale `-2`. A three-argument input (`DECIMAL(10,2,3)`) and an empty argument list (`DECIMAL()`) are NOT divergences — both already fall through to VARCHAR before and after
* *AND* `sum_emit_type`'s representative inputs SHALL be: an absent scale (`DECIMAL(10)`) moves from `DOUBLE PRECISION` to `DECIMAL(36,0)`; an untrimmed scale (`DECIMAL(10, 2)`) moves from `DECIMAL(36, 2)` to `DECIMAL(36,2)`; a leading-`+` scale (`DECIMAL(10,+2)`) moves from `DECIMAL(36,+2)` to `DECIMAL(36,2)`; a non-numeric scale (`DECIMAL(10,X)`) moves from `DECIMAL(36,X)` to `DOUBLE PRECISION`; a scale outside `i8` (`DECIMAL(10,200)`) moves from `DECIMAL(36,200)` to `DOUBLE PRECISION`; a three-argument input (`DECIMAL(10,2,3)`) moves from `DECIMAL(36,2,3)` to `DOUBLE PRECISION`; a precision outside `u8` (`DECIMAL(300,2)`) moves from `DECIMAL(36,2)` to `DOUBLE PRECISION`; and a non-numeric precision (`DECIMAL(X,2)`) moves from `DECIMAL(36,2)` to `DOUBLE PRECISION`. Inputs two through six are instances of invariant (a); the last two are instances of invariant (b). The absent-scale input is the one representative neither invariant generates — with no comma there is no scale text to diverge, and a precision `parse_decimal_args` rejects does NOT diverge here (`DECIMAL(X)` is `DOUBLE PRECISION` both before and after), so the move comes solely from `parse_decimal_args` defaulting an absent scale to `0` where `sum_emit_type` today declines the input entirely
* *AND* `sum_emit_type` SHALL thereby GAIN a whitespace-trimming step it does not have today, because `parse_decimal_args` trims each argument before parsing; this is the untrimmed-scale class above and is an intended consequence of consolidation, not an incidental one
* *AND* every input class above MUST be unreachable from every producer in this repo, argued PER PRODUCER rather than by one universal bound, because no such universal bound holds: `iceberg_primitive_to_exasol` and `spark_primitive_to_exasol` (`types/mapping.rs`) each emit a `DECIMAL` string only through the ONE shared `catalog_decimal_to_exasol` guard `scan-types/type-mapping` owns — branching on the extracted predicate `exasol_representable_catalog_decimal`, `1 <= p <= EXASOL_DECIMAL_MAX_PRECISION (36) && s <= p` over unsigned precision and scale — and return `VARCHAR(2000000)` otherwise, so `0 <= p,s <= 36` holds by that single guard rather than by any external claim or by two guards agreeing, and `iceberg_type_to_exasol` and `column_source_type_to_exasol` only delegate to them; `exasol_type_from_json` always emits both arguments and reads each from an unsigned JSON number under a `p <= 36 && s <= 36` guard, so `0 <= p,s <= 36` — though it does NOT check `s <= p`, which is deliberate and is NOT folded into the shared guard, because its input is Exasol's own `dataType` JSON for a type Exasol already accepted rather than catalog wire input; and `arrow_to_exasol_type` CAN render a negative or `s > p` scale, since its guard is `*p <= 36 && *s <= 36` over an `i8` scale with no lower bound and no `s <= p` check, but its ONE producer is the direct-storage kind's Parquet-footer column list, reaching it through the scan-spec tag vocabulary's lossless round trip, and the Apache Parquet format constrains its `DECIMAL` logical type to a precision above zero and a scale between zero and the precision inclusive, so `1 <= p` and `0 <= s <= p` hold on arrival and the guard admits only pairs with `0 <= s <= p <= 36`. This SUPERSEDES the clause's earlier `arrow_to_exasol_type` segment, which concluded from the function having NO call site anywhere in the crate that its output reaches neither `exasol_type_to_json` nor `sum_emit_type`; the recorded bound `0 <= p,s <= 36` is unchanged and now rests on the producer's input domain rather than on the absence of a producer
* *AND* the Arrow-input guard MUST NOT be folded into the shared catalog predicate, because that predicate takes an UNSIGNED scale and the Arrow one is a SIGNED `i8`, so the fold would admit a negative scale that Exasol rejects — the separation `scan-types/type-mapping` records deliberately
* *AND* `arrow_type_from_tag`'s lowercase `decimal128(p,s)` parse SHALL stay a separate implementation and SHALL NOT be folded behind a prefix parameter, because it reads the internal `ScanSpec::logical_schema` tag vocabulary rather than the Exasol SQL type grammar — a different wire format, changing for a different reason, and one that requires both arguments where `parse_decimal_args` defaults an absent scale to `0`
* *AND* no prefix parameter SHALL be added to `parse_decimal_args`, because every remaining consumer passes the same `DECIMAL(` prefix and a single-valued parameter is the decision-the-module-declined-to-make that `/speq:design-philosophy` rejects

### Scenario: The Exasol type string and VS dataType JSON conversions live in the type-mapping module

* *GIVEN* `exasol_type_to_json` (private in `adapter/mod.rs`) and its inverse `exasol_type_from_json` (`pub(super)` in `adapter/pushdown/support.rs`) — a matched pair over one grammar, neither reading any adapter or protocol state
* *WHEN* the adapter declares a `createVirtualSchema` column type, or reads a declared column or select-list type back off a pushdown request
* *THEN* both functions SHALL live in `crates/lakehouse-engine/src/types/mapping.rs` beside `arrow_to_exasol_type` and `exasol_type_to_arrow`, each declared `pub(crate)` — the narrowest visibility that reaches every call site
* *AND* every call site SHALL name the relocated path: the one `exasol_type_to_json` site in `adapter/mod.rs`, and the eight `exasol_type_from_json` sites spread across `adapter/pushdown/support.rs`, `adapter/pushdown/grouped_agg.rs`, `adapter/pushdown/file_resolution.rs`, and `adapter/pushdown/joins/planning.rs`
* *AND* the five existing unit tests for the two functions SHALL move to the `types/mapping.rs` test module with every test name and every asserted value unchanged
* *AND* the module doc comment of `types/mapping.rs` SHALL name all three representations the module now owns — the Arrow `DataType`, the Exasol SQL type string, and the VS `dataType` JSON object — so a reader landing in the module reads its scope there
* *AND* `extract_all_column_types` (`support.rs`) and `involved_table_columns` (`joins/planning.rs`) SHALL NOW be expressed on ONE shared builder, `support::column_types`. This clause's earlier `MUST NOT be merged` was a SCOPE FENCE around the relocation change, deferring the merge to issue #265; issue #265 has delivered the merge, so the fence no longer holds. `pushdown/pushdown-col-types-consolidation` owns the shared builder's contract — its parameters, what it absorbs, and each wrapper's signature and file — and this feature SHALL neither restate that contract nor forbid it, exactly as it keeps owning WHAT `classify_exa_type` returns while `pushdown/pushdown-module-structure` owns how each guard branches on the result. That owner name SHALL be `pushdown/pushdown-col-types-consolidation` and MUST NOT stay `pushdown/pushdown-module-structure`, because issue #265 split the builder's contract out into that feature, which is also where issue #270's removal of the builder's `fold_case` parameter is recorded — so a reader following this clause reaches the current owner rather than a superseded one
* *AND* the BEHAVIORAL contract of both relocated functions SHALL remain owned by the features that already specify it, because only the physical location moves — this feature claims where the code lives, never what it returns. For `exasol_type_from_json` that owner is `pushdown/pushdown-planning`, which names the function directly in three recorded clauses; those `pushdown/pushdown-planning` parentheticals stay correct and MUST NOT be retargeted at this feature. `exasol_type_to_json` is named by no recorded scenario at all — its output is specified behaviorally as the `createVirtualSchema` column `dataType` JSON by `vs-adapter/create-virtual-schema`, and that indirect ownership is likewise unchanged by the move

### Scenario: The Arrow-to-Value converter dispatches on one flat arm per Arrow type

* *GIVEN* `arrow_value_at` in `crates/lakehouse-engine/src/scan/convert.rs`, whose `DataType::Int64 | DataType::UInt32 | DataType::UInt64` arm re-matches on the same `dt` and closes with an `unreachable!()` that only the outer OR-pattern makes necessary
* *WHEN* the scan converts an `Int64`, `UInt32`, or `UInt64` column value to an SDK `Value`
* *THEN* the converter SHALL carry three flat top-level arms — one per `DataType` — each holding the downcast and conversion that arm performs today
* *AND* the inner `match dt` and the `unreachable!()` SHALL both be deleted, so the function retains no unreachable branch
* *AND* the produced `Value` MUST be unchanged for every input: `Value::Int64` for `Int64` and for `UInt32`, and for `UInt64` a `Value::Int64` at or below `i64::MAX` and a `Value::Numeric` of scale `0` above it
* *AND* the wildcard display-string fallback arm SHALL stay a wildcard match on `DataType` and MUST NOT be routed through the Arrow classifier, per the classifier scenario's exemption

### Scenario: One classifier names the Exasol type-string families the pushdown guards branch on

* *GIVEN* the three pushdown guards `guard_like_subject`, `is_bare_decimal_column`, and `coerce_string_position_arg` (`adapter/pushdown/support.rs`), which each branch over the same coarse Exasol-type-string family vocabulary — a `VARCHAR` or `CHAR` prefix, the exact string `DATE`, a `DECIMAL` prefix, and everything else — but each consume a DIFFERENT subset of it: `coerce_string_position_arg` uses all four families; `guard_like_subject` uses three, collapsing `DECIMAL` into the same declining branch as everything else; and `is_bare_decimal_column` is a two-way `DECIMAL`-versus-rest test
* *WHEN* a later change needs that family split
* *THEN* `types/mapping.rs` SHALL expose an `ExaTypeClass` enum with exactly the variants `Character`, `Date`, `Decimal`, and `Other`, and a `classify_exa_type` function taking an Exasol type string and returning that enum
* *AND* the function SHALL reproduce the guards' present predicates EXACTLY, pinned literally so no equivalent-looking variant can pass: `Character` iff the string `starts_with("VARCHAR")` OR `starts_with("CHAR")`; `Decimal` iff it `starts_with("DECIMAL")` with NO open paren — an implementation testing `starts_with("DECIMAL(")` MUST be rejected, because it silently diverges from all three guards on the bare string `DECIMAL`; `Date` iff the string EQUALS `DATE` exactly; `Other` otherwise. Adopting it is then a behavior-preserving substitution rather than a rewrite
* *AND* `classify_exa_type` SHALL take a NON-optional `&str`, because the column-lookup miss that all three guards ALSO decline on is not a type family and cannot be expressed by the classifier; that `Option<&str>` stays the caller's own branch, so #265's substitution replaces each guard's type-string match arms only and never its lookup handling
* *AND* both items SHALL be declared `pub`. The original reason was that a `pub(crate)` item with no consumer fails this crate's `-D warnings` clippy gate as dead code; that reason is DISCHARGED, because issue #265 supplied the consumers. `pub` is RETAINED regardless, and NOT because this feature's "public API gains exactly two items" clause forbids narrowing — that clause is amendable and settles nothing. `lakehouse-engine` ships as a UDF `.so` with no out-of-crate consumer, so both items are public API nothing outside the crate can call, and narrowing them to `pub(crate)` is the right end state; it is simply not issue #265's, whose contract is that no behavior and no API changes. `pub` is retained SOLELY to keep that diff API-neutral, and the narrowing SHALL be deferred to a separate API-pruning change rather than smuggled into a refactor that promises byte-identity
* *AND* the three guards MUST NOT be rewired in the change that introduces the classifier, because issue #265 owns that file set and splitting it across two changes would leave neither reviewable on its own; that rewiring is specified by `pushdown/pushdown-module-structure`, which owns the guards, and this feature SHALL NOT restate how any guard branches
* *AND* a unit test SHALL pin these representative strings: `VARCHAR(4) ASCII` and `CHAR(2)` as `Character`; `DECIMAL(20,0)` AND bare `DECIMAL` with no arguments as `Decimal` — the bare case is what separates the correct predicate from `starts_with("DECIMAL(")`, so omitting it leaves the contract untested; `DATE` as `Date`; and `TIMESTAMP` and `DOUBLE PRECISION` as `Other`, so #265's substitution is verifiable against a fixed contract
* *AND* the doc comment on `classify_exa_type` SHALL name its actual consumers — the three `adapter/pushdown/support.rs` guards — and SHALL NOT state that the guards run their own predicates independently nor that the classifier is not yet wired into them, because both ceased to be true when issue #265 landed; the guards' own `starts_with` and equality tests are gone, so a comment predicting a future consumer would misdescribe the code

### Scenario: Behavior is unchanged across the refactor

* *GIVEN* the pre-refactor unit and integration suites for the type-mapping, scan-execution, and pushdown-planning layers
* *WHEN* the suites run against the refactored code
* *THEN* every test MUST pass with no change to any test assertion or expected value, and the only permitted test edits are the module a relocated test lives in and the import path it names
* *AND* the Exasol type string returned by `arrow_to_exasol_type`, `iceberg_type_to_exasol`, `exasol_type_from_json`, and `sum_emit_type` MUST be byte-identical to the pre-refactor output for every input any producer in this repo emits
* *AND* the `createVirtualSchema` column `dataType` JSON MUST be byte-identical to the pre-refactor output, and the scan-driving SQL generated for a given pushdown request MUST be byte-identical to it EXCEPT for the scan-spec `storage` value, which this refactor does not touch and which `storage-access/storage-backend-enum` re-encodes as a tagged backend variant and `storage-access/scan-spec-credential-reference` then replaces with a connection reference or a sealed envelope
* *AND* the public API of the crate SHALL gain exactly two items — `ExaTypeClass` and `classify_exa_type` — and SHALL lose none
