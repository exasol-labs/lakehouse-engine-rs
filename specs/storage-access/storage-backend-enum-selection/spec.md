# Feature: Storage Backend Selection

Defines how every consumer carries a storage backend (`StorageBackend`) without naming a variant, which sites select a backend from input, and which modules may name a variant. This feature covers the static selector that parses the CONNECTION, the two vended selectors (one for Iceberg REST, one for Unity Catalog), the shared home of vended policy and construction, the source probes that guard these rules, and the store-address parameter that keeps CONNECTION credentials out of vended resolution.

## Background

* **The S3 payload type itself is NOT edited.** Its field set, its field order, its serde attributes, its default, its secret-value list, and its three unit tests are untouched. The backend's S3 variant WRAPS it. Every construction of the S3 payload in production and test code stays as written; only the places that HOLD, PASS, or MATCH a storage backend gain the wrapping layer. Inlining the seven fields onto the variant was rejected: it would edit the one type whose serde encoding `catalog/catalog-crate-structure` pins field-for-field, for no gain the wrapper does not already deliver.
* **One shared mapping is the single source of the six iceberg S3 config keys.** The keys are `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_SESSION_TOKEN`, and `S3_PATH_STYLE_ACCESS`; the first four are inserted only when non-empty, the session token only when present, and path-style always. The Iceberg file-IO builder folds that map into its configuration, and the REST catalog builder merges it into its props map, so neither declares a key of its own. `decision-log.md` [3] records the line-by-line evidence that the two pre-refactor mappings are identical.
* **Iceberg REST compliance is checked and unchanged.** The vended credential-source selection and the longest-prefix merge implement the `storage-credentials`-before-`config` rule and the longest-`prefix` rule of `apache/iceberg` `open-api/rest-catalog-open-api.yaml` (main), and their logic moves into the S3 arm VERBATIM. This feature introduces no deviation and fixes none, and it changes no file pruning, no snapshot or manifest reading, no delete-file handling, and no type mapping. `decision-log.md` [8] carries the normative quotations.
* **This feature replaces the "ONE selection site" fence with a "TWO selectors on disjoint inputs" fence, and is issue #276, slice D of six (A-F).** Slice C's clause declaring the static selector "the ONLY place a backend is SELECTED FROM INPUT" is superseded, not bent: `storage-access/pushdown-planning-cloud-credentials-vended-storage` now selects the backend from the table location's URI scheme when `use_vended_credentials` is true. Pretending that is not a selection would leave the fence technically intact and factually false, which on a credentials path is worse than no fence.
* **One selector per credential mode, chosen by ONE boolean at ONE site, on DISJOINT inputs.** The static selector selects from the CONNECTION credential shape and runs only when vending is disabled. The Iceberg REST vended selector selects from the `loadTable` response's table location and runs only when vending is enabled. Pushdown file resolution holds the single `use_vended_credentials` branch that picks between them. Neither selector reads the other's input, neither can override the other, and no path runs both. The count of DECISION POINTS is therefore still one, even though the count of SELECTORS is two.
* **The Iceberg REST vended selector takes no backend parameter, which makes the disjointness provable rather than asserted.** It once took a backend and overlaid vended values field-by-field onto the payload the static selector had chosen, which is precisely a second selector reading the first's output. Without that parameter, "the vended selector does not consult the static one" is a signature-level property that no future edit can quietly reverse.
* **Keeping ONE selector was considered and rejected on two counts.** Passing the URI scheme into the static selector would require the scheme at CONNECTION-parse time. The scheme is only known after `loadTable`, which runs later, once per table, and never on the `createVirtualSchema` path. A single selector would therefore have to be deferred past `loadTable` on every path, including the non-vended one, and would still have no answer for a request that resolves no table. Making the vended arm mutate the payload the static selector returned was rejected by this feature's own existing clause: "reaching into the payload to finish construction is exactly the knowledge this feature removes."
* **The count of modules permitted to name a variant was UNCHANGED at five by slice D.** The Iceberg REST vended selector was already on that list; only its documented ROLE changed, from overlaying credentials onto a caller-selected backend to selecting one from the anchor scheme. No module joined the list and none left it, so the fence was narrowed in prose and identical in extent.
* **`allow_http` is threaded in as a resolved virtual-schema property, so the Iceberg REST vended selector takes one non-CONNECTION parameter.** Slice C's reading is UNCHANGED: `allow_http` "arrives from the `ALLOW_HTTP` VS property and is consumed only by the S3 payload", and "the Azure backend carries no HTTP-scheme knob at all". Deriving the value from the vended `s3.endpoint`'s scheme was considered and REJECTED as a security regression. The property defaults to false, so a derivation would let a catalog vending `http://…` put vended credentials in the clear with no operator control. The parameter is NOT a CONNECTION value, so it does not weaken the rule that the vended selector reads no CONNECTION storage field. Adding a fourth backend method to expose `allow_http` was likewise rejected: it would leave the vended selector reading a CONNECTION-derived value, which is the exact coupling this feature removes.
* **The S3 payload, the ADLS credential, the wire encoding, and all three backend methods are UNEDITED.** No variant is added or removed, no field changes, no serde attribute changes, and the externally-tagged lowercase `{"s3":{…}}` / `{"adls":{…}}` encoding is byte-identical. A vended ADLS backend serializes exactly as a static one does, so every committed golden SQL fixture and scan-spec JSON fixture passes unedited.
* **The two-state ADLS credential invariant is preserved and newly exercised.** The vended ADLS arm assembles the SAS state and never the account-key state, so "both" and "neither" stay unrepresentable and `object_store`'s access-key-beats-SAS precedence stays unreachable. Slice C recorded that precedence as the reason the backend has this shape; a vended SAS is the first input that reaches the SAS state from anywhere other than the CONNECTION.
* No dependency is added and no dependency version changes.
* Issue #318 (plan `add-native-unity-catalog-client`) admits a third backend-selection site for native Unity Catalog credential vending. It supersedes both the two-selector invariant and the five-module variant-naming list (then six), but does NOT wire a new selector dispatch: the Unity Catalog vended selector is unit-tested only, and the catalog-kind-to-credential-family dispatch is deferred to #319/#320. The two existing selectors, the static one (CONNECTION shape, when `use_vended_credentials` is false) and the Iceberg REST vended one (URI scheme, when `use_vended_credentials` is true), stay unchanged.
* **Issue #330 moves vended POLICY and CONSTRUCTION into the shared home.** It supersedes the recorded clause that the shared home "SHALL own ONLY the scheme-to-variant-kind classification and MUST NOT construct a `StorageBackend` value", and the clause that the Iceberg REST vended selector "MUST NOT take a `StorageBackend`, a `ConnectionCreds`, or any other CONNECTION-derived value as a parameter". Both were written when the only shared thing was scheme classification; both are what let the two vended selectors drift.
* **The fork was at the wrong seam, and the drift is measurable.** The Iceberg REST and Unity Catalog vended selectors resolve the same output from different wire inputs. Only the scheme classification was shared; everything after it was copied. Scheme extraction, storage-host derivation, ADLS account-name derivation, the plaintext `http://` endpoint gate, and the `path_style` default were copied and stayed consistent. The `abfs://` plaintext consent gate and the S3 store-address check were NOT copied and became gaps: the Unity ADLS arm takes no `allow_http` parameter at all, so `abfs://` is always accepted and silently read over HTTPS.
* **The governing principle, stated once so a third catalog kind's author reads it rather than re-deriving it:** a catalog kind MAY fork on HOW a value is read off the wire; it MUST NOT fork on WHAT makes the resulting value acceptable. Consent gates, address rules, and target-variant decisions live in one shared home both kinds call.
* **Moving construction SHRINKS this feature's own invariant rather than widening it.** The exhaustive list of modules permitted to name a backend variant goes from SIX to FOUR: both vended selectors drop off it. That is the opposite direction from the two changes before it, which each added a module.
* **The repointed probe is strictly stronger than the two it replaces.** Before, each selector had merely to MENTION every variant name. After the repoint, the shared home must CONSTRUCT every variant, each selector must DISPATCH every vended kind, and the two enums' variant-name sets must be equal. A third backend variant therefore fails a probe at every one of the three levels instead of at two mention sites that can drift apart.
* **The Unity Catalog vended selector had no production caller when #330 landed**, verified by reference search: its only callers were its own unit tests, the catalog crate's public-surface test, and the crate-root re-exports. Delta scan execution reaches it in #319/#320. The `abfs://` gap was therefore latent, not live, which is why #330 is a follow-up rather than a #327 blocker, and why it must land BEFORE #319/#320, when the supersede cost grows.
* No dependency is added and no dependency version changes. The S3 payload, the ADLS credential, the variant set, the wire encoding, and all three backend methods are UNEDITED, so every committed golden SQL fixture and scan-spec JSON fixture passes unedited.
* **Issue #130 widens the store-address type by one addressing field.** It gains an optional `path_style` beside `endpoint` and `region`. No backend variant changes, no S3 payload field changes, and no wire encoding changes.
* **The credential-disjointness probe is unchanged.** `path_style` names none of the forbidden credential spellings. The one-construction and field-privacy rules cover the added field: it is private, read through an accessor, and the probe reads the declaration rather than a hardcoded list.
* See `storage-access/storage-backend-enum` for the backend's variants and methods, its wire encoding, and the scan's object-store registration.

## Scenarios

### Scenario: Every consumer holds a backend and no consumer names one

* *GIVEN* every production site that carries storage config from the CONNECTION object to the scan spec: in the catalog crate, the Iceberg REST vended selector, the REST catalog builder, and both namespace listings (signed and unsigned); in the adapter, the static selector, connection-configuration resolution, pushdown request handling, error redaction, pushdown handling, dispatch SQL building, pushdown file resolution, join planning, and join-side resolution together with each resolved join side's effective storage; and in the scan, the scan spec's storage field and its default, file-list registration, and the Parquet scan table
* *WHEN* the refactor lands
* *THEN* each of those SHALL hold, accept, or return a storage backend in place of a bare S3 payload, so the backend travels as one value from the CONNECTION object to the scan spec, and no site in that chain SHALL unwrap the payload to hand a bare S3 payload onwards
* *AND* the ONLY modules permitted to match on a backend variant or read its S3 payload SHALL be these six, exhaustively: the backend's own methods; the engine's single object-store registration; the Iceberg REST vended selector, which SELECTS the variant from the anchor's URI scheme and constructs the backend the vended credential source describes; the static selector, which constructs the backend at the CONNECTION-parsing entry point; the scan spec's default, which re-wraps a placeholder payload without choosing a backend from any input and so is a construction site but not a selection site; and the Unity Catalog vended selector (plan `add-native-unity-catalog-client`, issue #318), which constructs the S3 or ADLS variant from the Unity Catalog vended response's storage-location URI scheme. Test-only code in either crate MAY unwrap a payload or construct a variant, not only in a support module. No other production module SHALL name a variant, with the source-level variant probe covering BOTH vended selectors as the compensating gate
* *AND* there SHALL be EXACTLY TWO sites that SELECT a backend FROM INPUT ON THE VENDING-VERSUS-STATIC AXIS, one per credential mode, reading DISJOINT inputs: the static selector, whose variant depends on the CONNECTION credential shape and which runs only when `use_vended_credentials` is false; and the Iceberg REST vended selector, whose variant depends on the table location's URI scheme and which runs only when `use_vended_credentials` is true. A default that always re-wraps a fixed S3 placeholder is NOT a selection under this clause, because its variant depends on no input. The Unity Catalog vended selector is a THIRD selection site, admitted below, reading a disjoint Unity Catalog credential-vending input outside this two-site axis
* *AND* exactly ONE site SHALL choose between the two Iceberg-path selectors, the `use_vended_credentials` branch in pushdown file resolution, so the number of decision points on that axis stays ONE; the catalog-kind-to-credential-family dispatch that would choose the Unity Catalog vended selector is deferred to #319/#320, per the scenario below
* *AND* the Iceberg REST vended selector MUST NOT take a storage backend, the parsed CONNECTION credentials, or any other CONNECTION-derived value as a parameter, so the two selectors' input disjointness is enforced by its signature rather than by inspection of its body; its resolved `ALLOW_HTTP` parameter is a virtual-schema property and not a CONNECTION value, so it does not breach that disjointness
* *AND* because the vended selector matches on a URI SCHEME rather than on a backend variant, adding a third variant SHALL NOT break its build, so a source-level probe in the catalog crate's public-surface test SHALL EXTRACT the variant list from the backend's own source and assert every extracted name appears in the Iceberg REST vended selector's source, as the compensating gate for the compile-time failure that site cannot provide; a HARDCODED variant list SHALL NOT satisfy this clause, because it keeps passing after a third variant is added
* *AND* because the selected variant is PER TABLE LOCATION, a join SHALL carry one backend PER SIDE rather than collapsing onto one whole-spec value, and each side SHALL be read through a store built from its own backend, as `pushdown-joins/pushdown-planning-join` and `scan-aggregation/scan-execution-join` require, so no consumer ever holds a backend that names one side while another side's files are read through it. SUPERSEDES the earlier clause requiring the join planner to reject a join whose sides differ in backend variant or ADLS `account_name`: that guard is deleted, because per-side carriage removed the collapse it compensated for and backend identity was never what the scan's addressing depends on
* *AND* the static selector SHALL take the resolved `allow_http` value as a parameter and return a fully-formed backend, and connection-configuration resolution SHALL NOT change `allow_http` on the returned value afterwards, because reaching into the payload to finish construction is exactly the knowledge this feature removes
* *AND* the REST catalog builder SHALL merge the shared S3 config mapping's entries into its props map and MUST NOT insert an S3 config key of its own
* *AND* the Iceberg REST vended selector SHALL keep its name and its public status while returning a storage backend or an error, and it SHALL remain the catalog crate's ONLY Iceberg REST vended entry point, with every mechanism step crate-private
* *AND* the scan spec module SHALL publicly re-export the storage backend type beside its existing S3 payload re-export, so the scan layer's consumers reach it on the path they already import

### Scenario: The vended selector reaches the SAS state without widening the enum

* *GIVEN* the ADLS variant, which carries an account name and a two-state credential whose account-key and SAS states make "both" and "neither" unrepresentable
* *WHEN* the vended selector resolves an ADLS backend from a `loadTable` response
* *THEN* it SHALL construct the SAS state and MUST NOT construct the account-key state, so `object_store`'s access-key-beats-SAS precedence stays unreachable
* *AND* the two-state ADLS credential, the S3 payload, the backend's variant set, the backend's secret-value list, the shared S3 config mapping, and the Iceberg file-IO builder SHALL be UNEDITED, because a vended SAS is a new INPUT to the existing SAS state rather than a new state
* *AND* the wire encoding of both variants MUST be byte-identical to before, so nesting changes what encloses a backend and never its own bytes: every scan-spec JSON fixture passes UNEDITED, and of the committed golden SQL fixtures the six empty-result ones pass UNEDITED while the eighteen credential-bearing ones are regenerated by `storage-access/scan-spec-credential-reference` for their enclosing `storage` value alone
* *AND* the backend's secret-value list SHALL return the vended SAS as this backend's single secret value, so the value-based redaction that pushdown file resolution already applies covers a vended SAS exactly as it covers a static one

### Scenario: A Unity Catalog vended selector is admitted as a third backend-selection site

* *GIVEN* the invariant in "Every consumer holds a backend and no consumer names one" that there SHALL be EXACTLY TWO sites that select a backend from input, the static selector when `use_vended_credentials` is false and the Iceberg REST vended selector when it is true, with no third selector added without superseding that clause
* *WHEN* the native Unity Catalog credential-vending path lands, resolving a storage backend from a Unity Catalog temporary-table-credentials response
* *THEN* a THIRD backend-selection site, the Unity Catalog vended selector, SHALL be admitted, reading a DISJOINT input: the Unity Catalog temporary-table-credentials response shape, distinct from both the CONNECTION credential shape and the Iceberg REST `loadTable` response. This scenario SUPERSEDES the "EXACTLY TWO sites" and "no third selector" clauses accordingly
* *AND* the Unity Catalog vended selector SHALL select the backend variant from the table location's URI scheme ALONE and MUST NOT take a `warehouse`, a `region`, an existing storage backend, or any other CONNECTION-derived value as a parameter, so the three selectors' input disjointness is enforced by its signature
* *AND* the Unity Catalog vended path SHALL terminate in a storage backend value and is NOT wired into a pushdown dispatch in this plan, because Delta scan execution consumes it in #319/#320; the invariant is superseded now so the third selector is not a silent breach of the two-site rule
* *AND* the recorded clause naming "these five [modules], exhaustively" as the ONLY modules permitted to match on a backend variant or read its S3 payload, closing with "No other production module SHALL name a variant", SHALL be SUPERSEDED to admit a SIXTH module, the Unity Catalog vended selector in the catalog crate's Unity Catalog module, which constructs the S3 or ADLS variant from the Unity Catalog vended response's storage-location URI scheme. The amended exhaustive list is SIX: the backend's own methods, the engine's single object-store registration, the Iceberg REST vended selector, the static selector, the scan spec's default, and the Unity Catalog vended selector. No other production module SHALL name a variant, with the source-level variant probe covering BOTH vended selectors as the compensating gate (pinned in "The three-selector dispatch stays single-homed and probe-guarded" below)

### Scenario: The three-selector dispatch stays single-homed and probe-guarded

* *GIVEN* the admitted third selector, the Unity Catalog vended selector, and the "exactly ONE site chooses between selectors" clause of "Every consumer holds a backend and no consumer names one"
* *WHEN* the shared scheme-to-variant-kind classification and its source probe are wired, and the selector dispatch onto the Unity Catalog vended selector is left for #319/#320
* *THEN* the scheme-to-variant-KIND classification SHALL have ONE home shared by both vended selectors, mapping `s3`/`s3a` to the S3 variant kind and `abfs`/`abfss` to the ADLS variant kind in exactly one place rather than duplicated across the two vended selectors
* *AND* that shared home SHALL own ONLY the scheme-to-variant-kind classification and MUST NOT construct a storage backend value, while each vended selector constructs its OWN backend variant from its OWN disjoint credential family (the Iceberg REST selector from the Iceberg REST vended response, the Unity Catalog selector from the Unity Catalog temporary-table-credentials response), so the single-home requirement and the probe's requirement that every variant name appear in the Unity Catalog vended selector's own production source are simultaneously satisfiable rather than in conflict
* *AND* this plan SHALL NOT wire a new selector dispatch: the Unity Catalog vended selector is admitted and unit-tested but is reached by NO selector-choice site in #318, because a pushdown under the Unity Catalog kind is refused before any credential or file resolution (`catalog-kind-selection` § "A pushdown request under the Unity Catalog kind is refused as not yet executable"). The recorded clause that "exactly ONE site chooses between those two selectors", the `use_vended_credentials` branch in pushdown file resolution, therefore stays INTACT and is NOT superseded here. The catalog-kind-to-credential-family two-level dispatch that would supersede it is DEFERRED to #319/#320, when Delta scan execution first reaches the Unity Catalog vended selector, and is marked as a deferral exactly as the third selector's scan wiring is deferred in the scenario above
* *AND* a source-level probe SHALL extract the variant list from the backend's own source and assert every extracted name appears in the Unity Catalog vended selector's production source, and the existing probe asserting the same over the Iceberg REST vended selector's source SHALL remain, so the source-probe gate covers BOTH vended variant-naming selectors; a hardcoded variant list SHALL NOT satisfy either probe

### Scenario: Vended policy and construction move into the enum's own module

* *GIVEN* the recorded clause of "The three-selector dispatch stays single-homed and probe-guarded" that the shared scheme-to-variant-kind home "SHALL own ONLY the scheme-to-variant-kind classification and MUST NOT construct a `StorageBackend` value, while each vended selector constructs its OWN `StorageBackend` variant from its OWN disjoint credential family"
* *AND* the two policy rules that clause allowed to exist in ONE selector only: the `abfs://` plaintext consent gate, present in the Iceberg REST vended selector and ABSENT from the Unity Catalog one, and the S3 store-address check, present in the Iceberg REST vended selector alone
* *WHEN* vended policy and construction are given one shared home in the backend's own module, beside the scheme classification
* *THEN* that MUST-NOT-construct clause SHALL be SUPERSEDED: the shared home SHALL own the neutral vended S3 value shape, the URI-scheme and storage-host derivations, the ADLS account-name derivation, both plaintext-transport consent gates, the S3 store-address rule, and EXACTLY ONE construction function per backend variant
* *AND* the recorded exhaustive list of modules permitted to match on a backend variant or read its S3 payload SHALL SHRINK from SIX to FOUR: the backend's own module, the engine's single object-store registration, the static selector, and the scan spec's default, because NEITHER vended selector names a variant any more
* *AND* each vended selector SHALL keep its OWN wire extraction and SHALL reduce to three steps: classify the location's scheme, read its own credential family off its own wire shape, and hand the resulting neutral values to the shared construction function. The Iceberg REST selector reads a flat string map through the `storage-credentials`-before-`config` credential-source selection, and the Unity Catalog selector reads the typed temporary-table-credentials response
* *AND* a catalog kind MAY fork on HOW a value is read off the wire and MUST NOT fork on WHAT makes the resulting value acceptable, so every consent gate, every store-address rule, and every target-variant decision SHALL have exactly ONE home that both kinds call, and a second per-kind copy of any of them SHALL NOT be added
* *AND* the count of sites that SELECT a backend from input SHALL stay THREE and the count of sites that choose between the two Iceberg-path selectors SHALL stay ONE, because moving construction changes which module NAMES a variant and not which module CHOOSES a backend
* *AND* the shared construction functions SHALL be crate-private and MUST NOT join the crate's public surface, because they are mechanism steps of the one published vended entry point per catalog kind

### Scenario: The repointed source probe binds the shared home, both selectors, and both enums

* *GIVEN* the two recorded probes, each asserting that every variant name extracted from the backend's own source appears in one vended selector's production source
* *WHEN* construction moves into the shared home, so neither selector's source names a backend variant and both recorded probes would fail
* *THEN* those probes SHALL be REPOINTED rather than deleted or weakened, and the repointed gate SHALL bind at THREE levels instead of two mention sites that can drift apart
* *AND* ONE probe SHALL assert that every variant name extracted from the backend's own source appears as a type-qualified variant construction in the shared home's PRODUCTION source, which is non-vacuous because the backend's own methods name their arms through the self alias and only a construction expression spells the type-qualified form
* *AND* a per-selector probe SHALL assert that every variant name extracted from the vended-backend-kind enum's own source appears in EACH vended selector's production source, so a third vended kind still forces BOTH selectors to dispatch it
* *AND* a probe SHALL assert that the extracted variant-name SET of the vended-backend-kind enum EQUALS that of the backend, so adding a third backend variant fails that probe until a third kind exists, which fails the per-selector probes until both selectors dispatch it, which fails the construction probe until the shared home builds it
* *AND* every one of those probes SHALL extract its variant list from the enum's own source through ONE shared extractor parameterised by enum name, and a HARDCODED variant list SHALL NOT satisfy any of them
* *AND* every one of those probes SHALL read PRODUCTION source only, so text from the first test-only section onward MUST NOT satisfy it, exactly as the recorded probe already requires

### Scenario: The vended selectors take a store address that cannot carry a credential

* *GIVEN* the recorded clause that the Iceberg REST vended selector "MUST NOT take a `StorageBackend`, a `ConnectionCreds`, or any other CONNECTION-derived value as a parameter, so the two selectors' input disjointness is enforced by its signature rather than by inspection of its body", and the matching clause requiring the Unity Catalog vended selector to take no `warehouse`, `region`, or existing storage backend
* *AND* the defect those clauses cause: real Databricks AWS vends short-lived credentials with NO endpoint, and its credential type carries no region field at all, so a legal Databricks `s3://` table lands in exactly the state the Iceberg REST vended selector rejects with its "store address undetermined" error
* *WHEN* credentials are split from addressing
* *THEN* both clauses SHALL be SUPERSEDED for ADDRESSING ALONE: each vended selector SHALL take one additional parameter carrying the CONNECTION's configured store `endpoint`, `region`, and `path_style`, and carrying NOTHING else, SUPERSEDING the recorded clause naming `endpoint` and `region` alone (#130)
* *AND* the credential half of the disjointness rule SHALL be UNCHANGED: an access key, a secret key, a session token, an Azure account key, and a SAS token SHALL come from the vended response ALONE on every vended path, and MUST NEVER be read from the CONNECTION under vending
* *AND* because the signature no longer enforces that half, it SHALL be enforced MECHANICALLY rather than by prose: the new parameter's type SHALL declare EXACTLY the three addressing fields, and a source-level probe SHALL assert that its declaration names no field spelled `access_key`, `secret_key`, `session_token`, `token`, `account_key`, `sas_token`, or `password`, SUPERSEDING the recorded clause naming EXACTLY two addressing fields
* *AND* the added field SHALL be an optional boolean, because the resolution chain branches on whether the CONNECTION stated a value
* *AND* the type SHALL have EXACTLY ONE construction from the CONNECTION, declared beside it, so which CONNECTION fields are permitted to cross into vended resolution is one decision in one place rather than a struct literal repeated per call site
* *AND* that ONE-construction rule SHALL be enforced BY THE TYPE rather than by prose or by review: EVERY addressing field SHALL be declared private, reads SHALL go through accessor methods, and a source-level probe SHALL assert that the declaration keeps EVERY field private
* *AND* that probe SHALL read the field list out of the type's own declaration rather than holding a hardcoded list, so a field added later is covered without editing the probe
* *AND* passing the parsed CONNECTION credentials, a storage backend, or any other type carrying a credential field to either vended selector SHALL remain FORBIDDEN, so the superseded rule is narrowed to addressing and not dropped
* *AND* the disjointness rule's PURPOSE SHALL be restated in the spec rather than left to be inferred: it exists to stop a vended credential silently falling back to a static one, and it was never about addressing
