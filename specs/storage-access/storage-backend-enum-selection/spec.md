# Feature: Storage Backend Selection

Defines how every consumer carries a `StorageBackend` without naming a variant, which sites select a backend from input, and which modules may name a variant. This feature covers the static selector `storage_block`, the two vended selectors `resolve_vended_storage` and `resolve_uc_vended_storage`, the shared home of vended policy and construction, the source probes that guard these rules, and the store-address parameter that keeps CONNECTION credentials out of vended resolution.

## Background

* **`StorageProps` itself is NOT edited.** The struct, its field set, its field order, its serde attributes, its `Default` impl, its `secret_values` body, and its three unit tests are untouched. `StorageBackend::S3` WRAPS it as the variant payload. Every `StorageProps { .. }` construction literal in production and test code stays as written; only the places that HOLD, PASS, or MATCH a storage backend gain the wrapping layer. Inlining the seven fields onto the variant was rejected: it would edit the one type whose serde encoding `catalog/catalog-crate-structure` pins field-for-field, for no gain the wrapper does not already deliver.
* **`catalog_storage_props` is the single source of the six iceberg S3 config keys.** The keys are `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_SESSION_TOKEN`, and `S3_PATH_STYLE_ACCESS`; the first four are inserted only when non-empty, the session token only when `Some`, and path-style always. `file_io` folds that map into the `FileIOBuilder` and `build_rest_catalog` merges it into its props map, so neither declares a key of its own. `decision-log.md` [3] records the line-by-line evidence that the two pre-refactor mappings are identical.
* **Iceberg REST compliance is checked and unchanged.** `select_credential_source` and `merge_vended_into_storage` implement the `storage-credentials`-before-`config` rule and the longest-`prefix` rule of `apache/iceberg` `open-api/rest-catalog-open-api.yaml` (main), and their bodies move into the S3 arm VERBATIM. This feature introduces no deviation and fixes none, and it changes no file pruning, no snapshot or manifest reading, no delete-file handling, and no type mapping. `decision-log.md` [8] carries the normative quotations.
* **This delta replaces the "ONE selection site" fence with a "TWO selectors on disjoint inputs" fence, and is issue #276 — slice D of six (A-F).** Slice C's clause declaring `storage_block` "the ONLY place a backend is SELECTED FROM INPUT" is superseded, not bent: `storage-access/pushdown-planning-cloud-credentials-vended-storage` now selects the backend from the table location's URI scheme when `use_vended_credentials` is true. Pretending that is not a selection would leave the fence technically intact and factually false, which on a credentials path is worse than no fence.
* **One selector per credential mode, chosen by ONE boolean at ONE site, on DISJOINT inputs.** `storage_block` selects from the CONNECTION credential shape and runs only when vending is disabled. `resolve_vended_storage` selects from the `loadTable` response's table location and runs only when vending is enabled. `resolve_file_list` holds the single `if creds.use_vended_credentials` that picks between them. Neither selector reads the other's input, neither can override the other, and there is no path on which both run — so the count of DECISION POINTS is still one even though the count of SELECTORS is two.
* **Deleting `resolve_vended_storage`'s backend parameter is what makes the disjointness provable rather than asserted.** Before this delta it took a `&StorageBackend` and overlaid vended values field-by-field onto the payload `storage_block` had chosen, which is precisely a second selector reading the first's output. Removing the parameter turns "the vended selector does not consult the static one" into a signature-level property no future edit can quietly reverse.
* **Keeping ONE selector was considered and rejected on two counts.** Passing the URI scheme into `storage_block` would require the scheme at CONNECTION-parse time, but the scheme is only known after `loadTable`, which runs later, once per table, and never at all on the `createVirtualSchema` path — so a single selector would have to be deferred past `loadTable` for every path including the non-vended one, and would still have no answer for a request that resolves no table. Making the vended arm mutate the payload `storage_block` returned was rejected by this feature's own existing clause: "reaching into the payload to finish construction is exactly the knowledge this feature removes."
* **The count of modules permitted to name a variant is UNCHANGED at five.** `resolve_vended_storage` was already on that list; only its documented ROLE changes, from overlaying credentials onto a caller-selected backend to selecting one from the anchor scheme. No module joins the list and none leaves it, so the fence this feature exists to hold is narrowed in prose and identical in extent.
* **`allow_http` is threaded in as a resolved virtual-schema property, so the vended selector takes one new non-CONNECTION parameter.** Slice C's reading is UNCHANGED: `allow_http` "arrives from the `ALLOW_HTTP` VS property and is consumed only by the S3 payload", and "the Azure backend carries no HTTP-scheme knob at all". Deriving the value from the vended `s3.endpoint`'s scheme instead was considered and REJECTED as a security regression — the property defaults to false, so a derivation would let a catalog vending `http://…` put vended credentials in the clear with no operator control. The parameter is NOT a CONNECTION value, so it does not weaken the rule that the vended selector reads no CONNECTION storage field. Adding a fourth method to the enum to expose `allow_http` was likewise rejected: it would leave the vended selector reading a CONNECTION-derived value, which is the exact coupling this delta removes.
* **`StorageProps`, `AdlsCred`, the wire encoding, and all three enum methods are UNEDITED.** No variant is added or removed, no field changes, no serde attribute changes, and the externally-tagged lowercase `{"s3":{…}}` / `{"adls":{…}}` encoding is byte-identical. A vended ADLS backend serializes exactly as a static one does, so every committed golden SQL fixture and scan-spec JSON fixture passes unedited.
* **The `AdlsCred` two-state invariant is preserved and newly exercised.** The vended ADLS arm assembles the SAS state and never the account-key state, so "both" and "neither" stay unrepresentable and `object_store`'s access-key-beats-SAS precedence stays unreachable. Slice C recorded that precedence as the reason the enum exists in this shape; a vended SAS is the first input that reaches the SAS state from anywhere other than the CONNECTION.
* No dependency is added and no dependency version changes.
* This delta (plan `add-native-unity-catalog-client`, issue #318) admits a third backend-selection site for native Unity Catalog credential vending. It supersedes both the enum's two-selector invariant and its five-module variant-naming list (now six), but does NOT wire a new selector dispatch: `resolve_uc_vended_storage` is unit-tested only, and the catalog-kind-to-credential-family dispatch is deferred to #319/#320. The two existing selectors — `storage_block` (CONNECTION shape, static, when `use_vended` is false) and `resolve_vended_storage` (URI scheme, vended, when `use_vended` is true) — stay unchanged.
* **This delta moves vended POLICY and CONSTRUCTION into the shared home and is issue #330.** It supersedes the recorded clause that the shared home "SHALL own ONLY the scheme-to-variant-kind classification and MUST NOT construct a `StorageBackend` value", and the clause that `resolve_vended_storage` "MUST NOT take a `StorageBackend`, a `ConnectionCreds`, or any other CONNECTION-derived value as a parameter". Both were written when the only shared thing was scheme classification; both are what let the two vended selectors drift.
* **The fork was at the wrong seam, and the drift is measurable.** `vended.rs` and `unity/vended.rs` resolve the same output from different wire inputs. Only `classify_vended_scheme` was shared; everything after it was copied. Scheme extraction, storage-host derivation, ADLS account-name derivation, the plaintext `http://` endpoint gate, and the `path_style` default were copied and stayed consistent. The `abfs://` plaintext consent gate and the S3 store-address check were NOT copied and became gaps: the Unity ADLS arm takes no `allow_http` parameter at all, so `abfs://` is always accepted and silently read over HTTPS.
* **The governing principle, stated once so a third catalog kind's author reads it rather than re-deriving it:** a catalog kind MAY fork on HOW a value is read off the wire; it MUST NOT fork on WHAT makes the resulting value acceptable. Consent gates, address rules, and target-variant decisions live in one shared home both kinds call.
* **Moving construction SHRINKS this feature's own invariant rather than widening it.** The exhaustive list of modules permitted to name a `StorageBackend` variant goes from SIX to FOUR: both vended selectors drop off it. That is the opposite direction from the last two deltas to this feature, which each added a module.
* **The repointed probe is strictly stronger than the two it replaces.** Today each selector must merely MENTION every variant name. After the repoint, the shared home must CONSTRUCT every variant, each selector must DISPATCH every vended kind, and the two enums' variant-name sets must be equal — so a third `StorageBackend` variant fails a probe at every one of the three levels instead of at two mention sites that can drift apart.
* **`resolve_uc_vended_storage` has no production caller today** — verified by reference search: its only callers are `crates/lakehouse-catalog/src/unity/vended_tests.rs`, `crates/lakehouse-catalog/tests/catalog_public_surface.rs`, and the crate-root re-exports. Delta scan execution reaches it in #319/#320. The `abfs://` gap is therefore latent, not live, which is why this is a follow-up rather than a #327 blocker — and why it must land BEFORE #319/#320, when the supersede cost grows.
* No dependency is added and no dependency version changes. `StorageProps`, `AdlsCred`, the variant set, the wire encoding, and all three enum methods are UNEDITED, so every committed golden SQL fixture and scan-spec JSON fixture passes unedited.
* **This delta widens the store-address type by one addressing field (#130).** `StaticStoreAddress` gains `path_style: Option<bool>` beside `endpoint` and `region`. No `StorageBackend` variant changes, no `StorageProps` field changes, no wire encoding changes.
* **The credential-disjointness probe is unchanged.** `path_style` names none of the forbidden credential spellings. The one-construction and field-privacy rules cover the added field: it is non-`pub`, read through an accessor, and the probe reads the declaration rather than a hardcoded list.
* See `storage-access/storage-backend-enum` for the enum's variants and methods, its wire encoding, and the scan's object-store registration.

## Scenarios

### Scenario: Every consumer holds a backend and no consumer names one

* *GIVEN* the seventeen production sites that carry storage config today — in `lakehouse-catalog`: `resolve_vended_storage` (`vended.rs`), `build_rest_catalog` (`session.rs`), `list_namespace_tables` and `list_namespace_tables_unsigned` (`namespace.rs`); in the adapter: `storage_block` (`connection.rs`), `resolve_connection_config`, `handle_pushdown_request`, and `redact_error` (`adapter/mod.rs`), `handle_pushdown` and `build_dispatch_sql` (`pushdown/mod.rs`), `resolve_file_list` (`pushdown/file_resolution.rs`), `plan_join` (`pushdown/joins/mod.rs`), `resolve_one_join_side` plus the `pub` field `ResolvedJoinSide::effective_storage` and `ResolvedJoinSide::new`'s matching parameter (`pushdown/joins/planning.rs`); and in the scan: `CommonScanSpec.storage` and its `impl Default` initializer (`scan/spec.rs`), `register_file_list` (`scan/raw_scan.rs`), and `PositionalDeleteScanTable::new` (`scan/positional_deletes.rs`)
* *WHEN* the refactor lands
* *THEN* each of those SHALL hold, accept, or return `StorageBackend` in place of `StorageProps`, so the backend travels as one value from the CONNECTION object to the scan spec, and no site in that chain SHALL unwrap the payload to hand a bare `StorageProps` onwards
* *AND* the ONLY modules permitted to match on a `StorageBackend` variant or read its S3 payload SHALL be these six, exhaustively: the enum's own methods (`storage.rs`); the engine's single object-store registration function (`scan/object_store.rs`); `resolve_vended_storage` (`vended.rs`), which SELECTS the variant from the anchor's URI scheme and constructs the backend the vended credential source describes; `storage_block` (`connection.rs`), which constructs the backend at the CONNECTION-parsing entry point; `CommonScanSpec`'s manual `impl Default` (`scan/spec.rs`), which re-wraps a placeholder payload without choosing a backend from any input and so is a construction site but not a selection site; and `resolve_uc_vended_storage` in the `unity` module of `lakehouse-catalog` (plan `add-native-unity-catalog-client`, issue #318), which constructs `StorageBackend::S3` or `StorageBackend::Adls` from the Unity Catalog vended response's storage-location URI scheme. A test-only payload unwrapper or variant construction MAY appear in ANY `#[cfg(test)]` module of either crate, not only in a support module. No other production module SHALL name a variant, with the source-level variant probe covering BOTH vended selectors as the compensating gate
* *AND* there SHALL be EXACTLY TWO sites that SELECT a backend FROM INPUT ON THE VENDING-VERSUS-STATIC AXIS, one per credential mode, reading DISJOINT inputs: `storage_block`, whose variant depends on the CONNECTION credential shape and which runs only when `use_vended_credentials` is false; and `resolve_vended_storage`, whose variant depends on the table location's URI scheme and which runs only when `use_vended_credentials` is true. A `Default` impl that always re-wraps a fixed `S3` placeholder is NOT a selection under this clause, because its variant depends on no input. `resolve_uc_vended_storage` is a THIRD selection site, admitted below, reading a disjoint Unity Catalog credential-vending input outside this two-site axis
* *AND* exactly ONE site SHALL choose between the two Iceberg-path selectors — the `use_vended_credentials` branch in `resolve_file_list` — so the number of decision points on that axis stays ONE; the catalog-kind-to-credential-family dispatch that would choose `resolve_uc_vended_storage` is deferred to #319/#320, per the scenario below
* *AND* `resolve_vended_storage` MUST NOT take a `StorageBackend`, a `ConnectionCreds`, or any other CONNECTION-derived value as a parameter, so the two selectors' input disjointness is enforced by its signature rather than by inspection of its body; its resolved `ALLOW_HTTP` parameter is a virtual-schema property and not a CONNECTION value, so it does not breach that disjointness
* *AND* because the vended selector matches on a URI SCHEME rather than on a `StorageBackend`, adding a third variant SHALL NOT break its build, so a source-level probe in `crates/lakehouse-catalog/tests/catalog_public_surface.rs` SHALL EXTRACT the variant list from this enum's own source — already reachable there through the `CATALOG_SOURCES` `include_str!` table — and assert every extracted name appears in `vended.rs`, as the compensating gate for the compile-time failure that site cannot provide; a HARDCODED variant list SHALL NOT satisfy this clause, because it keeps passing after a third variant is added
* *AND* because the selected variant is PER TABLE LOCATION, a join SHALL carry one backend PER SIDE rather than collapsing onto one whole-spec value, and each side SHALL be read through a store built from its own backend, as `pushdown-joins/pushdown-planning-join` and `scan-aggregation/scan-execution-join` require — so no consumer ever holds a backend that names one side while another side's files are read through it. SUPERSEDES the earlier clause requiring the join planner to reject a join whose sides differ in backend variant or ADLS `account_name`: that guard is deleted, because per-side carriage removed the collapse it compensated for and backend identity was never what the scan's addressing depends on
* *AND* `storage_block` SHALL take the resolved `allow_http` value as a parameter and return a fully-formed `StorageBackend`, and `resolve_connection_config` SHALL NOT mutate `allow_http` on the returned value afterwards, because reaching into the payload to finish construction is exactly the knowledge this feature removes
* *AND* `build_rest_catalog` SHALL merge `catalog_storage_props`' entries into its props map and MUST NOT insert an S3 config key of its own
* *AND* `resolve_vended_storage` SHALL keep its name and its `pub` status while returning `Result<StorageBackend, UdfError>`, and it SHALL remain the crate's ONLY vended entry point with every mechanism step crate-private
* *AND* `lakehouse_engine::scan::spec` SHALL re-export `StorageBackend` beside its existing `StorageProps` re-export, at `pub` visibility, so the scan layer's consumers reach it on the path they already import

### Scenario: The vended selector reaches the SAS state without widening the enum

* *GIVEN* the `Adls { account_name: String, cred: AdlsCred }` variant and its two-state `AdlsCred`, whose account-key and SAS states make "both" and "neither" unrepresentable
* *WHEN* the vended selector resolves an ADLS backend from a `loadTable` response
* *THEN* it SHALL construct the SAS state and MUST NOT construct the account-key state, so `object_store`'s access-key-beats-SAS precedence in `build()` stays unreachable
* *AND* `AdlsCred`, `StorageProps`, the enum's variant set, and all three of `secret_values`, `catalog_storage_props`, and `file_io` SHALL be UNEDITED, because a vended SAS is a new INPUT to the existing SAS state rather than a new state
* *AND* the wire encoding of both variants MUST be byte-identical to before this delta, so nesting changes what encloses a backend and never its own bytes — every scan-spec JSON fixture passes UNEDITED, and of the committed golden SQL fixtures the six `empty_*` pass UNEDITED while the eighteen credential-bearing ones are regenerated by `storage-access/scan-spec-credential-reference` for their enclosing `storage` value alone
* *AND* `secret_values` SHALL return the vended SAS as this backend's single secret value, so the value-based redaction `resolve_file_list` already applies covers a vended SAS exactly as it covers a static one

### Scenario: A Unity Catalog vended selector is admitted as a third backend-selection site

* *GIVEN* the invariant in "Every consumer holds a backend and no consumer names one" that there SHALL be EXACTLY TWO sites that select a backend from input — `storage_block` when `use_vended` is false and `resolve_vended_storage` when `use_vended` is true — with no third selector added without superseding that clause
* *WHEN* the native Unity Catalog credential-vending path lands, resolving a `StorageBackend` from a Unity Catalog temporary-table-credentials response
* *THEN* a THIRD backend-selection site, `resolve_uc_vended_storage`, SHALL be admitted, reading a DISJOINT input — the Unity Catalog temporary-table-credentials response shape, distinct from both the CONNECTION credential shape and the Iceberg REST `loadTable` response — and this scenario SUPERSEDES the "EXACTLY TWO sites" and "no third selector" clauses accordingly
* *AND* `resolve_uc_vended_storage` SHALL select the backend variant from the table location's URI scheme ALONE and MUST NOT take a `warehouse`, a `region`, an existing `StorageBackend`, or any other CONNECTION-derived value as a parameter, so the three selectors' input disjointness is enforced by its signature
* *AND* the Unity Catalog vended path SHALL terminate in a `StorageBackend` value and is NOT wired into a pushdown dispatch in this plan — Delta scan execution consumes it in #319/#320 — but the invariant is superseded now so the third selector is not a silent breach of the two-site rule
* *AND* the recorded clause naming "these five [modules], exhaustively" as the ONLY modules permitted to match on a `StorageBackend` variant or read its S3 payload — closing with "No other production module SHALL name a variant" — SHALL be SUPERSEDED to admit a SIXTH module, `resolve_uc_vended_storage` in the new `unity` module of `lakehouse-catalog`, which constructs `StorageBackend::S3` or `StorageBackend::Adls` from the Unity Catalog vended response's storage-location URI scheme; the amended exhaustive list is SIX — the enum's own methods (`storage.rs`), the engine's single object-store registration function (`scan/object_store.rs`), `resolve_vended_storage` (`vended.rs`), `storage_block` (`connection.rs`), `CommonScanSpec`'s manual `impl Default` (`scan/spec.rs`), and `resolve_uc_vended_storage` (`unity` module) — and no other production module SHALL name a variant, with the source-level variant probe covering BOTH vended selectors as the compensating gate (pinned in "The three-selector dispatch stays single-homed and probe-guarded" below)

### Scenario: The three-selector dispatch stays single-homed and probe-guarded

* *GIVEN* the admitted third selector `resolve_uc_vended_storage` and the "exactly ONE site chooses between selectors" clause of "Every consumer holds a backend and no consumer names one"
* *WHEN* the shared scheme-to-variant-kind classification and its source probe are wired, and the selector dispatch onto `resolve_uc_vended_storage` is left for #319/#320
* *THEN* the scheme-to-variant-KIND classification SHALL have ONE home shared by `resolve_vended_storage` and `resolve_uc_vended_storage`, mapping `s3`/`s3a` to the S3 variant kind and `abfs`/`abfss` to the ADLS variant kind in exactly one place rather than duplicated across the two vended selectors
* *AND* that shared home SHALL own ONLY the scheme-to-variant-kind classification and MUST NOT construct a `StorageBackend` value, while each vended selector constructs its OWN `StorageBackend` variant from its OWN disjoint credential family — `resolve_vended_storage` from the Iceberg REST vended response and `resolve_uc_vended_storage` from the Unity Catalog temporary-table-credentials response — so the single-home requirement and the probe's requirement that every variant name appear in `resolve_uc_vended_storage`'s own production source are simultaneously satisfiable rather than in conflict
* *AND* this plan SHALL NOT wire a new selector dispatch: `resolve_uc_vended_storage` is admitted and unit-tested but is reached by NO selector-choice site in #318, because a pushdown under the Unity Catalog kind is refused before any credential or file resolution (`catalog-kind-selection` § "A pushdown request under the Unity Catalog kind is refused as not yet executable"); the recorded "exactly ONE site chooses between those two selectors — the `use_vended_credentials` branch in `resolve_file_list`" clause therefore stays INTACT and is NOT superseded here, and the catalog-kind-to-credential-family two-level dispatch that would supersede it is DEFERRED to #319/#320, when Delta scan execution first reaches `resolve_uc_vended_storage` — marked as a deferral exactly as the third selector's scan wiring is deferred in the scenario above
* *AND* a source-level probe SHALL extract the variant list from `enum StorageBackend`'s own source and assert every extracted name appears in `resolve_uc_vended_storage`'s production source (`unity` module), and the existing probe asserting the same over `resolve_vended_storage`'s source (`vended.rs`) SHALL remain — so the source-probe gate covers BOTH vended variant-naming selectors — and a hardcoded variant list SHALL NOT satisfy either probe

### Scenario: Vended policy and construction move into the enum's own module

* *GIVEN* the recorded clause of "The three-selector dispatch stays single-homed and probe-guarded" that the shared scheme-to-variant-kind home "SHALL own ONLY the scheme-to-variant-kind classification and MUST NOT construct a `StorageBackend` value, while each vended selector constructs its OWN `StorageBackend` variant from its OWN disjoint credential family"
* *AND* the two policy rules that clause allowed to exist in ONE selector only — the `abfs://` plaintext consent gate, present in `resolve_vended_storage` and ABSENT from `resolve_uc_vended_storage`, and the S3 store-address check, present in `resolve_vended_storage` alone
* *WHEN* vended policy and construction are given one shared home in `storage.rs`, beside `classify_vended_scheme`
* *THEN* that MUST-NOT-construct clause SHALL be SUPERSEDED: the shared home SHALL own the neutral vended S3 value shape, the URI-scheme and storage-host derivations, the ADLS account-name derivation, both plaintext-transport consent gates, the S3 store-address rule, and EXACTLY ONE construction function per `StorageBackend` variant
* *AND* the recorded exhaustive list of modules permitted to match on a `StorageBackend` variant or read its S3 payload SHALL SHRINK from SIX to FOUR — the enum's own module (`storage.rs`), the engine's single object-store registration function (`scan/object_store.rs`), `storage_block` (`connection.rs`), and `CommonScanSpec`'s manual `impl Default` (`scan/spec.rs`) — because NEITHER vended selector names a variant after this delta
* *AND* each vended selector SHALL keep its OWN wire extraction and SHALL reduce to three steps: classify the location's scheme, read its own credential family off its own wire shape, hand the resulting neutral values to the shared construction function — `resolve_vended_storage` reading a flat `HashMap<String, String>` through `select_credential_source`, `resolve_uc_vended_storage` reading the typed temporary-table-credentials response
* *AND* a catalog kind MAY fork on HOW a value is read off the wire and MUST NOT fork on WHAT makes the resulting value acceptable, so every consent gate, every store-address rule, and every target-variant decision SHALL have exactly ONE home that both kinds call, and a second per-kind copy of any of them SHALL NOT be added
* *AND* the count of sites that SELECT a backend from input SHALL stay THREE and the count of sites that choose between the two Iceberg-path selectors SHALL stay ONE, because moving construction changes which module NAMES a variant and not which module CHOOSES a backend
* *AND* the shared construction functions SHALL be crate-private and MUST NOT join the crate's public surface, because they are mechanism steps of the one published vended entry point per catalog kind

### Scenario: The repointed source probe binds the shared home, both selectors, and both enums

* *GIVEN* the two recorded probes, each asserting that every variant name extracted from `enum StorageBackend`'s own source appears in one vended selector's production source — `vended.rs` and `unity/vended.rs`
* *WHEN* construction moves into the shared home, so neither selector's source names a `StorageBackend` variant and both recorded probes would fail
* *THEN* those probes SHALL be REPOINTED rather than deleted or weakened, and the repointed gate SHALL bind at THREE levels instead of two mention sites that can drift apart
* *AND* ONE probe SHALL assert that every variant name extracted from `enum StorageBackend`'s own source appears as a `StorageBackend::<Variant>` construction in the shared home's PRODUCTION source, which is non-vacuous because the enum's own method bodies spell their arms `Self::<Variant>` and only a construction expression spells the qualified form
* *AND* a per-selector probe SHALL assert that every variant name extracted from `enum VendedBackendKind`'s own source appears in EACH vended selector's production source, so a third vended kind still forces BOTH selectors to dispatch it
* *AND* a probe SHALL assert that the extracted variant-name SET of `VendedBackendKind` EQUALS that of `StorageBackend`, so adding a third `StorageBackend` variant fails that probe until a third kind exists, which fails the per-selector probes until both selectors dispatch it, which fails the construction probe until the shared home builds it
* *AND* every one of those probes SHALL extract its variant list from the enum's own source through ONE shared extractor parameterised by enum name, and a HARDCODED variant list SHALL NOT satisfy any of them
* *AND* every one of those probes SHALL read PRODUCTION source only — text from the first `#[cfg(test)]` onward MUST NOT satisfy it — exactly as the recorded probe already requires

### Scenario: The vended selectors take a store address that cannot carry a credential

* *GIVEN* the recorded clause that `resolve_vended_storage` "MUST NOT take a `StorageBackend`, a `ConnectionCreds`, or any other CONNECTION-derived value as a parameter, so the two selectors' input disjointness is enforced by its signature rather than by inspection of its body", and the matching clause requiring `resolve_uc_vended_storage` to take no `warehouse`, `region`, or existing `StorageBackend`
* *AND* the defect those clauses cause: real Databricks AWS vends short-lived credentials with NO endpoint and its credential type carries no region field at all, so a legal Databricks `s3://` table lands in exactly the state `resolve_vended_storage`'s "store address undetermined" error rejects
* *WHEN* credentials are split from addressing
* *THEN* both clauses SHALL be SUPERSEDED for ADDRESSING ALONE: each vended selector SHALL take one additional parameter carrying the CONNECTION's configured store `endpoint`, `region`, and `path_style`, and carrying NOTHING else — SUPERSEDING the recorded clause naming `endpoint` and `region` alone (#130)
* *AND* the credential half of the disjointness rule SHALL be UNCHANGED: an access key, a secret key, a session token, an Azure account key, and a SAS token SHALL come from the vended response ALONE on every vended path, and MUST NEVER be read from the CONNECTION under vending
* *AND* because the signature no longer enforces that half, it SHALL be enforced MECHANICALLY rather than by prose: the new parameter's type SHALL declare EXACTLY the three addressing fields, and a source-level probe SHALL assert that its declaration names no field spelled `access_key`, `secret_key`, `session_token`, `token`, `account_key`, `sas_token`, or `password` — SUPERSEDING the recorded clause naming EXACTLY two addressing fields
* *AND* the added field SHALL be an OPTION of boolean, because the resolution chain branches on whether the CONNECTION stated a value
* *AND* the type SHALL have EXACTLY ONE construction from the CONNECTION, declared beside it, so which CONNECTION fields are permitted to cross into vended resolution is one decision in one place rather than a struct literal repeated per call site
* *AND* that ONE-construction rule SHALL be enforced BY THE TYPE rather than by prose or by review: EVERY addressing field SHALL be declared NON-`pub`, reads SHALL go through accessor methods, and a source-level probe SHALL assert that the declaration keeps EVERY field non-`pub`
* *AND* that probe SHALL read the field list out of the type's own declaration rather than holding a hardcoded list, so a field added later is covered without editing the probe
* *AND* passing a `ConnectionCreds`, a `StorageBackend`, or any other type carrying a credential field to either vended selector SHALL remain FORBIDDEN, so the superseded rule is narrowed to addressing and not dropped
* *AND* the disjointness rule's PURPOSE SHALL be restated in the spec rather than left to be inferred: it exists to stop a vended credential silently falling back to a static one, and it was never about addressing
