# Feature: Pushdown Aggregate SQL Consolidation

Gives three hand-repeated pieces of the aggregate-pushdown SQL assembly one owner each — the König–Huygens sufficient-statistics fragments behind the STDDEV/VARIANCE merge expressions, the "CAST to the declared type unless it is the `VARCHAR(2000000)` default" rule, and the aggregate-function-name to `AggKind` mapping — split out of `vs-adapter/pushdown-planning-grouped-agg` and `vs-adapter/pushdown-planning-single-group-agg` as issue [#179](https://github.com/exasol-labs/lakehouse-engine-rs/issues/179)'s SQL-assembly scope. Every merge formula, cast decision, and detection outcome those features record is unchanged and is consumed here, not restated: this feature records only who owns each repeated construction, and that the generated SQL is byte-identical.

## Background

* Three separate duplications, three separate owners, no shared mechanism between them. They are collected in one feature because they are one issue's cleanup of one file pair (`grouped_agg.rs`, `single_group_agg.rs`) and share one verification gate, not because they share a design.
* Duplication one, the statistical merge fragments (`grouped_agg.rs:902-962`). The König–Huygens numerator `(SUM(sumsq) - SUM(sum) * SUM(sum) / NULLIF(SUM(cnt), 0))` appears SIX times across the four statistical arms, the population denominator `NULLIF(SUM(cnt), 0)` appears six times, and the sample denominator `CASE WHEN SUM(cnt) <= 1 THEN NULL ELSE SUM(cnt) - 1 END` four times. Each `Stddev*` arm re-inlines its matching `Var*` arm's ENTIRE expression twice — once inside `CASE WHEN (…) IS NULL` and once inside `SQRT(GREATEST(0.0, …))`.
* The statistical arms' correctness rests on parenthesization that no existing test can distinguish. Every current assertion is a `.contains(...)` probe — `NULLIF`, `<= 1`, `CASE`, `SQRT(`, `IS NULL`, `GREATEST`, and the negative `!contains("- 1")` — so a fragment extraction that dropped a paren, swapped a denominator, or reordered the numerator's terms would leave all six tests green while changing every returned variance. Byte-exact golden fixtures, not the existing probes, are what makes this extraction safe.
* The reconstruction is exactly composable, which is why the extraction can be byte-identical rather than merely equivalent: `var_pop = numer / pop_denom`, `var_samp = numer / samp_denom`, and `stddev_of(var) = CASE WHEN (var) IS NULL THEN NULL ELSE SQRT(GREATEST(0.0, var)) END` reproduce all four arms' current text character for character, with `numer` carrying its own outer parentheses and the `stddev_of` wrapper adding exactly one pair around its `IS NULL` subject.
* **Exasol's `GREATEST` returns NULL if ANY argument is NULL.** Captured live on the Exasol 2025.2.1 container pinned in `docker-compose.yml`: `SELECT GREATEST(0.0, NULL), SQRT(GREATEST(0.0, NULL)) FROM dual` returns NULL in BOTH columns. The claim this feature previously recorded — "Exasol's `GREATEST(0.0, NULL)` returns `0.0`, not `NULL` (returns the max of non-NULL inputs; only returns NULL if ALL inputs are NULL)" — is FALSE: it describes DataFusion's contract, not Exasol's. It was carried in this feature's own scenario clause, in `stddev_of`'s and `merge_select_items`' doc comments (`adapter/pushdown/scalar_over_agg.rs`), and in the two NULL-passthrough tests' doc comments (`adapter/pushdown/grouped_agg_tests.rs`), and is corrected in all four places. `sql-comprehension/vs-expression-translator-scalar-fns` records the same one contract with its full evidence, so the library states ONE Exasol `GREATEST` contract rather than two opposite ones; this feature cites it rather than restating the capture.
* **Correcting that record changes NO generated SQL.** No formula, no parenthesis, and no byte of any golden fixture moves, and all six `.contains(...)` merge tests pass without edits to any expected value. What changes is which fact the codebase asserts about the engine it targets.
* **The `CASE WHEN … IS NULL` guard is RETAINED even though the true contract makes it redundant.** Under Exasol's real contract `SQRT(GREATEST(0.0, NULL))` is already NULL, so the guard adds no behavior. It stays for two reasons: removing it would change SQL that golden fixtures pin byte-for-byte, for no correctness gain; and it states the NULL path at the merge site rather than making a reader derive it from `GREATEST`'s NULL contract. The `GREATEST(0.0, …)` clamp keeps its ORIGINAL and still-correct purpose, which the false claim never touched: stopping a tiny negative rounding artifact from reaching `SQRT`.
* Duplication two, the declared-type CAST rule, is written SIX times, and one of the six is a doc comment claiming to BE the shared rule. `constant_projection_sql` (`grouped_agg.rs:117-127`), the `gk_select` closure (`:626-633`), `cast_merge_items` (`:1099-1111`), `cast_to_declared_type` (`:1113-1124`), `empty_agg_sql` (`file_resolution.rs:728-745`), and the `ScalarOverAggregate` arm of `empty_grouped_sql` (`file_resolution.rs:777-783`) each re-derive "wrap in `CAST(<expr> AS <ty>)` unless `<ty>` is `VARCHAR(2000000)`". Five of the six treat an absent declared type as "no cast"; `cast_to_declared_type` alone takes a non-optional `&str`, which is why the canonical form takes an `Option`.
* The `GroupKey` and `Aggregate` arms of `empty_grouped_sql` (`file_resolution.rs:766-772`) are deliberately EXCLUDED from that consolidation and MUST stay as they are. They render `CAST(NULL AS <ty>)` UNCONDITIONALLY, with no `VARCHAR(2000000)` guard, and applying the guard there would emit a bare `NULL` whose Exasol type is not `VARCHAR` — which is the positional `selectListDataTypes` validation the cast exists to satisfy. That divergence is a correctness requirement of the zero-row shape, not a missed dedup, and this feature names it rather than folding it in.
* Duplication three, `parse_agg_item`'s arms (`single_group_agg.rs:226-301`). `SUM`, `MIN`, `MAX`, and `AVG` are four bodies identical but for the `kind:` field. The six statistical names are six bodies identical but for `kind:`. `COUNT` is genuinely different — it splits on argument presence to distinguish `COUNT(*)` from `COUNT(<arg>)` — and stays its own branch.
* A `[(name, AggKind)]` table for the statistical family already exists in this repository, in a TEST (`parse_agg_item_recognises_stat_functions`, `single_group_agg.rs:839-846`). Promoting the table into production makes that test's own table a second copy, and the test SHALL keep its literal table rather than read the production constant, because reading it would assert the constant against itself.
* The verification instrument already exists and is already scoped to this kind of change: `adapter/pushdown/dispatch_golden_tests.rs` asserts full-string equality against committed fixtures under `testdata/dispatch_golden/`, and its module doc records that "every subsequent dedup task MUST leave these ten fixtures byte-identical; a diff here is a regression, never an expected update". None of the ten covers an `AVG` or a statistical aggregate, so this feature's own gate depends on adding fixtures for those shapes first.
* Iceberg spec compliance: checked, not engaged. This feature restructures SQL string assembly and one JSON-node-to-enum mapping inside the adapter. It touches no manifest read, snapshot resolution, field-id projection, delete-file application, or type-mapping surface, so no normative requirement of the Apache Iceberg table spec applies and there is no deviation to fix or track. The same holds for the Delta Lake protocol, and for this delta specifically: correcting a doc comment about Exasol's `GREATEST` reads no table format at all.

## Scenarios

### Scenario: The sufficient-statistics fragments have one owner per denominator

* *GIVEN* `merge_select_items` (`adapter/pushdown/grouped_agg.rs`), whose four statistical arms hand-inline the König–Huygens numerator six times, the population denominator six times, and the sample denominator four times, with each `Stddev*` arm re-inlining its matching `Var*` arm's whole expression twice
* *WHEN* the adapter builds the outer merge expression for `VAR_POP`, `VAR_SAMP`, `STDDEV_POP`, or `STDDEV_SAMP`
* *THEN* the numerator, the population denominator, and the sample denominator SHALL each be built ONCE per aggregate ordinal, and a `stddev_of` helper SHALL wrap a variance expression in the `CASE WHEN (<var>) IS NULL THEN NULL ELSE SQRT(GREATEST(0.0, <var>)) END` guard, so each of the four arms becomes a single composition
* *AND* the four arms' rendered SQL MUST be byte-identical to the pre-refactor text for every aggregate ordinal — `numer / pop_denom`, `numer / samp_denom`, `stddev_of(numer / pop_denom)`, and `stddev_of(numer / samp_denom)` respectively — asserted by full-string equality against a committed pre-refactor fixture
* *AND* the numerator SHALL carry its OWN outer parentheses and `stddev_of` SHALL add exactly ONE pair around its `IS NULL` subject and NONE around its `GREATEST` argument, because that is the parenthesization the pre-refactor text has and any other nesting changes the string while leaving every `.contains(...)` probe green
* *AND* the `CASE WHEN … IS NULL` guard and the `GREATEST(0.0, …)` clamp SHALL both be preserved, and their recorded rationale SHALL be CORRECTED rather than preserved — REPLACING the recorded claim that "Exasol's `GREATEST(0.0, NULL)` returns `0.0`, not `NULL`, so a bare `SQRT(GREATEST(0.0, NULL))` would return `0.0` instead of `NULL`", which is FALSE: Exasol returns NULL if ANY argument is NULL, so `SQRT(GREATEST(0.0, NULL))` is already NULL (captured live, see Background and `sql-comprehension/vs-expression-translator-scalar-fns`)
* *AND* the guard SHALL therefore be recorded as an EXPLICIT statement of the NULL path rather than as the thing that produces it, retained because removing it would change golden-pinned SQL for no correctness gain — while the `GREATEST(0.0, …)` clamp keeps its own unchanged purpose of stopping a tiny negative rounding artifact from reaching `SQRT`
* *AND* every doc comment carrying the false claim SHALL be corrected in the same change — `stddev_of`'s and `merge_select_items`' in `adapter/pushdown/scalar_over_agg.rs`, and the two NULL-passthrough tests' in `adapter/pushdown/grouped_agg_tests.rs` — because the clause below keeps those two tests precisely for naming WHY a guard exists, and a comment naming a false reason is worse than no comment
* *AND* the correction SHALL change NO rendered SQL: every golden fixture under `testdata/dispatch_golden/` MUST stay byte-identical and every existing merge assertion MUST pass with NO change to any expected value
* *AND* the partial column names the fragments reference SHALL come from the single name owner recorded in `datafusion-scan/scan-partial-agg-column-contract`, so `merge_select_items` retains NO `PARTIAL_` string literal of its own
* *AND* the six existing `.contains(...)` merge tests — `var_pop_merge_formula_divides_by_n`, `var_samp_merge_formula_divides_by_n_minus_1`, `stddev_pop_merge_formula_uses_sqrt`, `stddev_samp_merge_formula_uses_sqrt_and_n_minus_1`, `stddev_pop_merge_null_passthrough_for_n_zero`, and `stddev_samp_merge_null_passthrough_for_n_zero_and_n_one` — SHALL be KEPT unchanged and MUST NOT be deleted as redundant to the golden fixture, because each names WHY one guard exists and a golden diff alone reports only that some byte moved

### Scenario: The declared-type CAST rule has one owner

* *GIVEN* six sites that each re-derive "wrap in `CAST(<expr> AS <ty>)` unless `<ty>` is the `VARCHAR(2000000)` default" — `constant_projection_sql`, the `gk_select` closure, `cast_merge_items`, and `cast_to_declared_type` in `grouped_agg.rs`, plus `empty_agg_sql` and the `ScalarOverAggregate` arm of `empty_grouped_sql` in `file_resolution.rs` — one of which documents itself as being that shared rule
* *WHEN* any of the six decides whether to cast an outer-wrapper expression to its Exasol-declared type
* *THEN* exactly ONE helper SHALL own that decision, taking the rendered expression and an `Option<&str>` declared type and returning the expression cast or uncast, and each of the six sites SHALL retain NO `VARCHAR(2000000)` comparison and NO `CAST(` format of its own
* *AND* the helper SHALL take an `Option<&str>` rather than a `&str`, because five of the six sites read their declared type from a `.get(i)` on a possibly-shorter list and already treat absence as "no cast"; the sixth passes `Some(declared_type)` and its behavior is unchanged
* *AND* the helper SHALL be declared `pub(super)` in `adapter/pushdown/support.rs`, the submodule that already owns the pushdown tree's shared primitives, because its consumers live in two SIBLING submodules (`grouped_agg` and `file_resolution`) rather than in one
* *AND* the `GroupKey` and `Aggregate` arms of `empty_grouped_sql` MUST NOT be routed through the helper and SHALL keep their UNCONDITIONAL `CAST(NULL AS <ty>)`, because those arms deliberately cast even to `VARCHAR(2000000)`: a bare `NULL` in a zero-row `SELECT … FROM DUAL WHERE 1=0` carries no `VARCHAR` type and would fail the positional `selectListDataTypes` check the cast exists to satisfy
* *AND* every comment asserting the rule by convention SHALL be replaced by a reference to the helper rather than left standing — in particular `cast_to_declared_type`'s doc sentence naming `cast_merge_items`, `constant_projection_sql`, and the group-key cast as the sites it mirrors, and `constant_projection_sql`'s "mirrors the group-key and aggregate cast discipline" and "matching `group_key_exasol_types`" clauses — because a preserved sentence asserting a convention the code now enforces is the stale note this consolidation deletes
* *AND* the generated SQL for every single-group, grouped, and empty-result pushdown request MUST be byte-identical to its pre-consolidation output, and every existing `dispatch_golden` fixture and grouped-aggregate assertion MUST pass with NO change to any expected value

### Scenario: Aggregate function names map to AggKind through two tables

* *GIVEN* `parse_agg_item` (`adapter/pushdown/single_group_agg.rs`), where `SUM`, `MIN`, `MAX`, and `AVG` are four bodies differing only in their `kind:` field, and the six STDDEV/VARIANCE names are six bodies differing only in their `kind:` field
* *WHEN* the adapter resolves a `function_aggregate` select-list item's function name to an `AggKind`
* *THEN* the expression-capable names SHALL be resolved through ONE `[(&str, AggKind)]` table — `SUM`, `MIN`, `MAX`, `AVG` — and the statistical names through a SECOND such table — `STDDEV` and `STDDEV_SAMP` to `StddevSamp`, `STDDEV_POP` to `StddevPop`, `VARIANCE` and `VAR_SAMP` to `VarSamp`, `VAR_POP` to `VarPop`
* *AND* the two tables SHALL stay SEPARATE and MUST NOT be merged into one, because each table's members share an argument-resolution rule the other's do not: the first resolves its argument through `arg_column_or_expr`, admitting either a bare column or a rendered expression, while the second admits a bare column only (see `vs-adapter/pushdown-planning-aggregate-extensions`)
* *AND* `COUNT` SHALL remain its own branch and MUST NOT be folded into either table, because it is the only name whose `AggKind` depends on its ARGUMENT rather than on its name — no argument yields `Count`, an argument yields `CountCol`
* *AND* an unrecognized function name SHALL still decline the aggregate pushdown by returning `None`, and a `distinct: true` item SHALL still decline ahead of any table lookup, so the two tables change how a recognized name is resolved and never which names are recognized
* *AND* the existing test `parse_agg_item` stat-family table (`parse_agg_item_recognises_stat_functions`, `single_group_agg.rs:839-846`) SHALL keep its own LITERAL `[(name, AggKind)]` pairs and MUST NOT be rewritten to iterate the production table, because a test reading the table it verifies asserts the table against itself and would pass any consistent mis-mapping
* *AND* the `AggregatePlan` produced for every function name and argument shape MUST be identical to the pre-refactor plan, and every existing detection test in `single_group_agg.rs`, `grouped_agg.rs`, and `support.rs` MUST pass with NO change to any expected value
