# Feature: Pushdown Col Types Consolidation

Gives the pushdown type-rewrite guards' `col_types` handling one owner per decision — one lookup helper, one builder, one Exasol-type-family classifier substitution — split out of `vs-adapter/pushdown-module-structure` as issue #265's own cohesive scope.

## Background

* This delta adds THREE scenarios, all of issue #265: the shared `col_types` lookup helper, the merged `col_types` builder, and the three type-rewrite guards' adoption of the recorded Exasol-type-string classifier. Every existing scenario of this feature is unchanged, and no `vs-adapter/pushdown-planning*` scenario changes, because no per-node decision moves and no generated SQL changes.
* Issue #265's blocking dependency is discharged. `datafusion-scan/type-mapping-module-structure` already records `ExaTypeClass` and `classify_exa_type` in `types/mapping.rs`, and its classifier scenario states that "#265's substitution replaces each guard's type-string match arms only and never its lookup handling". This delta satisfies that clause; the classifier's own contract stays owned by that feature and is consumed here, not restated.
* Resolving a bare column node's Exasol type is TWO decisions, and this delta keeps them in two owners on purpose: node → uppercased name → `col_types` scan belongs to `support`, and type string → type family belongs to `types::mapping`. Keeping them apart is what holds the column-lookup MISS out of the classifier, which the recorded classifier scenario requires by taking a NON-optional `&str`.
* The `col_types` list is both CONSUMED and PRODUCED with a single fold, the Unicode `to_uppercase`: the shared `column_exa_type` lookup applies it for all three type-rewrite guards, and the shared `column_types` builder applies it for both wrappers. Issue #265 shipped the builder with a `fold_case` parameter so `involved_table_columns` could keep the ASCII-only `to_ascii_uppercase` it had always applied; issue #270 removes that parameter as dead flexibility, because the two folds cannot produce different output on any name the adapter can receive. Removing it is a SIMPLIFICATION, not a correctness fix. There is consequently no asymmetry left to preserve byte-for-byte and no separate reconciling change to defer.
* The divergence is UNREACHABLE through the real Virtual Schema path, for every column name and every table, and that is a measured finding rather than an assumption. This crate uppercases each Iceberg field name ITSELF before Exasol ever sees it. `resolve_table_schema` (`adapter/pushdown/file_resolution.rs:610-644`) maps every field through `(f.name.to_uppercase(), exasol_ty)` at line 640, and that pair list is the sole input to the per-column `"name"` that `build_virtual_tables` declares in the `createVirtualSchema` response (`adapter/mod.rs:551`, the `json!` at `:576`). Exactly ONE production site declares a column name, reached from exactly ONE caller (`adapter/mod.rs:255`) whose resolver is `resolve_table_schema`, so no column name reaches Exasol un-uppercased.
* LIVE CAPTURE, the plan's task 3 gate, against the local Docker Exasol container per CLAUDE.md § Verification discipline: an Iceberg column named `straße` added to the `typed_distinct_probe` fixture is served by `SELECT COLUMN_NAME FROM SYS.EXA_ALL_COLUMNS WHERE COLUMN_SCHEMA='MY_LAKEHOUSE' AND COLUMN_TABLE='TYPED_DISTINCT_PROBE'` as `STRASSE`, NOT `STRAßE`. The full served list is `ID, C_DECIMAL_A, C_DECIMAL_B, C_DOUBLE, C_VARCHAR, C_DATE, C_TS, C_BOOL, C_PRICE, C_QTY, STRASSE`. `STRASSE` is exactly `"straße".to_uppercase()`, which is what this crate declared: Rust's full-Unicode uppercase maps `ß` to `SS`. The `ß` is therefore erased one layer UPSTREAM of anything Exasol does.
* The agreement argument STANDS unchanged and is what makes #270 byte-identical rather than merely equivalent: a name already produced by `to_uppercase` is a fixed point of both folds — `to_ascii_uppercase` changes only ASCII `a-z`, of which `to_uppercase` output contains none, while `to_uppercase` is itself idempotent, swept exhaustively over all 1,112,064 Unicode scalar values with zero exceptions. What ceases to be true is the earlier closing clause, "the guards' Unicode-folding lookup can never miss a name the ASCII-folding join-side builder produced": after #270 there is no ASCII-folding join-side builder. The lookup and BOTH wrappers now fold identically by construction, so the guards' lookup cannot miss a name either wrapper produced for a structural reason rather than an input-domain one.
* The earlier two-captures-plus-one-inference chain is REFUTED, not merely unmeasured, and both captures are re-scoped rather than deleted. CAPTURE (2) stands as fact: `CREATE TABLE FOLDPROBE.T (nüm INT, straße INT, "nüm_q" INT)` stores `NÜM`, `STRAßE`, and `nüm_q`, so Exasol's fold of a NATIVE unquoted DDL identifier is Unicode SIMPLE (one-to-one) uppercasing and preserves `ß`. It does NOT govern adapter-declared column names, because such a name never reaches Exasol carrying a `ß`. CAPTURE (1) is withdrawn as evidence that Exasol normalizes an adapter-declared name: the names it read (`ID`, `C_VARCHAR`, `C_DECIMAL_A`) are exactly what `resolve_table_schema` declared, so that observation is equally consistent with Exasol echoing the declared name verbatim. The INFERENCE joining the two — that Exasol applies its native-identifier fold to an adapter-declared JSON `"name"` — is contradicted by the live capture, which served the `ß`-collapsed form.
* ONE narrow residual remains, far weaker than the one the refuted chain carried. The agreement argument needs Exasol not to de-normalize an already-uppercase declared name back toward lowercase. Exasol's own identifier fold uppercases, so it cannot introduce lowercase, and the live capture confirms the served form IS the declared form for the one non-ASCII column measured. Every ASCII name captured earlier is consistent with the same conclusion.
* Nothing survives: #270 removes the divergence rather than naming it, and the follow-up issue the earlier bullet cited is CLOSED by this change. That bullet also carried a DESIGN REFUSAL that #270 reverses, and the reversal is recorded here rather than left implicit. The refusal was that "making either builder's fold depend on `resolve_table_schema`'s uppercasing would put one module's decision inside another module's body, which is the information leakage this plan exists to remove" (`specs/_decision/042-refactor-col-types-guard-dedup.md:158` records the same rejection in its options table). That objection no longer decides, for two reasons. FIRST, the surviving fold is selected to match the list's CONSUMER, `support::column_exa_type`, which lives in the same module as the builder — so the builder encodes its OWN module's decision, not a foreign module's, and the alternative (ASCII) is what would leave the in-module consumer's fold unpaired. SECOND, `resolve_table_schema`'s uppercasing is a BEHAVIOR-PRESERVATION premise guarded by a live test, not a fold-selection rule: the fold would still be `to_uppercase` if that premise were dropped, and only the byte-identity claim would weaken. The unreachable-input-domain STANDARD invoked above — an unnamed divergence is indistinguishable from a regression — is unchanged and is applied below to the one new cross-fold pairing #270 creates.
* ONE `col_types` fold test remains, `support.rs`'s `column_exa_type_resolves_unicode_folded_list_and_misses_ascii_folded_list`, and it characterizes no DELIVERED column name. Its two `col_types` slices are CONSTRUCTED literals, `STRASSE` and `STRAßE`, chosen because Rust's two folds disagree on `STRAßE` — which is what makes the miss assertion falsifiable. Neither literal is a list any builder produces: since #270 both builders emit Unicode-folded names only. The builder-side companion test that pinned the two wrappers' divergent folds is deleted with the parameter, because it asserted a disagreement that no longer exists.
* Four further `col_types` linear scans in the pushdown tree are NOT targets of the lookup helper, because their input is an already-resolved column-name `&str` rather than a JSON node: `project_columns`'s `type_by_upper` closure (`support.rs`), the declined-`ORDER BY` hidden-column appender (`topn.rs`), `col_type_for` (`grouped_agg.rs`), and the logical-field scan in `scan/join_scan.rs`. Three of them also answer a different question, returning an owned `String` behind a default (`VARCHAR(2000000)`, `DOUBLE PRECISION`) rather than an `Option`.
* `parse_sort_key_element` (`topn.rs`) is likewise NOT a target even though it performs the node → `type == "column"` → `name` → Unicode-fold half verbatim: it reads an `orderBy` ELEMENT wrapper rather than an expression node, it also parses the `isAscending` and `nullsLast` flags off that wrapper, and it never touches `col_types`. It resolves an identifier, not a type.
* Neither builder wrapper becomes a pass-through of the kind the sibling `datafusion-scan/type-mapping-module-structure` feature rejects. The pass-through RULE is unchanged: a pass-through calls another function with the SAME arguments, and a wrapper supplying an argument the shared builder does not choose is a partial application naming a decision. Only the EXAMPLE narrows. After #270 each wrapper here supplies a different table selection and NOTHING else — `tables.first()` versus the find-by-name closure — so that selection ALONE is what keeps each wrapper a partial application rather than a pass-through, and both wrappers survive under the same exception.
* Removing `fold_case` creates exactly ONE new cross-fold pairing, and it is named here rather than left silent. `joins/rendering.rs::referenced_side_columns` narrows `involved_table_columns`' column list by membership in the set `collect_side_column_names` builds with `to_ascii_uppercase`; both sides folded ASCII before #270 and fold differently after it. They agree for exactly ONE reason, this feature's standing one: both read only names Exasol declared, `resolve_table_schema` already Unicode-uppercased every one of them, and such a name is a fixed point of both folds. There is NO second safety net, and the failure mode if that premise ever broke is a DROPPED column rather than a wider projection. `referenced_side_columns` (`joins/rendering.rs:316-325`) falls back to `full_cols` only when narrowing yields NOTHING: a side whose `full_cols` is `[STRASSE, ID]` measured against an ASCII-folded reference set `{STRAßE, ID}` narrows to `[ID]`, which is non-empty, so the fallback does NOT fire and the fan-out leg loses `STRASSE` while the outer wrapper still renders a reference to it. Only the ALL-MISS case widens a projection; the MIXED case drops a column and yields an erroring or wrong-result wrapper.
* The collect walks' fold divergence is NOT touched by #270 and is a different divergence: `column_tables` and `collect_side_column_names` keep `to_ascii_uppercase` while `collect_all_column_names` keeps `to_uppercase`, which `vs-adapter/pushdown-module-structure`'s "One blind traversal primitive backs every column-collecting walk" scenario forbids unifying. #270 removes a builder parameter, not that.
* `tests/e2e_non_ascii_identifier_test.rs::non_ascii_table_and_column_stay_queryable` is the standing live guard on that premise, not merely a past capture: it seeds an Iceberg `straße` column against a Docker Exasol container and asserts `SYS.EXA_ALL_COLUMNS` serves `STRASSE`. If `resolve_table_schema` ever stopped Unicode-uppercasing declared names, that test fails before any fold could matter.
* `pub(super)` on an item of `adapter::pushdown::support` reaches `adapter::pushdown` and every descendant, including `adapter::pushdown::joins::planning`. The shared builder therefore reaches the joins side at the visibility ceiling `vs-adapter/pushdown-joins-module-structure` already imposes, so no `use` path widens and no PRODUCTION item's visibility widens — the same reasoning this feature's collect-walk scenario records for the blind traversal primitive. No item's visibility widens in the other direction either, and this delta adds NO test-only item: it reaches that outcome by placing each new test where the items it needs are already visible, not by exporting anything.
* That reasoning does NOT run in the opposite direction, which is what decides WHERE each new test is declared. `involved_table_columns` is `pub(super)` in `joins/planning.rs`, `joins/mod.rs` declares `mod planning;` PRIVATE, and `joins/mod.rs` re-imports the name with a plain private `use planning::{involved_table_columns, …}` — so the name is scoped to `adapter::pushdown::joins` and its descendants, and `support` is a SIBLING of `joins`, not a descendant. A test in `support` therefore cannot call it, and neither a `use` re-export nor a test-only wrapper is needed to work around that, because neither test has to sit in `support`. The builder-divergence test SHALL be declared in `joins/planning.rs`'s OWN `#[cfg(test)] mod tests`, where `involved_table_columns` is declared in the same file and `support`'s `pub(super)` items are already reachable — that file's production code already imports two of them. The lookup-helper test stays in `support` and needs no builder at all, because it takes its `col_types` slices as literals. NO item's visibility changes in either direction, and no `#[cfg(test)]`-only export is introduced.
* FOUR comments assert the uppercase-then-look-up convention that the shared helper replaces, and they are not all doc comments. THREE are doc comments: `like_subject_type_guard`'s, `is_bare_decimal_column`'s, and `coerce_string_position_arg`'s. The FOURTH is an INLINE BODY COMMENT in `guard_like_subject`, sitting directly above the lookup block the helper replaces, and it is the ONLY one of the four that cites a line number (`support.rs:411`) that no longer points at the code it names — no doc comment carries that citation. Those four notes are precisely what issue #265 replaces with code: after the extraction the shared helper enforces what the notes asserted, so the notes are deleted rather than corrected.
* The joins-side verification asset is already scoped to this change and is consumed rather than restated: `vs-adapter/pushdown-joins-module-structure`'s "Generated join SQL is byte-identical across the split" scenario captures a golden-SQL baseline over "any duplication extraction", and its in-code gate carries the instruction to re-run after every dedup extraction. `vs-adapter/pushdown-joins-module-structure` therefore needs no delta.
* One import removal is a compile-enforced proof that the builder merge actually moved the mapping rather than copying it: `joins/planning.rs` calls `exasol_type_from_json` at exactly ONE site, inside `involved_table_columns`. Once that call lives in the shared builder, the file's `use crate::types::mapping::exasol_type_from_json` is unused, and this crate's `cargo clippy --workspace --all-targets -- -D warnings` gate fails until it is deleted.
* This delta carves the scan spec's `storage` value out of THREE clauses, the golden-fixture gate of each of this feature's three scenarios: "One helper resolves a bare column node's Exasol type for every type-rewrite guard", "One builder produces the column-type list for both the first-table and the named-table selection", and "The three type-rewrite guards read their type family from the shared classifier". It amends no other clause, supersedes no Background bullet, and changes no type-resolve, fold, builder, or classifier rule.
* `vs-adapter/storage-backend-enum` (issue #274) wraps the scan spec's `storage` value in an externally-tagged backend variant. That value is embedded in the scan-driving SQL, so five `dispatch_golden` fixtures and three join golden-SQL assertions change by exactly one substring each.
* The carve-out permits an edit to the `storage` value ALONE. Every other byte of every golden stays unedited, which is what keeps this feature's gate a working proof rather than a retired one. The guard unit tests in `support.rs` — leaf, non-`column`, nameless-column, unresolvable-column — embed no scan spec and are unedited.

## Scenarios

### Scenario: One helper resolves a bare column node's Exasol type for every type-rewrite guard

* *GIVEN* the three per-node type decisions in `pushdown/support.rs` — `guard_like_subject`, `is_bare_decimal_column`, and `coerce_string_position_arg` — which each hand-roll the same two-step resolve against the per-request `col_types: &[(String, String)]` list: read the node's `name`, fold it with the Unicode `to_uppercase`, then linear-scan `col_types` for a tuple whose first element equals it; and which each carry a doc-comment note asserting that it mirrors the other two's convention
* *WHEN* any of the three decides what to do with a bare `column` node
* *THEN* exactly ONE helper in the shared `support` submodule SHALL own that resolve, taking the node and the `col_types` slice and returning `Option<&str>` — the resolved Exasol type string, or nothing — and each of the three guards SHALL retain NO name-folding and NO `col_types` scan of its own
* *AND* the helper MUST NOT test the node's `type` tag, because a non-`column` node is NOT a failed lookup: `guard_like_subject` and `coerce_string_position_arg` return such a node UNCHANGED whereas a failed lookup makes them decline, so absorbing the tag test would convert a pass-through into a decline and silently drop pushdown for every computed expression and literal argument
* *AND* each guard SHALL therefore keep its own `type == "column"` test ahead of the call — the pass-through for the two `Option<Json>` guards, `false` for `is_bare_decimal_column` — so the helper owns the resolve and nothing else
* *AND* the helper SHALL fold the name with the Unicode `to_uppercase` and MUST NOT use `to_ascii_uppercase`, because all three guards fold that way today and the extraction MUST NOT change which fold they apply. The two folds agree on every name the adapter can declare, per the captured evidence above, so switching would be a gratuitous edit — and its harmlessness would rest on a normalization `resolve_table_schema` owns rather than on anything this helper can observe
* *AND* the helper SHALL return `None` for BOTH a nameless column node and a name absent from `col_types`, because all three guards already treat those two cases identically — a decline in the two `Option`-returning guards, `false` in the boolean one — so no third state is needed and none SHALL be introduced
* *AND* the helper SHALL be declared private to `support`, because its only three consumers live there
* *AND* every mirror-note comment SHALL be deleted, because the shared helper now enforces by construction what those notes asserted by convention: the three guards' doc-comment notes AND `guard_like_subject`'s INLINE BODY COMMENT above the lookup block the helper replaces, which is the sole carrier of the stale line-number citation; each guard's doc comment SHALL otherwise be preserved, in particular `coerce_string_position_arg`'s four-row per-type dispatch table and its `(#223)` non-`column`-argument exception — EXCEPT any sentence that names a predicate moving to `classify_exa_type`, which SHALL be reworded to name the classifier's family while KEEPING its rationale intact: `is_bare_decimal_column`'s "Integer columns are wire-encoded as `DECIMAL(p,0)`, so `.starts_with("DECIMAL")` also matches them (harmless: the trim is a no-op on a scale-0 value)" SHALL still record that integer columns classify as DECIMAL and that the trim is a harmless no-op at scale 0, but SHALL name `ExaTypeClass::Decimal` instead of the literal predicate, because after the substitution the guard no longer contains that predicate and a preserved sentence naming it would be a fresh instance of the stale-citation defect this delta deletes
* *AND* a unit test SHALL pin the helper's fold SENSITIVITY at this boundary, over a CONSTRUCTED column name whose Unicode and ASCII folds differ — `STRAßE`, chosen because `to_uppercase` yields `STRASSE` while `to_ascii_uppercase` leaves it unchanged: the helper MUST resolve a type against a Unicode-folded `col_types` list and MUST return `None` against an ASCII-folded one, so the fold the extraction preserves is asserted rather than assumed. That test MUST NOT be read as a claim that Exasol delivers such a name. The captured evidence above records that it does not, because this crate uppercases every Iceberg field name before declaring it
* *AND* that test SHALL construct both `col_types` slices as LITERALS — one carrying the Unicode-folded `STRASSE`, one carrying the ASCII-folded `STRAßE` — and SHALL call NEITHER builder, so it exercises the lookup alone and stays inside `support`. Calling the builders here would couple a lookup unit test to the builder contract the merged-builder scenario below already pins, and would require reaching a `pub(super)` item of `joins::planning` from a sibling module, which no test-only export SHALL be added to enable
* *AND* the scan-driving SQL generated for every pushdown request MUST be byte-identical to its pre-extraction output EXCEPT for the scan spec's `storage` value, which `vs-adapter/storage-backend-enum` re-encodes as an externally-tagged backend variant over a byte-identical payload; every existing guard unit test in `support.rs`, every join golden-SQL assertion, and every `dispatch_golden` fixture MUST pass with NO change to any test assertion or expected value outside that `storage` value — the leaf, non-`column`, nameless-column, and unresolvable-column tests of all three guards embedding no scan spec at all and therefore being unedited, and being the gate that makes the pass-through-versus-decline distinction falsifiable here

### Scenario: One builder produces the column-type list for both the first-table and the named-table selection

* *GIVEN* `column_types` (`pushdown/support.rs`), the ONE `col_types` builder, which takes `fold_case: impl Fn(&str) -> String` alongside its table selection so that `extract_all_column_types` can pass `str::to_uppercase` and `involved_table_columns` (`pushdown/joins/planning.rs`) can pass `str::to_ascii_uppercase`, preserving a fold divergence this feature's Background records as UNREACHABLE — `resolve_table_schema` (`adapter/pushdown/file_resolution.rs:640`) maps every Iceberg field through `f.name.to_uppercase()` before `build_virtual_tables` declares it, so no name carrying a lowercase non-ASCII letter reaches either wrapper, and `tests/e2e_non_ascii_identifier_test.rs::non_ascii_table_and_column_stay_queryable` pins that live against a Docker Exasol container by serving an Iceberg `straße` column as `STRASSE`
* *WHEN* the adapter builds the `(UPPERCASE name, Exasol type)` list for a single-table request, or for one named table of a join
* *THEN* `column_types` SHALL take exactly ONE parameter besides `request` — the table selection — and the `fold_case` parameter SHALL be REMOVED, because a parameter whose two arguments cannot produce different output is a decision the builder declined to make with nothing to decide
* *AND* `column_types` SHALL apply the Unicode `str::to_uppercase` in its OWN body, and MUST NOT apply `str::to_ascii_uppercase`, because `to_uppercase` is the fold every reachable name already carries — it is `resolve_table_schema`'s own fold, and the fold the shared `column_exa_type` lookup applies on the consuming side, inside the SAME module as the builder — so the builder converges on its own module's consumer rather than leaving that consumer's fold unpaired
* *AND* both wrappers SHALL survive with UNCHANGED signatures and declaration sites — `extract_all_column_types` as `pub(super) fn(&Json) -> Vec<(String, String)>` in `support.rs`, `involved_table_columns` as `pub(super) fn(&Json, &str) -> Vec<(String, String)>` in `joins/planning.rs` — so NO call site of either changes: for the former the production sites `support::extract_projection` and `pushdown::handle_pushdown` plus the test sites in `grouped_agg.rs` and `topn.rs`; for the latter the production sites `joins/mod.rs::plan_join`, `joins/sql_builders.rs::render_broadcast_join` (twice), `joins/sql_builders.rs::build_n_scan_join_sql`, and `joins/rendering.rs::extract_join_projection` (twice), plus the test sites in `sql_builders.rs` and `rendering.rs`
* *AND* neither wrapper SHALL be deleted as a shallow pass-through, because each still supplies a table selection the shared builder does not choose — `tables.first()` versus the find-by-name closure — so each remains a partial application that names a decision rather than a body forwarding the same arguments
* *AND* `column_types`' selection parameter SHALL stay a selection CLOSURE and MUST NOT be reshaped into an `Option<&str>` table name or any other data-shaped mode argument, because reshaping it edits a parameter this scenario is not removing and would change both call sites for no observable gain
* *AND* the unit test `each_builder_keeps_its_own_case_fold_on_a_constructed_non_ascii_literal` (`joins/planning.rs`) SHALL be DELETED together with the `// Case-fold characterization` section banner above it and the `#[cfg(test)]`-scoped `use crate::adapter::pushdown::support::extract_all_column_types` inside its body, of which it is the sole consumer, because with one fold the test has nothing left to distinguish: it asserts that two wrappers of one builder disagree, which after this change is a false statement rather than a weakened one
* *AND* NO replacement unified-fold test SHALL be added, because an agreement assertion over two wrappers that now share one fold restates `str::to_uppercase`'s stdlib behavior and guards nothing — the same reasoning by which the superseded scenario rejected an agreement test over already-uppercased names. Coverage of the surviving fold stays where it already is: `support.rs`'s `column_exa_type_resolves_unicode_folded_list_and_misses_ascii_folded_list` pins the consuming lookup's Unicode fold, and the pushdown, joins, top-N, and `dispatch_golden` suites exercise both wrappers end to end over real already-uppercased names
* *AND* every comment asserting the removed divergence SHALL be reworded or deleted rather than left standing, because a preserved sentence naming a fold that no longer exists is a fresh instance of the stale-citation defect this feature deletes. FIVE carriers exist and all five are in scope: (1) `column_types`' doc comment paragraph justifying selection and fold as two parameters plus its `(#270)` tracking note SHALL be deleted; (2) `involved_table_columns`' doc-comment claim that it "maps its columns with the ASCII-only `to_ascii_uppercase` fold" SHALL be reworded to name the shared Unicode fold; (3) `involved_table_columns`' CLOSING partial-application paragraph, "A partial application of `support::column_types`, supplying the find-by-name selection and the ASCII-only fold this side has always applied", SHALL DROP "and the ASCII-only fold this side has always applied" while KEEPING its find-by-name selection clause, because after the change this side supplies no fold at all; (4) `column_exa_type`'s doc sentence "`involved_table_columns`' ASCII-folded keys agree for every column name the adapter can declare — `resolve_table_schema` Unicode-uppercases names before declaring them, so no declarable name can differ between the two folds" SHALL be reworded so the agreement claim names the SINGLE fold both builders now apply instead of an ASCII-folded key set no builder produces, KEEPING the `resolve_table_schema` premise and leaving the `type`-tag paragraph intact; and (5) the sentence in `column_exa_type_resolves_unicode_folded_list_and_misses_ascii_folded_list`'s doc comment naming `involved_table_columns` as the producer of the ASCII-folded list SHALL be reworded to describe its `col_types` literal as a CONSTRUCTED ASCII-folded list that no builder produces, keeping the test's own falsifiability rationale intact
* *AND* the fold PAIRING this change alters SHALL be named rather than left silent: `joins/rendering.rs::referenced_side_columns` narrows `involved_table_columns`' names by membership in the set `collect_side_column_names` builds with `to_ascii_uppercase`, so a pair that folded identically before now folds differently, and its agreement rests SOLELY on the same upstream normalization as the rest of this scenario — both sides read only names Exasol declared, which `resolve_table_schema` already Unicode-uppercased, and every such name is a fixed point of both folds. The bound if that premise ever broke SHALL be recorded accurately and MUST NOT be recorded as "a wider projection, never a dropped column": `referenced_side_columns` falls back to `full_cols` only when narrowing yields NOTHING, so a MIXED side — one column's folds disagreeing while another's agree — narrows to a non-empty subset, the fallback does not fire, and the diverging column is DROPPED from the fan-out leg while the outer wrapper still references it. A wider projection is the ALL-MISS case only
* *AND* the ASCII folds of `column_tables` and `collect_side_column_names` SHALL be left UNCHANGED, because `vs-adapter/pushdown-module-structure`'s "One blind traversal primitive backs every column-collecting walk" scenario forbids unifying the collect walks' folds and this scenario removes a builder parameter, not that separate divergence
* *AND* the scan-driving SQL for every single-table pushdown request and the join SQL for every join shape MUST each be byte-identical to their pre-merge output EXCEPT for the scan spec's `storage` value, and every existing pushdown, joins, and top-N test MUST pass with NO change to any test assertion or expected value outside that value — the two fold-pinning tests above, which construct their own requests and assert names rather than SQL, being unedited by this carve-out

### Scenario: The three type-rewrite guards read their type family from the shared classifier

* *GIVEN* the same three guards' hand-written Exasol type-string predicates — `starts_with("VARCHAR") || starts_with("CHAR")`, the exact match `== "DATE"`, and `starts_with("DECIMAL")` — spelled out once per guard against the family vocabulary `datafusion-scan/type-mapping-module-structure` already records as the `ExaTypeClass` enum and the `classify_exa_type` function in `types/mapping.rs`
* *WHEN* a guard decides what to do with a resolved Exasol type string
* *THEN* each of the three guards SHALL obtain its type family by calling `classify_exa_type` and SHALL retain NO `starts_with` test and NO string equality test against an Exasol type string
