# Feature: Storage Backend Enum

Gives the storage-backend decision exactly one home: a `StorageBackend` enum whose variant IS the backend, so every other module asks the enum for what it needs instead of deciding for itself which backend it is talking to.

## Background

* **This delta lands the second variant, `Adls`, and is issue #275 — slice C of six (A-F).** It SUPERSEDES this feature's "Scope fence: ONE variant" bullet, which named the Azure variant as the declared successor slice and forbade it only in slice B. Everything slice B built is now exercised for the first time: with two variants, every `match` has two arms, every method's dispatch is observable, and the wire tag discriminates rather than merely existing.
* **The variant carries an account name and exactly one credential.** `Adls { account_name: String, cred: AdlsCred }` with `AdlsCred` holding an account-key state or a SAS state and no third state, so an Azure backend that names two credentials — or none — is unrepresentable rather than validated away at every use site. A struct variant rather than a wrapper struct: unlike `S3`, there is no pre-existing Azure credential type whose serde contract must be preserved, so a wrapper would be a type introduced for symmetry alone.
* **`AdlsCred` redacts its payload in `Debug`.** `ConnectionCreds` already does this for `secret_key`, `session_token`, `token`, and `client_secret`, and the three new CONNECTION fields join that manual impl. Doing the same on the wire type costs six lines and leaves issue #135 (credentials in cleartext in query plans) with strictly less to fix rather than strictly more.
* **The iceberg config keys are the crate's own named constants, verified against the resolved dependency, not spelled inline.** `iceberg::io::ADLS_ACCOUNT_NAME` = `"adls.account-name"`, `ADLS_ACCOUNT_KEY` = `"adls.account-key"`, `ADLS_SAS_TOKEN` = `"adls.sas-token"` (`iceberg-0.10.0/src/io/storage/config/azdls.rs:34-38`, re-exported through `iceberg::io`), mirroring the existing `S3_*` imports. `iceberg-storage-opendal-0.10.0/src/azdls.rs:46-85` reads exactly these strings from the `FileIO` props map.
* **`OpenDalStorageFactory::Azdls` is a UNIT variant** (`iceberg-storage-opendal-0.10.0/src/lib.rs:108-134`) — no fields, unlike `S3 { customized_credential_load }`.
* **The Azure arm MUST NOT emit `adls.connection-string`.** `iceberg-storage-opendal-0.10.0/src/azdls.rs:49-54` fails `FileIO` construction hard when that key is present.
* **`adls.account-name` doubles as a wrong-account guard, deliberately.** When it is set, `iceberg-storage-opendal` compares it against the account in each URI and raises `DataInvalid` on a mismatch (`azdls.rs:163-170`). Because `validate_creds` requires `account_name` for every Azure CONNECTION, the key is always present and the guard is always armed: a table whose location names a different storage account fails loud instead of attempting an unauthorised read.
* **The container comes from the URI, not from props.** `iceberg-storage-opendal` reads the filesystem/container from the URI userinfo and derives the endpoint from the URI host (`azdls.rs:195-207`, `azdls.rs:244-267`), so ONE `FileIO` serves every container in the account and neither key needs to be configured. Both `abfss://` and `abfs://` are accepted (`azdls.rs:144-159`).
* **The engine's object store is the asymmetry this slice has to close.** `MicrosoftAzureBuilder::with_url` on `abfss://<container>@<account>.dfs.core.windows.net` sets BOTH the account and the container (`object_store-0.13.2/src/azure/builder.rs:662-682`), so the built store is CONTAINER-scoped. DataFusion, however, keys the registry by scheme + `host:port` ONLY — `get_url_key` reads `Position::BeforeHost..Position::AfterPort` (`datafusion-execution-54.1.0/src/object_store.rs:268-274`), which EXCLUDES userinfo — so the key identifies the ACCOUNT. Two containers of one account therefore collapse onto one registered store, and without a guard a broadcast join's dimension side would be read out of the fact side's container with no error.
* **`ListingTableUrl::object_store()` is the finer notion and already sees the container.** It slices `Position::BeforeScheme..Position::BeforePath` (`datafusion-datasource-54.1.0/src/url.rs:323-327`), which INCLUDES userinfo. `validate_uniform_object_store_files` compares exactly that per data file and per delete file, so a file list that MIXES containers WITHIN one side is already rejected today and this delta does not edit that function's rule. What is missing is the ACROSS-side case, where two sides each internally uniform resolve to two different stores under one key.
* **Credential setters, verified against `object_store-0.13.2`:** a shared account key is `with_access_key` (`src/azure/builder.rs:730-734`), NOT `with_account_key`; a raw SAS string is `with_config(AzureConfigKey::SasKey, …)` (documented at `src/azure/builder.rs:252-262`, split by `split_sas` at `:1077-1094`, leading `?` optional), NOT the typed `with_sas_authorization`, which takes pre-split query pairs. In `build()` an access key BEATS a SAS (`:990` vs `:1021`); `AdlsCred` makes setting both unrepresentable, so that precedence can never be reached.
* **`MicrosoftAzureBuilder::with_url` accepts exactly FOUR `abfss://` host suffixes, and this slice does not widen that.** With a non-empty userinfo it splits the host once on `.` and matches the remainder against `dfs.core.windows.net`, `blob.core.windows.net`, `dfs.fabric.microsoft.com`, or `blob.fabric.microsoft.com`; every other host returns `Error::UrlNotRecognised` (`object_store-0.13.2/src/azure/builder.rs:660-682`). The account segment must also contain no further `.` (the `validate` closure at `:655-658`). A sovereign-cloud endpoint (`*.dfs.core.chinacloudapi.cn`), a private endpoint, and a custom-domain account therefore FAIL at `build()`. That is an upstream capability boundary, not a defect this slice introduces or hides: the arm surfaces the error redacted rather than special-casing the host, and `plan.md` names it a Non-Goal.
* **`s3a://` is the one existing input whose registered store key CHANGES.** `FileEntry::path` is documented as an absolute S3 **or s3a** URI (`crates/lakehouse-engine/src/scan/spec.rs:445`, `:730`). The deleted `extract_bucket_from_files` returned only the host, and its caller rebuilt the key as `format!("s3://{bucket}")` — rewriting an `s3a` scheme to `s3`. The lookup side never did: `register_file_list` takes `ListingTableUrl::parse(&first_abs).object_store()`, preserving `s3a`. Since `get_store` matches `scheme://host:port` exactly, the two disagree and an `s3a://` scan errors today with "No suitable object store found". `side_store_url` returns the scheme verbatim, so the key and the lookup agree and `s3a://` starts working. The S3 characterization gate is unaffected: every committed fixture uses `s3://`.
* **The `with_client_options` ordering hazard is identical to the S3 builder's** (`src/azure/builder.rs:859-863`): it REPLACES the whole `ClientOptions`. The Azure arm sets no `allow_http`, so nothing is currently at risk, but the same ordering discipline applies to any later setter that layers onto `ClientOptions`.
* **Iceberg spec compliance is checked and unchanged.** `apache/iceberg` `format/spec.md` defines data-file field `100 file_path` as "Full URI for the file with FS scheme" (required in v1, v2, and v3), and path resolution as "If the path starts with a URI scheme, it is absolute and is used without modification. If the path does not start with a URI scheme, the resolved path is the table location followed by the relative path joined by the URI separator character `/`." Both rules are scheme-agnostic, and `relativize_path_to_root` and `reconstruct_abs_uri` already implement exactly them. This delta therefore PINS their `abfss://` behaviour with tests and changes neither. The spec mandates no scheme-specific reader behaviour beyond that: it "only requires that file systems support the following operations: In-place write, Seekable reads, [and] Deletes". This delta introduces no deviation and fixes none; it changes no file pruning, no snapshot or manifest reading, no delete-file handling, and no type mapping.
* **`datafusion-scan/scan-execution-memory-and-credentials` needs no amendment.** Its two credential-passthrough scenarios are explicitly about vended S3 credentials and stay accurate, and its Background already assigns "how that store is derived and registered without the scan path naming a backend" to this feature.
* No new dependency is introduced and no dependency version changes: `object_store`'s `azure` feature and `iceberg-storage-opendal`'s `opendal-azdls` feature were both enabled by slice A (issue #273).
* Every scenario is a pure refactor. Every scenario of `vs-adapter/connection-credentials`, `vs-adapter/connection-credentials-catalog-auth`, `vs-adapter/rest-catalog-oauth-auth`, `vs-adapter/pushdown-planning*`, `vs-adapter/pushdown-file-pruning`, `datafusion-scan/scan-execution*`, and the S3 E2E suite stays behaviorally accurate, and those suites are the characterization gate that makes "S3 behavior unchanged" falsifiable.
* **`StorageProps` itself is NOT edited.** The struct, its field set, its field order, its serde attributes, its `Default` impl, its `secret_values` body, and its three unit tests are untouched. `StorageBackend::S3` WRAPS it as the variant payload. Every `StorageProps { .. }` construction literal in production and test code stays as written; only the places that HOLD, PASS, or MATCH a storage backend gain the wrapping layer. Inlining the seven fields onto the variant was rejected: it would edit the one type whose serde encoding `vs-adapter/catalog-crate-structure` pins field-for-field, for no gain the wrapper does not already deliver.
* **Three of the four methods live on the enum; the fourth cannot.** `vs-adapter/catalog-crate-structure` records that `lakehouse-catalog`'s manifest MUST NOT declare `object_store` or `datafusion` as a direct dependency. DataFusion object-store registration therefore cannot be a method on a catalog-crate type. Issue #274 states the same split ("Only `register_object_store` ... stays engine-side"), so the enum declares `secret_values`, `catalog_storage_props`, and `file_io`, and the engine owns one backend-dispatching registration function in `crates/lakehouse-engine/src/scan/object_store.rs`. The issue's `register_object_store(env, sample_uri)` is illustrative shorthand, not a literal signature. Only two of the three methods are `pub`: `catalog_storage_props`' consumers are both in-crate.
* **The crate boundary forces two owners.** The enum owns WHICH backend; the engine's single registration function owns that backend's object store. Before this feature four engine-side sites independently know the backend is S3 — `extract_bucket`'s `url.host()` bucket derivation, `build_s3_store`, `register_bucket_store`, and the `build_s3_file_io` call. After it, one.
* **`catalog_storage_props` is the single source of the six iceberg S3 config keys.** The keys are `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_SESSION_TOKEN`, and `S3_PATH_STYLE_ACCESS`; the first four are inserted only when non-empty, the session token only when `Some`, and path-style always. `file_io` folds that map into the `FileIOBuilder` and `build_rest_catalog` merges it into its props map, so neither declares a key of its own. `decision-log.md` [3] records the line-by-line evidence that the two pre-refactor mappings are identical.
* **A `HashMap` return is order-safe for both consumers.** `catalog_storage_props`' entries reach `build_rest_catalog` via `HashMap::extend` and `file_io` via repeated `FileIOBuilder::with_prop`; both are keyed inserts, so the map's nondeterministic iteration order cannot change either result.
* **The scan-spec wire gains a variant tag, and that is safe here.** `CommonScanSpec.storage` is serialized into the scan-driving SQL literal, so wrapping it changes that literal's `storage` value from `{...}` to `{"s3":{...}}`. `datafusion-scan/scan-execution-spec-reconstitution` already records that "the same `.so` produces and consumes the spec within one deploy (there is no cross-version wire-compatibility requirement)", which is exactly the property this change relies on. `vs-adapter/catalog-crate-structure`'s "the serde encoding of `StorageProps` MUST be unchanged field-for-field" clause also stays TRUE and is not amended: the payload's own encoding is byte-identical, and the tag is the enclosing enum's.
* **The wire tag is externally tagged and lowercase, and it lands in this slice.** `#[serde(untagged)]` MUST NOT be used. Every non-`storage` byte of every golden staying identical is this slice's proof that nothing but the tag moved. `decision-log.md` [1] carries the argument against the untagged wire.
* **`extract_bucket` is deleted, not branched.** It derives the bucket from `Url::host_str()`, which on an `abfss://` URI yields the storage account rather than the container. `extract_bucket_from_files` keeps the same logic but survives ONLY as the S3 arm's private derivation, unreachable from the backend-agnostic call site.
* **Iceberg REST compliance is checked and unchanged.** `select_credential_source` and `merge_vended_into_storage` implement the `storage-credentials`-before-`config` rule and the longest-`prefix` rule of `apache/iceberg` `open-api/rest-catalog-open-api.yaml` (main), and their bodies move into the S3 arm VERBATIM. This feature introduces no deviation and fixes none, and it changes no file pruning, no snapshot or manifest reading, no delete-file handling, and no type mapping. `decision-log.md` [8] carries the normative quotations.
* This crate's CI gate is `cargo clippy --workspace --all-targets -- -D warnings`, under which an item left without a caller is a build failure. That gate, not preference, is what forces each deleted function's callers to be repointed in the same change.
* No new dependency is introduced and no dependency version changes.
* **This delta replaces the "ONE selection site" fence with a "TWO selectors on disjoint inputs" fence, and is issue #276 — slice D of six (A-F).** Slice C's clause declaring `storage_block` "the ONLY place a backend is SELECTED FROM INPUT" is superseded, not bent: `vs-adapter/pushdown-planning-cloud-credentials` now selects the backend from the table location's URI scheme when `use_vended_credentials` is true. Pretending that is not a selection would leave the fence technically intact and factually false, which on a credentials path is worse than no fence.
* **One selector per credential mode, chosen by ONE boolean at ONE site, on DISJOINT inputs.** `storage_block` selects from the CONNECTION credential shape and runs only when vending is disabled. `resolve_vended_storage` selects from the `loadTable` response's table location and runs only when vending is enabled. `resolve_file_list` holds the single `if creds.use_vended_credentials` that picks between them. Neither selector reads the other's input, neither can override the other, and there is no path on which both run — so the count of DECISION POINTS is still one even though the count of SELECTORS is two.
* **Deleting `resolve_vended_storage`'s backend parameter is what makes the disjointness provable rather than asserted.** Before this delta it took a `&StorageBackend` and overlaid vended values field-by-field onto the payload `storage_block` had chosen, which is precisely a second selector reading the first's output. Removing the parameter turns "the vended selector does not consult the static one" into a signature-level property no future edit can quietly reverse.
* **Keeping ONE selector was considered and rejected on two counts.** Passing the URI scheme into `storage_block` would require the scheme at CONNECTION-parse time, but the scheme is only known after `loadTable`, which runs later, once per table, and never at all on the `createVirtualSchema` path — so a single selector would have to be deferred past `loadTable` for every path including the non-vended one, and would still have no answer for a request that resolves no table. Making the vended arm mutate the payload `storage_block` returned was rejected by this feature's own existing clause: "reaching into the payload to finish construction is exactly the knowledge this feature removes."
* **The count of modules permitted to name a variant is UNCHANGED at five.** `resolve_vended_storage` was already on that list; only its documented ROLE changes, from overlaying credentials onto a caller-selected backend to selecting one from the anchor scheme. No module joins the list and none leaves it, so the fence this feature exists to hold is narrowed in prose and identical in extent.
* **`allow_http` is threaded in as a resolved virtual-schema property, so the vended selector takes one new non-CONNECTION parameter.** Slice C's reading is UNCHANGED: `allow_http` "arrives from the `ALLOW_HTTP` VS property and is consumed only by the S3 payload", and "the Azure backend carries no HTTP-scheme knob at all". Deriving the value from the vended `s3.endpoint`'s scheme instead was considered and REJECTED as a security regression — the property defaults to false, so a derivation would let a catalog vending `http://…` put vended credentials in the clear with no operator control. The parameter is NOT a CONNECTION value, so it does not weaken the rule that the vended selector reads no CONNECTION storage field. Adding a fourth method to the enum to expose `allow_http` was likewise rejected: it would leave the vended selector reading a CONNECTION-derived value, which is the exact coupling this delta removes.
* **`StorageProps`, `AdlsCred`, the wire encoding, and all three enum methods are UNEDITED.** No variant is added or removed, no field changes, no serde attribute changes, and the externally-tagged lowercase `{"s3":{…}}` / `{"adls":{…}}` encoding is byte-identical. A vended ADLS backend serializes exactly as a static one does, so every committed golden SQL fixture and scan-spec JSON fixture passes unedited.
* **The `AdlsCred` two-state invariant is preserved and newly exercised.** The vended ADLS arm assembles the SAS state and never the account-key state, so "both" and "neither" stay unrepresentable and `object_store`'s access-key-beats-SAS precedence stays unreachable. Slice C recorded that precedence as the reason the enum exists in this shape; a vended SAS is the first input that reaches the SAS state from anywhere other than the CONNECTION.
* No dependency is added and no dependency version changes.
* This delta (plan `add-native-unity-catalog-client`, issue #318) admits a third backend-selection site for native Unity Catalog credential vending. It supersedes both the enum's two-selector invariant and its five-module variant-naming list (now six), but does NOT wire a new selector dispatch: `resolve_uc_vended_storage` is unit-tested only, and the catalog-kind-to-credential-family dispatch is deferred to #319/#320. The two existing selectors — `storage_block` (CONNECTION shape, static, when `use_vended` is false) and `resolve_vended_storage` (URI scheme, vended, when `use_vended` is true) — stay unchanged.

## Scenarios

### Scenario: One enum names the storage backend and answers every backend-specific question

* *GIVEN* the one-variant `StorageBackend` slice B landed, whose three methods `secret_values`, `catalog_storage_props`, and `file_io` each have a single S3 arm
* *WHEN* the Azure backend lands
* *THEN* `lakehouse-catalog` SHALL declare a SECOND variant, `Adls { account_name: String, cred: AdlsCred }`, beside the unmodified `S3(StorageProps)`, and a `pub` enum `AdlsCred` with EXACTLY TWO states — an account key and a SAS token — each carrying its secret as a `String`
* *AND* `AdlsCred` SHALL implement `Debug` MANUALLY so the wrapped secret is replaced by a redaction marker, matching what `ConnectionCreds` already does for `secret_key`, `session_token`, `token`, and `client_secret`
* *AND* `AdlsCred` SHALL derive `Clone`, `PartialEq`, `Eq`, `Serialize`, and `Deserialize`, because `StorageBackend` derives all five and stops compiling without them
* *AND* all three methods SHALL gain an Azure arm, and NO method SHALL gain a catch-all `_` arm, so a third backend is a build failure at every site with a decision to make rather than a silent fall-through
* *AND* `catalog_storage_props` SHALL emit `iceberg::io::ADLS_ACCOUNT_NAME` when `account_name` is non-empty, and EXACTLY ONE of `iceberg::io::ADLS_ACCOUNT_KEY` and `iceberg::io::ADLS_SAS_TOKEN` chosen by the `AdlsCred` state, and SHALL emit NO other key — in particular no `adls.connection-string`, which fails `FileIO` construction hard, and no `s3.*` key
* *AND* `catalog_storage_props` SHALL name those keys through the `iceberg::io::ADLS_*` constants rather than string literals, so this module stays the SINGLE source of every iceberg storage config key it emits, exactly as it already is for the six S3 keys
* *AND* `file_io` SHALL select the unit factory variant `OpenDalStorageFactory::Azdls` and SHALL configure it from `catalog_storage_props` alone, so the Azure props map and the Azure `FileIO` cannot drift
* *AND* `secret_values` SHALL return EXACTLY ONE value for the Azure variant — the account key or the SAS token — and SHALL return an EMPTY list when that value is the empty string, because every returned value is fed to literal-value error redaction and redacting `""` would strip every character of the error it guards
* *AND* `secret_values` MUST NOT return `account_name`, because a storage account name is not a secret and appears in every `abfss://` URI the engine handles
* *AND* the S3 arm of all three methods SHALL be UNEDITED, and `StorageProps` SHALL remain unedited, so the six S3 config keys, their inclusion conditions, and the S3 secret list are the same values in the same order as before this delta

### Scenario: Every consumer holds a backend and no consumer names one

* *GIVEN* the seventeen production sites that carry storage config today — in `lakehouse-catalog`: `resolve_vended_storage` (`vended.rs`), `build_rest_catalog` (`session.rs`), `list_namespace_tables` and `list_namespace_tables_unsigned` (`namespace.rs`); in the adapter: `storage_block` (`connection.rs`), `resolve_connection_config`, `handle_pushdown_request`, and `redact_error` (`adapter/mod.rs`), `handle_pushdown` and `build_dispatch_sql` (`pushdown/mod.rs`), `resolve_file_list` (`pushdown/file_resolution.rs`), `plan_join` (`pushdown/joins/mod.rs`), `resolve_one_join_side` plus the `pub` field `ResolvedJoinSide::effective_storage` and `ResolvedJoinSide::new`'s matching parameter (`pushdown/joins/planning.rs`); and in the scan: `CommonScanSpec.storage` and its `impl Default` initializer (`scan/spec.rs`), `register_file_list` (`scan/raw_scan.rs`), and `PositionalDeleteScanTable::new` (`scan/positional_deletes.rs`)
* *WHEN* the refactor lands
* *THEN* each of those SHALL hold, accept, or return `StorageBackend` in place of `StorageProps`, so the backend travels as one value from the CONNECTION object to the scan spec, and no site in that chain SHALL unwrap the payload to hand a bare `StorageProps` onwards
* *AND* the ONLY modules permitted to match on a `StorageBackend` variant or read its S3 payload SHALL be these six, exhaustively: the enum's own methods (`storage.rs`); the engine's single object-store registration function (`scan/object_store.rs`); `resolve_vended_storage` (`vended.rs`), which SELECTS the variant from the anchor's URI scheme and constructs the backend the vended credential source describes; `storage_block` (`connection.rs`), which constructs the backend at the CONNECTION-parsing entry point; `CommonScanSpec`'s manual `impl Default` (`scan/spec.rs`), which re-wraps a placeholder payload without choosing a backend from any input and so is a construction site but not a selection site; and `resolve_uc_vended_storage` in the `unity` module of `lakehouse-catalog` (plan `add-native-unity-catalog-client`, issue #318), which constructs `StorageBackend::S3` or `StorageBackend::Adls` from the Unity Catalog vended response's storage-location URI scheme. A test-only payload unwrapper or variant construction MAY appear in ANY `#[cfg(test)]` module of either crate, not only in a support module. No other production module SHALL name a variant, with the source-level variant probe covering BOTH vended selectors as the compensating gate
* *AND* there SHALL be EXACTLY TWO sites that SELECT a backend FROM INPUT ON THE VENDING-VERSUS-STATIC AXIS, one per credential mode, reading DISJOINT inputs: `storage_block`, whose variant depends on the CONNECTION credential shape and which runs only when `use_vended_credentials` is false; and `resolve_vended_storage`, whose variant depends on the table location's URI scheme and which runs only when `use_vended_credentials` is true. A `Default` impl that always re-wraps a fixed `S3` placeholder is NOT a selection under this clause, because its variant depends on no input. `resolve_uc_vended_storage` is a THIRD selection site, admitted below, reading a disjoint Unity Catalog credential-vending input outside this two-site axis
* *AND* exactly ONE site SHALL choose between the two Iceberg-path selectors — the `use_vended_credentials` branch in `resolve_file_list` — so the number of decision points on that axis stays ONE; the catalog-kind-to-credential-family dispatch that would choose `resolve_uc_vended_storage` is deferred to #319/#320, per the scenario below
* *AND* `resolve_vended_storage` MUST NOT take a `StorageBackend`, a `ConnectionCreds`, or any other CONNECTION-derived value as a parameter, so the two selectors' input disjointness is enforced by its signature rather than by inspection of its body; its resolved `ALLOW_HTTP` parameter is a virtual-schema property and not a CONNECTION value, so it does not breach that disjointness
* *AND* because the vended selector matches on a URI SCHEME rather than on a `StorageBackend`, adding a third variant SHALL NOT break its build, so a source-level probe in `crates/lakehouse-catalog/tests/catalog_public_surface.rs` SHALL EXTRACT the variant list from this enum's own source — already reachable there through the `CATALOG_SOURCES` `include_str!` table — and assert every extracted name appears in `vended.rs`, as the compensating gate for the compile-time failure that site cannot provide; a HARDCODED variant list SHALL NOT satisfy this clause, because it keeps passing after a third variant is added
* *AND* because the selected variant is PER TABLE LOCATION, a join SHALL carry one backend PER SIDE rather than collapsing onto one whole-spec value, and each side SHALL be read through a store built from its own backend, as `vs-adapter/pushdown-planning-join` and `datafusion-scan/scan-execution-join` require — so no consumer ever holds a backend that names one side while another side's files are read through it. SUPERSEDES the earlier clause requiring the join planner to reject a join whose sides differ in backend variant or ADLS `account_name`: that guard is deleted, because per-side carriage removed the collapse it compensated for and backend identity was never what the scan's addressing depends on
* *AND* `storage_block` SHALL take the resolved `allow_http` value as a parameter and return a fully-formed `StorageBackend`, and `resolve_connection_config` SHALL NOT mutate `allow_http` on the returned value afterwards, because reaching into the payload to finish construction is exactly the knowledge this feature removes
* *AND* `build_rest_catalog` SHALL merge `catalog_storage_props`' entries into its props map and MUST NOT insert an S3 config key of its own
* *AND* `resolve_vended_storage` SHALL keep its name and its `pub` status while returning `Result<StorageBackend, UdfError>`, and it SHALL remain the crate's ONLY vended entry point with every mechanism step crate-private
* *AND* `lakehouse_engine::scan::spec` SHALL re-export `StorageBackend` beside its existing `StorageProps` re-export, at `pub` visibility, so the scan layer's consumers reach it on the path they already import

### Scenario: The vended selector reaches the SAS state without widening the enum

* *GIVEN* the `Adls { account_name: String, cred: AdlsCred }` variant and its two-state `AdlsCred`, whose account-key and SAS states make "both" and "neither" unrepresentable
* *WHEN* the vended selector resolves an ADLS backend from a `loadTable` response
* *THEN* it SHALL construct the SAS state and MUST NOT construct the account-key state, so `object_store`'s access-key-beats-SAS precedence in `build()` stays unreachable
* *AND* `AdlsCred`, `StorageProps`, the enum's variant set, and all three of `secret_values`, `catalog_storage_props`, and `file_io` SHALL be UNEDITED, because a vended SAS is a new INPUT to the existing SAS state rather than a new state
* *AND* the wire encoding of both variants MUST be byte-identical to before this delta, so every committed golden SQL fixture and scan-spec JSON fixture passes UNEDITED
* *AND* `secret_values` SHALL return the vended SAS as this backend's single secret value, so the value-based redaction `resolve_file_list` already applies covers a vended SAS exactly as it covers a static one

### Scenario: The scan registers its object store without naming the backend

* *GIVEN* `register_side_store`, whose S3 arm derives its store key with the private `extract_bucket_from_files` (`Url::host_str()` on the side's first file), and whose sibling `validate_uniform_object_store_files` derives the same notion independently with `ListingTableUrl::object_store()` — a duplication slice B recorded and DEFERRED to the slice that adds the second backend
* *WHEN* the Azure backend lands
* *THEN* that deferral SHALL be discharged: `extract_bucket_from_files` SHALL be DELETED and replaced by ONE backend-agnostic derivation that returns the side's store URL as the `scheme://userinfo@host:port` slice of that side's first reconstructed file URI — the SAME slice `ListingTableUrl::object_store()` takes — so the two notions agree by construction instead of by inspection
* *AND* that one derivation SHALL be the ONLY store-key derivation in the module, with each arm reading what its builder needs OUT of the returned URL — the S3 arm the host as the bucket name, the Azure arm the whole URL — and NO arm re-parsing the file URI its own way
* *AND* the `Url` that derivation returns for an `s3://` file list MUST equal the value the deleted function's caller produced — `s3://<bucket>` — so every existing assertion on `register_side_store`'s returned URL passes UNEDITED
