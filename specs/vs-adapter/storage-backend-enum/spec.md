# Feature: Storage Backend Enum

Gives the storage-backend decision exactly one home: a `StorageBackend` enum whose variant IS the backend, so every other module asks the enum for what it needs instead of deciding for itself that the backend is S3. Behavior is unchanged — this feature constrains where the backend decision lives, never what an S3 scan reads or returns.

This is the storage layer's structural feature, the sibling of `vs-adapter/catalog-crate-structure`, `vs-adapter/adapter-module-structure`, `vs-adapter/pushdown-module-structure`, `datafusion-scan/scan-module-structure`, and `datafusion-scan/type-mapping-module-structure`. It exists because the S3 assumption it consolidates is spread across four features at once — `vs-adapter/catalog-crate-structure`, `vs-adapter/pushdown-planning-cloud-credentials`, `datafusion-scan/scan-execution-spec-reconstitution`, and `datafusion-scan/scan-execution-memory-and-credentials` — so no single behavioral feature can own it without leaking a structural decision across its edge. It implements issue #274, slice B of six (A-F) for Azure Data Lake Storage Gen2 (`abfss://`) support.

## Background

* **Scope fence: ONE variant.** `StorageBackend` gains exactly one variant, `S3`, in this feature. The Azure variant is issue #274's declared successor slice (C) and MUST NOT be added here. A second variant is what makes the enum's dispatch observable; with one variant every `match` has one arm and every method returns what the S3 path returns today.
* Every scenario is a pure refactor. Every scenario of `vs-adapter/connection-credentials`, `vs-adapter/connection-credentials-catalog-auth`, `vs-adapter/rest-catalog-oauth-auth`, `vs-adapter/pushdown-planning*`, `vs-adapter/pushdown-file-pruning`, `datafusion-scan/scan-execution*`, and the S3 E2E suite stays behaviorally accurate, and those suites are the characterization gate that makes "S3 behavior unchanged" falsifiable.
* **`StorageProps` itself is NOT edited.** The struct, its field set, its field order, its serde attributes, its `Default` impl, its `secret_values` body, and its three unit tests are untouched. `StorageBackend::S3` WRAPS it as the variant payload. Every `StorageProps { .. }` construction literal in production and test code stays as written; only the places that HOLD, PASS, or MATCH a storage backend gain the wrapping layer. Inlining the seven fields onto the variant was rejected: it would edit the one type whose serde encoding `vs-adapter/catalog-crate-structure` pins field-for-field, for no gain the wrapper does not already deliver.
* **Three of the four methods live on the enum; the fourth cannot.** `vs-adapter/catalog-crate-structure` records that `lakehouse-catalog`'s manifest MUST NOT declare `object_store` or `datafusion` as a direct dependency. DataFusion object-store registration therefore cannot be a method on a catalog-crate type. Issue #274 states the same split ("Only `register_object_store` ... stays engine-side"), so the enum declares `secret_values`, `catalog_storage_props`, and `file_io`, and the engine owns one backend-dispatching registration function in `crates/lakehouse-engine/src/scan/object_store.rs`. The issue's `register_object_store(env, sample_uri)` is illustrative shorthand, not a literal signature. Only two of the three methods are `pub`: `catalog_storage_props`' consumers are both in-crate.
* **The crate boundary forces two owners.** The enum owns WHICH backend; the engine's single registration function owns that backend's object store. Before this feature four engine-side sites independently know the backend is S3 — `extract_bucket`'s `url.host()` bucket derivation, `build_s3_store`, `register_bucket_store`, and the `build_s3_file_io` call. After it, one.
* **`catalog_storage_props` is the single source of the six iceberg S3 config keys.** The keys are `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_SESSION_TOKEN`, and `S3_PATH_STYLE_ACCESS`; the first four are inserted only when non-empty, the session token only when `Some`, and path-style always. `file_io` folds that map into the `FileIOBuilder` and `build_rest_catalog` merges it into its props map, so neither declares a key of its own. `decision-log.md` [3] records the line-by-line evidence that the two pre-refactor mappings are identical.
* **A `HashMap` return is order-safe for both consumers.** `catalog_storage_props`' entries reach `build_rest_catalog` via `HashMap::extend` and `file_io` via repeated `FileIOBuilder::with_prop`; both are keyed inserts, so the map's nondeterministic iteration order cannot change either result.
* **The scan-spec wire gains a variant tag, and that is safe here.** `CommonScanSpec.storage` is serialized into the scan-driving SQL literal, so wrapping it changes that literal's `storage` value from `{...}` to `{"s3":{...}}`. `datafusion-scan/scan-execution-spec-reconstitution` already records that "the same `.so` produces and consumes the spec within one deploy (there is no cross-version wire-compatibility requirement)", which is exactly the property this change relies on. `vs-adapter/catalog-crate-structure`'s "the serde encoding of `StorageProps` MUST be unchanged field-for-field" clause also stays TRUE and is not amended: the payload's own encoding is byte-identical, and the tag is the enclosing enum's.
* **The wire tag is externally tagged and lowercase, and it lands in this slice.** `#[serde(untagged)]` MUST NOT be used. Every non-`storage` byte of every golden staying identical is this slice's proof that nothing but the tag moved. `decision-log.md` [1] carries the argument against the untagged wire.
* **`extract_bucket` is deleted, not branched.** It derives the bucket from `Url::host_str()`, which on an `abfss://` URI yields the storage account rather than the container. `extract_bucket_from_files` keeps the same logic but survives ONLY as the S3 arm's private derivation, unreachable from the backend-agnostic call site.
* **Iceberg REST compliance is checked and unchanged.** `select_credential_source` and `merge_vended_into_storage` implement the `storage-credentials`-before-`config` rule and the longest-`prefix` rule of `apache/iceberg` `open-api/rest-catalog-open-api.yaml` (main), and their bodies move into the S3 arm VERBATIM. This feature introduces no deviation and fixes none, and it changes no file pruning, no snapshot or manifest reading, no delete-file handling, and no type mapping. `decision-log.md` [8] carries the normative quotations.
* This crate's CI gate is `cargo clippy --workspace --all-targets -- -D warnings`, under which an item left without a caller is a build failure. That gate, not preference, is what forces each deleted function's callers to be repointed in the same change.
* No new dependency is introduced and no dependency version changes.

## Scenarios

### Scenario: One enum names the storage backend and answers every backend-specific question

* *GIVEN* the storage-backend assumption spread across `build_s3_file_io` (`crates/lakehouse-catalog/src/iceberg_io.rs`), `build_rest_catalog`'s inline S3 key block (`crates/lakehouse-catalog/src/session.rs`), `merge_vended_into_storage` (`crates/lakehouse-catalog/src/vended.rs`), and `StorageProps::secret_values`' eight engine call sites
* *WHEN* the refactor lands
* *THEN* `lakehouse-catalog` SHALL declare an enum `StorageBackend` with EXACTLY ONE variant, `S3`, carrying an unmodified `StorageProps` as its payload
* *AND* `StorageBackend` SHALL declare EXACTLY three methods — `secret_values`, `catalog_storage_props`, and `file_io` — each resolving the whole backend-specific question its name states, so no caller reads the payload to answer it; `secret_values` and `file_io` SHALL be `pub` because the engine calls both, and `catalog_storage_props` SHALL be crate-private because its only two consumers, `build_rest_catalog` and `file_io`, are in-crate
* *AND* `StorageBackend` SHALL derive `Debug`, `Clone`, `PartialEq`, `Eq`, `Serialize`, and `Deserialize`, because the wrapped `StorageProps` derives all six and `CommonScanSpec` — which holds the enum and derives `Debug`, `Clone`, `PartialEq`, `Serialize`, `Deserialize` — stops compiling without them, and `datafusion-scan/scan-execution-spec-reconstitution`'s "reconstitute a `ScanSpec` value equal to" clause needs `PartialEq` specifically
* *AND* `catalog_storage_props` SHALL be the SINGLE source of the six iceberg S3 config keys, and `file_io` SHALL build its `FileIO` from that same map, so the key set and each key's inclusion condition are declared once rather than once per consumer
* *AND* `build_s3_file_io` SHALL be DELETED rather than retained as a wrapper, because a public function whose body is a call to a method with the same argument is the shallow-module red flag `vs-adapter/adapter-module-structure` already records
* *AND* `StorageProps` SHALL be unedited — its fields, field order, serde attributes, `Default` impl, `secret_values` body, and three unit tests all unchanged — because the enum wraps it as a payload rather than absorbing its fields
* *AND* `secret_values` SHALL return the same values in the same order as `StorageProps::secret_values` returns for the wrapped payload, so the eight engine redaction call sites keep their behavior with no change to what they assert

### Scenario: Every consumer holds a backend and no consumer names one

* *GIVEN* the seventeen production sites that carry storage config today — in `lakehouse-catalog`: `resolve_vended_storage` (`vended.rs`), `build_rest_catalog` (`session.rs`), `list_namespace_tables` and `list_namespace_tables_unsigned` (`namespace.rs`); in the adapter: `storage_block` (`connection.rs`), `resolve_connection_config`, `handle_pushdown_request`, and `redact_error` (`adapter/mod.rs`), `handle_pushdown` and `build_dispatch_sql` (`pushdown/mod.rs`), `resolve_file_list` (`pushdown/file_resolution.rs`), `plan_join` (`pushdown/joins/mod.rs`), `resolve_one_join_side` plus the `pub` field `ResolvedJoinSide::effective_storage` and `ResolvedJoinSide::new`'s matching parameter (`pushdown/joins/planning.rs`); and in the scan: `CommonScanSpec.storage` and its `impl Default` initializer (`scan/spec.rs`), `register_file_list` (`scan/raw_scan.rs`), and `PositionalDeleteScanTable::new` (`scan/positional_deletes.rs`)
* *WHEN* the refactor lands
* *THEN* each of those SHALL hold, accept, or return `StorageBackend` in place of `StorageProps`, so the backend travels as one value from the CONNECTION object to the scan spec, and no site in that chain SHALL unwrap the payload to hand a bare `StorageProps` onwards
* *AND* the ONLY modules permitted to match on a `StorageBackend` variant or read its S3 payload SHALL be these five, exhaustively: the enum's own methods (`storage.rs`); the engine's single object-store registration function (`scan/object_store.rs`); `resolve_vended_storage`'s S3 arm (`vended.rs`), which overlays vended credentials onto a backend the caller already selected and MUST NOT change which variant it received; `storage_block` (`connection.rs`), which constructs the backend at the CONNECTION-parsing entry point; and `CommonScanSpec`'s manual `impl Default` (`scan/spec.rs`), which re-wraps a placeholder payload without choosing a backend from any input and so is a construction site but not a selection site. A test-only payload unwrapper or variant construction MAY appear in ANY `#[cfg(test)]` module of either crate, not only in a support module. No other production module SHALL name a variant
* *AND* `storage_block` SHALL be the ONLY place a backend is SELECTED FROM INPUT — the single site whose choice of variant depends on the CONNECTION object, on deserialized wire bytes, or on a URI — so slice C has exactly one home for URI-scheme- or property-driven selection and adds no second decision point. A `Default` impl that always re-wraps a fixed `S3` placeholder is NOT a selection under this clause, because its variant depends on no input
* *AND* `storage_block` SHALL take the resolved `allow_http` value as a parameter and return a fully-formed `StorageBackend`, and `resolve_connection_config` SHALL NOT mutate `allow_http` on the returned value afterwards, because reaching into the payload to finish construction is exactly the knowledge this feature removes
* *AND* `build_rest_catalog` SHALL merge `catalog_storage_props`' entries into its props map and MUST NOT insert an S3 config key of its own
* *AND* `resolve_vended_storage` SHALL keep its name and its `pub` status while taking and returning `StorageBackend`, and its S3 arm SHALL call `select_credential_source` and `merge_vended_into_storage` with their bodies unchanged, so `vs-adapter/pushdown-planning-cloud-credentials`' field-for-field guarantee holds for the wrapped payload
* *AND* `lakehouse_engine::scan::spec` SHALL re-export `StorageBackend` beside its existing `StorageProps` re-export, at `pub` visibility, so the scan layer's consumers reach it on the path they already import

### Scenario: The scan registers its object store without naming the backend

* *GIVEN* `build_session_context` (`crates/lakehouse-engine/src/scan/object_store.rs`), which derives a bucket via `extract_bucket`, builds a store via `build_s3_store`, registers it via `register_bucket_store`, and repeats the derivation and registration for a broadcast join's dimension side when that side's bucket differs
* *WHEN* the refactor lands
* *THEN* `extract_bucket` SHALL be DELETED, because it derives the bucket from `Url::host_str()` — which on an `abfss://` URI yields the storage account rather than the container — so it cannot be salvaged for a second backend and MUST NOT survive beside a backend-aware path
* *AND* `build_s3_store` SHALL be DELETED as a named function, its body becoming the S3 arm of the engine's single backend-dispatching registration function
* *AND* `build_session_context` SHALL register each side's object store through that one function, passing the side's file list and table root, and MUST NOT name a bucket, host, container, or URL scheme at the call site
* *AND* the registration function SHALL derive each side's store key inside the S3 arm from that side's first file, reconstructed against that side's table root, so `extract_bucket_from_files` survives ONLY as the S3 arm's private derivation and is unreachable from the call site
* *AND* every registered store MUST still be wrapped in the caller-supplied-size HEAD decorator and MUST still carry the resolved `s3_max_connections` connection budget as its warm-connection-pool ceiling, unchanged for both sides
* *AND* the size index handed to EVERY side's registration MUST be the WHOLE-spec index — spanning the fact files AND the join dimension files — computed ONCE per `build_session_context` call, because the shared-bucket case registers ONE store that MUST answer BOTH sides' HEAD requests from it; the per-side `files` parameter selects the store KEY only and MUST NOT narrow the size map, since deriving a per-side map would leave a shared-bucket join's dimension HEADs to the network and break `datafusion-scan/scan-execution-file-metadata`'s "the UDF MUST NOT issue a per-file object-store metadata (`HEAD`) request" guarantee
* *AND* the registration function SHALL RETURN the store key it registered — `Result<Option<Url>, UdfError>`, `Some(url)` naming the URL it registered under and `None` meaning it registered nothing because that key was already registered on this context — because DataFusion's `ObjectStoreRegistry` exposes only `get_store(url)`, so without that return a skipped registration and a duplicate registration are indistinguishable from outside and no test of the skip can fail
* *AND* a broadcast join's dimension side whose derived store key equals the fact side's MUST cause the second call to return `Ok(None)` and MUST NOT re-register, preserving today's same-warehouse skip, and the call site MUST reach that outcome without comparing bucket names itself
* *AND* a broadcast join whose dimension file list is EMPTY MUST cause no dimension registration at all and MUST return `Ok`, preserving today's `!join.files.is_empty()` skip in `build_session_context`, because the S3 arm's first-file derivation errors with "scan spec has no files" on an empty list and dropping the guard would convert today's silent skip into a hard failure
* *AND* the sequence of values the registration function returns across a whole `build_session_context` call MUST match today's registrations for every spec shape — a single-table scan (one `Some`), a join whose two sides share a bucket (`Some` then `None`), a join whose sides span two buckets (two distinct `Some`), and a join whose dimension file list is empty (one `Some`, no second call) — so the registered `(store URL, store)` set is pinned by an observable value rather than by inspection of the registry
* *AND* the unit test `build_s3_store_applies_spec_connection_budget` SHALL be repointed at the new registration seam rather than deleted, asserting that a spec carrying a non-default `s3_max_connections` still registers a store without error and returns its URL; the budget's arrival at the client remains pinned by `client_options_carry_connection_budget`, which is unedited
* *AND* `validate_uniform_object_store_files` SHALL be unedited, because it keys on `ListingTableUrl::object_store()` rather than on an S3 host and is already backend-agnostic; its derivation and the S3 arm's `Url::host_str()` derivation MUST agree for every `s3://` URI, and unifying the two into one owner is deferred to the slice that adds the second backend rather than done here

### Scenario: The scan-spec wire carries the backend as a tagged variant

* *GIVEN* the shard-invariant common blob, whose `storage` field serializes today as the bare `StorageProps` object `{"endpoint":...,"path_style":true}`
* *WHEN* the common blob is serialized after the refactor
* *THEN* the `storage` value SHALL be an externally-tagged object whose single lowercase key names the backend variant, encoding the S3 backend as `{"s3":{...}}`
* *AND* the tagged payload MUST be byte-identical to today's `StorageProps` encoding — same field names, same field order, same `skip_serializing_if` omissions — so the tag is the ONLY wire difference
* *AND* the enum MUST NOT be declared `#[serde(untagged)]`, because variant selection by trial deserialization would make slice C's credential choice depend on which shape parses first and would replace a field-level parse error with `data did not match any variant`
* *AND* `storage` SHALL remain a top-level field of the common blob and MUST NOT move into or out of it, so it stays shard-invariant and serialized once per fan-out
* *AND* the five committed `dispatch_golden` fixtures that embed a `storage` value, the join golden-SQL full-string assertions, the `common_blob_wire_is_byte_stable` golden, and the scan-spec JSON test fixtures SHALL be updated to the tagged shape, and EVERY byte of each outside its `storage` value MUST be unchanged — that unchanged remainder is this scenario's proof that nothing but the tag moved
* *AND* the existing external-vantage test pinning `StorageProps`' own serde encoding SHALL pass UNEDITED, because the payload's encoding is untouched
* *AND* a scan-spec deserialization failure MUST NOT contain any storage access key, secret key, or session token, on the tagged wire exactly as on the untagged one

### Scenario: S3 behavior is unchanged across the refactor

* *GIVEN* the pre-refactor unit, integration, and S3 E2E suites
* *WHEN* the suites run against the refactored layout
* *THEN* every test MUST pass, and no assertion MUST be weakened, disabled, or deleted to accommodate a type change — a test edit is permitted ONLY to wrap a constructed value in `StorageBackend::S3`, to change a helper's return type, or to update a `storage` value on the wire
* *AND* the catalog request URLs, the header set on each request, the OAuth2 grant request body, and the props map `build_rest_catalog` builds MUST be identical to the pre-refactor shapes for the same query on every auth mode
* *AND* the file list resolved for a given table and the vended-versus-static storage resolved from a given `loadTable` response MUST be field-for-field identical to the pre-refactor output
* *AND* the scan-driving SQL generated for a given pushdown request MUST be byte-identical to the pre-refactor output EXCEPT for the `storage` value's variant tag
* *AND* `make test-e2e` MUST pass against a `.so` built from the refactored source, because the S3 E2E suite is this feature's declared characterization gate and a stale `.so` would make that gate vacuous
* *AND* no storage credential, catalog secret, live bearer token, or vended STS key SHALL appear in any returned SQL string or error message, on any path the refactor touches
