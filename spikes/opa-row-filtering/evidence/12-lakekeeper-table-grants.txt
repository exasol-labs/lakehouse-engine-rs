CONTRAST: the SAME script against the repo's DEFAULT Lakekeeper stack
(docker-compose.lakekeeper.yml alone, authz-backend = "allow-all")
captured earlier in this spike, before the OpenFGA overlay was added:

  GET /management/v1/info -> {"authz-backend":"allow-all"}
  GET|POST /management/v1/permissions/table/{id}/assignments -> HTTP 404
      (the whole /permissions/** tree is absent from its OpenAPI: there is no
       permission model to write grants into)

  orders_public      read_data      oidc~opa-spike-alice       -> {"allowed":true}
  orders_secret      read_data      oidc~opa-spike-alice       -> {"allowed":true}
  orders_public      get_metadata   oidc~opa-spike-alice       -> {"allowed":true}
  orders_public      read_data      oidc~no-such-user-anywhere -> {"allowed":true}
  orders_nonexistent read_data      oidc~opa-spike-alice       -> {"allowed":false}

i.e. allow-all grants everything to everyone, including a user that does not
exist. Only the missing TABLE is denied -- that is object resolution, not
authorization. Same fail-open shape as the Trino row-filters endpoint in
evidence/03. The grant model is NOT part of Lakekeeper's core: it comes from
the OpenFGA backend, so "can OPA enforce a Lakekeeper table grant" is only a
meaningful question on an OpenFGA-backed deployment.
